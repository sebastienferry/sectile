# ADR 0033: Engines are a workstation catalogue

Status: Accepted (#510)

Amends: [ADR 0031](0031-the-workstation-owns-the-invocation.md), the part
that describes the engine (provider, command templates, model, per-skill
models) as fields of the workstation defaults and of each project section.

## Context

ADR 0031 moved every execution setting to `~/.config/sectile/settings.json`,
with two levels: workstation defaults and one section per project. The engine
was five fields at each level, and a project resolved one engine by laying
its section over the defaults, with a rule that drops inherited templates on
a provider change.

#510 asks to hand a task to another CLI without editing the project back and
forth. With engines as fields, a second engine has no place to live, no name
to be shown by, and no identity a task could point at. The clarification
(`docs/clarifications/510.md`, round 2) settled that engines are declared once
per workstation, as full profiles, and picked by projects and tasks.

## Decision

- **An engine is a named, full profile** (provider, model, per-skill models,
  interactive and headless templates) with a stable identifier generated by
  the agent. Engines form an ordered **catalogue** on the workstation; one of
  them is the **workstation default engine**.
- **Projects and tasks point at engines; they do not describe them.** A
  project may pick its default engine, else it uses the workstation default.
  A task may be switched to any engine from the desktop ticket table, else it
  uses its project default. Every launch of a task on the workstation runs its
  engine; the resolution happens on the agent at dispatch, so the server,
  the dispatch contract and the capability report do not change.
- **Nothing is inherited between engines.** A profile resolves on its own,
  then on the provider's defaults. The template-drop rule of ADR 0031
  disappears with the levels it arbitrated.
- **A one-off launch model applies to the project default engine only.** It
  is offered from the capability report, which describes that engine; on any
  other engine it would name a model the CLI does not know.
- **Every catalogue provider is prepared.** Skills and the Sectile MCP
  registration are installed for the provider of every engine, on top of the
  configured extra setup providers.
- **The catalogue lives under a top-level `engines` key**, layout 3, outside
  the keys an agent of layout 2 replaces whole, so a save by an older agent
  does not lose it.
- **The engine fields of layout 2 are converted once, automatically.** Each
  level that stated an engine becomes a catalogue entry equal to what it
  resolved, identical profiles collapse, and a backup of the previous file is
  kept. The conversion is idempotent and runs again if an older agent writes
  engine fields back.

Worktrees, parallelism, terminal, extra setup providers, skill command names,
the model list per provider and the editor keep the levels ADR 0031 gave them:
they do not describe an engine.

## Consequences

- The desktop project settings lose their engine fields and gain a single
  default engine selector; the workstation settings gain an engine editor.
- The per-task choice is per workstation. A task run on another workstation
  follows that workstation's settings, and the web shows the project default
  engine only. The run record stays true through the engine report the agent
  already sends.
- A downgrade to an agent of layout 2 runs the default provider with its
  defaults until the owner reconfigures it. Desktop and agent ship together,
  and the upgrade is the supported direction.
- Sharing engines across a team (#493) can later target the catalogue as a
  whole rather than five fields per level.

## Implementation notes

Found while implementing #510, within the decision above:

- **Converted engines have derived identities.** The conversion runs in memory
  on every read until the agent persists it at start, so an entry it creates
  is identified by a hash of its profile, stable from one read to the next;
  an identity already taken by another profile gets a numbered suffix. An
  engine created from the desktop gets a random identity. The engine a
  workstation stating nothing runs has an identity of its own, so the server
  seed can tell "no statement" from "the default provider, stated".
- **The server seed writes catalogue entries.** The deployment's engine
  becomes the workstation default engine only while the default is that
  unstated engine. A project's engine becomes an entry the project picks,
  found or created, never an edit of an existing entry; a pick the project
  already has is treated as its own statement, which the seed only completes.
- **The one-off model rule is carried by the resolved configuration**
  (`OffProjectDefaultEngine`), whose zero value keeps today's behaviour for a
  configuration built without a task.
- **A task switched back to its project default engine stores no choice**, so
  it follows its project again if the project default engine changes later.
- **Engines are edited inline in the settings panel and every change is saved
  at once**, rather than in a separate dialog: the default then always names
  a stored engine, which the agent requires.
