# Clarification #522 - When running batch

Ticket: https://github.com/sebastienferry/sectile/issues/522 (Bug)

> We lack a visual indicator on all the ticket of the batch on web ux.

## Round 1 (2026-09-26)

### Restatement

When a batch pickup is launched from the web board or list, only the first
ticket of the batch shows that work is in progress; the other tickets of the
batch look idle until (and unless) the agent reaches them. Every ticket of a
running batch must show, in the web UI, that it belongs to a batch that is
running, for as long as that batch runs.

Out of scope: changing how the agent processes the batch (order, single
worktree, combined PR), the batch selection and launch dialog, and the desktop
app, which has no batch launch today.

### What the code does today

Files read:

- `web/src/context/AppContext.tsx` (`startBatchPickup`, `confirmBatchPickup`,
  `runSkill`)
- `web/src/lib/batchPickup.ts`, `web/src/components/BatchPickupModal.tsx`
- `web/src/components/TaskCard.tsx` (`latestActivity`, `isRunning`, `isQueued`)
- `web/src/components/ListView.tsx`, `web/src/components/BoardView.tsx`
- `internal/skills/catalog.go` (`pickup_issues`, `renderPickupSteps`)
- `internal/skills/fragments/contracts/pickup-header.md`,
  `internal/skills/fragments/contracts/transition.md`
- `internal/db/activerun.go` (one active run per task)

Findings:

1. `confirmBatchPickup` calls `runSkill(taskIds[0], 'pickup_issues', prompt)`:
   the server records **one** run, on the first ticket. The other ticket IDs
   exist only inside the prompt text (`buildBatchPickupPrompt`).
2. The server has no notion of batch membership: no column, no table, no
   activity links a member ticket to the lead run.
3. A card lights up (indigo "running", amber "queued") only from an activity
   whose `taskId` is the card's own (`TaskCard.tsx:246-252`, `:387-388`); the
   list rows do the same (`ListView.tsx:462`).
4. The transition contract says "A batch tracks each task separately", so an
   agent may call `start_run` on a member when it reaches it. That lights the
   member up only while it is being processed, and only if the agent does it:
   the tickets waiting their turn and those already done stay unmarked.

### Ambiguities (worst first)

1. **What the indicator says.** A plain "part of a running batch" badge, the
   same running state on every member, or a per-member state (waiting in the
   batch / being processed / done within the batch). Each leads to different
   data and different card code.
2. **Whether batch members are busy.** If members count as having an active
   run, another launch on a member is refused while the batch runs (the
   one-active-run rule of `activerun.go`). If they do not, a user can start a
   second agent on a ticket the batch is about to process.
3. **Which surfaces.** Board cards only, or also list rows and the task detail
   panel; web only, or the desktop task list too.

### Dependencies

- Membership must be persisted server-side: it must survive a page reload and
  be visible to other viewers of the board. That likely means a migration
  (new column or table, added in `migrations.go` only, never in the frozen
  baseline) and the matching rewind/replay test fixtures.
- If members become active runs, `idx_activities_one_active_run` and
  `start_run` reuse must accept the agent's later `start_run` on a member
  without a `TaskBusyError`.

### Technical choices resolved from the code

- Membership is recorded by the server when the batch is launched (the web
  already sends every task ID), not kept in browser state: a client-only
  marker disappears on reload and is invisible to other viewers.
- The indicator ends when the lead batch run ends, whatever its outcome
  (completed, failed, canceled), exactly like a single-ticket run today.
- The indicator reuses the existing card and row styles (indigo running,
  amber queued) rather than a new colour scheme; labels stay in French like
  the rest of the interface.

### Product questions

Asked to the owner in session; see Round 2 for the answers.

1. What does a member ticket show? Recommended: a per-member state, "en
   attente dans le lot" (amber) until the agent reaches it, then "en cours"
   (indigo), plus a small "Lot" badge naming the lead ticket.
2. Are batch members busy while the batch runs? Recommended: yes, another
   launch on a member is refused with a message naming the batch.
3. Which surfaces? Recommended: web board cards, list rows and the task
   detail panel; desktop out of scope.

## Round 2 - answers from the owner (2026-09-26)

The owner answered in session and confirmed the clarification is satisfactory.

### Settled decisions

1. **Per-member state.** While a batch runs, each member ticket other than the
   one being processed shows "en attente dans le lot" in the amber queued
   style; the member the agent is processing shows "en cours" in the indigo
   running style. Every member carries a small "Lot" badge naming the lead
   ticket of the batch.
2. **Finished member.** A member the agent has finished while the batch goes
   on loses the amber or indigo highlight and keeps only the "Lot" badge until
   the batch ends.
3. **Members are busy.** While the batch runs, a launch on any member is
   refused, with a message naming the batch (its lead ticket), consistently
   with the one-active-run rule.
4. **Surfaces.** Web board cards, web list rows and the web task detail panel.
   The desktop app is out of scope.
5. **End of the batch.** Every batch indicator disappears when the lead batch
   run ends, whatever its outcome.

### Reversed assumptions

None. The recommended option was chosen for every question.

### Consequences for the specification

- The server records batch membership at launch and exposes it with the
  activities, so the web derives the member states without parsing prompts.
- The "being processed" and "finished" member states need a signal from the
  agent (its per-task `start_run` / stage transitions, or an explicit member
  status); the specification decides which, and must keep the busy rule from
  refusing the agent's own `start_run` on a member of its batch.
- Persisting membership needs a migration in `migrations.go`, with the
  rewind/replay fixtures updated.

### Open questions

None.
