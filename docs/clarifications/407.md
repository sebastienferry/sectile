## Round 1: analysis (2026-09-24)

### Request restated

Make every invariant that `DB.mu` protects today hold when two server processes share
one PostgreSQL database: each read-check-write or read-modify-write guarded by the
process mutex becomes a conditional update, an append done in SQL, or a row lock
(`SELECT ... FOR UPDATE`) inside a transaction, and the per-project worker limit
becomes a database lock if it must hold across replicas. Out of scope: SQLite
multi-process (refused by #403), the job status guard and cross-replica cancel (#405),
the auto-sync claim and its in-memory pacing (#404), agent and MCP routing (#406,
#408), passphrase-unlocked keys (#409), the integration harness, readiness probe and
ADRs of the whole macro (#410).

### First-pass inventory of `DB.mu`

The ticket says 127 sections; `main` at `8171915` has **137** (the count grew with
#403's `instances.go`). Classified:

| Class | Count | Meaning |
|---|---|---|
| READ | 56 | read only |
| SINGLE | 51 | one statement, or statements whose correctness does not depend on the mutex |
| RMW | 16 | read a value, modify it in Go, write it back (lost update) |
| RCW | 11 | read, decide in Go, write (double apply) |
| MEM | 3 | also guards in-process memory (the `unlocked` key map) |

No code uses `FOR UPDATE` or `SKIP LOCKED` today; `pg_advisory_lock` only guards
migrations. Conditional updates with a `RowsAffected` check already exist and are the
model to follow (`finishRemoteRun`, `SetRemoteRunWaiting`, `heartbeatInstance`).

Most dangerous across two processes, worst first:

1. **Lost pull-request links.** `pr_links` is rewritten whole from a snapshot in
   `TransitionTaskStageBy` (snapshot read at `stage.go:30` without the lock),
   `applyDiscoveredPullRequests`, `applyPullRequestStates`, `adjustmentPrerequisite`,
   `PostBackTask` and `updateTaskBy`.
2. **Double stage transition.** `TransitionTaskStageBy` checks
   `managedStageRunningUnsafe` under the mutex but outside its transaction, and the
   `UPDATE tasks` has no condition on the current stage. Same shape in `MoveTask`,
   `MoveTaskToTrackerStatus`, `PostBackTask`.
3. **Lost appends.** `AppendRemoteRunOutput` (`output = current + chunk` in Go),
   `appendActivityStep` (steps JSON), `finishTrackerOp` (steps JSON). Only
   `appendToRunSummary` already appends in SQL.
4. **Duplicate activities.** `enqueueSkillOnTask`, `EnqueueFullChainRun`,
   `startRemoteRun`, `EnqueueSyncWith` insert without an in-lock "already active"
   check; the launch handler checks `ActiveRunOnTask` with no lock at all.
5. **Duplicate remote issue.** `ConvertTaskToRemote` creates the tracker issue outside
   any lock, then overwrites key and source.
6. **Key collisions.** `CreateTaskAs` computes the local key and position as `MAX+1`,
   and holds `d.mu` across the remote `CreateIssue` HTTP call. `UNIQUE(project_id, key)`
   turns a collision into an error, not a duplicate.
7. **Lost field edits.** `UpdateProjectAs`, `UpdateSettings`, `saveMacroMetaFull`,
   `UpdateUserSettings`, `UpdateBoardView` merge a whole row read earlier. The
   single-default-project rule spans several statements without a transaction in
   `CreateProjectAs`, `UpdateProjectAs`, `DeleteProject`.
8. **Double toggles.** `ToggleProjectBookmark`, `ToggleTaskPinnedBy`: two concurrent
   toggles cancel out.

`SyncRemoteRunStatusFor` (named in the ticket) is less severe than it looks: the
primary key makes a racing insert fail rather than duplicate; the real gap is that
its `UPDATE` has no status condition, so a late `running` can reopen a run another
replica just finished.

Other process-local state, outside `DB.mu`: `ProjectLimiter` (one server-side worker
per project, `db.go:3945`), `cancelMap` (#405), `autoSync.mu` (#404),
`unlockedKeys` (#409), `postBackListeners` (#405).

The full per-section table is the ticket's deliverable ("documented audit result"),
produced by the implementation from this first pass.

### Ambiguities, worst first

**A1: What "no double stage transition" means (open, Q1).** Two readings, different
code: (a) *serialize*: two concurrent transitions both apply, one after the other, on
a locked row, each recomputing labels and links from the locked state, so nothing is
lost but both are recorded and both push a tracker operation; (b) *compare and set*:
the transition is conditional on the stage the caller observed, and the loser gets a
conflict error. Today a transition to the stage the task already holds is accepted and
used to attach a follow-up pull request or post a note, which (b) would have to keep
working.

**A2: Breadth (open, Q2).** The ticket names three sections "and others found". Either
every RMW/RCW of the inventory is converted, or only those protecting a workflow
invariant (links, stages, appends, active runs, remote issues), leaving whole-row form
merges and toggles as documented last-writer-wins.

**A3: Cross-replica worker limit (open, Q3).** `ProjectLimiter` allows one server-side
job (synchronization, tracker field update, queued skill) per project at a time. With
N replicas it becomes N. Whether that must stay 1 decides between a database lock and
keeping the in-process limiter.

**A4: Check-then-act outside `DB.mu` (open, Q4).** The launch busy check
(`ActiveRunOnTask` then dispatch) and `enqueueSkillOnTask` hold no lock between the
check and the insert, so they are racy even on one process. Whether they belong to
this ticket.

### Resolved technical decisions (reversible, settled here)

- **D1: `DB.mu` stays.** It remains the in-process serializer (SQLite has one writer,
  and it guards the in-memory maps). What changes is that no invariant depends on it
  any more: every guarded sequence is correct on its own across processes. The
  "never take `d.mu` from a credential resolver" rule stays.
- **D2: Preference order for a conversion.** (1) do the work in one SQL statement
  (`output = output || ?`, `steps` appended in SQL, `CASE` for the truncation marker);
  (2) a conditional `UPDATE ... WHERE <expected state>` with a `RowsAffected` check;
  (3) a transaction with `SELECT ... FOR UPDATE` on the row, the check moved inside
  it. An `INSERT ... ON CONFLICT` or a unique constraint counts as already safe.
- **D3: Dialect hook for row locks.** A `dialect` method appends ` FOR UPDATE` on
  PostgreSQL and nothing on SQLite, where `DB.mu` plus SQLite's single writer already
  serialize.
- **D4: No row lock across a tracker HTTP call.** `CreateTaskAs` releases the lock
  before the remote call; `ConvertTaskToRemote` claims the task first with a
  conditional update (for example `source` from `local` to a converting marker), and
  a second replica's claim fails before any issue is created.
- **D5: `SyncRemoteRunStatusFor`** refuses to move a terminal run back to `running` or
  `queued` (conditional `UPDATE`); terminal-to-terminal stays allowed, since an owner
  may still report a run the server closed as canceled (ADR 0007, #307 amendment).
- **D6: Tests.** Each converted invariant gets a test opening two `*DB` handles on the
  same PostgreSQL DSN (two instance ids), racing N goroutines, and asserting the
  invariant (all chunks present, one transition, all links present). They reuse
  `openPostgres` and skip without the DSN, like the existing smoke tests.
- **D7: CI.** The Go job gains a PostgreSQL service and sets
  `SECTILE_TEST_POSTGRES_DSN`, so the acceptance tests run in the pipeline. The DSN
  points at a throwaway database: the suite truncates what it names.
- **D8: The audit lives in `docs/`** (`docs/db-concurrency-audit.md`): one row per
  section, its class, and what was done (converted, safe as is, covered by #404/#405,
  accepted). #410's ADR references it.
- **D9: No `CHANGELOG.md` line.** Nothing changes for a single-instance deployment;
  the multi-replica capability is announced by #410.

### Open product questions

**Q1: Concurrent stage transitions.** (a) serialize on a row lock, both apply, nothing
lost; (b) compare and set, the second gets a conflict error.
Recommendation: **(a)**, with the running-stage check moved inside the transaction.
It keeps today's accepted repeat transitions (follow-up PR, note), and "double" then
means "a transition that bypasses the running-stage guard or loses a write", which
(a) prevents.

**Q2: Breadth.** (a) every RMW/RCW of the inventory (except toggles); (b) only the
workflow invariants, form merges documented as last-writer-wins.
Recommendation: **(a)**: the form merges lose a field the other person did not touch,
which does not happen on one process today, and the fix is the same mechanical
transaction-plus-row-lock. Toggles are converted to explicit set/unset on the server
side only if cheap; otherwise documented.

**Q3: One server-side worker per project across replicas?**
Recommendation: **yes**, through a per-project PostgreSQL advisory lock held on a
dedicated connection for the job's duration, acquired with `pg_try_advisory_lock`
and a short retry, so a waiting job does not pin a pool connection. Two concurrent
synchronizations of one project would otherwise race `ImportOrUpdateTasks` and double
the tracker rate usage. SQLite keeps the in-process limiter.

**Q4: The launch busy check and `enqueueSkillOnTask` in scope?**
Recommendation: **yes**: "one active run per task" is the same class of invariant,
and an insert conditional on no active run (row lock on the task) closes it on one
process and across replicas.

## Round 2 - answers from the owner (2026-09-24)

Asked interactively in session; the owner accepted every recommendation.

### Settled product decisions

- **Q1 → serialize.** Concurrent stage transitions on one task both apply, one after
  the other, on a row lock (`SELECT ... FOR UPDATE` through the D3 dialect hook). Each
  recomputes labels and pull-request links from the locked row, and the running-stage
  guard (`managedStageRunningUnsafe`) moves inside the transaction. Repeat transitions
  to the current stage (follow-up pull request, note) stay accepted. "No double stage
  transition" in the acceptance criterion therefore means: no transition bypasses the
  running-stage guard, and no concurrent transition loses a write.
- **Q2 → every RMW/RCW of the inventory.** Form merges (`UpdateProjectAs`,
  `UpdateSettings`, `saveMacroMetaFull`, `UpdateUserSettings`, `UpdateBoardView`) and
  the single-default-project rule (`CreateProjectAs`, `UpdateProjectAs`,
  `DeleteProject`) are converted too. Toggles (`ToggleProjectBookmark`,
  `ToggleTaskPinnedBy`) become an atomic SQL flip or an explicit set/unset when cheap;
  otherwise they are listed in the audit as accepted.
- **Q3 → one server-side worker per project across replicas.** On PostgreSQL,
  `ProjectLimiter` is backed by a per-project `pg_try_advisory_lock`, held on a
  dedicated connection for the job's duration, with a short retry so a waiting job
  does not pin a pool connection. The lock key space must not collide with
  `migrationLockKey` (`dialect_postgres.go`). SQLite keeps the in-process limiter.
- **Q4 → in scope.** The launch busy check (`ActiveRunOnTask` in the handler) and
  `enqueueSkillOnTask` / `EnqueueFullChainRun` / `startRemoteRun` insert their
  activity only if no active run exists, checked under a row lock on the task in the
  same transaction. This also closes the race that exists today on one process.

## Round 3 - answers from the owner (2026-09-24)

The owner asked whether the locks are needed at all, or whether PostgreSQL can hold
the invariants by itself. Answered in session; the owner chose the partial unique
index for Q4. The stage stays `clarified`: these are reversible technical choices
that refine Round 2, not new product scope.

### What PostgreSQL already guarantees (no explicit lock)

A single `UPDATE` takes an implicit row lock. Under `READ COMMITTED` (the default,
and what the code uses today: no `BeginTx` sets an isolation level on `main`), a
concurrent `UPDATE` on the same row waits, then re-evaluates its `WHERE` against the
committed version. This covers the appends (`output = output || ?`, steps), the
toggles (`pinned = NOT pinned`) and the status guards (`WHERE status NOT IN
(<terminal>)`, D5). This is D2 preference (1) and applies to most of the inventory.

### Settled choices

- **R3-1: Q4 is enforced by a partial unique index, replacing the row-lock check of
  Round 2.** A partial unique index on `task_activities (task_id)` whose predicate
  selects the "active run" rows makes the database refuse a second active run on a
  task, on SQLite and PostgreSQL alike (both support partial indexes). The losing
  insert fails with a unique violation, which the launch path and
  `enqueueSkillOnTask` / `EnqueueFullChainRun` / `startRemoteRun` map to the existing
  "task busy" answer. No code path can bypass it.
  Conditions the specification must settle:
  - **Predicate.** `ActiveRunOnTask` (`skillresult.go:33-38`) counts only `running`,
    ignores `queued`, and excludes the agent-launch rows by matching the `action`
    text. The index predicate must state which statuses count as active (at least
    `queued` and `running`, plus `waiting` if it exists as a status) and must not
    depend on localized `action` text: the specification either normalizes the run
    kind (a column or a fixed `skill_id` set) or proves the predicate is stable.
    `ActiveRunOnTask` is aligned on the same predicate.
  - **Legitimate concurrency.** Verify that no chain (`pickup` and its stages, a
    `tracker_op` next to a `remote_run`) keeps two rows matching the predicate at
    once; rows that may coexist are excluded from the predicate.
  - **Existing data.** The migration first resolves tasks that already hold two
    active runs (closing the extra ones as `canceled` with an explanatory summary),
    then creates the index, so it cannot fail on an existing database. It is a new
    numbered migration in `migrations.go`, never an edit of the baseline.
- **R3-2: `SELECT ... FOR UPDATE` is kept for the read-decide-write sites** (stage
  transition with its label and `pr_links` recomputation, form merges, the
  single-default-project rule), rather than `SERIALIZABLE` or `REPEATABLE READ`.
  Those isolation levels would let PostgreSQL detect the conflict itself, but abort
  one transaction with SQLSTATE `40001`: every affected transaction would need a
  retry loop, concurrent transitions on one task would fail and replay instead of
  waiting, and the SQLite drivers reject non-default levels, so a dialect hook is
  needed anyway. Replacing a row lock by a single SQL statement (for example a JSON
  merge of `pr_links`) stays preferred wherever the dialects allow it (D2).
- **R3-3: the advisory lock of Q3 stands.** It is PostgreSQL's native mechanism, not
  an application lock. The alternative, a lease column (`claimed_by`, `lease_until`,
  like #404's claim), needs a heartbeat and an expiry, whereas an advisory lock is
  released by the server when the holding connection dies.

### Reversed assumption

- Round 2's Q4 mechanism ("checked under a row lock on the task in the same
  transaction") is replaced by R3-1. The scope decision itself (Q4 in scope) is
  unchanged.

### Status

Round 3 complete. No open product question; the stage remains `clarified`.
