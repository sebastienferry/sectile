## Round 1 (2026-09-25)

### Restated request and scope

Work that nobody asked for (the background synchronisation of a project) must
authenticate with exactly one server credential per provider
(`SECTILE_GITHUB_TOKEN`, `SECTILE_JIRA_TOKEN`, `SECTILE_GITLAB_TOKEN`), stored
in the database, set by an admin from the admin page, with the matching
environment variable as fallback; the generic `SECTILE_TRACKER_TOKEN` and the
providers' own variables (`GH_TOKEN`, `GITHUB_TOKEN`, `JIRA_API_TOKEN`,
`GITLAB_TOKEN`) leave the resolution, and the sync stops borrowing the
project owner's personal token.
Out of scope: the personal credentials of ADR 0014 themselves (storage,
sealing, profile screen), the tracker URLs and project keys (they are not
credentials), agent/desktop tokens (`SECTILE_AGENT_TOKEN`,
`SECTILE_DESKTOP_TOKEN`), and the orphaned-credential report of ADR 0020.

### Verified findings

Files read: `internal/trackerapi/client.go`, `internal/trackerapi/jira.go`
(`forProject`), `internal/trackerapi/adapters.go`, `internal/db/trackercredentials.go`,
`internal/db/autosync.go`, `internal/db/prstates.go`, `internal/db/db.go`
(tracker wiring, project columns), `internal/handlers/handlers.go`
(`HandleTrackerSetup`, settings update), `internal/handlers/authz.go`
(`trackerSettingsKeys`, `deploymentSettingsPayload`, `requireAdmin`),
`internal/handlers/usercredentials.go`, `internal/secrets/secrets.go`,
`web/src/components/AdminView.tsx`, `.env.sample`,
`docs/adrs/0014-personal-tracker-credentials-are-sealed.md`,
`docs/adrs/0020-an-ownerless-tracker-credential-is-reported-not-repaired.md`.

- **A database-stored server credential already exists.** The shared settings
  row carries `github_token`, `gitlab_token`, `jira_api_token` and
  `jira_email` (plus the URLs and GitLab project). `trackerCredentials`
  resolves project override → settings row → environment, so the database
  already wins over the environment, and `withoutTrackerTokens` already
  answers `…TokenSet` / `…TokenFromEnv` flags so a client can say "provided by
  the environment". The ticket is therefore mostly a change of *who may write*
  it, *where* it is edited, *what else* is consulted, and *when* it is used -
  not a new storage.
- **These tokens are stored in clear text.** Only the personal credentials go
  through `secrets.Seal` (`internal/db/usercredentials.go`).
- **Members can write them today.** `trackerSettingsKeys` lets a non-admin
  write `githubToken`, `gitlabToken`, `jiraApiToken`, `jiraEmail`, and
  `POST /api/setup/tracker` (`HandleTrackerSetup`) has no admin check. The
  admin page (`AdminView.tsx`) currently shows stats and users only.
- **Per-project overrides exist** for `github_token` and `gitlab_token` (and
  the API URLs); Jira only overrides the site URL, the e-mail and token stay
  global.
- **Environment chain** (`trackerToken`): specific variable →
  `SECTILE_TRACKER_TOKEN` → provider conventions. `SECTILE_JIRA_EMAIL` is read
  separately.
- **Owner borrowing**: `autosync.go` enqueues each pass with
  `EnqueueSyncWith(proj.OwnerUserID, …)`; that user id becomes the acting user,
  so `ForActingUser` substitutes the owner's personal token. A manual "Sync"
  click enqueues under the clicking user the same way.
- **Jira already refuses** a write for a named user without a personal token
  (`jira.go` `forProject`): "the work would be attributed to the server
  account". GitHub and GitLab do not refuse: a user without a personal token
  silently falls back to the server token.
- `missingCredential` tells the reader to add a token in *Profile*, which is
  wrong advice for an unattended sync.

### Ambiguities (worst first)

1. **Which calls use the server credential.** "Every project sync task" can
   mean the timer pass only, or also a sync a user triggers by hand, or also
   user-triggered writes (transitions, comments). Each reading touches a
   different set of call sites (`autosync.go` only, `EnqueueSyncWith` callers,
   or every `ForActingUser`). → Product question Q1.
2. **Fate of the per-project `github_token` / `gitlab_token`.** Keeping them
   contradicts "one credential per provider, nothing else"; dropping them
   removes the only way to point one project at a second instance (GitHub
   Enterprise, a second self-hosted GitLab). → Q2.
3. **Who may write the server credential.** The ticket says admin; today a
   member may, as part of pointing a project at its tracker. Making it
   admin-only changes the member's project setup flow. → Q3.
4. **Encryption at rest.** → Q4.
5. **Removed variables at startup: warn or refuse.** Reversible; resolved
   below as an assumption the owner may overturn.

### Critical dependencies

- **Schema**: moving the tokens out of the settings row, or sealing them in
  place, is a numbered migration (`internal/db/migrations.go`, never the
  frozen baseline). Existing clear-text values must be carried over, not lost.
- **Server key**: sealing with `SECTILE_SECRET_KEY` makes the credentials
  unreadable if the key changes or is lost (PostgreSQL: the environment is the
  only source of the key). The sync must then fail with an explicit error.
- **Multi-replica**: the credential is read per call from the database, so a
  change made on one replica is seen by the others without restart; nothing
  may cache it at startup.
- **Clients**: web (`AdminView`, `ProjectModal`, tracker setup,
  `web/src/lib/trackers.ts`) and desktop setup screens that currently post
  `githubToken` / `jiraApiToken` as a member.
- **Breaking change**: removing `SECTILE_TRACKER_TOKEN` and the provider
  conventions. Pre-1.0, so it takes the MINOR slot at release.

### Technical choices resolved from the code

- **Jira service identity**: Jira Cloud authenticates with `email:token`, so
  the Jira server credential is the pair `SECTILE_JIRA_EMAIL` +
  `SECTILE_JIRA_TOKEN` (settings `jiraEmail` + `jiraApiToken`), set and
  cleared together. GitHub and GitLab need no identifier.
- **Attribution**: a tracker attributes a write to the account behind the
  token; Sectile cannot change that. Unattended writes are attributed to the
  account that owns the server credential. The admin page shows that account
  (the existing `CheckTrackerCredentials` answer) next to each credential.
- **Precedence**: database first, environment only when the database holds
  nothing: the existing behaviour. The admin page keeps the
  "provided by the environment" indication through the existing `FromEnv`
  flags. Clearing the database value falls back to the environment.
- **Not sealable**: no passphrase; the server must use it unattended.
- **Write-only**: the token never travels back to a client (existing
  `keptToken` / clear-sentinel rule).
- **Error on absence**: a sync with no credential for its provider fails with
  a message naming the environment variable and the admin page; the
  `Profile` advice stays for user-triggered writes only.
- **Provider isolation**: each provider reads its own variable only, so the
  cross-provider leak described in the ticket disappears with
  `SECTILE_TRACKER_TOKEN`.
- **ADR**: a new ADR supersedes the unattended-work part of ADR 0014 and the
  owner fallback it implies, and records the server-credential rules; it is
  written at the specification stage.
- **Assumption - removed variables**: the server starts, and logs one warning
  per removed variable that is still set, naming its replacement. Refusing to
  start would take a deployment down for a variable whose absence already
  produces an explicit sync error.

### Product questions (recommended option first)

- **Q1: Scope.** Recommended: the server credential serves every sync pass,
  the timer's *and* one a user triggers by hand (both read the whole project,
  nobody's name belongs on them); user-triggered writes (transitions,
  comments, assignments) stay personal under ADR 0014, and GitHub/GitLab keep
  today's fallback to the server credential when the user has none.
  Alternatives: timer only; or every call, personal tokens removed from
  writes as well.
- **Q2: Per-project token overrides.** Recommended: drop `github_token` and
  `gitlab_token` from projects (migration keeps nothing), accepting one
  instance per provider per deployment. Alternative: keep them as admin-only
  overrides for projects on another instance.
- **Q3: Who writes the server credential.** Recommended: admin only, from the
  admin page; a member keeps setting the repository, project key and URL of a
  project, and the token fields disappear from the member setup screens.
  Alternative: keep the member write path alongside the admin page.
- **Q4: Encryption at rest.** Recommended: seal each server credential with
  the server key (`SECTILE_SECRET_KEY`, binding = provider), no passphrase;
  existing clear-text values are sealed by the migration.
  Alternative: keep clear text, as the settings row does today.

### Draft acceptance criteria (pending answers)

- With no credential for its provider, a project's sync fails with an explicit
  error naming the variable to set and the admin page.
- A GitHub credential is never sent to Jira or GitLab, and none of those is
  sent to another provider; `SECTILE_TRACKER_TOKEN`, `GH_TOKEN`,
  `GITHUB_TOKEN`, `JIRA_API_TOKEN` and `GITLAB_TOKEN` are no longer read.
- The sync no longer uses the project owner's personal token.
- An admin can set, replace and clear each credential (Jira: e-mail and token)
  from the admin page and sees the account it authenticates as and whether the
  value comes from the environment; a non-admin can neither read nor write it.
- A removed variable still set at startup produces a warning naming its
  replacement.
- `README.md`, `.env.sample` and `CHANGELOG.md` (`Removed` / `Changed`) are
  updated; a new ADR records the decision.

## Round 2 - answers from the owner (2026-09-25)

Answers given interactively in the session. Every recommendation of round 1
was accepted; no prior assumption is reversed.

### Settled decisions

- **Q1, scope**: the server credential serves every sync pass, the timer's
  and one a user triggers by hand. `EnqueueSyncWith` no longer carries the
  owner's or the clicking user's id into the tracker resolution of a sync.
  User-triggered writes (transitions, comments, assignments) stay personal
  under ADR 0014; Jira keeps refusing them without a personal token, GitHub
  and GitLab keep today's fallback to the server credential.
- **Q2, per-project overrides**: the `github_token` and `gitlab_token`
  columns of `projects` are dropped by a numbered migration, which keeps no
  value. One instance per provider per deployment is accepted. The per-project
  URL overrides are left as they are (they are not credentials); a project
  pointing at another instance then fails with the provider's own refusal.
- **Q3, write access**: admin only. `githubToken`, `gitlabToken`,
  `jiraApiToken` and `jiraEmail` leave `trackerSettingsKeys`; the token part
  of `POST /api/setup/tracker` requires an admin. A member keeps writing the
  repository, project key and URL of a project; the token fields leave the
  member setup screens (web and desktop). The admin page gains the server
  credentials section.
- **Q4, encryption**: each server credential is sealed with the server key
  (`SECTILE_SECRET_KEY`, binding = provider), without passphrase. The
  migration seals the clear-text values already stored. A credential that
  cannot be opened (key changed or lost) makes the sync fail with an explicit
  error naming the admin page.

### Carried-over assumption

- A removed variable still set at startup produces one warning naming its
  replacement; the server does not refuse to start.

None.
