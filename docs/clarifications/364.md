## Round 1 (2026-09-22)

### Restated request and scope

When a project's code lives on GitLab, the server-side PR evidence check that gates `specified` (specify-owned PR), `implemented` and `reviewed` must find the branch's merge request and apply the same evidence rules it applies to a GitHub pull request, instead of failing with `configure an explicit GitHub owner/repository`. GitHub projects keep their current behaviour; the GitLab *tracker* adapter and the GitLab settings (#251), GitLab PR creation, and any change to the evidence rules themselves are out of scope.

- `internal/db/adjustment.go` — `validateStagePR`, `validatePullRequestEvidence`, `adjustmentPrerequisite`, `adjustmentCheckout`, `lookupStagePR` (hard-wired to `trackerAs(userID, "github", projectID).BranchPullRequest`).

### Verified findings

- Every server-side evidence check funnels through one function, `lookupStagePR`, which only ever asks GitHub. Its three callers are the MCP/HTTP stage transition, the agent post-back, and the adjust launch prerequisite; fixing `lookupStagePR` fixes all three.
- `validateStagePR` already needs a connected agent (`git_evidence`), so asking the agent for the MR adds no new runtime dependency for GitLab projects.
- The agent's `Runner.BranchPullRequest` is close to what is needed but diverges from the GitHub server rules in two ways:
  1. `glab mr list` returns **open MRs only** by default, so a merged MR is never found. After the human merge, `reviewed` would be refused on GitLab while GitHub accepts it.
  2. With several open MRs on the branch it returns the **first** one, where the GitHub server path refuses them as ambiguous.
- Refusal messages in `validatePullRequestEvidence` / `validateStagePR` say "PR" and "forge"; the GitHub lookup errors say "GitHub". None names a GitLab merge request.
- `adjustmentCheckout` prefers `GithubRepo` over `GitRemoteUrl`, so a project with a stale `GithubRepo` and a GitLab remote would still be routed to GitHub.

### Ambiguities (worst first)

1. **Several open MRs on the same source branch.** Pick one (current agent behaviour) or refuse as ambiguous (GitHub server behaviour). Different code and different acceptance. → product question Q1.
2. **Merged MR after the human merge.** Keep the agent's open-only listing, or also list merged MRs. → resolved: list merged MRs too (D4), because the ticket asks for "the same evidence rules as for GitHub" and GitHub accepts a merged PR.
3. **Forge selection when `GithubRepo` and a GitLab remote disagree.** → resolved: the code remote wins (D2), as the ticket states.
4. **Where the lookup runs** (agent operation vs. a `trackerapi` GitLab client). → resolved: agent (D1).

### Critical dependencies

- A connected local agent with `glab` installed and authenticated on the GitLab host (already the case wherever `OpenBranchMergeRequestURL` works). No migration, no new setting.
- #251 may remove the stored `gitlab_url` / `gitlab_token`; the chosen route does not use them.
- Agent and server must be upgraded together: an older agent does not know the new operation, which must surface as a lookup failure, not as "no MR".

### Resolved technical decisions (reversible, from code and conventions)

- **D1 — Lookup on the agent.** Add an agent operation next to `git_evidence` (e.g. `pr_evidence`) that runs `Runner.BranchPullRequest` on the same resolved checkout and returns `URL`, `Branch`, `SHA`, `Open`, `Draft`, `Merged`, and the forge that answered. `lookupStagePR` calls it for GitLab remotes. No `trackerapi` GitLab client is added.
- **D2 — Forge from the code remote.** GitHub (current server path, unchanged) when the project's remote is a GitHub remote, or when there is no remote and `GithubRepo` is set; otherwise the agent operation. The issue tracker (Jira, GitHub, GitLab) plays no part. A self-managed GitLab whose hostname lacks "gitlab" still works because the agent already tries both CLIs.
- **D3 — Same evidence rules.** `validatePullRequestEvidence` and the `git_evidence` SHA/branch/clean checks are reused unchanged: open or merged, same source branch, head SHA equal to the checkout, draft accepted except where readiness is required (`adjust`, `pickup`), `prUrl` when given must equal the MR `web_url`, `AcceptPullRequest` on recorded links. The MR URL is then recorded as the task PR exactly like a GitHub PR URL.
- **D4 — Merged MRs are evidence.** The GitLab listing includes merged MRs (`glab mr list --source-branch <b> --all`, or an equivalent merged query); closed-unmerged MRs are ignored; with no open MR, the latest merged one wins — mirroring `Client.BranchPullRequest`.
- **D5 — Forge-aware messages.** Refusals say "merge request" / "GitLab" for a GitLab lookup and keep today's wording for GitHub. User-facing wording stays in the language the surface already speaks.
- **D6 — Failure is never absence.** Agent not connected, unknown operation (old agent), `glab` missing, not authenticated, timeout or network error → an error stating the MR lookup failed and why. Only a successful listing without a matching MR yields "no matching merge request".
- **D7 — Tests.** Existing `prEvidenceLookup` hook covers the GitLab evidence rules (open / draft / merged / other branch / stale head / lookup failure) with forge-aware messages; a forge-selection unit test covers a Jira project on a GitLab remote (and a `GithubRepo` + GitLab remote conflict); a runner test covers `parsePullRequestEvidence` for merged and multi-MR GitLab output. GitHub tests stay green unchanged.

### Product questions

- **Q1 — Several open MRs on the task branch.** Recommended: **refuse as ambiguous**, like the GitHub path, and apply the same rule to the agent's own adjust pre-check (`agent.go`) so both sides agree. Alternative: accept the most recently created open MR.
- **Q2 — Confirmation.** Is this clarification (scope, D1–D7) satisfactory to move to specification?

## Round 2 - answers from the owner (2026-09-22)

### Settled choices

- **Q1 — Several open MRs on the task branch: refuse as ambiguous.** Stage validation refuses, with a message naming the merge requests, when more than one open MR exists on the task's source branch, mirroring `Client.BranchPullRequest` on GitHub. The agent's own adjust pre-check (`Runner.BranchPullRequest` used from `internal/agent/agent.go`) applies the same rule, so the server and the agent never disagree about which MR is the task's.
- **Q2 — Clarification confirmed.** Scope and decisions D1–D7 from Round 1 are accepted as the specification baseline.

### Reversed assumptions

None. Round 1 recommendations were all accepted.

### Final settled scope

- In scope: GitLab-hosted code (any issue tracker) passes the `specified` (specify-owned PR) / `implemented` / `reviewed` evidence checks, the agent post-back check and the adjust launch prerequisite through an agent-side MR lookup (D1), forge chosen from the code remote (D2), same evidence rules (D3), merged MRs accepted (D4), forge-aware messages (D5), lookup failure never reported as absence (D6), ambiguity refused (Q1), tests per D7.
- Out of scope: the GitLab tracker adapter and GitLab settings (#251), MR creation, a `trackerapi` GitLab client, any change to GitHub behaviour.
