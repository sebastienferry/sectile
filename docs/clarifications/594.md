# Clarification #594 - Desktop safe default

- Ticket: https://github.com/sebastienferry/sectile/issues/594
- Branch: `feat/594`
- Report: `docs/clarifications/594.md` (committed)

## Round 1 - initial report (2026-09-28)

### Request

When neither the project section nor the workstation defaults of the desktop
settings state a number of parallel executions, a project runs up to 5
executions at a time instead of 1. Out of scope: the upper bound (stays 10),
the rule that a project without worktrees runs one execution at a time, and
any value a user has already set explicitly.

### What the code does today

- `internal/agentconfig/local.go` `ExecutionLimit`: project section, else
  workstation defaults, else **1**; clamped to 1..`MaxParallelism` (10); always
  1 when `useWorktrees` is false. Every consumer (queue in `agent_run.go`,
  consoles in `agent_console.go`, `agent_desktop.go`, the desktop settings view
  in `agent_desktop_settings.go`) goes through this function.
- The settings file stores `0` for "not set" (`workstation.go`), so an unset
  value and an explicit `1` are distinguishable on disk.
- `desktop/src/main.js`: the workstation panel shows `parallelism||1` and the
  hint "1 execution" as the default (around line 1425); the project panel
  falls back to `||1` (around line 2164) but otherwise displays the inherited
  value the agent computes.
- `docs/contracts/server-agent-v1.md` line 80 documents "else 1".
- Nothing on the server or the web side stores or reads parallelism (#305).

### Ambiguities (worst first)

1. **Who gets the new default.** Changing the fallback of `ExecutionLimit`
   moves every existing workstation that never touched the setting from 1 to
   5 executions on upgrade. The alternative, writing `5` into the defaults only
   for new installs, keeps today's behaviour for existing users. Different code
   and a different changelog line.
2. **Desktop only or the agent as a whole.** The ticket says "in Desktop app",
   but the limit is enforced by the local agent, which also runs without the
   desktop (headless `sectile-agent`). A desktop-only default would require the
   desktop to write the value; a fallback change in Go applies to both.

### Dependencies

- No migration: the value is unset (`0`) in the file, and only the fallback
  changes. No server or contract version bump; the contract document is
  updated in prose.
- Desktop UI tests reading "1 execution" as the default hint will need
  updating (they load `dist/index.html`, a `vite build` comes first).

### Technical choices settled from the code

- The fallback lives in one place, `agentconfig.ExecutionLimit`, and the
  desktop reads the effective value from the agent rather than hardcoding 5;
  the desktop fallbacks `||1` become the new default only where no value from
  the agent is available.
- A constant `DefaultParallelism = 5` next to `MaxParallelism`, mirrored in
  `desktop/src/main.js` like `MAX_PARALLELISM`.
- Without worktrees the limit stays 1 (shared checkout, cannot run two
  executions).
- `CHANGELOG.md` gets one line under `Changed` (user-visible).

### Open product questions

1. **Existing workstations**: should a workstation that never set the value
   move from 1 to 5 on upgrade? *Recommended: yes* - change the fallback; an
   explicit value, including 1, is kept. The changelog says so.
2. **Scope**: does the default apply to the headless agent too, not only to
   the desktop app? *Recommended: yes* - one fallback in the agent, so the two
   never disagree about what an unset value means.

## Round 2 - answers from the owner (2026-09-28)

Answers given interactively by the owner, both on the recommended option. No
product question remains open; the clarification is settled.

### Settled decisions

1. **Existing workstations move to 5.** The fallback of
   `agentconfig.ExecutionLimit` becomes 5: any workstation whose project
   section and defaults leave parallelism unset (`0` on disk) runs up to 5
   executions after the upgrade. An explicit value, including 1, is kept. The
   `CHANGELOG.md` line under `Changed` says so, so a user who wants one
   execution at a time knows to set 1.
2. **The whole agent, not only the desktop.** The default lives in the Go
   agent, so the desktop app and a headless `sectile-agent` agree on what an
   unset value means. The desktop mirrors the constant only for its display
   fallbacks.

No prior assumption is reversed.

### Settled scope

- `internal/agentconfig/local.go`: `DefaultParallelism = 5` next to
  `MaxParallelism`; `ExecutionLimit` falls back to it when both the project
  section and the defaults are unset. Values below 1 stored explicitly (the
  out-of-range `-1` written for an explicit zero) keep being rejected by
  validation, as today.
- Without worktrees the limit stays 1.
- `desktop/src/main.js`: `DEFAULT_PARALLELISM=5` mirrored beside
  `MAX_PARALLELISM`; the workstation panel shows 5 and the hint "5 executions"
  as the default; the project panel fallback `||1` becomes the constant.
- `docs/contracts/server-agent-v1.md`: "else 1" becomes "else 5".
- Tests: `TestExecutionLimitInheritance` covers the unset case at 5; desktop
  UI tests asserting the "1 execution" default are updated.
- `CHANGELOG.md`: one line under `Changed` in `[Unreleased]`.

### Acceptance criteria

- A workstation with no parallelism in its defaults nor in the project section
  runs up to 5 executions of a project that uses worktrees, the sixth queues.
- A project without worktrees still runs one execution at a time.
- An explicit value (1 to 10) in the defaults or the project section wins over
  the new default.
- The desktop workstation panel shows 5 as the default value and hint; the
  project panel shows the inherited 5.
- The contract document and the changelog state the new default.
