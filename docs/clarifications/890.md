### Restated request and scope

When a run starts (a skill launched on a ticket, or a conversation), the person can name an earlier run by its ID. Sectile gives the new run what that earlier run did as context, so the new agent picks up its findings instead of starting from scratch.

Out of scope: resuming or continuing the earlier run itself (it stays finished), changing how runs are recorded or kept, chaining stages automatically (the full chain already does that), and sharing a transcript across workstations through the server.

### Files read

- `internal/handlers/handlers.go` (2476-2560): `POST /api/tasks/{id}/run-skill`. `withComments` (or `--with-comments` in the prompt) appends the ticket's comments to the prompt. This is the closest precedent for injecting context.
- `internal/models/models.go`: `RunSkillRequest` (1371-1395) and `TaskActivity` (47-): a run's server record holds `prompt`, `summary`, `output` (chunks posted by the agent), `steps`, `error`, the engine, and the `finish_run` note.
- `internal/db/remoterun.go` (20-90): `RunLaunch`, what the launcher records on a run.
- `internal/db/activityattachment.go`: the `task_activities` schema.
- `internal/agent/run_store.go` (1-90): the full console and trace of a run are kept **only on the workstation that ran it** (#588), at most 100 finished runs, "as a courtesy" (a write can fail).
- `internal/agent/agent_trace.go`, `internal/agent/agent_conversation.go` (22-80, 507, 628): conversation transcripts are in-memory traces stored in the run store. Claude conversations carry a provider `session_id` and resume with `--resume`. Codex uses `thread/resume`.
- `internal/agent/agent_headless.go` (340-380): `postRunOutput` sends only some chunks (notices, errors) to the server, not the reasoning trace.
- `internal/agent/agent_config.go` (739): the prompt and model end up on a command line run through `sh -c`.

### Ambiguities, worst first

1. **What "context" means.** There are three readings, and each one leads to different code:
   - (a) **The server record**: prompt, summary, final note, posted output and steps. Readable everywhere, but thin: it does not hold what the agent actually reasoned or read.
   - (b) **The full transcript** from the workstation's run store. Rich, but present only on the device that ran it, for its last 100 runs.
   - (c) **The provider's native session** (`claude --resume <session> --fork-session`, Codex `thread/resume`). Highest fidelity, but tied to one provider, to the workstation, and to the working directory where the session was created (a removed worktree loses it). A Codex run cannot feed a Claude run.

   *Product question Q1.*
2. **Where the person names the earlier run.** Possible places: the launch dialog (desktop and web), an action on a finished run ("Use as context for a new run"), a conversation's composer, or an agent calling Sectile's MCP. Each is a different UI or API surface. *Product question Q2.*
3. **Which runs are eligible.** Readings: only runs of the same ticket; any run of the same project (an investigation on #A reused for #B); macro and project runs included. *Product question Q3.*
4. **One run or several.** One ID, or a list. *Product question Q4.*

### Critical dependencies

- **Prompt size on the command line.** The prompt goes through `sh -c` (and on Windows through a command line limited to about 32,000 characters). Pasting a full transcript into the prompt, the way `withComments` does with comments, would break on any long run. Context has to go through a file or an MCP read, not inline (D2).
- **Run store locality** (readings b and c): a run launched on workstation B cannot read a transcript kept on workstation A. The server holds no copy. Making it hold one would be a storage and privacy change of its own (out of scope).
- **Schema**: recording which run served as context on the new run needs a column on `task_activities`. Because of the table-rebuild pattern (`taskActivitiesSchema`), that is a migration on SQLite and PostgreSQL.
- **Permissions**: a run belongs to a user (`UserID`). Reading another person's run as context must follow the same visibility rules as the run list (D4).

### Reversible technical choices, settled

- **D1. Identifier:** the run's activity ID (the UUID shown in the desktop and web run views, `SECTILE_RUN_ID`). It is checked on the server: an unknown ID, or one the launcher cannot see, refuses the launch before anything is recorded, like the busy rule.
- **D2. Transport:** never inline in the command line. The launch carries `contextRunId`. The agent writes the context to a file in the run's private state directory and points the prompt at it ("Context from run <id>: read <path> before starting"). The same content is also readable through a new MCP tool `get_run(runId)`, which agents launched outside Sectile can call too.
- **D3. Traceability:** the new activity records `context_run_id`. The run views show "Context: run <short id> (<skill>, <ticket>)" with a link to the earlier run.
- **D4. Visibility:** a run is eligible when the launcher can already see it in the run list (same project, own runs or runs visible to project members). Nothing new is exposed.
- **D5. Size bound:** the context is capped (for example the final note and summary in full, then the transcript tail up to a fixed budget). A truncation marker says what was cut.
- **D6. Tests:** Go tests for launch validation (unknown, invisible or ineligible ID refused), for the recorded `context_run_id`, and for `get_run`. An agent test for writing the context file and the fallback when the run store holds nothing. Plus a desktop or web test for the chosen entry point.

### Product questions

- **Q1. What content should the earlier run hand over?**
  Recommended: **(b) its full transcript when the target workstation still holds it in its run store, otherwise (a) its server record**, with the context saying which one it got. (c) native session resume is left out: it ties the feature to one provider and one working directory, and could be a follow-up ticket.
- **Q2. Where does the person name the earlier run?** (several possible)
  Recommended: **an action on a finished run, "New run with this context"**, which opens the usual launch dialog with the field prefilled. Also **an optional "Context run" field in the launch dialog** (desktop and web), listing the ticket's recent runs, and **the MCP parameter** for agents. The conversation composer is left out of this ticket.
- **Q3. Which runs can serve as context?**
  Recommended: **any task run of the same project that the launcher can see**, on the same ticket or another one. Macro and project runs are excluded for now.
- **Q4. One run or several?**
  Recommended: **one.** Several runs would multiply the size problem (D5) and complicate the dialog. It can be extended later without breaking the API if the field becomes a list.
