# Clarification #588 - Store the state of tasks between agent restart

Ticket: https://github.com/sebastienferry/sectile/issues/588
Branch: `feat/588`

## Round 1 - initial report (2026-09-28)

### Request

The executions the desktop lists, and what their consoles showed, must still be
there after the local agent restarts: a person who restarts or updates the agent
finds the same consoles in the sidebar, with the conversation each one held and
the result it reached, instead of an empty list. The running processes
themselves are not preserved: an execution that was live when the agent went
down is not reattached or kept alive, and the task's workflow stage, which the
server already stores, is not what this ticket is about.

Out of scope: keeping engine processes alive across a restart, reattaching a
PTY, the web board, and moving any console content to the server.

### What exists today (files read)

- `docs/adrs/0003-local-desktop-consoles.md`: "A daemon restart loses sessions
  and the in-memory run index. Console replay is bounded by the existing PTY
  history buffer." This ticket reverses the first half of that sentence.
- `docs/adrs/0016-the-trace-of-an-autonomous-run-stays-on-the-workstation.md`:
  the headless trace lives in agent memory, bounded at 2000 lines, "forgotten
  with the run".
- `internal/agent/agent_run.go`: `runQueue.runs map[string]*controlledRun` is
  the only run index; nothing is written to disk.
- `internal/agent/agent_desktop.go`: `desktopRun` (the record the desktop
  lists: task, skill, directory, branch, status, engine, timestamps, prompt);
  `POST /desktop/restart` is refused while any run has not exited, so a restart
  from the desktop only ever loses finished runs; `DELETE /desktop/history`
  clears finished runs; `GET /desktop/run-result` serves the skill result.
- `internal/terminal/terminal.go`: each PTY session keeps a 64 KiB `history`
  replayed to a viewer on attach; it lives and dies with the session.
- `internal/agent/agent.go`: the restart path re-executes the binary; nothing
  is handed over to the new process.
- `desktop/src/main.js`: the sidebar, the per-task execution history selector,
  archive and rename (kept in the renderer's `localStorage`, so they already
  survive), "Clear finished consoles", and `refreshSkillResult`, which already
  expects a `null` result "once the history is cleared or the agent restarted".
- `desktop/src/run-console.mjs`: which runs attach to a console, which show a
  notice, and which attach read-only (the headless trace).
- `internal/agent/agent_desktop.go` `finishDesktopRun`: the server only receives
  a status and a note; interactive console output never leaves the workstation,
  so the server cannot be the fallback for what the console showed.

### Ambiguities (worst first)

1. **Which consoles.** The ticket says "the discussion". Either the `discuss`
   skill only, or every execution the sidebar lists (interactive skill runs,
   headless runs with their trace, macro runs, free consoles). The two lead to
   different persistence scopes. Product question Q1.
2. **Read-only replay or a conversation that can continue.** "The current
   progress" can mean seeing what was said, or picking the conversation up where
   it stopped. The second needs the engine's own session identifier and a resume
   command line (`claude --resume <id>` for Claude, unknown for the other
   engines), which is a different feature. Product question Q2.
3. **Retention.** Today the history is bounded by the process lifetime. On disk
   it needs its own bound. Product question Q3.
4. **Where it is stored.** On the workstation (the agent's state directory) or on
   the server (visible from the web and other machines, with a table and a
   migration). ADR 0016 chose the workstation for the trace. Product question Q4.
5. **Runs live when the agent died.** A desktop restart is refused while runs
   are active, but a crash, a `SIGTERM`, a machine reboot or an update can still
   kill live runs. Resolved below (D4).

### Critical dependencies

- An ADR amending ADR 0003 (run index lost on restart) and ADR 0016 (trace
  forgotten with the run).
- No server change and no migration under the recommended options.
- Console scrollback can contain whatever the engine printed, secrets included:
  the store must be private to the user (see D3).
- The desktop and the agent are versioned apart: a desktop talking to an older
  agent keeps today's behaviour, and a newer agent must not break an older
  desktop.

### Technical choices resolved from the code (reversible)

- **D1. The agent owns the store**, not the Electron renderer: the agent holds
  the run index, the PTY history and the trace, and the desktop can be closed
  while the agent keeps running (ADR 0003).
- **D2. What is stored per run**: the `desktopRun` record, the PTY history
  bytes (already bounded at 64 KiB) or the trace lines (already bounded at 2000),
  and the skill result served by `/desktop/run-result`.
- **D3. Location and permissions**: one directory under the agent's state
  directory (`~/.taskflow/`, next to `agent-connection.json`), one file per run,
  directory `0700` and files `0600`, written atomically (temp file + rename).
- **D4. Runs interrupted by the agent's death** are restored as `canceled`,
  with the history they had at the last write, and their console shows it
  read-only. The history is written when a run finishes and periodically while
  it runs, so a crash loses at most a few seconds. Queued and preparing runs are
  not restored: they had not started, and the server already closes their
  activity.
- **D5. A restored run attaches read-only** on the same
  `/desktop/terminal?id=<runId>` route, as the headless trace already does
  (`readOnlyConsole`); no PTY is spawned for it. The run record carries a flag
  the desktop reads; an older desktop without it sees a finished run with no
  session, i.e. today's notice.
- **D6. Clearing stays the user's gesture**: "Clear finished consoles" also
  deletes the stored files, and "Relaunch" keeps working on a restored run
  since it only needs the task and the skill.
- **D7. Archive and local names** already survive in `localStorage`; nothing
  changes for them.

### Product questions (with recommendation)

- **Q1. Which consoles survive?** Recommended: every finished execution the
  sidebar lists (skill runs, headless runs with their trace, macro runs,
  discussions, free consoles). Alternative: `discuss` runs only.
- **Q2. Read-only replay, or continue the conversation?** Recommended:
  read-only replay in this ticket, plus a follow-up ticket for "continue this
  conversation" through the engine's resume option. Alternative: include resume
  now, for Claude only.
- **Q3. Retention.** Recommended: kept until the user clears or the run is
  removed by "Clear finished consoles", with a cap of the 100 most recent
  finished runs (about 6.5 MiB at worst), oldest dropped first. Alternatives: a
  time limit (e.g. 30 days), or no cap.
- **Q4. Storage location.** Recommended: the workstation only, as ADR 0016
  decided for the trace. Alternative: the server, visible from the web.
