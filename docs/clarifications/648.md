# Clarification #648 - report_waiting rejects a macro run

- Ticket: https://github.com/sebastienferry/sectile/issues/648
- Branch: `feat/batch-393-497-498-584-647-648` (batch of #393, #497, #498, #584, #647, #648)
- Report: `docs/clarifications/648.md` (committed on the batch branch)

## Round 1 - initial analysis (2026-10-01)

### Request

`report_waiting` only accepts `taskKey`. A macro run, started with
`projectId` + `macroKey`, has no task, so the call fails with "remote run not
found or no longer running" although the run is open, and the board never
shows the run waiting on its user. `report_waiting` accepts the macro form,
like `start_run` and `finish_run`, and its error tells a wrong key from a
closed run.

Out of scope: how a task run's wait is shown (unchanged), the re-initialized
session (#498), and the macro todos (#647).

### Code read

- `internal/taskmcp/server.go`: `reportWaitingInput` (`taskKey`, `runId`,
  `waiting`), `runTarget`, the `start_run` / `finish_run` handlers that already
  branch on it.
- `internal/db/remoterun.go`: `ReportSessionRunWaitingAs` resolves the task
  and requires `existing.TaskID == task.ID`, which a macro run (empty task id)
  never satisfies; `setRemoteRunWaiting` itself only needs the run id;
  `notifyWaitChange` returns early when the run has no task, so even a mark on
  a macro run would reach no listener.
- `internal/db/macroruns.go`: `FinishMacroRunAs`, the ownership and matching
  rule to mirror; `macroRuns` does not select `waiting_since`.
- `web/src/lib/macroRuns.ts`, `web/src/components/MacroRealignButton.tsx`,
  `web/src/lib/remoteRunIndicator.ts`, `web/src/components/RemoteRunBadge.tsx`:
  task runs show the waiting glyph, macro runs show only "running".
- `internal/mcptest/contract.go`: the contract test calls `report_waiting`
  with a task run.

### Ambiguities

None that needs the owner. The ticket offers two forms (macro target, or the
run id alone); the macro target is the one consistent with the two sibling
tools.

### Technical choices settled here (reversible)

- **Input.** `report_waiting` takes `taskKey`, or `projectId` + `macroKey`,
  checked by `runTarget` like its siblings. `runId` stays required.
- **Macro path.** `ReportMacroRunWaitingAs` matches the run on project, empty
  task and macro key, under the same ownership rule and the same headless
  exception as a task run, then calls `setRemoteRunWaiting`.
- **Errors.** Three distinct answers on both paths: "no run with this id",
  "run <id> is not attached to <task or macro>", and "run <id> is no longer
  running (<status>)".
- **Display.** `notifyWaitChange` relays a macro run's change too, the macro
  run list returns `waitingSince`, and the macro's run indicator in the web
  shows the same waiting state a task card shows. The desktop already reads
  the waiting state from the run itself.
- **Tests.** DB tests for the macro mark, set and clear, ownership, headless
  run and the three errors; an MCP test that starts a macro run, reports
  waiting, then sees it cleared by the session's next call; a web unit test
  for the macro indicator.
- **Changelog.** One `Fixed` line.

None.
