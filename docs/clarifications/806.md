# Clarification #806 - Desktop project board

Ticket: https://github.com/sebastienferry/sectile/issues/806

## Round 1 - initial report (2026-10-09)

### Request

Give Sectile Desktop a project board: a full page that shows a project's tasks
in the six workflow columns (new, clarified, specified, implemented, reviewed,
finished), with the display options the web board already offers: the finished
column hidden by default, the macro (epic) colour bar when the project enables
it, and a toggle between the full card and the condensed one-line card.

Out of scope: the web board itself, the web's "Statuts" grouping by tracker
columns, the optional web views (triage, roadmap, timeline), multi-project
boards, batch pickup selection, quick-add from a column, and any change to how
the server stores tasks or stages.

### Ambiguities (worst first)

1. **Where the board lives and how it relates to the "Open tasks" list.** A
   new page beside the list, a list/board toggle inside the tickets pane, or a
   board that replaces the list lead to different entry points and code. (Q1)
2. **What a card does when dragged.** The web moves the stage on drop (it
   rewrites the `#stage` label and the tracker status, without launching a
   skill). Desktop could do the same, launch the next skill, or not support
   drag at all. (Q2)
3. **"Finished hidden by default" diverges from the web**, whose `hideDone`
   defaults to `false`. Whether the web default changes too is a product call.
   (Q3)
4. Which column a card lands in: Desktop's `taskStage` only reads labels and
   the internal status, while the web also reads the project's tracker
   column to stage mapping. Settled below (D3).
5. Whether the options are remembered per project or once for every project.
   Settled below (D5).

### Critical dependencies

- **Agent payload.** Desktop reaches the server only through the local agent
  (`connect-src 'none'`). `/desktop/project` must expose the project's
  `epicColors`, and its tracker column to stage mapping (`stageColumns` /
  `trackerColumns`), which the agent can already read from
  `/api/projects/:id`. Older agents will not send them: the board must degrade
  (no colour bar, label-only stages) rather than fail.
- **Finished tasks.** The tickets pane asks for `launchable=true`, which drops
  finished tasks. The board asks without it so the finished column can show
  its count and cards.
- **No migration, no new server endpoint.** Everything the board reads already
  exists on the server.

### Decisions settled from the code (reversible)

- **D1. Workflow view only.** The ticket names "the agentic workflow view";
  the web's tracker-status grouping is not ported.
- **D2. Same columns, order and colours as the web.** The six stages of
  `STAGES`, tinted with Desktop's existing `--stage-<stage>-bg` variables so
  the board matches the sidebar keys of #688, in light and dark themes.
- **D3. Same stage resolution as the web.** Desktop's `taskStage` gains the
  tracker column to stage step of the web's `resolveTaskStage`, so a task sits
  in the same column on both boards. The sidebar grouping of #688 uses the
  same function and benefits from it.
- **D4. Same macro colour as the web.** The bar is drawn from `parentKey` with
  the same hash and palette, so a macro keeps its colour across clients. The
  hash and palette move to `shared/` (Desktop already imports
  `shared/runStates.ts`) instead of being copied. Shown only when the
  project's `epicColors` is on.
- **D5. Options stored in Desktop's localStorage, once for all projects**, as
  the web does: finished hidden (default **hidden**), card display (default
  **condensed**, as the web). Independent from the web's settings, which live
  in the browser.
- **D6. Hidden finished column collapses to a narrow strip with its count**,
  as on the web; clicking it shows the column again.
- **D7. Card content.** Condensed: key, title, run state badge, actions menu.
  Full: adds parent/macro key, priority, labels, pull request link and
  assignee. The card actions reuse the tickets pane's menu (run the next
  skill, other skills, discussion, custom instructions, launch), so no new
  launch path is written.
- **D8. Order within a column** follows `task-list-order.mjs` (priority
  descending by default). The page carries the same search field as the
  tickets pane and refreshes as it does (on open and when a run finishes).
- **D9. Changelog.** User-visible: one `Added` line under `[Unreleased]`.

### Product questions

**Q1. Where does the board open, and what happens to the "Open tasks" list?**
- (a) **Recommended:** a new full page, "Open board", next to "Open tasks" in
  the project `…` menu and the command palette. The list stays as it is.
- (b) A list/board toggle inside the existing tickets pane, remembered.
- (c) The board replaces the list.

**Q2. Can a card be dragged to another column?**
- (a) **Recommended:** no drag and drop in this ticket. Cards act through their
  menu, as the list rows do; drag can follow in its own ticket.
- (b) Drag moves the stage as on the web (label and tracker status rewritten,
  no skill launched).
- (c) Drag onto the next column launches that column's skill.

**Q3. Should the web's finished column also become hidden by default?**
- (a) **Recommended:** no, Desktop only. The web keeps its default and every
  saved preference.
- (b) Yes, both clients hide it by default (the web only for users who never
  toggled it).
