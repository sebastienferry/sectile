# Clarification #906: Start a new conversation or skill using an archived conversation as context

## Round 1 (2026-11-15)

Report: `docs/clarifications/906.md` on `feat/906` (ticket [#906](https://github.com/sebastienferry/sectile/issues/906)), committed.

### Restated request and scope

From an archived conversation in Sectile Desktop (Tauri), the user can press **Start over**, choose between a fresh conversation and a skill, type new instructions, and start a new, distinct conversation or skill execution that receives the archived conversation's saved messages as background context. The archived conversation stays archived and byte-for-byte unchanged, and every failure (no history, agent disconnected, launch refused, history truncated) is shown rather than silently starting without context.

Out of scope: restoring or resuming the archived conversation itself, the legacy Electron client (`desktop/`) and the web client (neither has conversation archiving), cross-workstation access to a conversation journal held by another agent, and any change to how archiving is stored.

### Files read

- `desktop-tauri/src/App.tsx`: archived conversation IDs are a desktop-local preference (`archivedConversations` in `readPreference`/`savePreference`), the sidebar toggle "View archived conversations", `setArchived`, routing to the `prompt` view.
- `desktop-tauri/src/components/ProjectPrompt.tsx`: new-prompt composer (`createConversation` then `conversationFor(id).send`), engine/profile selection, the conversation header with its skill launch menu (only when `run.taskId` is set), the archive button.
- `desktop-tauri/src/components/Supervisor.tsx`: archive filter in the executions view.
- `desktop-tauri/src/components/WorkflowTask.tsx`: conversations opened from a ticket.
- `desktop-tauri/src/lib/conversation.ts`, `desktop-tauri/src/lib/conversation-controller.ts`: Tauri commands, the Go agent owns history and execution.
- `desktop-tauri/src/domain/execution.ts`: `launchInput`, `canLaunchTask` (one active run per ticket).
- `desktop-tauri/src-tauri/src/agent.rs`: `create_conversation` (`POST /desktop/consoles`), `launch_task` (`POST /desktop/tasks`, `LaunchTask` with `deny_unknown_fields`, 8 KB body limit, `task_id` required).
- `internal/agent/agent_desktop.go`: `/desktop/tasks` handler (8 KB `MaxBytesReader`, `taskId` required, task read from the API), `/desktop/consoles`, `/desktop/conversation`.
- `internal/agent/conversation_journal.go`: conversation history is a per-run journal of normalized display events (limit 4 MB) held by the local agent's run store.

### Ambiguities, worst first

1. **Which skill, on which ticket.** Every skill launch is bound to a ticket (`taskId` is required at the Tauri and Go layers, and the skill menu only shows when the conversation has `run.taskId`). A free conversation has no ticket. Reading A: the skill path is offered only when the archived conversation is linked to a ticket, and runs on that ticket. Reading B: the user also picks a ticket in the Start over dialog. B adds a ticket picker and cross-ticket eligibility checks.
2. **What "saved messages" means.** The journal holds user messages, assistant text, tool calls with inputs and outputs, notices and approvals. Passing everything inflates the context with tool noise; passing only user/assistant text loses what tools found. The two lead to different context builders and different sizes.
3. **Truncation policy.** History can reach 4 MB; provider context windows are smaller. Keeping the most recent messages versus the earliest ones, and where the budget sits, changes what the new session knows and what the user is told.
4. **Engine of the new session.** The archived conversation ran on Claude Code or Codex. Forcing the same engine is simpler; letting the user pick another one is possible because the context is plain text.
5. **Visible link between source and new session.** The new conversation can show "Started from <title>" pointing back to the archived source, or carry nothing. A back-link needs a stored source reference on the new run (never on the source).

### Critical dependencies

- **Launch body limit.** `/desktop/tasks` and the Tauri `launch_body` reject bodies over 8 KB, and the composer limits a prompt to 32,000 characters: the history cannot travel inside the launch request. The agent must read it from its own run store by reference.
- **Journal locality.** The history lives in the local agent's run store. In Fleet mode a conversation listed from another workstation has no local journal: that case must surface as "history unavailable", never as a launch without context.
- **Archive is client-side.** Archiving is a desktop preference, not server state, so "the source stays archived" is guaranteed as long as Start over never touches that preference or the source journal.
- **`LaunchTask` uses `deny_unknown_fields`.** Any new field (source reference) must be added to the Rust struct, its validation and the Go input struct together.

### Reversible technical choices (settled from the code)

- Pass the archived conversation by reference: an optional `contextRunId` on `create_conversation`/`POST /desktop/consoles` and on `launch_task`/`POST /desktop/tasks`. The agent validates that the source exists locally, belongs to the same project, is a conversation, and has at least one message; otherwise it refuses the launch with an explicit error.
- The agent builds the context block itself from the journal, clearly delimited as former context (not instructions), and prepends it to the first message of a new conversation or to the skill's launch prompt. The user's new instructions follow it.
- The source run and its journal are only read. The new run gets a fresh ID; the archived preference list is not modified.
- The skill path goes through the existing `/desktop/tasks` handler, so eligibility, project configuration, provider readiness and the one-active-run-per-ticket check (`canLaunchTask`) apply unchanged.
- After a successful start, Desktop navigates to the new conversation (`prompt` view), or to the new execution for a skill launched in terminal view.
- Start over is disabled with an explanation while the agent is unavailable or the history is still loading.
- Tests: Go tests on context building (filtering, truncation, empty/missing source, source journal unchanged), Rust validation tests for the new field, and frontend tests for both start paths and the disabled/error states.

### Product questions for the owner

1. **Skill path and tickets.** Should the skill option be offered only when the archived conversation is linked to a ticket, running on that same ticket (free conversations then offer only a new conversation)?
   *(Recommended: yes, same ticket only for now; a ticket picker can come later.)*
2. **Content of the former context.** Should the context contain only the user and assistant messages, with tool calls and outputs left out (and a one-line mention that they were omitted)?
   *(Recommended: yes, user and assistant text only.)*
3. **Truncation.** When the history exceeds the context budget, keep the most recent messages, and tell the user how many earlier messages were dropped, both in the Start over dialog before launching and at the top of the new session?
   *(Recommended: yes, keep the most recent messages, fixed budget of about 100,000 characters, notice in both places.)*
4. **Engine choice.** Can the user pick a different engine or profile (Claude Code or Codex) for the new session, defaulting to the archived conversation's engine?
   *(Recommended: yes, same picker as the new-prompt composer, defaulting to the source engine.)*
5. **Back-link.** Should the new conversation or execution show "Started from <archived conversation title>", opening the archived source read-only?
   *(Recommended: yes.)*
6. **Where the action appears.** Only on archived conversations, as the ticket says, or also on finished, non-archived ones?
   *(Recommended: archived only, as written; widening it is a separate ticket.)*

## Round 2 - answers from the owner (2026-11-15)

Answers given interactively by the owner. Every recommendation of Round 1 is accepted; no prior assumption is reversed, and no new ambiguity or dependency surfaced. Zero product questions remain open.

### Settled decisions

1. **Skill path and tickets.** The skill option of Start over appears only when the archived conversation is linked to a ticket, and the skill runs on that same ticket. A free conversation offers only a new conversation. A ticket picker is out of scope.
2. **Content of the former context.** Only user and assistant text messages from the archived conversation's journal. Tool calls, tool inputs and outputs, notices and approvals are left out, and the context block says in one line that they were omitted.
3. **Truncation.** When the history exceeds a budget of about 100,000 characters, the most recent messages are kept. The number of earlier messages dropped is shown in the Start over dialog before launching and at the top of the new conversation or execution.
4. **Engine choice.** The Start over dialog offers the same engine/profile picker as the new-prompt composer, defaulting to the archived conversation's engine. For the skill path, the existing skill launch options apply.
5. **Back-link.** The new conversation or execution shows "Started from <archived conversation title>", which opens the archived source read-only. The source reference is stored on the new run only, never on the source.
6. **Placement.** Start over appears only on archived conversations. Offering it on finished, non-archived conversations is a separate ticket.

### Updated acceptance criteria

- [ ] An archived conversation exposes Start over; a non-archived one does not.
- [ ] A new conversation receives the former context (user/assistant text only) followed by the user's new instructions, on the engine/profile chosen in the dialog (default: the source's).
- [ ] An archived conversation linked to a ticket can start an eligible skill on that ticket with the former context; a free conversation offers no skill option.
- [ ] Existing skill eligibility, project configuration, provider readiness and one-active-run-per-ticket checks still apply.
- [ ] The archived source stays archived and its journal is unchanged.
- [ ] The new session shows "Started from <title>" linking to the source.
- [ ] A history over ~100,000 characters keeps the most recent messages, and the dropped count is shown before launch and in the new session.
- [ ] Loading, agent disconnected, empty or locally unavailable history, and failed launch are each shown explicitly; nothing starts without the requested context.
- [ ] Go, Rust and frontend tests cover both start paths, truncation, the failure states and source preservation.
- [ ] User documentation and `CHANGELOG.md` (`Added`) describe the feature.
