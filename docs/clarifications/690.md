# Clarification #690 - "Discussion in native terminal" from the tickets pane opens a bare shell

## Round 1 (2026-10-02)

Batch `pickup-issues` #675, #690, #693, branch `feat/batch-675-690-693`.

### Request

In Sectile Desktop, "Discussion in native terminal" from the tickets pane opens
a shell in a native terminal window with no engine running in it. It should
start the same ticket discussion as "Discussion (no skill)" (the task's
configured engine, `--add-dir` for the project's folders, `SECTILE_REPOSITORIES`
and the project's Claude Code sandbox settings), in a native terminal attached
to the agent's console for that run.

Out of scope: the conversation view (a native terminal is a terminal by
construction), the "Detach to native terminal" action of a running console,
which already works, the web interface, and the other launches of the menu.

### Ambiguities, worst first

1. **Where the fix lives.** In the agent's `desktopTasksTerminalExternal`, or
   in Desktop by launching an in-app discussion and detaching it. The second
   breaks when the owner chose the conversation view for Claude consoles (a
   conversation has no PTY to detach) and opens a window in the app first.
   Settled: the agent.
2. **Which engine.** The task's engine, as the in-app discussion uses it
   (`agentconfig.ResolveTask` with the workstation overrides), not the
   project's raw configuration the handler reads today.

### Critical dependencies

- Agent only: Desktop and the server are unchanged. The fix reaches users with
  an agent upgrade, which Desktop ships.
- `CREATE_NO_WINDOW` does not apply: this is the native terminal a user asked
  to see, already launched through `launchExternalTerminal`.

### Technical choices settled here (reversible)

- `desktopTasksTerminalExternal` resolves the configuration with
  `agentconfig.ResolveTask(config, overrides, task.ID)`, builds the folder map
  with `taskFolderMap`, the Claude settings with `launchClaudeSettings`, and the
  line with `dispatchCommand(config, task.ID, "discuss", "", "", "", "", "",
  agentCommandContext{...})`, exactly as the dispatch path does.
- The line is wrapped with `wrapRun` so the run ends when the engine exits, as
  an in-app discussion does; the run is registered as `preparing` for that, then
  moved to `running` once the line is typed.
- `SECTILE_REPOSITORIES` joins the environment when the map is not empty, and
  the run records `discussionProvider`, so "Add folder" can type `/add-dir` into
  it.
- `runInPty` replaces the bare `GetOrCreateSession`, so the console is tapped
  and its answers watched like any other interactive run. A failure to build or
  type the line releases the run and answers an error, as a PTY failure does
  today.
- Tests in `internal/agent`: the existing test asserts the typed line names the
  engine and carries `--add-dir` for an attached folder, and the session
  environment carries `SECTILE_REPOSITORIES`; a shell stub replaces the engine
  so nothing real starts (memory: `shellArguments` runs the line).
- `CHANGELOG.md`: one `Fixed` line.
