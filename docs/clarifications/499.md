## Round 1 (2026-09-26)

### Restated request and scope

A run that a launcher created and handed to a session through its runId must
be adoptable with `start_run` while it shows `queued`, and closable with
`finish_run`, so the board shows it running and records its outcome. The
agent's own queue and admission logic, and the session ownership rules
(a launcher run is not adopted by the session), are out of scope.

### Verified findings

- The launcher records the run as `running` (`StartAgentRun`,
  `internal/handlers/handlers.go` dispatch path). The agent reports its own view
  of the run on every task pull (`ApplyAgentRunningTasksFor` →
  `SyncRemoteRunStatusFor`), and while the run waits for a slot the agent calls it
  `queued` (`internal/agent/agent_run.go`, `enqueueRunLocked`). That report
  moves the record back to `queued`, and nothing moves it forward again unless a
  later pull happens while the agent sees it running.
- `startRemoteRun` (`internal/db/remoterun.go`) accepts a supplied runId only when
  the record is `running`. A `queued` one is refused with "remote run does not
  match an active execution on this task", which is what #475 met.
- `finishRemoteRun` closes only `status='running'` (plus the owner's rewrite of a
  disconnect cancellation), so the same `queued` run answered "remote run not
  found or already finished with another status".
- The macro twin (`internal/db/macroruns.go`) has the same two checks.

### Ambiguities

1. **Should `finish_run` also close a run still `queued`** (a session that
   skipped `start_run`, or an agent pull that re-queued it after adoption)?
   Resolved: yes. The caller holds the runId, and the owner check of
   `FinishRemoteRunAs` still applies. Refusing only loses the outcome.
2. **Should an agent report of `queued` demote a run a session adopted?**
   Resolved: once a session has adopted it, a run is running, and a `queued`
   report no longer moves it back. The agent's report of `running` or of an end
   is unchanged.
3. **Macro runs.** Resolved: the same rule, since `start_run` and `finish_run`
   take both paths and the refusal is identical.

### Resolved technical decisions

- Adoption turns `queued` into `running`, sets `started_at` when it was cleared,
  and returns the run. A run that has already ended, or belongs to another task,
  is still refused, with an error that says which case applies and what to do
  (start a new run without a runId, or report through the launcher).
- `finish_run` closes a run that is `running` or `queued`.
- `SyncRemoteRunStatusFor` no longer moves `running` back to `queued`. A run
  the agent really queued is inserted or kept as `queued` as before.

### Critical dependencies

None: no migration, no protocol change, no agent release.

### Questions

None. The acceptance criteria fix the behaviour; the three points above are
reversible technical readings of them.

### Settled scope

- `internal/db/remoterun.go` and `internal/db/macroruns.go`: adoption, closing and
  no demotion.
- Tests: queued → running → completed through `start_run` and `finish_run` with the
  launcher runId, the refusal messages, and a `queued` report after adoption.
- `CHANGELOG.md`: one `Fixed` line (the board now shows these runs and their
  outcome).
