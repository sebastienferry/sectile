# Clarification Report - #821

## Round 1 - 2026-10-12

### Request and scope

When a sprint is closed from the Timeline, the user picks which sprint receives its unfinished work items, among the project's open sprints, instead of being limited to "the next sprint", the backlog, or keeping them in the closed sprint. Creating a new sprint from the close dialog, changing how a sprint is reopened, and giving GitHub projects (read-only sprints, no close button) a close action are outside the proposed scope.

### Code evidence

Files actually read: AGENTS.md; web/src/components/SprintTimelineView.tsx (close handlers and close dialog); web/src/lib/sprints.ts (sprintManagementOf, sprintTarget, nextSprintAfter); web/src/lib/sprintApi.ts; web/src/locales/sprints.ts (close strings); internal/models/models.go (SprintPatch); internal/db/sprints.go (UpdateProjectSprint, moveOpenWork, nextSprint).

- The close dialog offers three destinations for unfinished work: `next`, `backlog`, `keep`. The `next` option is only shown when there is a following sprint, and is labelled "Move to {name} (recommended)".
- Two code paths close a sprint, chosen by `sprintManagementOf`:
  - **tracker** (Jira): the client sends `PATCH sprint {state: closed, moveOpenTo: next|backlog}`. The server (`moveOpenWork`) resolves "next" itself with `nextSprint` (earliest non-closed sprint starting at or after the closing one, by start date), calls `ts.SetSprint` on the tracker, then relinks the local rows, and only then closes the sprint. `keep` sends no `moveOpenTo`.
  - **local** board: the client moves unfinished tasks with `setTasksSprint` to `sprints[index + 1]`, then saves the sprint list with the closed state.
  - **readonly** (GitHub): no close button.
- `moveOpenTo` only accepts `next` or `backlog`; anything else is refused with "destination invalide". It is used by the web client only (no MCP tool, no other caller).
- Existing inconsistency: on a Jira project the dialog names `sprints[index + 1]` as the "next" sprint and as the sprint to activate, while the handler and the server use `nextSprintAfter` / `nextSprint` (by start date). Since a batch created later is appended at the end of the list, the dialog can name one sprint and the server move the work into another.
- The "Start {next} automatically" checkbox activates the next sprint (by date on Jira, by index locally) when it is `future`.
- `internal/db/sprints_test.go` covers `moveOpenTo` on the server side.
- Reference behaviour: Jira's own "Complete sprint" dialog lets the user move open issues to the backlog, to any future sprint, or to a new sprint.

### Ambiguities (worst first)

1. **Which sprints can be chosen.** Only `future` sprints, or also another `active` sprint (Jira parallel sprints, or the local board where several can be active)? A closed sprint is never a valid target: Jira refuses to move issues into one.
2. **What the "start automatically" checkbox applies to** once the target is free: the chosen target sprint, or still the next sprint by date whatever the target.
3. **Whether the three-option layout stays**: a sprint picker replacing the "Move to {next}" option (backlog and keep unchanged), or a single dropdown listing backlog, sprints and keep.

### Critical dependencies

- No migration, no new tracker capability: `SetSprint` already moves work items to any sprint id; only the destination resolution changes.
- The API contract `SprintPatch.moveOpenTo` changes; its only client is the web app of the same release, so no compatibility shim is needed beyond keeping `next` and `backlog` accepted.

### Reversible technical choices (settled from the code)

- **API**: add a sprint id to the close patch (`moveOpenTo: "sprint"` with `moveOpenToSprint: <id>`, or an id accepted in place of `next`; the specification picks one). `next` and `backlog` keep working. The server validates the target: it belongs to the project, is not the closing sprint, and is not closed; otherwise it refuses before anything moves, as today.
- **Default selection**: the dialog preselects the sprint `nextSprintAfter` returns (the server's rule), on both paths. This also fixes the inconsistency above, by making the dialog name the same sprint the server would choose.
- **Local board**: the client moves the work into the selected sprint by name, as `setTasksSprint` does today.
- **Toast**: the "moved to {name}" message names the chosen sprint.
- **Tests**: server tests for a chosen target, a closed target, an unknown target and the closing sprint itself; the timeline's existing UI suite for the dialog.
- **Changelog**: the change is visible to users, so it adds an `Added` line under `## [Unreleased]`.

### Product questions (recommendation first)

1. **Selectable targets.** Recommended: every sprint of the project that is not closed and is not the one being closed (`future` and `active`), ordered by start date, the next one preselected. Alternative: `future` sprints only, as Jira's own dialog.
2. **Automatic start.** Recommended: the checkbox follows the chosen target ("Start {target} automatically"), shown only when that target is `future`; with backlog or keep, it applies to the next sprint by date, as today. Alternative: always the next sprint by date, whatever the target.
3. **Layout.** Recommended: keep the three options, the first becoming "Move to a sprint" with a dropdown of the selectable sprints (preselected on the next one, still marked recommended); "Backlog" and "Keep in {sprint}" unchanged. Alternative: a single dropdown holding all destinations.
4. **New sprint from the dialog** (Jira offers it). Recommended: out of scope; it can be a separate ticket.
