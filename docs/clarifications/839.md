# Clarification Report — #839: Desktop : Detect new versions

## Round 1 — initial analysis (2026-10-14)

### Request and scope

Sectile Desktop should detect when a newer version is available and make that information visible to its user. The proposed scope is detection and a link to obtain the update; automatic download, installation, agent replacement, and server upgrades remain outside scope unless the owner chooses otherwise below.

Desktop exposes app.getVersion() and the running agent version through its main process. Changelog settings display both and embed release notes at build time, so they remain readable offline. Existing agent mismatch detection compares SHA-256 fingerprints against the bundled agent and can offer a restart; it does not discover a newer published Desktop release. Existing notifications deduplicate run-state transitions.

Tagged releases publish Desktop archives to GitHub Releases and the GitLab package registry. ADR 0045 additionally publishes rolling main builds on GitLab, superseding ADR 0034's tags-only archive restriction. Rolling builds retain the last tagged Desktop manifest version while their bundled agent reports <iid>-main: comparing Desktop SemVer alone cannot detect a newer rolling build. Packaging uses @electron/packager; the manifest contains no updater dependency.

### Ambiguities, highest impact first

1. Detection with a download link versus downloading/installing an update changes packaging, lifecycle, and acceptance criteria.
2. Tagged releases only versus rolling main as well changes metadata sources and requires a reliable build/channel identity beyond the Desktop manifest.
3. Desktop only versus independently detecting newer agent/server versions changes the products checked and how a mismatch is explained.
4. Manual checks only versus startup/periodic checks and proactive notifications changes network scheduling, UI, and notification persistence.

### Reversible technical choices and proposed baseline

- Reuse Electron main-process services and preload IPC for remote checks, and the existing Changelog settings pane for installed/latest version and check status.
- Keep bundled-agent mismatch/restart behavior distinct from published Desktop update availability.
- For tagged releases, compare numeric SemVer values, excluding drafts/prereleases and never proposing a downgrade. Preserve offline access to installed versions and embedded notes.
- Bound checks, avoid overlapping requests, and distinguish an unsuccessful check from a successful result with no update. Follow the language already used by the touched UI surface (the inspected Desktop version controls currently use English).
- No production code or technical specification is written in this stage. A user-visible implementation will need an English Unreleased changelog entry.

### Critical dependencies

- A release metadata source with a complete archive for the current supported OS/architecture; independently built GitHub/GitLab streams may finish at different times.
- Network availability and metadata endpoint throttling; checks must work without requiring workstation tracker credentials.
- Rolling-channel support, if selected, needs reliable installed build metadata and a latest fully published build identifier. Current Desktop manifest versions cannot supply that identity.
- Automatic installation, if selected, requires a separate decision about archive-based distribution, signing, platform lifecycle, and active agent executions; no existing updater configuration was found in the inspected manifest.
- No application-data migration is identified for the proposed detection-only scope.

### Essential questions for the owner

1. What should an available update do? Recommended: detect a newer Desktop version and offer a release/download link, without downloading or installing it. Also confirm whether this ticket checks Desktop only (recommended), or separately checks agent/server updates.
2. Which channel is covered? Recommended: stable tagged releases from GitHub only for this ticket. Alternatively include rolling main builds from GitLab, with explicit channel/build identity and no silent channel switching.
3. When and where should detection appear? Recommended: check at launch, then every 24 hours while open, plus a manual Check for updates control in Changelog settings; show a persistent availability indicator and notify once per new version. Alternatively manual settings checks only, or specify another cadence/surface.

The owner must answer these questions and explicitly confirm that the resulting clarification is satisfactory before transition to clarified.

## Round 2 - answers from the owner (2026-10-14)

### Owner confirmation and settled scope

The owner answered "ok" after being invited to confirm all three recommendations. This confirms the clarification as satisfactory and settles the scope below:

1. Detect newer Sectile Desktop versions and offer a release/download link. Automatic download or installation and independent agent/server update checks are outside this ticket.
2. Check stable tagged GitHub Releases only. Drafts, prereleases and rolling main builds on GitLab are excluded. Compare numeric SemVer values and never offer a downgrade.
3. Check at application launch and every 24 hours while the application remains open. Provide a manual Check for updates control in Changelog settings, a persistent availability indicator, and at most one notification per newly detected version.

Keep installed version information and embedded release notes usable offline. Failed or throttled checks must be distinguishable from a successful check finding no update and must not interrupt normal Desktop use. The existing bundled-agent mismatch/restart behavior remains separate. Reuse the existing Electron main/preload boundary and Changelog settings conventions, preserving the language of the touched runtime surface.

No prior recommendation was reversed. There are no remaining product questions or newly identified critical dependencies. Stable release metadata and availability of the archive matching the supported OS/architecture remain the external dependencies; no data migration is identified. Rolling build identity and automatic installation dependencies are outside the agreed scope. The implementation will need an English Unreleased changelog entry for this user-visible change.
