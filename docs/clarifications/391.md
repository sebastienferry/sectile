## Round 1 (2026-09-25)

### Restated request and scope

When the server asks the connected local agent for an operation that agent's
build does not know (`pr_evidence` today, any newer operation tomorrow), the
caller must get an explicit error that names the outdated agent and the fix
(restart or update it), and the desktop app must stop silently keeping an
outdated agent running after its bundled binary changed. Out of scope: an
automatic update channel for the agent binary, a negotiated protocol version
bump for existing operations, and refusing old agents at connection time.

### Files read

- `internal/agent/agent_operations.go`: the operation allow-list (line 109) and
  the `unknown local operation %q` default (line 111).
- `internal/agent/agent.go`: the WebSocket dial (`projectId`, `deviceId` only,
  line 589), the `/health` answer that already carries `version.Current()`, and
  the restart path that re-executes `os.Executable()` with the same arguments.
- `internal/agent/agent_desktop.go`, `internal/agent/agent_version_test.go` -
  `/desktop/version` and `/desktop/restart`.
- `internal/agentprotocol/message.go`, `internal/agentprotocol/operations.go` -
  the envelope and `Operation`; `RunWaitingType` documents that an unknown
  *message type* is tolerated by old agents, unlike an unknown *operation*.
- `internal/handlers/handlers.go` (`HandleAgentConnect`, `HandleAgentStatus`),
  `internal/handlers/agent_dispatcher.go` (`AgentConn`).
- `internal/db/adjustment.go`: `lookupStagePR` wraps the relay error as
  `<forge> lookup failed on the local agent: …` (line 370); `errAgentTooOld`

- `internal/db/adjustment_test.go:394`: a test already injects

- `internal/handlers/macroruns.go:197` (`slicingReadError`) and

- `desktop/electron/main.cjs`: `start` reuses any agent already answering

- `desktop/electron/runtime.cjs`: binary resolution (`desktop/bin` in dev,

### Verified findings

1. **Root cause confirmed in code.** The agent is a detached process that
   survives the desktop app. `start` reconnects to whatever agent answers the
   loopback, so upgrading or rebuilding the desktop never replaces a running
   agent. Nothing on either side compares builds.
2. **The server knows nothing about the agent build.** The WebSocket URL carries
   `projectId` and `deviceId`; `AgentConn` has no version or capability field;
   `/api/agent/status` cannot show one.
3. **The restart path is sufficient as a fix.** `/desktop/restart` re-executes
   `os.Executable()`, i.e. the binary currently on disk at that path, so a
   restart picks up a rebuilt binary. This matches the ticket's hypothesis.
4. **The problem is generic, the handling is ad hoc.** Two operations have hit it
   (`macro_spec_file`, `pr_evidence`); each is or would be patched by matching
   the error string. Every future operation will hit it again.
5. **Two version sources already exist:** the desktop's `app.getVersion()` and
   the agent's `version.Current()`, both derived from the Git tag (ADR 0018).
   Between tags both read the same tag or `dev`, so a version string alone
   cannot detect a rebuild of `desktop/bin` during development: which is
   exactly the incident reported.

### Ambiguities (worst first)

1. **What the desktop does on a mismatch** (AC 3): restart silently, prompt, or
   only flag. A restart stops active executions (the existing dialog says so),
   so the readings lead to different code and different risk. → Q1.
2. **Where the error surfaces and in which language** (AC 2): MCP
   `transition_stage` errors are English today; the web/desktop UI speaks
   French. → resolved below (D4), no question.
3. **Scope of the detection**: only `pr_evidence`, or every operation. →
   resolved below (D1), confirmed in Q2.
4. **AC 5 (SFE-360 transition)**: an operational check on another project, not a
   code deliverable of this branch. → Q3.
5. **Whether the web board flags an outdated agent too** (it can once the server
   knows the agent's capabilities). → Q2.

### Critical dependencies

- **Old agents in the field.** An agent built before this change announces
  nothing. The server must treat "no announcement" as "capabilities unknown",
  keep sending operations, and translate the relay's `unknown local operation`
  reply. It must not refuse legacy agents outright, or every workstation breaks
  until it upgrades.
- **Wire compatibility.** New announcement data must be additive (a query
  parameter or a new message type), in line with the `RunWaitingType`
  precedent, so neither side needs `agentconfig.Version` bumped.
- **No migration.** Capabilities live on the in-memory `AgentConn`; nothing is
  persisted.
- **Multi-replica.** An operation routed to an agent held by another instance
  (presence, #397) must carry the same explicit error; the check belongs where
  the operation is relayed, not only in the local dispatcher.

### Reversible technical choices (resolved)

- **D1: Capabilities, not version comparison.** The agent announces the list of
  operations it supports when it connects (derived from the same allow-list as
  `executeOperation`, so the two cannot drift), plus its build
  (`version.Current()`). The server checks the list before relaying an
  operation. Version strings are only displayed: they cannot detect a
  same-tag rebuild (finding 5).
- **D2: One generic error.** A single typed error ("the local agent on
  <device> (<version>) does not support <operation>; restart or update the
  Sectile desktop app") replaces string matching. `slicingReadError` and
  `lookupStagePR` both consume it; `errAgentTooOld` is folded into it where it
  describes the same situation.
- **D3: Legacy fallback.** With no announcement, the server keeps relaying and
  converts an `unknown local operation %q` reply into the same typed error, so
  today's agents already get the explicit message.
- **D4: Language per surface** (repository `AGENTS.md`): the MCP/API error text
  stays English, like the rest of `transition_stage`'s errors; the UI message
  shown by the web and desktop stays French, as `slicingReadError` does.
- **D5: Tests.** A db-level test drives `pr_evidence` against an agent without
  the capability (announced list and legacy reply), asserting the wording; a
  handler test covers the announcement at connect; `macroslicing_test` keeps
  passing on the new typed error.
- **D6: Changelog.** User-visible (a clearer error, a desktop prompt): one
  `Fixed` line under `[Unreleased]`.

### Product questions (with recommendation)

- **Q1: Desktop behaviour on a mismatch.** How does the desktop react when the
  running agent is not the one it bundles (detected by comparing the running
  agent's build with the bundled binary's, at start and when reconnecting)?
  *Recommended:* prompt to restart through the existing restart dialog (which
  already warns about active executions), and keep a visible "agent outdated"
  mark in the settings panel until it is restarted. No silent restart, since it
  kills running executions.
- **Q2: Scope of the detection and the web board.** Apply the check to every
  server-to-agent operation (recommended) and also expose the agent's version
  and an "outdated" flag in `/api/agent/status` so the web board can show it?
  *Recommended:* generic check yes; web board flag as a small follow-up only if
  cheap, otherwise out of scope.
- **Q3: AC 5 (SFE-360).** Keep "the SFE-360 `implemented` transition with MR !97
  goes through" as an acceptance criterion of this branch, or treat it as an
  operational verification done by restarting the agent (possibly already done
  since 2026-09-23)? *Recommended:* drop it from the acceptance criteria and
  record it as a manual verification.

## Round 2 - answers from the owner (2026-09-25)

The owner answered the three questions interactively, choosing the recommended
option each time.

### Settled decisions

- **Q1 settled: prompt to restart.** When the desktop finds that the running
  agent is not the binary it bundles, it opens the existing restart dialog
  (which already lists the active executions that a restart stops) and keeps an
  "agent outdated" mark in the settings panel until the agent is restarted. The
  desktop never restarts the agent silently.
- **Q2 settled: generic check, no web board UI.** The capability check applies to
  every server-to-agent operation (D1 to D3). The agent's build and its
  "outdated" state are exposed by `/api/agent/status`, but no web board
  indicator is built in this ticket.
- **Q3 settled: manual verification.** "The SFE-360 `implemented` transition with
  MR !97 goes through" is removed from the acceptance criteria of this branch
  and kept as an operational check: restart the agent, then replay the
  transition.

### Reversed or adjusted assumptions

- Ticket AC 3 offered "restart, or prompt, or flag": narrowed to "prompt and
  flag", silent restart excluded.
- Ticket AC 5 leaves the acceptance criteria (see Q3).
- No prior technical decision (D1 to D6) is reversed.

### Remaining detail for the specification (not a product question)

- How the desktop learns the bundled binary's identity (asking the binary for
  its build without starting it, or comparing the running agent's announced
  capabilities/build with the bundled one) is a specification choice. It must
  detect a same-tag rebuild of `desktop/bin` in development, the reported
  incident, not only a tag change.

### Settled acceptance criteria

1. On connection, the agent announces its build and the operations it supports;
   the server keeps them on the agent connection and exposes them through
   `/api/agent/status`.
2. Before relaying any operation, the server checks the announced list; an agent
   that lacks the operation gets a typed error naming the device, the agent
   build, the operation and the fix (restart or update the Sectile desktop app),
   never `unknown local operation`. A legacy agent that announces nothing still
   receives operations, and its `unknown local operation` reply is converted
   into the same error.
3. `transition_stage` with a `prUrl` on such an agent fails with that English
   message; the macro slicing import keeps its French UI message, now driven by
   the typed error instead of string matching.
4. The desktop detects that the running agent differs from its bundled binary
   (including a same-tag rebuild), prompts to restart through the existing
   dialog, and shows an "agent outdated" mark in its settings until restarted.
5. Tests cover `pr_evidence` against an agent without the capability (announced
   and legacy), assert the error wording, and cover the announcement at connect.
6. `CHANGELOG.md` gets one `Fixed` line under `[Unreleased]`.
