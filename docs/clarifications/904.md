# Clarification report: #904 - We should be able to have a form to ask question with proposal to the user

Ticket: https://github.com/sebastienferry/sectile/issues/904 (no description, parent: macro)

## Round 1 - initial analysis (2026-11-15)

An earlier Round 1 was written on 2026-11-15 but never committed (Git refused the
index lock) and its file is not in this worktree. Only its summary was published as
a ticket comment. This section rebuilds it from that summary and a fresh reading of
the code; the three open questions are the same.

### Restatement

When an agent needs a decision from the owner, Sectile should present the question
as a form with proposed answers (choices, a recommended option, a free answer)
rather than as plain text, and send the selected answer back to the agent.
Out of scope: changing how a skill decides what to ask, and any tracker-side form
(GitHub/Jira) for unattended runs, unless the owner brings it into scope.

### What already exists

- Native Desktop conversations already render such a form:
  - Tauri: `desktop-tauri/src/components/QuestionForm.tsx`, wired in
    `desktop-tauri/src/components/ProjectPrompt.tsx:381-384` for an `AskUserQuestion`
    approval (radio / checkbox options with descriptions, "Other answer" free text,
    secret answers, "Skip request", 16 KB bound).
  - Electron: `desktop/src/conversation.js:290,318-` (`questionForm`).
  - Agent side: `internal/agent/agent_conversation_approvals.go:103-325` (Claude
    `AskUserQuestion` answers, validated by `checkAnswers`) and
    `internal/agent/agent_codex_conversation.go:98-100,905` (Codex
    `requestUserInput`, mapped to the same approval).
- `report_waiting` (`internal/taskmcp/server.go:106`, `internal/agentmcp/mcp.go`)
  only flags a run as waiting: it carries no question and no proposed answers.
- Related #879 proposes displaying the waiting question; it does not provide answers.

### Ambiguities (worst first)

1. **Which surface lacks the form.** Native conversations have it. Runs launched in
   a terminal (`SECTILE_REMOTE_MODE`, the Claude/Codex CLI in a native terminal, as
   this very run) ask in the terminal, and the board/web only see "waiting". Reading
   A (extend to terminal-launched runs, via a question payload on `report_waiting`
   or a new MCP tool, answered from Desktop/web) and reading B (polish the existing
   native form) lead to entirely different code.
2. **Answer controls.** Single/multiple choice, a highlighted recommended option,
   free text, per-question skip: which are required.
3. **Submission, skip and resumption.** Whether the answer goes back to a live
   session only, or is also stored (on the run, or as a ticket comment) so that a
   later run or an unattended run can resume from it.

### Critical dependencies

- A terminal-launched CLI cannot receive an answer from Desktop unless the agent
  polls for it (a blocking MCP tool call that waits for the answer); the Claude CLI
  MCP call timeout bounds how long such a call can wait.
- #879 (waiting-question display) overlaps reading A; the two should share one
  question payload.
- The web app (`web/src`) has no question form today.

### Technical choices resolved from the code

- Reuse the existing question shape (`questions[] { question, header, options[]
  { label, description }, multiSelect }`) and the existing `QuestionForm`
  component rather than a new schema.
- Keep the 16 KB answer bound and the "do not echo secret answers" rule.
- Runtime UI strings stay in the language the surface speaks (English in
  desktop-tauri today).

### Open product questions (owner)

1. Which surfaces and execution modes must show the form? Recommended: terminal-launched
   (remote) skill runs answered from the Desktop task view, sharing #879's payload.
2. Which answer controls are required? Recommended: the existing set (single/multi
   choice, option descriptions, free answer) plus a marked "(Recommended)" option.
3. What happens on submission, skip and resumption? Recommended: the answer is
   returned to the waiting agent and also recorded on the run's activity; skip
   returns "skipped" to the agent; no ticket comment.

## Round 2 - answers from the owner (2026-11-15)

### Answers

1. Surfaces: **native Desktop conversations only (polish)**, in the **Tauri** app only.
   Electron keeps its current form.
2. Controls: the existing set (single/multiple choice, option descriptions, free
   answer, secret answers, "Skip request" for the whole request) **plus** a
   highlighted recommended option **plus** skipping one question individually.
3. Submission: the answers go back to the waiting agent **and** are recorded on the
   run's activity; no ticket comment.
4. Per-question skip: the agent receives an explicit `Skipped by the owner` answer for
   that question and decides by itself.

### Reversed assumptions

- Round 1 recommended extending the form to terminal-launched runs (shared payload
  with #879). The owner rejected it: no new MCP tool, no question payload on
  `report_waiting`, no web form. #879 stays independent.

### Settled scope

- In scope: `desktop-tauri/src/components/QuestionForm.tsx` (and its wiring in
  `ProjectPrompt.tsx`), the agent answer path
  (`internal/agent/agent_conversation_approvals.go`, Codex mapping in
  `internal/agent/agent_codex_conversation.go`) and the recording of the
  question/answer exchange on the run activity of a task-linked conversation.
- Out of scope: Electron (`desktop/src/conversation.js`), web app, terminal-launched
  runs, `report_waiting`, tracker comments.

### Technical choices resolved from the code

- **Recommended option detection**: an option whose label ends with
  `(Recommended)` (the convention Claude's `AskUserQuestion` and the Sectile skills
  already use) is rendered highlighted, with the suffix shown as a badge rather than
  in the label; it is not preselected, so the owner still makes an explicit choice.
  Codex options get the same treatment when their label carries the suffix.
- **Per-question skip**: `checkAnswers` requires one non-empty answer per question,
  so a skipped question is sent as the literal answer `Skipped by the owner`; the
  agent-side validation is unchanged. The whole-request "Skip request" (deny) stays.
  Sending with every question skipped is allowed and differs from "Skip request":
  the agent receives answers, not a denial.
- **Run activity record**: the answered questions are recorded as one activity step
  (question → answer lines, as `answersDetail` already formats them), secret answers
  masked; when the conversation is not linked to a run, nothing is recorded beyond
  the existing transcript.
- UI strings stay in English (the Tauri app's language).

### Dependencies

- None external. #879 is unaffected.

None.

## Round 3 - answers from the owner (2026-11-15)

### Answers

- The owner finds the current form layout poor and asks for **one tab per question**.
- Settled tab behaviour (accepted as proposed):
  - one tab per question, labelled with the question's short `header`, else `Q1`,
    `Q2`, ...;
  - each tab shows its state: to answer, answered (✓), skipped;
  - choosing an option in a single-choice question moves to the next tab
    automatically (multiple choice and free answers do not);
  - the "Send answers" button stays visible under the tabs and is enabled once every
    question is answered or skipped;
  - a request with a single question shows no tabs.
- No "Review" tab.
- The owner confirmed the clarification is satisfactory.

### Settled scope (final)

Polish of the native question form of the **Tauri** Desktop app
(`desktop-tauri/src/components/QuestionForm.tsx`, wired in `ProjectPrompt.tsx`),
for Claude `AskUserQuestion` and Codex `requestUserInput`:

1. one tab per question, with the behaviour above;
2. the option labelled `(Recommended)` is highlighted with a badge, not preselected;
3. each question can be skipped individually: the agent receives
   `Skipped by the owner` for it; the whole-request "Skip request" (deny) stays;
4. the answers go back to the waiting agent and are recorded as one step of the run's
   activity (secret answers masked); no ticket comment.

Out of scope: Electron, web app, terminal-launched runs, `report_waiting`, #879.

### Open questions

None. Exit condition met.
