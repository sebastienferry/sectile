## Round 1 (2026-09-25)

### Restated request and scope

When several server instances share one PostgreSQL database, a person who unlocks a
sealed tracker credential through one replica can use it through every replica: the
key derived from the passphrase is handed to the other live instances over the
internal channel, kept in memory only, and a replica that starts asks its peers for
the keys they hold. Locking, replacing or deleting the credential takes effect on
every replica as well.

Out of scope: SQLite (single instance, unchanged), the passphrase itself (never sent,
never stored), unsealed credentials (the shared server key already opens them on every
replica), and any change to the sealing format.

### Verified findings

1. **The internal channel is plain HTTP inside the deployment.** The bearer
   authenticates the caller, but the body travels in clear on the pod network. A
   derived key must therefore not be sent as is.
2. **A replaced credential invalidates old keys by itself.** Storing a credential again
   draws a new salt, so a key derived for the previous record no longer opens the new
   one. A peer that missed the replacement fails safely (the credential reads as
   locked), it never opens the new token with the old phrase.
3. **Locking changes nothing in the database.** Today a lock only forgets the key in
   memory. With several replicas, a lock that fails to reach one peer (timeout,
   network partition, a peer starting at that very moment and pulling the keys) leaves
   the credential usable there, while the owner was told it is locked. See Q2.
4. **The resolver runs under the store lock.** `userTrackerCredential` is reached from
   paths that hold `d.mu`, so asking peers for a missing key at that point would put
   network I/O under the store lock. Keys are therefore pushed when they change and
   pulled once at start, never fetched on a miss.

### Ambiguities, worst first

- **A1: What "lock" guarantees across replicas** (Q2). Best effort on the live peers,
  or authoritative whatever a peer missed. The two readings differ by a migration.
- **A2: Which option for sharing** (Q1). The ticket asks to confirm option (a).

### Critical dependencies

- Every replica holds the same `SECTILE_SECRET_KEY` (already mandatory under
  PostgreSQL): it authenticates the channel and wraps the key in transit.
- Q2 option (a) adds a numbered migration (ADR 0021), with the usual replay and rewind
  test fixtures to extend.

### Resolved technical decisions (reversible)

- **D1: Push on change, pull at start.** Unlock, lock, store and delete are pushed to
  every live peer, in parallel, each within a short bound; a failure is logged and does
  not fail the person's request. A starting replica asks each live peer for the keys it
  holds and keeps the union.
- **D2: Wrapped in transit.** A key crosses the channel sealed with the server key
  (`secrets.Seal`, AES-GCM) under a binding naming the user and the tracker, so the pod
  network only ever carries ciphertext, and a key cannot be replayed under another
  identity.
- **D3: Verified before being kept.** A received key is kept only if it opens the
  credential's current record, so a stale or forged key is dropped.
- **D4: New internal route** `/internal/credentials/keys` on the internal listener,
  behind the same bearer as the agent and MCP routes.
- **D5: Nothing written down.** No derived key in the database, the logs or on disk; a
  test asserts that no key material reaches the database or the log output.

### Open product questions

**Q1: Confirm option (a), share the derived key between replicas in memory?**
Options: (a) broadcast over the authenticated internal channel, memory only; (b) the
person unlocks on every replica (unusable behind a load balancer); (c) persist it
encrypted with `SECTILE_SECRET_KEY` (the passphrase then protects nothing beyond the
server key). Recommendation: **(a)**.

**Q2: Must a lock hold on every replica, even one the broadcast did not reach?**
Options: (a) authoritative lock: each credential carries a non-secret generation
counter in the database, bumped by lock; a held key is used only while its generation
matches, so a missed broadcast cannot keep a locked credential usable (one migration);
(b) best effort: the lock is broadcast like an unlock, and a peer that missed it keeps
the key until it restarts. Recommendation: **(a)**: the owner locks precisely to stop
the credential from being used, and (b) can silently break that promise.

## Round 2 - answers from the owner (2026-09-25)

### Settled

- **Q1: option (a).** The derived key is shared between replicas over the
  authenticated internal channel, wrapped with the server key in transit (D2), kept in
  memory only; a starting replica pulls the keys from its peers (D1).
- **Q2: option (a), authoritative lock.** Each credential carries a non-secret
  generation counter in the database. Unlock records the generation it read with the
  key; lock bumps it; store and delete end the row's history as today. A held key is
  used only while its generation matches the row's, so a peer that missed a lock
  broadcast reads the credential as locked. The broadcast only frees memory sooner.

### Consequences recorded

- One numbered migration adds `user_tracker_credentials.unlock_generation`
  (`INTEGER NOT NULL DEFAULT 0`), in `migrations.go` only, never in the frozen
  baseline, with the replay and rewind fixtures extended.
- The generation check applies on a single instance too: it costs one column read on
  a query the resolver already makes.
- No reversed assumption: every Round 1 decision stands.

### Exit condition

Met: no open product question. Ready to transition to `clarified`.
