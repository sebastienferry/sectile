### Restated request and scope

Every view of the web UI that filters its content does so with the same shared filter controls: one look, one placement in the view's toolbar, one way to see which filters are active and to clear them. The same dimension (sprint, parent, assignee, priority, search...) reads and behaves the same wherever it appears.

Out of scope: controls that look like filters but are not (see the corrected inventory below), the server-side filtering API, the global command palette, and the admin panels.

### Ambiguities, worst first

1. **Look only, or also where the state lives.** Uniformizing the controls can leave each filter where it is (global and server-side on Board/List, local on Triage and Activities), or also move state, for example making the Triage sprint filter the global one. The second changes what users see when switching views and what the server receives.
2. **Which pattern is the reference.** `TaskFilters` puts secondary filters in a panel behind a "Filters" button; the Roadmap shows each filter in the toolbar and lists the active ones as chips. The two lead to different toolbars on every view.
3. **Cardinality.** Tracker status, issue type, epic labels and origins are multi-select; sprint, team, assignee, parent and priority are single. Making, for example, assignee multi-select changes the server query.
4. **Activities.** Its filters act on run history, not on tickets. It can adopt the shared primitives or be left alone.

### Critical dependencies

- None on the backend if the state and cardinality stay as they are (question 1 and 3).
- Every new string goes through `web/src/locales/*` in both languages.
- No test covers filters today: the primitives need their own tests in `web/tests/`.

### Reversible technical choices

- Shared primitives under `web/src/components/filters/`: a filter popover (single and multi, with search through `LookupField`), a toggle chip, a search input with clear, a filter bar slot, and an active-filters chip row with "Clear all". The existing `useClickOutside` hook, extended with Escape, replaces the copies in `EpicLabelFilter`, `EpicOriginFilter` and the timeline dropdown.
- The existing `TaskFilters`, `EpicLabelFilter`, `EpicOriginFilter` and the timeline parent dropdown are rebuilt on the primitives, keeping their props and the state they read.
- Native `<select>` filters are replaced by the shared popover; the non-filter selects listed above are not touched.
- One pull request, view by view in separate commits.

### Product questions for the owner

1. **State scope.** Recommended: look and behaviour only; every filter keeps its current state and server behaviour. Moving state would be a separate ticket.
2. **Reference pattern.** Recommended: the `TaskFilters` model (main toggles inline, secondary filters in a "Filters" panel with a count badge) plus the Roadmap's active-filter chip row with "Clear all", shown on every view that filters.
3. **Cardinality.** Recommended: keep each filter's current single or multi cardinality; only the look changes.
4. **Activities in scope.** Recommended: yes, it adopts the primitives (segmented status, skill popover, search), its state stays local.
