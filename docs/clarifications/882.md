### Restated request and scope

The web Triage view (`TriageView.tsx`) lets the owner fill in, row by row or for a selection, the sprint, macro, team and assignee of tickets; it does not show or set the priority. This ticket adds the priority to the triage: each row shows its priority and can change it, and a selection can be given one priority at once.

Out of scope: the desktop app, the priority levels themselves (`urgent`, `high`, `medium`, `low`), the Jira priority mapping (#679), the epic priority of the Roadmap (`p0`-`p3`), and any change to how the other views show the priority.

### Ambiguities, worst first

1. **A GitHub or GitLab ticket's priority does not survive a sync.** Neither adapter reads nor writes a priority; every sync resets the stored priority to `medium`. A priority set in the triage of a GitHub project (this one included) would silently revert at the next sync. The same is already true from the List view and the task detail. Two readings: (a) this ticket only adds the priority to the triage, and the persistence is a separate ticket; (b) this ticket also makes the sync keep the local priority of tickets whose tracker has no priority. *Product question Q1.*
2. **What "add priority" covers.** Readings that lead to different code: an editable priority column per row; a priority action in the batch bar; a priority filter in the Filters panel; a "missing priority" pill. *Product question Q2.* A "missing priority" pill is not offered: the priority is never empty (it defaults to `medium`), so the pill would count nothing, and "still `medium`" cannot be told apart from "chosen `medium`".
3. **Priority filter, if wanted: local or global.** The global `priorityFilter` of the board already narrows the triage's tickets server-side today, invisibly, since the triage shows no chip for it. Reusing it (as the macro picker reuses `parentFilter`) makes that hidden filter visible and clearable; a local filter would stack on top of it. Settled below (D3) if Q2 keeps the filter.

### Critical dependencies

- **Tracker sync** (ambiguity 1): no migration needed either way; reading (b) changes `ImportOrUpdateTasks` for GitHub and GitLab only (Jira has a native priority and must keep overwriting).
- **Jira refusals** (#679): a priority write on a Jira ticket can be refused when the project's mapping only guessed it; the triage must surface it like `handleBulkPriority` does, not drop it.
- No other service, no new data.

### Reversible technical choices, settled

- **D1. Row editor:** a compact dot-select per row, the same pattern as `ListView` (native `<select>` behind the priority dot, `PRIORITY_COLORS`), placed after the title column; written through `updateTask(task.id, { priority })`.
- **D2. Batch action:** a priority picker plus *Confirm* in the selection bar, like sprint, macro and team; each selected ticket is written in turn and refusals are toasted, reusing `partitionBulkOutcomes` from `lib/priorityMapping` as `ListView` does.
- **D3. Filter (if kept):** the priority dots inside the triage's Filters panel, bound to the global `priorityFilter`, with a chip in `ActiveFilterChips` and counted by the panel's Reset, consistent with #866.
- **D4. Strings:** new keys in the triage catalog of `web/src/locales/planning.ts`, French and English, reusing `t.priority[level]` for the level names.
- **D5. Tests:** a web test for the row editor, the batch action (including a refused ticket) and, if kept, the filter chip.

### Product questions

- **Q1. Should this ticket also make a GitHub/GitLab ticket's priority survive the sync?**
  Recommended: **no, open a separate ticket.** The reset is a backend sync bug that already affects the List view and the task detail; fixing it here would widen a UI ticket into a sync change. Downside: until that ticket lands, the triage priority of a GitHub project reverts on sync.
- **Q2. Which of these does "add priority" include?** (several possible)
  Recommended: **the editable column and the batch action**, plus **the priority filter** (D3), since it makes the already-active hidden filter visible. No "missing priority" pill (see ambiguity 2).

## Round 2 - answers from the owner (2026-10-28)

Answers given interactively in the run's session. Report committed on `feat/882`, not pushed (`pushStageCommits` off).

### Settled choices

- **Q1, persistence: in this ticket.** The sync of a GitHub or GitLab ticket keeps the priority stored in Sectile instead of writing `medium` over it. A Jira ticket keeps taking its native priority from Jira on every sync, as today. The priority stays local: it is not mirrored to the tracker (no `priority:*` label is written on GitHub or GitLab). A ticket imported for the first time still starts at `medium`.
- **Q2, scope in the triage: the editable column only.** Each row shows its priority as the coloured dot and can change it (D1). No batch action, no priority filter, no "missing priority" pill.

### Reversed assumptions

- Q1 reverses the Round 1 recommendation: the persistence fix is part of #882, not a separate ticket. The ticket now changes the server (`ImportOrUpdateTasks`) as well as the web.
- D2 (batch action) and D3 (priority filter) are dropped. The global `priorityFilter` keeps narrowing the triage's tickets invisibly, as it does today; making it visible is left out of this ticket.

### Updated technical choices

- **D1, unchanged:** a per-row dot-select after the title column, the `ListView` pattern, written through `updateTask(task.id, { priority })`; a Jira refusal (#679) surfaces through `updateTask`'s existing error path.
- **D6. Sync:** in `ImportOrUpdateTasks` (`internal/db/db.go`, the update branch around 1262), the priority column is only overwritten when the incoming ticket comes from a tracker that carries a priority (Jira); for GitHub and GitLab the stored priority is kept. The insert branch is unchanged. The decision is made from the ticket's source/tracker provider, not from the value `medium`, so a Jira ticket set to Medium in Jira still syncs. The same rule is checked in the other write path that copies a tracker ticket over the stored row (`internal/db/postback.go` ~237, `db.go` ~3319) and applied there if it also resets the priority.
- **D7. Tests:** a Go test proving that a GitHub (and GitLab) ticket keeps a locally changed priority across a re-import while a Jira ticket takes the tracker's; a web test for the triage row editor.
- **D4, unchanged:** column header and select title in the triage catalog of `web/src/locales/planning.ts`, French and English.
