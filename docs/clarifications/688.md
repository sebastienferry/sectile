# Clarification #688 - Group option in project tasks

Ticket: https://github.com/sebastienferry/sectile/issues/688

## Round 1 - initial report (2026-10-01)

### Request

In the Sectile Desktop sidebar, where each project lists its local tasks, add
an option that orders those tasks by workflow stage (new, clarified, specified,
implemented, reviewed, finished), and tint the task key with a light background
colour that tells its stage at a glance.

Out of scope: the web board and backlog (they already group by workflow with
`BoardGroupingToggle`), the Desktop "Open tasks" pane (it already sorts by a
stage column), filters, and any server or tracker change.

### Code read

- `desktop/src/main.js`: the sidebar (`project-group`, `local-task` rows, the
  `.task-number` key button, around lines 540-640), the project `…` menu
  (`projectMenu`, line 456), and `refreshPRs` (around line 2832), which already
  fetches every task of each listed project to read titles and pull requests.
- `desktop/src/task-order.mjs`: current row order (run state, then submission
  time, anchored on the earliest execution).
- `desktop/src/workflow.mjs`: `taskStage()`, which maps labels and status to a
  stage.
- `desktop/src/task-list-order.mjs`: `STAGE_ORDER` and the stage sort of the
  tickets pane.
- `web/src/components/BoardGroupingToggle.tsx` and `web/src/lib/boardGrouping`:
  the web's workflow / status grouping, the neighbouring feature.

### Ambiguities (worst first)

1. Which "project tasks" list: Desktop sidebar, Desktop "Open tasks" pane or
   web backlog.
2. Grouping as section headers per stage, or as an ordering without headers
   (the ticket says "not necessarily a sub group").
3. Key colour always shown, or only while grouping is on.
4. Where the option lives and whether it is per project or global.

### Dependencies

- A sidebar row is a run, not a task: the stage needs the task's labels and
  status. `refreshPRs` already calls `api.serverTasks(projectId)` for every
  listed project, at most every 15 s, and caches titles and pull requests per
  `taskId`. The stage can be cached there the same way: no new request, no
  server change.
- No migration, no API change, no third-party limit.

### Technical choices resolved from the code

- The stage comes from `taskStage()` and the stage order from `STAGE_ORDER`,
  shared with the tickets pane, so both surfaces agree.
- Within a stage, rows keep the current `orderedTaskGroups` order, so a
  relaunch never moves a row inside its stage.
- A free console, a macro run, or a task whose stage is not known yet (before
  the first `serverTasks` answer, or when it fails) has no stage: it goes after
  the staged rows and its key has no tint.
- The preference is stored in `localStorage`, like `collapsedProjects`.
- The tint is a set of colour tokens on `:root` in `desktop/src/style.css`,
  redefined for the dark theme, one per stage, light enough to keep the key
  readable.

## Round 1 - answers from the owner (2026-10-01)

Asked interactively; the owner answered every question with the recommended
option.

### Settled decisions

1. **Surface**: the Desktop sidebar, the local tasks listed under each project.
2. **Grouping form**: an ordering by stage (new first, finished last), with no
   section headers.
3. **Key colour**: always shown, whatever the grouping, with a tooltip naming
   the stage; one light tint per stage, readable in the light and dark themes.
4. **Option**: a "Group by stage" entry in each project's `…` menu, toggled and
   remembered per project on the workstation (`localStorage`). Off by default,
   so the current order is unchanged until the owner turns it on.
5. **Branch**: keep the current base of `feat/688` (see "Branch base").

### Reversed assumptions

None.

### Open questions

None. Exit condition met: the clarification is settled.

### Acceptance criteria baseline

- The project `…` menu offers "Group by stage", checked when on; the choice
  survives a restart and is independent per project.
- When on, the project's rows are ordered new → clarified → specified →
  implemented → reviewed → finished, then the rows without a stage; the
  existing order applies within each stage.
- When off, the order is exactly today's.
- Every task key in the sidebar carries the light tint of its stage, with a
  tooltip naming it, whether grouping is on or off; rows without a stage carry
  none.
- A stage change on the tracker is reflected at the next task refresh, without
  an extra request per task.
- `CHANGELOG.md` gets one `Added` line under `[Unreleased]`.
