# #50 — Task management and completion contract for local skill sessions

## Request and scope

Make the task-management and result interface actually usable by a skill session launched through the local agent: the session must be able to read its own ticket and its project context, and to report its run result to the owning activity, without falling back to raw HTTP or to the tracker CLI. Reworking the agent/server split (#54), the stage-validation rules themselves, tracker credential provisioning, and the desktop UI are outside this change.

## Ambiguities and decisions

1. **SDD framework.** The project record says `speckit`, `.taskflow/config.json` and the repository itself say OpenSpec, which is what every prior change used. Decision: OpenSpec, per repository convention and detection rule; a Spec Kit tree here would be an isolated orphan.
2. **Degradation vs. failure on comment retrieval.** Two readings: a partial read is a failure (current behaviour), or the task is returned with the retrieval error carried as a field. Decision: the second. The acceptance check asks for “an actionable error and bounded recovery”, and losing the whole ticket because a tracker comment call failed is the reported bug. Comments stay absent and the reason is explicit, so a session never mistakes a fetch failure for “no comments”.
3. **Shrinking the project context.** Reading the whole skill catalogue inline vs. exposing identity/settings plus skill references. Decision: keep the payload to identity, execution settings, framework and PR stage, and reduce each skill to its id, directory, command name and resolved file paths. A session that genuinely needs a skill body reads the file. This preserves every field the transition contract actually consumes.
4. **Scope of the `.git` suffix on `githubRepo`** (`sebastienferry/sectile.git`, not a valid GitHub slug). Decision: out of scope here, recorded for a separate ticket; it comes from the stored project record, not from the session interface.

## Critical dependencies

None blocking. No migration, no external service, no other team. Go toolchain plus the existing `internal/db` and `internal/taskmcp` test suites are sufficient. Live project settings: branch `feat/50`, worktrees enabled, PR creation at the `specified` stage, tracker GitHub.

## Questions

None blocking. The only product-level call — degrade versus fail on a partial task read — is resolved by the ticket's own acceptance check (“a missing bridge or contract reports an actionable error and supports bounded recovery”) and recorded as decision 2 above.

## Settled assumptions

`get_task` returns the locally known task whenever it exists, with comments when they can be read and an explicit retrieval error otherwise; it fails only when the task itself is unknown. `get_project_context` returns a bounded payload that keeps project identity, execution settings, specification framework, PR creation stage and per-skill references without inlining skill bodies. Both changes are covered by tests. The generated skill routing, the managed-run gate, `start_run`/`finish_run` and the stage-validation rules are unchanged.
