## Round 1: analysis (2026-09-23)

### Request restated

Let any server instance reach a local agent connected to another instance: record which
instance holds each agent in the database, and forward agent-bound work to that instance
over an authenticated internal call. Out of scope: MCP session routing (#408), sharing
passphrase keys (#409), and anything on the agent side (the agent keeps one WebSocket to
whichever instance the load balancer gives it).

### Files read

- `internal/handlers/agent_dispatcher.go`: `AgentDispatcher` maps, `Register` (kicks the
  previous connection with 4001), `Unregister`, `Lookup` with its `default`/`all`/empty
  project fallbacks, `WaitForAgent` and `agentWasRecentlyConnected` (4 s grace, 5 min
  recency), `Dispatch`, `DispatchAndWait`, `PullTasks`, `ConnectedAgents`.
- `internal/handlers/agent_operations.go`: `CallOperation`, the request/response path
  every store-side agent call uses (`SetAgentOperations`): workspace and git operations,
  `git_evidence` for `transition_stage`, `execute_skill` for queued skills.
- `internal/handlers/handlers.go`: the seven call sites that use the registry directly
  (`Lookup` then `Dispatch`/`DispatchAndWait` in the launch paths, `HandleAgentDispatch`,
  `HandleAgentPull`, `HandleAgentStatus`), `/ws/agent-connect`.
- `internal/handlers/remote_run.go`: `DispatchAndWait` for remote runs.
- `internal/db/instances.go` (#403): instance id, `server_instances`, the reaper.
- `web/src/hooks/useAgentStatus.ts`: listens to unnamed SSE `message` events while the
  server sends named ones (found in #405).

### Findings

- **Three verbs cover every cross-instance need.** `CallOperation` (request/response),
  `Dispatch` (fire and forget) and `DispatchAndWait` (launch confirmed by the agent) are
  all serialisable: user, project, task and a JSON payload in, a JSON value or an error
  out. `PullTasks` is a fourth, used by the manual pull endpoint. Forwarding these four
  at the dispatcher leaves every caller unchanged.
- **Correlation stays local.** The instance holding the WebSocket keeps matching agent
  replies to requests, as today; the forwarding instance only waits for the HTTP answer.

### Resolved technical decisions (reversible, settled here)

- **D1: Presence table, migration 7.** `agent_presence (user_id, project_id, instance_id,
  device_id, connected_at, disconnected_at)`, primary key `(user_id, project_id)`.
  Register upserts it; Unregister sets `disconnected_at` only if the row is still this
  instance's and this device's. A row whose instance is not live counts as absent; the
  #403 reaper deletes those rows.
- **D2: Lookup order.** Local map first (no database round trip for the common case),
  then presence, with the same `default`/`all`/empty fallbacks.
- **D3: Forwarding.** Four internal endpoints on the owning instance, one per verb; the
  owner runs its local method and returns the result. Timeouts follow the caller's
  context.
- **D4: Waiting.** `WaitForAgent` and "recently connected" read presence too, so an
  agent reconnecting through another instance is awaited, not reported absent.
- **D5: Rebinding across instances.** When an agent registers and presence names
  another live instance, the new owner asks it to close the old connection (4001), as
  one instance does today.
- **D6: Status.** `/api/agent/status` lists presence rows of live instances, the same on
  every instance.
- **D7: Internal authentication.** A bearer derived from `SECTILE_SECRET_KEY` (HMAC of a
  fixed label), which every instance already shares under PostgreSQL. No new secret.
  Without the key, forwarding is refused with an explicit error.
- **D8: `useAgentStatus` fix.** Listen to the named `agent_connected` and
  `agent_disconnected` events; two lines, and without it the aggregated status only
  refreshes on its polling interval.

### Open product questions

**Q1 (Q2 from #397): an operation forwarded to an instance that dies before answering.**
(a) fail with an explicit error, as a local agent disconnect does today; (b) retry once
against the agent's new instance once it reconnects. Recommendation: **(a)**. A retried
`execute_skill` or workspace write could run twice; the caller already reports and lets
the user retry.

**Q2: where the internal endpoints listen.** (a) a separate internal port
(`SECTILE_INTERNAL_PORT`, default 8092), which the ingress does not expose, plus the
bearer; (b) the public port under `/internal/`, protected by the bearer only.
Recommendation: **(a)**: the endpoints act for any user's agent, so they should not be
one leaked token away from the internet. It needs a container port in the deployment,
not a route.

**Q3: how an instance advertises its internal address.** (a) auto-detected (the first
non-loopback IPv4 plus the internal port), overridable with `SECTILE_INTERNAL_URL`;
(b) `SECTILE_INTERNAL_URL` mandatory under PostgreSQL. Recommendation: **(a)**: a pod has
one interface, and the override covers any other setup.
