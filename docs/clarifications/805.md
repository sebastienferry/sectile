## Round 1 (2026-10-09)

### Restated request and scope

Sectile Desktop should let a user create a task and edit an existing one in a full page of its own (the ticket says "plain page, Notion like"), with a rich Markdown description, the task's pull request link(s) and its assignee, saved through the local agent to the server and the task's tracker. Out of scope: the web task modal, fields the ticket does not name (status, stage, priority, labels, due date, sprint, epic, branch), comments, and the sidebar's existing rename of a local run name.

### Files read and findings

- `desktop/src/main.js:3532` (`quickAdd`): Desktop already creates tasks, in a modal dialog with project, title and a plain `textarea` description ("Optional, Markdown"). After creation it offers "Clarify now", "Launch task", "Add another" and "Done". It is opened by Cmd+N / Ctrl+N (`desktop/src/new-task-shortcut.mjs`) and by the command palette entry "New task" (`main.js:3422`).
- `desktop/src/main.js:2885` (`openTickets`) and `main.js:2974`: the Tickets pane lists a project's server tasks in a table; each row has a run button and a "…" menu. There is no task detail or edit view anywhere in Desktop.
- `desktop/src/main.js:764-829`: the sidebar row of a local run has a pencil that renames the run's local display name only (stored in `localTasks`); it never touches the server task.
- `desktop/src/markdownView.mjs`: a read-only Markdown renderer (markdown-it, commonmark + tables + strikethrough, no raw HTML, links filtered) used by the Changes panel. Desktop has no Markdown editor and no WYSIWYG dependency.
- `desktop/electron/main.cjs:518` and `preload.cjs:47`: `createTask` goes through IPC to the agent's `/desktop/create-task`, gated on the agent capability `create-task` ("The running local agent is outdated…").
- `internal/agent/agent_desktop.go:1091` (`desktopCreateTask`): accepts project, title, description and tracker id, and forwards a `models.CreateTaskRequest` with `RequireRemoteCreation` to the server's `POST /api/tasks`. It drops every other field. There is no `/desktop/...` route to update a task.
- `internal/models/models.go:1220` (`CreateTaskRequest`): already carries `Assignee`. `models.go:1262` (`UpdateTaskRequest`): `Title`, `Description`, `Assignee`, `AssigneeAccountID`, `PrURL` and `PrLinks` (replaces the whole set; an empty slice detaches every link).
- `internal/handlers/handlers.go` (`HandleTaskDetail`): `/assignable` serves the tracker's assignee lookup; `PUT`/`PATCH /api/tasks/<id>` applies `UpdateTaskRequest`.
- `web/src/components/TaskDetailModal.tsx`: the web edit form, the reference for behaviour: assignee picker backed by `/assignable` when the tracker supports `assigneeLookup`, free text otherwise; `prLinks` edited as an ordered set; one explicit save that sends only changed fields.

### Ambiguities, worst first

1. **Editor kind.** "Notion like … rich markdown" reads either as (a) a WYSIWYG block editor where formatting renders as you type, or (b) a Markdown source editor with formatting shortcuts and a rendered preview. (a) adds a new editor dependency (Tiptap/ProseMirror, Milkdown…) and a Markdown round trip that can rewrite descriptions written elsewhere (Jira, GitHub); (b) reuses `markdownView.mjs`. See Q1.
2. **Page or dialog, and the fate of quick add.** "Plain page" can mean a full pane in the Desktop window (like the Tickets pane) or a larger dialog. And creation already exists: does Cmd+N open the new page, or does the quick dialog stay for fast capture? See Q2.
3. **Save model.** Notion saves as you type; a tracker write per pause would spam Jira/GitHub history and notifications. See Q3.
4. **"MR link".** One field (`prUrl`) or the full ordered set (`prLinks`) the task already holds, and is it offered at creation too? See Q4.
5. **Assignee at creation.** Only at edit, or at creation as well (the server request already has the field). See Q4.

### Dependencies

- **Agent route and capability.** Desktop reaches the server only through the agent. Editing needs a new agent route (for example `/desktop/update-task`) and a new capability string, so an outdated agent gets the same readable refusal as `create-task`. Creation with assignee or PR links needs `desktopCreateTask` to forward more fields.
- **Tracker writes need an acting user** (#482): the update goes out with the paired user's token, as creation already does.
- **Assignee lookup per tracker.** GitHub (login), Jira (accountId) and GitLab differ; key-only tracker calls need the project in context (`tracker.WithProject`). The web already handles this through `/assignable`, which Desktop will reuse.
- **Description round trip on Jira.** The server converts Markdown to and from Jira's format; an editor that reformats the Markdown on load would create a diff on save. This weighs on Q1.
- **`desktop/src/main.js` is large** (3,759 lines); the page is better written as its own module, with `node --test` coverage like the other `desktop/src/*.mjs`, plus a `.ui.cjs` UI test.

### Technical choices resolved here (reversible)

- The page lives in its own module (`desktop/src/task-editor.mjs` or similar) and is shown in the workspace area, the way the Tickets pane replaces the run view.
- "Edit task" is added to the Tickets pane row's "…" menu, and to the current run's header when the run belongs to a server task. The sidebar pencil keeps renaming the local run name only.
- The editor loads the task fresh from the server when it opens, and sends only the fields that changed (as the web does). Concurrent edits: last write wins, no conflict detection in this ticket.
- Links in the preview are rendered with the existing `markdownView.mjs` rules (no raw HTML, external links opened through the existing safe opener).
- PR links are validated as `http(s)` URLs on the client and on the agent.
- New user-facing strings are English, like the rest of the Desktop UI.

### Product questions (with recommendation)

**Q1. Which editor?**
- (a) **Recommended:** Markdown source editor with a toolbar and shortcuts (bold, italic, heading, list, checklist, link, code, Cmd+B/Cmd+I/Cmd+K), auto-growing, with a Write / Preview toggle (or side-by-side on wide windows) rendered by `markdownView.mjs`. No new dependency, the Markdown is stored exactly as typed.
- (b) WYSIWYG block editor (Notion feel: `/` commands, inline rendering). New dependency and a risk of reformatting existing descriptions on save.

**Q2. Where does it open, and what happens to the quick add dialog?**
- (a) **Recommended:** a full page in the workspace for both creation and edition. Cmd+N and the palette's "New task" open it in creation mode; the quick add dialog is removed, and its post-creation actions (Clarify now, Launch task, Add another, Done) move to the page.
- (b) Same page, but Cmd+N keeps the quick dialog for fast capture, with an "Open full editor" link to the page.

**Q3. How does it save?**
- (a) **Recommended:** explicit save (button and Cmd+Enter / Ctrl+Enter), an "unsaved changes" mark, and a confirmation before leaving the page with unsaved changes.
- (b) Autosave after a pause (Notion-like), one tracker write per pause.

**Q4. Which fields exactly, and at creation too?**
- **Recommended:** creation and edition both show project (creation only, and the tracker when the project has several, as #741 allows), title, description, assignee and pull request links. Pull requests are the task's ordered set (add, remove, reorder; the last one is the current `prUrl`), not a single field. Assignee uses the tracker lookup when available, free text otherwise, as in the web. Nothing else (priority, labels, due date, status) is in scope.
- Alternative: one single "PR / MR link" field, and assignee and link only when editing.

## Round 2 - answers from the owner (2026-10-09)

### Answers

- **Q1, editor:** WYSIWYG, Notion-like (option b). This reverses the round 1 recommendation of a Markdown source editor with a preview.
- **Q2, page:** one full page in the workspace for creation and edition. Cmd+N / Ctrl+N and the palette's "New task" open it in creation mode. The quick add dialog is removed; its post-creation actions (Clarify now, Launch task, Add another, Done) move to the page.
- **Q3, save:** explicit save (button and Cmd+Enter / Ctrl+Enter), an "unsaved changes" mark, and a confirmation before leaving the page with unsaved changes. No autosave.
- **Q4, fields:** creation and edition both show title, description, assignee and the ordered set of pull request links (add, remove, reorder; the last one is the current `prUrl`). Creation also shows the project, and the tracker when the project has several. Assignee uses the tracker lookup (`/assignable`) when the tracker supports it, free text otherwise. Priority, labels, due date and status stay out of scope.

### Reversed assumptions

- Round 1 assumed a source editor reusing `markdownView.mjs` and no new dependency. The description editor is now a WYSIWYG editor, which brings a new runtime dependency to `desktop/package.json`. `markdownView.mjs` stays the renderer of the Changes panel and is not reused by the editor.

### Consequences of the WYSIWYG choice, resolved here (reversible)

- **Library.** A Markdown-native ProseMirror editor, so the stored value stays Markdown and the server's Markdown/Jira conversion is unchanged. Milkdown (its "Crepe" preset gives the Notion-like slash menu, block handles and inline toolbar, and parses and serializes with remark) is the first candidate; Tiptap with a Markdown serializer is the fallback. The specification settles it after checking bundle size, the CSP below and Markdown fidelity.
- **CSP compatibility.** `desktop/index.html` allows `script-src 'self'`, inline styles and `img-src 'self' data:`. The editor must run under it: no `eval`, no remote fonts or scripts. Remote images in a description are not loaded, as in the Changes panel.
- **Feature set.** Headings, bold, italic, strikethrough, inline code, code blocks, bullet, numbered and task lists, quotes, links, tables and horizontal rules: the CommonMark plus GFM subset that GitHub, GitLab and the server's Jira conversion carry. No embeds, colours, callouts or other blocks Markdown cannot store.
- **Round trip protection.** Loading a description into the editor and serializing it back can normalize its Markdown (list markers, emphasis characters, spacing). The page therefore sends `description` only when the user changed the content, compared on the editor's document rather than on the raw text, so opening and saving an untouched task never rewrites a description written in Jira or GitHub.
- **Source escape hatch.** A "Markdown" toggle on the description shows and edits the raw Markdown, for constructs the WYSIWYG editor cannot represent (raw HTML, footnotes, unusual Jira markup). Switching back re-parses it.
- **Safety.** Links are not followed on click inside the editor; they open through the existing external-link opener with the `isExternalLink` rule. Pasted HTML is converted to the supported subset, never inserted raw.
- **Tests.** Markdown parse/serialize round trips get `node --test` coverage on a fixture set (GitHub and Jira-converted descriptions); the page gets a `.ui.cjs` UI test for create, edit, unsaved-changes guard and the Markdown toggle.

### Updated scope

Sectile Desktop gets one task page, opened in the workspace for creation (Cmd+N, palette) and for edition (Tickets pane "…" menu, run header), replacing the quick add dialog. It edits title, a WYSIWYG Markdown description, assignee and the ordered pull request links, plus project and tracker at creation, and saves explicitly through new or extended agent routes gated by a capability. Everything else on the task stays read-only in Desktop.
