# Clarification Report — Ticket #722

**Ticket**: `#722` (`gh-8b726529-6cf4-48cb-91e1-cdb93ccf491c-722`)
**Title**: Stop every browser reloading three full lists on each task_updated event
**Date**: 2026-10-14
**Mode**: Autonomous (`pickup-issues` batch)

## 1. Context & Codebase Analysis

1. **Current SSE Fan-Out (`web/src/context/AppContext.tsx:2116-2145`)**:
   - On every `task_updated` SSE event, each connected browser calls `fetchTasks()`, `fetchActivities()`, and `fetchActivityStats()`, issuing 3 full list reads (`GET /api/tasks`, `GET /api/activities`, `GET /api/activities/stats`) per browser per event, and re-subscribing `EventSource('/api/events')` whenever `selectedTask` or any filter changes.
2. **Server Event Payload (`internal/handlers/handlers.go:35-40, 113-129, 258-274`)**:
   - `handlers.Event` already carries `Task *models.Task` and `Activity *models.TaskActivity`.
   - On a relayed event from another replica (`deliverRelayedEvent`, `handlers.go:258-274`), the receiving replica already loads `h.db.GetTaskByID(msg.TaskID)` and `h.db.GetActivityByID(msg.ActivityID)` once and broadcasts the hydrated `Event` to its local SSE subscribers.
   - On the writing replica (`NewHandler`'s post-back listener, `handlers.go:113-127`), re-reading `GetTaskByID(task.ID)` and `GetActivityByID(activity.ID)` before broadcasting ensures `task.ProjectID`, `task.ProjectIDs`, and `task.Batch` (as well as `activity.UserName`, `activity.TaskKey`, and `activity.TaskTitle`) are identically populated on the origin replica and on relayed replicas.

## 2. Decisions Recorded

1. **Update Tasks, Selected Task, Activities, and Activity Stats In Place from `task_updated` (`web/src/lib/taskUpdatedEvent.ts` & `web/src/context/AppContext.tsx`)**:
   - When a `task_updated` SSE event arrives carrying `data.task` and/or `data.activity`:
     - Update `selectedTask` in place when `sameTask(current, data.task)` holds.
     - Update `tasks` in place via `applyUpdatedTask(tasks, data.task, scope)`: replace an existing task if it still matches the active project/view and filters, remove it if it no longer matches, or insert it if it newly matches the active project/view and filters.
     - Update `activities` and `activityStats` in place via `applyUpdatedActivity(activities, activityStats, data.activity, selectedProjectId, data.task)`: replace an existing activity and adjust status bucket counts when its status changes, or prepend a new in-scope activity and increment `total` and its status bucket.
   - Keep a coalesced fallback (`createCoalescedRefetch`) only for bare `task_updated` events that carry neither `task` nor `activity`, so a burst of bare events triggers at most one refetch.
   - Keep `EventSource('/api/events')` stable across `selectedTask` and filter changes by reading the latest scope through a ref.

2. **Hydrate Origin `task_updated` Events Consistently (`internal/handlers/handlers.go`)**:
   - In `NewHandler`'s post-back listener, re-read `GetTaskByID(task.ID)` and `GetActivityByID(activity.ID)` when those records exist in the store, matching `deliverRelayedEvent` on other replicas.
