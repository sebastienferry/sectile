# Clarification #917 - Tauri: @ mentions for project files, folders, conversations, and tickets with inline chips

Ticket: https://github.com/sebastienferry/sectile/issues/917
Branch: `feat/917`

## Round 1 - initial analysis (2026-11-17)

### Request

In Sectile Desktop (Tauri), typing `@` in a conversation composer opens an
autocomplete popup listing the project's files and folders (working folder and
attached folders), its conversations and its tickets; picking a file, a
conversation or a ticket inserts an inline chip deleted atomically by
`Backspace`, picking a folder inserts `@path/` to keep browsing, and on send
each mention is resolved into a reference the provider can use. Out of scope:
the Electron client (`desktop/`), the web UI, the server, `/` slash commands,
mentions in the ticket editor, the question form and ticket comments, and any
mention of entities from another project.

### Current state

- Both composers are plain `<textarea>` elements bound to a string `draft`;
  nothing in `desktop-tauri`, `desktop` or `web` implements `@` mentions.
- The frontend already holds the project's conversations (execution snapshot)
  and tickets (`listTasks`); it has no file listing. No agent route lists the
  files of a working folder.
- The agent already knows how to render a conversation transcript within a
  character budget and inject it before a provider message (#906).

### Ambiguities (worst first)

1. **What "resolved reference" means per type.** A path or key only, or the
   content (file text, ticket description, conversation transcript) inlined
   into the provider message. Changes the agent code, the message size and
   what the provider sees. -> Q1, Q2.
2. **What the transcript shows after sending.** Chips (the user's text) or the
   expanded text the provider received. -> Q3.
3. **Which composers.** New-conversation composer, in-conversation composer,
   queued messages, ticket conversations. -> settled below (T1), confirm in Q4.
4. **Which conversations and tickets are listed.** Current conversation,
   archived conversations, finished tickets. -> settled below (T6, T7).
5. **Folder selection.** The ticket says folders insert `@path/` text rather
   than a chip; whether a trailing `@path/` left in the draft is sent as a
   folder reference. -> settled below (T5).

### Critical dependencies

- **New agent route** for safe file and folder listing (Go, `internal/agent`)
  plus a Tauri command proxying it. A Desktop newer than its agent gets a 404:
  the popup must still list conversations and tickets and say files are
  unavailable.
- **Agent-side resolution** of mentions in `POST /desktop/conversation`
  message handling, next to `withFormerContext`.
- **No editor dependency today**: the composer has no CodeMirror or
  ProseMirror; inline atomic chips need an editor component (T2).
- **Windows**: any `git` call the listing makes goes through
  `agentexec.Hidden` (repository AGENTS.md).
- **Large repositories**: the listing must be bounded in entries and time and
  cached per folder, or the popup stalls on a monorepo.

### Technical choices settled (reversible)

- **T1 - Composers.** Both conversation composers (new conversation and
  in-conversation, including when the message is queued). Not the ticket
  editor, the question form or the task comment fields.
- **T2 - Editor.** A small `contenteditable` composer component, without a new
  npm dependency, whose value stays a plain string: a mention is serialized as
  `@[label](sectile:<type>/<id>)` (`file`, `conversation`, `ticket`) and
  rendered as a non-editable chip; `Backspace` next to a chip removes the whole
  token. `controller.submit(string)`, the queue, `maxLength` and
  Enter/Shift+Enter keep working unchanged.
- **T3 - Trigger and popup.** `@` at the start of the draft or after
  whitespace opens a floating popup above the caret; arrow keys, Enter/Tab to
  pick, Escape to close (Escape no longer interrupts the turn while the popup
  is open). Case-insensitive substring filter with the matched part
  highlighted; icons from `Icon.tsx` per type. Results capped (around 50).
- **T4 - File index.** New `GET /desktop/mentions/files?projectId=&runId=&query=`
  on the agent: lists the conversation's working folder and the project's
  attached folders; in a Git checkout uses `git ls-files --cached --others
  --exclude-standard` (ignored files and `.git` excluded), otherwise a bounded
  walk skipping `.git` and `node_modules`; symlinks resolving outside the root
  are dropped; bounded (entries and time) and cached briefly per root. Ranking
  in the agent: prefix match on the base name, then path prefix, then newest
  `mtime`, a folder's `mtime` being the newest of its descendants. Paths are
  returned relative to their root, with the root label for attached folders.
- **T5 - Folders.** Picking a folder inserts `@<relative path>/` as text and
  reopens the popup scoped to that folder. On send, a `@path/` token naming an
  existing folder inside the roots is resolved as a folder reference.
- **T6 - Conversations listed.** The project's conversations from the
  execution snapshot, excluding the current one, archived ones included and
  marked archived, newest first after the text match.
- **T7 - Tickets listed.** The project's tickets from `listTasks`, every stage,
  matched on key and title; key prefix match first, then most recently updated.
- **T8 - Resolution site.** The agent resolves mentions when it receives the
  message: it validates each file and folder path against the roots again
  (never trusting the client), and appends a "Referenced context" block to the
  provider message; the user event keeps the original text so the transcript
  can show chips. Ticket and conversation mentions of another project are
  refused.
- **T9 - Tests.** Go tests for listing bounds, ignore rules, symlink escape,
  ranking and resolution; Vitest for the trigger, filtering, chip
  serialization, atomic Backspace, and submission of a draft with mentions.
- **T10 - Changelog.** One `Added` line under `[Unreleased]`.

### Open product questions (owner: @sebastienferry)

1. **Q1 - File and folder mentions: reference or content?**
   - (a) **Recommended**: path only (absolute path plus the path relative to
     its root); the provider reads the file with its own tools, which keeps
     messages small and always current.
   - (b) Inline the file content (bounded, text files only) in the message.
2. **Q2 - Ticket and conversation mentions: what does the provider receive?**
   - (a) **Recommended**: a ticket gives its key, full task ID, title, stage
     and external URL (the provider reads the rest with the Sectile MCP
     `get_task`); a conversation gives its title and a bounded transcript of
     its user and assistant messages, rendered like the #906 former context
     (about 30,000 characters per mention), since no MCP tool reads a
     conversation.
   - (b) Inline both fully: ticket description and comments, conversation
     transcript.
   - (c) Reference only for both (ID and title), no transcript.
3. **Q3 - What the transcript shows for a sent message with mentions?**
   - (a) **Recommended**: the user's message with the same chips as in the
     composer; the resolved block is hidden like the existing injected
     trailers.
   - (b) The raw expanded text the provider received.
4. **Q4 - Confirm scope of T1/T6/T7**: both conversation composers only;
   archived conversations listed (marked), current one excluded; tickets of
   every stage listed. Answer "OK" or name what to change.

## Round 2 - answers from the owner (2026-11-17)

Answers given interactively by @sebastienferry; every recommended option was
kept and the scope of Q4 confirmed. No product question remains open: the
clarification is settled.

### Settled choices

- **Q1 -> (a) Files and folders: path only.** The provider receives the
  absolute path and the path relative to its root (working folder or attached
  folder label); no file content is inlined. The agent re-validates the path
  against the roots before resolving it.
- **Q2 -> (a) Tickets: reference; conversations: bounded transcript.** A ticket
  mention gives its key, full task ID, title, stage and external URL, and tells
  the provider to read the rest with the Sectile MCP `get_task`. A conversation
  mention gives its title and a transcript of its user and assistant messages,
  rendered like the #906 former context, newest messages kept whole within
  about 30,000 characters per mention, tool events omitted.
- **Q3 -> (a) Transcript shows chips.** A sent message displays the same chips
  as the composer; the "Referenced context" block the agent appended is hidden
  from the displayed user message, as the existing injected trailers are.
- **Q4 -> OK.** T1, T6 and T7 stand: both conversation composers only (new
  conversation and in-conversation, queued messages included); archived
  conversations listed and marked, the current conversation excluded; tickets
  of every stage listed.

### Reversed assumptions

None. Technical choices T1 to T10 of Round 1 stand as written.

### Final scope (settled)

- `@` mention autocomplete in both Tauri conversation composers, over the
  project's files and folders (working folder and attached folders, Git-ignored
  entries excluded, bounded and safely scoped), conversations and tickets,
  with per-type icons and match highlighting; files and folders ranked by
  prefix match then newest `mtime` (propagated to ancestor folders).
- A `contenteditable` composer whose value stays a serialized string; files,
  conversations and tickets become atomic chips; folders insert `@path/` text.
- Agent route `GET /desktop/mentions/files` and its Tauri proxy; agent-side
  resolution on send as settled in Q1 and Q2; transcript chips as in Q3.
- Go and Vitest tests (T9); one `Added` changelog line (T10).
- Out of scope: Electron client, web UI, server, slash commands, other
  composers, cross-project mentions.

### Open product questions

None.
