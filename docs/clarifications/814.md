Have each local agent announce the projects available on its workstation at connection time and refresh that announcement as local configuration changes, so the authenticated server can list connected workstations for a project. - The relay currently sends projectId/deviceId connection parameters and heartbeat envelopes, not an availability inventory.
- Dispatcher keys are (userID, projectID), with default/all wildcard lookup. A second device in the same slot closes the first; the tests explicitly assert this. Supporting concurrent device inventories therefore requires changing connection registration even if execution selection remains a separate concern.

### Ambiguities, highest impact first

1. Multiple connected devices versus execution routing: maintaining all workstations changes today's replacement behavior. Selecting a launch target when several devices serve a project requires a separate policy.
2. Ready means either an accessible configured Git checkout or a validated execution environment (commands, providers, credentials, permissions and dependencies). These produce different inventory checks and failure behavior.
3. Paths and capabilities: the description suggests repository paths, but the existing contract deliberately keeps paths local. The title could also imply OS, installed CLIs or concurrency capacity, none of which appear in acceptance criteria.

### Recommended technical baseline

- Use a versioned inventory payload on the existing authenticated relay, rather than paths in connection query parameters. Associate it with the authenticated user and connection device; authorize advertised project IDs against that user's projects.
- Reuse localProjectRoot and existing settings resolution, including implicit current-repository fallback and disconnected-project exclusion; do not scan the disk or clone repositories.
- Replace each device's complete inventory atomically, including an explicit empty list. Refresh on connection/reconnection, Desktop configuration updates, and periodic revalidation to cover folder disappearance and external settings edits.
- Report only currently connected devices as available; remove their live availability when the connection ends. An in-memory connection-scoped registry is sufficient for these acceptance criteria; durable offline history is proposed as out of scope.
- Reuse the current agent status mechanism or an authenticated project-filtered helper, without requiring new UI. Keep repository paths and command templates local.
- Define explicit compatibility for agents that do not advertise an inventory; never silently treat a wildcard connection as proof every project is locally available. The owner must settle the routing scope before specifying compatibility behavior.

### Dependencies and acceptance implications

- Connection lifecycle, authenticated project discovery, local settings mutation, and dispatcher consumers must remain coherent. Reconnect and unregister must not erase a newer connection's inventory.
- Existing slot replacement and wildcard dispatch tests require revision if simultaneous device presence is accepted. Existing launch/cancel operations remain bound to their actual connection.
- No third-party service limit or database migration is required for the recommended live inventory; durable storage would change that assumption.
- Future validation should cover two devices with different and overlapping projects, empty/removal updates, invalid roots, disconnected projects, reconnect replacement, user isolation, and legacy agents.

### Open questions for the owner

1. Should #814 retain simultaneous connections and expose their availability only, with automatic selection and a workstation picker handled separately? Recommended: yes; settle any minimum compatibility required for existing launches during specification. Alternatively include inventory-aware automatic routing now, which needs a selection rule for overlapping projects.
2. Is an accessible local Git checkout, resolved by existing mappings/fallback and not disconnected, enough to count as available? Recommended: yes; missing CLI/credentials/build dependencies remain execution-time validation. Alternatively require full execution readiness and specify which checks are mandatory.
3. Does the advertised capability scope consist only of project availability, with local paths kept on the workstation? Recommended: yes. Alternatively identify the additional workstation fields required and whether repository paths must be uploaded.
