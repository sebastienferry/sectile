## Round 1 - initial analysis (2026-10-02)

### Restated request and scope

In Sectile Desktop's light appearance, the interactive console shows the agent's bold question text in near-white on the light background, so it cannot be read. Make console text readable in light mode. The dark appearance, the web interface's theme and a redesign of the light palette elsewhere in the app are out of scope.

### Verified findings

- The "interactive console" is the xterm.js terminal (`@xterm/xterm` 6.0.0). It renders the raw PTY output of the agent CLI: `desktop/src/main.js:61` creates it and `desktop/src/main.js:184` writes the bytes.
- The console already follows the appearance (#507). `desktop/src/main.js:60-62` switches `terminal.options.theme` between the two palettes of `TERMINAL_THEMES` (`desktop/src/appearance.mjs`).
  - The light palette sets the background to `#f5f6f8`, the foreground to `#111315`, `white` to `#6b7480` and `brightWhite` to `#8c949e`.
- No other xterm option is set: `minimumContrastRatio` stays at its default of 1, which does nothing.
- The PTY advertises 24-bit colour: `TERM=xterm-256color COLORTERM=truecolor` (`internal/terminal/terminal.go:159`).
  - Nothing tells the CLI that the background is light. There is no `COLORFGBG`, no theme flag and no `--settings`, and the Desktop appearance never reaches the agent (`internal/agent/agent.go:1217-1236`, `internal/agent/agent_config.go:577-578`).
- **Probable cause (a hypothesis, not reproduced):** Claude Code draws in RGB from its own theme. That theme defaults to dark, whose text colour is `rgb(255,255,255)`. RGB cells ignore the xterm palette, so the bold question text paints `#fff` on `#f5f6f8`, a contrast of about 1.1:1.
  - To confirm it, capture the raw PTY bytes of a Claude question in light mode and look for `ESC[38;2;255;255;255m`.
- **Secondary weakness (verified by calculation):** even palette colours are weak in light mode.
  - xterm draws bold ANSI white as `brightWhite` (`drawBoldTextInBrightColors` defaults to true), which is `#8c949e`, about 2.8:1 on `#f5f6f8`. That fails WCAG AA.
  - Plain `white` (`#6b7480`) is about 4.4:1.
  - `desktop/tests/appearance.test.mjs:33-38` only checks that the light colours have luminance < 0.6. It does not check contrast.
- **The lever exists:** xterm 6 has `minimumContrastRatio`. Its DOM renderer applies it to palette and RGB foregrounds alike (`node_modules/@xterm/xterm/src/browser/renderer/dom/DomRendererRowFactory.ts:426-442`, `_applyMinimumContrast`). Dim cells get half the ratio.
- The opt-in Conversation view (`desktop/src/conversation.js`, `claude -p --output-format stream-json`) renders HTML with the CSS tokens of `desktop/src/style.css`. It does not share this cause.

### Ambiguities (worst first)

1. **Which view.** Read "interactive console" as the Terminal view, the xterm console. The Conversation view is styled by CSS tokens and would need different code.
2. **How far "readable" goes.** Two readings:
   - Raise the contrast of the *text* (a contrast floor plus a darker `white`/`brightWhite`).
   - Also neutralise dark *backgrounds* that the CLI's dark theme paints into the light console, such as highlighted options and diff blocks.
   The second is a larger, heuristic change.
3. **Renderer fix or CLI theme.** Sectile could instead make Claude Code use its own light theme. That theme lives in the user's global Claude Code config, so this touches the user's settings outside Sectile. It also fixes one engine only: Codex and Gemini (#510) would still emit their own colours.

### Critical dependencies

- No server, migration or external service. The change is in the Desktop renderer: `desktop/src/main.js` and `desktop/src/appearance.mjs`, plus their tests.
- Third-party limits:
  - The colours come from each agent CLI's own theme, which Sectile does not control.
  - xterm's contrast adjustment changes the CLI's chosen hue (it darkens it). It does not restore the CLI's intended light-theme colours.
- An xterm upgrade could change `minimumContrastRatio` behaviour, so a UI test should pin the outcome.

### Technical choices resolved from the code (reversible)

- Fix it in the renderer and keep it engine-agnostic. Do not send the appearance to the agent, and never edit the user's Claude Code config.
- Set `minimumContrastRatio` to 4.5 (WCAG AA) in light mode, at the same switch point as the theme (`main.js:61-62`). The dark appearance stays pixel-identical: its palette values are pinned by `appearance.test.mjs`, and the dark ratio stays at 1.
- Darken the light palette's `white` and `brightWhite` so palette text meets 4.5:1 on its own. The light palette is not otherwise redesigned.
- Acceptance test shape for the specification:
  - A unit test asserting that every light ANSI foreground has a contrast of at least 4.5:1 against the light background.
  - A UI test in `desktop/tests/appearance.ui.cjs` that writes a bold truecolor-white sample (`ESC[1;38;2;255;255;255m`) into the light console and checks that the rendered colour reaches the ratio.

### Product questions (recommended option first)

1. **Which view?** Recommended: only the Terminal view (xterm console). Alternative: the Conversation view as well. Its CSS tokens would then need to be audited.
2. **Scope of the fix?** Recommended: a text contrast floor (WCAG AA 4.5:1) plus darker `white`/`brightWhite` in the light palette. Dark backgrounds painted by the CLI stay out of scope unless you have seen them. Alternative: also lighten or neutralise CLI-painted dark backgrounds in light mode.
3. **Renderer-only, or also switch Claude Code to its light theme?** Recommended: renderer-only, which covers every engine and does not touch your Claude Code settings. Alternative: also pass a light theme to Claude Code runs when Desktop is light.
