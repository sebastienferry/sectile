# #308 - Un lancement de skill concurrent n'est pas détecté, et le worktree est résolu par clé de tâche

Round 1 - 2026-09-21

## Request restated

Two independent defects let a skill launch collide with a session already working the same
task: the desktop "Next: …" guard only sees the local daemon's own queue, so a run declared
through MCP `start_run` by an external Claude Code session leaves the button active; and
`ensureLocalWorktree` derives the worktree path from the task key instead of resolving the
assigned branch, so it refuses a launch whose branch actually lives in another linked worktree.
The ticket asks for a server-side duplicate guard, a branch-based worktree resolution, an end
to the silent `feat/<key>` derivation, and caller attribution on the `agent_launch` activity.

Out of scope for this ticket: the queue admission logic itself (`sharesCheckout`,
`awaitRunSlot`), the full-chain runner, cancelling or reaping orphan runs, any change to how
stages or transitions are decided, and the desktop's own client-side guard beyond making it
honest about a server refusal.

## Technical choices resolved here (reversible, settled by existing code)

1. **A new dedicated DB helper, not an extension of `managedStageRunningUnsafe`.** That helper
   is the transition/postback guard (`stage.go:35`, `stage.go:131`, `postback.go:104`); adding
   `remote_run` to its skill list would silently change when transitions are blocked. Fix 1
   gets its own query over `remote_run` **and** the workflow skill ids, excluding
   `agent_launch` the same way.
2. **Branch resolution through `git worktree list --porcelain`**, parsed in `internal/agent`,
   rather than probing each candidate directory: it is the only command that reports every
   linked worktree and its branch in one call, including the main checkout, which makes the
   existing l.305-316 fallback a special case of the general rule instead of a separate branch
   of code.
3. **The refusal stays a `409 Conflict`** from the `run-skill` sub-action, before
   `StartAgentRun`, so no activity is recorded for a rejected launch. `run-skill` already
   answers `400` for client mistakes, so the status code carries the distinction.
4. **The desktop keeps its local guard** and additionally renders the `409` message; the
   client guard is an ergonomic nicety, the server one is the barrier.

## Open product questions

1. **Scope.** Does this ticket ship fixes 1, 2 and 3, with fix 4 (caller attribution on
   `agent_launch`: credential type, device) split into its own ticket?
   *Recommendation: yes — 1-3 are the safety fix, 4 is observability on a different surface and
   needs a schema column.*

2. **What makes the task "busy" for the 409, and can it be forced?** A run stuck `running`
   because a session died leaves no way to launch anything on that task ever again — which is
   exactly the shape of the `#296` residue. Options: (a) refuse unconditionally; (b) refuse,
   but accept an explicit `force` in the payload that the desktop surfaces as "a run is already
   active, stop it or launch anyway"; (c) refuse unless the run has been `running` past a
   staleness threshold.
   *Recommendation: (b). It keeps the barrier real while leaving the owner a way out, and it
   needs no timer. Also: should a run `waiting_since` (waiting for user input) count as busy?
   I would say yes.*

3. **Fix 3 — how strict?** Two readings of "do not derive `feat/<key>` in silence":
   (a) in worktree mode, require `task.BranchName` and refuse the launch when it is empty;
   (b) keep deriving it, but **persist** the derived name onto the task at the moment the
   branch is created, so every later launch resolves the same branch.
   *Recommendation: (b). (a) breaks the very first launch on every new task, which is the
   normal path — `agent_config_test.go:105` encodes it deliberately. (b) removes the
   divergence that caused occurrence 2 without adding a manual step.*

4. **Fix 2 — what happens when `.tasks/worktrees/<key>` exists but carries another branch?**
   Once the branch is resolved elsewhere, that stale path is simply unused. Options: (a) use
   the resolved worktree and leave the stale path alone; (b) use it and log a warning naming
   the stale path; (c) refuse, as today, on the grounds that the path is the task's own slot.
   *Recommendation: (b). (c) is the current bug.*

5. **The pending cleanup.** `.tasks/worktrees/#296` / `feat/296` and the orphan branch
   `claude/clarify-issue-workflow-bbb85f`: is removing them a manual operation for the owner
   (out of this ticket's code scope), or should the ticket also ship a detection/prune path?
   *Recommendation: manual, out of scope, and noted in the ticket. Note that with fix 2 the
   residue stops being blocking, which removes the urgency.*

### Settled decisions

1. **Scope.** This ticket ships fixes 1, 2 and 3. Fix 4 — caller attribution on the
   `agent_launch` activity (credential type, device) — is split into its own ticket; it needs a
   schema column and is observability rather than safety.
2. **The 409 guard.** `run-skill` refuses with `409 Conflict`, before `StartAgentRun`, when the
   task already carries an active run. A run in `waiting_since` (waiting for user input)
   **counts as active**. The refusal is overridable by an explicit `force` in the payload; the
   desktop surfaces it as "a run is already active — stop it, or launch anyway". No staleness
   threshold and no timer.
3. **Branch derivation.** `feat/<key>` keeps being derived when `task.BranchName` is empty, but
   the derived name is **persisted onto the task** at the moment the branch is created, so every
   later launch resolves the same branch. Launches on a task without a branch are not refused.
4. **Stale key path.** When `.tasks/worktrees/<key>` exists on another branch while the assigned
   branch lives in a different linked worktree, the resolved worktree is used and the stale path
   is reported as a warning. The current refusal is the bug and goes away.
5. **Cleanup.** Removing `.tasks/worktrees/#296`, `feat/296` and the orphan branch
   `claude/clarify-issue-workflow-bbb85f` is a manual operation for the owner, outside this
   ticket's code scope. Fix 2 makes the residue non-blocking, so it carries no urgency.

### Reversed prior assumptions

None. No Round 1 assumption was contradicted; all four technical choices recorded in Round 1
stand as written.

### Newly surfaced points, resolved here

- **Who may `force`, and what it skips.** Authorization mirrors `cancel-run`: the run's owner or
  an admin, the rule `ErrRunNotYours` already encodes (`internal/db/remoterun.go`). `force`
  skips the duplicate check **only** — mode validation, model validation and
  `ensureLocalWorktree` still apply, and it is never the desktop's default.
- **Where the derived branch is persisted.** `ensureLocalWorktree` returns the resolved branch
  already (`agent_config.go:262`, second return value); the write belongs to the dispatch caller
  that owns the task record, not to the git helper, which stays free of DB access.

### Settled scope for the specification stage

In scope: a dedicated DB helper counting active `remote_run` and workflow-skill activities; the
`409` + `force` path in the `run-skill` sub-action; branch-based worktree resolution through
`git worktree list --porcelain` with a warning on a stale key path; persistence of the derived
branch name; the desktop rendering of the refusal; and the rewrite of
`agent_config_test.go:56-59` and `:105`.

Out of scope: fix 4, `sharesCheckout` and the queue admission logic, the full-chain runner,
reaping or cancelling orphan runs, stage/transition decisions, and the residue cleanup.
