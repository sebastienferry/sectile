# Clarification #736: separate Macro and Issue specifications folders

Ticket: https://github.com/sebastienferry/sectile/issues/736
Work branch: `feat/736`

## Round 1 (2026-10-05)

### Request

A project's workstation settings gain a second specifications folder: the
current "Specifications folder" (`ProjectSettings.SpecPath`) becomes the
**Macro** specifications folder with its stored value, and a new, empty
**Issue** specifications folder lets the issue skill-set write its clarification
reports and specifications outside the code checkout, in a task worktree and
branch the agent prepares there, as it already does for macros.

Out of scope: any server-side or web setting (the folders stay workstation
settings, ADR 0027), the one-off upload from the web (#735), moving existing
specifications between folders, and changing where the macro skills write.

### Neighbouring features

- The macro worktree (ADR 0026, `ensureMacroWorktree`) is exactly the mechanism
  the ticket asks for, keyed by macro instead of task. It is reused, not copied.
- `prepare_macro_worktree` is how a macro skill invoked by hand (outside a
  Sectile launch) finds its folder; the issue skills have no equivalent.
- The multi-repository folder map (`SECTILE_REPOSITORIES`, roles `primary`,
  `changed`, `context`, `spec`) already advertises a `spec` folder to task runs.

### Ambiguities, worst first

1. **Hand-invoked issue skills.** `SECTILE_SPEC_*` only exist in a run Sectile
   launches. A `/specify-issue` typed in a session the owner opened (as this
   one) would not see the Issue folder and would write in the code worktree.
   Reading A: launched runs only. Reading B: an MCP tool (mirror of
   `prepare_macro_worktree`) the skills call when the variables are absent.
   B adds an MCP tool, so the bridge whitelist and its count tests change.
2. **Which artefacts move.** The clarification report
   (`docs/clarifications/<n>.md`) and the specification (`specs/<KEY>-<slug>/`
   or `openspec/changes/<KEY>-<slug>/`) are both "issue specifications" by the
   #487 definition. Reading A: both move. Reading B: only the specification.
3. **Publication of the specifications branch.** Who pushes it, whether a pull
   request is opened in the specifications repository, and whether the code
   pull request links to it.
4. **Handoff.** Whether `handoff-issue` removes the specifications worktree and
   branch, and on what condition.

### Critical dependencies

- No migration: the settings live in the workstation settings file. The new
  key must be added to `localProjectRoot`'s known keys and emptied by
  `WriteSettings` (memory "New Overrides key needs a merge").
- Skill fragments change, so the plugin golden files under
  `internal/skills/testdata/plugin` are regenerated (`UPDATE_GOLDEN=1`, outside
  the sandbox). The marketplace plugin is maintained by hand and is not touched
  here.
- If an MCP tool is added (ambiguity 1), `agentmcp`'s catalog whitelist, its
  count and the `mcptest` fixtures change too.
- Desktop UI tests need a `vite build` and run outside the sandbox.

### Technical choices settled from the code (reversible)

- **Storage.** `ProjectSettings.SpecPath` keeps its JSON key `specPath` and
  becomes the Macro folder, so an existing workstation keeps its value without a
  migration. The new field is `IssueSpecPath`, JSON `issueSpecPath`. The Go
  field may be renamed `MacroSpecPath` with the JSON key unchanged.
- **Resolution.** `localSpecRepo` becomes two resolvers sharing one helper:
  empty means the code checkout, a relative path is relative to it, a missing
  folder is refused with a message naming the setting ("Dossier des
  spécifications Macro" / "Dossier des spécifications Issue"; runtime messages
  stay French).
- **Worktree.** The issue worktree is prepared by the same code as the macro
  one (`ensureMacroWorktree` generalised): `.tasks/worktrees/<safe task key>`
  in the Issue folder, fetch bounded to 30 s, existing tree reused as it is,
  worktrees off returning the checkout, a non-Git folder written in place with
  a warning and no branch.
- **Branch name.** The specifications branch carries the task's own branch name
  (`feat/736` here), so the two branches of one task read as a pair. When the
  task has no branch yet, the task branch the launch computes is used.
- **Only when distinct.** The agent prepares a specifications worktree only
  when the resolved Issue folder is not the code checkout; otherwise nothing
  changes and the issue skills behave as today.
- **Environment.** Task runs get `SECTILE_SPEC_REPO`, `SECTILE_SPEC_BRANCH` and
  `SECTILE_SPEC_WORKTREE`, pointing at the task worktree and branch when the
  Issue folder is the code checkout, so a skill always reads one place. A skill
  that finds no such variable writes in its current worktree, as today.
- **Dropped artefacts (#487).** The exclude block is written in the checkout
  that holds the issue specifications, the Issue folder when it is distinct.
- **Folder map.** A task run's folder map lists the Issue folder as the `spec`
  entry with its task worktree; the Macro folder is not listed in a task run,
  since no task operation reads it. Macro runs keep listing the Macro folder.
  `attachFolder` refuses either folder.
- **Checks.** `transition_stage` keeps checking the code worktree only; the
  specifications worktree is not part of the PR-commit check.
- **ADR.** A new ADR supersedes ADR 0027 in part (one folder becomes two).

### Product questions (owner)

1. **Hand-invoked issue skills.** Recommended: add a `prepare_task_spec_worktree`
   MCP tool, the issue counterpart of `prepare_macro_worktree`, so the Issue
   folder is honoured whether the skill was launched by Sectile or typed by
   hand. Alternative: launched runs only; a hand-typed skill writes in the code
   worktree.
2. **Artefacts moved.** Recommended: both the clarification report and the
   specification go to the Issue folder. Alternative: the specification only;
   clarification reports stay in the code repository.
3. **Publication.** Recommended, as for macros: the issue skill commits only the
   task's artefacts in the specifications worktree and pushes its branch;
   opening a pull request in the specifications repository is the human's
   gesture; the code pull request description names the specifications
   repository and branch. Alternative: the skill opens that second pull request
   and records it on the task next to the code one.
4. **Handoff.** Recommended: `handoff-issue` removes the specifications worktree
   and its local branch only when that branch is merged into the
   specifications repository's default branch, and otherwise keeps both and
   says so in its report. Alternative: always remove the worktree, keep the
   branch.
