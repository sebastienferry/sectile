## Round 1 (2026-09-26)

### Restated request and scope

The server pings every live MCP session every 25 s, so no proxy cuts the
standalone `GET /mcp` stream, and closes a session with no adopted run after
3 consecutive failed pings, so orphaned sessions stop piling up for 8 h. The
ingress change in the deployment repository, `/api/events` and
`/ws/agent-connect` are out of scope.

### Verified findings

- `internal/handlers/agent_api.go` serves `/mcp` with
  `StreamableHTTPOptions{JSONResponse: true, SessionTimeout: 0}` and no
  `ServerOptions.KeepAlive`. `internal/taskmcp/sessions.go` holds the registry, its
  silence (`SECTILE_MCP_SESSION_TIMEOUT`, 4 h) and abandon
  (`SECTILE_MCP_SESSION_ABANDON_AFTER`, 8 h) bounds and a sweeper goroutine.
- go-sdk v1.7.0 has `ServerSession.Ping`. With `JSONResponse: true`, a request made
  on a detached context goes to the standalone SSE stream. With no stream open,
  and no `EventStore` configured, the write fails at once ("undelivered
  message"): nothing is buffered, so pinging a session that has no stream costs
  nothing.
- `Touch` is called from a receiving middleware, which only sees client-to-server
  methods. A ping *reply* is a response, not a method, so it never reaches
  `Touch`. The acceptance criterion "a ping reply does not call `Touch`" holds by
  construction, and a test will pin it.
- Only sessions that created their own run adopt it (`start_run` without a
  runId). A launcher run is not adopted, so a session carrying only one is a
  session "without an adopted run".
- The settings are documented in `README.md` (MCP session section).

### Ambiguities

1. **A client that posts but never opens the `GET` stream** fails every ping,
   although it is alive. Closing it would make it re-initialize, which is the
   churn this ticket removes. Resolved: a client message resets the failure
   count. A session is closed only after 3 consecutive failed pings with no
   client message between them. The orphaned sessions the ticket describes say
   nothing, so they are still closed.
2. **Ping timeout.** Resolved: half the interval, as go-sdk's own keepalive does,
   so a ping never overlaps the next one.
3. **Setting names.** Resolved: `SECTILE_MCP_KEEPALIVE_INTERVAL` (duration,
   default 25s) and `SECTILE_MCP_KEEPALIVE_FAILURES` (integer, default 3), parsed
   like the existing ones: an invalid or non-positive value keeps the default.

### Resolved technical decisions

- Pinging lives in `SessionRegistry`, not in go-sdk's `ServerOptions.KeepAlive`,
  as the ticket requires: a close the SDK decides would go through
  `SessionRegistry.Close`, which cancels adopted runs.
- One registry loop pings all live sessions each interval, concurrently and
  outside the lock. No goroutine per session.
- A session with an adopted run keeps being pinged, and a failure is logged,
  but it is never closed by the keepalive. The silence notice and the 8 h
  abandon keep their #319 meaning.
- Closing an orphan goes through the same path as abandonment
  (`Close` then `ServerSession.Close`), so its goroutines are released.

### Critical dependencies

- The ingress `timeout-server` change is the owner's, in the deployment
  repository (branch `fix/sectile-mcp-stream-timeout`, not pushed). It is
  independent of this fix.
- The "flat `go_goroutines` over 24 h" criterion can only be checked after
  deployment. It stays open until the owner observes it.

### Questions

None. The ticket fixes the behaviour and the values. The three points above are
reversible technical choices.

- `internal/handlers/`: reading the two settings and passing them to the registry.
- Tests: one session kept across more than the proxy's silence with a short
