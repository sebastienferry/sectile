## Round 1 (2026-09-25)

### Restated request and scope

The search bar in the web header must find a ticket whatever the case of the
query and of the ticket's text: `BUG`, `bug` and `Bug` return the same tickets.
Out of scope: fuzzy or typo-tolerant search, ranking, full-text indexing,
searching comments, and the facet pickers of the filter panel (they already
fold case in the browser).

### Verified findings

Files read: `web/src/components/Header.tsx`, `web/src/context/AppContext.tsx`
(`buildTaskQuery`), `web/src/lib/roadmap.ts` (`matchesEpicSearch`),
`web/src/components/TriageView.tsx`, `web/src/components/ActivitiesView.tsx`,
`web/src/components/TaskFilters.tsx`, `internal/handlers/handlers.go`,
`internal/db/db.go` (`GetTasksInScope`, `GetActivities`, `lowerASCII`,
`asciiLower`, `viewLabelScope`, `escapeLike`), `internal/db/dialect.go`,
`internal/db/dialect_sqlite.go`, `internal/db/dialect_postgres.go`.

- The header search is not filtered in the browser. `buildTaskQuery` sends it
  as `q` to `GET /api/tasks`, except on the roadmap, which filters its rows
  itself.
- The server matches it at `internal/db/db.go:1662` with a raw
  `key LIKE ? OR title LIKE ? OR description LIKE ? OR labels LIKE ? OR assignee LIKE ? OR parent_key LIKE ? OR parent_title LIKE ?`
  and the pattern `%<query>%`.
- **Root cause.** `LIKE` means two different things on the two engines Sectile
  supports since #407:
  - SQLite: case-insensitive for ASCII letters only (`é` does not match `É`);
  - PostgreSQL: case-sensitive. `bug` does not find `Bug`.
  The shared remote server runs PostgreSQL, which
  explains the report.
- The activities view has its own search input, sent as `q` to
  `GET /api/activities`, and matched by the same raw `LIKE` pattern at
  `internal/db/db.go:5286`. It has the same defect on PostgreSQL.
- The browser-side searches already fold case with `toLowerCase()`: roadmap
  (`matchesEpicSearch`), triage, facet pickers. They are Unicode-aware, so
  there they already treat `É` and `é` as the same letter.
- The codebase already has a convention for case-insensitive comparison that
  behaves identically on both engines: `lowerASCII` on the column
  (`LOWER(x)` on SQLite, `LOWER(x COLLATE "C")` on PostgreSQL) and
  `asciiLower` on the Go value, as used by `viewLabelScope` (ADR 0025). It
  folds A-Z only, on purpose, because PostgreSQL's `LOWER` on non-ASCII letters
  depends on the cluster's collation.
- The query is not escaped: `%` and `_` typed in the bar act as wildcards.
  `escapeLike` exists next to `viewLabelScope`.

### Ambiguities (worst first)

1. **What "case insensitive" covers for accented letters.** Two readings lead
   to different code:
   - (a) ASCII only: reuse `lowerASCII`/`asciiLower`. Identical on both
     engines, no migration, but `équipe` still misses `Équipe`.
   - (b) Full Unicode case: `é` finds `É`. On PostgreSQL this needs a
     collation-independent Unicode fold (for instance `LOWER(x COLLATE "und-x-icu")`
     where ICU is available, or folding in Go on a stored normalized column).
     On SQLite, `LOWER` does not fold non-ASCII without the ICU extension, so
     it needs a Go-registered function or a stored folded column, meaning a
     migration.
   Accent-insensitivity (`equipe` finds `Équipe`) is a third, larger step and
   is assumed out of scope.
2. **Does the activities search belong to this ticket?** It has the same
   defect, the same fix, and a different input. Including it or not changes
   the diff.

### Critical dependencies

- Both SQL engines must behave the same way. The tests must run against
  PostgreSQL as well as SQLite (`SECTILE_TEST_POSTGRES_DSN`, see the
  PostgreSQL test notes); a SQLite-only test would pass on the buggy code.
- Reading (b) needs a migration or an engine extension; reading (a) needs
  neither.

### Reversible technical choices resolved from the code

- Fold both sides with the existing helpers (`lowerASCII` on the column,
  `asciiLower` on the query) rather than `ILIKE`, which exists on PostgreSQL
  only and would fork the query per engine.
- Escape `%`, `_` and `!` in the query with `escapeLike` and `ESCAPE '!'`, as
  `viewLabelScope` does, so a literal `50%` searches for `50%`.
- Leave the browser-side searches as they are: they already ignore case.
- No user-visible text changes; a `Fixed` line goes under `[Unreleased]` in
  `CHANGELOG.md`, since the fix is user-visible.

### Product questions

1. **Accented letters.** Recommended: (a) ASCII case folding now, consistent
   with the existing label filter and saved views, and a follow-up ticket for
   Unicode case and accent folding if needed.
2. **Activities search.** Recommended: include it, since it is the same defect
   and a two-line change.

## Round 2 - answers from the owner (2026-09-25)

### Answers

1. **Accented letters: case and accents.** The search ignores both case and
   diacritics: `equipe`, `Equipe` and `ÉQUIPE` all find `Équipe`.
2. **SQLite is not considered.** The owner states that SQLite support is meant
   to be retired, so its behaviour is not a requirement of this ticket.
3. **Activities search: included.**

### Reversed assumptions

- Round 1 recommended ASCII-only folding through `lowerASCII`/`asciiLower`.
  That recommendation is withdrawn: it cannot fold accents.
- Round 1 listed accent-insensitivity as out of scope. It is now in scope.
- Round 1 required identical behaviour on both engines. Only PostgreSQL is
  required now.

### New findings

- PostgreSQL 16 is the engine used in CI (`postgres:16` service in
  `.gitlab-ci.yml`) and on the shared server. No extension is created anywhere
  in the codebase today.
- `unaccent` is a contrib extension marked *trusted* since PostgreSQL 13: a role
  holding `CREATE` on the database can install it without being superuser. It
  is available on the usual managed offerings.
- `unaccent()` maps `É` to `E`, which makes the fold independent of the
  cluster's collation when it is followed by `LOWER(... COLLATE "C")`: after
  `unaccent`, the letters left to lower are ASCII in the common Latin cases.

### Technical choices resolved from the code (reversible)

- **Approach on PostgreSQL:** a numbered migration in `migrations.go` runs
  `CREATE EXTENSION IF NOT EXISTS unaccent`, and a new dialect method folds
  both the column and the pattern as
  `LOWER(unaccent(<expr>) COLLATE "C")`. No stored column, no backfill.
  A Go-maintained folded column was considered and rejected: tasks are written
  from many paths (tracker sync, MCP, UI), and every one would have to keep it
  up to date.
- **SQLite:** the dialect method keeps today's behaviour (`LOWER(<expr>)`), so
  the SQLite build still compiles and runs; no effort is made to fold accents
  there, per answer 2.
- **Fields searched:** unchanged. Tasks: key, title, description, labels,
  assignee, parent key, parent title. Activities: skill name, summary, output,
  task key, task title.
- **Wildcards:** `%`, `_` and `!` typed in the bar are escaped with
  `escapeLike` and `ESCAPE '!'`.
- **Browser-side searches** (roadmap, triage, activities list filtering in the
  browser, facet pickers) fold case already; making them accent-insensitive
  too, so that the roadmap and the board agree, is done with a shared
  `normalize('NFD')` plus diacritic strip helper. This keeps the header bar
  consistent across views.
- **Tests:** PostgreSQL tests under `SECTILE_TEST_POSTGRES_DSN` cover
  `bug`/`Bug`/`BUG` and `equipe`/`Équipe`/`ÉQUIPE` on both searches, and a
  literal `%`. Browser helpers get unit tests.
- **Changelog:** one `Fixed` line under `[Unreleased]`.

### Critical dependency

- The migration fails if the database role lacks `CREATE` on the database or
  the server lacks the contrib package. A failed migration stops the server at
  start. This is the one deployment prerequisite; see question 3.

### Product question

3. **Deployment prerequisite.** Can the migration assume the shared server's
   database role may create the `unaccent` extension? Recommended: yes, and the
   migration fails loudly with an explicit message naming the extension if it
   cannot, rather than silently falling back to case-only search.

## Round 3 - answers from the owner (2026-09-25)

3. **Deployment prerequisite: settled as recommended.** The migration assumes
   the shared server's role can run `CREATE EXTENSION IF NOT EXISTS unaccent`.
   If it cannot, the migration fails with an explicit message naming the
   extension and the server does not start. No silent fallback to case-only
   search.

The owner confirmed that the clarification is satisfactory. No product
question remains open.

## Settled scope

- The header search bar (tasks, `GET /api/tasks?q=`) and the activities search
  (`GET /api/activities?q=`) ignore case and diacritics on PostgreSQL.
- Implementation: numbered migration creating `unaccent`; a dialect method
  folding column and pattern with `LOWER(unaccent(<expr>) COLLATE "C")`;
  `%`, `_` and `!` escaped in the query.
- SQLite keeps its current behaviour and is not a requirement.
- Browser-side searches (roadmap, triage, activities, facet pickers) become
  accent-insensitive through one shared helper, so every view answers the same.
- Out of scope: fuzzy search, ranking, indexing, searching comments, and the
  label filter (`labels LIKE ?`).
- Tests on PostgreSQL (`SECTILE_TEST_POSTGRES_DSN`) and browser unit tests; one
  `Fixed` line in `CHANGELOG.md`.
