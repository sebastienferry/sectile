## Ambiguities, worst first

1. **Which placeholders constitute parity?** Adopt all eight tokens supported by server command preparation, rather than only the five advertised in its web UI. This follows the ticket's explicit reference to server support.
2. **Which machine supplies paths and branches?** Use the resolved local execution directory and branch. A server filesystem path or a synthetic branch would be unsuitable for a local CLI command. `{issueKey}` remains the human-facing key such as `#63`, while existing skill invocation and run tracking retain the full task ID.
3. **Does parity mean copying raw shell substitution?** Preserve the local agent's protection of inserted data and extend it to the new values. Quotes, whitespace, multiline descriptions, dollar signs, backticks, and shell metacharacters must remain data. Do not recursively expand placeholder-looking text inside values. Exact parsing and helper structure belong to specification.
4. **Which launch paths change?** Apply expansion wherever a task skill or custom-instructions launch uses the configured CLI template, including relaunch and terminal-routed skill execution. Preserve explicit raw terminal commands and the existing no-skill interactive launcher.

## Settled scope and assumptions

| Token | Value |
| --- | --- |
| `{prompt}` | Existing assembled local launch instructions, including run metadata |
| `{issueKey}` | Task display key |
| `{issueTitle}` | Task title |
| `{issueDesc}` | Task description, including an empty description |
| `{branchName}` | Branch resolved for local execution |
| `{repoPath}` | Absolute local execution directory, including the task worktree when used |
| `{tracker}` | Lowercase task source, then effective project tracker, with the server's `github` fallback |
| `{repo}` | Effective configured GitHub repository when present; otherwise the basename of the local execution directory, matching the server fallback |

- Retain local override versus server inheritance, save/reset behavior, provider defaults, and the existing `{prompt}` requirement for configured task-launch templates.
- Leave unknown tokens literal, consistent with existing replacement behavior; introduce no new validation language.
- Support repeated recognized tokens and the existing quoted/unquoted prompt usage without executing inserted values as shell code.
- Expand at launch using current task metadata and local execution context; persist the template itself, not a command containing a previous task's values.
- Update desktop placeholder help and relevant documentation during implementation. No code or specification is produced in this clarification stage.
