# Clarification of #841: WebUI : Always provide ticket link in toaster

Ticket: https://github.com/sebastienferry/sectile/issues/841
Task ID: gh-419341cd-a3ed-4229-acb5-9680f5dbc522-841
Report path: `docs/clarifications/841.md`, committed on `feat/841`.
Project: Sectile. The ticket has no description and no comments; its parent is a macro.

## Round 1 (2026-10-15)

### Request

Every WebUI toast that concerns a ticket offers a link to that ticket, so the user can reach it from the notification. This is the follow-up of #840 (merged in #845), which added the link only to the success toasts of issue creation, cloning, macro stories and ordinary edits, and explicitly left warnings, failures, move/export, run outcomes and every other notification without one. Out of scope: toasts that concern no ticket (settings, projects, board views, credentials, global sync), macro-only toasts, the Desktop app's native notifications, and the toast design, lifetime and pause behaviour.

### Evidence and files read

- `docs/clarifications/840.md` and commit `23ade8f0` (#845): the scope #840 settled and what it left out.
- `web/src/lib/issueToast.ts`: `issueToastLink` builds "Open #N" (in-app) plus the tracker icon, or a tracker-only link.
- `web/src/types/index.ts`: `ToastMessage` carries one `link` or a `links` list; `ToastLink` is in-app (`onOpen`) or external (`externalUrl`).
- `web/src/components/ToastContainer.tsx`: renders every link; a linked toast waits for the user (pause on hover and focus).
- `web/src/context/AppContext.tsx`: 119 `addToast` calls across about 60 handlers; `taskLink`, `tokenOfferToast`, `refusalToast`; the activity poller that announces finished runs.
- Targeted call sites in `TaskDetailModal.tsx`, `TaskCard.tsx`, `RemoteRunBadge.tsx`, `ExecutionRecovery.tsx`, `CommandPalette.tsx`.

Toasts that name one ticket and carry no link today (non-exhaustive):

### Ambiguities, worst first

1. **Which toasts.** "Always" may mean every toast that names a ticket (success, info, warning and error), or only the outcome toasts #840 left out (runs, transitions, moves). The two readings change the number of handlers touched from about ten to about forty.
2. **Error toasts with a credential offer.** `refusalToast` replaces the error toast with a token offer whose single `link` opens the credentials. Adding the ticket link means showing two actions in one toast, or keeping the offer alone.
3. **Toasts for several tickets.** Bulk sprint/team/macro moves and batch creation produce one toast for N tickets: one link per ticket, a capped list, or none.
4. **Deleted tickets.** After a deletion there is nothing to open in Sectile; a tracker link may still point to an existing issue, or to nothing, depending on what deletion did on the tracker.

### Critical dependencies

- Run outcome toasts come from activities, which carry `taskId`/`taskKey` but no `Task`. The ticket may be outside the loaded board (another project or filter). Opening it needs the ticket fetched by id on click; no new endpoint is expected, since the task detail is already readable by id.
- `ToastMessage` already supports `links`, so two actions per toast need no type change.
- No migration, server change or new dependency is identified. A user-facing changelog entry under `[Unreleased]` is needed.

### Reversible technical choices (settled here)

- Reuse `issueToastLink` and the `taskLink` wrapper for every new link, with the same labels as #840 ("Open #N" plus the tracker icon; tracker-only link when there is no local task).
- When a handler has the returned `Task`, link it directly. When it has only an id (activities, errors), resolve the ticket from the loaded board first and fetch it by id on click otherwise; never fabricate a `Task`.
- Keep toast presentation, lifetime and pause behaviour. A linked toast already waits for the user, as #840 established; that now applies to more toasts.
- Desktop native notifications stay untouched: the ticket title says WebUI.

### Open questions for the owner

1. **Scope.** Recommended: every toast that concerns exactly one ticket gets its link, whatever its type (success, info, warning, error), including run outcomes from the activity poller. Alternatives: (b) success and info toasts only, errors unchanged; (c) only the run and stage outcome toasts.
2. **Errors with the token offer.** Recommended: show both actions, the credentials offer first and the ticket link second. Alternative: keep the offer alone, as today.
3. **Several tickets.** Recommended: one link per ticket up to five, then "+N more" with no link. Alternatives: a link for every ticket; no link on multi-ticket toasts.
4. **Deletion.** Recommended: no link on the deletion toast. Alternative: a tracker link when the deleted ticket had an external URL.

## Round 2 - answers from the owner (2026-10-15)

### Settled scope and decisions

The owner chose the recommended option for each Round 1 question, then explicitly confirmed that the resulting clarification is satisfactory. The exit condition is met.

1. **Scope.** Every WebUI toast that concerns exactly one ticket offers its link, whatever its type (success, info, warning, error). This includes the run outcome toasts raised by the activity poller, run queue/retry/cancel, stage transitions and moves, single-ticket sync, comments and single-ticket field updates, and the error toast of each of these handlers.
2. **Errors with the token offer.** The toast shows both actions: the credentials offer first, the ticket link second.
3. **Several tickets.** A toast about several tickets offers one link per ticket up to five, then a "+N more" line without a link.
4. **Deletion.** The deletion toast offers no link.
5. **Unchanged.** Toasts that concern no ticket, macro-only toasts, the Desktop app's native notifications, and the toast presentation, lifetime and hover/focus pause stay as they are. The links reuse the #840 labels and helper ("Open #N" plus the tracker icon; a tracker-only link when there is no local task).

No Round 1 assumption was reversed and no new ambiguity surfaced. Open product questions: none.

### Carried into specification

- Activities carry `taskId`/`taskKey` without a `Task`: resolve the ticket from the loaded board, and fetch it by id on click when it is not loaded. Never fabricate a `Task`.
- `ToastMessage.links` already holds several actions; the "+N more" line needs a new string in both locale catalogs.
- No migration, server change or new dependency is identified. Implementation adds a user-facing changelog entry under `[Unreleased]`.
