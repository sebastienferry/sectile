## Round 1 (2026-09-25)

### Restated request and scope

Prove, in CI, that two server instances sharing one PostgreSQL database serve as one:
an agent operation requested through the replica that does not hold the agent, a
board update seen on the other replica's event stream, an MCP session used through
both, and a replica killed mid-run whose agent reconnects to the survivor. Add a
readiness probe distinct from `/api/health`, and document the topology (new ADR,
amendment of ADR 0016, README, CHANGELOG) so an operator knows everything the external
deployment needs.

Out of scope: the change to the external deployment repository (replica count, probe
wiring, disruption budget, ingress timeouts), settled as the owner's follow-up in
#397 Q4; multi-replica on SQLite; horizontal autoscaling.

### Verified findings

1. **In-process tests cannot kill a replica.** The existing two-instance tests share one
   Go process: "killing" one means closing its listeners, but its heartbeat goroutine
   keeps the instance row fresh, so survivors never declare it dead. A faithful node
   kill needs real processes.
2. **`/api/health` cannot serve as readiness.** It answers before the store is proven
   reachable and whatever the state of the internal listener, so a balancer would send
   traffic to a replica that cannot reach its peers.
3. **Liveness bounds are compiled in.** Dead-after is 45 s: a kill test waits that long
   unless the bounds can be shortened for the harness.

### Ambiguities, worst first

- **A1: What happens on a deliberate stop** (Q1). A rolling deploy sends SIGTERM; today
  the process dies at once and its peers take 45 s to notice.

### Critical dependencies

- The `test:postgres` job (PostgreSQL 16 service) is where the harness runs; `test:go`
  has no database and skips it, as it skips every PostgreSQL test.
- Budget: the harness builds the server binary once and waits for one death; it must
  stay well under the job timeout.
- Public repository: no internal host, project or secret name in the operator
  documentation.

### Resolved technical decisions (reversible)

- **D1: Real processes.** The harness builds `cmd/server`, starts two instances on one
  database and kills one with SIGKILL. A small balancer in the test spreads requests
  and agent connections over the live replicas, and a scripted agent speaks the agent
  protocol over the WebSocket.
- **D2: Shorter bounds for the harness only.** Heartbeat, dead-after and reclaim
  intervals become overridable by environment variables, documented as test settings,
  defaults unchanged.
- **D3: Readiness at `/api/ready`, public like `/api/health`.** 200 once the store
  answers a ping and, on a shared store, this instance is registered and its internal
  listener serves; 503 with the reason otherwise. `/api/health` stays the liveness
  probe.
- **D4: Documentation.** ADR 0030 records the active/active topology and points at each
  child ticket; ADR 0016 gets an amendment; the README gains an "Several replicas"
  section (shared `SECTILE_SECRET_KEY`, PostgreSQL, `SECTILE_INTERNAL_PORT` and
  `SECTILE_INTERNAL_URL`, probes, disruption budget, WebSocket and SSE timeouts); one
  CHANGELOG line under `[Unreleased]`.

### Open product questions

**Q1: Should a deliberate stop (SIGTERM) drain the replica?**
Options: (a) no drain: the process stops as today, its agents reconnect and its MCP
sessions are lost, peers reclaim its work after the dead-after bound (the loss settled
for #397 Q2); (b) minimal drain: on SIGTERM readiness turns 503 at once, and the
instance removes its row and closes its connections after a short grace, so peers
take over in seconds rather than 45 s. Recommendation: **(b)**: it is a few dozen
lines, it is what a rolling deploy exercises every time, and the harness can test it
alongside the kill.
