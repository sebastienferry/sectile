# Clarification #312 — The auto-sync runs without an actor and falls back on the server credential

Ticket: https://github.com/sebastienferry/sectile/issues/312
Type: Technical debt, split from #310 (round 2, decision 1).
Branch: `feat/312`.

## Round 1 — scoping (2026-09-23)

### Restatement

The ticket says the auto-sync loop queues its work with no acting user, so every background read resolves the
project or server credential. A tracker that has only personal credentials therefore cannot be synchronised, and the
activity records nobody. The ticket asks which actor the loop should borrow, and requires that no background sync
path falls back on the server credential unless that fallback was decided on purpose.

Out of scope: the `task_activities` schema (#310), agent and MCP credential resolution (ADR 0019 / 0020), and any
change to the write paths a person triggers.

### The premise is mostly outdated

The ticket was written against a tree older than #328 (`bd19427`, ADR 0018 "The background synchronisation runs as
the project's owner"). On the assigned branch (`1b61c40`, current `main`):

- `EnqueueSingleTaskSync` no longer exists. The loop queues one project pass through
  `EnqueueSyncWith(owner, …, SyncOptions{Background: true})` (`internal/db/autosync.go:222-224`).
- The actor is `projects.owner_user_id`. It is set to the project's creator, adopted by the first person who saves a
  project that predates the column (`db.go:6014`), never read from a payload, and never replaced.
- `processSyncJob` restores `job.ActingUser` into the context (`db.go:4013`), and the activity stores the owner in
  `user_id` (`db.go:4680`).
- Jira: `JiraAdapter.forProject` (`internal/trackerapi/jira.go:59-70`) returns an error when the owner's sealed
  credential is locked, and refuses when the owner has no personal token. It never falls back silently.
- Ownerless project: the server credential is kept. ADR 0018 decided this on purpose ("what `SECTILE_JIRA_TOKEN` is
  for").

The ticket's three consequences are covered for Jira: a tracker with only personal credentials syncs in the
background, the rights applied are the owner's, and the activity carries a `user_id`. The four options the ticket
offered have been decided: option 1, the project owner, as recorded by ADR 0018.

### What remains: the GitHub residue

One background path still falls back without a decision behind it. `GithubAdapter.forProject`
(`adapters.go:90-96`) handles a `ForActingUser` error, which is how a **locked** sealed credential surfaces, by
returning `g.client.For(projectID)`: the project or server token. The GitHub sync reads (`FetchSingleGithubIssue`,
`IssuePullRequests`, …) go through it. So a background pass whose owner sealed their GitHub token and did not unlock
it reads with the server token and records the owner in `user_id`. The activity then names someone whose credential
was never used. That contradicts ADR 0018 ("a locked credential still fails, loudly … instead of falling back to the
server") and the ticket's acceptance criterion.

`trackerAs` (`trackercredentials.go:85`) has the same fallback, but none of its callers is a background sync path
(`adjustment.go:127`, `agentoperations.go:121`, `board.go:171`). It is out of scope here.

A second GitHub case is different: an owner who stored **no** personal GitHub token gets the project or server token.
`ForActingUser` returns `personal == false` without an error. Unlike Jira, the GitHub adapter does not refuse in that
case. This is arguably correct, since a GitHub token has always been a project credential as well (`projects.github_token`).
It is still an undecided fallback in the ticket's sense.

### Reversible technical choices, settled here

1. Any change stays in `GithubAdapter.forProject`. The loop and the queue stay as they are.
2. The refusal message follows the Jira adapter's wording and language (English error, surfaced in the French
   activity steps as-is).
3. Tests go next to the existing adapter tests, one per case: locked credential and missing personal token.

### Dependencies

- ADR 0018 (#328): the behaviour this ticket asked for, already merged.
- ADR 0014: the sealed-credential semantics that make "locked" an error.
- No migration, no external service, no third-party limit.

### Open product questions

1. **Is #312 superseded by #328?** *Recommendation: yes for its stated premise. Keep the ticket open only for the
   GitHub residue below, retitle it accordingly, and close it if you answer "no change" to question 2.*
2. **GitHub, locked owner credential in a background pass: refuse or fall back?** *Recommendation: refuse, like Jira,
   with a failed activity naming the owner. That is what ADR 0018 already states.*
3. **GitHub, owner has no personal token: keep falling back on the project or server token?** *Recommendation: keep
   it, and record the decision (a line in ADR 0018's consequences). A project GitHub token is a legitimate project
   credential, and refusing would break every deployment configured through `SECTILE_GITHUB_TOKEN` or the project
   field.*
4. **Should the refusal in question 2 apply only to background passes, or to every GitHub call routed through
   `forProject` with an actor** (interactive writes included)? *Recommendation: every call. The same misattribution
   applies to a person's request, and a background-only check would need a flag the context does not carry today.*

To be decided by the ticket owner.

### Acceptance criterion (restated against the current tree)

A background pass never reads with a credential other than the owner's when the owner's credential exists but is
locked. The activity's `user_id` names only an account whose credential was actually used. Every remaining fallback on
the server credential (ownerless project, and possibly an owner without a personal GitHub token) is recorded as a
decision.

## Round 2 - answers from the owner (2026-09-23)

The owner accepted all four Round 1 recommendations.

### Settled decisions

1. **Scope.** #328 (ADR 0018) covers the ticket's original premise. #312 stays open for the GitHub residue only, and is
   retitled to say so.
2. **Locked owner credential on GitHub: refuse.** `GithubAdapter.forProject` stops turning a `ForActingUser` error into
   `g.client.For(projectID)`. The error propagates, so the background pass fails with an activity whose `user_id`
   names the owner whose credential was refused. This matches the Jira adapter and ADR 0018.
3. **Owner without a personal GitHub token: keep the fallback.** `personal == false` with no error still resolves the
   project or server token. This fallback is now a decision. It is recorded as a consequence line in ADR 0018, which
   the implementation amends.
4. **The refusal applies to every call through the GitHub tracker adapter that carries an actor**, not only to
   background passes. Interactive
   GitHub calls through `forProject` whose actor's sealed token is locked fail as well, instead of acting under the
   server token.

### Consequences on the implementation

- `forProject` returns an error, as the Jira adapter's does (`(*Client, error)`). Its callers in
  `internal/trackerapi/adapters.go` (`IssuePullRequests`, `CreateGithubIssue`, `FetchSingleGithubIssue`,
  `UpdateGithubIssue`, and the rest) propagate it.
- A call with no actor (`userID == ""`) is unchanged: `ForActingUser` returns the project client with no error.
- `trackerAs` (`internal/db/trackercredentials.go:85`) keeps its fallback. None of its callers is a background sync
  path, and question 4 covered only `GithubAdapter.forProject`. Aligning it is a possible follow-up, not part of this
  ticket.
- Tests: locked credential with an actor → error (background pass and interactive call). Actor without a personal
  token → project token. No actor → project token.

### Reversed assumptions

None.

### Final acceptance criterion

A call made through the GitHub tracker adapter that carries an actor whose sealed credential is locked fails instead
of reading or writing with the project or server token, whether it comes from a background pass or from a person. A failed background pass records
the owner in `user_id`. The two remaining fallbacks on the project or server credential, an ownerless project and an
owner without a personal GitHub token, are both recorded as decisions in ADR 0018.

### Status

Round 2 done. **Zero open product questions**, and the owner confirmed. Exit condition met: `new → clarified`.
