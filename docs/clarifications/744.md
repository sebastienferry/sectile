# Clarification #744 - Workstation Sandbox allow rules lost after the #730 migration

Ticket: https://github.com/sebastienferry/sectile/issues/744
Branch: `feat/744`

## Round 1 (2026-10-06)

### Request

After the layout 3 to 4 conversion of #730 folded the per-project Claude Code
Sandbox values into the workstation level, the folded allow rules disappeared
from both levels without any log line. The fix makes sure no save path removes
a rule the user did not see and delete, and adds a regression test that folds
project rules, then runs every Desktop save path with the payload its dialog
sends. Out of scope: re-validating or rewriting existing rule syntax (the
`git fetch origin *` entry), and the recovery already done by hand on the
workstation.

### Code and files read

- `internal/agent/agent_desktop_sandbox.go`: `desktopWorkstationSandbox`
  (`PUT /desktop/workstation/sandbox`, not `/desktop/workstation-sandbox` as the
  ticket writes), `desktopPromoteSandboxRule`.
- `internal/agent/agent_desktop_settings.go`: `projectSettingsInput.apply` and
  the `PUT /desktop/workstation` handler, which copies `ClaudeSandbox` and
  `ClaudeSandboxProjects` from the stored settings.
- `internal/agent/agent_claude_sandbox.go`: `addProjectAllowRules` ("Always
  allow" writes to the project level).
- `internal/agentconfig/claude_sandbox.go`: `MergeClaudeSandbox`,
  `NormalizeClaudeSandbox`, `foldProjectSandboxes`.
- `internal/agentconfig/settings.go`: `ReadSettings`, `readConverted`,
  `WriteSettings`, `UpdateSettings`.
- `internal/agentconfig/engines_migration.go`: `MigrateSettingsReport`.
- `internal/agentconfig/seed.go`: `ApplyWorkstationSeed`.
- `desktop/src/sandbox-settings.mjs` (`sandboxSettings`: `payload()`,
  `base()`), `desktop/src/main.js` (`workstationSandboxPanel`, project panel
  save).
- `desktop/electron/main.cjs`: the Electron writers of `settings.json`
  (`saveCredential`, `save-settings`, `set-appearance`, `set-console-view`,
  agent start).
- On the workstation, read-only: `~/.config/sectile/settings.json`,
  `settings.json.bak-layout3`, `settings.json.bak-before-sandbox-restore-20261006-074608`,
  and `~/Library/Application Support/sectile-desktop/agent.log`.

### Findings

1. **The file was not empty before the restore.** The copy taken at 07:39
   (`bak-before-sandbox-restore`) is layout 4 and holds five workstation allow
   rules: `WebFetch(domain:github.com)`,
   `WebFetch(domain:release-assets.githubusercontent.com)`,
   `WebFetch(domain:releases.astral.sh)`, `WebFetch(domain:pypi.org)`,
   `WebFetch(domain:files.pythonhosted.org)`. None of them was on a project in
   `bak-layout3`. So the folded rules were replaced, not merely cleared, and
   five new rules reached the workstation level afterwards. The ticket also
   counts 23 rules on PE; the backup holds 22.
2. **The Desktop save paths do not explain it on their own.**
   - `PUT /desktop/workstation` keeps the stored Sandbox values.
   - `PUT /desktop/workstation/sandbox` with a base only drops an entry the
     dialog showed (in the base) and the owner removed. A dialog opened on
     empty values sends an empty base, so the merge keeps every stored rule.
     Only a save without `claudeSandboxBase` replaces everything, and the
     current Desktop always sends one.
   - The project save writes the project level only; promote and "Always
     allow" only add.
3. **A second, silent fold matches the final state exactly.**
   `foldProjectSandboxes` runs inside `readConverted`, that is on every
   `ReadSettings`, whenever the file's layout is below 4, and only
   `MigrateSettingsReport` (agent start) logs it. If something rewrites the
   file at layout 3 without `defaults.claudeSandbox`, the next `UpdateSettings`
   of the running agent folds whatever the projects then hold into an empty
   workstation level and stamps layout 4, with no log line. With an "Always
   allow" having put the five `WebFetch` rules on a project in between, that
   gives the observed state: five workstation rules, no project rules,
   layout 4, nothing in `agent.log`.
4. **What can write such a file.** Only a binary that predates #730: its
   `Defaults` has no `ClaudeSandbox` field, `defaults` is an owned key replaced
   whole, so the field is dropped, and it stamps layout 3. The Desktop log
   shows only post-#730 agents after the fold (459b2be7, a7ca796b, 33540b3a),
   and no migration log at the 07:08 start, so the file was back at layout 4
   by then. An agent outside the Desktop log (a worktree build, `go run`, a
   standalone `sectile-agent`, a branch server's agent) cannot be ruled out
   from here.
5. **A second writer without a lock.** Electron reads, merges and rewrites the
   whole `settings.json` (connection keys, appearance, console view, and at
   every agent start) with no lock shared with the agent; `settingsMu` only
   serializes the agent's own cycles. A write landing between the two halves
   of either side reverts the other's change. This is a lost-update risk in
   its own right, though alone it reverts to an older state rather than
   wiping the rules.
6. **The Go tests are isolated** (`testhome.Temp`), so they do not write the
   real file.

### Ambiguities, worst first

1. **What the fix covers.** Read narrowly, the ticket asks for the regression
   test and a fix in a Desktop save path. The evidence points instead at the
   silent fold on any read and at writers the agent does not control. The two
   readings lead to different code (see Q1).
2. **What happens when an older binary meets a newer file.** Today it drops
   what it does not know. Guarding against that changes `WriteSettings` (Q2).
3. **Whether the Electron race belongs here** (Q3).

### Dependencies

- No migration, no server change, no third-party limit. Desktop and agent
  ship together in the Desktop archives.
- A downgrade guard only protects against binaries built after it lands;
  binaries already out there keep their behaviour.

### Technical choices settled from the code

- The regression test follows the ticket: a layout 3 file with project rules,
  `MigrateSettingsReport`, then each save path with the payload its dialog
  sends: `PUT /desktop/workstation`, `PUT /desktop/workstation/sandbox` with a
  stale base, an empty base and no base, the project save with
  `claudeSandbox` and `claudeSandboxBase`, the promotion, and "Always allow".
  It asserts that every folded rule survives each one.
- A second test writes a layout 3 file without `defaults.claudeSandbox` over a
  folded layout 4 file and asserts the outcome chosen in Q1.
- Error messages and log lines stay in the language they already use.

### Open product questions

**Q1. Scope of the fix.** Recommended: **B**.
- A. Regression test plus whatever hardening the Desktop save paths need,
  nothing else.
- B. A, plus: the fold runs only in the start-up migration (with its backup
  and log line), never silently in an ordinary read; a file found back at an
  older layout after a newer one was written is backed up
  (`.bak-layout<N>-<timestamp>`) and logged as a downgrade, so the next loss
  leaves a trace.
- C. B, plus restoring the folded rules automatically from the newest
  `.bak-layout3` when the workstation level lost them.

**Q2. An agent that meets a settings file newer than itself.** Recommended:
**A**.
- A. `WriteSettings` refuses to write a file whose layout is above its own
  `SettingsLayout` and the save fails with a message saying the agent is
  older than the settings file.
- B. It writes anyway, as today.
- C. It keeps the unknown keys of `defaults` and of each project section
  (passthrough) and writes.

**Q3. The unlocked read-modify-write of `settings.json` by Electron.**
Recommended: **B**.
- A. Fix it in this ticket (a lock or a compare-and-swap shared with the
  agent).
- B. Record it as a separate ticket; this one only names it.
- C. Leave it.

**Q4. Origin of the five `WebFetch` rules.** Do you remember how they reached
the workstation level ("Always allow" on a `uv`/PyPI fetch, then "Move to
global"; typed in the dialog), and whether any other Sectile agent binary ran
on the workstation between 2026-10-05 15:16 and 2026-10-06 07:39 (a worktree
build, `go run`, a branch server)? The answer does not change the code of Q1 B,
but it confirms the cause the report rests on.

## Round 2 - answers from the owner (2026-10-06)

### Answers

- **Q1: B.** The regression test, plus: the Sandbox fold runs only in the
  start-up migration (`MigrateSettingsReport`, with its backup and log line),
  never silently inside an ordinary `ReadSettings`; a file found back at an
  older layout after a newer one was written is backed up
  (`.bak-layout<N>-<timestamp>`) and logged as a downgrade.
- **Q2: A.** `WriteSettings` refuses to write a settings file whose layout is
  above its own `SettingsLayout`; the save fails with a message saying the
  agent is older than the settings file.
- **Q3: B.** The unlocked read-modify-write of `settings.json` by Electron
  (`desktop/electron/main.cjs`) is recorded as a separate ticket; #744 only
  names it.
- **Q4.** The five `WebFetch` rules came from "Always allow" in a
  conversation, then "Move to global".

### Reversed assumption

Finding 3 of round 1 explained the five workstation rules by a second, silent
fold. That is withdrawn: they reached the workstation through the promotion,
which only adds to the stored values. So the 35 folded rules were already gone
when the promotion ran, and the writer that dropped `defaults.claudeSandbox`
between 2026-10-05 15:16 and the promotion is still unidentified. A binary
that predates #730 remains the only code path known to drop the field
(finding 4); the Desktop save paths do not (finding 2).

### What this settles for the specification

1. Regression test: a layout 3 file with project rules goes through
   `MigrateSettingsReport`, then through every Desktop save path with the
   payload its dialog sends (`PUT /desktop/workstation`,
   `PUT /desktop/workstation/sandbox` with a stale base, an empty base and no
   base, the project save with `claudeSandbox` and `claudeSandboxBase`, the
   promotion, "Always allow"); every folded rule survives each one.
2. `readConverted` no longer folds on an ordinary read; the fold belongs to the
   start-up migration only, which logs it.
3. A start that finds the file at a layout below the one a previous agent
   wrote keeps a timestamped backup and logs a downgrade. How "a newer layout
   was written" is remembered is a technical choice for the specification.
4. `WriteSettings` refuses a file whose layout is newer than its own, with an
   explicit error; the save paths surface it.
5. A separate ticket is opened for the Electron lost-update race.
6. Out of scope, unchanged: rule syntax validation, and the manual recovery.
