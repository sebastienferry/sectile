## Restated request and scope

Allow a user to maintain simultaneous WebSocket connections from multiple distinct workstations (identified by `deviceId`) without triggering `4001 Session Rebound`. Out of scope: distributed multi-node clustering, changing tracker synchronization, and modifying how local agent daemons execute skills inside their worktrees.

## Verified findings

- **`AgentDispatcher` is purely in-memory**: The ticket description references updating a database table `agent_presence` (`PRIMARY KEY (user_id, project_id)`) and updating multi-replica routing (`agent_cluster`). Inspection of the codebase reveals that neither `agent_presence` nor `agent_cluster` exists anywhere in the repository or git history. The server's agent registry (`internal/handlers/agent_dispatcher.go`) is held strictly in-memory in `AgentDispatcher.agents`.
- **Session Rebound mechanism**: In `internal/handlers/agent_dispatcher.go`, `agentKey` is defined as `struct { UserID string; ProjectID string }`. When a new WebSocket connection registers for a key that is already present in `d.agents`, `Register` calls `existing.Close(4001, "Session Rebound")`. Because default agent daemons register with `projectId="all"` (or `"default"`), connecting a second workstation for the same user immediately disconnects the first workstation with code `4001`, causing a 2-second reconnect loop.
- **Device identification**: `HandleAgentConnect` (`internal/handlers/handlers.go:2864`) already extracts `deviceId := r.URL.Query().Get("deviceId")`. Furthermore, the bearer API key resolves via `h.resolveAgentCredential` to a `device_credentials` row (`internal/db/identity.go`), where `credential.Device.ID` is known.
- **Dispatch routing**: When skills or actions are triggered (`run-skill`, `HandleAgentDispatch`, `LaunchTaskExternalTerminal`), the server invokes `d.agentDispatcher.Lookup(userID, projectID)`. With multiple concurrent devices for a single user, `Lookup` must have a deterministic strategy to select which workstation receives the command when no specific device is targeted.
- **Run cancellation**: When stopping a run (`POST /api/runs/{id}/stop` in `internal/handlers/remote_run.go`), `DispatchAndWait` sends `cancel_run`. If routed to a device that is not executing the run, the agent answers with `agentprotocol.RunNotOwned` (`ErrRunNotOwned`).
- **OpenSpec specification**: `openspec/specs/remote-agent-decoupling/spec.md` specifies the previous rebound scenario: *"WHEN a new agent daemon connects for the same user and project THEN the server terminates the older connection with close code 4001 Session Rebound"*. This specification requires updating to reflect the new device-aware rebound criteria.

## Ambiguities, worst first

1. **Presence persistence and clustering vs. in-memory registry**: The ticket description describes modifying an `agent_presence` database table and `agent_cluster` routing. Since neither exists in the codebase, implementing them would require creating brand new schema migrations, persistence logic, and multi-replica synchronization, whereas keeping presence in-memory matches the rest of Sectile's architecture.
2. **Dispatch target selection across concurrent workstations**: When a user has multiple devices connected (e.g., a laptop and a desktop) and triggers a skill execution without specifying a target device, the system must decide which device executes the job. Two readings lead to different code: (a) route automatically to the most recently active device (by last ping / `LastSeen()`), with optional `deviceId` parameter support in the dispatch API; or (b) fail with an error requiring the caller to specify `deviceId`.
3. **Run cancellation routing**: When canceling an active run, if the run record does not store the target `deviceId`, dispatching `cancel_run` to the wrong workstation produces `ErrRunNotOwned`. The server can either broadcast `cancel_run` across the user's connected devices until the owning device confirms, or record `deviceId` on the run launch so cancellation routes directly.
4. **Uniqueness constraint for Session Rebound**: Rebinding with `4001 Session Rebound` occurs when an agent connects with the *same* device ID. Does it key on `(UserID, DeviceID)` globally across projects, or `(UserID, ProjectID, DeviceID)`? Because a physical workstation typically runs one agent daemon for the user, `(UserID, DeviceID)` avoids duplicate daemons on the same machine regardless of project parameter nuances.

## Critical dependencies

- None: The change is internal to the Sectile server (`AgentDispatcher`, HTTP handlers, and unit tests). No external services or database schema changes are required if presence remains in-memory.

## Reversible technical choices resolved

- **Fallback device identification**: If `r.URL.Query().Get("deviceId")` is missing or empty, fall back to `credential.Device.ID` from the authenticated API key. If both are absent, default to `"unknown"`.
- **Rebound condition**: Close an existing connection with `4001 Session Rebound` if and only if a newly registering connection has the same `UserID` and `DeviceID`.
- **Unregister safety**: `Unregister` will match both the `(UserID, DeviceID)` key and the specific `*websocket.Conn` pointer so that a rebind does not race with an unregister from the closed connection.
- **Connected agents snapshot**: `ConnectedAgents()` and `ActiveConnections()` will return all connected devices across all users.

## Open product questions

1. **Scope confirmation on `agent_presence` / `agent_cluster`**:
   - **(Recommended) Option A**: Keep presence in-memory within `AgentDispatcher`. Do not introduce a database table or multi-node cluster abstraction in this task.
   - **Option B**: Introduce a new `agent_presence` database table and schema migration to persist connected workstation metadata across server restarts.
2. **Dispatch routing when multiple devices are connected**:
   - **(Recommended) Option A**: Automatically route dispatches to the user's most recently active device (measured by `LastSeen()` / ping activity), while accepting an optional `deviceId` in dispatch requests for explicit targeting.
   - **Option B**: Require explicit `deviceId` selection whenever more than one device is connected, returning an error if omitted.
3. **Handling `cancel_run` across multiple devices**:
   - **(Recommended) Option A**: When canceling a run, route to the device that launched the run (if known), or broadcast `cancel_run` across the user's connected devices, ignoring `ErrRunNotOwned` until the owning device responds.
   - **Option B**: Only attempt cancellation on the most recently active device, requiring `force: true` if that device does not own the run.
