# Clarification — #550: taskflow/config.json

## Round 1 — 2026-09-26

### Request restated

Determine whether the retired `.taskflow/config.json` still has a runtime role,
why it existed, and what should replace it. The intended change is to correct
stale documentation or instructions; it does not migrate the remaining
`.taskflow/` workstation state or change the server-to-agent protocol.

### Evidence and settled facts

- The checkout does not contain `.taskflow/config.json`; `.gitignore` excludes
  it. It was explicitly untracked as part of the provider-scoped setup
  migration.
- The released provider-scoped setup migration stopped generating both the
  managed `AGENTS.md` project-context block and `.taskflow/config.json`.
  Project identity and workflow context now reach an agent in its dispatch
  context and through `get_project_context` over the authenticated Sectile MCP
  connection.
- No production code reads or writes `.taskflow/config.json`. The agent writes
  `.taskflow/remote-config.json` only as a diagnostic snapshot; it is never an
  offline configuration cache or a source of execution settings.
- `.taskflow/agent.json` remains a different, legacy per-checkout fallback for
  workstation settings. It is not a replacement for project/tracker context
  and is not to be removed by this ticket.
- `AGENTS.md` still says that `.taskflow/config.json` is the source of truth,
  which is incorrect. `docs/ARCHITECTURE.md` and one paragraph in
  `docs/contracts/server-agent-v1.md` also retain outdated claims that the
  agent writes that file.

### Scope decision needed

1. Should implementation remove or rewrite **all** stale references to the
   retired file (`AGENTS.md`, `docs/ARCHITECTURE.md`, and
   `docs/contracts/server-agent-v1.md`), while preserving accurate historical
   references in archived OpenSpec changes and clarifications? **Recommended:**
   yes. Limiting the fix to `AGENTS.md` leaves published architecture and
   contract documentation internally inconsistent.

### Dependencies

No migration, compatibility shim, external service, or data change is needed.
The live Sectile MCP project-context endpoint is the existing replacement.
