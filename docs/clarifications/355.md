## Round 1 (2026-09-22)

### Restated request and scope

The generated `create_pr` skill should publish with a plain `git push` whenever that is enough, and use `git push --force-with-lease` only when the branch's already-published history was actually rewritten. This change covers the wording of the generated skill instructions, their golden files and their tests. It does not change Sectile's Go push/branch code (`internal/workspace/git.go` only deletes remote branches), the base-branch integration policy (rebase vs merge), or the non-force push paths of other stages.

### Files read

- `internal/skills/fragments/create_pr/steps.md`: step 2 says *"prefer rebase when the branch is private, and use git push --force-with-lease only when an authorized private-branch rebase requires it"*. Step 3 then says only *"Commit and push"*.
- `internal/skills/fragments/adjust/steps.md`: step 6 says *"If rebasing an already-pushed branch, use `git push --force-with-lease`, never an unguarded force push"*. The same text is embedded in the `pickup` and `pickup_issues` goldens.
- `internal/skills/catalog_test.go:111`: `TestCreatePRSkillIntegratesRemoteDefaultBranchBeforePublishing` requires the literal string `git push --force-with-lease` in the rendered `create_pr` skill.
- `internal/skills/testdata/golden/*`: these are regenerated with `UPDATE_GOLDEN=1` (`catalog_test.go:259`).
- The `implement` and `specify` fragments contain no push/force wording.

### Findings

- The current `create_pr` wording is conditional, but the condition is vague. "An authorized private-branch rebase requires it" does not say how to detect that need. The mention of force-with-lease sits in the base-reconciliation step, before the plain push step, so an agent can read it as the default way to publish after reconciling.
- Force is needed only in one case: `origin/<branch>` exists and is not an ancestor of the local `HEAD` (the published history was rewritten). A force is never needed in these cases:
  - first publication of the branch (no `origin/<branch>`);
  - the branch was not rebased (it was not behind `origin/main`, or base commits were merged in);
  - the local branch fast-forwards the remote branch.
- A detection rule an agent can run: `git fetch origin`, then `git merge-base --is-ancestor origin/<branch> HEAD`. Success, or a missing remote ref, means a plain push. Otherwise use `--force-with-lease` (a rewrite happened).

### Ambiguities (worst first)

1. **Which skills change.** The title names PR creation (`create_pr`). `adjust` (and the `pickup`/`pickup_issues` skills that embed it) carries the same force-with-lease instruction and publishes to the same PR. Two readings: change only `create_pr`, or apply the same decision rule to `adjust` too.
2. **Observed failure.** It is unclear whether the agent's force push failed (lease rejected / "stale info", blocked by a permission prompt or hook, refused by branch protection) or just ran when it was not needed. If it failed, the skill also needs an instruction for a rejected lease.

### Reversible technical choices (resolved from conventions)

- Put an explicit decision rule in the push step (step 3) of `create_pr` rather than in step 2. Step 2 keeps the reconciliation policy.
- Keep the literal `git push --force-with-lease` in the text so the existing test contract still holds. Add assertions for the plain-push default and the ancestor check.
- Regenerate the affected goldens with `UPDATE_GOLDEN=1 go test ./internal/skills/...`.
- An unguarded `--force` stays forbidden everywhere.

### Dependencies

- None external. Installed copies of the skills (for example `~/.claude/skills/create-pr`) are regenerated from the catalogue, so users only get the fix after they re-install or regenerate their skills.

### Product questions

1. **Scope:** should the same "plain push unless published history was rewritten" rule also apply to `adjust` (and through it to `pickup`/`pickup_issues`)? *Recommended: yes.* It is the same push to the same PR, and one consistent rule avoids the same problem at the next stage.
2. **Rejected lease:** if `--force-with-lease` is rejected (the remote moved), should the agent stop and report a blocker, or fetch, re-integrate and retry once? *Recommended: stop and report, never escalate to `--force`.* A rejected lease means someone else pushed to the branch.
3. **Symptom:** what actually went wrong: a failed/blocked push, or just an unnecessary force? *Recommended: if it was a permission prompt or hook block on first publication, the plain-push default above fully covers it and no extra handling is needed.*

## Round 2 - answers from the owner (2026-09-22)

### Answers

1. **Scope:** yes. The same push rule applies to `create_pr` and `adjust`, and through `adjust` to `pickup` and `pickup_issues`.
2. **Rejected lease:** if the push is refused because a commit landed on the remote branch in between, resync the local branch with the remote branch and retry. Never fall back to `--force`.
3. **Symptom:** the agent ran `git push --force-with-lease` when the branch did not exist on the remote yet, and the push failed.

### Settled decisions

- **Push decision rule** (both skills), after `git fetch origin`:
  - `origin/<branch>` missing: first publication, run `git push -u origin <branch>`. Never force. This is the case that failed.
  - `git merge-base --is-ancestor origin/<branch> HEAD` succeeds: fast-forward, run a plain `git push`.
  - Otherwise, published history was rewritten by an authorized rebase: run `git push --force-with-lease`.
- **Rejected push (lease or non-fast-forward because the remote moved):** run `git fetch origin`. Replay the local commits on top of `origin/<branch>` (`git rebase origin/<branch>`) so the remote commits are kept. Resolve any conflicts, re-run the required checks if new commits were brought in, then retry with the rule above.
- An unguarded `git push --force` stays forbidden in every case, including after a rejection.

### Reversed or refined assumptions

- Round 1 recommended stopping on a rejected lease. The owner reversed this: resync and retry instead.
- Round 1 left the root cause open. It is now known to be the missing-remote-branch case, which the first branch of the rule covers.

### Reversible choices made in this round

- **Resync method:** rebase the local commits onto `origin/<branch>`. This keeps history linear and does not rewrite anything already published. A merge is acceptable if the rebase causes conflicts the agent cannot resolve safely.
- **Retry bound:** one resync-and-retry. If the push is rejected a second time, or the rejection is not caused by the remote moving (for example branch protection, permissions or auth), stop, keep the work and report a blocker.
- **Tests:** add `catalog_test.go` assertions for the missing-branch plain push, the ancestor check and the resync-then-retry instruction, for both `create_pr` and `adjust`. Regenerate the goldens with `UPDATE_GOLDEN=1`.
