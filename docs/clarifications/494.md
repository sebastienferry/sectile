### What the code does with the file today

- One Go reader, `readLegacyRepositoryFile` (`internal/agentconfig/local.go:218-245`).
  A missing file returns empty `Settings` and no error (l.223-224); only a
  non-ENOENT read error or malformed JSON is an error.
- `readFolded` (`settings.go:46-97`) uses the whole file when `settings.json`
  is missing, and its `projects` / `worktrees` / `parallelism` for a
  `settings.json` below layout 2. `WithRepositoryFile` (`local.go:249-258`,
  called from `agent_config.go:194-198`) overlays it per project at any layout.
- The checkout read is the **main checkout** of the repository the agent was
  started in: `findRepoRoot` takes the parent of `git rev-parse
  --git-common-dir` (`agent.go:962`), so an agent started from this repository
  without `--repo` (`go run`, `make dev`), or from any of its worktrees, picks
  up the committed copy today.
- Nothing writes `.taskflow/agent.json`. `UpdateSettings` (`settings.go:172-184`)
  does migrate whatever `ReadSettings` folded, legacy file included, into
  `settings.json` at layout 2 (first connection in `seed.go:57/76`, desktop
  engine, MCP and settings saves).
- Tests never use the repository's copy: they write their own into

  No CI workflow, Makefile target, script or README references it.
- The desktop merges `<repo>/.taskflow/agent.json` into its own settings with
  errors swallowed (`desktop/electron/main.cjs:222-224`).
- `git ls-files .taskflow` lists only this file, added in c5d2a84f (2026-09-14).

### Ambiguities (worst first)

1. **Remove the fallback code too, or only the committed file?** Settled: only

2. **Copies of the mapping already migrated into users' `settings.json`.**

   elsewhere. A clean-up would be a follow-up ticket of its own.

### Critical dependencies

- **Main checkout, not the worktree.** Because `findRepoRoot` resolves to the
  main checkout, deleting the file in `issue-494` proves nothing about startup
  until the change reaches the checkout the agent is started from. The
  "starts without the file" check must run against a checkout where the file
  is absent (for example a temp clone, or `--repo` pointing at one).
- **The author's workstation.** Once the deletion is pulled, a checkout that
  relied on the committed mapping with no `settings.json` loses it. Pulling a
  removal deletes the working copy even though the path is then ignored. The
  owner should have the mapping in `settings.json` (or a local copy kept aside)
  before pulling.
- The path has been public since c5d2a84f; the change stops the leak going
  forward only and does not rewrite history.

### Settled technical choices

- `git rm .taskflow/agent.json` (file removed from the tree, not only from the
  index), following 42564a96, with a commit body saying the file is still read
  as a local fallback but must never be committed.
- `.gitignore`: add one line `.taskflow/agent.json` to the second block
  ("Agent installation bookkeeping and recovery copies"), where 42564a96 put
  `.taskflow/config.json`, following the file-by-file pattern. The duplicated
  `.taskflow/*` lines of the two blocks are left as they are (out of scope).
- No code change to `readLegacyRepositoryFile`, `readFolded`,
  `WithRepositoryFile` or `main.cjs`.
- Add one unit test in `internal/agentconfig` pinning that `ReadSettings` on a
  root with neither `settings.json` nor `.taskflow/agent.json` returns empty
  settings and no error (no test covers that case today).
- Documentation: no change needed, since the fallback still exists and
  reads a local copy. At most one sentence in `docs/contracts/server-agent-v1.md`
  that the file is workstation-local and never committed; the specification
  decides.
