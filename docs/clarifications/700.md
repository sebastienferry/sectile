# Clarification #700 - Desktop: Sandbox configuration

Ticket: https://github.com/sebastienferry/sectile/issues/700
Branch: `feat/700`

## Round 1 - initial report (2026-10-02)

### Request

> How to configure the autorisation of the sandboxed mode easily and retain the values

Restated: Sectile Desktop should let the owner set what Claude Code's sandbox
allows (and the approvals they grant while a session runs) from Sectile itself,
without editing Claude Code's settings files by hand, and those values should
still apply to the next task instead of being lost with the task's worktree.

Out of scope: Electron's own renderer sandbox (`webPreferences.sandbox` in
`desktop/electron/main.cjs`, a security setting that is not user-facing),
the web client, and engines other than Claude Code (Codex has its own
sandbox, see `addDirArgs` in `internal/agent/agent_config.go`).

### What exists today (files read)

- `internal/agent/agent_conversation.go`: a Desktop conversation runs
  `claude -p --permission-mode <default|acceptEdits|plan> --permission-prompt-tool stdio --allowedTools=mcp__sectile`,
  with the task worktree as its working directory. No `--settings` is passed:
  the sandbox is whatever `~/.claude/settings.json` and the worktree's
  `.claude/settings*.json` say.
- `internal/agent/agent_conversation_approvals.go` and
  `desktop/src/conversation.js`: each tool call Claude asks about shows
  Allow / Always allow / Deny. "Always allow" hands Claude's own
  `permission_suggestions` back verbatim as `updatedPermissions`, so Claude
  chooses where the rule is written. For a Bash or a sandbox retry that is
  usually `localSettings`, i.e. `<task worktree>/.claude/settings.local.json`,
  which disappears when handoff removes the worktree. This is the most likely
  reason the values are "not retained" (to verify at specification time with a
  captured control request).
- `internal/agent/agent_config.go`: headless runs use
  `--permission-mode bypassPermissions`; interactive terminal runs are a plain
  `claude` the owner drives, where `/sandbox` and `/permissions` already work.
- `internal/agentconfig/local.go`, `internal/agentconfig/settings.go`,
  `desktop/electron/connection-settings.cjs`: Sectile's workstation settings
  live in `~/.config/sectile/settings.json`, shared by the desktop and the
  local agent; per-project overrides already exist there.
- `desktop/src/main.js`: the Desktop "Execution settings" panel, the natural
  home for a new section.

### Ambiguities, worst first

1. **Which "sandbox"?** (a) Claude Code's sandbox (`sandbox.enabled`,
   `sandbox.network.allowedDomains`, `sandbox.filesystem.allowWrite`,
   `excludedCommands`...), (b) Claude Code permission rules
   (`permissions.allow` / `deny`, what "Always allow" writes), or (c) both.
   Each is a different settings shape and a different UI.
2. **Where the values are retained.** (a) in Claude Code's user settings
   `~/.claude/settings.json` (applies to every Claude session on the machine,
   inside and outside Sectile), (b) in Sectile's workstation settings, per
   project, injected on each launch with `claude --settings <file>`, or
   (c) written into each new task worktree's `.claude/settings.local.json`.
3. **Which launches honour them.** Desktop conversations only, or also
   interactive terminal sessions and headless (`bypassPermissions`) runs.
4. **What "Always allow" does.** Keep Claude's destination, or rewrite the
   suggestion so the rule lands in the retained store of question 2.

### Critical dependencies

- Claude Code's sandbox runs on macOS and Linux only; on Windows the section
  would have nothing to drive and must say so (or be hidden).
- `--settings` merges with the other scopes: arrays such as allowed domains add
  up, so a value Sectile injects cannot remove one set in `~/.claude/settings.json`.
- The `permission_suggestions` shape (`addRules`, `setMode`, `destination`) is
  Claude Code's, undocumented beyond the Agent SDK types; rewriting the
  destination relies on it.
- The workstation settings file is merged key by key (memory "New Overrides
  key needs a merge"): a new key must be carried through `localProjectRoot`
  and `WriteSettings`.

### Reversible technical choices (settled here)

- Storage of Sectile-owned values: `~/.config/sectile/settings.json`, beside
  the other workstation settings, never uploaded to the server.
- Injection: a generated settings file passed with `--settings=<path>` (the
  `=` form, as for `--add-dir`), rather than editing files Claude Code owns.
- The editor is a section of the Desktop settings panel.

### Product questions (recommended option first)

1. Scope of "sandbox": **both the Claude Code sandbox (on/off, allowed
   network domains, extra writable paths) and the permission rules that
   "Always allow" creates** / sandbox only / permission rules only.
2. Retention level: **Sectile workstation settings, per project, injected with
   `--settings`** / user-level `~/.claude/settings.json` / copied into each
   worktree.
3. Launches covered: **Desktop conversations only** (the only launch where
   Sectile shows the approvals) / also interactive terminal sessions / all
   launches including headless.
4. "Always allow" in a conversation: **writes the rule into the retained store
   of question 2, so it survives the worktree** / keeps Claude's own
   destination.
