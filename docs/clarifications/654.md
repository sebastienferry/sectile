# Clarification #654: Connect Jira through Atlassian OAuth instead of a pasted API token

Ticket: https://github.com/sebastienferry/sectile/issues/654
Branch: `feat/654`
Decision record: `docs/adrs/0044-personal-jira-access-is-authorised-through-oauth.md` (Proposed, on branch `docs/654-jira-oauth-adr`, not yet on `main`)

## Round 1 - initial report (2026-09-30)

### Request

A person on a Jira project connects their Jira account from *Profile → Tracker
credentials* with one Atlassian consent screen (OAuth 2.0 authorisation code
grant, 3LO) instead of pasting an API token, and every write they cause keeps
going out under their own account, refreshed in the background, exactly as the
attribution rules of ADR 0029 require.

Out of scope: the server credential used by unattended work (stays an API
token), removing the API token path, GitHub and GitLab, Jira Data Center /
Server (3LO is Jira Cloud only), and the desktop app (tracker credentials are
managed in the web profile only).

### Code read

- `internal/trackerapi/client.go`: `ForActingUser` substitutes the personal
  token, e-mail and **site** on a copy of the project client; `MissingPersonalCredentialError`.
- `internal/trackerapi/jira_client.go`: every call is `c.JiraURL + path` with
  `jiraBasicAuth(email, token)`; `CheckJira` probes `/rest/api/3/myself`.
- `internal/db/usercredentials.go`: `user_tracker_credentials` (one row per
  person and tracker; `site_url`, `email`, `record`, `sealed`, `salt`, `account`),
  passphrase sealing and unlocks (ADR 0032).
- `internal/db/trackercredentials.go`: the Jira site comes from the global
  settings (`settings.JiraUrl`) **and a Jira project may override it**
  (`proj.TrackerUrl`); `ResolveUser` is wired in `internal/db/db.go:247`, server side only.
- `internal/auth/oidc.go`, `internal/handlers/auth.go`: the sign-in flow already
  stores a single-use `state` in the database (`StartLoginFlow` /
  `ConsumeLoginFlow`) and reads its callback from an explicit
  `SECTILE_OIDC_REDIRECT_URL`; there is no "server public URL" setting.
- `internal/auth/roles.go`: every deployment has a web session (OIDC or local
  e-mail sign-in), so a session-bound `state` is always possible.
- `web/src/components/TrackerCredentialsTab.tsx`, `TrackerCredentialForm.tsx`;
  `docs/USER_GUIDE.md` § "Set up a personal Jira token"; `docs/API_AND_DATA_SPEC.md`
  (`GET /api/me/tracker-credentials`).
- Agile endpoints in use: `/rest/agile/1.0/board`, `/board/{id}/...`,
  `/sprint`, `/sprint/{id}/...`, `/backlog/issue`.

### Ambiguities, worst first

1. **Which Jira site a grant must cover.** The ticket and the ADR speak of "the
   site the deployment is configured for", but the site is per project: a Jira
   project can override the global `JiraUrl`. A person's credential is one row
   per tracker, and today its own `site_url` replaces the project's site. Reading
   A (one site, the global one) refuses people whose projects live elsewhere;
   reading B (every site the grant covers) needs the grant to hold a list of
   `cloudId`s and the client to pick one per project. → **Q1**.
2. **Whether the API token form is still reachable once OAuth is configured.**
   "The API token form stays otherwise" reads as "hidden when OAuth is
   configured", while "removing the API token form" is out of scope. The two
   readings produce different UI and different tests. → **Q2**.
3. **Callback URL.** The ADR says it is derived from "the server's public URL",
   which Sectile does not have. Settled below as a technical choice.

### Critical dependencies

- **Outside the code (blocking for the end-to-end acceptance criterion):** the
  Atlassian organisation must allow people to authorise third-party OAuth 2.0
  apps, and an OAuth 2.0 integration must be registered on
  developer.atlassian.com with distribution enabled, the callback URL and the
  scopes. → **Q3**.
- **ADR 0044 is not on `main`.** It lives on `docs/654-jira-oauth-adr`. The
  implementation either lands after it or carries it. Its title still reads
  "ADR 0042" while the file is numbered 0044; that line is corrected when the ADR
  moves to Accepted.
- **Numbered migration** for `kind`, `version`, a `disconnected` marker and the
  OAuth flow table (never in the frozen baseline; the rewind and replay test
  fixtures follow the new columns).
- **Atlassian limits:** refresh tokens rotate and expire after about 90 days
  unused; the app's rate limit is computed per app and site, not per person;
  Atlassian offers no token revocation endpoint for 3LO apps.

### Technical choices resolved from the code and conventions

- **Callback URL:** an explicit setting, `SECTILE_JIRA_OAUTH_REDIRECT_URL`,
  mirroring `SECTILE_OIDC_REDIRECT_URL`, also editable on the Administration
  page next to the client id and secret. The ADR's "derived from the public URL"
  line is amended accordingly. No derivation from request headers.
- **State storage:** a dedicated table modelled on the sign-in flow
  (`StartLoginFlow` / `ConsumeLoginFlow`): random, single use, about 10 minutes,
  bound to the web session and the user id; consumed atomically so a replay or a
  second replica finds nothing.
- **Env versus Administration page:** the same precedence the server tracker
  credentials already follow (ADR 0028); the secret is write-only in the API and
  never returned.
- **Transport:** the client keeps `JiraURL` as the site (people-facing links,
  caches keyed by site) and gains a separate API base
  `https://api.atlassian.com/ex/jira/{cloudId}` plus a Bearer header; paths are
  unchanged.
- **Account:** recorded from `/rest/api/3/myself` through the grant, as today;
  the OAuth row has no e-mail, the profile shows the confirmed account name.
- **Disconnect:** deleting the row forgets the grant locally; the profile tells
  the person they can also remove Sectile from their Atlassian account's
  connected apps (no revocation API exists).
- **Refresh:** on demand, when the access token is expired or within a minute of
  expiry, as a compare-and-set on the row `version`; the loser re-reads the row.
  `invalid_grant` marks the row disconnected and surfaces the ADR 0029
  missing-credential error; transient errors (5xx, network) fail the call
  without disconnecting.
- **Sealed API tokens:** unchanged until their owner connects (which replaces
  the row) or deletes them; an OAuth row is never sealed.

### Product questions

- **Q1. Sites covered by a grant.** Recommended: **B**. Store every
  accessible resource of the grant (`cloudId` and site URL); a write resolves the
  `cloudId` matching the project's effective Jira site. Connecting is refused,
  storing nothing, only when the grant covers none of the Jira sites configured
  on the server (global or per project). A write on a project whose site the
  grant does not cover fails with the missing-credential error, saying to
  reconnect and pick that site on the consent screen. Alternative A: only the
  global site counts, and projects overriding the site keep API tokens.
- **Q2. API token form when OAuth is configured.** Recommended: *Connect Jira*
  is the primary action and the API token form stays reachable behind a
  secondary "Use an API token instead" link, so a site the app cannot reach still
  has a way in. Alternative: hide the form entirely while OAuth is configured.
- **Q3. Prerequisites.** Has the Atlassian organisation confirmed that people
  may authorise third-party OAuth 2.0 apps, and is the integration registered (or
  who registers it)? Recommended: specify and implement now against a fake
  Atlassian endpoint; the end-to-end acceptance criterion is checked once the app
  exists.

## Round 2 - answers from the owner (2026-09-30)

The owner answered Q1 to Q3 interactively and took the recommended option each time.

### Settled decisions

- **Q1, sites covered by a grant: every granted site.** The OAuth record stores
  every accessible resource of the grant (`cloudId` and site URL). A Jira call
  resolves the `cloudId` matching the project's effective site (the project's
  `TrackerUrl` when it overrides it, else the global `JiraUrl`). Connecting is
  refused, storing nothing, only when the grant covers none of the Jira sites
  configured on the server, and the refusal names those sites. A write on a
  project whose site the grant does not cover fails with the ADR 0029
  missing-credential error, telling the person to reconnect and pick that site
  on the consent screen; it never falls back to the server credential.
- **Q2, API token form when OAuth is configured: secondary link.** *Connect
  Jira* is the primary action; the API token form stays reachable behind a
  "Use an API token instead" link. Without OAuth configured, the profile is
  unchanged.
- **Q3, prerequisites: proceed now.** Specification and implementation go ahead
  against a fake Atlassian authorisation, token and accessible-resources
  endpoint. The end-to-end acceptance criterion (a real consent and an
  attributed transition, comment and assignment) is checked once the
  organisation allows third-party OAuth apps and the integration is registered;
  the pull request says so rather than claiming it.

### Reversed or amended assumptions

- The ticket's "selection of the `cloudId` matching the configured site; a grant
  without that site is refused" becomes: all granted `cloudId`s are kept, and
  the refusal applies only when none of the configured sites is covered. The
  acceptance criterion "a grant that does not include the configured site stores
  nothing and says why" is read with that meaning, plus a new one: a write on a
  project whose site the grant lacks fails with the missing-credential error.
- ADR 0044 is amended on these two points (sites covered, callback URL setting)
  when it moves to Accepted, and its title is renumbered from 0042 to 0044.

### New ambiguities or dependencies

None. The technical choices of Round 1 stand.
