## Round 1 (2026-10-09)

### Restated request and scope

The ticket asks for GitHub and GitLab "SSO (or SAML)" authentication, "like was done for JIRA", and has no description. What was done for Jira is #654 (ADR 0044): a person clicks *Connect Jira* in *Profile → Tracker credentials* and authorises Sectile through Atlassian OAuth 2.0 (3LO). Sectile then makes that person's tracker reads and writes under their own Atlassian account, instead of with an API token they pasted. The likely reading is therefore *Connect GitHub* and *Connect GitLab* through OAuth, replacing the pasted personal access token (PAT). Out of scope in that reading: signing in to Sectile, the server credential used by unattended work, and Sectile Desktop and the MCP tools.

The ticket's premise needs a correction.
- What was done for Jira is not SSO. Signing in to Sectile is a separate flow: OpenID Connect (ADR 0008) through the Equativ Auth0 private tenant. Jira OAuth only obtains a per-person credential for the tracker API.
- SAML cannot fit either reading. GitHub and GitLab are not SAML identity providers for third-party applications: SAML on GitHub or GitLab protects the organisation or group itself, upstream of Okta. Sectile has no SAML code, and the Auth0 repository defines no SAML app.

### Files read and findings

- `specs/654-jira-oauth-connect/spec.md`, `docs/clarifications/654.md` and `docs/adrs/0044-personal-jira-access-is-authorised-through-oauth.md`: the Jira precedent. Its scope lists "GitHub and GitLab" explicitly as out of scope (`spec.md:28-40`), which makes this ticket its natural follow-up.
- `internal/handlers/jiraoauth.go`:
  - `POST /api/me/tracker-credentials/jira/connect` (`connectJira`) answers an `authorizeUrl`. Only a web session can call it.
  - The callback is `/auth/jira/callback` (`JiraOAuthCallbackPath`). It reads the session cookie and lands the person on *Profile → Tracker credentials* with the outcome.
- `internal/atlassian/oauth.go`: the Jira-specific steps:
  - the authorize URL, the code exchange and the refresh;
  - the accessible-resources (cloudId) lookup;
  - the scopes.
- `internal/db/oauthapps.go`: the OAuth app in force.
  - An app saved from Administration (`tracker_oauth_apps`, row `tracker = 'jira'`) wins over the `SECTILE_JIRA_OAUTH_*` environment variables.
  - Its secret is sealed under the server key.
- `internal/db/migrations.go`:
  - Migration 40 adds `kind` (`api_token`|`oauth`), `version`, `disconnected_at` and `refresh_claimed_at` to `user_tracker_credentials`.
  - Migration 41 creates `jira_oauth_flows` (state hashed, bound to the session, single use, 10-minute TTL).
  - Migration 42 creates `tracker_oauth_apps`, keyed by `tracker` only.
  - Migration 49 creates `trackers`, with a `site` per tracker.
- `internal/db/jiragrants.go`:
  - The grant is sealed under the server key (never under a passphrase).
  - Refresh happens on demand, under a compare-and-set on `version`, because Atlassian rotates refresh tokens.
  - `invalid_grant` marks the row disconnected, with no fallback to the server credential.
- `internal/db/usercredentials.go`: personal credentials are keyed by `(user_id, tracker)`. Today GitHub and GitLab only have a pasted token there, which can be passphrase-sealed.
- `internal/trackerapi/client.go` (`ForActingUser`, lines 136-185):
  - Only Jira handles an OAuth grant (`credential.Bearer`) and resolves a site.
  - GitHub and GitLab just substitute `GithubToken`/`GitlabToken`.
  - Both clients already send `Authorization: Bearer <token>`, so an OAuth access token needs no transport change.
  - `GitlabURL` comes per tracker (default `https://gitlab.com/api/v4`), so a self-hosted GitLab is possible.
- `internal/auth/oidc.go` and `internal/auth/roles.go`: sign-in.
  - One OpenID Connect provider (`SECTILE_OIDC_*`) or local sign-in.
  - Roles come from a claim.
  - A `users` row has a single `subject`; there is no link table for several external identities.
- `C:\git\auth0` (context repository): `private/assets/clients/Sectile ##Env##.json` registers Sectile as a plain OIDC `regular_web` client.
  - Dev callback: `https://sectile.internal.eqtv.dev/auth/callback`.
  - No SAML addon, and nothing about Jira, Atlassian, GitHub or GitLab.
  - Private-tenant connections are not managed in Git; they are enabled in the Auth0 dashboard (`CHANGELOG.md:17`).

### Ambiguities, worst first

1. **What "SSO like Jira" means.** The two readings lead to unrelated code. See Q1.
   - (A) **Connect GitHub / Connect GitLab** through OAuth, for the person's tracker credential: the mirror of #654.
   - (B) **Sign in to Sectile with GitHub or GitLab.** This can be done with no Sectile code: add a `github` social connection, or a custom OAuth2 connection for GitLab, to the Auth0 private tenant behind Sectile's existing OIDC client. That is an Auth0 dashboard change, owned by the private tenant's administrators, after which the task would close with no repository change. If (B) means providers wired into Sectile itself instead, Sectile would need several sign-in providers and the linking of several identities to one user, which it does not have.
2. **Which GitLab instances (reading A).**
   - `tracker_oauth_apps` holds one app per provider.
   - A GitLab OAuth application belongs to one instance, while Sectile's GitLab trackers each carry their own site.
   - Supporting self-hosted GitLab means one OAuth app per instance (keyed by provider and site), with the per-site resolution Jira already has.
   - See Q2.
3. **The kind of GitHub app (reading A).** See Q3.
   - A **GitHub OAuth App**:
     - is simple, with a token that does not expire and no refresh;
     - can only ask for coarse scopes: `repo` grants read and write on every repository the person can reach, private ones included.
   - A **GitHub App** (user-to-server tokens):
     - gets fine-grained permissions (issues, pull requests, contents) limited to the repositories where it is installed;
     - has tokens that expire after 8 hours and refresh with rotation;
     - requires an organisation owner to install the app on the organisations concerned.

### Reversible technical choices resolved from existing conventions (reading A)

- Follow the #654 shape per provider:
  - a *Connect* button in *Profile → Tracker credentials*;
  - `POST /api/me/tracker-credentials/{github,gitlab}/connect`;
  - a public callback at `/auth/{github,gitlab}/callback` that reads the web session;
  - the outcome shown on the profile.
- Reuse the existing tables:
  - `user_tracker_credentials` with `kind = 'oauth'`;
  - `tracker_oauth_apps` for the app saved from Administration, with `SECTILE_{GITHUB,GITLAB}_OAUTH_CLIENT_ID/_CLIENT_SECRET/_REDIRECT_URL` environment variables as fallback;
  - the grant sealed under the server key, never under a passphrase.
- Generalise rather than copy:
  - make the OAuth flow table (`jira_oauth_flows`) provider-generic;
  - generalise the grant refresh with compare-and-set and the `Bearer` branch of `ForActingUser`.
  - GitLab needs the refresh: its access tokens expire after 2 hours and its refresh tokens rotate. A GitHub OAuth App token needs none.
- The pasted token stays available behind "Use a token instead", as the API token did for Jira. Existing tokens are not migrated.
- The tracker `account` used by *My Tasks* is filled from GitHub `GET /user` (`login`) and GitLab `GET /user` (`username`), as it is for pasted tokens today.
- Scopes are the least the current calls need, pinned by a test, as `trackerapi/jira_scopes_test.go` does for Jira.
- Disconnecting deletes the row. GitHub offers a grant revocation endpoint and GitLab a token revocation endpoint, and calling them on disconnect is cheap and tidy. It is a reversible addition that changes no acceptance criterion; the specification will settle it.
- Unchanged: the server credential stays a token (ADR 0028, ADR 0029), and Desktop and the MCP tools are out of scope (as in #654).
- Documentation follows #654: a new ADR (or an amendment to ADR 0044), `docs/API_AND_DATA_SPEC.md`, `docs/USER_GUIDE.md`, French and English strings, `.env.sample`, and a CHANGELOG entry under Unreleased.

### Critical dependencies

- **OAuth apps registered outside the code (reading A).**
  - A GitHub OAuth App or GitHub App under the organisation that owns the repositories, with callback `https://sectile.internal.eqtv.dev/auth/github/callback`. A GitHub App also has to be installed on each organisation.
  - A GitLab application on gitlab.com (group- or user-owned), with callback `https://sectile.internal.eqtv.dev/auth/gitlab/callback`.
  - Whoever administers those organisations does this. As for #654, the end-to-end check against the real providers depends on it; tests use fake providers.
- **Organisation policies.** Organisations that restrict third-party OAuth access (GitHub "OAuth app access restrictions", GitLab group SAML enforcement) must approve the app. Otherwise people's grants will not see their repositories.
- **Reading B:** a change to the Auth0 private tenant (`auth-private-staging-equativ.eu.auth0.com`) by its administrators. It is not in the `auth0` repository, which does not manage private-tenant connections.
- No database migration beyond those listed under reading A; no other Sectile repository is involved.

### Product questions

1. **Q1 — Which reading?** Recommended: (A), *Connect GitHub / Connect GitLab* through OAuth for the personal tracker credential, mirroring #654. It is what was done for Jira, and it removes the pasted PAT. Alternative: (B), signing in to Sectile with GitHub or GitLab. Done in Auth0, (B) needs no Sectile code and ends this task without a pull request.
2. **Q2 — GitLab scope?** Recommended: gitlab.com only for now, with one GitLab OAuth app. A self-hosted GitLab keeps the pasted token. Alternative: one OAuth app per GitLab instance, configured per site.
3. **Q3 — GitHub app type?** Recommended: a GitHub App, which gives fine-grained permissions limited to the repositories where it is installed, at the cost of a refresh and an installation by an organisation owner. Alternative: a GitHub OAuth App, which is simpler and has no refresh but takes the broad `repo` scope over everything the person can reach.
4. **Q4 — Baseline:** is this clarification satisfactory? That includes:
   - keeping the pasted token as a fallback;
   - leaving the server credential, Desktop and the MCP tools unchanged;
   - leaving the registration of the OAuth apps on GitHub and GitLab to their administrators.

## Round 2 - answers from the owner (2026-10-09)

The owner chose the recommended option on Q1, Q2 and Q4 and the alternative on Q3, and confirmed the baseline.

- **Q1 settled: reading (A), Connect GitHub / Connect GitLab.** This is an OAuth *Connect* button per provider in *Profile → Tracker credentials* that obtains the person's own tracker credential, mirroring #654. Signing in to Sectile with GitHub or GitLab (reading B), SAML and any change to the Auth0 tenant are out of scope.
- **Q2 settled: gitlab.com only.** There is one GitLab OAuth app, stored in `tracker_oauth_apps` under `tracker = 'gitlab'` (Administration first, then the `SECTILE_GITLAB_OAUTH_*` environment variables). A GitLab tracker on another instance does not offer *Connect* and keeps the pasted token. `tracker_oauth_apps` keeps its key; no per-site app.
- **Q3 settled: a GitHub OAuth App** (the alternative, not the recommendation). This reverses the Round 1 recommendation of a GitHub App. Consequences:
  - It asks for the classic scopes. `repo` gives read and write on every repository the person can reach, private ones included. The specification pins the exact scope list the current calls need (expected `repo`, plus `read:user` if `GET /user` requires it), in a test as for Jira.
  - The token does not expire and comes without a refresh token. The GitHub grant has no refresh path. A token GitHub answers `401` for (revoked by the person or the organisation) marks the row disconnected, as `invalid_grant` does for Jira, with no fallback to the server credential.
  - No installation on organisations. An organisation that enforces "OAuth app access restrictions" must approve the app, or people's grants will not see its private repositories. This dependency stays.
- **GitLab refresh kept.** GitLab access tokens expire after 2 hours and its refresh tokens rotate, so the compare-and-set refresh generalised from `internal/db/jiragrants.go` is in scope for GitLab only.
- **Q4 settled: baseline confirmed.** In detail:
  - The pasted token stays available behind "Use a token instead", and existing tokens are not migrated.
  - The server credential stays a token (ADR 0028, ADR 0029).
  - Sectile Desktop and the MCP tools are unchanged.
  - Registering the OAuth apps on GitHub and gitlab.com, with callbacks `https://sectile.internal.eqtv.dev/auth/github/callback` and `https://sectile.internal.eqtv.dev/auth/gitlab/callback`, is left to their administrators. The end-to-end check against the real providers depends on it; tests use fake providers.
- **Unchanged from Round 1:** the reversible technical choices (the #654 shape per provider, `kind = 'oauth'`, the provider-generic OAuth flow table, a grant sealed under the server key, the `account` filled from `GET /user`, least scopes pinned by a test, documentation and CHANGELOG). Calling the provider's revocation endpoint on disconnect is left to the specification.
- No new ambiguity, dependency or product question.
