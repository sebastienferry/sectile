# Clarification: colorize board cards per epic

## Round 1 — 2026-09-23

The board should offer an option that tints each task card according to the
epic (the parent work item) it belongs to, so that a column can be read at a
glance as a set of epics rather than a list of unrelated tickets. Out of scope:
any change to how parents are imported, filtered or edited, to the workflow
stages, and to the tracker synchronization — this is a presentation option and
nothing else.

### Evidence

Read `web/src/components/TaskCard.tsx`, `web/src/components/BoardView.tsx`,
`web/src/components/BoardGroupingToggle.tsx`, `web/src/components/ListView.tsx`,
`web/src/lib/boardGrouping.ts`, `web/src/lib/boardDisplayMode.ts`,
`web/src/lib/accents.ts`, `web/src/lib/roadmap.ts`, `web/src/types/index.ts`,
`web/src/context/AppContext.tsx`, `internal/db/macros.go`, `AGENTS.md` and the
existing `web/tests/board*.test.mjs` / `condensed-card.browser.mjs` suites.

What the code already establishes:

- An "epic" is carried on the task itself as `parentKey` / `parentTitle` /
  `parentType`; there is no card for it on the board. The condensed card does
  not show the parent at all, the expanded card shows `parentKey` as a
  clickable filter in its first line.
- `TaskCard` is rendered by `BoardView` only. The Backlog (`ListView`) has its
  own row rendering, and shares the grouping toggle but not the card.
- The card root already spends its border and ring on state: running
  (indigo), queued (amber), selected (accent), dragging. A colour applied to
  the card border would collide with those states.
- Board-level display preferences (`boardGrouping`, `boardCardDisplayMode`)
  are per-user and stored in `localStorage`, not on the server.
- A 12-entry palette already exists in `web/src/lib/accents.ts`, used for
  project accents. `MacroMeta` (`internal/db/macros.go`) persists per-epic
  metadata (horizon, description, todos) but carries no colour field.

### Ambiguities, worst first

1. **Where the colour comes from.** A colour derived automatically from the
   epic key and a colour chosen and stored per epic lead to different code: the
   first is a pure front-end function, the second needs a `MacroMeta` field, an
   API and a picker in the UI.
2. **What the colour paints.** A left border, a tinted background and a dot
   next to the key are three different renderings, and only some of them
   survive next to the running/queued/selected states and the condensed card.
3. **Which surfaces are covered.** Board only, or Backlog rows, sprint
   timeline and roadmap as well.
4. **Where the option lives and how it persists.** A per-user toolbar toggle
   like the existing ones, or a project-level setting shared by the team.

### Dependencies

None outside the web front end if the colour is derived. A per-epic stored
colour pulls in `internal/db/macros.go`, the macros API and a migration.
No tracker, third-party or data dependency either way: `parentKey` is already
synchronized and present on the tasks.

### Reversible technical choices, settled here

- Derive the palette from `web/src/lib/accents.ts` rather than introducing new
  hex values, so the colours keep following the theme.
- Tasks without a `parentKey` get no colour at all — they stay exactly as they
  render today.
- The option is off by default; the board looks unchanged until it is enabled.
- The mapping is stable within a session and across reloads for the same set of
  epics, and colours may repeat when the epic count exceeds the palette size.
- Colour is never the only carrier of information: the parent key stays
  readable, so the board remains usable for colour-blind users.
- Pure helper in `web/src/lib/`, covered by a `web/tests/*.test.mjs` node test,
  as `boardGrouping` and `boardDisplayMode` already are.

### Open product questions

1. Automatic colour per epic, or a colour chosen and stored per epic?
2. What does the colour paint on the card?
3. Which surfaces beyond the Board?
4. Per-user preference or project-level setting?

Asked to the owner in session; the answers are recorded in Round 2.
