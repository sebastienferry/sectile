**Restated request.** Make the Claude Code hooks Sectile installs actually work on a Windows workstation: a session there must report waiting/working to the local agent, and an unpaired one must raise its banner, exactly as on macOS/Linux. Out of scope: the hook state machine itself (events, notification types, autonomous-run rules — settled by #174 / ADR 0012), the desktop banner rendering, and any non-Claude provider.

### Root cause, reproduced on a Windows 11 host

`registerClaudeHooks` writes the command as the bare script path, e.g. `C:\Users\<me>\.claude\hooks\sectile-hook.sh` (confirmed in a live `~/.claude/settings.json`). Claude Code on Windows hands that string to `cmd.exe`, which resolves `.sh` through the file association. On the probed host that is `sh_auto_file="C:\Program Files\Git\git-bash.exe" --no-cd "%L" %*` — a **detached GUI (MinTTY) process**. Probe result: `cmd /c "<script>"` returned exit 0 immediately, the script body never ran (its side-effect file was not written), stdin was never connected.

So on Windows today:
- the JSON payload never reaches the script, so no event is ever read;
- each of the five registered events tries to pop a Git Bash window;
- on a host with no `.sh` association, `cmd.exe` answers "not recognized as an internal or external command" → a hook error on **every tool call**.

The hook is not partly broken on Windows; it has never run.

### Ambiguities, worst first

1. **What the registered command should be on Windows.** The one expensive-to-reverse decision: it fixes the script's language, the test strategy, and whether `sectile-hook.sh` must be retired on all platforms.
2. **Where the Windows behaviour gets tested.** `.gitlab-ci.yml` runs Go tests in Linux Docker images only; it cross-compiles Windows binaries but never executes them. `hookscripts_test.go:25` hard-codes `exec.Command("/bin/sh", script)`, so the whole hook suite is unrunnable on Windows.
3. **Whether the `cwd` → session-name path is in scope.** Even once the script runs, `basename "$cwd"` on a Windows payload path `C:\git\sectile` returns the whole string, and `tr -d '"\\'` then collapses it to `C:gitsectile`, mislabelling the banner.

### Critical dependencies

- **Claude Code's Windows hook-execution contract** — `cmd.exe` semantics were verified by emulation, not from Claude Code's source. Options A and B hinge on it; option C is immune.
- **Git for Windows** — required by option B (de facto present wherever Claude Code runs natively on Windows; it also supplies `curl`, `sed`, `tr`, `basename` and sets `HOME`).
- **The agent binary's installed path** — required by option C. `Scaffold` runs inside the agent, so `os.Executable()` gives it, but a moved or reinstalled binary must still be recognised as Sectile-owned by `sectileHookFile`.
- **No Windows CI runner exists**; adding one is an infra change outside this pipeline as written.

### Questions

**Q1 — What does Windows register as the hook command?** *Recommended: C.*
- **A. A companion `sectile-hook.cmd` / `.ps1`**, installed and registered on Windows only. Minimal blast radius, but duplicates the whole event→state machine in a second language, kept in sync by hand. Under PowerShell, `curl` is an alias for `Invoke-WebRequest`, so it must call `curl.exe`.
- **B. Keep one POSIX script, prefix the command with a discovered bash**, e.g. `"C:\Program Files\Git\bin\bash.exe" "C:\Users\...\sectile-hook.sh"`. One script, one logic; needs bash discovery at install time (`bash.exe`, not `git-bash.exe`, which detaches) and correct `cmd.exe` quoting. Brittle if Git moves, and it still leaves the `basename` defect of item 3.
- **C. Make the hook a subcommand of the already-installed agent binary** (`sectile-agent hook`), registered on every platform. Removes the whole class of bug — no shell, no `curl`, no `sed`, no `jq`, no `HOME` assumption — puts the logic in Go where `internal/agentconfig` can unit-test it on any host, and the existing ownership machinery already supports the migration (`sectile-hook.sh` moves into `retiredClaudeHookFiles`, which is exactly what that list is for). Cost: it changes macOS/Linux behaviour too, so it is the largest diff and the retirement path has to be right.

**Q2 — What counts as verified for this fix?** *Recommended: (a).*
(a) GOOS-parameterised Go tests over the registration (command string, quoting, ownership/retirement), plus the existing POSIX script tests skipped on Windows with a documented reason, in the style of `internal/terminal/posix_shell_test.go`. (b) Also add a Windows CI job. (c) Manual verification on a Windows workstation only.

**Q3 — Is the mislabelled session name (item 3) part of this ticket?** *Recommended: yes* — it is the same "hooks on Windows" defect, and under option C it disappears for free (`filepath.Base` handles both separators).

### Settled scope and assumptions (resolved from existing code, no answer needed)

- Only the `claude` provider is touched; `hookFiles` returning an empty map for every other provider stays a valid installation.
- `executableHooks`' `Chmod(0700)` stays as is: a no-op on Windows, and `os.Root.Chmod` does not error there.
- The merge rules in `registerClaudeHooks` are unchanged — read, decode, touch only Sectile-owned entries, preserve third-party hooks and unknown keys, rewrite atomically, leave an unparseable file exactly as it is and report it.
- Whatever command form is chosen, ownership keeps being read from the file/executable **name**, never the full path, so a home directory or install location that moved is updated in place instead of gaining a second dead entry.
- Any rename of the installed script is accompanied by adding the old name to `retiredClaudeHookFiles`, otherwise an existing manifest is rejected as foreign by `anyManagedPath` and the stale registration fails on every turn.
- `~/.taskflow/agent-connection.json` remains the pairing file; on Windows it resolves from `os.UserHomeDir()` / `USERPROFILE`, not from a `$HOME` the shell may not set.
- Work happens in the assigned worktree `.tasks/worktrees/#260` on branch `feat/260`. No production code was written at this stage.
