# #298 - PR not synched

Round 1 - 2026-09-21

## Request restated

A task's pull request links are local Sectile state: they are written by the stage and
adjustment paths and never read back from the forge. When the same repository is opened as a
project on a second Sectile instance, the ticket sync imports the issue but no pull request
is attached to it, because nothing in the sync path ever looks for one. The ticket asks for
the ticket sync to (re)discover the pull request of a task from the forge, so a freshly
imported task carries the same evidence as the instance that created it.

Out of scope: changing how a PR is recorded at stage time, the `AcceptPullRequest` swap
guard's rules, merging or creating pull requests, and any change to the workflow stages
themselves.

## Diagnosis

Three facts, together, are the bug:

1. `ImportOrUpdateTasks` writes neither `branch_name`, `pr_url` nor `pr_links`, on INSERT or
   on UPDATE. That is deliberate for the UPDATE path - sync must not erase local evidence -
   but it means a row created by an import on a second instance starts with none.
2. `SyncSingleTaskAs` carries `BranchName` and `PrURL` over from the existing row before
   importing, and does not carry `PrLinks` at all. It never queries the forge.
3. The only forge read, `lookupStagePR` -> `BranchPullRequest(repo, branch)`, needs a branch,
   and it is called only from the adjustment / stage validation paths.

So the evidence is reachable (the forge has it), but nothing on the sync path goes and gets
it, and on a fresh instance there is not even a branch to ask with.

What does travel between instances today is the workflow stage, because it is carried by
tracker labels (`#new`, `#clarified`, ...) and mapped back in `mapping.go`. The pull request
link has no such carrier.

## Ambiguities (resolved, reversible technical choices)

1. **Where the discovery hook lives.** In `SyncSingleTaskAs`, after `GetIssue` and before
   `ImportOrUpdateTasks`, so both the background loop and a manual single-task sync get it,
   and so the discovered link is written by the same statement path as the rest.
   A separate "discover PRs" job would duplicate the scheduling machinery for no gain.
2. **How the branch is guessed when the row has none.** The repository's own convention,
   `feat/<key stripped of '#'>`, is what `ensureLocalWorktree` already derives; a derived
   branch is used only to *ask* the forge, never written to `branch_name` unless a PR comes
   back for it.
3. **What gets written on a hit.** `branch_name` from `pr.Branch` when the row has none, and
   the link appended through `models.AppendPullRequestLink` so `pr_url` stays the set's last
   entry. Never a raw UPDATE of `pr_url` alone.
4. **Failure is silent.** `BranchPullRequest` returning "expected one matching open or merged
   pull request, got 0" is the normal case for most tasks. It must not fail the sync, not be
   recorded as a sync error, and not fill the activity log.
5. **Jira and local projects are out.** `BranchPullRequest` exists only on the GitHub client;
   a Jira project has no repository binding on this path. The hook is a no-op for any tracker
   other than GitHub. Flagged, not silently assumed - see open question 4.

## Dependencies

- GitHub API budget. Autosync already issues one `GetIssue` per unfinished task per pass. A
  naive per-task PR lookup doubles that. Question 3 below is about containing it.
- Finished tasks are skipped by `runAutoSyncPass` (`StatusFinished` / tracker status `Done`).
  On a second instance, a task imported straight into `#finished` would never be visited, so
  it would never recover its PR link. A one-shot backfill would need its own entry point.
- No migration: `pr_links` and `pr_url` already exist, and a row with an empty set is the
  exact state this feature fills in.

## Open product questions

1. **Scope: link only, or state too?** Should the sync only attach a *missing* pull request,
   or also refresh the state (open / merged / draft) of an already recorded one so the board
   can show a merged PR without running a stage?
   *Recommendation: link only for this ticket. Refreshing state means storing state, which is
   a new column and a new UI contract - a separate ticket.*

2. **Discovery source.** Which signal identifies the PR of an issue?
   (a) the conventional branch `feat/<n>` only - one API call, exact, but blind to a PR on a
   hand-named branch; (b) the branch, then the issue's GitHub cross-references / closing
   keywords as a fallback - catches any branch, but a mere mention in a PR body also shows up
   as a cross-reference; (c) one repo-wide scan of open and recently merged PRs per pass,
   matched by branch and by `Fixes #n`, then spread over the tasks - cheapest at scale.
   *Recommendation: (a) now, and record (b)/(c) as follow-ups. The repository's PRs are all on
   `feat/<n>`, and (c) trades exactness for a matching heuristic the swap guard would then
   have to police.*

3. **Which tasks, at what cadence.** Every unfinished task on every pass, or only tasks whose
   link set is empty and whose stage is at or after the project's `prCreationStage`?
   *Recommendation: the restricted set. A task with a recorded link needs nothing, and a task
   still in `#new` has no branch yet - both are pure API cost.*

4. **Non-GitHub projects.** Confirm that a Jira-tracked project keeps no PR discovery at all
   for now, rather than this ticket also introducing a repository binding for Jira.
   *Recommendation: confirm out of scope.*

5. **Contradiction handling.** If the forge returns a PR on a branch unrelated to the links
   already recorded, `models.AcceptPullRequest` refuses it today for a stage transition.
   What should a *background sync* do - ignore it silently, append it anyway, or surface it
   as something the user resolves from the task detail view?
   *Recommendation: ignore silently and never append; the sync is not a place to override a
   guard the interactive paths enforce.*
