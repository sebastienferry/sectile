# Clarification #515 - Desktop close and next button

- Ticket: https://github.com/sebastienferry/sectile/issues/515
- Branch: `feat/515`
- Stage: new -> clarified

## Round 1 - analysis (2026-09-26)

### Request restated

In the desktop app's console toolbar, the workflow button that launches the
task's next step carries a `>` chevron like the web task card, and a second
`>>` button launches the full `pickup` chain on the selected task in one
click. Out of scope: the closing button (the circled check of `#stop`, which
the ticket keeps as is), the web client, the workflow itself, and the launch
mechanics already behind the next-step button (freshness recheck, duplicate
guard, "Launch anyway").

### What exists today (files read)

- `desktop/src/main.js:41`: the toolbar holds the icon buttons `#rerun`,
  `#save-log`, `#stop`, then the text buttons `#next-step`, `#mark-reviewed`,
  `#retry-next-step` and `#force-next-step`.
- `desktop/src/main.js:2046` `iconPaths`: `#stop` ("Stop execution") is drawn
  as a circle holding a check mark. This is the "check button" the ticket
  calls the closing button and keeps.
- `desktop/src/main.js:2589` `renderNextStep()`: since #500 the button reads
  `Next: <label>` when idle and enabled, and `Current: <skill>` (disabled)
  while any execution of the task is active or being submitted.
- `desktop/src/main.js:2645` `launchNextStep(force)`: re-reads the task and
  the runs, refuses when the step changed or a run became active, then calls
  `api.launchServerTask(projectId, taskId, skillId, '', undefined, force)`. A
  409 duplicate refusal reveals "Launch anyway".
- `desktop/src/main.js:2238`: the Tickets pane's per-row menu already offers
  "Pickup (full chain)" when the project exposes a `pickup` skill, launched
  through `submitTicketLaunch()` with no mode.
- `desktop/src/workflow.mjs`: `nextTaskStep()` and `skillLabel()`; `pickup`
  is shown as `Pickup`.
- `web/src/components/TaskCard.tsx:984-1009`: the full card shows two
  icon-only buttons, `ChevronRight` (next step, tooltip `stepTooltip`) and
  `ChevronsRight` (full chain, tooltip `autoTooltip`), both disabled while a
  launch from the card is in flight or when the task is finished. The
  condensed card puts the same two actions in its menu (line 602-608).
- `web/src/context/AppContext.tsx:3021` `advanceTask(auto)`: the full chain
  is one run of the `pickup` skill, forced to `mode: 'autonomous'` ("a full
  chain is autonomous by construction"); the single step accepts the one-off
  mode override.

### Ambiguities (worst first)

1. **Icon only, or chevron plus label.** The web buttons are icon-only.
   Reading A replaces the `Next: Specify` / `Current: Pickup` text by a bare
   `>` icon, the label moving to the tooltip and accessible name. Reading B
   keeps the #500 label and adds the chevron in front of it. #500 was merged
   yesterday precisely to show that label on the button, so the two readings
   produce visibly different toolbars.
2. **What `>>` shows during a run.** The `>` button turns into the
   `Current: <skill>` indicator while a run is active. `>>` can be disabled,
   or hidden, in that state.
3. **Launch mode of `>>`.** The web forces `autonomous`; the desktop Tickets
   pane's "Pickup (full chain)" sends no mode, so the precedence (override >
   skill > project default > interactive) decides.
4. **Tickets pane.** Whether the per-row `Run: <label>` button of the
   Tickets pane gains the same `>` / `>>` pair or is left alone.

### Critical dependencies

None. The change is confined to the desktop renderer (`desktop/src/main.js`,
its stylesheet and UI tests). The server already accepts a `pickup` launch
through the same endpoint and reports `pickup` in `server.skills` when the
project has it. No migration, MCP or tracker change.

### Technical choices resolved from the code

- **Icons.** The chevrons are drawn in the existing `iconPaths` style
  (24x24 stroke SVG, `currentColor`), matching the lucide `ChevronRight` and
  `ChevronsRight` glyphs the web uses.
- **`>>` availability.** Hidden when the project exposes no `pickup` skill
  or the task is finished, like the next step. Disabled while any execution
  of the task is active or a launch is being submitted, sharing the busy and
  pending guard of `>`.
- **`>>` launch path.** It reuses `launchNextStep()`'s mechanics (freshness
  recheck of the runs, duplicate refusal, "Launch anyway", selection of the
  new console) with `pickup` as the skill instead of the stage's step, so
  both buttons behave identically apart from the skill launched.
- **Label while running.** A running pickup already reads `Current: Pickup`
  through #500; nothing new is needed.
- **Accessible names and tooltips** in English, consistent with the rest of
  the toolbar: `>` keeps `Next: <label>` / `Current: <skill>` as its
  accessible name; `>>` is named `Pickup (full chain)`, the wording the
  Tickets pane menu already uses.
- **Tests.** `desktop/tests/next-step.ui.cjs` gains the `>>` cases
  (visible, disabled during a run, launches `pickup`, hidden without the
  skill); the existing `Next:` / `Current:` assertions stay valid through the
  accessible name.
- **Changelog.** User-visible, so one `Changed` or `Added` line under
  `[Unreleased]`.

### Product questions (recommendation first)

1. Shape of the next-step button: **Recommended: chevron plus the existing
   label** (`> Next: Specify`, `Current: Pickup` while running), because #500
   has just put that label on the button. Alternative: icon-only `>` as on
   the web card, label in the tooltip.
2. `>>` during a run: **Recommended: visible and disabled**, so the toolbar
   does not shift when a run starts or ends. Alternative: hidden.
3. Launch mode of `>>`: **Recommended: forced `autonomous`**, as the web
   card does, since nobody answers a full chain step by step. Alternative:
   let the configured precedence decide, as the Tickets pane menu does today.
4. Tickets pane `Run: <label>`: **Recommended: out of scope**; its menu
   already offers "Pickup (full chain)". Alternative: add the same `>` / `>>`
   pair to each row.

## Round 2 - answers from the owner (2026-09-26)

### Settled choices

1. **Icon buttons plus a small badge.** `>` and `>>` are icon-only buttons,
   as on the web card. The step label moves out of the button into a small,
   non-clickable badge placed next to them: `Next: Specify` when idle,
   `Current: Pickup` while an execution of the task is active or being
   submitted. The label rules settled by #500 (which skill `Current:` names,
   what counts as running) are unchanged; only where the text is drawn moves.
2. **`>>` during a run: visible and disabled**, sharing the busy and pending
   guard of `>`, so the toolbar does not shift when a run starts or ends.
3. **`>>` launches `pickup` in forced `autonomous` mode**, as the web card
   does.
4. **The Tickets pane is out of scope**: its `Run: <label>` button and its
   "Pickup (full chain)" menu entry stay as they are.

Reversed assumption: round 1 recommended keeping the label inside the
next-step button (chevron plus text). The owner chose icon-only buttons with
the label in a separate badge.

### Follow-up points resolved from the code

- **Accessible names.** The `>` button keeps `Next: <label>` /
  `Current: <skill>` as its accessible name and tooltip, so the existing
  #500 assertions in `desktop/tests/next-step.ui.cjs` keep their meaning; the
  badge repeats that text visually and is hidden from assistive technology to
  avoid announcing it twice (the footer `#next-step-status` already is the
  live region). `>>` is named and titled `Pickup (full chain)`.
- **Badge visibility** follows the `>` button: hidden whenever `>` is hidden
  (no task selected, free console, finished task, step unavailable, workflow
  loading or in error).
- **Launch mode plumbing.** `api.launchServerTask()` already takes a mode
  argument (the Tickets pane passes it through `submitTicketLaunch()`); `>>`
  passes `autonomous`, `>` keeps passing none.

### Acceptance criteria

- The toolbar shows a `>` icon button and, when the project exposes a
  `pickup` skill, a `>>` icon button, both drawn in the existing icon style.
- A small badge next to them reads `Next: <label>` when idle and
  `Current: <skill>` while an execution of the task is active or being
  submitted, following the #500 rules.
- `>` launches the stage's next step exactly as the former text button did.
- `>>` launches `pickup` in `autonomous` mode through the same freshness
  recheck, duplicate refusal and "Launch anyway" path, and selects the new
  console.
- During an active or submitted execution, both buttons are visible and
  disabled; on a finished task, both buttons and the badge are hidden.
- `#stop`, "Mark reviewed", "Retry", "Launch anyway", the footer status and
  the Tickets pane behave as today.
- `desktop/tests/next-step.ui.cjs` covers the badge, the `>>` launch and its
  mode, its disabled state during a run, and its absence without a `pickup`
  skill.
- `CHANGELOG.md` gains one line under `[Unreleased]`.

None. The owner confirmed the clarification on 2026-09-26.
