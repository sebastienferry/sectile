# Clarification #580 - Add option to create branch and PR at clarification state

- Ticket: https://github.com/sebastienferry/sectile/issues/580
- Branch: `feat/580`
- Report: `docs/clarifications/580.md` (committed on `feat/580`)

## Round 1 - initial analysis (2026-09-28)

### Request

The project setting "PR creation stage" (`prCreationStage`) offers two values
today, `implemented` (default) and `specified`. The ticket asks for a third
value, `clarified`, so that the clarification skill pushes the task branch and
opens a draft pull request, which the later stages then update, and so that
the server requires that pull request on the `new -> clarified` transition.

Out of scope: changing the six workflow stages, making the pull request ready
before adjustment, opening pull requests in context repositories at
clarification, and any change to the default (`implemented`) or to projects
that already use `specified`.

The ticket has no description and no comments; this reading comes from its
title and from the existing `specified` option, which is the same feature one
stage later.

### Code read

- `internal/db/db.go` (create/update project validation, lines ~6405 and ~6553):
  only `specified` and `implemented` are accepted.
- `internal/agentconfig/validation.go`: same two-value check on the agent side.
- `internal/db/adjustment.go`: `prCreationOwner` returns `specify` or
  `implement`; `stagePRRequired` requires evidence for `implement`, `adjust`,
  `pickup`, `create_pr`, and `specify` only when it owns creation.
- `internal/db/stage.go` and `internal/db/postback.go`: the stage-to-skill map
  used for PR validation has no `clarified` entry, so a `clarified` transition
  is never checked for a pull request today.
- `internal/db/stageprs.go`: `prDeferredBySpecArtifacts` defers the PR when the
  workstation drops specification artefacts, for `specify` only.
- `internal/db/projectskills.go`: the "Project pull request policy" paragraph is
  appended to `specify`, `implement`, `adjust`, `pickup`, `pickup_issues`, not
  to `clarify`, and knows two timings.
- `internal/db/prdiscovery.go`: rediscovery is gated by `stageRank` of the
  creation stage; `clarified` already ranks correctly.
- `web/src/components/ProjectModal.tsx`, `web/src/locales/projectSettings.ts`,
  `web/src/types/index.ts`, `web/src/lib/workflow.ts` (`prRecoverySkill`),
  `desktop/src/workflow.mjs` (`implementedStep`): UI select, labels, type and
  the "Create PR" recovery step, all two-valued.
- `docs/contracts/server-agent-v1.md` ("PR/MR creation timing", "Adjustment and
  PR ownership") and `docs/adrs/0004-adjustment-and-earlier-pr-ownership.md`.

Neighbouring feature: the `specified` value (#61, ADR 0004), including the
dropped-artefacts deferral (#487). The new value reuses both mechanisms.

### Ambiguities (worst first)

1. **When, during clarification, the pull request is opened.** Clarification
   runs in rounds and may stop several times with open questions before the
   `clarified` transition. Opening the draft at the first round that commits
   the report lets the owner read and comment on it in the PR during the
   rounds; opening it only at the final round keeps unresolved clarifications
   off the forge. The code differs: the first reading makes every committed
   round push and create-or-reuse the PR; the second only the final one.
   Either way the server checks the PR at the `clarified` transition only.
   -> Product question Q1.
2. **A third value versus a separate toggle.** "Add option" could mean a new
   checkbox independent of `prCreationStage`. The setting already expresses
   exactly "which stage creates the draft", so a third value is the natural
   fit. -> Product question Q2 (recommendation: third value).
3. **Dropped artefacts.** When `docs/clarifications/<n>.md` is ignored by Git,
   the clarification commits nothing and there is nothing to push. Resolved
   below by reusing the existing deferral.
4. **"Create branch".** The task branch `feat/<n>` already exists locally at
   clarification (Sectile assigns it at launch); what is missing is its
   publication. Resolved below: "create the branch" means push it.

### Critical dependencies

- No migration: `pr_creation_stage` is a free `TEXT` column; only validation
  changes. No new column, so no replay-fixture or rewind-helper impact.
- Forge access is required at clarification when the value is `clarified`,
  exactly as for `specified` today (ADR 0004 consequence).
- Agents on older builds validate `prCreationStage` against two values
  (`internal/agentconfig/validation.go`): a project set to `clarified` read by
  an old agent fails that validation. The agent and server ship together, but
  the desktop agent may lag; to be covered in the specification.

### Technical choices resolved from existing conventions

- **Value and ordering**: `prCreationStage` accepts `clarified`, `specified`,
  `implemented`; default stays `implemented`. Validation in `db.go` (create and
  update) and `agentconfig/validation.go` accepts the three.
- **Ownership**: `prCreationOwner` returns `clarify` for `clarified`.
  `stagePRRequired` requires evidence for `clarify` when it owns creation. The
  stage-to-skill map in `stage.go` and `postback.go` gains
  `clarified -> clarify`, so the transition is validated like `specified`.
- **Later stages**: with `clarified`, `specify` also requires the PR (it must
  update the existing draft, not create another), and `implement` and `adjust`
  behave as they do under `specified`.
- **Skill policy text**: the "Project pull request policy" paragraph is also
  appended to `clarify`, with a `clarified` wording: push the branch
  (`git push -u origin <branch>`, never force), create or reuse a draft PR,
  pass its URL as `prUrl` in the `clarified` transition; later stages update
  the same PR; readiness only after adjustment.
- **Dropped artefacts**: when the clarification report is ignored by Git, the
  `clarified` transition is accepted without a PR, with the same deferral
  notice; `specify` then owns creation if its artefacts are kept, else
  `implement`. `prDeferredBySpecArtifacts` extends to `clarify`.
- **Recovery ("Create PR" at `implemented` without a PR)**: routed to
  `implement`, not `clarify`, since re-running a clarification dialogue to
  publish a branch makes no sense. `web/src/lib/workflow.ts` and
  `desktop/src/workflow.mjs` keep `specify` for `specified`.
- **PR discovery gate**: unchanged; `stageRank("clarified")` already places it
  before `specified`.
- **Multi-repository tasks**: only the primary repository gets a PR at
  clarification; context repositories are not changed at this stage.
- **UI**: a third option, "Brouillon après la clarification" / "Draft after
  clarification", first in the list; `prHelp` wording checked.
- **Docs**: `docs/contracts/server-agent-v1.md` updated; ADR 0004 amended (or a
  short follow-up ADR) to record the earlier owner; `CHANGELOG.md` gets an
  `Added` line under `[Unreleased]`, since the option is user-visible.

### Open product questions

- **Q1 - When is the draft opened during clarification?**
  - (a) *Recommended*: at the first round that commits the report, reused by
    every later round, required at the `clarified` transition. The owner can
    follow and comment on the clarification in the PR.
  - (b) Only at the final round, when the owner confirms the clarification.
- **Q2 - Form of the option?**
  - (a) *Recommended*: a third value `clarified` of the existing
    "PR creation stage" setting.
  - (b) A separate project toggle.
