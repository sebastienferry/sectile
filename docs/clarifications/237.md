## Restated request and scope

Give Sectile a real user layer for a server shared by several people: sign in
and out against an identity provider, a profile page, a role per user, a
binding between users and projects, and interface controllers that refuse
anonymous callers. Out of scope, as read: a local password store or account
creation inside Sectile, a per-task permission model, task-level visibility
rules, and any change to how the tracker itself authenticates.

## Verified findings

Three of the five bullets already exist on `main`; the ticket is mostly about
the two that do not.

- **Login / Logout.** ADR 0008 ships OpenID Connect sign-in (authorization code
  with PKCE, server-side opaque sessions, `HttpOnly` cookie): `/auth/login`,
  `/auth/callback`, `/auth/logout`, `/api/me` in `internal/handlers/auth.go`,
  provider discovery in `internal/auth/oidc.go`, sessions in
  `internal/db/sessions.go`. The ticket says "OAuth"; OIDC is OAuth 2.0 plus an
  identity layer, and the deployment target (Okta) is an OIDC provider.
- **Profile page.** `web/src/components/ProfileModal.tsx` already hosts
  `SignInStatus` (who is signed in, sign in / sign out), `ApiKeysPanel`
  (workstations, pairing, keys) and `LocalAgentSetup`. Its name and e-mail
  fields still write the global `settings.userName` / `userEmail` /
  `userAvatar` columns, a single-user leftover that is not tied to the signed-in
  user; the `users` table carries `email` and `display_name` from the provider.
- **Controllers restricted to authenticated callers.** `RequireSession` wraps
  the whole mux in `cmd/server/main.go`, and `publicPath` names the exemptions
  (`/auth/`, `/api/me`, `/api/v1/agent/`, `/mcp`, `/ws/agent-connect`,
  `/health`, static files). `TestOnlyIntendedPathsBypassTheSessionGuard`
  pins that list. The guard is active **only when an OIDC provider is
  configured**; without one every request resolves to `ImplicitUser`
  (`internal/handlers/pairing.go`), which ADR 0008 chose deliberately for
  personal deployments. Machine surfaces authenticate with the workstation API
  key of ADR 0011, which resolves to a user (`resolveAgentCredential`).
- **User role: absent.** No `role` column, no admin concept, no authorization
  check anywhere. ADR 0008 states it verbatim: "Identity is authentication,
  not authorization. Roles would be a separate decision." Global settings are
  one row shared by everyone who signs in.
- **User-to-project binding: absent.** `projects` has no owner or member
  column. `teams` / `team_members` are tracker-side accounts imported from the
  issue tracker, not Sectile users, and cannot serve as the binding. The only
  user-to-project relation today is the in-memory dispatcher key
  `(UserID, ProjectID)` that routes a run to the right connected agent, and
  `AgentProjects()` serves every project to every key holder. ADR 0007 records
  that "tasks stay shared" and that a per-user view "would be a product
  decision, not a consequence".
- **Attribution gap.** `task_activities` has no user column and
  `task_comments.author` is free text. A role model that cannot say who did
  what is half a model; the ticket does not ask for attribution, so it is
  listed as an assumption below rather than added silently.
- **Authorization hole worth closing in this ticket.** `HandleAgentDispatch`
  accepts a `userId` in the request body and only falls back to the session
  when it is empty. Once roles exist, any signed-in user could drive another
  user's agent by naming them. The same applies to `/api/settings`, which any
  session can rewrite for everyone.
- **Small inconsistency, out of scope but noted.** `publicPath` exempts
  `/health` while the route is `/api/health`, which `alreadyServing` and the
  desktop server check call. With a provider configured those probes get a 401.

## Ambiguities, worst first

1. **What a role is and what it gates.** "Implement the user role" names
   neither the roles nor the actions they protect. Two roles with a fixed
   matrix and a free-form permission set are different schemas, different
   handlers and a different profile page.
2. **What the project binding means.** Three readings lead to different code:
   a visibility filter (a member sees only bound projects and their tasks), an
   authorization scope (everyone sees everything, only members may act), or a
   routing hint (which agent receives a run, which already exists). The first
   reading reverses ADR 0007's "tasks stay shared".
3. **Who the first administrator is.** With an identity provider, every user
   arrives through sign-in as an equal. Without a bootstrap rule nobody can
   assign roles or bind projects, so the feature is unusable on day one.
4. **Whether a personal deployment must now sign in.** "Controllers are
   restricted to isAuthenticated" read literally would end the implicit-user
   mode of ADR 0008 and require an OIDC provider to run Sectile alone.
5. **Whether roles and bindings also bind machine callers.** Agents, the
   desktop app and MCP clients hold a key that resolves to a user. Applying
   the same rules there means filtering `AgentProjects`, dispatch and MCP tool
   calls; not applying them leaves a bypass.

## Critical dependencies

- A reachable OIDC provider (Okta in the target deployment) to exercise real
  multi-user sign-in; the exchange itself is untestable offline, as ADR 0008
  notes. Roles and bindings can be tested with `SECTILE_DEV_IDENTITY=1`.
- A SQLite schema change: a `role` column on `users` and a new
  `project_members` table, following the idempotent `CREATE TABLE IF NOT
  EXISTS` / `ALTER TABLE ADD COLUMN` pattern already used in
  `initIdentitySchema`. Explicit column lists in `users` queries must be
  updated together (the trap recorded in `.agents/MEMORY.md`, section 5).
- The server/agent contract v1 (`GET /api/v1/agent/projects`,
  `/api/agent/dispatch`) if the binding filters what an agent may see.
- No other team or external service. No data we do not have.

## Questions and answers

1. **Which roles, gating what?**
   Answered: two roles, `admin` and `member`, stored on `users.role`. Admin:
   manage users and roles, create and delete projects, edit global settings
   and tracker credentials, revoke anyone's workstations, cancel anyone's run.
   Member: everything else. A read-only `viewer` is deferred.
2. **Visibility filter, authorization scope, or routing hint?**
   Answered: routing hint (reading A), with one ownership rule on runs. The
   board stays shared: every signed-in user sees every project and every task,
   as ADR 0007 and 0008 promise. The user-to-project binding is the existing
   agent registration, one connected agent per `(user, project)`. What a
   member may not do is act on a colleague's execution: dispatching a run to
   another user's agent and canceling a run started by someone else are
   refused unless the caller is an admin. No `project_members` table is
   created in this ticket; a persisted membership remains a later decision.
3. **How is the first admin chosen?**
   Answered: roles come from the identity provider (option 3), through a group
   claim, and Sectile acts as its own minimal identity provider until a real
   one is connected. In that local mode an account is created from an e-mail
   address alone, without password, and the first account created is admin.
   The role is stored on `users.role` in both modes; with an external provider
   it is refreshed at every sign-in from the configured group claim.
4. **Okta / Auth0 interconnection?**
   Answered: one active provider at a time, chosen by configuration, and the
   role read from a group or role claim, Auth0 being the probable first
   provider. The existing OIDC flow already supports both vendors without
   code; the change is the claim.

## Resolved decisions (reversible, settled from existing code)

- **Two sign-in modes, never both.** `SECTILE_OIDC_ISSUER` set: the OIDC
  flow of ADR 0008, unchanged. Not set: the new local mode, reached from the
  same `/auth/login` route, which asks for an e-mail and opens a session for
  the matching account, creating it on first use. The `SECTILE_DEV_IDENTITY`
  header switch is retired: the local mode is its supported successor. The
  provider-less implicit user survives only for a database that has no local
  account yet, so an existing personal deployment keeps working until its
  owner creates the first account.
- **Local mode is identification, not authentication.** An e-mail without a
  password or a mailed link proves nothing; anyone who types a colleague's
  address is that colleague. The owner accepts this as a transitional step
  toward a real provider. The mode is therefore explicit in the sign-in
  screen and in `/api/me`, documented in `.env.sample` and `README.md` as
  unsuitable outside a trusted network, and disabled the moment a provider is
  configured. A mailed magic link is the first hardening if the transition
  lasts; it is not in this ticket.
- **Role claim is configuration.** `SECTILE_OIDC_ROLE_CLAIM` names the claim
  (Okta: a `groups` claim on the authorization server; Auth0: a namespaced
  claim added by an Action) and `SECTILE_OIDC_ADMIN_GROUP` names the value
  that grants `admin`; any other value or an absent claim yields `member`.
  The claim is read from the UserInfo response the flow already fetches, and
  falls back to the ID token payload if the provider only puts it there. The
  exact Auth0 Action and Okta claim setup are verified during specification
  against a tenant, not assumed.
- **Machine callers are bound by the same rules.** `resolveAgentCredential`
  already yields a user; the ownership rule on runs applies at that resolution
  point for `/api/v1/agent/*`, the agent WebSocket, `/mcp` tools and the
  desktop routes, so a key is never a way around the board's rules.
- **`userId` in request bodies is no longer trusted.** `HandleAgentDispatch`
  and any handler that accepts a caller-supplied user take the session's or
  the key's user instead; an admin acting for someone else is an explicit
  future case, not an implicit one. Global settings and tracker credentials
  become admin-only mutations.
- **Runs record who started them.** The ownership rule needs an owner:
  `task_activities` gains a `user_id` column, written by `start_run`, the
  dispatcher and the tracker operations, following the explicit-column-list
  pattern in `.agents/MEMORY.md`. Comments record the acting user id as well.
  No backfill of existing rows; a run without owner may be canceled by an
  admin only.
- **OIDC satisfies "OAuth".** No GitHub OAuth app is added; the provider is
  configuration (ADR 0008).
- **The profile stays where it is.** Extend `ProfileModal` with the sign-in
  mode, the identity, the role and the projects where the user has a
  registered agent, next to the existing workstation panel. The
  `settings.userName` / `userEmail` / `userAvatar` fields stop being written
  once an account exists and are retired in a later ticket, per the
  retired-column pattern in `.agents/MEMORY.md`.
- **Unauthenticated interface calls redirect to sign-in.** The SPA has no 401
  handling today; a 401 on the interface API sends the browser to
  `/auth/login?redirect=<current path>` rather than failing silently. The
  JSON 401 for non-browser callers is unchanged.

## Settled scope and explicit assumptions

- Reuse the assigned branch and worktree. No production code and no
  specification were written at this stage.
- Deliverables for specification: local sign-in mode (e-mail account creation,
  session, sign-in screen, retirement of `SECTILE_DEV_IDENTITY`),
  `users.role` with the first-account-is-admin rule and the OIDC group claim
  refresh, `task_activities.user_id` and comment attribution, the ownership
  rule on dispatch and cancel, admin-only users view (list, role change),
  admin-only global settings and tracker credentials, the dispatch `userId`
  fix, profile extensions, the SPA sign-in redirect, an ADR recording the
  role model, the local mode and its limits, and updates to
  `docs/contracts/server-agent-v1.md`, `docs/CAPABILITIES.md`, `.env.sample`
  and `README.md`.
- Assumption: the role model has exactly two values; a provider group that
  maps to neither is `member`. Assumption: an admin may change any local
  account's role from the users view, and that change is overwritten at the
  next sign-in when an external provider supplies the claim.
- Not in scope: a `project_members` table or any visibility filter,
  task-level permissions, passwords or mailed links in the local mode,
  several simultaneous providers, tracker-side permission mirroring,
  migrating `team_members` into Sectile users.
