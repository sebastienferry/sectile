## Round 1 (2026-09-30)

### Request

A Jira project can already declare other tracker projects, but only so that
their story keys attach to slicing lines. This ticket reads the epics of those
declared projects into the roadmap, lets the viewer pick which projects to show
(with a count per project, remembered), marks those epics as read only, lets a
slicing line create its story in a declared project, and adds a per-project
opt-in to write the priority and the quarter on those epics, one epic at a time.

Out of scope: importing any work item other than epics from a declared project
(board, counters and facets stay those of the project's own key); declared
projects on GitHub or GitLab (the setting is Jira only today,
`web/src/components/ProjectModal.tsx:431`); mapping the axes to tracker custom
fields (#635); epic template sections (rows 44 to 46, left out by #426); batch
creation of stories (#634).

### What already exists

- `projects.roadmap_projects` stores the declared keys, normalised
  (upper-cased, deduplicated, own key dropped). Only Jira projects save it.
- The declared keys only feed `entryKeyPrefixes`: a story key of theirs found in
  a slicing file attaches to its line. Creating a story on such a line is
  refused (`macros.go:527`).
- `ImportMacroHorizons` reads the epics of the project's own key only, through
  a single `ListEpics` call (`jiraJQL(key, nil, "issuetype = Epic")`).
- Every axis write and every pending push already skips an epic whose key does
  not carry the project's prefix (`belongsToProject`), so the server side of
  "read only" is in place; the panel has nothing to mark because foreign epics
  never arrive.
- Axis writes on an epic are labels today (#627); custom fields are #635.

### Ambiguities, worst first

1. **Does creating a story in a declared project break the read-only rule?**
   #426 wrote "Sectile creates no story there". The ticket asks for exactly that
   (row 43) and says the only exception is the axis opt-in. Creating a story and
   setting its epic parent are writes to the declared project. Two readings: the
   creation is allowed to anyone, as Taskativ does, or it sits behind the same
   per-project opt-in as the axes. → **Q1**.
2. **What does a story created in a declared project become locally?** Every
   Sectile task belongs to a Sectile project, and a declared key is not one.
   Either it is not imported (the line keeps its key and links to the tracker;
   the epic's counters and progress never count it), or it is imported somewhere,
   which contradicts "no work item of a declared project is imported". → **Q2**.
3. **What does the axis opt-in write while #635 is open?** Taskativ opened the
   writes once the axes landed in real tracker fields. In Sectile they are still
   labels (`roadmap:`, priority and quarter labels), so the opt-in would put
   Sectile's labels on another team's epics. → **Q3**.
4. **Default origin selection on a first visit.** Showing all declared projects
   can bring thousands of epics (Taskativ saw 1,363 foreign epics for 162 of its
   own). Settled below (D5): own key only.
5. **What the count per project counts.** Settled below (D6).

### Critical dependencies

- **Jira only.** Declared projects exist for Jira projects only; nothing changes
  for GitHub, GitLab or local projects.
- **One read per declared key.** Each key is its own `ListEpics` call with its own
  timeout; a single JQL `project in (...)` would let one unreachable key fail the
  project's own read. N declared keys means N+1 calls per epic import.
- **Acting user (#482).** A story created in a declared project, and an opted-in
  axis write, go through the acting person's Jira token like any other tracker
  write.
- **Migration.** The opt-in is one new column on `projects`, closed by default,
  added in `internal/db/migrations.go` only (never in the frozen baseline), with
  the rewind test helpers updated.
- **Study not merged.** The comparison document cited by the ticket is not on
  `main`; the specification must not link to a path that does not exist there
  unless #619 lands first.
- **Existing foreign macros.** A macro whose key carries another prefix can
  already exist locally (attached through a story's parent); it will now be
  grouped under its own prefix in the origin selection.

### Technical choices settled here (reversible)

- **D1. Storage.** Foreign epics are stored in `macros` under the declaring
  project's id, like any macro; their origin is derived from the key prefix
  (`belongsToProject`), never stored. No new table.
- **D2. Read path.** `ImportMacroHorizons` reads the own key, then each declared
  key through its own call; a failing key is named in the returned summary and
  does not stop the others. Labels, title, status and closed state are imported
  exactly as for own epics.
- **D3. Read-only mark.** The roadmap panel shows a "read only" mark with the
  origin key on a foreign epic, and hides its write actions (horizon push, axes,
  labels, framing comment push, creation of the epic). The existing server
  guards stay the single crossing point and remain the enforcement.
- **D4. Classification stays local.** Classifying a foreign epic (horizon,
  priority, quarter) is recorded locally and says so; it never enters the pending
  pushes list.
- **D5. Default selection.** On a first visit, only the project's own key is
  shown. An empty selection falls back to the own key. A key no longer declared
  but still carried by stored epics stays offered. A declared key with no epic
  is offered at zero.
- **D6. Count.** Each origin shows the number of its epics the roadmap would list
  with the other current filters applied (closed epics follow the same rule as
  the list).
- **D7. Remembered selection.** Stored in `localStorage`, keyed per project, like
  the other roadmap view choices (`usePersistedFlag`); per browser, not synced
  between web and desktop.
- **D8. Target picker.** Declared keys join the slicing line's target picker with
  a sublabel naming them as tracker projects; the key is rechecked against the
  current declaration at creation time.
- **D9. Batch passes.** Any pass that walks every macro keeps skipping foreign
  epics whatever the opt-in; the opt-in only opens the single-epic controls.
- **D10. Opt-in location.** The opt-in is a checkbox under the declared projects
  field in the project's Tracker settings, shown only when at least one project is
  declared. When it is off, the panel says why the priority and quarter controls
  are missing and where to open them.

### Product questions

- **Q1. Is creating a story in a declared project allowed without the opt-in?**
  Recommended: **yes**. Each creation is an explicit gesture on one line that names
  its target, and it adds new work rather than changing another team's items.
  The #426 rule then reads "Sectile never changes an existing item of a declared
  project, except the axes when opted in", and the ticket's last sentence is
  amended accordingly. Alternative: gate it behind the same opt-in as the axes.
- **Q2. Is a story created in a declared project left out of Sectile?**
  Recommended: **yes, not imported**. The line records its key and links to the
  tracker; the story does not enter the board, the counters or the epic's
  progress. That is the price of not importing another team's tickets. The
  alternative (import it into the project creating it) would make the board show
  tickets of another team.
- **Q3. What should the axis opt-in write while #635 is open?** Recommended:
  **keep row 42 in this ticket and write through the same crossing point as own
  epics**, which means Sectile's priority and quarter labels today and the mapped
  fields once #635 lands; closed by default. Alternatives: (b) ship rows 39 to 41
  and 43 now and move row 42 to after #635; (c) drop row 42.

### Settled

- **Q1 → creation allowed without the opt-in.** A slicing line may create its
  story in a declared project whatever the opt-in says, and set the epic as its
  parent. The #426 rule is restated as: *Sectile never changes an existing item
  of a declared project, except the priority and the quarter of one epic at a
  time when the project opted in.* The ticket's last sentence ("except for that
  opt-in") is read with that amendment: creating a new story is not a change to
  an existing item.
- **Q2 → the story is not imported.** The line records the created key and links
  to the tracker. The story enters neither the board, the counters, nor the
  epic's progress. The creation's answer says so, so the person is not surprised
  when the story does not appear on the board.
- **Q3 → row 42 stays in #632, through labels.** The opt-in, closed by default,
  opens the priority and quarter controls on a foreign epic, one epic at a time.
  The write goes through the same crossing point as an own epic's axes: Sectile's
  priority and quarter labels today, the mapped fields once #635 lands, with no
  second change needed here. Batch passes and pending pushes keep skipping
  foreign epics (D9, D4); horizon, free labels and the framing comment stay
  refused on them.

### Reversed or refined assumptions

- The #426 wording "Sectile creates no story there" no longer holds; it is
  replaced by the rule above. The `macros.go:527` refusal is replaced by the
  creation path of D8.
- D4 is refined: with the opt-in open, a priority or quarter set from the panel
  on a foreign epic is pushed; without it, it stays local. The horizon of a
  foreign epic stays local in every case.

### New ambiguities or dependencies

None that alter acceptance criteria. For the specification: `createStoryUnder`
needs a target that is a tracker project key rather than a Sectile project
(`CreateTaskAs` takes a `ProjectID`), so the creation into a declared key is its
own path on the Jira adapter, recording no local task.
