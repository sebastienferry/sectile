## Round 1 — analysis (2026-09-23)

### Restated request and scope

The Kanban board (`BoardView`) must let the user select several task cards at once and,
from a selection bar, launch the existing `/pickup-issues` batch skill on them, the same way
the Curation, Triage and Sprint Timeline views already do. Out of scope: changing the
`pickup-issues` skill itself, its server-side launch path, cross-project batches, and
(unless question 2 opens it) any other bulk action on the board.

### Files read

- `web/src/components/BoardView.tsx` (stage / status / tracker columns, `handleDropWorkflow`, `handleDropStatus`, `handleDropTrackerColumn`, `displayedTasks`)
- `web/src/components/TaskCard.tsx` (card root: `draggable`, `onDragStart`, `onClick={() => setSelectedTask(task)}`, compact mode, action menus)
- `web/src/context/AppContext.tsx` (`startBatchPickup`, lines 3242-3250)
- `web/src/components/CurationTable.tsx` (checkbox selection, batch bar, "Lancer le lot" button, line 293)

- `web/src/components/SprintTimelineView.tsx` (checkbox selection, batch bar, lines 737-800 and 1509)
- `web/src/components/ListView.tsx` (`selectedTaskIds` Set, select-all / per-group toggles, bulk stage / status / priority / labels / delete bar — no batch pickup)

### Findings

1. **The batch launch already exists; only the board lacks a selection.** `startBatchPickup(taskIds)`
   in `AppContext` refuses a cross-project selection and calls
   `runSkill(firstId, 'pickup_issues', '/pickup-issues <id> <id> …')`. Curation, Triage and
   Sprint Timeline each keep a local checkbox selection and render the same purple
   "Lancer le lot (Git tree + Auto-pilot)" button. The board has none of it.
2. **The existing spec already names the board.** `batch-issue-pickup/spec.md` requires the button
   in "Kanban/Curation, Triage et Sprint Timeline". The Kanban half was never delivered, so this
   ticket completes an existing requirement and needs no new backend capability.
3. **The card's gestures are all taken.** A plain click on the card opens the detail modal, the
   card is `draggable` for stage/status moves, and the footer and menus stop propagation. A
   selection gesture has to coexist with both click-to-open and drag-and-drop.
4. **Order matters.** `pickup-issues` processes tickets "in the exact order provided", so the
   order in which ids are passed is user-visible behaviour.

### Ambiguities (worst first)

1. How a card gets selected (question 1) — decides the `TaskCard` changes.
2. Which actions the board selection bar offers (question 2) — batch pickup only, or ListView's bulk edits too.
3. Batch order (question 3) — click order vs board display order.
4. Which tasks may be selected (question 4) — e.g. finished tasks.
5. What dragging a selected card does (question 5).

### Critical dependencies

- None on the backend: the `pickup_issues` skill, its catalog entry and the launch through
  `runSkill` exist. A launch still needs the local agent connected, as for the other views.
- Board columns come in three modes (workflow stage, status, tracker columns), and the card has a
  compact mode: the selection must work in all of them.

### Reversible technical choices (settled from existing conventions)

- Selection state is local to `BoardView`, like `ListView`/`TriageView`; not persisted, not shared across views.
- Selection is pruned to the currently displayed tasks (as `TriageView` does with `filteredRows`), and cleared on project change, after a successful launch, and with `Escape`.
- The board reuses `startBatchPickup` unchanged, including its cross-project guard, and the same button label, icon and styling as the other views.
- The selection bar shows the count ("N sélectionné(s)") and a clear button, and floats above the board like `ListView`'s bar. UI strings stay in French.

### Product questions for the owner

1. **Selection gesture.** Recommended: a checkbox that appears on card hover/focus (always shown
   once at least one card is selected), plus Ctrl/Cmd+click as a shortcut; a plain click still
   opens the detail. Alternatives: Ctrl/Cmd+click only (no visible affordance), or a "selection
   mode" toggle in the board header.
2. **Actions in the board selection bar.** Recommended: batch pickup and clear only, as the ticket
   asks. Alternative: also bring ListView's bulk stage / priority / labels actions to the board.
3. **Batch order.** Recommended: board display order (columns left to right, then top to bottom
   within a column), consistent with the other views which pass their row order. Alternative:
   the order in which the user clicked the cards.
4. **Selectable tasks.** Recommended: finished tasks cannot be selected; tasks with an active run
   stay selectable (`pickup-issues` reuses existing artifacts). Alternative: everything selectable.
5. **Dragging a selected card.** Recommended: moves only that card, as today; multi-card drag is
   out of scope. Alternative: dragging a selected card moves the whole selection.

Expected answerer: the ticket owner (@sebastienferry).

## Round 2 - answers from the owner (2026-09-23)

Answered in session: the recommendations are accepted for questions 1, 2, 3 and 5; question 4 is
answered differently.

### Settled decisions

1. **Selection gesture.** A checkbox appears on card hover/focus and stays visible on every
   selectable card once at least one card is selected; Ctrl/Cmd+click toggles a card as a shortcut.
   A plain click still opens the detail modal.
2. **Selection bar actions.** Batch pickup ("Lancer le lot (Git tree + Auto-pilot)") and clear only.
   No bulk stage / priority / label actions on the board.
3. **Batch order.** Board display order: columns left to right, then top to bottom within a column.
4. **Selectable tasks.** Only tasks whose workflow stage is `new` or `clarified` can be selected.
   Every other card shows no checkbox and ignores Ctrl/Cmd+click.
5. **Dragging a selected card.** Moves only that card, as today. Multi-card drag is out of scope.

### Reversed assumption

- Round 1 recommended "everything except finished tasks is selectable". Replaced by the stricter
  rule in decision 4: `specified`, `implemented`, `reviewed` and `finished` cards are not selectable.

### Consequences and assumptions

- The stage is read with `resolveTaskStage(task, project)`, so the rule is the same whichever
  column mode the board shows (workflow stage, status or tracker columns).
- A selected card that leaves `new`/`clarified` (a stage moves it on, a drag, a sync) drops out of
  the selection, the same way pruning to the displayed tasks works.
- Having an active run is not an extra exclusion: a `new` or `clarified` card with a run in
  progress stays selectable. This was not asked again and can be revisited in specification.
- No new ambiguity or dependency surfaced. No open product question remains.
