# Clarification #393 - A launcher-owned run reverts to running after finish_run reported it completed

- Ticket: https://github.com/sebastienferry/sectile/issues/393
- Branch: `feat/393`
- Report: `docs/clarifications/393.md` (committed on `feat/393`)

## Round 1 - initial analysis (2026-09-29)

### Request

A run the board launched on the local agent, adopted by the skill session
through `start_run(runId)` and closed with `finish_run(completed)`, was later
shown as `running` again with the summary "Execution running on agent". The
ticket asks that a run in a final state never goes back to `running`, and that
`finish_run` never answers `completed` and then loses that outcome.

Out of scope: runs that were never finished and stay silent or orphaned
(#318, #319, #307), the inactivity limit, and the way a run's outcome hands the
workflow back to the board.

### Code read

- `internal/db/remoterun.go`: `startRemoteRun` and `adoptRun` (adoption of a
  launcher runId), `finishRemoteRun` (closes only a `running` or `queued` row,
  or a disconnect-canceled one for an identified caller),
  `SyncRemoteRunStatusFor` (agent reports).
- `internal/handlers/handlers.go`: `ApplyAgentRunningTasksFor` builds the
  summary `fmt.Sprintf("Execution %s on agent", t.Status)`. This is the exact
  text seen on the reopened runs, so the reopening came from this path, which
  sends every run the agent still holds as `queued` or `running` to
  `SyncRemoteRunStatusFor`.
- `internal/agent/agent.go` (`handlePullTasks`): the agent reports a run as
  long as its process has not exited. An interactive session that called
  `finish_run` keeps its console open, so the agent keeps reporting it as
  `running` after the server closed it.
- `internal/agent/agent_desktop.go` (`finishDesktopRun`): when the process
  finally exits, the agent reports the end through the MCP `finish_run`, which
  is refused with "already finished with another status" if the session already
  closed the run differently, and is a no-op if the status is the same.
- `internal/db/db.go` (`closeLaunch`), `internal/db/instances.go` (restart
  reclaim), `internal/handlers/remote_run.go`: the other writes to a run's
  status. None of them moves a terminal row back to `running`.
- `internal/db/headless_test.go` (around line 332): the #407 test that a late
  agent `running` does not reopen a `failed` run.

### Finding: the root cause is already fixed on `main`

`SyncRemoteRunStatusFor` updates a row to `running` or `queued` only
`WHERE ... status NOT IN ('completed', 'failed', 'canceled')`. That guard was
added by #407 (PR #433, merged 2026-09-24 19:21Z, released in 0.3.0). Before
it, the same statement had no status condition: every agent report of a run
still open on the agent rewrote the row to `running`, cleared `completed_at`
and replaced the summary. Both occurrences in the ticket predate the merge
(SFE-361 on 2026-09-23, #426 at 14:18Z on 2026-09-24), which matches the lead
in the ticket's comment. The "insert not covered by `ON CONFLICT (id) DO
NOTHING`" candidate does not apply: the row exists, so the insert branch is
never taken.

`finish_run` itself was never lying: it did close the run. A later agent report
reopened it.

### Gaps left on `main`

1. **The ticket's acceptance test does not exist.** The #407 test forces the
   run to `failed` with raw SQL on a run the agent created by reporting it. No
   test goes through the ticket's actual sequence: a launcher run created with
   `StartAgentRun`, adopted with a runId, closed with `FinishRemoteRunAs`, then
   reported `running` (and `queued`) by the agent through
   `ApplyAgentRunningTasksFor`.
2. **A later observation may not be covered by the guard.** On 2026-09-25
   (#474, after #407 was merged), a server restart showed an earlier finished
   clarify run of the same task (`5d3e048c`, finished at 10:23) as `running`
   again, with a fresh `createdAt`. A fresh `createdAt` does not match the
   update path the guard covers. It may come from a server still running a
   pre-#407 build, or from another path. This has not been reproduced.
3. **The two stale runs** `e07e72c2-dbaf-423b-9e83-051a97372164` (SFE-361) and
   `b25f6ca9-941a-4dd5-b2b6-e52ebf3065d6` (#426) could not be checked from this
   session: both tasks are finished, and `get_task` no longer returns their
   activities. The live server does not use the checkout's `tasks.db`, so their
   current state is unknown here.
4. **The agent still believes the run is live.** After `finish_run`, the agent
   keeps the run in its queue (and in the desktop list) until the console
   process exits, and keeps reporting it. The server now ignores those reports,
   but the agent's slot and the desktop's view stay "running".

### Ambiguities (worst first)

1. What #393 still has to deliver, given that the reopening path is already
   closed: a regression test only, or also an investigation of the 2026-09-25
   restart observation (gap 2). The two readings lead to different work: a
   test file only, or a reproduction of a server restart with a finished
   launcher run, and possibly a fix in the restart or reconnection path.
2. Whether the agent-side view (gap 4) is part of this bug. The ticket's
   expected behaviour is about the server's record. Making `finish_run` tell
   the agent that the run ended changes the agent protocol and what the
   desktop shows while the console is still open.
3. How the second acceptance criterion ("the run `e07e72c2` can be closed and
   stays closed") is met: by code, or by a one-time check and a manual closure
   on the live server.

### Dependencies

- The regression test runs on SQLite and on PostgreSQL. The PostgreSQL run
  needs `SECTILE_TEST_POSTGRES_DSN` on a throwaway database, never the dev one.
- Checking or closing the two stale runs needs access to the live server's
  database or an admin session on it. It is data work, not a migration.
- Reproducing gap 2 needs a branch server on a copy of the database, started
  without the tracker token, so that nothing reaches Jira or GitHub.

### Technical choices settled here (reversible)

- **Where the test lives.** A DB-level test in `internal/db` that follows the
  ticket's sequence (`StartAgentRun`, adoption through `StartRemoteRunBy` with
  the runId, `FinishRemoteRunAs(completed)`, then `SyncRemoteRunStatusFor`
  with `running` and with `queued`). It asserts that the status, `completed_at`
  and summary are unchanged. It also asserts that a second `finish_run` with the
  same status is still accepted, and that one with another status is refused.
  A handler-level test drives `ApplyAgentRunningTasksFor` with the same run, so
  the path that actually produced "Execution running on agent" is covered.
  Both run on the shared SQLite/PostgreSQL harness.
- **No production change is planned for gap 1.** The guard is already in
  place, so the test is expected to pass on `main` as it is. The test is still
  checked against the pre-#407 statement, by reverting the guard locally, to
  prove it would have caught the bug.
- **Changelog.** If #393 ships only tests, it adds no line: the fix shipped in
  0.3.0 with #407, and a `Fixed` line under `[Unreleased]` would credit a
  release that changes nothing. If a new code path is fixed (question 1), that
  fix gets its own `Fixed` line.

### Open product questions

1. **Scope of #393 now that #407 fixed the reopening path.**
   - A. Regression test only (gap 1), then close.
   - B. Regression test, plus a bounded reproduction of the 2026-09-25 restart
     observation (gap 2). If it reproduces, fix it in #393. If it does not,
     record the result and close.
   - Recommended: **B**. The only evidence that the bug still exists after
     #407 is gap 2. Closing without checking it would repeat the situation of
     the first occurrence.
2. **Agent-side view after `finish_run` (gap 4).**
   - A. Out of scope. The server's record is correct. The agent keeps the run
     until its console exits, which is when the process really ends.
   - B. In scope. `finish_run` also tells the owning agent that the run ended,
     so the desktop and the agent's slot follow the server.
   - Recommended: **A**, with a separate ticket if the desktop showing a
     finished run as live while its console is open is a problem in practice.
3. **Second acceptance criterion: the stale run `e07e72c2` on SFE-361 (and
   `b25f6ca9` on #426).**
   - A. Replace it with a one-time check on the live server. If either run is
     still `running`, an admin closes it from the activities view and checks
     that it stays closed after the next agent reconnection. No code.
   - B. Keep it as a code criterion, for example with a startup repair that
     closes launcher runs reopened before 0.3.0.
   - Recommended: **A**. Those rows are two known artefacts of a bug already
     fixed, and a repair migration would be permanent code for a one-time
     cleanup.
