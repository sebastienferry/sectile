# Clarification: choose how board columns are sorted

## Round 1 - 2026-09-25

Every board column is sorted by priority only today. The request is to let the
viewer choose the sort order of the cards inside each column: by parent epic,
by priority, by key and possibly other criteria, so that, among other things,
the tickets of one epic can be kept together. Out of scope: the column set and
the Workflow / Status grouping, drag and drop (it changes the stage and never
reorders within a column), the Backlog's own column-header sorting, and any
server-side or tracker change.

### Evidence

Read `web/src/components/BoardView.tsx`, `web/src/components/BoardGroupingToggle.tsx`,
`web/src/components/ListView.tsx`, `web/src/components/EpicMarker.tsx`,
`web/src/lib/boardGrouping.ts`, `web/src/lib/boardDisplayMode.ts`,
`web/src/context/AppContext.tsx` (board preferences), `web/src/types/index.ts`
(`Task`) and `docs/clarifications/388.md`.

What the code already establishes:

- `BoardView` sorts with a local `byPriorityDesc` in three places: the
  workflow columns, the tracker-status columns and the "unassigned" column.
  The sort is not stable on anything but priority: ties keep the order of the
  `tasks` array.
- The ticket description was written before the owner's comment of
  2026-09-25 ("actually add option to select the sort algo: parent, priority,
  id, ..."). That comment widens the request from a Priority / Epic switch to a
  selectable sort criterion.
- `ListView` (Backlog) already sorts by key, title, status, priority, due
  date and creation date through clickable table headers, with a direction
  toggle. Its key comparator is `localeCompare(..., { numeric: true })`, which
  orders `#9` before `#402` and `PROJ-9` before `PROJ-12`.
- Board preferences (`boardGrouping`, `boardCardDisplayMode`) live in
  `localStorage` per viewer; `boardDisplayMode.ts` is the pattern with an
  injectable storage for tests.
- The epic is carried on the task as `parentKey` / `parentTitle` /
  `parentType` (a Jira epic, or a Sectile macro such as `M-7`). #388 already
  paints an epic colour bar on the card (`EpicBar`), opt-in per project.
- `Task` also carries `dueDate`, `createdAt` / `updatedAt` (import dates) and
  `trackerCreatedAt` / `trackerUpdatedAt` (tracker dates).

### Ambiguities, worst first

1. **Which criteria are offered.** "parent, priority, id, ..." leaves the list
   open. Each extra criterion is a comparator, a label in both languages and a
   test; "..." could mean due date, last update or creation date.
2. **Whether the viewer also picks a direction.** A fixed natural direction per
   criterion and an ascending / descending toggle (like the Backlog) lead to a
   different control and a different stored preference.
3. **Which way "id" sorts.** Oldest first (ascending key) and newest first
   read differently on a board; only matters if there is no direction toggle.
4. **Whether the Epic mode shows group headers.** Contiguous cards only (the
   #388 colour bar already marks the groups when enabled) versus a header per
   epic inside each column, which changes the column rendering and the
   keyboard / selection order.

### Dependencies

None outside the web front end. No migration, no API, no tracker field:
`priority`, `key`, `parentKey` and the dates are already on every task.
#388 is related (colour bar) but not required.

### Reversible technical choices, settled here

- **One comparator module.** The criteria move to a pure `web/src/lib/boardSort.ts`
  (comparators + load / save of the preference, same shape as
  `boardDisplayMode.ts`), unit-tested with `node --test`, and `BoardView`
  replaces its three `byPriorityDesc` calls with it.
- **Deterministic ties.** Every criterion falls back to priority (descending)
  then to the key (numeric-aware `localeCompare`, as in the Backlog), so two
  renders of the same data never swap cards.
- **Epic mode as stated in the ticket.** Groups by `parentKey`; groups ordered
  by their highest priority, then by parent key; cards by priority inside a
  group; tickets without a parent last.
- **Persistence.** Per viewer in `localStorage` under `sectile_board_sort`,
  unknown or missing values falling back to the default. Not per project.
- **Placement.** A compact select in the board toolbar, next to the Workflow /
  Status toggle, labelled in French like the rest of the interface (and in
  English through the existing `t` dictionary).
- **Default.** Priority, so nothing changes for a viewer who never touches it.
- **Selection order.** The batch selection is ordered from the on-screen
  lists (`workflowColumnTasks` / `statusColumnTasks`), so it follows the
  chosen sort without further work.

### Product questions for the owner

1. **Criteria offered.** Recommended: Priority (default), Epic, Key, Last
   updated (tracker update date). Alternatives: only Priority / Epic / Key; or
   add Due date and Created too.
2. **Direction.** Recommended: no direction toggle, a fixed natural order per
   criterion (priority highest first, key oldest first, last updated most
   recent first). Alternative: an ascending / descending toggle like the
   Backlog.
3. **Epic group headers.** Recommended: no header, cards of one epic are only
   kept contiguous. Alternative: a small header with the epic key and title
   above each group in a column.
4. **Backlog.** Recommended: board only; the Backlog keeps its header sorting.
   Alternative: the same choice drives the Backlog's grouped view.
