## Request restated

Since #307 a silent MCP session never loses its runs, so a client that really
died without closing its connection leaves its run `running` indefinitely: the
four-hour bound only appends a sentence. The ticket asks for a written decision
on what happens to such a run, and the code that decision calls for.

Out of scope: agent-dispatched runs (their supervisor reports the real exit and
ADR 0006 covers them), the restart sweep of ADR 0007, and the #318 waiting
signal.

## Settled decisions (owner, round 2)

- **S1 - Two bounds.** `SECTILE_MCP_SESSION_TIMEOUT` (default 4h) still only adds
  a note. A new `SECTILE_MCP_SESSION_ABANDON_AFTER` (default **8h**) closes the
  session through `SessionRegistry.Close`, which cancels its runs with
  `RunDisconnectNote`, so the owner can still undo it through the #307 rewrite.
- **S2 - A "silent" state on the board**, read from `RunSilencePrefix` in the
  run's summary. No migration.
- **S3 - A board "Close" button for client-created runs**, owner or admin only,
  which writes the disconnect note.
- **S4 - The Activities-view cancel of a `remote_run`** goes through
  `FinishRemoteRunAs`, with the owner check, the chain hand-back and the release
  of the run from its MCP session.
- **S5 - A second amendment to ADR 0007.**
- **Scope:** runs whose action is `RunActionClient` only.

## Reversed assumption

The recommended abandon bound was 24h; the owner chose **8h**.

## Technical decisions (reversible, settled here)

- **T1 - The abandon bound is clamped to the silence bound**: a value at or
  below the silence bound would close a session before anyone was told it was
  quiet, so the abandon bound is raised to the silence bound in that case, and
  an unparseable or non-positive value keeps the default, as the silence bound
  already does.
- **T2 - Closing a session also closes the SDK session**, so a client that comes
  back is told its session is gone rather than served under a registry that
  forgot it.
