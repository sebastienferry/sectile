Title: Only seal credentials if user is not connected for 30 minutes

## Round 1 (2026-09-25)

### Restated request and scope

The ticket carries a title and no description. Read against the code, it asks
that a sealed personal tracker credential (ADR 0014) which its owner unlocked
be locked again automatically once that person has not been connected for 30
minutes, instead of staying unlocked until the server restarts or the person
presses "Lock all". While the person stays connected, the credential stays
unlocked and every write they cause keeps working.
Out of scope: the sealing itself (passphrase, Argon2id, AES-GCM binding), the
unsealed credentials (the server key always opens them), the server
credentials of ADR 0028, and sharing an unlocked key between server replicas.

### Verified findings

Files read: `docs/adrs/0014-personal-tracker-credentials-are-sealed.md`,
`docs/adrs/0029-server-tracker-credential-signs-unattended-work-only.md`,
`internal/secrets/secrets.go`, `internal/db/usercredentials.go`
(`unlockedKeys`, `UnlockUserTrackerCredential`, `LockUserTrackerCredential`),
`internal/db/db.go` (`unlocked` field), `internal/handlers/usercredentials.go`
(`unlock`, `lock` routes), `internal/handlers/auth.go` (sign-out),
`internal/db/sessions.go` (`UserForWebSession`, `RevokeWebSession`),
`internal/db/useractivity.go` (`sessionTouchInterval`, `ActiveUserWindow`),
`internal/db/presence.go` (`agent_presence`), `internal/db/instances.go`,
`web/src/lib/session.ts`, `web/src/components/SignInScreen.tsx`,
`web/src/context/AppContext.tsx` (`lockAllUserCredentials`).

- **An unlocked key lives until the process ends.** `unlockedKeys` is a plain
  map in `DB`, filled by `UnlockUserTrackerCredential` (sign-in screen or
  profile) and emptied only by the `lock` route, a re-store, a delete, or a
  restart. Nothing expires it.
- **Sign-out does not lock.** `RevokeWebSession` only revokes the cookie; the
  derived key stays in memory, so a person who signed out hours ago still has
  their sealed token usable by anything acting as them.
- **"Connected" already has a cluster-wide measure for the browser.**
  `web_sessions.last_seen_at` is written at most once a minute by
  `UserForWebSession`, and an open tab keeps it fresh through the event stream
  (`ActiveUserWindow` = 5 min relies on that). It lives in the database, so
  every replica reads the same value.
- **The desktop and agents are a second kind of presence.** A local agent holds
  a WebSocket recorded in `agent_presence` (`disconnected_at IS NULL` while
  up), keyed by user. An MCP client authenticates with the workstation API key,
  and no last-use time is recorded for that key today.
- **Writes Sectile makes later on a person's behalf need the key** (ADR 0029):
  a queued operation, a stage report, a managed run's transition. Once the key
  is forgotten, they fail loudly with the "unlock it" message, by design.
- **Unlocked keys are per replica.** An unlock reaches the one instance that
  served the request. This is an existing limitation, not introduced here.

### Ambiguities (worst first)

1. **What counts as "connected".** Browser only (`web_sessions.last_seen_at`),
   or browser *or* a connected local agent (`agent_presence`). Browser only
   locks the credential of a person who works from the desktop app and a
   running agent while no tab is open, and a long agent run then fails its
   stage transition (ADR 0029). Different code: a second presence source.
2. **Whether explicit sign-out locks at once.** Today it does not. Locking on
   the sign-out of the person's last open session is a separate trigger.
3. **Whether 30 minutes is fixed or a setting.** A constant versus a new
   server or personal setting (and its UI).

### Critical dependencies

- No migration needed if presence is read from `web_sessions` and
  `agent_presence`, which already exist.
- ADR 0014 states the derived key is "held in memory for as long as the server
  runs". The change amends it; an ADR records the new lifetime.
- Multi-replica: each instance must expire its own map from the shared
  presence data, never from an in-memory `lastSeen`.

### Technical choices resolved from the code

- A periodic sweep on each instance (once a minute, the precision of
  `sessionTouchInterval`) forgets the keys of users whose last presence is
  older than 30 minutes. It reads presence from the database, so all replicas
  agree.
- The unlock time counts as presence, so a key unlocked just now is never
  swept because an old session row is stale.
- Only sealed credentials are affected; nothing changes for unsealed ones.
- The profile tab already shows `unlocked: false` and offers "Unlock all"; the
  sign-in screen already asks for the passphrase. No new unlock surface.
- `CHANGELOG.md` gets a `Changed` line (the behaviour is user-visible).

### Product questions for the owner

1. **Presence sources.** Recommended: the person is connected while a browser
   session of theirs was seen **or** one of their local agents is connected.
   Alternative: browser only.
2. **Sign-out.** Recommended: explicit sign-out of the person's last open
   browser session, with no agent of theirs connected, locks immediately.
   Alternative: sign-out changes nothing, only the 30-minute rule applies.
3. **Delay.** Recommended: a fixed 30-minute constant, no setting.
   Alternative: a server setting for admins.
