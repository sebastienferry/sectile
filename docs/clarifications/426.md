### Restatement

`realign-macro` skill, one worktree per macro, sprint management, and close
the four gaps #423 documents in place (`TargetProjectID` not consumed, one

### Findings from the code

- **Sprints are not "local" in taskativ.** `sprints.go` creates, updates and
  deletes sprints *on the tracker* (Jira Agile sprints, GitLab iterations),
  synchronously, and only mirrors them locally. Its header says why: a local
  sprint could never receive a ticket, since the Agile API only moves a ticket
  to a sprint id it knows. The ticket's "local sprint management" wording
  therefore reads two ways (see Q2). Sectile today only reads sprints
  (`ListSprints`) and assigns tickets to them (`SetSprint`).
- **GitHub has no sprints.** This repository's own project is on GitHub, where
  milestones are already used as macros. Sprint management can only apply to
  Jira and GitLab projects.
- **`realign-macro` writes in the macro's worktree, on its branch.** In
  taskativ the worktree-per-macro feature is what prepares that branch, "so no
  skill switches branch". The two features are coupled: realignment without a
  prepared macro branch has nowhere safe to write.
- **The worktree-per-macro feature targets the specifications repository.**
  Sectile has one `RepoPath` per project (`macroSpecRepoPath` documents it).
  A macro worktree created in the code repository is the wrong place for a
  team whose specifications live elsewhere, so the "specifications repository"
  setting is a prerequisite of the macro worktree, not an independent gap.
- **Sectile has no `specify-macro`.** Its only macro skill is `refine-macro`,
  which proposes todos and tickets but writes no specification. `realign-macro`
  assumes a specification already exists in the repository (written by hand,
  by taskativ, or by a future skill); `FindMacroSpecDir` already finds it.
- **The `scenarios` source needs the EPIC template field map**, which Sectile
  lacks entirely (read, display, edit, concurrent-edit guard). That is a
  feature in its own right, not a reader.
- **`TargetProjectID` crosses trackers.** Creating a story in another project
  means another tracker, possibly another kind: a GitHub milestone is per
  repository and cannot parent an issue in another repository, whereas a Jira
  epic can parent a story from another project of the same instance.

### Ambiguities (worst first)

1. **Delivery shape.** Eight items of very different size in one ticket: one
   PR or several tickets. Changes every downstream stage (see Q1).
2. **Sprint management target.** Tracker writes (as taskativ) versus a local
   sprint model; and which operations (create, rename, dates, close, delete).
   (Q2)
3. **Cross-project story creation.** What happens when the target project
   cannot carry the macro as parent. (Q3)
4. **`scenarios` source.** In scope with the field map, or deferred. (Q4)

### Critical dependencies

- Specifications repository setting → worktree per macro → `realign-macro`
  (writes on the macro branch). This order is forced.
- Sprint writes need Jira Agile write scopes and GitLab iteration APIs;
  tracker writes must go through the tracker operation queue except where
  taskativ deliberately calls synchronously (sprint creation).
- New project settings are new columns: numbered migrations only, never the
  frozen baseline (`internal/db/migrations.go`).
- `scenarios` source → EPIC template field map (not present).

### Reversible technical choices, resolved from conventions

- **`realign-macro` is a macro-scoped skill** registered next to
  `refine-macro` (`SkillDirNames`, `internal/skills/catalog.go`, golden files
  per SDD framework), launched from the macro panel like `refine-macro`.
  Its body ports taskativ's `realignMacroFrameworkBody` (Spec Kit and
  OpenSpec variants), with the surgical rules: add, rename, mark orphans as to
  be removed, never touch an existing entry's body, never delete.
- **Specifications repository** is a second, optional path on the project,
  falling back to `RepoPath` when empty; `macroSpecRepoPath` is its single
  reader, so `FindMacroSpecDir` and the slicing inherit it.
- **Macro worktree** follows the task worktree conventions
  (`.tasks/worktrees/<macro key>`, branch named after the macro key, based on
  an up-to-date default branch), gated on `UseWorktrees`; `findMacroBranch`
  already matches a branch by macro key prefix.
- **Additional roadmap projects** is a list of extra key prefixes on the
  project, read-only: they only let a story key attach to a slicing line,
  never trigger a write (taskativ invariant "a declared roadmap project is
  read, never written").
- UI strings stay in French; code, comments and docs in English.

### Product questions

1. **Q1 - Delivery shape.** Recommended: split into child tickets under M-7;
   #426 keeps the coupled chain *specifications repository → macro worktree →
   `realign-macro`*; separate tickets for sprint management, `TargetProjectID`,
   additional key prefixes, and `scenarios` + field map.
2. **Q2 - Sprint management.** Recommended: tracker writes as in taskativ
   (Jira sprints, GitLab iterations; nothing on GitHub), operations create,
   rename, dates, close.
3. **Q3 - Cross-project story creation.** Recommended: allow only target
   projects on the same tracker instance as the macro, where the parent link
   holds; refuse others with an explicit message.
4. **Q4 - `scenarios` source.** Recommended: defer, together with the EPIC
   template field map, to its own ticket.
