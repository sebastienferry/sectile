# Clarification #745 - Claude settings and preset rules

- Ticket: [#745](https://github.com/sebastienferry/sectile/issues/745)
- Task ID: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-745`
- Report: `docs/clarifications/745.md`

## Round 1 - initial report (2026-10-06)

### Request

The ticket renames the Desktop "Sandbox" settings category, at workstation and
project level, to "Claude settings". It also offers ready-made presets that
fill the workstation lists in one click: allow rules per language or
toolchain, deny rules for dangerous actions (such as `terraform apply`), and
the standard network domains. Out of scope: other engines than Claude Code,
custom command templates (they never receive the generated settings), the
server, the owner's own `~/.claude/settings.json`, the storage keys and the
endpoint, and the permission mode of headless runs.

### What the code does today

Files read:

- `desktop/src/main.js`: `SETTINGS_CATEGORIES` and
  `PROJECT_SETTINGS_CATEGORIES` both hold `{id:'Sandbox',label:'Sandbox'}`;
  `workstationSandboxPanel` with its "Save Sandbox settings" button, its
  "Sandbox settings saved" notice and its stopped-agent notice.
- `desktop/src/sandbox-settings.mjs`: the panel: state, allowed domains,
  extra writable paths, allow and deny lists, the "both lists" warning, the
  "Global" tag, "Move to global", and the scope and coverage texts that say
  "workstation Sandbox settings".
- `internal/agent/agent_conversation_approvals.go`,
  `agent_claude_sandbox.go`, `agent_desktop_sandbox.go`, `agent.go`: the
  activity lines, errors and log lines that name "the project's Sandbox
  settings" or "Invalid Sandbox settings".
- `docs/CAPABILITIES.md` (two lines name the **Sandbox** category),
  `docs/adrs/0048-…` and `docs/adrs/0050-…`.
- Tests: `desktop/tests/sandbox-settings.test.mjs`,
  `desktop/tests/sandbox-settings.ui.cjs`, `desktop/tests/settings-version.ui.cjs`.

Facts that shape the presets:

- Headless runs use `--permission-mode bypassPermissions`: allow rules change
  nothing for them (the panel says so), while deny rules still apply. Allow
  presets therefore help conversations and terminal sessions only.
- On Windows the sandbox does not run: the domain and writable-path lists are
  disabled and only the rules apply.
- Lists are merged workstation-then-project, each entry once (ADR 0050). A
  preset applied at workstation level reaches every covered project.

### Ambiguities, worst first

1. **What applying a preset stores.** (a) a copy of its entries in the lists,
   each then an ordinary entry; (b) a reference to the preset, resolved at
   launch, so a Sectile update changes the rules. These need different
   storage, merge and UI code. See question 1.
2. **What a preset covers.** Allow rules only, or allow rules plus the
   domains and writable paths the same toolchain needs (a sandboxed
   `go test` fails without a writable `~/.cache/go-build` and access to
   `proxy.golang.org`). See question 2.
3. **When a preset is applied.** Opt-in only, or suggested or seeded on a
   fresh install. See question 3.
4. **Where presets are offered.** Workstation only, or at project level too.
   See question 4.
5. **What "dangerous" includes.** `rm -rf` and `git reset --hard` are routine
   inside a task worktree. See question 5.

### Critical dependencies

- **Claude Code rule syntax.** A pattern with a wildcard in the middle
  (`Bash(gcloud * delete …)`) and the legacy `:*` suffix must be checked
  against the installed Claude Code version, as ADR 0048 did for the keys.
  Otherwise a deny rule may silently match nothing.
- No migration, no server change, no new endpoint: the presets write the
  existing workstation lists through `/desktop/workstation/sandbox`.

### Reversible choices settled from the code

- **Label-only rename.** The category `id` stays `'Sandbox'`, and so do
  `claudeSandbox`, `claudeSandboxProjects`, `/desktop/workstation/sandbox` and
  the generated file. The rename covers every user-visible string: both
  category labels, the save button, the notices, the "Global" tooltip, "Move
  to global", the scope and coverage texts, the whitelist aria label, the
  agent's activity lines and errors that say "Sandbox settings", and
  `docs/CAPABILITIES.md`. The "Claude Code sandbox" state control keeps its
  name. Released `CHANGELOG.md` sections and ADRs are left as written.
- **No broad read commands in the allow presets.** `Bash(cat:*)`,
  `Bash(grep:*)` and `Bash(rg:*)` would let a command read `.env` past the
  `Read(**/.env)` deny rule, and `Bash(find:*)` can `-exec` or `-delete`.
  Claude Code has its own Read, Grep and Glob tools. The Common preset keeps
  the read-only git commands and `ls`.
- **No catch-all package-manager rules.** `Bash(pnpm:*)`, `Bash(yarn:*)` and
  `Bash(uv:*)` also allow `publish`. They become their install, run and test
  subcommands.
- **No `storage.googleapis.com` unless proven necessary.** It reaches any GCS
  bucket. It enters the domain list only if the specification shows a Go
  module download needs it.
- **Presets live in code.** They sit in a pure desktop module, versioned with
  Sectile and covered by `node --test`, in the same style as
  `sandbox-settings.mjs`.
- **Windows.** Applying a preset there adds its rules only, and the panel
  says that its domains and paths do not apply.
- **The guardrail notice.** The deny preset says it matches command prefixes
  and is not a security boundary.

### Open product questions

1. **Copy or reference?** Recommended: **copy**. Applying a preset adds its
   missing entries to the workstation lists, each visible and removable like
   any other, as ADR 0048 wants. A preset shows "Applied" while all its
   entries are present. Removing it takes out its entries that no other
   applied preset holds. A Sectile update never changes a list the owner
   already has.
2. **Toolchain bundles?** Recommended: **yes**. A language preset (Go,
   Node/TypeScript, Python, Java/Kotlin, Rust, .NET, Infrastructure read-only)
   fills the allow rules, the domains and the writable cache paths of that
   toolchain (for example `~/.cache/go-build` and `~/go/pkg/mod` for Go,
   `~/.npm` for Node, `~/.m2` for Maven). It sits beside a "Common" preset
   (git read-only, GitHub and GitLab domains) and the "Dangerous actions"
   deny preset.
3. **Seeded or opt-in?** Recommended: **opt-in only, never applied on
   upgrade**. While the workstation lists are empty, the category shows one
   "Apply recommended" action: Common plus Dangerous actions.
4. **Project level too?** Recommended: **workstation only**. A project keeps
   adding its own entries by hand. Through the whitelist, the workstation
   values already reach just the projects that want them.
5. **`rm -rf` and `git reset --hard` in the deny preset?** Recommended:
   **leave them out**. Agents use them routinely on build outputs and inside
   the task worktree, and with the sandbox on, writes are already confined to
   the writable paths. Keep `sudo`, the force pushes, the publishes and the
   infrastructure and cloud mutations.
