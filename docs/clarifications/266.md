# #266 — In the UI when clicking outside of a popup, it should close

Tracker: https://github.com/sebastienferry/sectile/issues/266

## Round 1 — clarification (2026-09-19)

### Restated request

When a popup is open in the UI, a click outside its bounds must dismiss it, the same way
`Escape` already does. Out of scope: any change to what closing *does* (save vs. discard),
keyboard/focus handling, the drag-and-drop board, and the Go backend.

### Ambiguities, worst first

1. **What counts as a "popup".** Anchored menus (`LookupField`, `TaskFilters`, `Sidebar`,
   `TaskCard`, `ListView`, `McpSessions`) already close on an outside `mousedown`. Read
   narrowly the ticket is already done; read broadly it is the modal dialogs. Treated as:
   **the modal dialogs are the subject.**
2. **Outside click on a modal holding unsaved input** (ProjectModal, QuickAddModal,
   CloneTaskModal, ProfileModal). A backdrop click is easy to do by accident, and `Escape`
   already discards silently — is the cheap gesture allowed to be as destructive as the
   deliberate one? See Q1.
3. **Layering.** `TrackerSetup` (`z-60`) opens over `ProjectModal` (`z-50`), and the expanded
   spec reader (`z-60`) over `TaskDetailModal` (`z-50`). One click must close exactly one
   layer. Resolved by scoping the handler to each dialog's own backdrop element.
4. **Gesture and drag false positives.** A document-level `mousedown` listener would fire
   during @dnd-kit drags and on text selections released outside the dialog. Resolved by the
   press-target guard below.
5. **Six copies of the same outside-click effect** in the components that already have one.
   Reversible; resolved below.

### Critical dependencies

None. No backend, API, migration or other team involved — this is UI-local.

### Questions and answers

**Q1 — Should an outside click discard unsaved form input, exactly as `Escape` does today?**
→ **Yes, identical to `Escape`.** The outside click calls the same `onClose`/`handleClose`
the dialog already uses, with no confirmation prompt. `TaskDetailModal.handleClose` already
autosaves its edits on close, so the big one loses nothing; the smaller creation dialogs are
short forms whose `Escape` path is already lossy, and a confirm step on only those would make
the two gestures behave differently.

**Q2 — Is the Electron desktop UI in scope?**
→ **No, web UI only.** The desktop row-action menu already dismisses on outside `pointerdown`
(`desktop/src/main.js`); its only other popup is a native `<dialog>.showModal()`, where light
dismiss is a separate, unrelated change.

**Q3 — Should `SprintTimelineView`'s close-sprint dialog and `TrackerSetup` also gain
`Escape`, since they are the two dialogs with no dismissal at all?**
→ **Yes.** Both are dismissible dialogs with a visible close button; leaving them
keyboard-inert while every sibling closes on both gestures is the same defect.

### Settled scope and assumptions

- **Mechanism:** a press-and-release guard on each dialog's own backdrop element — close only
  when both the `mousedown` and the `click` landed on the backdrop itself. Not a
  document-level listener: this keeps one click to one layer (ambiguity 3), leaves @dnd-kit
  drags untouched, and extends the idiom `AdminModal`/`ChangelogModal`/`ProfileModal`/
  `ProjectModal` already use.
- **Drag safety:** a press started inside the dialog and released on the backdrop must not
  close it. The press-target check covers it — the `click` event would otherwise fire on the
  common ancestor, which is the backdrop.
- **Close action:** reuse each dialog's existing close path verbatim, so `TaskDetailModal`'s
  autosave-on-close is preserved and nothing else changes.
- **Anchored menus keep `mousedown` + `ref.contains`**; the duplicated effect is extracted
  into a `useClickOutside` hook and the verbatim call sites migrate to it. No behaviour change.
- **Accessibility/aria untouched**; no new dependency.
- **Not doing:** confirmation prompts, focus-trap work, `Escape` beyond Q3, the desktop
  `<dialog>`, and `SignInScreen` (not dismissible by design).
