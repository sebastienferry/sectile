# Clarification — #577: AGENTS.md project-context block

## Round 1 — 2026-09-28

### Request restated

Sectile should stop adding its project-context block to `AGENTS.md` in repositories and task worktrees. This ticket does not change project context delivered through the authenticated MCP connection or the user's other instructions in `AGENTS.md`.

### Evidence and settled technical facts

- The provider-scoped setup migration already removed the writer for the old `taskflow:project-context` block. `Scaffold` now installs provider configuration at user level and calls `retireCheckout` to clean earlier checkout artifacts.
- `retireContextBlock` recognizes only `<!-- taskflow:project-context:start -->` and `<!-- taskflow:project-context:end -->`; it removes the enclosed block and keeps instructions around it. A block-only file is deleted.
- This repository's tracked `AGENTS.md` begins with `sectile:project-context` markers, so the current retirement function leaves that block in place. The block contains repository identity and workflow guidance that the project context MCP tool and dispatch context already provide.
- The active `agent-provider-setup` specification says dispatch must not create or modify the managed project-context block in a checkout. Its historical migration proposal says the block should stop being generated and previously managed copies should be retired.
- The existing cleanup test covers old `taskflow` markers and preserving surrounding personal text; it does not cover `sectile` markers.

### Ambiguity, highest impact first

1. Does “stop adding” cover cleanup of existing `sectile:project-context` blocks, including the tracked block in this repository, or only prevention of future insertion? These readings change whether implementation must update `retireContextBlock`, its tests, and the tracked `AGENTS.md`.

### Recommended product decision

Remove existing blocks with either managed marker spelling during normal scaffold, and remove this repository's tracked managed block as part of the change. Preserve all instructions outside a complete managed block. This fulfills the earlier provider-setup decision and prevents a stale tracked block from continuing to appear in every worktree.

### Technical choices resolved by convention

- Retain the existing MCP and dispatch-context source for project identity; no new repository file or migration is needed.
- Preserve personal `AGENTS.md` content and the existing error on incomplete managed markers. Keep cleanup scoped to the marker-delimited block rather than matching ordinary prose.
- Leave historical references in archived designs and prior clarification reports as history.

### Dependencies

No service, schema, external API, or third-party limit is involved. The work depends on the existing `internal/agentconfig` scaffold path and its tests. The tracked `AGENTS.md` must remain usable after its managed block is removed.
