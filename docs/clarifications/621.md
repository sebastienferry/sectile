# Clarification #621 - Allow the user to choose the format of the branch name

Ticket: https://github.com/sebastienferry/sectile/issues/621 (parent macro M-8 "Core features").
The ticket has a title only: no description, no comments.

## Round 1 - analysis (2026-09-29)

### Request

A project can define the name format of the branch Sectile creates for a task, instead of the
hard-coded `feat/<key slug>` (for example `feat/621`, `feat/auc-1234`); the default stays today's
format, so a project that sets nothing sees no change. Out of scope: renaming branches already
assigned to tasks, projects running without worktrees (the agent then works on the checkout's current
branch and creates none), and, unless the owner decides otherwise (Q3), macro specification branches.

### Code read

- `internal/agent/worktree_paths.go` - `taskWorktreeBranch`: the branch actually created,
  `task.BranchName` when set, else `feat/` + lower-case key slug (`#621` -> `feat/621`).
- `internal/agent/agent_config.go` (~l.235-260), `internal/agent/agent_operations.go`
  (`prepare_workspace`, `workspace_info`), `internal/agent/agent_desktop.go` (~l.1234): callers;
  without worktrees the current checkout branch is used as is.
- `internal/db/db.go` (~l.2200): the branch returned by `prepare_workspace` is persisted in
  `tasks.branch_name`, which then wins over any format on every later stage.
- `internal/db/db.go` `GenerateTaskBranchName` (`<key>-<title slug>`): referenced nowhere.
- `internal/runner/runner.go` (~l.452-463): legacy prompt fallback `<key>-<title[:30]>`, a third,
  divergent format used only for the `{branchName}` prompt placeholder.
- `internal/models/macrobranch.go`: macro branches `<KEY>-<title slug>`, and
  `MacroBranchMatches`, which recognizes a macro branch by its last path segment.
- `internal/models/branch.go` `SanitizeBranchName`; `internal/workspace/git.go` guards against
  `main`/`master`/`HEAD`.
- `internal/models/models.go` `Project`: neighbouring project settings (`PRCreationStage`,
  `SpecArtifacts` with its workstation override in `internal/agent/agent_desktop_settings.go`,
  `PushStageCommits`), edited in `web/src/components/ProjectModal.tsx`.
- `docs/adrs/0017-pull-requests-are-rediscovered-on-sync.md`: PR discovery deliberately does not
  derive branches from the `feat/<number>` convention, so a new format does not break it.

### Ambiguities (worst first)

1. **Where the format lives**: a project setting shared by the whole team, a workstation override
   (like `SpecArtifacts`), or both. It decides the storage, the server/agent protocol and the UI.
2. **How the format is expressed**: a free template with placeholders, or a choice among presets.
   With a template, the placeholder set and the casing of the key matter: Jira/GitLab development
   integrations recognize an issue key in a branch only in upper case (`AUC-1234`), which today's
   lower-cased `feat/auc-1234` defeats; that is the likeliest motivation for the ticket.
3. **Macro branches**: included in the same setting, a separate one, or untouched.
4. **Tasks that already have a branch**: keep it (recommended) or re-derive it.

### Dependencies

- Agent and server are separate binaries: the setting must reach the agent in the project
  configuration it already receives (as `PRCreationStage`/`UseWorktrees` do). An older agent
  ignores the field and keeps `feat/<key>`; acceptable, no migration needed.
- Database: one new nullable column on `projects` (empty = default format); no data migration.
- Git ref rules: a rendered name must pass `git check-ref-format --branch`, which the agent
  already runs before creating the worktree.
- No tracker or third-party limit otherwise.

### Technical choices resolved from the code (reversible)

- T1. One generator, in `internal/models`, used by the agent (`taskWorktreeBranch`) and by the runner
  fallback, so the prompt and the created branch cannot disagree; the unused
  `db.GenerateTaskBranchName` goes away with it.
- T2. The empty setting renders exactly today's `feat/<lower-case key slug>`; existing tests keep
  passing unchanged.
- T3. The format applies only when a task has no `branch_name` yet; an assigned branch is never
  renamed (the worktree is resolved by branch, a rename would orphan it and its PR).
- T4. The format is validated when the project is saved: it must contain a key placeholder (so two
  tasks can never render the same branch), and a sample render must be a valid Git branch that is not
  `main`/`master`/`HEAD`. Invalid formats are refused with a message in the UI's language (French).
- T5. Rendered values are sanitized per placeholder with the existing `SanitizeBranchName` rules;
  the title slug, when used, is lower-case and bounded (about 30 characters, like macro branches).
- T6. The web project settings modal gets the field, with a live example rendered from a sample key;
  the text is French like the rest of the UI. `CHANGELOG.md` gets an `Added` line.
- T7. Skill and docs wording that says "the assigned `feat/<n>` branch" becomes "the assigned
  branch"; skills already read the branch from the task, so no contract change.

### Product questions (with recommendation)

- **Q1. Scope of the setting.** Recommended: **a project setting only** (one convention per repository,
  shared by the team); a workstation override can come later if someone needs it.
- **Q2. Form and placeholders.** Recommended: **a template** with `{key}` (tracker key as displayed,
  `#` dropped, case preserved: `621`, `AUC-1234`), `{key_lower}` (`621`, `auc-1234`) and `{title}` (title
  slug), plus presets in the UI (`feat/{key_lower}` default, `{key}`, `feat/{key}-{title}`). Alternative:
  presets only, no free text.
- **Q3. Macro branches.** Recommended: **out of scope**; they keep `<KEY>-<title>` (their detection by
  last segment relies on it). A follow-up ticket if needed.
- **Q4. Existing branches.** Recommended: **never renamed** (T3). Confirm.

## Round 2 - answers from the owner (2026-09-29)

The owner answered interactively and confirmed that the clarification is satisfactory.

### Settled decisions

- **Q1. Scope**: a project setting only, shared by the team and edited in the project settings
  modal. No workstation override in this ticket.
- **Q2. Form**: a free template with the placeholders `{key}` (tracker key, `#` dropped, case
  preserved: `621`, `AUC-1234`), `{key_lower}` (`621`, `auc-1234`) and `{title}` (lower-case title
  slug), plus presets in the UI: `feat/{key_lower}` (default, today's behaviour), `{key}`,
  `feat/{key}-{title}`.
- **Q3. Macro branches**: out of scope; they keep `<KEY>-<title slug>`.
- **Q4. Existing branches**: never renamed; the format applies only to tasks without an assigned
  branch.
- Technical choices T1-T7 of Round 1 stand as written.

### Reversed assumptions

None: every answer matches the Round 1 recommendation.

### Acceptance baseline

- A project with no format creates `feat/<lower-case key slug>` exactly as today.
- A project with `{key}` creates `AUC-1234` for `AUC-1234` and `621` for `#621`.
- A project with `feat/{key}-{title}` creates `feat/AUC-1234-<title slug>` (slug bounded to about 30
  characters).
- A template without `{key}` or `{key_lower}`, or whose sample render is not a valid Git branch or is
  `main`/`master`/`HEAD`, is refused on save with a French message.
- A task whose `branch_name` is already set keeps it after the format changes.
- The runner prompt `{branchName}` and the created worktree branch always agree.
- Macro branches are unchanged.
