# Clarification #475 - Restart after question

Ticket: https://github.com/sebastienferry/sectile/issues/475
Branch: `feat/475`

## Round 1 (2026-09-25)

### Request

In the desktop app, a run that declares a question (`report_waiting` with
`waiting: true`) shows the `?` "Waiting for your answer" glyph on its skill
badge and the "Waiting for you" run state. Once the owner has answered and the
execution resumes, the glyph must disappear; today it stays.

Out of scope: the permission prompts of the agent CLI (never reported as a
wait, by design), headless runs (never marked), and any change to how a wait is
declared.

### What the code does today

Files read:

- `internal/taskmcp/server.go` - `report_waiting` tool; the receiving
  middleware calls `sessions.Resume` on any `tools/call` other than
  `report_waiting` (`resumesWaits`).
- `internal/taskmcp/sessions.go` - `MarkWaiting`, `ForgetWaiting`, `Resume`,
  `clearWaits`: the wait is held per MCP session and cleared on that session's
  next Sectile tool call, on `waiting: false`, on `finish_run`, or when the
  session closes.
- `internal/db/remoterun.go` - `SetRemoteRunWaiting` writes
  `task_activities.waiting_since`; a terminal status nulls it.
- `internal/handlers/handlers.go` - `pushRunWaiting` relays each change to the
  owner's agent as a `run_waiting` message. A clear is only relayed for a run
  whose mark was relayed by this process (`pushedWaits`, in memory).
- `internal/agent/agent.go` - `handleRunWaiting` copies the mark onto the
  agent's run list entry (`desktop.WaitingSince`), which the desktop polls;
  `pty_input` forwards the owner's keystrokes to the run's PTY.
- `desktop/src/skill-result.mjs`, `shared/runStates.ts`,
  `desktop/src/notifications.mjs` - the `?` glyph, the "waiting" run state
  and its banner, all derived from `run.waitingSince`.
- `internal/agentconfig/hooks.go` - the Claude Code hook that once reported
  waits was withdrawn (#260); nothing else observes the CLI's own prompts.

### Ambiguities, worst first

1. **What "start over" means.** Two readings lead to different code:
   - *A - the same session resumes after the answer.* The owner answers in
     the console, the agent works (edits, shell, commits) and makes its next
     Sectile call minutes later, or only at `finish_run`. The glyph is right by
     the current rule and wrong for the owner: nothing but a Sectile call
     clears it. Fixing this needs a new signal that the owner answered.
   - *B - the clear never reaches the desktop.* The session did make a
     Sectile call, the server cleared `waiting_since`, but the agent's copy
     stays set. Plausible causes found in the code: `pushedWaits` is in
     memory, so a server restart (or another replica handling the clear) drops
     the clear; an agent disconnected at clear time misses it and the mark is
     never re-sent on reconnect. Fixing this is a robustness fix, no product
     decision.
2. **What proves that the owner answered** (reading A only): a keystroke in
   the run's console, an Enter in the console, or only the agent's next
   Sectile call (status quo).
3. **Which surfaces must follow the clear**: the desktop only, or the web
   board badge too (`web/src/components/RemoteRunBadge.tsx` reads the server's
   `waiting_since`).

### Critical dependencies

- A clear decided on the workstation (reading A) has no channel to the server
  today: the agent protocol only carries `run_waiting` server -> agent. A new
  agent -> server message, or an agent HTTP call, is needed, and an older
  server must ignore it.
- No migration: `waiting_since` already exists.
- Multi-replica routing (#449): the clear must be applied where the run lives,
  and relayed to the agent whichever replica handles it.

### Reversible technical choices (settled from the code)

- The source of truth stays the server's `waiting_since`; the agent's copy is
  a cache. A local clear must also be sent to the server, otherwise the next
  `run_waiting` push or a reconnect would restore the glyph.
- On agent reconnect, the server re-sends the current mark (set or cleared)
  for every running run the agent holds, instead of relying on `pushedWaits`
  alone. This covers reading B whatever the answer to question 1.
- The MCP rule (next Sectile call clears the wait) stays as a second, later
  signal.

### Product questions (owner)

1. Which scenario did you observe - A (the session resumed after your answer
   but has not called Sectile yet), B (the glyph stays even after the run
   called Sectile again), or both? *Recommendation: fix both; B is cheap and
   removes a real stuck state.*
2. For A, what should clear the wait? *Recommendation: the owner pressing
   Enter in that run's console (desktop or web terminal), relayed to the
   server so every surface agrees. Any keystroke is too eager (scrolling,
   Ctrl-C on a prompt); output resuming is unreliable (spinners, redraws).*
3. Should the web board badge clear at the same moment as the desktop?
   *Recommendation: yes, it follows from clearing on the server.*

## Round 2 - answers from the owner (2026-09-25)

### Settled decisions

1. **Both scenarios are in scope.** A (the session resumed after the answer
   and has not called Sectile yet) and B (the server cleared the wait, the
   desktop never learned it) are fixed together.
2. **The owner pressing Enter in the run's console clears the wait.** This
   holds for the desktop console and the web terminal alike. Any other
   keystroke (arrows, scrolling, Ctrl-C) does not clear it. An Enter on a run
   that is not waiting changes nothing. The next Sectile tool call keeps
   clearing the wait as it does today, so a wait answered outside the console
   still ends.
3. **The clear is applied on the server** (`waiting_since`), so the desktop
   skill badge, the desktop run state and banner, and the web board badge all
   drop the glyph together.

No prior assumption was reversed.

### Resulting acceptance criteria (for the specification)

- After `report_waiting(true)`, an Enter typed in that run's console clears
  the `?` glyph on the desktop and the waiting badge on the web board within
  one poll, without any Sectile call from the session.
- After the session's next Sectile call clears the wait, the desktop glyph
  disappears even if the server restarted, or the agent was disconnected,
  between the mark and the clear.
- A headless run, a run that is not waiting, and keystrokes other than Enter
  keep their current behaviour.
- Tests cover the Enter clear, the non-Enter keystroke, and the re-sync of
  marks on agent reconnect.
- `CHANGELOG.md` gets a `Fixed` line under `[Unreleased]`: the waiting glyph
  now clears as soon as the question is answered.

### Left to the specification (technical, reversible)

- How an Enter typed in the desktop console reaches the server: the web
  terminal's `pty_input` already transits through the server, which can clear
  the wait itself; the desktop path must be checked and, if it talks to the
  agent directly, gets an agent -> server clear message that an older server
  ignores.
- The re-sync on agent reconnect: the server sends the current mark, set or
  cleared, for every running agent-dispatched run the agent holds, instead of
  relying on the in-memory `pushedWaits` alone.

### Open product questions

None.

### Owner confirmation

The owner confirmed the clarification as satisfactory on 2026-09-25.

Reproduction observed during this run: the wait declared at 10:17:18Z before
the Round 1 questions was still set after they were answered and while
Round 2 was being written. The session made no Sectile call in between, and
the second `report_waiting(true)` returned the original `waitingSince`
(scenario A).

### Addendum - a third cause observed after the transition (2026-09-25)

After the owner's confirmation, this session called `transition_stage` and
then `get_task`. Both are tool calls that `resumesWaits` should treat as a
resume. The run still carried `waitingSince: 2026-09-25T10:17:18Z` after both.
So the server-side rule ("the next Sectile call ends the wait") did not apply
at all to this session. That is a cause of its own, beyond A and B.

Likely mechanism, to confirm in the specification: `MarkWaiting`,
`ForgetWaiting` and `Resume` only act on a session found in
`SessionRegistry.live`. `report_waiting` writes `waiting_since` in the
database whether or not the session is registered. A session that is not in
`live` (never `Watch`ed, registered on another replica, or lost across a
server restart) gets a mark that nothing but `finish_run` or
`waiting: false` can clear.

This stays within the settled scope ("fix both", server as the source of
truth). The specification must make the next Sectile call clear the wait
whether or not the session is registered, for example by resolving the waits
from the database (running runs of the caller with `waiting_since` set and
adopted by, or reported from, this session) instead of the in-memory map
alone. No new product question.
