# Clarification - #281 - Detach and run task discussion in native terminal (Ghostty, Terminal)

Stage: new → clarified.

Ticket: https://github.com/sebastienferry/sectile/issues/281
Task Key: #281 (`gh-ef5a2777-920f-4744-a7e8-a58a4c257a23-281`)
Branch: `feat/281`

## Restated request and scope

Allow developers to run and detach interactive task discussions (`skillId = 'discuss'`) directly in their host native terminal emulator (such as Ghostty, Terminal.app, iTerm2, Alacritty) instead of solely inside the embedded xterm.js canvas in the Sectile desktop app. When running in a native terminal, discussions preserve full task context (`SECTILE_*` environment variables, working directory set to the task worktree, git branch), remain tracked and stoppable within the desktop app, and can be detached on the fly from a running desktop session without terminating the underlying discussion process.

Out of scope:
- Triggering workflow stage transitions or skill prompt mutations (discussions remain free-form interactive sessions with no skill prompts or stage advances).
- Launching non-discussion skills (such as `clarify`, `specify`, `implement`) in native external terminals (those continue following their configured interactive or autonomous runner pipelines).
- Web-only terminal spawning without a connected local agent (an external terminal emulator inherently requires a local workstation agent daemon).

## Ambiguities, worst first

1. **Architecture of the Detach & Attachment mechanism.**
   - *Ambiguity*: Should the native terminal spawn an independent child process running the agent CLI directly, or attach to the local agent daemon's existing PTY session?
   - *Impact*: If the native terminal runs an independent process, an in-flight discussion started in the desktop app cannot be detached without terminating the process and losing the active conversation history. Furthermore, the desktop app cannot monitor or mirror the session.
   - *Decision*: The native terminal will run an attach client via `sectile-agent attach --session <id>` (or a launcher script invoking loopback WebSocket attach). Because `terminal.Manager` in the agent daemon already owns the PTY session and supports concurrent WebSocket clients with history replay and resize handling, the native terminal connects its stdio in raw mode directly to that existing daemon PTY session.
   - *Rationale*: This satisfies all acceptance criteria:
     - Discussions can be started directly in native terminal or detached from desktop.
     - Detaching does not terminate the underlying discussion process.
     - Desktop can mirror output in real time or display an active external session banner.
     - Desktop "Stop" button and execution lifecycle tracking continue to work seamlessly.

2. **Desktop UI and Session State during Detachment.**
   - *Ambiguity*: What should the desktop execution view display when a discussion is running in or detached to an external terminal?
   - *Impact*: Closing the xterm view completely leaves an empty space and prevents viewing output. Leaving it unchanged might confuse the user regarding where inputs should be typed.
   - *Decision*: In the desktop console view, output continues to be mirrored live in xterm.js. A prominent status badge is displayed in the header: **Active in Ghostty** (or configured terminal emulator). The toolbar provides a **Detach / Focus native terminal** button when attached to desktop, and keyboard input in desktop xterm remains functional (broadcast input).

3. **Terminal Emulator Selection & Configuration Precedence.**
   - *Ambiguity*: Where should the user select their preferred terminal emulator, and what is the precedence between project, workstation, and auto-detected defaults?
   - *Impact*: Ambiguity across configuration files (`~/.config/sectile/settings.json`, SQLite DB, project config).
   - *Decision*:
     - Precedence order:
       1. Explicit call parameter (`terminalOverride` if supplied).
       2. Project configuration (`models.Project.ExternalTerminalCommand`).
       3. Workstation/User setting (`agentconfig.Overrides.Terminal` in `settings.json` / `user_settings.external_terminal_command`).
       4. System auto-detection via `detectDefaultTerminal()` (`Ghostty` → `iTerm` → `Terminal.app` on macOS; `wt` → `cmd` on Windows; `x-terminal-emulator` on Linux).
     - UI Exposure:
       - Expose a **Terminal emulator** selector (options: Ghostty, Terminal.app, iTerm, Custom command) in the Desktop Project configuration dialog (`openProject` → Local tab).
       - Expose the workstation default in the Profile / Settings dialog.

4. **Entry Points for Native Terminal Discussion.**
   - *Ambiguity*: Where should the user trigger a discussion in a native terminal?
   - *Impact*: Crowded menus vs discoverability.
   - *Decision*:
     - In the ticket row `…` (more) menu: add an entry **Discussion in native terminal** directly below **Discussion (no skill)**.
     - In the execution toolbar: when an active `discuss` session is open in the desktop console, display a **Detach to native terminal** button.

## Critical dependencies

- None external.
- SQLite schema already includes `external_terminal_command` on `projects` and `user_settings` tables; no database migrations needed.
- macOS platform utilities: `open -a <App> <args>` or launcher script.
- Standard terminal raw mode handling (`golang.org/x/term` or POSIX stty) for `sectile-agent attach`.

## Numbered questions with recommended options

1. **How should the Desktop UI behave while the discussion is open in the native terminal?**
   - *(Recommended) Option A*: Mirror terminal output live in Desktop xterm.js, with an informative status badge (`Active in Ghostty`) and a button to focus/re-open the external window.
   - *Option B*: Decouple Desktop xterm.js and display a static placeholder card ("Discussion detached to Ghostty") with a "Re-attach to Desktop" button.

2. **How should launching a discussion in a native terminal be surfaced in the ticket list?**
   - *(Recommended) Option A*: Add **Discussion in native terminal** directly as a menu item in the ticket row `…` menu.
   - *Option B*: Add a settings toggle in the Compose/Launch modal specifying execution target (Desktop vs Native Terminal).

## Settled scope and assumptions

1. **Agent Terminal Attach Command**:
   - Introduce `sectile-agent attach --session <id>` (or `--url <loopback> --token <token> --session <id>`) in `cmd/agent/main.go` and `internal/agentattach/`.
   - The attach command connects to `ws://127.0.0.1:<port>/desktop/terminal?id=<sessionID>`, puts the terminal in raw mode, forwards input, receives output, and listens for terminal window resize events (`SIGWINCH`) to resize the daemon PTY.
2. **Native Terminal Launcher**:
   - Implement external terminal launcher helper in `internal/agent/` supporting macOS (`Ghostty`, `Terminal.app`, `iTerm`, custom command) and Linux/Windows.
   - When launching directly in native terminal, the agent starts the PTY session in `terminal.Manager` and invokes the native terminal emulator running the attach command.
3. **Desktop Detach & Launch Controls**:
   - Add **Discussion in native terminal** to ticket row `…` menu in `desktop/src/main.js`.
   - Add **Detach to native terminal** button to execution toolbar when viewing an active discussion.
   - Add IPC handler in Electron `preload.cjs` and `main.cjs` to request launching or detaching the session to the native terminal.
4. **Project Settings**:
   - In `desktop/src/main.js` (`openProject`), add a Terminal emulator setting in the Local tab, persisted through `mapProject` and `settings.json`.
5. **Testing**:
   - Unit tests for terminal resolution, attach command, and launcher arguments.
   - Desktop UI tests asserting the presence and actions of the native terminal discussion menu items and toolbar detach button.
