## Round 1 — initial analysis (2026-09-29)

### Restated request and scope

On Windows, preparing a task worktree from the local agent must not open a visible, flickering console window: every console child the agent starts for itself during that preparation must go through the existing `agentexec.Hidden` helper. Out of scope: consoles the user is meant to see (the native terminal launcher, interactive `StartControlled` runs, the editor opened by "Open in editor"), the POSIX side (where `Hidden` is a no-op), and any change to how or when worktrees are provisioned.

### Verified findings

- The helper the ticket remembers exists: `agentexec.Hidden` (`internal/agentexec/process_windows.go:110`), introduced by `e73a02dd fix(301): run the agent's own commands without a console window`. It OR-s `CREATE_NO_WINDOW` into the command's creation flags. The desktop starts the agent detached (`desktop/electron/main.cjs:222`, `detached:true`), so the agent owns no console and Windows allocates a fresh visible one for every console child that does not ask for none.
- Every `git` call of the worktree creation itself is already hidden: `gitLocal` (`internal/agent/agent_config.go:142`) wraps `exec.CommandContext` in `agentexec.Hidden`, and `git worktree add` (`agent_config.go:282-292`) goes through it. Git hooks run by `worktree add` inherit that hidden console.
- **Root cause:** right after the worktree exists, `provisionWorktree` (`internal/agent/provision.go:60`) runs `npm ci` in every package folder through `npmInstall` (`provision.go:38-49`), and that command is built with a bare `exec.CommandContext(ctx, "npm", "ci")`, without `agentexec.Hidden`. On Windows `npm` resolves to `npm.cmd`, run by `cmd.exe`, which then starts `node`; the console window stays open for the whole install (about four minutes for this repository, per the comment on `provisionFolderTimeout`). The provisioning was added after fix #301 (`813808c0 feat(agent): install node_modules in task worktrees before the session starts`) and never adopted the helper.
- Both provisioning entry points are affected: the launch path (`prepareDispatch`, `agent_config.go:301-316`) and the board's branch checkout (`prepare_workspace` operation, `agent_operations.go:306-323`, which provisions in the background).
- A scan of non-test `exec.Command`/`exec.CommandContext` calls finds one other agent-owned launch whose output the agent reads itself and that is not hidden: `gitOutput` in `internal/sddfiles/sddfiles.go:202`, used when the agent reads a macro's specification files (`internal/agent/agent_macro_dispatch.go:233`). It is not part of worktree creation.
- The remaining unwrapped launches are intentional or already hidden elsewhere: `agentexec/exec.go:85` (interactive run through `StartControlled`, owns the user's terminal), `agent_headless.go:43` (goes through `StartDetached`, which calls `Hidden`), `terminal_launcher.go:173` (opens the native terminal the user asked for), `runner.go:1038` (opens the user's editor), and the POSIX-only `stty` calls.

### Ambiguities (worst first)

1. **Scope of the sweep** — fix only the worktree-creation path (`npm ci`), or also the sibling `sddfiles.gitOutput` launch that flashes a console when the agent reads macro specification files. The two readings touch different packages and different acceptance criteria. → Open question 1.

No other reading leads to different code.

### Critical dependencies

- None external: no migration, no service, no third-party limit. `internal/sddfiles` can import `internal/agentexec` (already a dependency of `internal/runner` and `internal/workspace`, same layer).
- Verification of the absence of a window is manual on a Windows workstation with the desktop-launched (detached) agent; automated tests can only assert the creation flag, as `process_windows_test.go` already does for `Hidden`.

### Resolved technical choices (reversible, from existing conventions)

- Reuse `agentexec.Hidden` — no new helper, no change to its semantics. `CREATE_NO_WINDOW` is inherited by `cmd.exe`, `node` and the install scripts they start, so the whole install tree stays windowless.
- Keep `npmInstall` a variable (tests replace it), and make its command construction testable so a Windows test can assert `CREATE_NO_WINDOW` on the `npm ci` command, following `process_windows_test.go`.
- Leave the intentionally visible launches listed above untouched.

### Open product questions

   - **B:** no — keep #638 strictly to worktree creation and file a separate ticket for it.

## Round 2 - answers from the owner (2026-09-29)

### Answers

1. **Hide `sddfiles.gitOutput` too:** the owner chose **A — yes, include it**, answered interactively.

### Settled scope

- On Windows, the agent's own console children no longer open a window in these two places:
  - `npmInstall` (`internal/agent/provision.go`): `npm ci` run by `provisionWorktree` after a worktree is created, from both the launch path (`prepareDispatch`) and the board's `prepare_workspace` operation.
  - `gitOutput` (`internal/sddfiles/sddfiles.go`): the `git` calls the agent makes when it reads a macro's specification files.
- Both go through the existing `agentexec.Hidden` helper. The helper stays as it is, and so do the POSIX behaviour and the provisioning timing and timeouts.
- Out of scope: launches meant to be visible (native terminal launcher, interactive `StartControlled` runs, "Open in editor").

### Settled decisions and reversed assumptions

- Round 1's open question is closed in favour of the recommended option. No Round 1 assumption was reversed.
- The technical choices from Round 1 still hold. Reuse `agentexec.Hidden`, keep `npmInstall` replaceable in tests, and add Windows tests that assert `CREATE_NO_WINDOW` on the `npm ci` command and on `gitOutput`'s command, following `process_windows_test.go`. Absence of the window is confirmed manually with the desktop-launched agent.

### Acceptance criteria (baseline for specification)

- On Windows, with the agent started by Sectile Desktop, creating a task worktree (from a launch or from the board's branch checkout) opens no console window during the `git worktree add` or the `npm ci` that follows.
- On Windows, reading a macro's specification files through the agent opens no console window.
- The install still runs, succeeds or fails, and gets logged as it does today, and its timeouts are unchanged.
- Existing visible consoles (native terminal, interactive run, editor) behave as before.

None.

None. Exit condition met: the owner answered the only product question.
