Title: Token isolation problem

## Round 1 (2026-09-25)

### Restated request and scope

The server tracker credential introduced by #464 (ADR 0028) must be used for
the background synchronisation only. Every tracker write a signed-in person
causes (creating, editing or commenting a ticket, a macro or an epic, including
title, description, labels and the stage report comment) must travel under that
person's own credential, and must never silently fall back to the server
credential; today comments reach Jira under the server account.
Out of scope: the storage, sealing and administration of the credentials
themselves (#464, ADR 0014), the reads a person triggers (they attribute
nothing), and the environment-variable resolution of the server credential.

### Verified findings

Files read: `internal/trackerapi/client.go` (`ForActingUser`,
`missingCredential`), `internal/trackerapi/jira.go` (`forProject`),
`internal/trackerapi/jira_client.go` (`jiraConfigured`),
`internal/trackerapi/adapters.go` (GitHub `forProject`),
`internal/db/trackercredentials.go` (`trackerAs`), `internal/db/comments.go`,
`internal/db/trackerops.go` (queue, stage op), `internal/db/interactive.go`,
`internal/db/macros.go`, `internal/db/db.go` (`CreateTask`, `UpdateTaskBy`,
`AddTaskComment`, remote conversion), `internal/db/postback.go`,
`internal/taskmcp/server.go` (`add_comment`, `create_task`, `update_task`,
`transition_stage`, `callerOf`), `internal/handlers/pairing.go`
(`actingContext`, `webSessionUser`), `docs/adrs/0028-tracker-sync-uses-a-server-credential-per-provider.md`,
`docs/clarifications/464.md`.

- **The per-call rule exists and is right for Jira.** `JiraAdapter.forProject`
  refuses a call whose context names a user without a personal Jira token. So
  a Jira write only reaches the server credential when **the acting user has
  been lost on the way**, the context naming nobody.
- **Paths that lose the acting user** (each ends up on the server credential):
  1. `runStageOp` (`internal/db/trackerops.go:780`) posts the stage report with
     `d.AddTaskComment(task.ID, …)`, i.e. `context.Background()`, although the
     op carries `op.UserID` and its own `ctx` already names them. This is the
     `transition_stage` note that is auto-posted to the issue, and the most
     likely source of the reported Jira comments.
  2. MCP `create_task` (`internal/taskmcp/server.go:403`) calls
     `database.CreateTask`, the no-actor variant, where the REST handler calls
     `CreateTaskAs(h.actingContext(r), …)`.
  3. Local-to-remote conversion (`internal/db/db.go:5790`) calls
     `ts.CreateIssue(context.Background(), …)`.
  4. Story creation under a macro (`internal/db/macros.go:555` `CreateTask`,
     `:581` `SetParent` with `context.Background()`).
  5. GitHub milestone writes backing macros (`internal/db/macros.go`: create,
     update, delete, set, transfer) go through `d.tracker(proj.ID)`, which is
     the server credential by construction.
  6. `pushStageToTracker` (`internal/db/interactive.go:48`) uses
     `context.Background()` for its label update and comment, but has no caller
     left; it is dead code.
- **GitHub and GitLab fall back on purpose.** `GithubAdapter.forProject` and
  `ForActingUser` hand a user without a personal token the server token; ADR
  0028 states it ("GitHub and GitLab fall back to the server credential").
  Closing this ticket as worded reverses that line of the ADR.
- **An MCP or REST call may name nobody.** `callerOf` returns an empty caller
  when the resolver cannot map the key to a user, and `webSessionUser` returns
  `""` for an agent credential without a device. Those calls are user-caused
  but anonymous, and today take the server credential.

### Ambiguities (worst first)

1. **GitHub/GitLab writes without a personal token**: refuse (as Jira does) or
   keep the server fallback of ADR 0028. Refusing is a breaking change for
   deployments that run on a shared GitHub token. → product question Q1.
2. **User-caused calls that name nobody** (legacy agent key, key without a
   device): refuse, or treat as unattended. → product question Q2.
3. **What "background sync" covers**: only the sync pass (its reads and the
   housekeeping writes it makes itself), or also writes the server makes on
   its own initiative (e.g. a managed run's post-back when its launcher is
   unknown). → product question Q3.

### Critical dependencies

- ADR 0028 must be amended (or superseded) if Q1 is "refuse"; CHANGELOG entry
  under `Changed` (breaking) in that case.
- No migration: the acting user is already stored on queued ops
  (`op.UserID`) and on activities (`activity.UserID`).
- Desktop/local agent keys must resolve to a user for MCP writes to keep
  working if Q2 is "refuse".

### Reversible technical choices (settled from the code)

- Every user-caused write propagates the actor through the context
  (`tracker.WithActingUser`), including the queued ops and the stage report
  comment; the no-actor helpers (`CreateTask`, `AddTaskComment`) stay for
  genuinely unattended callers only.
- MCP `create_task` uses `CreateTaskAs` with the caller, like the REST handler.
- Macro milestone writes resolve through `trackerAs` / `ForActingUser` with the
  requesting user, like `board.go` already does for its GraphQL read.
- Dead `pushStageToTracker` is removed rather than fixed.
- A refused tracker write during a stage transition keeps the local
  transition and records a failure step with the actionable message ("add your
  token in Profile → Tracker credentials"), as the stage op already does for a
  failed label sync.
- A regression test per leaking path asserts that the tracker call receives the
  acting user (a fake adapter recording `tracker.ActingUser(ctx)`).

### Product questions

- **Q1 - GitHub and GitLab without a personal token.** When a signed-in person
  who stored no GitHub/GitLab token creates, edits or comments, should the
  write be refused (like Jira) or keep falling back to the server token?
  *Recommendation: refuse, for all three providers*, so the server credential
  never signs a user action; amend ADR 0028 and flag it as breaking.
- **Q2 - Anonymous user-caused calls.** An MCP/REST write whose key does not
  resolve to a user: refuse it, or let it use the server credential?
  *Recommendation: refuse with an explicit error*; only the server's own
  unattended work (sync, jobs nobody launched) may use the server credential.
- **Q3 - Managed run post-back.** A run's report and stage transition are
  posted after the session ends. Should they use the launcher's credential
  (the run records its user), with the server credential only when no user is
  recorded? *Recommendation: launcher's credential; refuse (failure step) when
  the launcher has none*, consistent with Q1.

## Round 2 - answers from the owner (2026-09-25)

Answers given interactively in the session.

### Settled decisions

- **Q1 - refuse, for all three providers.** A write a signed-in person causes
  on GitHub or GitLab without a personal token is refused, as on Jira, with
  the "add yours in Profile → Tracker credentials" message. The server
  credential never signs a user action. ADR 0028's line "GitHub and GitLab
  fall back to the server credential" is reversed: the ADR is amended (or a
  new ADR supersedes that part), and the CHANGELOG carries a breaking
  `Changed` entry.
- **Q2 - refuse anonymous user-caused writes.** An MCP or REST write whose key
  resolves to no user fails with an explicit error. Only the server's own
  unattended work (the sync pass and jobs nobody launched) uses the server
  credential.
- **Q3 - post-back uses the launcher.** A managed run's report and stage
  transition travel under the credential of the user recorded on the run;
  when that user has no personal token, the tracker step fails with the
  actionable message and the local transition is kept.

### Reversed assumptions

- Round 1 treated the GitHub/GitLab fallback as intended behaviour (ADR 0028);
  it is now a defect to remove.

### Consequences and remaining technical points (no product question)

- The refusal applies to **writes** only. User-caused **reads** (comments
  shown on a ticket, PR states, GraphQL board reads) keep falling back to the
  server credential: a read attributes nothing, and refusing it would blank
  screens for members without a token. The GitHub/GitLab adapters therefore
  need a write-side check distinct from the read path.
- Keys that name no user (legacy shared agent key, agent credential without a
  device) lose their write access to trackers; the release note names the fix
  (pair the desktop / use a personal key).
- Scope of the fix is the six paths listed in Round 1 plus the post-back, each
  with a regression test asserting the acting user reaches the adapter.
