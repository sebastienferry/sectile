# #320 - Skills require a CHANGELOG.md entry in a repository that has none

Round 1 - 2026-09-23

## Request restated

When #307 was specified, it carried an acceptance criterion ("the fix is listed in
`CHANGELOG.md`") that could not be met, because the repository had no changelog. The ticket asks for
a written decision: either create and maintain `CHANGELOG.md` (Keep a Changelog), or drop the
requirement everywhere it is stated, so that later tickets stop repeating the same caveat.

Out of scope: the release procedure itself (tag, SemVer bump, manifests), how the changelog is served
in the product, and rewording existing changelog entries other than the ones named below.

## The premise is out of date

The ticket was filed on 2026-09-21 at 20:13. Since then, the first option has been **implemented and
recorded**:

| When | Commit | What |
| --- | --- | --- |
| 2026-09-21 22:09 | `7bbaf09` (#307, PR #315) | #307 merged. Its task T22 (`CHANGELOG.md` entry) could not be done |
| 2026-09-22 06:30 | `ea8d895` (#329) | `CHANGELOG.md` created (Keep a Changelog, English only), ADR 0018 accepted, release procedure written in `AGENTS.md` |
| 2026-09-22 → today | 12 of the 40 commits since `ea8d895` | Feature PRs add their own line under `## [Unreleased]` (e.g. #266, #345, #356, #357) |

So the decision the ticket asks for already exists, in ADR 0018 ("`CHANGELOG.md` lives at the
repository root, in Keep a Changelog format… The changelog ships inside the product"). Option 2
(drop the requirement) now contradicts an accepted ADR and would break the build: the file is
embedded (`changelog.go`, `.dockerignore` `!CHANGELOG.md`) and served on `GET /api/changelog`.

## What remains of the ticket

Against its four acceptance criteria:

1. *The decision is taken and written*: done by ADR 0018. Nothing left, except that this ticket
   should point to it.
2. *The file exists, follows Keep a Changelog, and an entry covers at least #307*: the first two
   parts are met. **No line mentions #307.** The `[0.1.0]` section summarises the unversioned history
   in broad lines ("Local agent", "Workflow stages") and does not cover the fix (a quiet run no
   longer canceled after 15 minutes; a disconnected run can be recovered). That fix is user-visible.
3. *Requirement removed*: not applicable, since the file was created.
4. *A later ticket no longer carries the caveat*: met as long as the file exists. One gap is left:
   **nothing states when an entry is written.** `AGENTS.md` step 3 writes the entries **at release
   time**, from the commits. Actual practice (12 PRs) writes them **in each PR** under
   `[Unreleased]`. The two readings lead to different skill instructions (see Q2).

## Ambiguities (worst first)

1. **Where the #307 line goes.** Under `[0.1.0]` (it shipped before the first tag, and the tag does
   not exist yet), or under `[Unreleased]` (it has never been announced). These produce different
   diffs and different release notes.
2. **When an entry is written: per PR, or at release time.** If per PR, the specify/implement stages
   should add a line under `[Unreleased]` for every user-visible change, and the release procedure
   only promotes the section and fills gaps. If at release time, PRs must not touch the file, and
   the 12 recent PR entries go against the convention. Recent history supports per PR, but
   `AGENTS.md` does not say so.

## Dependencies

- None external. The file is compiled into the server (`changelog.go`) and the desktop app (Vite
  `?raw` import), so any edit must keep the Keep a Changelog structure that
  `desktop/src/changelog.mjs` parses (`desktop/tests/changelog.test.mjs` pins it).
- The v0.1.0 tag has not been cut. If it is cut before this ticket is implemented, the #307 line can
  no longer go under `[0.1.0]`, and Q1 falls back to option (b).

## Reversible choices settled here

- **Keep option 1 (keep the changelog).** ADR 0018 already decided it, and it is load-bearing in the
  build. This is not asked as a product question. It is recorded so that the ticket's either/or is
  closed.
- **No ADR is needed.** ADR 0018 is the decision record. At most, a sentence in `AGENTS.md` makes the
  per-PR convention explicit (depends on Q2).
- **The `runner.go` handoff prompt stays as it is.** It is conditional, which matches both readings
  of Q2. It is a prompt given to agents, not a runtime surface shown to users, but rewording it is not
  needed here.
- **Nothing to remove from the stage skills**: none of them requires a changelog.

## Open product questions (for the ticket owner)

**Q1. Where does the #307 fix go in `CHANGELOG.md`?**
- (a) **Recommended**: one `### Fixed` line under `[0.1.0]`, since #307 merged before the first tag
  and that tag is not cut yet. Something like: "An agent run that stays quiet for a long time (a long
  build, a question to its owner) is no longer canceled after fifteen minutes, and a run whose client
  disconnected can be recovered and finished."
- (b) One `### Fixed` line under `[Unreleased]`.
- (c) No line: accept that `[0.1.0]` covers the pre-release history in bulk, and drop that
  acceptance criterion.

**Q2. When is a changelog entry written?**
- (a) **Recommended**: in the PR that makes the user-visible change, under `[Unreleased]`. This is
  what recent PRs do. `AGENTS.md` step 3 would say that the release procedure promotes that section
  and only adds the entries that are missing. The specify stage keeps a changelog acceptance
  criterion **only for user-visible changes**.
- (b) At release time only, as `AGENTS.md` step 3 currently says. PRs do not touch the file, and
  specs no longer carry a changelog criterion.

Once both questions are answered, the implementation is a small documentation change:
`CHANGELOG.md` (one line), and, for Q2 (a), one paragraph in `AGENTS.md`.

## Round 2 - answers from the owner (2026-09-23)

The owner confirmed both recommendations in session and considers the clarification complete.

### Settled decisions

- **Keep the changelog (option 1).** ADR 0018 is the decision record. This ticket adds no ADR and
  removes nothing from the stage skills or from the `runner.go` handoff prompt.
- **Q1 → (a).** Add one `### Fixed` line under `## [0.1.0] - 2026-09-22` for #307: an agent run that
  stays quiet for a long time is no longer canceled after fifteen minutes, and a run whose client
  disconnected can be recovered and finished. Written for users, in English, and referencing the PR
  (`(#315)`) as the release procedure requires.
- **Q2 → (a).** A changelog entry is written **in the PR that makes the user-visible change**, under
  `## [Unreleased]`. `AGENTS.md` step 3 is reworded: the release procedure promotes `[Unreleased]`
  and adds only the entries that are missing. A specification carries a changelog acceptance
  criterion **only when the change is visible to users**.

### Reversed assumptions

- None. Both answers match the Round 1 recommendations.

### Fallback kept

- If `v0.1.0` is tagged before this ticket is implemented, the #307 line goes under `[Unreleased]`
  instead (Q1 option b), since a released section is not edited afterwards.

### Scope for the next stages

- `CHANGELOG.md`: the #307 line.
- `AGENTS.md`: the per-PR convention in "Write the changelog entries".
- Checks: `desktop/tests/changelog.test.mjs` and the Go tests that read the embedded file
  (`internal/handlers/version_test.go`) still pass.

No product question remains open.
