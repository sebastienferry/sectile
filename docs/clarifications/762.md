# Clarification #762 - Desktop: Folders

Ticket: https://github.com/sebastienferry/sectile/issues/762
Branch: `feat/762`

## Round 1 - initial report (2026-10-06)

### Request

Sectile Desktop shows one path for the selected execution, the worktree of its
primary repository, as a "Copy this path" button in the toolbar. A task can
span several folders (other repositories' worktrees, read-only context
repositories, attached folders, a distinct specifications worktree): the ticket
asks for a menu that lists those folders and copies their paths.

Out of scope: opening a folder in an editor or a terminal from that menu,
changing which folders a task has (attaching, detaching, preparing a worktree),
and the web client.

### What I read

- `desktop/src/main.js`: the toolbar markup (`#worktree`, `#directory`,
  `#open-editor`, `#worktree-copied`), `showDirectory`, the `#worktree` click
  handler (`api.copyText`, "Copied" notice), the project row menu
  (`createProjectMenu`-style `more`/`menu` with keyboard handling) and the
  ticket row menu (`.ticket-more` / `.ticket-menu`).
- `desktop/src/run-folders.mjs`: the "Add folder…" action of a run (#676, #689).
- `internal/agent/agent_desktop.go`: `desktopRun`, the payload the desktop
  reads for each run. It carries `directory` only, no folder list.
- `internal/agent/repositories.go`: `taskFolderMap`, `projectFolderMap`,
  `buildFolderMap`, `withSpecWorktree`, `folderMapPrompt` (the "Folders of this
  task" block of the prompt) and `folderMapDirs`.
- `internal/agent/agent.go`, `agent_desktop.go`, `agent_console.go`,
  `agent_conversation.go`: where the folder map is computed at launch and
  exported as `SECTILE_REPOSITORIES`.
- `internal/models/repository.go`: `FolderMapEntry` (`remote`, `identity`,
  `role`, `path`, `worktree`, `kind`, `attached`).
- `internal/taskmcp/server.go`: `prepare_repository_worktree`, which adds a
  worktree to a running task after launch.

### Ambiguities, worst first

1. **Where the menu lives.** Readings: (a) on the toolbar path itself, which
   becomes a split control: the path still copies on click, a chevron beside
   it opens the folder list; (b) a new entry in the sidebar row's `…` menu of
   the task; (c) the native application menu. They are different code paths
   and (a) is the only one bound to the selected execution, which is where the
   single path is shown today.
2. **What "copy the path of all the folders" copies.** Readings: (a) one menu
   item per folder, each copying its own path; (b) a single "Copy all paths"
   item copying them together; (c) both.
3. **Which folders are listed.** The launch folder map holds: the primary
   worktree, the worktrees of other changed repositories, read-only context
   repositories (their checkout, not a worktree), attached Git and plain
   folders, and the specifications worktree when distinct (#736). Entries "not
   mapped" or "not found on this workstation" have no path. Readings: every
   entry that has a path, or only the writable ones (primary, changed,
   specifications).
4. **Folders added after launch.** `prepare_repository_worktree` creates a
   worktree during the run; "Add folder…" attaches one. Readings: the menu shows
   the folders known at launch (what `SECTILE_REPOSITORIES` says), or it follows
   those additions.
5. **Which executions offer it.** Ticket runs have a task folder map;
   conversations and free consoles have a project folder map
   (`projectFolderMap`). Readings: tickets only, or every execution with more
   than one folder.

### Critical dependencies

- **The desktop has no folder list today.** `desktopRun` exposes `directory`
  only; the map is computed in the agent at launch and handed to the engine
  through the prompt and `SECTILE_REPOSITORIES`, never to the desktop. The
  agent must keep the map on the run and expose it.
- **Restored runs (#588).** A run reloaded from the run store has no session;
  the folder list must be persisted in the run store to survive an agent
  restart, or the restored run falls back to its single path.
- **Older agents.** A desktop paired with an agent that does not send the list
  must keep today's single "Copy this path" button unchanged.
- No server, tracker or database change: the folder map is a workstation fact
  and stays on the agent.
- No child process is started, so the `agentexec.Hidden` rule does not apply.

### Reversible technical choices, resolved

- **Data source:** the agent stores the folder map it already computes for the
  launch on the run and adds it to `desktopRun` as `folders`
  (`[]FolderMapEntry`, omitted when empty). It is the same list the engine was
  given, so the menu and the prompt cannot disagree.
- **Feature detection:** the field's presence is the signal; no new capability
  string is needed. An absent or one-entry list keeps today's control.
- **Labels:** each item shows what `folderMapPrompt` already names: the
  repository identity's last segment (as `repositoryName` does for pull
  requests), "specifications" for the spec folder, the folder path for an
  attached folder without identity, followed by the role (primary, changed,
  context, attached, specifications) and the full path as secondary text.
- **Copy format for several paths:** one absolute path per line, in folder map
  order (primary first), no labels, so it pastes into a shell or a `cd`.
- **Confirmation:** the existing "Copied" notice beside the path is reused.
- **Menu mechanics:** the same popup pattern as the project and ticket menus
  (`role=menu`, arrow keys, Escape, outside pointer dismisses).
- **User-facing strings:** new strings are written in English, like the
  surrounding desktop toolbar ("Copy this path", "Copied").

### Product questions

1. **Where does the menu go?** Recommended: (a) on the toolbar path of the
   selected execution: the path keeps copying on click, a chevron next to it
   opens the folder list, shown only when the execution has more than one
   folder.
2. **What does the menu copy?** Recommended: (c) both, one item per folder that
   copies that folder's path, and a "Copy all paths" item at the top that
   copies them all, one per line.
3. **Which folders?** Recommended: every folder of the map that has a path on
   this workstation, read-only context folders and attached folders included,
   each labelled with its role; entries without a path are left out.
4. **Folders added during the run?** Recommended: yes, the list follows the
   worktrees `prepare_repository_worktree` creates and the folders "Add folder…"
   attaches for that run, so the menu matches what the session can actually
   reach.
5. **Conversations and free consoles?** Recommended: yes, every execution whose
   folder map has more than one entry, since they get one from
   `projectFolderMap` already.

## Round 2 - answers from the owner (2026-10-06)

Answers given interactively in the session.

### Settled decisions

1. **Placement:** on the toolbar path of the selected execution. The path keeps
   copying itself on click; a chevron beside it opens the folder list. The
   chevron is shown only when the execution has more than one folder.
2. **What it copies:** one menu item per folder, each copying that folder's
   absolute path. There is no "Copy all paths" item.
3. **Which folders:** every entry of the folder map that has a path on this
   workstation: the primary worktree, the other repositories' worktrees, the
   read-only context repositories, the attached Git and plain folders, and the
   specifications worktree when distinct. Each item is labelled with its role.
   Entries that are not mapped or not found on this workstation are left out.
4. **Folders added during the run:** included. The list follows the worktrees
   `prepare_repository_worktree` creates and the folders "Add folder…"
   attaches for that run.
5. **Executions offering it:** every execution whose folder map has more than
   one entry, ticket runs, conversations and free consoles alike.

### Reversed assumptions

- Round 1 recommended a "Copy all paths" item copying every path, one per line.
  The owner chose one item per folder only, so the multi-path copy format of
  round 1 is dropped.

### Consequences for the specification

- The agent keeps the folder map on each run (task map for ticket runs,
  project map for conversations and free consoles), exposes it on
  `desktopRun` as `folders`, persists it in the run store for restored runs,
  and updates it when `prepare_repository_worktree` or "Add folder…" adds a
  folder to that run.
- The desktop shows the chevron and menu only when `folders` has more than one
  entry with a path; otherwise, and with an older agent, today's single
  "Copy this path" control is unchanged.
- Each item reuses the existing "Copied" notice.

### Status

- Report committed on `feat/762` (`docs(spec): clarify #762 (round 2)`).
- Open questions: none. The owner confirmed the clarification is satisfactory.
- Stage transition: new → clarified.
