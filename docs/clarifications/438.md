## Round 1 (2026-09-24)

### Restated request and scope

When the user ends a discussion (the "Discussion (no skill)" launch in Sectile
Desktop), the execution is reported as *Cancelled*, which reads as an abnormal
outcome for what is simply the normal way a discussion ends; the two glyphs
shown for the execution are also hard to read (the second one is ambiguous
between "done" and "still running"). The change makes the end of a discussion
read as a normal ending and makes the indicators of a discussion unambiguous.

Out of scope: the outcome of real skill runs (clarify, specify, …) stopped by the
user, which stay *Cancelled*; the notification and run-state vocabulary as a
whole beyond what a discussion needs; the web activity history layout.

### Verified findings

Files read: `shared/runStates.ts`, `desktop/src/skill-result.mjs`,
`desktop/src/main.js` (run rows, header, Stop button, launch menu),
`internal/agent/agent_desktop.go` (`/desktop/stop`, orphaned PTY recovery,
`finishDesktopRun`), `internal/agent/agent_run.go` (`handleRunControl`),
`internal/agent/agent.go` (dispatch and launch failure), `internal/agent/agent_config.go`
(`liveSessionMode`).

- A discussion is an ordinary interactive run with `skillId: "discuss"`. It has a
  server activity, and the local agent closes it through `finish_run` like any
  other run.
- There are three ways a discussion ends today, with three different outcomes:
  1. **Stop execution** button in the Desktop toolbar → `/desktop/stop` sets
     `canceled`, and `finish_run` records `canceled` / "Execution canceled".
  2. **The embedded terminal disappears** (tab/console closed) →
     `recoverOrphanedPTYRun` records `canceled` / "Execution canceled after its
     local terminal closed".
  3. **The user quits the CLI** (`/exit`, Ctrl+D) → `agent-exec` reports the exit
     code: `completed` on 0, `failed` otherwise.
- Each execution shows **two indicators** side by side, in the sidebar row and in
  the toolbar header:
  - the **run state** (`shared/runStates.ts`, lucide glyphs): for `canceled` a grey
    circle with a diagonal bar, labelled "Cancelled";
  - the **skill result** badge (`skill-result.mjs`, text glyphs): `✓` Skill
    completed, `!` Skill failed, `⊘` Skill canceled, `◷` pending (awaiting stage
    validation, stopping, or "Execution ended · skill completion unconfirmed").
- For a stopped discussion the user therefore sees two "cancelled" glyphs drawn in
  two different styles, and the badge says *Skill* canceled although a discussion
  runs no skill. The `◷` clock of the pending badge is the likely "tick or
  running?" confusion: it is neither a tick nor the spinner, and a `completed`
  discussion can show it when its activity is not matched.
- A free console (`run.kind === 'console'`) already gets no skill-result badge at
  all, because it runs no skill: the precedent a discussion can follow.

### Ambiguities (worst first)

1. **What "close a discussion" is.** Stop button, closing the console, or quitting
   the CLI lead to different code paths (see findings). The ticket most likely
   means the Stop button or closing the console, which are the two paths that
   record *Cancelled*.
2. **What the ending should be called.** Either reuse `completed` ("Finished",
   green check) or introduce a dedicated neutral state ("Closed"). A new state
   touches `RUN_STATES`, the notification icons, the server activity status set
   and every `['completed','failed','canceled']` terminal check.
3. **Which icon is "the second one".** The run-state glyph or the skill-result
   badge; the fix is different for each.

### Critical dependencies

- `finish_run` accepts only `completed`, `failed`, `canceled`: a new "closed"
  status is a server-side model change (activity status, filters, web history
  counters "Annulées"), not only a Desktop change.
- `shared/runStates.ts` is shared by the Desktop row and the Desktop notification
  icon; both change together by construction.
- No migration is needed if an existing status is reused.

### Reversible choices resolved from the code

- The skill-result badge is dropped for a discussion, as it already is for a free
  console: a discussion has no skill verdict, so only the run state is shown. This
  removes the duplicated cancel glyph and the `◷` for discussions.
- Skill runs keep their current behaviour; only `skillId === "discuss"` changes.
- The wording shown to the user stays in the surface's current language.

### Product questions (with recommendation)

1. **Which action do you call "closing a discussion"?**
   - (a) *Recommended*: the Stop button **and** closing its console: both end a
     discussion normally.
   - (b) Only the Stop button.
   - (c) Something else (please describe where you clicked).
2. **How should a discussion that the user ends be reported?**
   - (a) *Recommended*: as a normal end: `completed`, green check, "Finished",
     notification "finished its turn", with no new state to propagate.
   - (b) A new dedicated neutral state "Closed" with its own icon (larger change:
     server status, web history, notifications).
   - (c) Keep *Cancelled*, but with a clearer cancel icon (e.g. an ✕ in a circle)
     and no duplicated badge.
3. **The "second icon" you did not understand - which one was it?**
   - (a) *Recommended assumption*: the small text badge next to the state
     (`⊘` / `◷` / `✓`), which is removed for discussions (see resolved choices).
   - (b) The coloured run-state glyph itself.
   If the `◷` badge also confuses you on skill runs, should it be replaced there
   too (for example by an hourglass with an explicit tooltip)? Recommended: out of
   scope here, a separate ticket.
4. **Should a discussion whose CLI exits with a non-zero code still be *Failed*?**
   Recommended: yes: a crash is not a normal close.

## Round 2 - answers from the owner (2026-09-24)

### Settled choices

1. **Closing a discussion** is both the **Stop execution** button and **closing
   its console** (orphaned PTY recovery). Both paths end a discussion normally.
2. **A discussion ended by the user is reported `completed`**: green check,
   "Finished", notification "finished its turn". No new state is introduced, so
   `finish_run`, the activity status set and the web history stay unchanged.
3. **The confusing "second icon" is the coloured run-state glyph**, not the text
   badge.
4. **A discussion whose CLI exits with a non-zero code stays `failed`.**

### Reversed or adjusted assumptions

- Round 1 assumed the confusing icon was the skill-result text badge. It is the
  run-state glyph instead. Dropping the skill-result badge for a discussion stays
  a resolved reversible choice (a discussion has no skill verdict, like a free
  console), but it no longer answers the "tick or running?" remark on its own.

### Newly surfaced question

- With answer 2, a stopped discussion will show the `completed` glyph (green
  circle with a check) instead of the grey circle with a bar. Which glyph read as
  "tick or running?" decides whether the shared `RUN_STATES` glyphs change too.
