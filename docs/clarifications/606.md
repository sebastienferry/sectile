# Clarification - #606 - The user guide explains how a workflow skill shows up in a Claude desktop session

Task: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-606`
Issue: https://github.com/sebastienferry/sectile/issues/606
Branch: `feat/606`

## Round 1 (2026-09-29)

### Restated request

Add to the user guide a description of what a workflow skill run looks like in a
Claude desktop session once #603 lands: the status emoji in the session title,
the ticket and pull request links, the project sidebar group, the chapters, the
diff pane, the next-step command and the notifications, and what happens when the
host lacks one of these or refuses it. The goal is that a user reading the
sidebar and the conversation knows why titles change and groups appear.

Out of scope: changing the skill behaviour itself (owned by #603 and
`internal/skills/fragments/contracts/session-title.md`), the reverse link from a
Sectile run to its Claude session (#602), the Sectile Desktop app's own waiting
and result indicators (already in `desktop/README.md`), and translating anything.

### What the code and docs say today (files read)

- `docs/USER_GUIDE.md` (106 lines). **Use a prompt in Claude Code** (lines 79-87)
  is three numbered steps plus one paragraph; it says nothing about session
  titles, links, groups or notifications. The guide has no images at all, and
  its sections are short task-oriented steps pointing to deeper guides.
- `desktop/README.md`: documents **Sectile Desktop**, a different application
  from the **Claude desktop app**. Its only mention of Claude sessions is the
  waiting indicator driven by the Claude Code hooks (around line 238).
- PR #603 (`feat/session-title-status-emoji`, open, not merged), in particular
  `internal/skills/fragments/contracts/session-title.md` and its three
  `CHANGELOG.md` lines under `[Unreleased] / Added`. The behaviour to document:
  - Title `<ticket ID> - <ticket title>`; a batch pickup uses
    `#47 (+2) - <title>`. No emoji while the skill works; `❓` while it waits for
    the owner or stops on open questions, `✅` once it reached its goal, `❌` when
    it stops on a failure or blocker.
  - A `Ticket:` line right after the rename (Jira, GitHub, GitLab), a `PR:` line
    once a pull or merge request exists. A GitHub pull request is also bound to
    the session's PR bar; on GitLab the line is the only link.
  - Sidebar group named after the Sectile project (reused, created only if
    missing); a chapter when the skill starts in a session with earlier work,
    one chapter per stage under a pickup; the diff pane after implement, adjust
    or pickup changed code (else the worktree path is named); the next step's
    command at the end (`/sectile:<skill>` when installed as a plugin); one
    notification on `❓`, `✅` or `❌`.
  - Nested stage skills under a pickup leave all of this to the pickup.
  - Any agent: uses whatever renaming capability it exposes; every item is
    skipped silently when absent or refused, and never blocks the skill.
- `README.md` line 95: plugin skills run as `/sectile:clarify-issue`.

### Ambiguities (worst first)

1. **Placement.** A subsection of **Use a prompt in Claude Code**, a new
   top-level section, or `desktop/README.md` lead to different files and a
   different table of contents.
2. **Timing relative to #603.** Documenting behaviour that is not on `main`
   makes the guide wrong until #603 merges; folding the text into #603 instead
   changes which pull request carries it.
3. **Screenshots.** Adding images means a new asset folder and upkeep whenever
   the Claude desktop app changes its UI.

### Dependencies

- **#603 must merge first** for the guide to describe `main`. Nothing else: no
  migration, no service, no data.
- The Claude desktop app's sidebar, chapter, pane and notification tools are
  third-party; the guide should describe what the skill does, not how the app
  renders it, so an app redesign does not stale the page.

### Reversible technical choices, settled from conventions

- **Form:** prose plus one short table for the three emojis (meaning and when
  each appears), matching the guide's plain style. UI names in bold, no French
  translations needed since these are Claude app surfaces, not Sectile ones.
- **Other CLIs and refusals:** one paragraph: the skills behave the same in any
  CLI but use only what the host exposes; in a terminal or another CLI the
  title may stay unchanged and only the conversation lines remain; a refused
  rename, binding or move is skipped and the run continues.
- **Nested pickup:** one sentence saying the pickup owns the title, links and
  chapters, with one chapter per stage, and the batch title form.
- **Next step:** mention the `/sectile:<skill>` form for plugin installs,
  linking to the README's plugin paragraph rather than repeating it.
- **Sectile Desktop link:** one sentence pointing to the Desktop guide for the
  distinct Sectile Desktop indicators, to keep the two apps apart.
- **Changelog:** no new line. #603 already adds three user-facing lines for the
  feature; this is documentation of that feature, not a new change.

### Open product questions

1. **Where does the text go?** Recommended: a subsection
   `### What the session shows` at the end of **Use a prompt in Claude Code**.
   It is where the reader already is when running a skill there; the Desktop
   guide documents Sectile Desktop, a different app, and putting Claude desktop
   behaviour there would blur the two.
2. **Wait for #603?** Recommended: write it on `feat/606` now and open the pull
   request only once #603 is merged (rebasing on `main`), so `main` never
   documents behaviour it does not have. Alternative: add the section to #603
   directly and close #606 with it.
3. **Screenshots?** Recommended: none. The guide has no images, the Claude
   desktop app's UI is not ours and changes independently, and the repository is
   public, so captured sidebars risk showing unrelated sessions or internal
   names. The emoji table carries the information a screenshot would.

## Round 2 - answers from the owner (2026-09-29)

Answers given in session to the round 1 questions:

1. **Placement: settled** as recommended. A subsection
   `### What the session shows` at the end of **Use a prompt in Claude Code**
   in `docs/USER_GUIDE.md`. `desktop/README.md` is not changed.
2. **Timing: settled** as recommended. The text is written on `feat/606` now.
   The pull request is opened only once #603 has merged, after merging
   `origin/main` into `feat/606`. If #603's wording changes before it merges,
   the guide follows the merged contract.
3. **Screenshots: yes. This reverses the round 1 recommendation.** The guide
   gets its first images.

### Consequences of the reversal

- **Storage, settled:** PNG files under `docs/images/user-guide/`, referenced
  by relative path from `docs/USER_GUIDE.md`, each with alt text that says what
  the image shows. The emoji table stays, so the guide still reads without the
  images, for screen readers and plain-text viewers.
- **Public repository constraint:** every capture must show only a demo project
  and demo tickets. No internal project names, hosts, e-mail addresses, other
  sessions or unrelated sidebar groups.
- **Upkeep:** the Claude desktop app's UI is third-party and will change; the
  images are expected to go stale before the text does. The text stays the
  reference and the images illustrate it.

### Open product questions

4. **Which captures?** Recommended: two. (a) The sidebar with the project group
   holding three sessions titled with ❓, ✅ and ❌. (b) The top of a
   conversation showing the `Ticket:` and `PR:` lines, with the PR bar bound to
   a GitHub pull request. Chapters, the diff pane and notifications are
   described in text only.
5. **Who produces them?** Recommended: the owner captures them on a demo
   project and hands the files over (the agent cannot reliably drive and capture
   the Claude desktop app, and the capture has to be checked for private
   content anyway). The implementation then adds the files and the references.
   Alternative: the agent draws mock-ups of the two views, which avoid any
   privacy risk but imitate a third-party UI and drift from it.
