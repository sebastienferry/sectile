## Round 1 (2026-09-26)

### Restated request and scope

The ticket asks for several code directories to be attached to a project in the
desktop project settings of a workstation, and for those directories to be
passed to skill executions as context. A large part of this was delivered by
#456 (ADR 0028) the day the ticket was written, so this clarification first
settles what #484 adds on top of it.

Out of scope, whatever the answers: changing how the primary repository of a
ticket is resolved, the pull request rules for changed repositories, and the
specifications folder (ADR 0027), all settled by #456 and #443.

### What already exists (verified on `origin/main`, f8f913f2)

- A multi-repo project (`monoRepo=false`) lists its repositories by remote on
  the server (`projects.repositories`), edited in the **web** project settings.
- The desktop project settings show an *Other repositories* row, only for a
  multi-repo project, with one folder field per repository the web declared
  (`desktop/src/main.js:1648`). The desktop cannot add or remove a repository;
  it only maps a known remote to a folder, stored in
  `~/.config/sectile/settings.json` under `repositories`
  (`internal/agentconfig/local.go:28`). A folder is accepted only if its
  checkout's `origin` is that repository.
- Every launch receives a folder map, built by the local agent
  (`buildFolderMap`, `internal/agent/repositories.go:111`): each repository with
  its role (primary, changed, context, spec), its folder and the ticket's
  worktree. It reaches the agent in `SECTILE_REPOSITORIES`
  (`internal/agent/agent.go:1177`) and in the prompt (`folderMapPrompt`), and
  Claude also gets the context folders as `--add-dir` (`addDirArgs`,
  `internal/agent/agent_config.go:513`). Other providers get no flag; the
  `{addDirs}` template placeholder expands to nothing for them.
- A context repository becomes writable only through
  `prepare_repository_worktree`, which requires a remote and leads to a pull
  request per changed repository.

### What the ticket asks that does not exist yet

1. **Mono-repo projects get nothing.** The *Other repositories* row is hidden,
   and the folder map holds only the code checkout (and the specifications
   folder when it is separate). A mono-repo project that wants a sibling
   library, a design-system checkout or a documentation folder as context has
   no way to declare it.
2. **The declaration is on the web, not on the desktop.** A folder only exists
   on the workstation, yet the list of repositories is a server setting that
   the desktop cannot extend.
3. **Only Git checkouts with a matching `origin` qualify.** A plain folder, or
   a checkout whose remote is not one of the project's, cannot be attached.
4. **Only Claude receives the folders as directories.** Codex and vibe see
   them in the prompt and the environment variable only.

### Ambiguities (worst first)

1. **Is #484 a new, workstation-only list of context folders, or is it covered
   by #456?** The first adds a list stored locally, per project, with no remote
   and no server record; the second closes the ticket or narrows it to a UI
   change. Different data model and different code. → Q1.
2. **Which projects and which folders.** Mono-repo only, or every project; Git
   checkouts only, or any folder. → Q2.
3. **Whether an attached folder can ever be written.** Read-only context by
   instruction (as #456 context repositories), or also worktrees and pull
   requests, which need a remote. → Q3.
4. **Which providers get the folders as CLI directories.** → Q4.

### Reversible technical choices (settled from the code and conventions)

- An attached folder is a workstation setting, stored in the project section of
  `~/.config/sectile/settings.json` (layout 2, ADR 0031), written only by the
  agent and edited by the desktop through it. The server never receives a
  path (ADR 0003, ADR 0028).
- The folders join the existing folder map with a role of their own (for
  example `extra`), so `SECTILE_REPOSITORIES`, the prompt block and
  `folderMapDirs` carry them without a second channel. A folder already in the
  map (the code checkout, a mapped repository, the specifications folder) is
  refused or deduplicated rather than listed twice.
- A missing folder at launch is reported in the map as not found and skipped,
  never a launch failure: the map describes the launch, it never decides it
  (as `taskFolderMap` already does).
- A new setting key needs the merge in `localProjectRoot` and the nulling of an
  emptied list in `WriteSettings` (known trap of #443).
- The desktop row reuses the existing folder picker (`api.chooseRepository`)
  and list layout of *Other repositories*.

### Critical dependencies

- No server schema change if the list stays local; the agent and the desktop
  change together, which they already do.
- CLI support: Claude has `--add-dir`. Codex's equivalent must be checked
  against a current release before being relied on (not installed here); vibe
  has no known flag.
- The desktop UI tests load `dist/index.html`, so they need a build.

## Round 2 - answers from the owner (2026-09-26)

Answers given interactively in the session.

### Settled decisions

- **Q1 What #484 adds:** a new list of *context folders*, per project,
  declared only in the desktop project settings, stored on the workstation and
  never sent to the server. No remote is required to attach one. The folders
  join the folder map handed to the skills.
- **Q2 Eligibility:** every project, mono-repo and multi-repo alike, and any
  folder: a Git checkout or a plain folder, detected and shown the way the
  specifications folder is (ADR 0027).
- **Q3 Writing:** an attached folder that is a Git checkout can be changed
  through a worktree on the ticket's branch and then needs its own pull
  request, like a changed repository of #456. This needs a remote.
- **Q4 Providers:** Claude keeps `--add-dir`; Codex gets its equivalent once
  the flag is verified on a current release; vibe gets the prompt block and
  `SECTILE_REPOSITORIES` only.

### Reversed or refined assumptions

- Round 1 treated attached folders as read-only context. Q3 makes a Git one
  writable through a worktree and a pull request.

### Newly surfaced conflicts with the existing code

Q1 (the server knows nothing of an attached folder) and Q3 (a changed
repository needs its pull request) meet three guards of #456:

1. `PrepareRepositoryWorktree` (`internal/db/repositories.go:328`) refuses a
   repository the project does not declare, and refuses every mono-repo
   project (`repositories.go:343`). The agent side refuses the same two cases
   (`repositoryWorktree`, `internal/agent/repositories.go:340`).
2. `taskChangedRepositories` (`internal/db/repositories.go:125`) ignores a
   changed repository that is not a project repository, and returns nothing
   for a mono-repo project, so its pull request would never be required nor
   checked by the stage transitions (`internal/db/stageprs.go`).
3. A plain folder, or a checkout without `origin`, has no remote and cannot
   carry a pull request.

These are settled in round 3.

## Round 3 - answers from the owner (2026-09-26)

Answers given interactively in the session, after the first wording of the
pull request question was explained with an example (a mono-repo project
`acme/app` with an attached checkout of `acme/ui`).

### Settled decisions

- **Q5 A Git folder with a remote the project does not declare:** when the
  agent must change it, its remote is **added to the project's repositories**
  on the server (`projects.repositories`). A mono-repo project then becomes a
  multi-repo one. From there on it is an ordinary repository of #456: mapped on
  the workstation to the attached folder, worktree on the ticket's branch, its
  own pull request required and checked by the transitions.
- **Q6 A folder without a remote** (plain folder, or checkout without
  `origin`): the agent may **write in place**, with no worktree and no pull
  request. The transitions check nothing there.

### Consequences to confirm (round 4)

- Turning a mono-repo project into a multi-repo one changes behaviour for the
  whole team, not only for the workstation that attached the folder:
  - the primary repository of a ticket is no longer the code repository by
    default: an unpinned ticket, launched on a workstation that maps more than
    one repository, waits for a choice (ADR 0028, resolution order);
  - macro operations no longer inherit the code checkout as the
    specifications folder and refuse to run until one is set (ADR 0027);
  - the web shows the project as multi-repo.
- Adding a repository to a project is a write to a shared project setting,
  today done from the web project settings only.
- Writing in place in a folder without a remote leaves no reviewable trace:
  no branch, no pull request, and no undo other than the user's own.

## Round 5 - answers from the owner (2026-09-26)

Answers given interactively in the session, after a worked example
(`acme/app` with `~/src/acme-ui` and a plain `~/notes/acme` attached) and an
explanation of why the server records the repositories a ticket changed.

### Settled decisions

- **Q9 Attaching is manual, writing is on demand.** The owner attaches folders
  by hand in the desktop project settings. Every attached Git folder with a
  remote is writable: the agent asks for a worktree in it through
  `prepare_repository_worktree` when a ticket must change it.
- **Q10 The server never learns an attached folder, and the project's
  repository list is untouched.** This **reverses round 3 Q5** ("the remote is
  added to the project's repositories"). When a worktree is prepared in an
  attached Git folder, the server records only that repository's identity
  (`host/path`, never a path) on the ticket, in `tasks.changed_repositories`,
  as #456 does. `projects.repositories` stays as the list a ticket can be
  pinned to from the web.
- **Q11 Forgotten pull requests are detected on the server.** The transitions
  that require pull request evidence refuse a ticket whose changed
  repositories, attached folders included, lack a pull request. The pull
  requests attached to a ticket say what was submitted; the changed
  repositories say what should have been, and are visible from the web, from
  another workstation and to the handoff cleanup.
- **Q12 The "choose a repository" wait of #456 is removed.** Without the flag,
  an unpinned ticket's primary repository is always the code repository. No
  launch parks on `waiting_reason='repository'`; the desktop console picker
  goes away. Pinning a ticket to another repository stays, from the ticket
  detail, before launching.
- **Q13 Instructions live in the local agent, not in the skills.** The skills
  are in a shared Claude Code marketplace plugin. The rule for attached
  folders (work in the primary worktree; call `prepare_repository_worktree`
  before changing an attached Git folder; a folder without a remote may be
  changed in place) is carried by the folder map block the local agent adds to
  the prompt (`folderMapPrompt`) and by the description of the
  `prepare_repository_worktree` MCP tool. No change to the plugin is required
  for #484 to work.
- The owner confirmed the clarification is satisfactory.

### Reversible technical choices (settled)

- `prepare_repository_worktree` accepts, beside a project repository, the
  identity of a folder attached on the caller's workstation. The server cannot
  check that folder: it relays the request to the caller's agent, which
  refuses an identity it neither maps nor has attached, and records the
  identity on the ticket only when the agent answers with a worktree.
- `taskChangedRepositories` stops filtering on the project's repository list:
  every identity recorded on the ticket, other than the primary one, needs its
  pull request.
- An attached Git folder whose `origin` is already a project repository is the
  same repository: it is stored as that repository's mapping, not listed
  twice.
- The folder map gains the attached folders, with their identity when they
  have a remote, their kind (Git checkout or plain folder) and a role that
  says whether a worktree or in-place writing applies.
- Codex receives the folders as additional directories once its flag is
  verified against a current release during the specification; until then it
  gets the prompt block and `SECTILE_REPOSITORIES` only, like vibe.
- One ADR records the removal of the flag, the attached folders and the
  ticket-level record of changed repositories, superseding ADR 0027 and ADR
  0028 in part.

## Settled scope (final)

### Request

Let a workstation attach any number of code folders to any project, by hand,
in the desktop project settings, and hand them to every skill execution as
context. Attached Git folders become writable through a worktree and a pull
request when a ticket needs them; plain folders are writable in place. The
mono-repo/multi-repo distinction disappears.

### Out of scope

- Any change to the skills of the shared marketplace plugin. Their sentence
  "On a multi-repo project, `$SECTILE_REPOSITORIES` lists the task's folders"
  becomes inaccurate once the flag is gone; updating it is left to the
  plugin's owner.
- Sharing attached folders between workstations or with the server.
- Enforcing read-only access; context folders stay read-only by instruction
  only, as in #456.

### Acceptance criteria (for the specification)

1. The desktop project settings list the attached folders of the project on
   this workstation, for every project; a folder can be added with the folder
   picker and removed. Each shows whether it is a Git checkout (with its
   remote) or a plain folder, or that it is missing.
2. Attached folders are stored only in `~/.config/sectile/settings.json`; no
   request to the server carries a path.
3. Every launch lists the attached folders in `SECTILE_REPOSITORIES` and in the
   prompt folder map; Claude receives them as `--add-dir`, Codex too once its
   flag is verified. A missing folder is reported in the map and does not fail
   the launch.
4. A skill can call `prepare_repository_worktree` for an attached Git folder
   with a remote; the local agent creates or reuses the ticket's worktree on
   `feat/<n>` in it, and the server records the identity on the ticket.
5. The `implemented` and `adjust` transitions are refused when a changed
   repository recorded on the ticket, attached folder included, has no pull
   request whose head matches its worktree.
6. The prompt folder map tells the agent that a folder without a remote may be
   changed in place, with no worktree and no pull request.
7. The mono-repo/multi-repo flag is gone from the model, the database (a
   numbered migration for SQLite and PostgreSQL), the web project settings,
   the desktop settings and the agent configuration. A ticket's primary
   repository is the code repository unless the ticket is pinned to another
   project repository.
8. No launch waits for a repository choice any more; the desktop console
   picker and the parking of a run are removed.
9. The specifications folder of every project defaults to its code checkout
   unless the desktop sets another one.
10. Handoff removes the ticket's worktrees in every changed repository,
    attached folders included, where they are on this workstation.
11. `CHANGELOG.md` gets an entry under `[Unreleased]` (user-visible change),
    including the removal of the *Mono-repo* setting.
12. An ADR records the decision and supersedes ADR 0027 and ADR 0028 in part.
