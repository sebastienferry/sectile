# Clarification #741 - Change Tracker vs Project in Sectile

## Round 1 (2026-10-05)

### Request

A tracker (a Jira space such as `GODE`, a GitHub repository, a GitLab project)
becomes a server-level source that Sectile synchronises in full, whatever
projects use it. A Sectile project stands for an application (its
repositories, rules and skills) and shows the subset of tickets of one or more
trackers that carry the project's label: `delivery-admin` tickets from `GODE`
and `BE`, `bidder-admin` tickets from `GODE`.

Out of scope: label expressions beyond one label per project (ALL-of,
exclusions, JQL), project memberships or permissions (ADR 0018: everyone sees
every project), changing how stages are carried on the tracker (ADR 0013),
and the personal saved views of ADR 0025, which keep working over the new
model.

### The reading this report recommends

Everything in this ticket hangs on one choice: **who owns the local record of
a remote ticket**.

- **Tracker-owned (recommended).** One local record per remote ticket, keyed
  by its tracker. A project is a selector (trackers + label) over those
  records. Stage, pull requests, activities and pins exist once per ticket.
- **Project-owned with a label filter.** Today's model plus a hidden-by-label
  rule. This is exactly PR #354, closed in favour of #387: ADR 0025 records
  that when several projects synchronise one tracker scope "each keeps its own
  local record", and that "a fix belongs to how projects share a tracker
  scope, not to the view". It also keeps two projects polling the same Jira
  space.

The ticket's own wording ("the backend should sync any and all tickets of the
GODE board ... projects show a subset") is the tracker-owned reading. The rest
of this report assumes it; question 1 confirms its main consequence.

### What the code does today (files read)

- `internal/models/models.go:116-229` (`Project`): the tracker coordinates
  (`IssueTracker`, `TrackerUrl`, `JiraProject`, `GithubRepo`, `GitlabUrl`,
  `GitlabProject`), the board mirror (`BoardID`, `TrackerColumns`,
  `StageColumns`, `Sprints`, `IssueTypes`), `RoadmapProjects` and
  `AutoSyncEnabled` / `AutoSyncIntervalMin` all sit on the project.
  `Task` (`models.go:883-959`) stores no tracker coordinates.
- `internal/db/db.go:435-519`: `tasks` is `UNIQUE(project_id, key)`; the
  import dedups on `WHERE project_id = ? AND (key = ? OR id = ?)`
  (`db.go:1001`).
- Task IDs embed the project: `gh-<projectId>-<n>`, `jira-<projectId>-<KEY>`,
  `gl-<projectId>-<n>` (`FormatTaskID`, `internal/tracker/ticketing.go:39`,
  `internal/trackerapi/adapters.go:241`, `jira.go:100`, `gitlab.go:97`), and
  several places parse them back (`cleanJiraKey` in `jira_mapping.go:341`,
  `gitlab_mapping.go:174`, `registry.go:81`, `macros.go:1517,1639`).
  `GetTaskByID` falls back to `WHERE key = ? LIMIT 1`, already ambiguous
  across projects.
- Sync is per project: `runAutoSyncPass` (`internal/db/autosync.go:180-253`)
  and `processSyncJob` (`db.go:4498-4700`) call `SyncIssues` with the project,
  then stamp `ProjectID` and `FormatTaskID(p.ID, ...)` (`db.go:4554-4557`).
  `afterTrackerSync` refreshes board columns, sprints, teams, macro horizons
  and PRs per project. Jira reads `project = "<JiraProject>" AND issuetype IN
  (...)` (`jiraJQL`, `jira_mapping.go:315-330`); no tracker reads by label.
- Write-back resolves the tracker from the task's project:
  `Registry.ForProject` / `ForTask` (`internal/tracker/registry.go:41-90`),
  `runStageOp` (`internal/db/trackerops.go:822-924`), and for GitHub
  `resolveGithubRepo(req.Project)` (`adapters.go:123`) in `CreateIssue`,
  `UpdateIssue`, `AddComment`, `GetComments`. A GitHub task row only knows
  `#42`: that is the hardest 1:1 coupling.
- `CreateTaskAs` (`db.go:2501-2627`) takes tracker and scope from the project;
  the MCP `create_task` requires `projectId` (`internal/taskmcp/server.go:509`).
- Credentials are already per provider on the server (ADR 0028 tracker-sync,
  0029; `internal/db/trackercredentials.go:31-72`); a project only overrides
  site URLs.
- Macros are keyed `(project_id, key)` (`internal/db/macros.go:79-91`);
  `sameTrackerInstance` (`internal/db/trackerinstance.go:49-93`) already
  compares project tracker coordinates; `macrohorizons.go` assumes the
  project's Jira prefix.
- Sync never removes a ticket that leaves its scope: the only
  `DELETE FROM tasks` are the user delete paths (`db.go:3388,3394`) and a
  reset (`db.go:950`). Under the tracker-owned model, losing the label only
  changes project membership, so this is not blocking.
- Neighbouring features: multi-repository projects keyed by remote identity
  (`internal/models/repository.go:79-100`, ADR 0028 repositories, ADR 0036),
  saved views by label (ADR 0025, `db.go:1281-1301`), declared roadmap
  projects (ADR 0043, `internal/db/roadmapprojects.go:124-133`).
- Web: tracker settings live in `web/src/components/ProjectModal.tsx:200-466`
  and `SyncView.tsx:45-80`; Desktop has no tracker fields.
- Macro M-8 (parent) carries no todos that slice this work.

### Ambiguities (worst first)

1. A ticket carrying two application labels: one shared record or one per
   project, and which project's repositories an agent run uses. (Question 1.)
2. Tickets of a tracker that carry no project label: invisible or shown
   somewhere. (Question 2.)
3. A project with no label: all tickets of its trackers, or none.
   (Question 3.)
4. Where a ticket created from a project goes when the project reads several
   trackers. (Question 4.)
5. Whether epics/macros belong to the tracker or the project. (Question 5.)
6. How much of this one story delivers. (Question 6.)

### Dependencies

- **Schema migration 47** on SQLite and PostgreSQL (ADR 0021): a `trackers`
  table, the project-to-tracker link, task rows rekeyed by tracker, merge of
  duplicate rows that two projects hold today for the same remote ticket,
  rewrite of every reference to a task ID (activities, PR links, pins, batch
  members, macros, worktree records).
- **MCP / agent contract**: `get_project_context` exposes `jiraProject` and
  the tracker; `create_task` needs a target tracker; `list_tasks` filters by
  project; `SECTILE_TASK_ID` and worktree naming carry today's IDs.
- **Web**: a new admin "Trackers" screen; `ProjectModal` loses its tracker
  fields for a tracker list and a label; `SyncView` becomes per tracker.
- **ADRs**: a new ADR for the tracker/project split; ADR 0025 (its
  "duplicates are shown" consequence disappears) and ADR 0043 (roadmap
  projects are likely subsumed by "a project reads several trackers") are
  amended or superseded.
- **Jira**: reading the whole space instead of filtering per project changes
  the sync volume per pass, not the number of passes (one per tracker instead
  of one per project). GitHub and GitLab labels are already read.
- `CHANGELOG.md` (user-visible, breaking for deep links if old IDs were not
  kept resolvable).

### Technical choices settled from the code (reversible)

1. **A tracker entity** holds the provider, the site, the scope (Jira project
   key, GitHub `owner/repo`, GitLab project path), the board mirror now on
   `projects` (`BoardID`, `TrackerColumns`, `StageColumns`, `Sprints`,
   `IssueTypes`) and the auto-sync settings. Status-to-stage mapping is
   therefore per tracker.
2. **A project references N trackers by stable identity**, following the
   `ProjectRepository{URL, Identity}` pattern of ADR 0028, plus one label.
3. **The sync loop runs per tracker** (`auto_sync_projects` becomes per
   tracker); one pass imports every ticket of the scope once.
4. **Task identity is the tracker's**: new IDs keyed by tracker (for example
   `jira-<trackerId>-GODE-12`, `gh-<trackerId>-741`), `UNIQUE(tracker_id,
   key)`. Write-back (`Registry.ForTask`, `resolveGithubRepo`, `runStageOp`,
   comments) resolves from the task's tracker, which retires the
   `#` / `gh-` key heuristics. Existing IDs stay resolvable as aliases so
   links, branches and worktrees keep working.
5. **Membership is computed, not stored**: a ticket is in a project when it
   comes from one of the project's trackers and carries its label, matched
   with ADR 0025's whole-token, ASCII-folded predicate. Removing the label on
   the tracker removes the ticket from the project at the next sync; nothing
   is deleted.
6. **Migration of existing data is behaviour-preserving**: each distinct set
   of tracker coordinates (`sameTrackerInstance`) becomes one tracker; each
   existing project references it with no label (see question 3); rows that
   two projects held for one remote ticket are merged, keeping the most
   advanced stage and the union of PR links and activities.
7. **Credentials do not change**: the server credential per provider and the
   personal credentials for writes a person causes (ADRs 0014, 0028, 0029,
   0044) already fit a server-level tracker.

### Product questions (open)

1. **A ticket with two application labels** (`delivery-admin` and
   `bidder-admin`): is it one shared record shown in both projects, with one
   stage, one set of PRs and one activity history?
   *Recommended:* yes, one shared record. When an agent run starts on such a
   ticket, the run asks which project (hence which repositories, rules and
   skills) it works for; the PRs it opens are recorded on the shared ticket.
   *Alternative:* first matching project wins, the ticket appears in one
   project only.
2. **Tickets of a tracker without any project label**: where are they seen?
   *Recommended:* in a per-tracker backlog view ("not in a project"), from
   which a ticket can be given a project label (written back to the tracker).
   *Alternative:* not shown anywhere in Sectile.
3. **A project with no label**: does it show every ticket of its trackers?
   *Recommended:* yes. It keeps today's GitHub "one repository = one project"
   setup (this repository) working unchanged, and makes the migration a
   no-op for existing projects. The label is never mandatory: two unlabelled
   projects on one tracker simply show the same tickets.
   *Alternative:* a project without a label shows nothing, and every project
   must declare one.
4. **Creating a ticket from a project that reads several trackers**: where
   is it created?
   *Recommended:* the project declares a default tracker for creation (the
   first one by default); the creation form lets the user pick another of the
   project's trackers; the project's label is always added, next to `#new`.
5. **Epics / macros**: does a Jira epic of `GODE` belong to the tracker or to
   a project?
   *Recommended:* to the tracker (one record, like tickets). A project shows
   an epic when the epic carries its label or when at least one of the
   epic's children belongs to the project. GitHub/GitLab local `M-<n>`
   macros, which have no tracker counterpart, stay owned by their project.
6. **Scope of this story**: one model for Jira, GitHub and GitLab delivered
   under #741, or Jira first?
   *Recommended:* one generic model for the three providers (the coupling
   points are shared code, and a Jira-only model would leave two ID schemes),
   delivered in several pull requests on this branch if needed: (a) tracker
   entity + migration + per-tracker sync, (b) label membership + multi-tracker
   projects + creation, (c) web settings and admin screen. Splitting into
   child stories under M-8 is the alternative if you want each part tracked.

## Round 2 - answers from the owner (2026-10-05)

The owner answered the six questions interactively, each with the recommended
option. The tracker-owned reading is confirmed.

### Settled decisions

1. **One shared record per remote ticket.** A ticket carrying two project
   labels appears in both projects with one stage, one set of pull requests
   and one activity history. (Q1)
2. **Unlabelled tickets live in a per-tracker backlog** ("not in a project"),
   from which a ticket can be given a project label, written back to the
   tracker. (Q2)
3. **A project's label is optional.** A project without a label shows every
   ticket of its trackers; two unlabelled projects on one tracker show the
   same tickets. Existing projects migrate with no label and no visible
   change. (Q3)
4. **Creation goes to the project's default tracker**, the first one unless
   the project names another; the creation form (web and MCP `create_task`)
   accepts another of the project's trackers; the project's label is always
   added next to `#new`. (Q4)
5. **Epics are tracker records.** A Jira epic exists once per tracker and
   shows in a project when it carries the project's label or when at least
   one of its children belongs to the project. GitHub/GitLab local `M-<n>`
   macros, which have no tracker counterpart, stay owned by their project.
   (Q5)
6. **One generic model for Jira, GitHub and GitLab, delivered under #741.**
   Several pull requests on `feat/741` are allowed; no child stories. (Q6)

### Reversed assumptions

None. Every Round 1 recommendation stands.

### Ambiguities surfaced by the answers, settled from the code (reversible)

1. **Which project a run works for when its ticket belongs to several.** A run
   launched from a project's board, or with a `projectId`, works for that
   project. A run launched without one (all-projects board, saved view, a
   bare task key over MCP) on a ticket with several projects asks for the
   project interactively and is refused in an unattended pickup, with the
   list of candidate projects in the error. A ticket with exactly one project
   needs no choice. The chosen project is recorded on the run, so its
   activities and the pull requests it opens name the repository they belong
   to, as `ChangedRepositories` already does.
2. **Labelling from the backlog** reuses the existing label write path of each
   adapter (GitHub labels, Jira labels, GitLab labels); the ticket enters the
   project at once locally, without waiting for the next sync.
3. **The default tracker** is stored on the project as a tracker identity;
   removing that tracker from the project falls back to the first remaining
   one.
