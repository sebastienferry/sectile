## Round 1 (2026-09-23)

### Restated request and scope

When a project has no recorded `BoardID`, the board picker in the project settings pre-selects the first scrum board. Confirming that
pre-selected board from the picker must persist it on the project and import its columns, exactly as choosing a different board does.

Out of scope: changing how the default board is resolved (`pickBoardId` / `resolveBoardID`), the "Détecter les statuts" flow, the
tracker sync, and any server-side change to `POST /api/projects/{id}/board-columns`.

### Verified findings

- `pickBoardId` returns `project.boardId` when it is known, otherwise the first scrum board, otherwise the first board. The client and
  `resolveBoardID` on the server agree, so the pre-selected board is the one the sync would use anyway.
- `handleBoardChange` returns early when `nextBoardId === boardId`, where `boardId` is the *displayed* selection, not the persisted
  `project.boardId`.
- **More important than the early return:** the picker is a native `<select>`. Browsers emit no `change` event when the user picks
  the option that is already selected. Removing the guard alone therefore fixes nothing: `handleBoardChange` is never called for
  the pre-selected board. The fix needs an interaction that actually produces an event (see Q1).
- The server already accepts this case: `ImportProjectBoardColumns` writes `BoardID` whenever it differs from the stored value
  (empty → chosen), then runs the same sync as "Détecter". No backend change is needed.
- The sync itself persists the resolved `BoardID` (`board.go` l. 472-477), which is why the pre-selection "lands" today through
  "Détecter" or the next sync.

### Ambiguities (worst first)

1. **Which interaction confirms the pre-selection.** Because the `<select>` cannot emit a change for the current option, "confirm from
   the picker" has several readings that lead to different code (product question Q1).
2. **Guard semantics.** Should the guard compare against the persisted `project.boardId` rather than the displayed `boardId`? Resolved
   below as a reversible technical choice.

### Resolved technical choices (reversible)

- The "unchanged" guard compares the chosen board with the persisted `project.boardId`, not with the displayed selection: re-importing
  a board that is already recorded stays a no-op; choosing a board when none is recorded always imports.
- The import goes through the existing `importProjectBoardColumns` call; no new endpoint, no server change.
- On failure the picker reverts to `pickBoardId(boards, project.boardId)`, as today.
- A regression test covers the guard decision with the existing `node --test` suite (`web/tests/boardColumns.test.mjs`), by extracting
  the decision into a small pure helper in `web/src/lib/boardColumns.ts`, matching how `pickBoardId` is tested.

### Critical dependencies

None: the endpoint and the persistence already handle the empty → chosen transition. Only trackers exposing boards (Jira today) show
the picker.

### Product questions

**Q1. How does the user confirm the pre-selected board?**

- **A (recommended).** While the project has no recorded board, the picker starts on a placeholder option ("Choisir un board…") and the
  suggested board is labelled "(suggéré)" in the list. Choosing any board, the suggested one included, fires a real change and imports
  it. Once a board is recorded, the placeholder disappears and the picker behaves as today. Keeps the fix inside the picker, as the
  ticket asks.
- **B.** Keep the pre-selection displayed and show a "Retenir ce board" button next to the picker while no board is recorded.
- **C.** Persist the pre-selected board automatically when the settings open, without any user action.
