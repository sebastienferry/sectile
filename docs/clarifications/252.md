## Round 1 (2026-09-23)

### Restated request and scope

`MarkdownToADF` must keep a list item whose text continues on an indented line (after a blank line or not) as one `listItem`, instead of closing the list, emitting a top-level paragraph and opening a second list. Out of scope: the GitHub tracker (it sends raw Markdown), the inline parser, tables, headings and every other block type outside lists, and any change to how Jira validates or rejects payloads.

### Verified findings

- The defect has two triggers in `parseMarkdownList` (`internal/trackerapi/adf.go:195`):
  - after a blank line, the list only continues when the *next* line is a list marker (`adf.go:206`); `  continued` is not, so the list ends;
  - a non-blank, non-marker line ends the list unconditionally (`adf.go:214`), so `- a\n  continued` (no blank line) is split the same way.
- The caller hands the list its own indent (`adf.go:142`, the #180 fix); nested lists are hung under the previous item (`adf.go:221-233`). Both behaviours must survive.
- ADF constraint kept from #180: a `listItem` must start with a `paragraph`. Allowed later children are `paragraph`, `bulletList`, `orderedList`, `codeBlock` and `mediaSingle`; `heading`, `blockquote`, `table` and `rule` are **not** valid inside a `listItem`.
- `MarkdownToADF` is used for Jira descriptions on create/update and for comments (`jira.go:221`, `:351`, `:564`). `ADFToMarkdown` is used when reading Jira issues and comments back (`jira.go:601`, `jira_mapping.go:202`), so a description goes Jira → Markdown → Jira on every edit.
- The reverse renderer `renderADFList` (`adf.go:407`) writes a second paragraph of an item as `  text` on the very next line with no blank line, and only indents the first line of a multi-line child (e.g. a code block). A multi-paragraph item created in Jira therefore comes back as Markdown that today's parser splits into three blocks, and that the fixed parser would read as one paragraph with a hard break (see Q3).
- `inlineLines` (`adf.go:177`) joins the lines of a paragraph with `hardBreak`: reports are written for GitHub and rely on single newlines being visible.

### Ambiguities (worst first)

1. **What a continued item may contain.** Paragraphs only, or also fenced code blocks (common in agent-written reports: `- step\n\n  ```sh\n  cmd\n  ```\n`)? The two readings produce different code (recursive block parsing vs. paragraph accumulation). → Q1.
2. **Unindented (lazy) continuation.** `- a\ncontinued` — GitHub/CommonMark render it as one item; the ticket only mentions indented lines. → Q2.
3. **Round trip.** Whether the reverse direction is fixed in the same change, so a multi-paragraph item survives Jira → Sectile → Jira. → Q3.
4. **Indent threshold** ("indented at least as far as the current item"): the marker column or the content column? Resolved below as a reversible technical choice.

### Resolved technical choices (reversible)

- **Threshold = the item's content column** (marker indent + marker + following spaces: 2 for `- a`, 3 for `1. a`), which is the CommonMark rule GitHub applies. A line indented to that column after a blank line belongs to the item; a less-indented non-marker line ends the list as today. This also decides nesting correctly: under `  - x`, a paragraph at column 2 belongs to the outer item, at column 4 to `x`.
- **Blank-line-separated continuation → a new `paragraph` in the same `listItem`**; continuation without a blank line → appended to the item's current paragraph with a `hardBreak`, consistent with `inlineLines`.
- The item's first child remains its marker-line paragraph, so the #180 invariant (a `listItem` starts with a `paragraph`) holds by construction.
- A deeper list marker after a continuation paragraph still nests under the same item (existing rule unchanged).
- Tests go in `internal/trackerapi/adf_test.go`, next to `TestAnIndentedListIsNotNestedUnderAnEmptyBullet`, with the ticket's example (`- a\n\n  continued\n- b` → one `bulletList`, first `listItem` = two paragraphs, second = `b`) plus the no-blank-line, ordered-list and nested-list variants. The existing tests must keep passing.

### Critical dependencies

- None external: no migration, no other service, no new library. Only the Jira ADF schema constraints listed above.
- Jira is the only consumer; GitHub is unaffected.

### Product questions

1. **Q1 — Fenced code blocks inside an item.** Should a fenced code block indented under an item become a `codeBlock` inside that `listItem`?
   *Recommendation: yes — paragraphs and fenced code blocks (both valid ADF children). Anything ADF forbids inside an item (heading, table, blockquote, rule) keeps ending the list, as today.*
2. **Q2 — Unindented lazy continuation.** Should `- a\ncontinued` (no blank line, no indent) join the item like GitHub renders it?
   *Recommendation: yes, as a hard break in the item's paragraph — only when there is no blank line in between (after a blank line an unindented line still ends the list, as in CommonMark).*
3. **Q3 — Fix the reverse direction too.** Should `renderADFList` emit a blank line between the paragraphs of one item and indent every line of a multi-line child, so a multi-paragraph item survives a Jira round trip?
   *Recommendation: yes, in this ticket — without it, editing a Jira task in Sectile rewrites its multi-paragraph items into single paragraphs with hard breaks.*
