## Request and scope

Replace the Create PR workflow action with Adjust between implemented and reviewed, with PR creation owned by specification or implementation according to project policy. Preserve the existing workflow states and human merge/handoff boundary; redesigning the board, adding states, and automating merge are outside scope.

## Evidence

However, the application default is `implemented`, whose generated instructions currently say to create the PR after implementation **and review**. Therefore, replacing the action requires clarifying ownership of PR creation for that default, not only renaming a button.

## Resolved ambiguities, in priority order

1. **Adjust responsibilities:** full branch review and corrective work, or only responding to human review feedback? The latter changes completion criteria and whether unattended adjustment can finish without feedback.
2. **Missing PR:** requiring an existing PR makes earlier creation an invariant; allowing recovery creation keeps creation behavior inside Adjust. Existing implemented tickets and projects using the default policy can encounter this case.

## Questions and confirmed decisions

1. Should Adjust review the complete branch, fix findings, incorporate available PR feedback, rerun checks, and mark the existing PR ready, or only address reviewer feedback? **Recommended: full review and adjustments**, retaining the existing quality gate without requiring feedback to exist.
2. If an implemented ticket has no PR, should Adjust stop and require creation through the earlier stage, or create a recovery PR itself? **Recommended: require an existing PR**, report the missing prerequisite, and leave the ticket implemented.

User answer: “Full review, earlier-stage”. Both recommendations are accepted. Adjust reviews the complete branch, fixes findings, incorporates available feedback, reruns checks, and marks the existing PR ready. It does not require human feedback to exist. If no PR exists, Adjust reports the missing prerequisite and leaves the ticket implemented; creation must be completed through specification or implementation according to project policy. No product questions remain open.

## Settled scope and reversible assumptions

- Preserve `new → clarified → specified → implemented → reviewed → finished`; “done” in the ticket describes the terminal state, not a requested storage/label migration.
- Retain both PR timing settings. For `specified`, reuse the draft created with the specification. For `implemented`, move PR creation into implementation before adjustment. Assume drafts remain draft until adjustment succeeds, consistent with the existing early-PR policy.
- Use Adjust as the visible action and provisionally `adjust` / `/adjust-issue` as its canonical ID/command, following the existing issue skill naming convention.
- Update server routing, result validation, runner prompts, generated skills, single/batch pickup instructions, frontend actions, and relevant documentation together.
- Preserve old `create_pr` and `review` invocations as compatibility aliases to the replacement behavior. Preserve activity history and user overrides; surface incompatible custom creation instructions instead of silently discarding them. Exact migration mechanics belong in specification.
- Preserve verified build/lint/test evidence and the existing PR verification gate for full review. PR existence alone must not mark a task reviewed.
- Keep human merge and subsequent handoff. Adjustment must support repeating work on the same branch and PR.
- Align the standalone missing-PR shortcut with the selected creation ownership; it must not accidentally complete review merely by creating a PR.
