# Clarification #586 - Reset skill status

Ticket: https://github.com/sebastienferry/sectile/issues/586
Branch: `feat/586`

## Round 1 - initial report (2026-09-28)

### Restatement

When a console is left open after its skill finished, and a new skill is then
started on the same task, the "skill completed" indicator (`✓`) of Sectile
Desktop keeps showing the verdict of the previous skill; it must be reset so
that it describes the skill that is now running. Out of scope: the run-state
badge (process alive or not), the server-side activity lifecycle, the web
board's activity list (its `✓` marks activity steps, not skills), and any
change to how or when a stage is validated.

### Code read

- `desktop/src/skill-result.mjs`: `skillResult(run, result)` derives the badge
  (`✓ Skill completed`, `◷ Awaiting stage validation`, `! failed`, `⊘ canceled`,
  `? waiting`). It only trusts an activity whose `id` equals the desktop run's
  `id` (`matched`).
- `desktop/src/main.js`: `refreshSkillResult` (per-run cache `skillResults`),
  `renderTaskSkillStatuses` (sidebar row badge `.task-skill-status`), the header
  badge `#skill-result`, `renderNextStep` / `launchTaskWork` (the `Next:` button
  is disabled while any run of the task is active; `Launch anyway` forces it).
- `desktop/src/task-order.mjs`: `orderedTaskGroups` picks the run a task row
  represents: running/preparing first, then queued, then newest.
- `internal/agent/agent_desktop.go` `desktopRunResult`: returns the task and the
  one activity whose id is the desktop run id.
- `internal/db/remoterun.go` `startRemoteRun` / `adoptRun`: `start_run` with an
  ended runId is refused ("already ended as completed; call start_run without
  a runId"), so a second skill in the same session creates a new, unlinked
  `remote_run` activity.
- `internal/agent/agent_console.go`, `agent_desktop.go`: the console exports
  `SECTILE_RUN_ID` = the desktop run id, fixed for the life of the process.

### How the stale `✓` happens today

Two paths lead to it, and they need different code.

- **A. Same console, next skill.** The owner keeps the session open and starts
  the next skill inside it (typing `/specify-issue`, or the agent chaining).
  The skill's `start_run` with the inherited `SECTILE_RUN_ID` is refused because
  that run already ended, so it creates a new activity. The desktop still asks
  for the result of the first activity, which is `completed`, and keeps
  showing `✓` for the whole second skill.
- **B. New execution while the old console stays open.** The owner launches the
  next step from the board or with `Launch anyway`. A new desktop run appears,
  but while it is queued (the checkout is held by the open console) the task
  row keeps representing the old, still-running console, whose badge says `✓`.
  The header also keeps `✓` while the old console is selected.

### Ambiguities (worst first)

1. Which path the ticket means (A, B or both). Reading A changes how the badge
   finds its activity; reading B changes which run a row reflects.
2. What "reset" displays: an empty badge until the new skill reports, or the new
   skill's own state (nothing while it runs, `?` when it waits, `✓` when it
   completes, `!` / `⊘`).
3. Whether the old console, when selected, keeps its own verdict in the header
   (accurate for that execution) or is reset too.

### Dependencies

- No migration, no server API change needed for B.
- For A, the new activity carries no link to the console that created it
  (`start_run` without runId). Attribution must rely on the task and time
  (newest `remote_run` of the task created after the console's activity), since
  a second session on the same task could also create one. `desktopRunResult`
  already loads all task activities, so it can pick it without a new endpoint.
- Desktop UI tests need a build (`npx vite build`) before running.

### Reversible technical choices (settled)

- The fix lives in the desktop (`skill-result.mjs`, `main.js`) and in the
  agent's `desktopRunResult`; the server is untouched.
- The skill result of a run is cleared from the `skillResults` cache as soon as
  a newer skill is known for its task, rather than waiting for the next poll.
- Changelog: user-visible, one `Fixed` line under `[Unreleased]`.

### Product questions

1. Which situation must be fixed? Recommended: **both A and B**.
2. After the reset, what does the badge show? Recommended: **the new skill's
   own state** (no glyph while it runs, then `?`, `✓`, `!` or `⊘`), never a blank
   that outlives the new skill.
3. When the old console is selected, does its header badge keep `✓`?
   Recommended: **the task row follows the newest skill; the header of an old
   console keeps its own verdict in B, and follows the new skill in A** (in A the
   console is the one running the new skill).

### Status

Round 1 committed on `feat/586`. Three product questions open, to be answered
by the owner. No transition until they are settled.
