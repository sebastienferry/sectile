# Clarification #678: a context repository prepared but left unchanged blocks the implemented transition

## Round 1 (2026-10-01)

### Restated request

A secondary repository whose task branch carries no work of its own must stop
requiring a pull request: the stage transition succeeds with the pull requests
of the repositories that did change, and its report names that repository as
"prepared, unchanged". Out of scope: a task that changes no repository at all,
primary included (#584); any relaxation for a secondary branch that has commits;
and treating a failed lookup as an absence.

### Code read

- `internal/db/stageprs.go`: `validateStagePRs` builds `required` from
  `taskChangedRepositories` plus the primary repository, and fails on the first
  repository without a pull request; `checkSecondaryPRs` applies the same rule at
  adjustment.
- `internal/db/repositories.go`: `AddChangedRepository` appends to
  `tasks.changed_repositories` when `PrepareRepositoryWorktree` succeeds; nothing
  ever removes an entry, which is why deleting the worktree changed nothing (the
  owner's comment of 2026-10-01).
- `internal/db/adjustment.go`: `validateStagePRAt` looks the pull request up
  first (`lookupStagePR`, faked by `prEvidenceLookup` in tests), then asks the
  agent for `git_evidence`; a missing checkout is only a notice, after the
  lookup.
- `internal/agent/agent_operations.go` (`git_evidence`, `pr_evidence`) and
  `internal/agent/evidence.go` (`verifiedCheckout`): the agent can read a
  secondary repository's checkout (mapped or attached folder) but reports
  nothing about commits ahead of the default branch.
- `internal/agent/repositories.go`: `repositoryWorktree` (the worktree
  `prepare_repository_worktree` returns) and `buildFolderMap` (role `changed`).
- Tests: `internal/db/crossrepo_test.go` (`fakeCrossRepoAgent` answering
  `pr_evidence` and `git_evidence`, `prEvidenceLookup` overrides).

### Ambiguities, worst first

1. **What counts as "unchanged" once the worktree or the branch is gone.** The
   ticket says "no commit ahead and not pushed"; the owner's comment shows the
   other path to the same state: worktree removed, local branch deleted, never
   pushed. Reading A: only a branch that exists with zero commits ahead counts.
   Reading B: a branch absent locally and on `origin`, in a checkout the agent
   does find, counts too. Different code, and only B unblocks PEPORT-1 as it now
   stands. (Q1)
2. **Whether "not pushed" is part of the rule.** A pushed branch identical to
   the default branch has nothing to review, but the ticket names the condition
   explicitly. (Q2)
3. **Whether the repository is dropped from the task or only skipped.** The
   comment offers "a way to drop a prepared repository from a task, or the check
   runs when the transition is made". (Q3)
4. **Where "prepared, unchanged" is shown.** In the transition report only, or
   as a state on the task (API, web and desktop). (Q4)

### Critical dependencies

- **The agent decides, the server cannot.** GitLab checkouts live on the
  workstation, so the "commits ahead" answer must come from the local agent.
  An agent too old to answer (or that does not echo the repository) is a failed
  lookup, never an absence: the pull request stays required. No server-only
  path exists.
- **Default branch resolution** happens in the repository's own checkout
  (`origin/HEAD`); an unresolvable default branch is a failed lookup too.
- **No migration** if the repository is skipped rather than dropped (Q3, option
  A); dropping it with a new MCP tool would touch the agentmcp whitelist, mcptest
  and the two tool-count tests (known cost).
- **Test hook.** `prEvidenceLookup` fakes the forge only; the "unchanged" answer
  comes from the agent, faked through `fakeCrossRepoAgent` (or an equivalent
  hook). The acceptance criterion "through the existing `prEvidenceLookup`
  hook" is read as "with the forge faked by it", plus the agent fake.

### Technical choices settled from the code

- The check runs **at transition time**, before the forge lookup, and only for a
  secondary repository with no pull request given in `prUrls` nor recorded on
  the task branch. A repository with a given or recorded link keeps the current
  rules unchanged.
- The agent answers through the existing operation channel: either new fields
  on `git_evidence` or a new action; the choice is left to the specification.
- "Commits ahead" means `git rev-list --count origin/<default>..<branch>` in the
  repository's own checkout, on the remote-tracking ref already present (no
  fetch is required: a branch cut from an older default branch is still 0 ahead).
- A branch whose commits were squash-merged elsewhere still counts as changed
  (commits ahead > 0): its pull request is required, the conservative reading.
- The same rule applies on every path that checks secondary pull requests:
  `validateStagePRs` (implemented, and clarify/specify when the creation owner is
  early) and `checkSecondaryPRs` (adjustment), so a later stage is not blocked
  where implemented was not.
- The primary repository is never exempted here (#584 covers it).
- A `CHANGELOG.md` line under `Fixed` (user-visible: a transition that failed
  now succeeds).

### Product questions (with recommendation)

**Q1. A secondary repository whose task branch no longer exists, locally or on
`origin`, in a checkout the agent finds: unchanged or not?**
Recommended: **unchanged**. Nothing was pushed, so no pull request can exist,
and it is the only way the PEPORT-1 case, worktree already removed, reaches
`implemented`. A repository with no checkout found on the workstation stays a
failed lookup (pull request required).

**Q2. Does a pushed branch with zero commits ahead of the default branch also
count as unchanged?**
Recommended: **yes**, "no commit ahead" alone decides: pushing an empty branch
adds nothing to review, and GitHub refuses a pull request with no diff anyway.
The alternative keeps the ticket's literal "and is not pushed" and still forces
an empty merge request in that case.

**Q3. Skip the repository at transition time, or remove it from the task?**
- A (recommended): **skip at transition time**, keep it recorded. A later stage
  that commits there needs its pull request again, no new tool, no migration.
- B: add a way (MCP tool or API) to drop a prepared repository from a task.
- C: both.

**Q4. Where is "prepared, unchanged" shown?**
- A (recommended): **in the transition report** (the stage notice, as the
  "head commit not verified" notice already is), naming each repository.
- B: also as a state on the task, visible in the web and desktop task detail.

## Round 2 - answers from the owner (2026-10-01)

The owner answered Q1 to Q4 interactively, each with the recommended option.

### Settled decisions

- **Q1, unchanged without a branch.** A secondary repository counts as
  unchanged when the agent finds its checkout and the task branch exists
  neither locally nor on `origin`. This is the PEPORT-1 case after the worktree
  and the local branch were removed. A repository with no checkout found on the
  workstation stays a failed lookup: its pull request is still required.
- **Q2, the gap alone decides.** A branch with zero commits ahead of the
  repository's default branch is unchanged, pushed or not. The ticket's
  "and is not pushed" condition is dropped (reversed assumption).
- **Q3, skipped at transition time.** The repository stays recorded in
  `tasks.changed_repositories`; the check runs on every transition. A later
  stage that commits there needs its pull request again. No new MCP tool, no
  API, no migration.
- **Q4, shown in the transition report.** The stage notice names each
  repository as "prepared, unchanged", the way the existing "head commit not
  verified" notice is carried. No new task state, no web or desktop change.

### Resulting rule

For each secondary repository of the task with no pull request given in
`prUrls` nor recorded on the task branch, before the forge lookup, the agent is
asked about the task branch in that repository's checkout:

| Agent answer | Outcome |
| --- | --- |
| checkout found, branch absent locally and on `origin` | unchanged, skipped, named in the notice |
| checkout found, branch with 0 commits ahead of `origin/<default>` | unchanged, skipped, named in the notice |
| checkout found, branch with commits ahead | pull request required (rules of #392 and #456) |
| no checkout, default branch unresolvable, Git failure, agent too old | failed lookup: pull request required |

The primary repository is never exempted (#584). The same rule holds in
`validateStagePRs` and in `checkSecondaryPRs`.

### Acceptance criteria, as settled

- The PEPORT-1 case transitions to `implemented` with the primary `prUrl` only,
  and the report names `argocd-pl-tooling` as prepared, unchanged; both the
  "branch with 0 commits ahead" and the "branch gone" variants are covered.
- The transition still fails when the secondary branch has commits and no pull
  request, and when the agent cannot answer.
- Tests fake the forge through `prEvidenceLookup` and the agent through
  `fakeCrossRepoAgent` (or the equivalent agent fake).
- `CHANGELOG.md` gets one line under `Fixed`.
