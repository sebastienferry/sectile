# Clarification #878: Desktop: make skill status reporting clear and focused on outcomes

## Round 1 - initial report (2026-10-27)

Report: `docs/clarifications/878.md` on `feat/878` (worktree `.tasks/worktrees/issue-878`). Committed, not pushed (`pushStageCommits` off). No pull request at this stage (`prCreationStage` is `implemented`).

### Restatement

Sectile Desktop shows, for a task's current execution, one primary status that says what the user's situation is (working, needs your answer, done, needs verification, could not finish, stopped) together with a concrete outcome, reason or next step, instead of a run-state glyph and a separate "Skill …" badge the user has to reconcile. The raw run state and the recorded skill outcome stay available as diagnostic details, and the precedence between conflicting signals is defined and tested.

Out of scope: the web UI's activity badges, desktop notifications (they announce run-state transitions from `shared/runStates.ts` and keep doing so), the sidebar execution list wording, the skills' own `finish_run` notes, and any change to how the server validates a stage.

### Code read

- `desktop/src/skill-result.mjs`: `workflowSkill()`, `verdict()`, `stopping()`, `skillResult()`. The whole badge logic: `completed` becomes `pending` "Awaiting stage validation" until the task reaches the skill's expected stage; `failed` / `canceled` become "Skill failed" / "⊘ Skill stopped"; a run that exited with no server record becomes "Execution ended · skill completion unconfirmed"; a successor skill in the same console (#586) takes over the badge.
- `desktop/src/main.js`: `renderTaskSkillStatuses()` (task rows: glyph only, label in the tooltip) and `showDirectory()` (bottom task status bar / conversation status row: glyph and label), both beside the run-state glyph drawn by `renderRunState()` from `runStateOf()` / `runStateLabel()`.
- `shared/runStates.ts`: the run states shared with the web UI and notifications: `waiting` "Waiting for you", `silent`, `running`, `queued`, `completed` "Finished", `failed`, `canceled` "Stopped".
- `internal/agent/agent_desktop.go` (≈1460-1528): the agent endpoint the badge reads. It returns `activity {id, taskId, skillId, status}`, `successor {…, waitingSince}` and `task {status, labels}`, and nothing else.
- `internal/models/models.go` `TaskActivity`: the server already stores `Summary` (where `finish_run` appends its note, `internal/db/remoterun.go` `finishRemoteRun`), `Error`, `WaitingSince`, `WaitingReason`, `CompletedAt`.
- `desktop/tests/skill-result.ui.cjs` (current precedence coverage), `desktop/README.md` "Skill result indicator", `docs/USER_GUIDE.md` (links to it), `docs/clarifications/586.md` (the successor rule).

### Why today's display is hard to read

Two indicators sit side by side and answer different questions with overlapping words: the run state ("Finished", "Stopped", "Failed": the process) and the skill badge ("Skill completed", "Skill stopped", "Skill failed": the server record). A console still open after its skill completed shows "Running" next to "✓ Skill completed"; a run whose process exited cleanly shows "Finished" next to "◷ Execution ended · skill completion unconfirmed". "Skill completed" never says what was achieved, and nothing says why something stopped or failed, because the endpoint does not carry the reason even though the server stores it.

### Ambiguities (worst first)

1. **One status or two.** Either the primary status replaces the run-state glyph and the skill badge in the task row and the task status bar, or it replaces only the skill badge and the run-state glyph stays beside it. These lead to different rendering code and different tests. Product question 1.
2. **Where the reason and the outcome come from.** The agent endpoint does not expose `Summary`, `Error`, `WaitingReason` or `CompletedAt`. "Show the actual error" and "show why when known" require extending that endpoint (Go, agent side) and therefore an updated local agent; an older agent can only yield "reason not available". Settled below, with a question on how much of the note is shown (question 3).
3. **"Show the question" for a wait.** No question text is recorded anywhere: `report_waiting` takes a boolean, and the Claude Code hooks only set `WaitingSince`. Showing the question needs a new field through MCP, server, agent and skills. Product question 2.
4. **Outcome of a skill with no expected stage.** `pickup`, `pickup_issues`, `create_pr`, `rewrite_story`, `refine_macro`, `realign_macro` have no entry in `expected`. Settled below.
5. **User cancellation vs. disconnection.** Both end as `canceled`. Desktop knows a stop it asked for (`cancelRequested`); a run closed by the server because its client disconnected carries the server's closing text in `Summary`. Settled below: the reason is named only from those two facts, otherwise stated as unknown.

### Dependencies

- **Agent endpoint** `GET …/skill-result` (`internal/agent/agent_desktop.go`): add the matched activity's `summary`/`error` (trimmed), `waitingReason` and `completedAt`, for both `activity` and `successor`. Additive JSON, so an older desktop ignores it and a newer desktop facing an older agent falls back to "reason not available". No server API, database or migration change: the fields already exist on `/api/tasks/{id}/activities`.
- **Agent update**: the honest-reason part needs the local agent shipped with this change; the README must say so, as it already does for the result lookup.
- No dependency on the web UI or on `shared/runStates.ts`: notifications keep their run-state wording.

### Reversible technical choices (settled)

- **Interface language.** Desktop labels are in English today ("Skill completed", "Running", "Waiting for you"); the new labels stay in English. Repository documentation in English.
- **Pure function stays the single source.** `skill-result.mjs` is reworked into one function that takes the run, the server result and the task, and returns `{kind, label, detail, next, diagnostics}`; both the task row and the status bar render from it. The precedence table below is its specification and the unit tests enumerate it row by row.
- **Working** shows the skill name ("Working · Clarify"); no live parsing of the console to find a "current action". A finer action would need the skill to report steps, which no skill does today.
- **Done** names the stage reached, mapped from the skill: clarify "Clarified", specify "Specification ready", implement "Implemented", adjust/review "Review complete", handoff "Handed off". It never says the task is finished unless the stage is `finished`. For `pickup`/`pickup_issues`, the outcome is the stage the task is in at completion if it moved forward during the run, otherwise "Needs verification · no stage advanced". For skills with no stage (`create_pr`, `rewrite_story`, macro skills), a reported completion shows "Done" with the label "reported by the skill", because no validation exists for them.
- **Next step** for Done is a text hint of the next workflow skill (for example "Next: specify"), not a launch button.
- **Stopped** reason: "Stopped by you" only when Desktop recorded `cancelRequested` for this run; "Session disconnected" only when the server's closing text says so; otherwise "Stopped · reason not recorded". Never an actor that is not on record.
- **Diagnostics** keep the run state and the skill record verbatim (for example "Execution: Running · Skill record: completed · Task stage: specified") in the tooltip and the accessible label, so nothing currently inspectable is lost.

### Proposed precedence (to confirm, question 1)

The first matching row wins. "Skill" is the successor when one exists (#586), else this execution's own record.

| # | Signals | Primary status | Detail / next |
|---|---------|----------------|---------------|
| 1 | Stop requested, not yet effective | Stopping | "Waiting for the session to exit" |
| 2 | Skill record `completed`, stage reached (or no stage expected) | Done · <outcome> | Next: <next skill>; an open console does not change this |
| 3 | Skill record `completed`, expected stage not reached | Needs verification | "<skill> reported completion; the task is still at <stage>" |
| 4 | Skill record `failed` | Could not finish | Recorded error/note, or "no reason recorded"; next: "Open the console" / "Relaunch <skill>" |
| 5 | Skill record `canceled` | Stopped | Known reason (see above) or "reason not recorded" |
| 6 | Process running, wait declared | Needs your answer | "Answer in the console" |
| 7 | Process queued / preparing / running | Working · <skill> | - |
| 8 | Process exited with no skill record | Needs verification | "The session ended without reporting a result" |
| 9 | Process failed / canceled with no skill record | Could not finish / Stopped | Process exit reason when known, else "not recorded" |

Row 9 is a change: today those cases show no skill badge because the run state already said it. With a single primary status they must be shown.

### Product questions

1. **One primary status replacing both indicators?** Recommended: yes. In the task row and the task status bar, the primary status (glyph from its kind, label, detail) replaces the run-state glyph and the skill badge; run state and skill record move to the tooltip/accessible label (task row) and a details line under the status (status bar). The precedence table above becomes the acceptance criterion. Alternative: keep the run-state glyph and only reword the skill badge, which leaves two signals side by side.
2. **"Needs your answer": show the question text?** Recommended: not in this ticket. Show "Needs your answer · answer in the console" and open a follow-up ticket to add an optional question text to `report_waiting` (MCP, server, agent, skills). Alternative: include it here, which widens the change to four layers and to every skill.
3. **How much of the recorded reason is shown for Could not finish / Stopped / Needs verification?** Recommended: the first line of the recorded error, or of the `finish_run` note when there is no error, truncated to about 120 characters in the status bar and the tooltip, with the full text in the details. The note is free text written by the agent in the conversation's language and is shown as is.
4. **Successor rule confirmation.** Recommended: keep #586: once another skill starts in the same console, the status speaks only for that skill, and the previous skill's outcome is visible in diagnostics only. Alternative: show the previous outcome until the successor itself ends.

## Round 2 - answers from the owner (2026-10-27)

Report: `docs/clarifications/878.md` on `feat/878`, appended to the Round 1 commit `8b5962a5`. Not pushed (`pushStageCommits` off). Round 1 was published as a ticket comment; this section is the transition note.

### Answers and settled decisions

1. **One primary status.** Adopted. In the task row and in the task status bar, the primary status replaces both the run-state glyph and the skill badge. The run state and the skill record move to diagnostics: tooltip and accessible label on the task row, a details line on the status bar. The Round 1 precedence table (rows 1 to 9, first match wins) is an acceptance criterion and is tested row by row, including the cases named in the ticket: open console after completion (row 2), missing completion reporting (row 8), completion before stage validation (row 3), user cancellation and session disconnection (row 5 / row 9 with their reasons), successor skill in the same console (rule below).
2. **Question text for a wait.** Not in this ticket. "Needs your answer" shows "answer in the console". Follow-up created with the owner's approval: [#879](https://github.com/sebastienferry/sectile/issues/879) "Desktop: show the question a waiting skill asks".
3. **Reason shown.** The first line of the recorded error, or of the `finish_run` note when there is no error, truncated to about 120 characters in the status bar and the tooltip; the full text in the details. Free text is shown as recorded, without translation. When no reason is recorded, the status says so ("reason not recorded").
4. **Successor rule.** The #586 rule is kept: once another skill starts in the same console, the primary status speaks only for that skill; the previous skill's outcome stays visible in diagnostics.

### Reversed assumptions

None. Every Round 1 recommendation was adopted. Row 9 of the precedence table (a failed or canceled process with no skill record now shows a status, where today it shows no skill badge) is confirmed as an intended change.

### Settled scope for the specification

- `desktop/src/skill-result.mjs` becomes the single status function returning `{kind, label, detail, next, diagnostics}`; `renderTaskSkillStatuses()` and `showDirectory()` in `desktop/src/main.js` render the primary status only.
- The agent's skill-result endpoint (`internal/agent/agent_desktop.go`) adds `summary`, `error`, `waitingReason` and `completedAt` to `activity` and `successor`, additively; a desktop facing an older agent shows "reason not available".
- Labels stay in English, the Desktop interface's current language.
- `desktop/README.md` "Skill result indicator" is rewritten for the new status, `docs/USER_GUIDE.md` keeps its link valid, and `CHANGELOG.md` gets an Unreleased entry.
- Out of scope: web UI, notifications, sidebar execution list, the question text (#879).

### Open questions

None. The owner confirmed the clarification is satisfactory on 2026-10-27.
