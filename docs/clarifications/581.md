# Clarification #581 - Board filters not respected

## Round 1 - initial report (2026-09-28)

### Request

The Sprint, Team and Assignee filters of the board no longer seem to be
applied: the board shows tickets that the selected filters should hide, or
loses the selection. Out of scope: new filters, the filter bar layout, the
saved board views feature itself (#387) and the server-side sort (#402).

### Code read

- `web/src/context/AppContext.tsx`: filter state (l. 560-603), per project and
  per view persistence (`persistFilter`, l. 755-842), restore on scope change
  (l. 1277-1305), `buildTaskQuery` and `fetchTasks` (l. 1197-1273), facet
  loading (l. 1307-1337), pruning of stale remembered filters (l. 1648-1671),
  the SSE `task_updated` listener (l. 1776-1801) and the activity poll refresh
  (l. 1809-1916).
- `web/src/components/TaskFilters.tsx`: Sprint, Team and Assignee lookups
  (l. 416-460), shown only when the facets carry values.
- `web/src/lib/lookups.ts`: `valueLookup`, the option id is the raw value.
- `web/src/components/BoardView.tsx`: the board renders `tasks` as received,
  only `activeOnly` refilters client side.
- `internal/handlers/handlers.go` (`GET /api/tasks`, l. 1833-1873) and
  `internal/db/db.go` (`GetTasksInScope`, l. 1686-1810): `sprint = ?`,
  `team = ?`, `assignee = ?` are applied, and the view scope is narrowed by
  the other filters. No server-side regression found.
- Recent history of these files (#402, #487, #522, #540, #564): none of them
  changes the filter path.

### Findings

Two defects in the web client explain both readings of "not respected":

1. **Out-of-order task responses.** `fetchTasks` is neither aborted nor
   sequenced. On mount, the first fetch runs with empty filters, then the
   restore effect sets the remembered filters and a second, filtered fetch
   starts. Whichever answer arrives last wins: when the unfiltered one (the
   bigger, slower one) lands second, the board shows every ticket while the
   selectors still show the filter. The same race happens on every project or
   view switch, on an SSE `task_updated` burst and on the poll refresh.
2. **Pruning against stale facets.** On a project or view switch, the restore
   effect loads the new scope's filters while `taskFacets` still holds the
   previous scope's values. The pruning effect then sees the restored sprint,
   team or assignee as "no longer existing", clears it and persists the null:
   the filter is forgotten for good, not just for this render.

### Ambiguities (worst first)

1. Which symptom is observed: the selector keeps its value but the board shows
   other tickets (finding 1), or the selector itself is emptied, after a
   reload or a project switch (finding 2). The fix differs; both can be fixed.
2. Whether the other filters (status, priority, label, types, tracker
   statuses, macro) are in scope. Finding 1 affects every filter, finding 2
   only sprint, team and assignee.
3. Which client: the desktop app embeds the same web UI, so a fix in
   `AppContext.tsx` covers both, unless the owner sees it only on one.

### Dependencies

- None on the server, the database or the trackers.
- Reproducing finding 1 needs a board large enough for the unfiltered answer
  to be slower than the filtered one, or a delayed response in a test.

### Reversible technical choices (settled by convention)

- Only the last task request started may write `tasks`: a request sequence
  number (or an `AbortController`) in `fetchTasks` and in the poll refresh,
  covering the SSE path that calls `fetchTasks`.
- Facets carry the scope they were fetched for; pruning runs only when the
  facets belong to the current `filterScope`, and never persists a null
  derived from another scope's facets.
- Tests in the existing web test style (`node --test`), with a delayed
  response and a scope switch.
- A `Fixed` line under `## [Unreleased]` in `CHANGELOG.md`, the change being
  visible to users.

### Open product questions

1. Symptom: board shows tickets outside the filter, or the filter is reset?
   Recommended: fix both, they share the same area.
2. Scope: every board filter, or only Sprint, Team and Assignee?
   Recommended: every filter for the out-of-order fix (it is one mechanism),
   the pruning fix naturally concerns only Sprint, Team and Assignee.
3. Client and context: web, desktop, a saved view, a particular project or
   tracker? Recommended: fix in the shared web UI, which covers both clients.
