## Round 1: analysis (2026-09-23)

### Request restated

Make `sectile-server` run as more than one replica behind a load balancer, without
losing requests, sessions or runs when a request lands on a different replica, or
when one replica restarts. Out of scope: multi-replica on SQLite (a file cannot be
shared across pods), the agent daemon and the desktop application (they stay
single-process on a workstation), and HTTP rate limiting.

The ticket says the server "would need a session store or some ingress stickiness".
The inventory below shows that premise is only partly true: web sessions are
**already** in the database, and stickiness cannot fix the hardest blocker (agent
routing), because the replica a user's request reaches and the replica the agent's
WebSocket reached are unrelated.

### Ambiguities, worst first

**A1: What "multi-replica" is for (open, Q1).** Two readings produce different code:

- *Active/passive (high availability)*: N pods, one leader elected through a
  PostgreSQL advisory lock; standbys report not-ready, so the load balancer only sends
  traffic to the leader. S2-S9 stay in-process and correct, because only one process
  serves. What must change: leadership acquisition before serving, readiness tied to
  leadership, and the restart sweep (S6) only after leadership. Failover drops agent
  WebSockets and MCP sessions (agents reconnect; MCP runs are canceled and recoverable
  through `finish_run`, as today on a restart). No stickiness needed.
- *Active/active (horizontal scale)*: every replica serves. Requires cross-replica
  agent routing (S2: presence table plus forwarding or pub/sub), sticky routing on
  `Mcp-Session-Id` plus DB-persisted run ownership (S3), shared pub/sub for SSE (S4),
  a leader lease for auto-sync (S5), per-instance ownership with heartbeats for runs
  (S6, S7), row locks or conditional updates (S8), and an answer for S9. Roughly an
  order of magnitude more work and risk.

**A2: Behaviour during a replica loss or a rolling deploy (open, folded into Q1/Q2).**
Whether dropping MCP sessions and agent connections on failover is acceptable, or
whether a deploy must be invisible to a running agent session.

**A3: Passphrase-sealed credentials (open, Q3).** Under active/active they cannot be
shared without defeating the passphrase. Under active/passive they behave as today
after a restart (the user unlocks again after a failover).

**A4: Deployment manifests (open, Q4).** Whether the ticket includes the change to
the external deployment repository (replica count, readiness probe, disruption
budget, ingress settings) or only makes the server capable of it.

### Critical dependencies

- **PostgreSQL is a prerequisite.** Multi-replica is refused on SQLite: the server
  must fail fast (or refuse the leader role cleanly) rather than let two processes
  share one file.
- **Shared `SECTILE_SECRET_KEY`** across replicas (already required under PostgreSQL).
- **Load balancer behaviour**: active/passive needs only a readiness probe honoured by
  the balancer; active/active additionally needs header-based affinity on
  `Mcp-Session-Id` and long-lived WebSocket/SSE support on every replica.
- **ADR changes**: ADR 0016 states single instance and would be amended; ADR 0007's
  restart sweep changes meaning (sweep on leadership, or per-instance ownership). A new
  ADR records the chosen topology.
- **Public repository**: internal hostnames, projects and secret names stay out of the
  committed docs.

### Resolved technical decisions (reversible, settled here)

- **D1: No session store.** Web sessions are already persisted; the ticket's "session
  store" is not needed for them.
- **D2: Coordination through PostgreSQL, no new infrastructure.** Leader election via
  `pg_try_advisory_lock` on a dedicated connection (the pattern `LockForMigration`
  already uses); if active/active is chosen, pub/sub via `LISTEN/NOTIFY` rather than
  introducing Redis.
- **D3: SQLite stays single-instance**; the multi-replica mode is only reachable with
  `DB_DRIVER=postgres`.
- **D4: The restart sweep must stop being global.** Whatever the topology, a booting
  process must not cancel work another live process owns: in active/passive it runs
  only once the lock is acquired; in active/active it becomes ownership plus heartbeat.
- **D5: `/health` stays a liveness probe; a separate readiness signal reflects the
  ability to serve** (leadership in active/passive).
- **D6: Operator-visible change**: the chosen mode is documented in `README.md`, the
  ADR, and gets a `CHANGELOG.md` line under `[Unreleased]`.

### Open product questions

**Q1: Topology: active/passive or active/active?**
Recommendation: **active/passive** (leader lock, standby not ready). Sectile's load is
one team's board; the real need is surviving a node loss and deploying without the new
pod cancelling the old pod's work. It keeps every in-process design correct and fixes
S6 on the way. Active/active can follow later on the same leader primitive.

**Q2: Is losing live MCP sessions and agent connections on failover acceptable?**
Recommendation: **yes**: agents reconnect on their own, and a canceled MCP run stays
recoverable by its owner (ADR 0007 amendment). A handover that keeps sessions alive would require
active/active plus persisted session state.

**Q3: Passphrase-sealed credentials after failover.**
Recommendation: **the user unlocks again**, exactly as after a restart today; the keys
stay memory-only by design.

**Q4: Does the ticket include the external deployment change?**
Recommendation: **no**: this ticket makes the server capable and documents the
required probe and replica settings; the change to the deployment repository is done
by the owner afterwards (it is outside this public repository).

## Round 2 - answers from the owner (2026-09-23)

### Settled: Q1, active/active (reverses the Round 1 recommendation)

The owner expects load growth, so several replicas must serve at once. Active/passive
is rejected as the target. The owner's reading: HTTP APIs and MCP are mostly stateless
(the web session lives in the database), so the real challenge is the long-lived
connections.

### Correction recorded: MCP is not stateless today

Since ADR 0007 the MCP endpoint is served statefully on purpose: the go-sdk keeps its
sessions in memory (`agent_api.go:186`, `SessionTimeout: 0`) and `taskmcp.SessionRegistry`
binds runs to them. A request carrying an `Mcp-Session-Id` that another replica created
gets `404 session not found`. The plain REST API is stateless apart from S5-S9 below;
MCP is a long-lived session like the WebSockets, and belongs to the same challenge.

### Answer to the owner: what happens to a WebSocket when a node dies

A WebSocket cannot be transferred: it is one TCP connection to one process, and it dies
with the node. What survives is the client's reconnection:

- **Agents** already reconnect on their own (`internal/agent/agent.go:354`): exponential
  backoff from 1 s up to 60 s, reset after a successful connection, and a failed
  heartbeat hangs up immediately. Through the load balancer the new connection lands on
  a surviving replica, typically within one to two seconds. Runs dispatched to an agent
  survive (ADR 0006): its supervisor reports the real outcome on reconnection.
- **Browsers** (SSE, `EventSource`) reconnect automatically as well.
- **MCP clients** receive `404` for the lost session and must open a new one; the runs
  that session owned are closed as canceled and stay recoverable through `finish_run`.

What the server must add is not the transfer but the **routing**: knowing, from any
replica, which replica currently holds a given agent (or MCP session), and reaching it.

### Target design (technical, reversible, to be refined in the specification)

- **D7: Instance identity and liveness.** Each replica gets an instance id at boot and
  heartbeats a `server_instances` row (id, internal address, last_seen). A replica not
  seen for a bound is dead; survivors reclaim what it owned.
- **D8: Agent presence and forwarding (S2).** On `/ws/agent-connect`, the replica
  records `(user, project) -> instance` in an `agent_presence` table. A replica that
  needs an agent it does not hold forwards the operation to the owning replica over an
  authenticated internal HTTP call (pod to pod) and relays the reply; request/response
  correlation stays local to the owner. "Kick the older connection" becomes: the new
  owner asks the previous owner to close it. `WaitForAgent` polls presence, so a
  reconnection in progress on another replica is awaited, not reported as absent.
- **D9: Shared event bus for SSE (S4) and cancellation (S7).** PostgreSQL
  `LISTEN/NOTIFY` feeds `BroadcastEvent` on every replica, carrying event ids rather
  than large payloads (8 kB limit). A cancel is published on the same bus so the replica
  running the job stops it; the job's final `UPDATE` gains a status guard.
- **D10: MCP session routing (S3).** Two candidates, see Q5.
- **D11: Background work (S5).** The auto-sync pass takes a per-project
  `pg_try_advisory_lock` (or a lease row) and persists its pacing and 429 backoff, so
  one replica syncs a project at a time.
- **D12: Restart sweep (S6).** Activities carry the owning instance id; a booting
  replica only reclaims work owned by instances declared dead, never global `UPDATE`s.
- **D13: Races (S8).** Read-check-write sequences guarded by `DB.mu` move to
  conditional updates or `SELECT ... FOR UPDATE`; the per-project limiter (S7) becomes a
  database lock if strict one-worker-per-project is required.
- **D14: Scale assumption.** A handful of replicas (2 to 5) and hundreds of agents.
  PostgreSQL `LISTEN/NOTIFY` and pod-to-pod forwarding suffice; no Redis. Revisit if
  the target is an order of magnitude higher.

### Open product questions after Round 2

**Q2 (still open, reframed): loss on node death.** In-flight agent operations routed
through the dead node fail with an error; MCP sessions on it are lost (canceled runs,
recoverable). Recommendation: **accept**, with no automatic replay of agent
operations beyond the existing reconnection grace.

**Q3 (still open, reframed): passphrase-unlocked keys (S9).** Options: (a) broadcast
the derived key to the other replicas over the authenticated internal channel, memory
only, never in the database; (b) require the user to unlock on every replica (not
usable behind a balancer); (c) persist it encrypted with `SECTILE_SECRET_KEY`, which
weakens the passphrase to the server key. Recommendation: **(a)**, a new replica asking
its peers at boot.

**Q4 (still open): external deployment change in scope?** Recommendation: **no**.

**Q5 (new): MCP session routing.** (a) Keep stateful MCP and forward in-app: the
session id carries the owning instance id, and a replica receiving a foreign session
proxies the request to its owner (works behind any balancer, reuses D8's forwarding);
(b) balancer affinity on the `Mcp-Session-Id` header (depends on the balancer
supporting header hashing); (c) serve MCP statelessly and move run ownership off the
session (reverses ADR 0007: runs would be closed by a heartbeat timeout instead of a
disconnect). Recommendation: **(a)**.

**Q6 (new): delivery shape.** The work spans about six independent slices (D7+D12,
D11, D8, D9, D10, D13+S9). Recommendation: **turn #397 into a macro with child
tickets**, delivered in that order, D7+D12 first since it also fixes today's rolling
deploy.
