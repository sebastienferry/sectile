Task: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-397`

## Round 1: analysis (2026-09-23)

### Request restated

Make `sectile-server` run as more than one replica behind a load balancer, without
losing requests, sessions or runs when a request lands on a different replica, or
when one replica restarts. Out of scope: multi-replica on SQLite (a file cannot be
shared across pods), the agent daemon and the desktop application (they stay
single-process on a workstation), and HTTP rate limiting.

The ticket says the server "would need a session store or some ingress stickiness".
The inventory below shows that premise is only partly true: web sessions are
**already** in the database, and stickiness cannot fix the hardest blocker (agent
routing), because the replica a user's request reaches and the replica the agent's
WebSocket reached are unrelated.

### Inventory: what two replicas break today

| # | State | Where | With 2 replicas |
|---|---|---|---|
| S1 | Web sessions, OIDC state/nonce/PKCE, local sign-in, pairing codes, API keys | `web_sessions`, `login_flows`, `pairing_codes` tables (`internal/db/sessions.go`, `identity.go`) | **OK**: DB-backed, single-use consumption is transactional. No session store needed. |
| S2 | Connected agents and request/response correlation | `AgentDispatcher` maps (`agent_dispatcher.go:136`) | **Wrong replica**: any call reaching the replica without the agent fails with "no local agent connected". This includes `transition_stage` (git evidence goes through the agent), workspace operations, queued skills, launches. The "kick the older connection" rule only works within one replica. |
| S3 | MCP streamable sessions and run adoption | go-sdk in-memory session map (`agent_api.go:186`), `taskmcp.SessionRegistry` | **Lost state**: a request after `initialize` on another replica gets `404 session not found`. Disconnect cleanup and the silence sweeper only see local sessions. |
| S4 | Browser live updates (SSE) | `subscribers` fan-out (`handlers.go:46`, `BroadcastEvent`) | **Missed events**: a board streaming from replica A never sees a change made through replica B. |
| S5 | Tracker auto-sync loop | `StartAutoSync` (`autosync.go:81`), pacing and 429 backoff in memory | **Duplicated work**: N passes per interval, N full syncs at boot, a rate-limit backoff on one replica ignored by the others. |
| S6 | Restart sweep | `recoverInterruptedRuns` (`db.go:695`), global `UPDATE`s | **Corrupts the healthy replica**: any replica booting marks every running job failed and every client-owned run canceled, including those of the other replica. This already bites a rolling deploy with surge today. |
| S7 | Job queue, cancellation, per-project limiter | `jobQueue` chan, `cancelMap`, `ProjectLimiter` (`db.go`) | Jobs are not duplicated (the ADR 0016 wording overstates it) but are stranded on crash; a cancel on replica B does not stop the job on replica A, whose final unguarded `UPDATE` can overwrite `canceled`; per-project concurrency becomes N. |
| S8 | Read-check-write guarded by a process mutex | `DB.mu` (`db.go:153`), stage guard (`stage.go:132`), `AppendRemoteRunOutput` | Races across replicas (lost output appends, double stage transitions). |
| S9 | Keys derived from a sealing passphrase | `unlockedKeys` (`usercredentials.go:55`) | **Lost state**: a credential unlocked on one replica stays locked on the others. By design these keys are never written down. |
| S10 | Jira metadata caches (10 min TTL) | `internal/trackerapi/jira_*.go` | OK: brief disagreement only. |
| S11 | Server encryption key | `SECTILE_SECRET_KEY` | OK if every replica gets the same secret (already mandatory under PostgreSQL). |
| S12 | Migrations | `pg_advisory_lock` (`dialect_postgres.go:88`) | OK on PostgreSQL. |

No Helm/Kubernetes manifest lives in this repository; replicas, ingress and probes are
defined in the external deployment repository that `promote:dev` updates.

### Ambiguities, worst first

**A1: What "multi-replica" is for (open, Q1).** Two readings produce different code:

- *Active/passive (high availability)*: N pods, one leader elected through a
  PostgreSQL advisory lock; standbys report not-ready, so the load balancer only sends
  traffic to the leader. S2-S9 stay in-process and correct, because only one process
  serves. What must change: leadership acquisition before serving, readiness tied to
  leadership, and the restart sweep (S6) only after leadership. Failover drops agent
  WebSockets and MCP sessions (agents reconnect; MCP runs are canceled and recoverable
  through `finish_run`, as today on a restart). No stickiness needed.
- *Active/active (horizontal scale)*: every replica serves. Requires cross-replica
  agent routing (S2: presence table plus forwarding or pub/sub), sticky routing on
  `Mcp-Session-Id` plus DB-persisted run ownership (S3), shared pub/sub for SSE (S4),
  a leader lease for auto-sync (S5), per-instance ownership with heartbeats for runs
  (S6, S7), row locks or conditional updates (S8), and an answer for S9. Roughly an
  order of magnitude more work and risk.

**A2: Behaviour during a replica loss or a rolling deploy (open, folded into Q1/Q2).**
Whether dropping MCP sessions and agent connections on failover is acceptable, or
whether a deploy must be invisible to a running agent session.

**A3: Passphrase-sealed credentials (open, Q3).** Under active/active they cannot be
shared without defeating the passphrase. Under active/passive they behave as today
after a restart (the user unlocks again after a failover).

**A4: Deployment manifests (open, Q4).** Whether the ticket includes the change to
the external deployment repository (replica count, readiness probe, disruption
budget, ingress settings) or only makes the server capable of it.

### Critical dependencies

- **PostgreSQL is a prerequisite.** Multi-replica is refused on SQLite: the server
  must fail fast (or refuse the leader role cleanly) rather than let two processes
  share one file.
- **Shared `SECTILE_SECRET_KEY`** across replicas (already required under PostgreSQL).
- **Load balancer behaviour**: active/passive needs only a readiness probe honoured by
  the balancer; active/active additionally needs header-based affinity on
  `Mcp-Session-Id` and long-lived WebSocket/SSE support on every replica.
- **ADR changes**: ADR 0016 states single instance and would be amended; ADR 0007's
  restart sweep changes meaning (sweep on leadership, or per-instance ownership). A new
  ADR records the chosen topology.
- **Public repository**: internal hostnames, projects and secret names stay out of the
  committed docs.

### Resolved technical decisions (reversible, settled here)

- **D1: No session store.** Web sessions are already persisted; the ticket's "session
  store" is not needed for them.
- **D2: Coordination through PostgreSQL, no new infrastructure.** Leader election via
  `pg_try_advisory_lock` on a dedicated connection (the pattern `LockForMigration`
  already uses); if active/active is chosen, pub/sub via `LISTEN/NOTIFY` rather than
  introducing Redis.
- **D3: SQLite stays single-instance**; the multi-replica mode is only reachable with
  `DB_DRIVER=postgres`.
- **D4: The restart sweep must stop being global.** Whatever the topology, a booting
  process must not cancel work another live process owns: in active/passive it runs
  only once the lock is acquired; in active/active it becomes ownership plus heartbeat.
- **D5: `/health` stays a liveness probe; a separate readiness signal reflects the
  ability to serve** (leadership in active/passive).
- **D6: Operator-visible change**: the chosen mode is documented in `README.md`, the
  ADR, and gets a `CHANGELOG.md` line under `[Unreleased]`.

### Open product questions

**Q1: Topology: active/passive or active/active?**
Recommendation: **active/passive** (leader lock, standby not ready). Sectile's load is
one team's board; the real need is surviving a node loss and deploying without the new
pod cancelling the old pod's work. It keeps every in-process design correct and fixes
S6 on the way. Active/active can follow later on the same leader primitive.

**Q2: Is losing live MCP sessions and agent connections on failover acceptable?**
Recommendation: **yes**: agents reconnect on their own, and a canceled MCP run stays
recoverable by its owner (ADR 0007 amendment). A handover that keeps sessions alive would require
active/active plus persisted session state.

**Q3: Passphrase-sealed credentials after failover.**
Recommendation: **the user unlocks again**, exactly as after a restart today; the keys
stay memory-only by design.

**Q4: Does the ticket include the external deployment change?**
Recommendation: **no**: this ticket makes the server capable and documents the
required probe and replica settings; the change to the deployment repository is done
by the owner afterwards (it is outside this public repository).
