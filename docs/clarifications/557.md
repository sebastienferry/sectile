## Round 1 (2026-09-27)

### Restated request and scope

Generate safe directory names for newly created task worktrees, independently of tracker identity, and resolve the actual checkout consistently for creation, reuse, discovery, desktop launches, and cleanup in primary and secondary repositories. Preserve existing worktrees in place; automatic migration, tracker-key changes, branch renaming, and repairing arbitrary unsafe parent repository paths are outside this ticket.

### Files read and findings

- `.agents/MEMORY.md`: workstation agents own local Git operations; server paths must not become authoritative workstation paths.
- `internal/agent/agent_config.go`: `ensureLocalWorktree` validates keys and assigned branches, then reuses the assigned branch wherever Git reports it, including the main checkout. New paths use the raw task key, including the occupied-path sibling fallback. That fallback sanitizes the branch but still retains the unsafe key.
- `internal/agent/agent_operations.go`: `localTaskPath` resolves by branch first but otherwise builds the raw-key path. Workspace information, removal, diff, and editor operations consume this resolution.
- `internal/agent/agent_desktop.go`: the discussion launch independently probes the raw-key directory and otherwise falls back to the project root. It can miss safe names and nonstandard existing worktrees.
- `internal/agent/repositories.go`: secondary and attached Git repositories call `ensureLocalWorktree`; multi-repository cleanup already resolves by branch and protects the main checkout.
- `internal/agent/agent_config_test.go`: regression coverage already protects reuse of a branch at an arbitrary path while a legacy key directory belongs to another branch; detached worktrees must not match.
- `internal/agent/agent_macro_worktree.go`: macros also generate raw-key worktree directories, use branch-first reuse, and have a separate occupied-path policy. Including them changes the scope and needs an owner decision.
- `internal/agent/agent_skill_files.go`: discovery enumerates Git worktrees rather than predicting their names.
- `internal/workspace/git.go`: broad branch cleanup enumerates actual directories under `.tasks/worktrees`, rather than deriving them from keys. It does not need a naming change.
- `web/src/lib/batchPickup.ts`: user-selected batch directory names already accept only ASCII letters, digits, underscores, and hyphens. Shared batch checkout resolution must remain compatible; batch naming changes are unnecessary.
- `docs/ARCHITECTURE.md`: documents raw-key task paths and needs an update when the behavior changes.
- `docs/clarifications/417.md`: earlier browser-test work recorded Vite failures from paths containing `#`; its accepted harness workaround did not change production worktree naming. It also records that fixing only the Vite root is insufficient when Vite itself is installed under an unsafe path.
- `CHANGELOG.md`: implementation needs a user-facing entry under Unreleased for safe newly generated worktree paths.

### Ambiguities, worst first

1. Does the common safe naming convention cover macro specification worktrees as well as task worktrees? Both generate raw-key paths, but the ticket explicitly names tasks. Including macros touches a separate preparation flow and its tests. See Q1.

### Reversible technical choices resolved from existing conventions

- Keep task IDs, display keys, assigned branches, and remote tracker identity unchanged. Naming is a workstation concern, with no server schema migration.
- Use a centralized deterministic naming policy and a common checkout resolver. Reserve `issue-<number>` for numeric GitHub keys such as `#289`; use a bounded ASCII-safe basename for other keys, with deterministic disambiguation that retains the original key or identity as input. The implementation must cover case-insensitive filesystems, normalization collisions, reserved names, and collisions with the reserved `issue-<number>` namespace; stripping punctuation alone is insufficient.
- Preserve existing validation against empty keys, dot components, and path separators; do not introduce traversal through a legacy lookup.
- Resolve the assigned branch through Git metadata before predicting any path, preserving arbitrary legacy paths, the main checkout, and shared batch worktrees. Never reset another checkout to fit a predicted name.
- When no branch match exists, verify any legacy candidate against the task's assigned branch before reuse. A directory's existence alone is insufficient evidence of ownership.
- A newly generated sibling path for an occupied destination must also be safe and must never overwrite an unrelated directory. Repeated preparation must reuse the actual branch checkout.
- Creation and lookup do not rename or delete legacy worktrees. Explicit handoff/removal continues using the actual checkout and existing non-forced Git removal safeguards; this ticket does not introduce a new cleanup lifecycle.
- Existing worktrees containing `#` remain discoverable and usable by Sectile, but retaining their paths does not repair Vite inside them. The Vite acceptance criterion applies to a newly generated path under a safe repository root, with dependencies installed in that worktree so the verification does not mask an unsafe Vite installation path through a shared dependency directory.
- Keep the existing browser-test workaround from #417; removing it would break supported legacy paths.

### Critical dependencies and validation expectations

- No external service, new database field, or infrastructure repository change is required. Git metadata and local workstation configuration remain the source of checkout location.
- Run meaningful Go naming and real-Git integration tests for safe numeric keys, punctuation and case collisions, occupied destinations, repeat preparation, legacy reuse, mismatched legacy paths, primary/secondary preparation, and consumers such as workspace information and desktop discussion launches.
- Verify a minimal Vite application actually serves and loads its source module from a newly generated worktree, with Vite installed under that path. A naming assertion or a browser harness that relocates execution is insufficient for this acceptance criterion.
- Implementation updates the relevant architecture/agent-contract documentation and adds the user-visible changelog entry. No production code or implementation tests are changed during clarification.
