# Clarification #573 — Desktop task header

Ticket: https://github.com/sebastienferry/sectile/issues/573
Branch: `feat/573`

## Round 1 — 2026-09-28

### Requested outcome

Arrange the desktop task header in two rows: the task title on the left with the execution history dropdown and next-step badge aligned right in the first row; the worktree path on the left with the action buttons aligned right in the second row. This is a layout change to the existing header, not a change to task identity, workflow behavior, action availability, or the footer status.

### Existing behavior and evidence

- `desktop/src/main.js` renders the header in `#toolbar`: `.toolbar-identity` contains the title and worktree path, while `.toolbar-actions` contains the execution history dropdown, view controls, pull request link, run controls, next-step action, next-step badge, and conditional workflow actions. `renderHeader()` builds the title from task identity, optional task name, and selected skill; `renderNextStep()` controls the badge and workflow actions.
- `desktop/src/style.css` uses a wrapping flex layout for `#toolbar`, with the identity and path in a left column and all controls in a right group. The title and path already truncate when space is limited.
- `desktop/tests/task-header.ui.cjs` checks title updates, execution switching, narrow-window truncation, control visibility, keyboard focus, and footer status placement.
- `docs/clarifications/560.md` settles the separate execution-status move to the footer and retains the `Next: <skill>` label beside next-step actions. This ticket changes that label's position in the header only.
- `.agents/MEMORY.md` records that desktop UI tests require a Vite build and `npm run test:ui`; `make test` does not run them.

### Settled layout decisions

1. The first row contains the existing title at left. The execution history dropdown and the existing `#next-step-label` badge occupy the right side, preserving their current visibility conditions and text. The native-terminal indicator remains attached to the title when shown.
2. The second row contains the existing worktree path and its adjacent open-editor and copied-state affordances at left. The existing action bar occupies the right side, including view switching, pull request access, run controls, and workflow buttons. The next-step button remains an action in this row even when its `Next: <skill>` badge appears in the first row.
3. Keep the current order within each group, keyboard access, accessible names, tooltips, disabled/hidden behavior, and selected-run semantics. No control is removed.
4. Preserve both rows at narrow window widths. The title and path may truncate as they do today; controls must remain visible and usable without overlapping or escaping the window. A row may grow in height to accommodate its controls.
5. The generic execution and macro states use the same header layout, with controls hidden according to their existing rules.

### Ambiguities and dependencies

The words “next badge” map to the existing `#next-step-label` element, and “buttons bar” maps to the current action controls. Their placement above resolves the only interpretation choices using the existing component roles. No new service, data, API, migration, or third-party dependency is required. The desktop UI test must cover both rows at normal and narrow widths.

### Open product questions and exit condition

No unresolved product question changes the implementation or acceptance criteria. Owner confirmation of this baseline is pending before transitioning the ticket to `clarified`.

## Round 2 — answers from the owner (2026-09-28)

### Confirmed and added

- The owner explicitly confirmed the two-row header layout from Round 1. That layout is settled.
- The owner also requested that the Console and Changes controls act as toggle buttons so both views can share the content area, separated by a divider bar. This expands the scope beyond header layout. No earlier assumption is reversed; the existing view switch is extended.

### Additional implementation evidence

- `desktop/src/gitDiff.js` currently treats Changes as a single `active` Boolean. Its `view()` hides either `#changes` or `#terminal`, updates the two `aria-pressed` values as opposites, and refreshes the diff when Changes is selected. `select()` and `disconnect()` handle execution changes and stale requests.
- `desktop/src/main.js` creates the diff view with the current content nodes and calls `changes.select()` when the selected run changes. `desktop/src/style.css` gives each content node the available article space and already has a draggable sidebar divider pattern.
- `desktop/tests/git-diff.ui.cjs`, `desktop/tests/discussion-header.ui.cjs`, and `desktop/tests/task-header.ui.cjs` cover the existing view controls and header behavior.

### Proposed split-view behavior awaiting owner confirmation

1. Treat Console and Changes as independent pressed states. With one pressed, that view fills the content area; with both pressed, show Console on the left and Changes on the right with a visible, draggable divider. Prevent turning off the last visible view.
2. Start with Console only, preserving the current default. The divider starts at an even split, can be moved by pointer or keyboard, and needs no saved position across restarts.
3. Keep the existing status footer below the shared content area. Keep console output, selected execution, diff refresh, error states, and focus behavior intact. Load Changes when it becomes visible and discard stale diff responses after a selection change or disconnect.
4. Keep both toggle buttons in the second-row action bar from Round 1.

### Open product question

1. **Q1 — Is the proposed split behavior correct?** Recommended: side-by-side Console and Changes with a draggable divider, Console-only by default, either view full-width when shown alone, and at least one view always visible. If a fixed divider, vertical stacking, or a different default is intended, specify it before the ticket moves to `clarified`.

### Exit condition

The two-row header is confirmed. The split-view addition remains open until the owner answers Q1; no stage transition is appropriate yet.

## Round 3 — answers from the owner (2026-09-28)

The owner confirmed Q1 exactly as proposed in Round 2. Console and Changes are independent toggles. Either visible view fills the content panel alone; when both are selected, Console appears on the left and Changes on the right with a draggable divider. Console alone is the default, at least one view remains visible, and the divider position does not need to persist across restarts. The divider must support pointer and keyboard adjustment.

The two-row header and its control placement from Round 1 remain confirmed. No prior decision is reversed. There are no open product questions or external dependencies. The clarification exit condition is met.
