# Clarification for GitHub #405 (Cross-replica event bus for live board updates and cancellation)

## Round 1: analysis (2026-09-23)

### Request restated

Relay the live events a server pushes to browsers (SSE) to every server instance sharing
the PostgreSQL database, relay cancellations to the instance running the job, and
stop a job's final status update from overwriting `canceled`. Out of scope: agent and
MCP routing (#406, #408), SQLite multi-process, and the web client.

### Files read

- `internal/handlers/handlers.go`: `Event`, `SubscribeEvents`, `BroadcastEvent` (the
  single fan-out), the post-back listener registered in `NewHandler`, the five
  agent-side emissions (`agent_connected`, `agent_disconnected`, `agent_pty_output`,
  `agent_step_status` twice), `HandleEventsSSE`.
- `internal/db/postback.go`: `RegisterPostBackListener`, `notifyPostBackListeners`.
- `internal/db/db.go`: `CancelActivity` (local cancel function, then status),
  `processSkillJob` and the sync, tracker-update and panic paths, each ending with an
  unguarded status `UPDATE`; `internal/db/trackerops.go` final update.
- `internal/db/dialect_postgres.go`: pgx `ParseConfig` + `stdlib.OpenDB`.
- `internal/db/instances.go` (#403): the instance id.
- `web/src/context/AppContext.tsx`, `web/src/hooks/useAgentStatus.ts`: the consumers.

### Findings

- **One choke point.** Every SSE event goes through `Handler.BroadcastEvent`, including
  the post-back events the store raises. Relaying there covers all 18 emission sites
  without touching them.
- **What browsers read.** Only `task_updated` is consumed (`AppContext.tsx`). The agent
  events are sent as named SSE events, but `useAgentStatus` listens to unnamed
  `message` events, so it never receives them: an existing bug, not in this ticket's
  scope, recorded here for #406, which reworks agent status.
- **Why #403.** A relayed message carries the instance that published it, so each
  instance ignores its own messages; that id comes from #403.

### Resolved technical decisions (reversible, settled here)

- **D1: Transport.** PostgreSQL `LISTEN/NOTIFY` on one channel, `sectile_events`, no new
  dependency. A dedicated pgx connection listens, opened from the same configuration
  as the pool, and reconnects with a backoff if dropped. SQLite keeps local delivery
  only: one process.
- **D2: Payload.** A small JSON message: origin instance, kind (`event` or `cancel`),
  event type, task id, activity id, error truncated to 1000 characters. It stays far
  below the 8000-byte limit; the receiver reloads the task and the activity by id.
- **D3: Which events.** All types except `agent_pty_output`, which is emitted per
  terminal chunk, has no consumer, and would flood the channel.
- **D4: Local delivery unchanged.** `BroadcastEvent` still delivers to local
  subscribers at once with the full objects, then publishes. A relayed event is
  delivered locally only, never republished.
- **D5: Cancel.** `CancelActivity` cancels locally if it can, marks the row `canceled`,
  then publishes `cancel`; the instance that holds the job's cancel function calls it.
- **D6: Status guard.** Every terminal and start `UPDATE` of a queued job (start, sync
  end, tracker-update end and not-found, tracker-op end, agent-launch end, panic)
  gains `AND status != 'canceled'`.
- **D7: Lifecycle.** The listener is started by the server (`StartEventBus`), like
  `StartInstance`; tests and tools do not listen. Publishing without a listener
  still works: NOTIFY is a plain statement.
