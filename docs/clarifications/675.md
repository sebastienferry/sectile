# Clarification #675 - A finished run deleted from the activities view comes back as running

## Round 1 (2026-10-02)

Batch `pickup-issues` #675, #690, #693, branch `feat/batch-675-690-693`.

### Request

When a finished `remote_run` is deleted from the activities view while its
console is still open, the agent's next `running_tasks` report recreates it as
`running`, because `SyncRemoteRunStatusFor` finds no row and takes its insert
branch. The fix makes the server remember that it deleted a finished remote run,
so that an agent report never brings it back, while a run the server never knew
about is still inserted from the agent's report.

Out of scope: telling the agent that a run ended (agent protocol, left out of
#393 by decision), deleting a run that is still running, deleting a whole task
or project, and the desktop's own view of the run while its console is open.

- `internal/db/migrations.go`: numbered migrations, last one 45.
- `docs/clarifications/393.md`, gaps 2 and 4.

### Ambiguities, worst first

1. **Which option.** A (server-side record), B (protocol) or C (refuse the
   deletion). Settled below as a technical choice, because A changes nothing a
   user sees except the bug going away, while B reopens a decision of #393 and C
   changes what the activities view allows.
2. **Which deletions are remembered.** Only a `remote_run` row that is
   terminal (`completed`, `failed`, `canceled`) when it is deleted. A running
   run that is deleted and still reported is really running, so recreating it is
   the existing, correct behaviour.
3. **Bulk clear.** "Clear completed activities" removes the same finished runs
   and has the same bug, so it records them too.

### Critical dependencies

- One migration: a new table. It is created with `CREATE TABLE IF NOT EXISTS`
  so the test fixtures that forget schema versions and replay them keep working.
- Multi-replica: the record lives in the shared store, so every instance
  refuses the recreation, whichever one received the deletion.

### Technical choices settled here (reversible)

- **Option A.** A table `deleted_remote_runs (id TEXT PRIMARY KEY, deleted_at
  TIMESTAMP NOT NULL)`. `DeleteActivity` and `ClearCompletedActivities` record
  every terminal `remote_run` they delete, in the same locked section as the
  deletion.
- `SyncRemoteRunStatusFor` checks the record before its insert branch. A
  recorded id is not inserted and the call returns no activity and no error, so
  `ApplyAgentRunningTasksFor` skips the broadcast as it already does for a nil
  activity.
- Retention: records older than 30 days are purged when a new one is written.
  An agent keeps a run until its console exits; a console left open longer than
  that is not a case worth an unbounded table.
- Tests in `internal/db`: the ticket's sequence (launcher run finished, deleted,
  reported `running`), the same through "clear completed", a run first reported
  by the agent still inserted, and a running run deleted then reported still
  recreated.
- `CHANGELOG.md`: one `Fixed` line, since the board showed a ghost run.
