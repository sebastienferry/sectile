# Clarification #735 - Roadmap slicing import from an uploaded file

- Ticket: [#735](https://github.com/sebastienferry/sectile/issues/735)
- Task ID: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-735`
- Report: `docs/clarifications/735.md`

## Round 1 - initial report (2026-10-05)

### Request

The Roadmap framing panel can produce a macro's slicing from `tasks.md` or
`spec.md`, but only by asking the requesting user's local agent to find the
file under `specs/<KEY>-*/` in the workstation's specifications folder. The
ticket adds a one-off import from a file the user picks in the browser: its
content is sent to the server, which parses and merges it exactly like the
agent-read import. Out of scope: choosing or remembering a folder, a
per-macro override, any change to the agent-read import, and the separation of
Macro and Issue specifications folders (#736).

### What the code does today

Files read:

- `web/src/components/RoadmapView.tsx` (import row, around line 3413): three
  buttons `tasks.md`, `spec.md` and "stories", each calling
  `produceMacroSlicing(projectId, macroKey, source)`, disabled while one import
  runs (`slicingSource`) or while a batch holds the macro (`slicingLocked`).
- `web/src/context/AppContext.tsx` (`produceMacroSlicing`): `POST
  /api/projects/{id}/macros/{key}/slicing` with `{ source }`, then a toast
  whose description is the `origin` the server returns.
- `internal/handlers/handlers.go` (around line 1428): routes `stories` to
  `TodosFromMacroStories`, anything else to `TodosFromSDD` after
  `NormalizeSlicingSource`.
- `internal/db/sddslicing.go`: `TodosFromSDD` reads the file through the
  agent (`macro_spec_file`), extracts units with `ExtractTaskGroups` or
  `ExtractSpecRequirements`, builds entries with `SDDEntriesFrom`, merges with
  `mergeSDDEntries`, saves, schedules the tracker mirror, and returns
  `origin + describeAttached(entries)`.
- `internal/db/sddentries.go`: `mergeSDDEntries`, `describeAttached`.
- `internal/sddfiles/sddfiles.go`: the agent-side lookup this ticket bypasses.

### Ambiguities, worst first

1. **How the upload is offered in the panel.** One upload control per source,
   or a single "file" button whose source is inferred. They lead to different
   components and different handling of a file named neither `tasks.md` nor
   `spec.md`. Product question 1.
2. **The wording of the origin.** The ticket says `upload: <file name>`, but
   what Sectile shows at runtime is written in French today, and AGENTS.md makes
   a change of language a decision of its own. Product question 2.

### Settled technical choices (reversible, from the code and conventions)

- **Same endpoint.** `POST /api/projects/{id}/macros/{key}/slicing` accepts two
  optional fields, `content` and `fileName`. With `content` present, the server
  parses that text instead of asking the agent. The routing, the response
  shape (`macro`, `epic`, `origin`) and the web toast stay the same.
- **Shared parsing.** `TodosFromSDD` is split: the agent read stays in it, and
  the extract, merge, save and mirror step becomes a function both the agent
  path and the upload path call. The upload never calls `callAgentContext`, so
  it works with no agent connected.
- **Source rules.** `content` is only accepted with `tasks` or `spec`. With
  `stories`, or with an unknown source, the request is refused rather than
  falling back on `tasks.md` in silence.
- **Size limit: 1 MiB**, checked twice. The browser refuses a larger file
  before reading it. The server reads the body through `http.MaxBytesReader`
  and refuses a larger one with a message naming the limit. The slicing is
  left untouched in both cases.
- **Text only.** The content must be valid UTF-8. The file picker accepts
  `.md`, `.markdown`, `.txt`, `text/markdown` and `text/plain`. Validation
  stays on the server.
- **Empty or unit-less file.** The refusal is the existing "ne porte aucune …"
  message, with the uploaded file in place of the path.
- **Lock.** The upload is disabled under the same conditions as the existing
  buttons (`slicingSource !== null || slicingLocked`).
- **Nothing is remembered.** The upload writes no setting, no file and no
  repository change. The agent-read buttons keep working as today.
- **Strings.** New web labels go in `web/src/locales/planning.ts` (FR and EN).
  Server refusals stay in French, like the neighbouring ones.

### Dependencies

None: no migration, no agent protocol change, no tracker change beyond the
existing slicing mirror.

### Open product questions

1. **Upload control.** Recommended: a small upload icon button attached to
   each of `tasks.md` and `spec.md`, the file being parsed as that source
   whatever its name. Alternative: a single "Fichier…" button that infers the
   source from the name (`spec.md` gives spec, anything else gives tasks).
2. **Origin wording.** Recommended: keep the runtime surface French, with the
   origin reading `fichier importé : <nom du fichier>` (and `imported file:
   <name>` in English if the toast's origin is ever localised). Alternative: the
   literal `upload: <file name>` from the ticket.

## Round 2 - answers from the owner (2026-10-05)

### Settled

1. **Upload control**: a small upload icon button attached to each of
   `tasks.md` and `spec.md`. The file is parsed as that source whatever its
   name.
2. **Origin wording**: the runtime surface stays French. The origin reads
   `fichier importé : <nom du fichier>`, followed by the existing
   `describeAttached` suffix.

### Reversed assumptions

- The ticket's literal `upload: <file name>` origin is replaced by the French
  wording above.

### Settled scope

Every choice of round 1 stands, with the two answers above. No product
question remains open: the clarification is complete.
