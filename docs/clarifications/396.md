Title: *Spike : Have a local board in desktop*

## Round 1: analysis (2026-09-23)

### Restatement

The ticket has a title and no description. Read literally, it asks for a time-boxed
investigation (a spike) into giving Sectile Desktop a task board of its own, so that a
workstation user can see and act on the board without leaving the Electron companion.
Out of scope unless the owner says otherwise: changing the web board itself, the
workflow stages, the tracker adapters, and shipping a production-grade feature from the
spike.

### Evidence and files read

- `docs/ARCHITECTURE.md`: the server owns the store, the web UI is embedded in the
  server binary, the desktop talks only to the local agent over a private loopback
  control API, and Electron packages the agent executable only: never the server.
- `docs/adrs/0003-local-desktop-consoles.md`: "Sectile web owns projects, tasks,
  workflow, reports, and PR/MR links"; the desktop is a console host with navigation
  blocked and a sandboxed renderer behind a narrow preload bridge.
- `docs/adrs/0015-sign-in-is-mandatory-and-settings-are-personal.md`: no anonymous
  board; `webSessionUser()` resolves a session cookie or a workstation API key.
- `desktop/README.md`: today **Connected** (and the project heading's web action) opens
  the board in the external browser; the sidebar is a per-project task list plus the
  execution queue.
- `desktop/electron/main.cjs`: `open-board` and `open-task` call `shell.openExternal`
  on the server URL; tasks reach the renderer through `/desktop/tasks` on the agent.
- `desktop/electron/preload.cjs`, `desktop/src/main.js`: vanilla-JS renderer (no
  React), about 2,200 lines; `openBoard` is its only board entry point.
- `web/src/components/BoardView.tsx`: the React Kanban board (≈900 lines) with the
  columns, grouping and drag-and-drop the web offers.
- `internal/tracker/local.go`, `internal/tracker/registry.go`: "local" already names
  a tracker: a project with no remote tracker, whose tasks live only in Sectile's
  database ("the local board" in `internal/taskmcp/server.go`).
- `.agents/MEMORY.md` §11: desktop suites are outside `make test`; `test:ui` needs a
  `vite build` first.

### Ambiguities (worst first)

1. **What "local" means.** Three readings produce entirely different code:
   - **A: the server's board, shown inside the desktop.** A desktop window or pane
     loads the web board from the connected server instead of `shell.openExternal`.
     Server still required; the work is Electron windowing, authentication of that
     view (the workstation API key or a session) and loosening ADR 0003's navigation
     block for that one origin.
   - **B: a native desktop board.** The renderer draws its own Kanban from
     `/desktop/tasks` (and new agent endpoints for moves/columns). Server still
     required; duplicates `BoardView.tsx` in vanilla JS, or brings React/shared
     components into the desktop build.
   - **C: a board that works without a server.** The desktop runs its own store
     (embedded `sectile-server` with SQLite, or an agent-side store) and shows tasks of
     the existing `local` tracker kind, offline. Contradicts the current topology
     (Electron packages the agent only, the server owns the store) and needs an ADR.
2. **What a spike delivers.** A written finding with a recommendation and an ADR draft,
   a throwaway prototype on `feat/396`, or a first mergeable increment. Changes whether
   production code and tests are expected at all.
3. **Board interactions in scope.** Read-only view, or also moving cards between
   stages, opening task detail and launching skills from a card (which the desktop can
   already do from its task list).

### Critical dependencies

- **Authentication of an embedded view (A):** the web UI mounts only after `/api/me`
  answers; ADR 0015 forbids anonymous access. Either the desktop injects the workstation
  API key (it lives in Electron's main process, never in the renderer), or the view goes
  through the web sign-in (OIDC or local e-mail) inside Electron.
- **Security posture (A/B):** ADR 0003 blocks navigation and keeps the renderer
  sandboxed; loading a remote origin in the app needs a separate, isolated
  `BrowserWindow`/`WebContentsView` with no preload bridge.
- **Topology change (C):** packaging and supervising a server on the workstation, data
  ownership, and how a local-only board coexists with the shared team board. ADR 0006
  ("independent server and agent runtimes") and ADR 0016 (store choice) are affected.
- **Test gates:** desktop tests are outside `make test`; any prototype needs
  `npx vite build` then `npm run test:ui` run by hand.

### Reversible technical choices (resolved from conventions)

- Whatever the reading, the spike's written outcome lives in the repository in English
  (`docs/` and, for a topology or security change, an ADR under `docs/adrs/`).
- The existing `open-board` / `open-task` external-browser actions stay available as a
  fallback until the owner decides to replace them.
- Runtime strings shown to the user stay in French, as the desktop already speaks.

### Open product questions (owner to answer)

1. **Meaning of "local board"**: A (server board inside the desktop), B (native
   desktop board, server still required) or C (serverless board on the workstation)?
   *Recommendation: A.* It reuses the existing board and authentication, keeps one
   source of truth, and is the smallest change that removes the round-trip to the
   browser; C is the only literal "local" reading but reverses the architecture.
2. **Spike deliverable**: written finding + ADR draft only, a throwaway prototype on
   the branch, or a first mergeable increment?
   *Recommendation: finding + ADR draft backed by a minimal prototype on `feat/396`.*
3. **Interaction scope of the board**: read-only, or card moves / task detail /
   skill launch as on the web?
   *Recommendation: full web parity for reading A; read-only for B or C.*
