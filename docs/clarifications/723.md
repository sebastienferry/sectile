# Clarification Report — Ticket #723

**Ticket**: `#723` (`gh-8b726529-6cf4-48cb-91e1-cdb93ccf491c-723`)
**Title**: Stop taking the database write lock on every task list read for the default bookmark
**Date**: 2026-10-14
**Mode**: Autonomous (`pickup-issues` batch)

## 1. Context & Codebase Analysis

1. **Current Write-Lock Contention on Hot Reads**:
   - `GetTasksInScope` (`internal/db/db.go:1923`), `GetTaskFacetsInScope` (`internal/db/db.go:1669`), `GetProjectsForUser` (`internal/db/db.go:6964`), `GetUserProjectBookmarks` (`internal/db/bookmarks.go:61`), and `TaskSourcesInScope` (`internal/db/mytasks.go:149`) all call `EnsureDefaultBookmark(userID)` before taking `d.mu.RLock()`.
   - `EnsureDefaultBookmark` (`internal/db/bookmarks.go:11-21`) unconditionally acquires `d.mu.Lock()` (the exclusive write lock) and executes `SELECT COUNT(*) FROM user_project_bookmarks WHERE user_id = ?` on every call, even though it only inserts a row when a user has zero bookmarks.
   - As a result, every `all`-scope `GET /api/tasks` poll serializes against all other reads and writes on the instance and issues an extra bookmark count query before `bookmarkedProjectsUnsafe(userID)` queries `user_project_bookmarks` again.

## 2. Decisions Recorded

1. **Read-Only Fast Path and In-Memory Seeded-User Tracking (`internal/db/bookmarks.go`, `internal/db/db.go`, `internal/db/membership.go`)**:
   - Track users known to have at least one bookmark in an in-memory set (`d.seededBookmarkUsers`, `sync.Map`) on `DB`.
   - When `userID` is present in `d.seededBookmarkUsers`, `EnsureDefaultBookmark(userID)` returns `nil` immediately without taking `d.mu.Lock()` or `d.mu.RLock()` and without issuing any SQL statement.
   - On a cold cache entry, `EnsureDefaultBookmark(userID)` first checks under `d.mu.RLock()` whether the user already has any bookmark (`hasUserBookmarkUnsafe`). If so, it records `userID` in `d.seededBookmarkUsers` and returns `nil` without ever acquiring `d.mu.Lock()`.
   - Only when the user has zero bookmarks does `EnsureDefaultBookmark(userID)` acquire `d.mu.Lock()`, re-check `ensureDefaultBookmarkUnsafe(userID)`, and record `userID` in `d.seededBookmarkUsers` once a bookmark exists.
   - `BookmarkProject`, `GetUserProjectBookmarks`, and `bookmarkedProjectsUnsafe` also record `userID` in `d.seededBookmarkUsers` when bookmarks are present; `UnbookmarkProject`, `ToggleProjectBookmark` (when unbookmarking), and `DeleteProject` invalidate the cache entry so unbookmarking the last project preserves existing behavior.
   - In `GetTasksInScope`, `GetTaskFacetsInScope`, `TaskSourcesInScope`, `GetUserProjectBookmarks`, and `GetProjectsForUser`, when a user already has a bookmark, the read path never takes `d.mu.Lock()` and issues no default-bookmark check/insert statement.
