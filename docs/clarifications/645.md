## Round 1 (2026-09-29)

### Restated request and scope

When a person triggers an action that writes to the tracker and Sectile refuses it because
that person has no personal token for the provider, Sectile should offer to register the
token right away, in Profile → Tracker credentials, instead of only showing a refusal message.
Out of scope: the refusal rule itself (ADR 0029 stays as is: no fallback to the server
credential), the admin server credential, the credential form, and proactively disabling
actions before they are attempted.

### Verified findings

- **Detection is centralised.** `ForWrite` (`internal/trackerapi/client.go:183`) returns
  `MissingPersonalCredentialError{Tracker}` when the acting user has no personal credential
  for the provider. Its message is English: "no personal GitHub token for this user: add one
  in Profile → Tracker credentials, or the work would be attributed to the server account".
- **Synchronous REST writes** go through `writeTrackerError`
  (`internal/handlers/handlers.go:285`): HTTP 403 with `{"error": "<message>"}`. This covers
  create task (single and batch), comment, clone, convert to remote, migrate, sprints, and
  the macro/epic writes. The anonymous-key refusal (`ErrNoActingUser`) is also a 403, so the
  status alone does not identify the case. **There is no machine-readable code.** The busy
  refusal (`writeTaskBusy`, l.388) is a precedent for a richer error body.
- **Queued writes do not answer with a refusal.** Board column moves, stage changes,
  assignee, parent, team, sprint, and priority/quarter labels answer 200/202. The refusal
  surfaces later: the activity is marked `failed`, and its `error` column holds the message
  (`internal/db/trackerops.go:889`). The web activity poller then shows a generic
  "skill failed" toast without the reason (`web/src/context/AppContext.tsx:1866`). The board
  change is kept locally, and the next sync pull undoes it.
- **Where the token is registered.** On the web, `ProfileModal` has a Trackers tab
  (`TrackerCredentialsTab`) holding one `TrackerCredentialForm` per provider. The modal
  always opens on the `account` tab (`ProfileModal.tsx:57`), and no API opens it on a given
  tab. A second wrapper around the same form, `TrackerSetup`, already exists
  (`isTrackerSetupOpen`) and is shown after a project is saved without credentials
  (`needsCredentialsFor`, `web/src/lib/trackers.ts:328`). Credentials are per user and per
  provider (github, gitlab, jira), never per project (`/api/me/tracker-credentials`).
- **Toasts can already carry an action.** `ToastLink {label, onOpen}`
  (`web/src/types/index.ts:782`) is rendered as a button, and a toast with a link stays on
  screen. Today it is only used to open a created task. Some calls discard the server text:
  task creation throws a generic "createFailed" (`AppContext.tsx:2259`).
- **Desktop has no credential screen.** Settings → Profile is read-only and offers
  "Open the web interface" (`desktop/src/main.js:1669`). Desktop writes (create task,
  "declare as reviewed" → queued stage) only show `err.message` inline.
- **MCP/agents.** `create_task`, `add_comment` and `update_task` return the raw English
  message as the tool error. `transition_stage` answers `trackerSync: queued`, and the
  refusal only lands in the failed activity.
- **Locked credential.** A token that exists but is sealed and not unlocked is a different
  error (`secrets.ErrSealed` / `db.ErrCredentialLocked`). It is not a
  `MissingPersonalCredentialError`, and it keeps the handler's status (400/500).

### Ambiguities (worst first)

1. **Which actions count.** Synchronous writes (create, comment, and so on) get a 403 at
   once. Queued writes (moving a card, stage, assignee, labels), the most frequent ones, only
   fail later, in an activity. Covering them means marking the failed activity as a
   missing-credential refusal and reacting in the poller.
2. **What "offer" means.** Either a notification with a button that opens the profile on
   the right tab, or a dialog embedding the credential form that retries the action once the
   token is saved.
3. **Which surfaces.** Web only, or also Desktop (which has no credential screen and would
   need to open the web interface on the right tab), or also the MCP message given to agents.
4. **Missing versus locked.** Whether a sealed but locked credential should get the same
   offer (to unlock rather than register).

### Critical dependencies

- No migration is needed if the refusal is recognised from a structured code in the REST
  body. Recognising it on a failed activity needs either a stored error code (a new column,
  added in `migrations.go` only) or a stable detection of the stored message. This is to be
  decided at specification.
- ADR 0029 and #482 FR-8 stay in force. This ticket adds a UI path on top of the message and
  does not change the rule.
- The server message is English, while the web interface speaks French. The offer shown to
  the user must be a localised UI text, keyed on a code, not the raw server string.

### Reversible technical choices (settled from the code)

- Add a machine-readable body to the missing-credential 403, following the `writeTaskBusy`
  precedent: `{"error": "<message>", "code": "tracker_credential_missing", "tracker": "github"}`.
  The `error` text is kept unchanged for existing clients and agents.
- Let `ProfileModal` open on a given tab (an initial tab in the app context), and reuse
  `TrackerCredentialsTab` / `TrackerCredentialForm` as they are. Do not add a third
  credential form.
- Reuse `ToastLink` for the action button, with a localised French label.
- Fix the call sites that discard the server error (task creation) so the refusal can be
  recognised there too.

### Product questions (with recommendation)

1. **Queued actions: include them?** Recommended: **yes**. Moving a card or changing a stage
   without a token is the most common way to hit the refusal. When a failed activity is a
   missing-credential refusal, its toast carries the same "Add my token" action instead of
   the generic "skill failed".
2. **Form of the offer: button or inline dialog with retry?** Recommended: **an action in the
   error notification**, "Ajouter mon jeton GitHub". It opens Profile → Tracker credentials
   with the provider concerned. No automatic retry: the user replays the action once the
   token is saved. A queued board move is undone by the next sync, as today.
3. **Surfaces: web only, or also Desktop and agents?** Recommended: **web in this ticket**.
   Desktop and the MCP message stay as they are (the message already names Profile →
   Tracker credentials). Desktop becomes a follow-up ticket: its notice would open the web
   interface on the Trackers tab.
4. **Locked credential: same offer?** Recommended: **no, out of scope**. The ticket speaks of
   an undefined token. A locked one calls for "unlock", a different action, and would be its
   own ticket.

Out of scope, unless the owner reverses it: disabling or annotating write actions in advance
when the token is missing (a proactive check).

## Round 2 - answers from the owner (2026-09-29)

The owner answered the four Round 1 questions interactively and accepted every
recommendation. No product question remains open.

### Settled decisions

1. **Queued actions are included.** When a queued tracker write (board column move, stage
   change, assignee, parent, team, sprint, priority/quarter labels) fails because the acting
   user has no personal token, the toast for that failed activity offers the same action,
   instead of the generic "skill failed". Synchronous writes that answer 403 at once
   (create task, comment, clone, convert, migrate, sprints, macro/epic writes) are covered too.
2. **The offer is a button in the error toast.** Its localised label names the provider, for
   example "Ajouter mon jeton GitHub". It opens the profile on the Trackers tab
   ("Identifiants Trackers") for that provider. There is no automatic retry: the user
   replays the action after saving the token. A queued board move is still undone by the
   next sync, as today.
3. **Web only.** Desktop and the MCP message given to agents stay as they are (the message
   already names Profile → Tracker credentials). Desktop is left to a follow-up ticket, which
   this clarification does not create.
4. **A locked credential is out of scope.** A sealed token that exists but is not unlocked
   keeps its current error, with no action attached.

Also confirmed out of scope: disabling or annotating write actions in advance when the token
is missing.

### Reversed assumptions

None. The Round 1 recommendations stand as written.

### Remaining for specification (technical, reversible)

- How a failed activity is recognised as a missing-credential refusal: a stored error code
  (a new column, added in `migrations.go` only) or a stable detection of the stored message.
- The shape of the structured 403 body (`code`, `tracker`), keeping the `error` text
  unchanged for existing clients and agents.
- How `ProfileModal` receives its initial tab and provider from the app context.
