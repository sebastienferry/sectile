# Clarification of #630: Roadmap | Go from a ticket to its epic and back

Ticket: https://github.com/sebastienferry/sectile/issues/630 (parent M-11, Roadmap).
Report path: `docs/clarifications/630.md`, committed on
`claude/clarify-issue-630`.

## Round 1 (2026-09-30)

### Request

From a ticket that has a parent, the user opens the roadmap on that epic,
selected with its panel shown whatever the roadmap was showing; from an
epic's panel, the user opens the ticket view they came from, filtered on that
epic with the existing parent filter. An epic the roadmap does not hold is
refused with a message naming it and its cause, and no other epic's panel is
opened in its place.

Out of scope: showing the epics of other tracker projects on the roadmap
(#632), a navigation history beyond one step, changing what a click on the
parent key does today (it filters the ticket views), and any server change.

### Ambiguities, worst first

1. **The ticket filters reach the roadmap.** `buildTaskQuery` sends the parent
   filter (and every other ticket filter) to the query the roadmap reads. So
   the return trip sets a parent filter on the ticket views, and the next visit
   to the roadmap shows that epic with its tickets and every other epic empty
   or gone. The round trip this ticket builds makes that visible at once.
   Question 3.
2. **A ticket outside the displayed project.** With "all projects" or a
   multi-project view selected, the roadmap has no project (`currentProject`
   is null). Opening the epic then means switching the selected project, and
   the return trip either keeps the new project or restores the wider scope.
   Question 2.
3. **Where the entry sits on a ticket.** The card menu, the detail header and
   the list row all show the parent key; the key already filters on click and
   the detail's key already opens the tracker. Question 1.

### Critical dependencies

- **#629 (remember the view)**: merged (`e227c762`). The selected epic is
  remembered per project and the panel can be hidden; the focus must write the
  selection through the same setter and bring a hidden panel back.
- **#626 and #627**: merged. Their label and priority filters are among those
  the focus clears so the epic shows.
- **#632 (epics of declared tracker projects)**: open. Until it lands, a Jira
  ticket whose parent lives in another tracker project has no roadmap row and
  is refused; once it lands, the same path finds it.
- **Optional views.** A project that does not enable the roadmap offers no
  entry from its tickets; one that disables the view the user came from sends
  the return trip to the board.
- **No migration, no API.** Web app and strings only.

### Technical choices settled from existing code

- **Focus request.** The ticket side records a one-shot request (epic key,
  project, origin view) in the app context, then switches to the roadmap. The
  roadmap honours it once its epics are loaded, then consumes it, so a later
  filter change never reopens the epic.
- **What the focus changes on the roadmap.** It selects the epic through the
  remembered selection, moves to the tab of its horizon (Unclassified when it
  has none, Hidden when hidden), turns the closed toggle on when the epic is
  closed, clears the roadmap's search, label, priority and "only issues"
  filters, and shows the panel when it was hidden. It leaves the grouping, the
  sort, the row shape and the expanded panel as they were.
- **Unknown epic.** When the loaded roadmap holds no row for the key, the
  request is consumed, the user is sent back to the view they came from, and
  an error toast names the key and says why: the parent is not an epic of this
  project's roadmap, re-read the epics with a sync, or check that its tracker
  project is declared. No selection, tab or filter changes.
- **Return trip.** The epic panel gets an "Open its tickets" button next to
  "Open in tracker", shown when the epic has at least one ticket, open or
  closed. It sets the existing parent filter to the epic key and opens the
  ticket view (board, list, triage or timeline) last shown before the user
  entered the roadmap, by any route; the board when there is none in this
  session or that view is not enabled. The other ticket filters are kept, and
  the parent filter chip clears as it does today.
- **One step.** The origin view is held in memory for the session, not
  stored; entering the roadmap again overwrites it.
- **Strings.** Every new string in French and English. `CHANGELOG.md` gets one
  `Added` line under `[Unreleased]`.

### Product questions

1. **Entry points on a ticket.** Recommended: an entry "Open the epic in the
   roadmap" in the card menu (board and list cards) and a button beside the
   parent key in the detail header. The parent key keeps its current click
   (filter on the card, tracker link in the detail).
2. **A ticket seen under "all projects" or a multi-project view.**
   Recommended: the entry switches the selected project to the ticket's
   project and opens its roadmap; the return trip stays on that project. The
   alternative is to restore the wider scope on the way back, at the cost of a
   parent filter kept on a scope where it means another thing.
3. **Ticket filters on the roadmap.** Recommended: the roadmap's query stops
   sending the parent filter, as it already stops sending the search, so a
   parent filter set by the return trip never empties the other epics. The
   other ticket filters keep reaching the roadmap as today.

## Round 2 - answers from the owner (2026-09-30)

Answered interactively by the owner in the clarification session. All three
round 1 recommendations were accepted; no prior assumption is reversed.

### Settled decisions

1. **Entry points on a ticket.** An entry "Open the epic in the roadmap" in
   the card menu, on the board and the list, and a button beside the parent
   key in the detail header. A click on the parent key keeps its current
   effect: it filters on the card and opens the tracker in the detail.
2. **A ticket seen under "all projects" or a multi-project view.** The entry
   switches the selected project to the ticket's project and opens its
   roadmap. The return trip stays on that project; the wider scope is not
   restored.
3. **Ticket filters on the roadmap.** The roadmap's query no longer sends the
   parent filter, as it already does not send the search. The other ticket
   filters keep reaching the roadmap as they do today.

### Consequences settled from those answers

- **Parent filter chip.** The header chip of the parent filter is not shown
  while the roadmap is displayed, since the filter no longer applies there. It
  shows again, unchanged, on the ticket views.
- **Project switch.** The switch goes through the existing project selector,
  so the ticket filters restored for that project are the ones remembered for
  it; the return trip then sets the parent filter on top of them.
- **Entry availability.** The entry is offered only on a ticket with a parent
  whose project enables the roadmap, whatever the scope currently selected.

None, pending the owner's confirmation that the clarification is
satisfactory.
