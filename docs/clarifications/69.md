# #69 — Discussion moving around the list

Stage: new → clarified.

## Restated request

The task rows in the Sectile Desktop sidebar (one row per task "discussion" /
console, grouped under its project) change position on their own while the user
is looking at or clicking on them. The fix is to make that list's position
stable from the user's point of view, so a row only moves when something the
user actually did or a state change they care about justifies it.

Out of scope: the web board's task list ordering (`web/src/…`), the execution
queue view (`renderQueue`), the comment/discussion list in the web task modal,
and the server-side ordering of `GET /api/runs`.

## What the code does today (files read)

- `desktop/src/main.js:299-305` — a `setInterval` polls every **2 s** and calls
  `refresh()`.
- `desktop/src/main.js:268-287` — `refresh()` compares a JSON serialization of
  the runs payload; any difference triggers a full `render()`.
- `desktop/src/main.js:207-236` — `render()` rebuilds every project group and
  every task row from scratch (`document.createElement` per row, no keyed
  reconciliation), so the DOM nodes are replaced on each render.
- `desktop/src/task-order.mjs` — `orderedTaskGroups()` sorts the groups with
  `compareRuns`, and each group is represented by its own best run
  (`[...executions].sort(compareRuns)[0]`).
- `desktop/tests/task-order.ui.cjs` — locks the current ordering contract
  (introduced by #72: "Order by status and execution start time").

### Why rows move "for unknown reason"

The sort key is volatile, and the list is re-sorted and re-created every 2 s:

1. **Rank flip on status change** — `stateRank` is 0 for `running`/`preparing`,
   1 for `queued`, 2 for everything else. When a run finishes, its row leaves
   the top cluster and drops among the finished ones; every row below it shifts
   up by one.
2. **Time basis flip on start** — `executionTime()` uses `createdAt` while the
   run is `queued`/`preparing`, then switches to `startedAt` once it runs. A row
   therefore jumps at the exact moment it starts, even though its rank may not
   have changed, and it drags its neighbours with it.
3. **Group representative change** — a group is positioned by its *best* run.
   Relaunching a skill on an already-listed task makes a new run the
   representative, so the whole group teleports to the top.
4. **Full DOM rebuild** — even when the order is unchanged, rows are recreated,
   which drops hover state, focus and any in-progress interaction, making the
   list feel like it moves more than it does.

Points 1–3 are the reordering itself; point 4 is what makes it feel abrupt.

## Ambiguities, worst first

1. **What "stable" means.** Two very different implementations: (a) keep the
   current ordering rules but freeze the list while the user is interacting with
   it (hover/focus/pending click), re-sorting only when the pointer leaves;
   (b) change the ordering key to something that does not flip — e.g. sort once
   by first-seen order per project and never re-sort, status only changing the
   row's badge. These are not compatible and (b) partially reverts #72.
2. **Whether the running/finished split must be preserved.** #72 explicitly
   asked for "order by status and execution start time". If rows must stop
   moving when a run finishes, that requirement is being relaxed and
   `desktop/tests/task-order.ui.cjs` has to be amended, not just extended.
3. **Relaunch behaviour.** When a new execution is launched on a task already
   in the list, should the row move to the top (it is now the most recent
   activity) or stay where it is (the user is watching another row)?
4. **Scope of the fix: order vs. DOM.** Even with a perfectly stable order, the
   2 s full rebuild loses hover and focus. Whether keyed row reuse is part of
   this ticket or a follow-up changes the size of the change substantially.

## Critical dependencies

- None external. Everything lives in `desktop/src/main.js`,
  `desktop/src/task-order.mjs` and the Node test suite under `desktop/tests/`.
- Coupling with #72 (ordering contract) and its test file: whichever option is
  chosen, that test must be revisited.
- The payload must expose `createdAt`/`startedAt` reliably; the current fallback
  chain in `executionTime()` already tolerates missing or invalid values.

## Questions (recommended option first)

1. **Which stabilisation strategy?**
   - **Recommended — (a) stable sort key + interaction freeze:** keep the
     status/time ordering, but (i) always derive the time from a single
     immutable field (`createdAt` of the group's first execution) instead of
     switching to `startedAt`, and (ii) suspend re-ordering while the pointer is
     over the list or a row has focus, applying the pending order when the
     interaction ends. Rows then move only on a genuine status change, never
     mid-click.
   - (b) Freeze the order entirely per project (first-seen order), status shown
     only by the badge. Simplest and most predictable, but drops #72's intent.
2. **Does a finished run still fall to the bottom of the project group?**
   - **Recommended:** yes, but only after the freeze is lifted, so it never
     happens under the cursor. Keeping it preserves #72.
3. **Does relaunching a task move its row to the top?**
   - **Recommended:** no. The group keeps the position derived from its first
     execution; the new run shows in the execution history dropdown and in the
     row's status badge. This removes the "teleport" of point 3.
4. **Is keyed row reuse in scope?**
   - **Recommended:** yes, minimally — reuse the existing row element when its
     task key is unchanged and only update its text/attributes. It is the part
     that makes the list feel unstable, and it is a small, local change in
     `render()`.

## Settled scope and assumptions

- The subject is the **desktop sidebar task list**, not the web board and not
  the task-modal comment list.
- The cause is established and reproducible from the code: a volatile sort key
  re-applied by a 2 s poll over a fully rebuilt DOM.
- The fix stays inside `desktop/`; no server, API or database change.
- Acceptance will be expressed as: no row changes index while the pointer is
  over the list; a row's position does not change on `startedAt` becoming
  available; a relaunch does not reposition the group; existing ordering tests
  updated to the agreed contract and extended with a stability test.
- Assumption if no answer arrives before specification: **option (a)** with
  recommendations 2, 3 and 4 as stated above.
