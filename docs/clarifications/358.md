## Round 1 — analysis (2026-09-22)

### Restated request and scope

When synchronizing or importing tickets from external issue trackers (GitHub, Jira), capture and store the ticket creator's identity (`creator`) and avatar URL (`creator_avatar`) on the task entity, persisting them in the database and displaying them in the web and desktop UI alongside existing assignee metadata. For local tasks created directly in Sectile, attribute the creator from the acting authenticated user.

Out of scope:
- Mutating remote ticket creators (ticket authorship is immutable on remote trackers).
- Filtering or faceting the board or list views by creator (a pure display/attribution field for now).
- Altering project ownership semantics (`projects.owner_user_id`).

### Verified findings

1. **GitHub tracker mapping ignores issue creator**:
   GitHub issues API returns the author under `user: { login: string, avatar_url: string }`. In `internal/trackerapi/mapping.go`, `GithubIssueItem` currently only captures `Assignees`, discarding `user` completely.
2. **Jira tracker mapping ignores issue creator & reporter**:
   Jira Cloud REST API returns `creator: { accountId: string, displayName: string, avatarUrls: { "48x48": string } }` and `reporter: { ... }`. In `internal/trackerapi/jira_mapping.go`, `jiraIssue.Fields` ignores both `creator` and `reporter`.
3. **Database schema lacks creator columns**:
   The `tasks` table currently has `assignee` and `assignee_avatar`, but no `creator` or `creator_avatar`. Under ADR 0021, baseline version 1 is frozen; a numbered migration `version: 2, name: "tasks.creator"` is required.
4. **All tasks SELECT/INSERT/UPDATE queries must be updated**:
   As documented in `MEMORY.md`, explicit column lists in `internal/db/db.go` and `internal/db/postback.go` must have placeholders and column lists updated in tandem.
5. **UI has no creator display**:
   `TaskDetailModal` and `ListView` display `assignee` and `assigneeAvatar`, but no creator information.

### Ambiguities, worst first

1. **Jira creator vs reporter semantics**:
   - *Ambiguity*: In Jira, tickets have both `creator` (who entered the ticket) and `reporter` (on whose behalf it was created).
   - *Decision*: Map `creator` with fallback to `reporter` if `creator` is missing or empty. Capture `displayName` (falling back to `accountId`), and avatar from `avatarUrls["48x48"]` (or highest available resolution).
2. **Local tasks creator attribution**:
   - *Ambiguity*: How should tasks created locally within Sectile determine their creator?
   - *Decision*: Set `creator` to the acting user's display name or username from the request context, and `creator_avatar` to their avatar (if available), or empty if unauthenticated. Keep it read-only once created.
3. **UI presentation and interactions**:
   - *Ambiguity*: Where should the creator be shown, and should it be editable?
   - *Decision*: Creator is read-only author information. Display it in `TaskDetailModal` alongside task creation/update metadata or beside the assignee field, with avatar and name.

### Critical dependencies

- **ADR 0021 Migration 2**:
  Add `creator TEXT NOT NULL DEFAULT ''` and `creator_avatar TEXT NOT NULL DEFAULT ''` to `tasks` table via numbered migration in `internal/db/migrations.go`.
- **Full column query synchronization**:
  All SQL queries scanning or inserting `tasks` across `internal/db/` must remain synchronized.

### Essential product questions

1. **UI Display scope**:
   - Option A: (Recommended) Display Creator with avatar in `TaskDetailModal` in the metadata/header area, and optionally in `ListView`, but keep Kanban cards focused on Assignee to avoid card clutter.
   - Option B: Display Creator on Kanban cards as well.
2. **Creator editing**:
   - Option A: (Recommended) Creator is strictly read-only, reflecting the original author on both remote trackers and local tasks.
   - Option B: Allow manual editing of creator in the UI for local tasks.

## Round 2 — answers and settled decisions (2026-09-22)

The recommended decisions were confirmed:

1. **UI Display scope**:
   - Creator is displayed with their avatar in `TaskDetailModal` (metadata / header area near created date / author) and in `ListView`.
   - Kanban cards retain their concise focus on `Assignee` to avoid visual clutter.
2. **Strictly Read-Only Authorship**:
   - `Creator` and `CreatorAvatar` are immutable attributes representing the original ticket author across GitHub, Jira, and local tasks.
3. **Tracker Mapping**:
   - **GitHub**: Map `item.User.Login` -> `task.Creator`, `item.User.AvatarURL` -> `task.CreatorAvatar`.
   - **Jira**: Map `issue.Fields.Creator` (or `issue.Fields.Reporter` as fallback) -> `task.Creator` (`displayName` or `accountId`) and `task.CreatorAvatar` (`avatarUrls["48x48"]`).
   - **Local**: On task creation, populate `creator` and `creator_avatar` from the acting principal user.
4. **Database & Migrations**:
   - Add Migration 2 (`version: 2, name: "tasks.creator"`) with `ALTER TABLE tasks ADD COLUMN creator TEXT NOT NULL DEFAULT ''` and `ALTER TABLE tasks ADD COLUMN creator_avatar TEXT NOT NULL DEFAULT ''`.
   - Synchronize all column lists and scan destinations across `internal/db/db.go` and `internal/db/postback.go`.

**Exit condition**:
All product and technical questions resolved. Zero open questions remain. Stage ready to transition to `clarified`.
