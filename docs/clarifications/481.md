## Round 1 (2026-09-25)

### Restated request and scope

When a project is set up in Sectile Desktop with a local folder that is not a
Git repository, the desktop offers to initialize one there with a first commit,
and explains that this repository does not need to be pushed anywhere: it only
exists so that Sectile can create worktrees from it. Out of scope: creating or
configuring a remote, pushing, creating a hosted repository (GitHub, GitLab),
and any change to the web interface's project settings.

### Verified findings

- The ticket has a two-line description, no comments and no parent epic.
- Desktop project settings expose two folder pickers
  (`desktop/src/main.js`, around line 1313): **Local repository** (the code
  checkout) and **Specifications folder**. A third picker maps each repository
  of a multi-repo project (`showRepositoryChoice` and the repository rows).
- **Local repository** is refused outright when the folder is not a Git
  checkout: the agent answers `Select a local Git repository`
  (`internal/agent/agent_desktop.go:474`). `localProjectRoot` then requires
  `git rev-parse --show-toplevel` on every launch
  (`internal/agent/agent_config.go:175`). A mapped mono-repo folder needs no
  `origin`: the remote identity is only checked when no mapping exists.
- **Specifications folder** accepts a plain folder
  (`normalizeSpecFolder`, `specFolderKind`), and the desktop labels it
  `Folder, not a Git repository`. `ensureMacroWorktree`
  (`internal/agent/agent_macro_worktree.go:57`) then writes the specification
  in place, with no branch, no commit and no worktree, and warns about it. A
  Git folder with no `origin` is already supported ("la base est la branche
  par défaut locale").
- **Multi-repo repository mapping** (`mapRepository`,
  `internal/agent/agent_desktop_repositories.go:93`) requires a checkout whose
  `origin` matches the repository identity. A freshly initialized repository
  has no `origin`, so it would still be refused there.
- Task worktrees are created from the local default branch, `main` then
  `master` (`internal/workspace/git.go:170`), under `.tasks/worktrees/` inside
  the checkout. A repository without any commit (unborn `HEAD`) has no branch
  to start a worktree from, so `git init` alone is not enough: the first
  commit is what makes worktrees possible.
- The desktop interface is written in English; new strings follow it.

### Ambiguities (worst first)

1. **Which pickers offer the initialization.** Local repository only,
   Specifications folder only, or both. The multi-repo mapping cannot accept an
   initialized folder without also adding an `origin`, which changes the
   identity check.
2. **What the first commit contains.** Either the folder's current content
   (`git add -A`, honouring any `.gitignore`), so worktrees carry the files, or
   an empty commit (`--allow-empty`), which makes worktrees possible but leaves
   the existing files untracked and absent from every worktree.
3. **A Git folder with no commit yet** (unborn `HEAD`). It passes today's
   `rev-parse --show-toplevel` check but cannot host a worktree. Either offer
   the same first commit there, or leave it as it is.

### Critical dependencies

- None on the server, the tracker or the database: the change lives in the
  desktop renderer, the Electron bridge and the local agent.
- A commit needs a Git identity (`user.name`, `user.email`). A workstation
  without one makes `git commit` fail.
- A project with no remote cannot reach the pull request stage. The
  explanation must not suggest otherwise; that limit is not changed here.

### Reversible technical choices (resolved from the codebase)

- The initialization runs in the local agent, through a new desktop endpoint
  using `gitLocal`, like every other Git call made for the desktop. Electron
  only forwards the request, as it does for `mapRepository`.
- `git init -b main`: `main` is the first default branch every consumer looks
  for.
- The commit uses the workstation's Git identity. When none is configured, the
  error Git returns is shown as it is, and nothing is half-done beyond the
  `git init` (which a retry reuses).
- The offer is a confirmation shown when a non-Git folder is chosen or saved,
  with an explicit "Initialize a Git repository" action and a sentence saying
  the repository stays local, is never pushed, and only serves worktrees.
  Declining keeps today's behaviour: the Local repository is refused, the
  Specifications folder is kept as a plain folder.
- `.tasks/` is excluded through `.git/info/exclude`, so Sectile's own worktree
  folder never ends up in the user's commits.
- A `CHANGELOG.md` line under `Added`, the change being user-visible.

### Product questions

1. Which folder pickers offer the initialization?
   *Recommended:* Local repository and Specifications folder; the multi-repo
   mapping stays out of scope (it requires an `origin`).
2. What does the first commit contain?
   *Recommended:* the folder's current content, honouring `.gitignore`, so the
   worktrees hold the project's files.
3. Is a Git folder without any commit offered the same first commit?
   *Recommended:* yes, since it cannot host a worktree either.

## Round 2 - answers from the owner (2026-09-25)

### Settled choices

1. **Pickers:** Local repository and Specifications folder offer the
   initialization. The multi-repo repository mapping stays out of scope.
2. **First commit:** an empty commit (`git commit --allow-empty`). Nothing of
   the folder's current content is staged or committed.
3. **Git folder without any commit:** offered the same empty first commit,
   without running `git init` again.

### Reversed assumptions

- The recommendation to commit the folder's current content is reversed. The
  existing files stay untracked in the main checkout, so a worktree created
  from this first commit starts empty: it holds none of them. The explanation
  shown next to the action says so, rather than letting the user discover it
  in a worktree.
- Because nothing is staged, excluding `.tasks/` from the first commit is no
  longer needed for that commit. Adding it to `.git/info/exclude` is kept as a
  reversible convenience for later commits, to be confirmed at specification.

### Resulting scope

- Local repository, non-Git folder: offer `git init -b main` then an empty
  first commit; declining keeps today's refusal.
- Local repository or Specifications folder, Git folder with unborn `HEAD`:
  offer the empty first commit alone.
- Specifications folder, non-Git folder: offer the same initialization;
  declining keeps the plain folder, written in place as today.
- The explanation states that the repository stays local, is never pushed,
  exists only for worktrees, and that worktrees start without the folder's
  existing files.
