## Round 1 (2026-10-08)

### Restated request and scope

When Sectile creates a worktree for a ticket with a Jira key such as `AUC-1234`, the folder under `.tasks/worktrees/` should be named after the key alone, not `key-auc-1234-<64-hex SHA-256>` as today. Out of scope: branch names and the branch name format (`{key}`, `{key_lower}`, `{title}`), the `issue-<n>` names of GitHub numeric keys, user-chosen batch worktree names, and renaming or migrating worktrees that already exist.

The ticket's premise needs a correction: Sectile has no worktree name template. `{key}` is a placeholder of the project's branch name format only (`internal/models/branchformat.go`, `web/src/components/ProjectModal.tsx:999`). The worktree folder name comes from a fixed rule, `safeWorktreeName` (`internal/agent/worktree_paths.go:17`): `#<n>` gives `issue-<n>`, and every other key gives `key-<slug>-<full SHA-256 of the key>`. A Jira key falls in the second case, hence the hash.

### Files read and findings

- `internal/agent/worktree_paths.go`: `safeWorktreeName` builds the name; `availableTaskWorktreePath` and `occupiedWorktreeName` add a `-<SHA-256 of the branch>-<counter>` suffix when the destination is already occupied by something else; the limit is 120 characters.
- `internal/agent/agent_config.go` (`ensureTaskWorktree`) and `localTaskPath`: task worktrees are found by branch first (`worktreeForBranch`), and the predicted folder name is only used to create a new one. Renaming the rule therefore leaves existing worktrees usable where they are.
- `internal/agent/spec_folders.go` (`ensureTaskSpecWorktree`) and `internal/agent/agent_macro_worktree.go` (`ensureMacroWorktree`, `ensureSpecWorktree`): the task specification worktree and the macro worktree use the same helper, so macro keys such as `M-7` or `PE-12` also get the hash today. Both resolve by branch before creating.
- `internal/agent/worktree_paths_test.go` (`TestSafeWorktreeNames`): asserts names match `^[a-z0-9-]+$`, stay within 120 characters, are stable, and never collide case-insensitively, over keys including `#289`, the literal `issue-289`, `A B`/`a b`, Unicode variants, `CON`, `NUL`, and very long keys.
- `docs/clarifications/557.md` and `openspec/changes/557-safe-worktree-directory-names/design.md` (#557, merged as #559): the hash is a deliberate choice. The design says: "Compute SHA-256 from the original key bytes … retain the full hexadecimal digest, so punctuation/case/Unicode variants remain distinct and the `issue-` namespace cannot collide." The `key-` prefix also keeps Windows reserved device names (`CON`, `NUL`…) out.
- `internal/models/branchformat.go`: the branch format and its key slug are a separate rule, unchanged by this ticket.
- `web/src/components/BatchPickupModal.tsx`: the only user-visible "worktree name" is the batch pickup's chosen name, unaffected.

### Ambiguities, worst first

1. **Fixed rule or new setting.** "The template … {key}" can mean (a) change the fixed naming rule so a clean key is used as is, or (b) add a per-project worktree name format with placeholders, like the branch name format. (b) adds a project field, validation, UI and server/agent plumbing. See Q1.
2. **Which keys get the short name.** Only Jira-shaped keys (`ABC-123`), or any key that is already a clean slug (lower-cased, only letters, digits and dashes, nothing dropped or truncated)? The general rule also shortens macro worktrees (`m-7`, `pe-12`) and task specification worktrees, since all three go through the same helper. See Q2.
3. **Exact form of the name.** Bare lower-case key (`auc-1234`) or keep the prefix (`key-auc-1234`)? The ticket asks for "only the Jira key". See Q3.

### Reversed prior decision (#557)

Shortening the name reverses part of #557: for the keys that get the short name, the folder no longer carries a digest. This is safe only for keys whose slug loses nothing. The remaining risk is two keys differing only by case (`AUC-1` and `auc-1`) on a case-insensitive filesystem; Jira keys are canonically upper-case, and an occupied destination still falls back to the existing safe sibling name instead of overwriting. Every other key (punctuation, spaces, Unicode, too long) keeps the current `key-<slug>-<digest>` form.

### Reversible technical choices resolved from existing conventions

- The short name is lower-case, matching the `issue-<n>` precedent and the `^[a-z0-9-]+$` safety rule of #557.
- Guards keep the #557 guarantees: a key whose short name would start with `issue-` (for example a Jira project keyed `ISSUE`, or the literal key `issue-289`), would be a Windows reserved device name (`con`, `prn`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`), would exceed the limit, or would lose characters keeps the hashed form. `#289` and `issue-289` therefore never collide.
- Existing `key-…-<hash>` worktrees are neither renamed nor deleted; branch-first lookup keeps finding them. Only newly created worktrees get the short name.
- The occupied-destination sibling (`<name>-<SHA-256 of the branch>-<n>`) is a different hash, used only when the target folder is already taken by something else. It stays as is and is out of scope.
- Tracker identity, task keys, branch names and the branch name format are unchanged; no server or database change.
