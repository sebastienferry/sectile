# Clarification - #226 - Desktop app: tickets list

Stage: new → clarified.

Ticket: https://github.com/sebastienferry/sectile/issues/226
Related: #225 (Desktop actions bar), #62/#72 (existing project task launcher).

## Restated request and scope

Replace the desktop "Launch task" card stack with a proper **tickets list**: one
row per open task of a project, laid out like the web backlog table, sorted by
priority descending then task identity ascending by default, with sortable
column headers, and a small per-row control that launches a skill on that task.

Out of scope: editing tasks from the list (priority, status, labels, delete,
clone, pin as the web backlog does), multi-selection and bulk launch (#109), a
new server or agent endpoint, changes to the sidebar execution list and its
ordering (`desktop-task-ordering`), and the toolbar entry point of #225.

## Ambiguities, worst first

1. **Where the list lives.** "Like the backlog" implies a table with several
   sortable columns; the current dialog is 720 px wide and stacks one card per
   task. Two readings: keep the dialog and turn its body into a table, or open
   the list in the content area beside the sidebar, the way **Agent logs** and
   the worktree **Changes** view already replace the console. → Decision 1.
2. **What the "small button to run skills" does.** Readings: (a) one button that
   launches the task's next workflow step, as the toolbar **Next: …** does;
   (b) the current skill selector plus Launch, made compact; (c) a per-row menu
   listing every skill. The choice decides whether custom instructions, the
   discussion console and the one-off execution mode (#123) stay reachable from
   the list. → Decision 2.
3. **What "id asc" means.** GitHub keys are `#226`; Jira keys are `PROJ-12`;
   local tasks have no key. Lexical order would put `#9` after `#100`.
   → Decision 3.
4. **Which columns are sortable and how direction toggles.** → Decision 4.
5. **Whether the sort choice persists** across reopenings or restarts.
   → Decision 5.
6. **Whether a task with an active local execution is still launchable** from
   the list. The toolbar disables **Next** while the task runs; the current
   dialog does not check. → Decision 6.

## Critical dependencies

None outside this repository. The data (`priority`, `key`, `id`, `labels`,
`status`, `prUrl`) already reaches the renderer through the existing agent
endpoint, and skill launch reuses `launchServerTask`. No server, agent, database
or tracker change is required. No migration.

## Decisions (reversible choices settled from existing code)

1. **Placement: content-area pane, not the dialog.** The list opens where the
   console sits, like the agent-log pane (`#agent-log-pane`), with a **Close**
   control and Escape returning to the selected execution. Both existing entry
   points (project **Open tasks** icon, **+ → Run an existing ticket**) open it;
   the dialog form is removed. Rationale: a sortable multi-column table needs
   the width; the app already has the pattern; a modal would block reading the
   console while choosing a task. Only one project's list is shown at a time.
2. **Per-row control: one primary button plus a compact menu.** Each row ends
   with a small **Run** button labelled with the next workflow step resolved by
   `nextTaskStep` (`Clarify`, `Specify`, `Implement`, `Review and create PR`,
   or `Close the task` via `closingStep`), launching with the project's default
   mode in one click. A small **…** menu beside it offers **Pickup** (full
   chain), the other server skills, **Discussion (no skill)** and **Custom
   instructions…**; the last one opens the existing prompt textarea and the
   execution-mode control inline under the row before submitting. Rationale:
   this mirrors the web card (`advance` / `advanceAuto` / skill launcher) and
   the desktop toolbar, and keeps every capability of the current dialog
   reachable without a `<select>` on every row. When the next step is
   unavailable (finished, awaiting merge, skill missing, project unconfigured)
   the button is disabled with the message `nextTaskStep` returns as tooltip.
3. **Identity order is natural numeric on the key, falling back to the id.**
   Compare `task.key || task.id` with `localeCompare(…, undefined, {numeric:
   true})`, the same rule as the web backlog. `#9` sorts before `#100`;
   `PROJ-9` before `PROJ-10`. Identity is always the final tie-break, so the
   order is deterministic whatever the server returns.
4. **Default sort and sortable columns.** Default: priority descending
   (`urgent > high > medium > low`, unknown or empty last), then identity
   ascending. Columns: **Key**, **Title**, **Stage** (from `taskStage`),
   **Priority**; all four sortable. First click on a column sorts ascending,
   except Priority which starts descending, as in the web; a second click
   flips the direction; an arrow marks the active column and direction and is
   announced via `aria-sort`. A **PR** icon column reuses the sidebar's pull
   request glyph and is not sortable. Labels, assignee and due date are not
   shown: the desktop has no editing use for them and the width is better spent
   on the title.
5. **Sort choice lives for the window session only.** Reopening the pane
   restores the default order; nothing is written to `settings.json`.
   Rationale: the web backlog behaves the same, and adding a persisted
   preference is a one-line change if asked later.
6. **Active executions stay visible and launchable, with a state glyph.** A
   row whose task has a local execution shows the shared run-state glyph
   (#211) before the title so the user sees it is running; the **Run** button
   is disabled while that task has an active (queued, preparing, running)
   execution, matching the toolbar **Next** rule, while the **…** menu stays
   available for Discussion. Rationale: avoids the double-launch the toolbar
   already prevents, without hiding work in progress.
7. **Search stays and applies server side** through the existing `q`
   parameter, with the same loading, empty and error messages the current
   spec requires; results are sorted after filtering.
8. **Ordering is a pure module with unit tests**, `desktop/src/task-list-order.mjs`
   alongside `task-order.mjs`, so the comparator is tested without Electron.

## Questions for the owner, with recommended option

1. Placement: content-area pane replacing the console view (recommended, decision
   1), or keep the modal dialog and put the table inside it?
2. Row control: **Run next step** button plus a **…** skill menu (recommended,
   decision 2), or keep a skill `<select>` and Launch on each row?
3. Should the sort preference persist in `settings.json`? Recommended: no
   (decision 5).

The recommended options are applied as assumptions below; the specification can
be adjusted if the owner answers differently.

  the content area; entry points unchanged; search unchanged.
