## Round 1 (2026-09-30)

### Restated request and scope

Two small gaps from the #619 Taskativ comparison. First, the global search of
the header stops narrowing the tickets the Timeline reads, as it already does
not narrow the Roadmap (row 2). Second, an epic's framing and its slicing
checklist, today stored in Sectile only, are published as comments on the
epic's tracker ticket and rewritten in place whenever they change, never
posted again (row 47).

Out of scope: a new search on the Timeline (its backlog keeps its own search
field); the parent filter on the Timeline; publishing the macro description,
horizon, priority, quarter or readiness (they already have their own tracker
writes); reading edits made to those comments on the tracker back into
Sectile; any change to how a macro is represented on each tracker.

Row 2, search on the Timeline:

- `buildTaskQuery` (`web/src/context/AppContext.tsx:1367`) sends `q` to the
  server for every view except `roadmap`. On `timeline` a search therefore
  comes back with a truncated `tasks`, and `SprintTimelineView` maps that list
  to sprints (`SprintTimelineView.tsx:253-298`): sprints empty out, with their
  counters and progress bars, and the backlog loses its tickets.
- The Timeline already has a search of its own, on its backlog
  (`backlogSearch`, `SprintTimelineView.tsx:169`), applied client-side.
- No client-side search narrows `filteredTasks`, so exempting `timeline` from
  the server query is the whole fix. Taskativ did exactly this: the exemption
  names the set of views that filter themselves, `roadmap` and `timeline`.

Row 47, framing and slicing as comments:

- The framing is `MacroMeta.FramingComment` (`internal/models/models.go:283`,
  column `macros.framing_comment`) and the slicing checklist is
  `MacroMeta.Todos`. Both are saved by `UpdateMacro`
  (`internal/db/macros.go:306`), which says so: "the horizon, the framing and
  the slicing are Sectile's own". Nothing is sent to any tracker.
- What a macro is on the tracker depends on the tracker:
  - **Jira**: an epic, an issue of its own, which takes comments. The Jira
    adapter can post one (`AddComment`, `internal/trackerapi/jira.go:575`,
    converting Markdown with `MarkdownToADF`) and list them (`GetComments`),
    but cannot rewrite one, and `AddComment` does not return the id Jira gives
    the new comment.
  - **GitHub**: a milestone (`githubMilestoneMacros`,
    `internal/db/macros.go:1467`). A milestone has a title, a description, a
    due date and a state; it has **no comments**. The macro description is
    already written into the milestone description.
  - **GitLab**: a pair of labels (`macro:<title>`, `parent:<key>`), ADR 0030.
    There is no object to comment on at all.
  - **Local board**: no tracker.
- Taskativ, Jira only, publishes two comments per epic (framing, then the
  checklist with the story key of each line turned into a story), finds them
  again by their stored id, then by a footer signature, then creates them, and
  queues the publication as a tracker operation whenever the framing or the
  checklist is saved by a person (never on a sync pass).
- Sectile already has a queue of epic tracker operations
  (`epic_horizon`, `epic_labels`, `epic_priority`, `epic_quarter`,
  `epic_readiness` in `internal/db/trackerops.go`), which is the natural home
  for a new `epic_comments` operation.

### Ambiguities, worst first

1. **Which trackers row 47 covers.** On GitHub, the tracker of this very
   project, a macro has no ticket to comment on. Reading "its tracker ticket"
   as Jira only makes the feature a no-op for GitHub and GitLab projects;
   reading it as "every tracker" requires another carrier on GitHub (a
   section of the milestone description) and has no carrier at all on GitLab.
   The two readings lead to different code. Product question 1.
2. **When the comments are written.** On every save of the framing or the
   checklist (Taskativ), or only on an explicit "Publish on the ticket"
   action. The first keeps the ticket current without a gesture but writes to
   the tracker while the person is still drafting; the second never surprises
   but lets the ticket fall behind. Product question 2.

### Critical dependencies

- A new migration in `internal/db/migrations.go` for the two stored comment
  ids (framing, checklist) on `macros`. Never in the frozen baseline; the
  rewind and replay test helpers must drop the new columns.
- The Jira adapter needs a comment update (`PUT /rest/api/3/issue/{key}/comment/{id}`)
  and a comment creation that returns the new id.
- Tracker writes need an acting person since #482: the queued operation must
  carry the actor who saved the framing, as the other epic operations do.
- Row 2 needs nothing but the web change.

### Reversible choices settled from the code

- Row 2: `buildTaskQuery` exempts the views that filter themselves, `roadmap`
  and `timeline`, as one named set, as Taskativ did. The header search field
  stays visible and keeps its value on the Timeline; it applies again when
  the person goes back to a ticket view. The Timeline's backlog search is
  unchanged.
- Row 47: two comments per epic, as in Taskativ, because the framing is read
  and the checklist is ticked; an empty framing or an empty checklist
  publishes nothing and deletes nothing.
- Each comment is found again by its stored id, then by a readable footer
  signature, then created. A comment deleted by hand on the tracker is
  therefore recreated at the next publication rather than failing it.
- The checklist comment shows each line as done or not and, for a line turned
  into a story, that story's key.
- The comment text is what a tracker reader sees, so it is written in French,
  like the rest of what Sectile shows today (footer such as "Rédigé dans
  Sectile, mis à jour le …").
- The publication goes through the existing tracker operation queue, with its
  activity, so a failure is visible and retried like the other epic writes,
  and never undoes the local save.
- Only a save made by a person queues it; a sync pass never does.

### Product questions for the owner

1. **Which trackers get the framing published?** Recommended: **Jira only**,
   as Taskativ does, since only a Jira epic is a ticket that takes comments.
   On GitHub, GitLab and local projects the framing stays in Sectile, and the
   framing panel says so. Alternative: on GitHub, also write the framing and
   checklist into a delimited section of the milestone description, which
   rewrites text the person may also edit on GitHub. Third option: drop row 47
   from this ticket, since this project is on GitHub and would not use it.
2. **When is the ticket updated?** Recommended: **automatically**, on each
   save of the framing or the checklist by a person, through the queue, as
   Taskativ does. The framing editor already saves only on its explicit
   "Enregistrer" button (`RoadmapView.tsx:2480`), not on every keystroke, so
   each publication follows a deliberate save.
   Alternative: an explicit "Publier sur le ticket" action in the framing
   panel.
