# Clarification - #122 - Introduce a skill to operate transition and reporting

## Round 1 (2026-09-23)

### Request and scope

Add one dedicated workflow skill that owns how a run reports to Sectile — the run indicator (`start_run` / `finish_run`), the stage transition (`transition_stage`, `prUrl`), ticket comments (`add_comment`) and the managed-run result-contract rule — and remove that block from every other generated skill, which then delegates to it. Out of scope: changing the MCP tools themselves, the stage-validation rules on the server, the managed-run result-file mechanism, and the per-skill *content* of what each stage reports (its `## Report` bullets).

### Ambiguities (worst first)

1. **Delegation mechanism.** (a) A real, separately provisioned skill (e.g. `report-stage`) that stage skills are told to invoke/read at start and end; or (b) only a rendering refactor. (b) is already the case at source level, so the ticket is read as (a). Consequence: agents that do not auto-load a referenced skill (Codex, Gemini, plain file readers) must find it by path — the pointer must name the file in the agent's own skill directory.
2. **What moves out.** Only `transition.md` ("Execution and ticket state"), or also `task-access.md` (Sectile task access) and `session-title.md`. The title says "transition and reporting"; task access (reads, fallback to `localhost:8090`) is arguably the same concern. → **Q1**.
3. **Per-skill gates.** Where the "when may I transition" rule lives. → decided below (D2).
4. **Fallback when the helper is not loaded.** Full removal (the ticket's literal reading) risks a run silently never transitioning or never finishing its run; a minimal inline invariant avoids that but keeps some duplication. → **Q2**.
5. **Exposure of the new skill.** Launchable from the board / skill editor like the others, slash-command only, or internal. → **Q3**.
6. **"Reporting" meaning.** Reporting *to Sectile* (finish_run note, transition note, comment) vs. the per-skill `## Report` section. Read as the former; the `## Report` bullets stay in each skill because they differ per stage (D1).

### Critical dependencies

- None external. No migration, no MCP/server API change.
- Provisioning: the new skill must be written to every `models.SkillAgentDirs` directory and to `.claude/commands/`, and cleaned up by the same managed-skill mechanism (`.taskflow/skill-backups/`, user-config install). Adding it to `StageSkills` gives this for free.
- `get_project_context` lists skills; the new one will appear there (fine, it is a reference, not a body — #50).
- Golden-file tests and `catalog_test.go` must be regenerated / extended.
- Nested runs: pickup / pickup_issues embed clarify/specify/implement/adjust bodies; the helper must still enforce "nested skills reuse the outer run; only the owner finishes it".

### Decisions on reversible technical choices

- **D1** — Per-stage `## Report` bullets (what to put in the report) stay in each skill; only the mechanics of *delivering* the report to Sectile move.
- **D2** — Per-skill gates stay in the stage skill as one short line each (clarify: "transition only when the exit condition is met"; adjust: "include prUrl"; pickup: "record each stage after it completes"; others: "`<from>` → `<to>` when this step is complete"). The helper holds everything generic and takes the stage, note, branch and optional prUrl as inputs.
- **D3** — Implementation stays in the existing fragment system: a new `fragments/report_stage/{goal,steps,guard,report}.md` built from today's `contracts/transition.md`; `renderTicketTransitionContract` is replaced by a short delegating paragraph. Skill id `report_stage`, directory/command `report-stage` (`/report-stage`), no `FromStage`/`ToStage` (it does not own a stage). Final name can change at specify time without product impact.
- **D4** — Macro-scoped skills (refine_macro) are unchanged: they render no transition contract today.

### Open product questions (owner: @sebastienferry)

1. **Q1 — Scope of extraction.** Move only the transition / run / comment block (`transition.md`), or also the "Sectile task access" block and the session-title block?
   *Recommendation:* transition + task access (both are "how to talk to Sectile"); keep session title in each skill (it must happen first, before anything is loaded).
2. **Q2 — Fallback in stage skills.** Remove the block entirely and leave only a pointer to `/report-stage`, or keep a 2–3 line inline invariant ("call start_run first / finish_run last; never transition before your gate; managed runs use the result contract only")?
   *Recommendation:* pointer + the 2–3 line invariant, so an agent that fails to load the helper still does not leave a dangling run or transition early.
3. **Q3 — Exposure.** Should `report-stage` be visible and launchable from the board and the skill editor like other skills, or be a slash command only (usable by a human to record a stage by hand) and hidden from board actions?
   *Recommendation:* slash command + visible (read-only-ish) in the skill editor, hidden from board launch actions.

## Round 2 - answers from the owner (2026-09-23)

Answered interactively in the session.

### Settled choices

- **Q1 → transition + task access.** `contracts/transition.md` ("Execution and ticket state") and `contracts/task-access.md` ("Sectile task access") move into the new `report-stage` skill. `contracts/session-title.md` stays inline in every skill.
- **Q2 → pointer + short invariant.** Each task-scoped skill keeps a pointer to `/report-stage` (naming the file in the agent's own skill directory) plus a 2–3 line invariant: call `start_run` before work and `finish_run` when the whole invocation ends (reuse a supplied runId; nested skills never finish the outer run); never transition before this skill's gate; managed runs submit only through their result contract. The per-skill gate line (D2) stays next to it.
- **Q3 → slash command, hidden from the board.** `report-stage` is provisioned like other skills (all agent skill dirs + `.claude/commands/`) and listed in the skill editor, but is not offered as a board launch action.

### Reversed or adjusted assumptions

- None reversed. Round 1 decisions D1–D4 stand. D3 is extended: the new skill's fragments absorb both `transition.md` and `task-access.md`, and `renderTaskAccessContract` is replaced by the delegating pointer as well.

### New ambiguities or dependencies

- The board-hiding filter is new: `internal/db/db.go` (skills the UI offers) must exclude `report-stage` while `internal/db/projectskills.go` (skill editor) keeps it. A catalogue flag (e.g. an internal/utility scope) is the expected vehicle; exact shape left to specify.
- Skills with no stage (`create_pr`, `rewrite_story`) still get the pointer + invariant, since they report runs and comments.

All product questions answered. The owner confirmed the clarification is satisfactory (2026-09-23); exit condition met, transition new → clarified.
