# Clarification #443 - Specifications folder

- Ticket: https://github.com/sebastienferry/sectile/issues/443
- Branch: `feat/443`
- Stage: new -> clarified

## Round 1 - analysis (2026-09-25)

### Request restated

The folder that carries a project's specifications becomes a workstation
setting only, edited from the desktop project settings: the server-side
"Dépôt des spécifications" of the web project modal disappears. On a mono-repo
project it defaults to the local code checkout and can be overridden; on a
multi-repo project the user points it at wherever the specifications live,
which may be a plain folder rather than a Git checkout, and Sectile says which
of the two it is.

Out of scope: the code repository mapping itself (`Projects` in the local
overrides), the SDD framework choice (still a server setting), and the
content or layout of the specifications (`specs/`, `openspec/changes`).

### What exists today (files read)

#426 deliberately introduced **two** declarations, recorded in
`docs/adrs/0026-macro-runs-and-macro-worktrees.md` ("The specifications
repository has two declarations"):

- **Server**: `projects.spec_repo_path` (migration 10,
  `internal/db/migrations.go`), `Project.SpecRepoPath` and the create/update
  requests (`internal/models/models.go`), edited in
  `web/src/components/ProjectModal.tsx` ("Dépôt des spécifications"). Its only
  reader is `macroSpecRepoPath` (`internal/db/sddslicing.go`), used by
  `TodosFromSDD`, i.e. the slicing import `POST .../macros/<key>/slicing`
  (`internal/handlers/handlers.go`). That import reads files **on the server's
  disk**, which is meaningless now that the server is remote.
- **Workstation**: `Overrides.SpecRepos` (`internal/agentconfig/local.go`),
  edited in the desktop settings "Specifications repository"
  (`desktop/src/main.js`), saved by the map-project handler
  (`internal/agent/agent_desktop.go`), which **requires a Git checkout** and
  normalises to its top level. Read by `localSpecRepo`
  (`internal/agent/agent_macro_dispatch.go`) for the macro worktree
  (`ensureMacroWorktree`, `internal/agent/agent_macro_worktree.go`, which also
  refuses a non-Git folder), macro skill launches (`SECTILE_SPEC_REPO`,
  `SECTILE_SPEC_BRANCH`) and `prepare_macro_worktree`
  (`internal/db/macroruns.go` -> agent operation `macro_worktree`).
- `Project.MonoRepo` is a server setting, shown read-only in the desktop
  "Server" panel.

Neighbouring pattern: `PrepareMacroWorktree` already asks the caller's local
agent to act on a workstation path through `callAgentContext`
(`agentprotocol.Operation`). That is the existing way for the server to reach a
local folder.

### Ambiguities (worst first)

1. **Which specifications.** Today only the macro workflow uses the
   specifications folder. Task stages (clarify/specify) write
   `docs/clarifications/<n>.md` and `specs/<n>-*` into the code repository, on
   the task branch, reviewed in the PR. Extending the folder to them changes
   where every task's spec lands and what the PR contains.
2. **Non-Git folder.** The macro worktree, the macro branch, the
   `SECTILE_SPEC_BRANCH` variable and the slicing fallback "read from the macro
   branch" all assume Git. Accepting a plain folder needs a defined degraded
   behaviour.
3. **Slicing import once the server path is gone.** Either the import is routed
   to the requesting user's local agent (needs the desktop agent online), or it
   is removed from the web.
4. **"Automatically filled" and "must be set".** Pre-filling can mean storing
   the code checkout path as the value (it then stops following a later change
   of the local repository) or showing it as the inherited default with an
   explicit override. On multi-repo, "must be set" can mean a blocking error or
   a warning with a fallback.
5. **"This should be indicated".** Either Sectile detects and displays whether
   the folder is a Git checkout, or the user declares it.

### Critical dependencies

- **Server-agent contract**: routing the slicing import to the agent adds an
  operation to `docs/contracts/server-agent-v1.md` and `agentprotocol`; an
  agent older than the server does not know it.
- **ADR 0026** records the two-declaration decision this ticket reverses; a new
  ADR superseding that paragraph is needed.
- **Migration**: removing `spec_repo_path` must be a new numbered migration,
  never an edit of the baseline (see migration notes); the existing server
  values name server paths and cannot be carried to a workstation.
- **Desktop and web** both change; `CHANGELOG.md` gets a user-visible line.

### Technical choices resolved from the code

- The single source becomes `Overrides.SpecRepos`, read through
  `localSpecRepo`; `macroSpecRepoPath`, `Project.SpecRepoPath` and the
  create/update request fields go away, with a numbered migration dropping the
  column. Existing server values are discarded, not transferred.
- The web project modal loses the "Dépôt des spécifications" field; nothing
  replaces it on the web.
- The desktop map-project handler stops requiring a Git checkout for the
  specifications path; it keeps requiring an absolute, existing directory, and
  still normalises a folder inside a Git repository to that repository's top
  level.
- The desktop label becomes "Specifications folder" since the target may not
  be a repository; the desktop UI stays in English.

### Product questions (with recommendation)

1. Scope: macro workflow only, or task stages too? Recommended: macro
   workflow only.
2. Behaviour on a non-Git folder? Recommended: accepted; macro skills write
   directly in the folder with no worktree and no branch, and the slicing reads
   the folder only.
3. Slicing import from the web? Recommended: routed to the requesting user's
   local agent, with an explicit error when none is connected.
4. Mono-repo default and multi-repo requirement? Recommended: show the local
   code checkout as the inherited default and store only an override; on
   multi-repo, an empty value is flagged in the settings and macro operations
   fail with a message pointing to the setting.
5. How is "Git or not" indicated? Recommended: detected automatically and shown
   next to the field.

## Round 2 - answers from the owner (2026-09-25)

The owner took the recommended option on every question (answer: "1A 2A 3A 4A
5A"). No prior assumption is reversed, and the technical choices of round 1
stand.

### Settled decisions

1. **Scope: macro workflow only.** The specifications folder serves the
   slicing import, the macro worktree, macro skill launches and the
   realignment. Task stages keep writing `docs/clarifications/<n>.md` and
   `specs/<n>-*` into the code repository, on the task branch, with the PR.
2. **A non-Git folder is accepted.** Macro skills write directly in the
   folder: no worktree, no macro branch; `prepare_macro_worktree` and the
   launch environment report the folder with no branch, and the slicing
   import reads the folder only (no "read from the macro branch" fallback).
   A Git folder keeps today's worktree-per-macro behaviour.
3. **Git or not is detected, not declared.** The desktop settings detect it
   and show it next to the field; there is no user toggle.
4. **The web slicing import goes through the local agent.** The server asks
   the requesting user's local agent to read the specification files, the way
   `PrepareMacroWorktree` already calls `callAgentContext`. With no agent
   connected, or an agent too old to know the operation, the import fails with
   an explicit message.
5. **Defaults.** Mono-repo: the field shows the local code checkout as the
   inherited value and only an explicit override is stored in
   `Overrides.SpecRepos`. Multi-repo: an empty value is flagged in the desktop
   settings, and macro operations fail with a message pointing to the setting
   (no silent fallback to the code checkout).

### Points left to the specification (technical, not product)

- The name and payload of the new agent operation for reading a slicing
  source, and its entry in `docs/contracts/server-agent-v1.md`.
- How `realign-macro` and the other macro skills behave when
  `SECTILE_SPEC_BRANCH` is empty (non-Git folder).
- Where the desktop reads `monoRepo` from to decide between "inherited" and
  "flagged when empty" (it is already in the project info payload).
- The migration number dropping `projects.spec_repo_path`, and the ADR
  superseding the "two declarations" paragraph of ADR 0026.

### Exit condition

All product questions are answered and none remains open. The clarification
is settled.
