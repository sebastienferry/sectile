# Clarification #755 - Desktop: archive clean-up

- Ticket: [#755](https://github.com/sebastienferry/sectile/issues/755)
- Task ID: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-755`
- Report: `docs/clarifications/755.md`

## Round 1 - initial report (2026-10-06)

### Request

Archiving a task in the Sectile Desktop sidebar ("Archive <task>" or "Stop and
archive <task>") should also remove the task's local worktree, so archived
work stops leaving folders under `.tasks/worktrees/` on the workstation. Out of
scope: the tracker (archiving never transitions, closes or comments on the
ticket), remote branches and pull requests, the web board, and the handoff
skill's own clean-up, which stays as it is.

### What the code does today

Files read:

- `desktop/src/main.js`: `requestArchive` and `archiveTask` (around line 3175).
  Archiving is purely a display state: it stops the active executions when the
  user confirms, then stores the task's run ids in `localTasks[...].archivedRuns`
  (browser `localStorage`) and hides those runs (`hiddenRun`). Nothing reaches
  the agent or the server, and the worktree stays on disk.
- `internal/agent/agent_operations.go`: the agent already answers a
  `remove_workspace` operation. It runs a plain `git worktree remove <path>`
  (no `--force`), so Git refuses a worktree with uncommitted or untracked
  changes, and it refuses a task with no isolated worktree (worktrees off, or
  the worktree is the checkout itself).
- `internal/agent/repositories.go` (`removeRepositoryWorktrees`): the same
  operation over several repositories, for a ticket that changed more than one
  (#456); each repository is reported as removed or failed.
- `internal/db/db.go` (`RemoveTaskWorktree`) and
  `internal/handlers/handlers.go` (`DELETE /api/tasks/{id}/worktree`): the
  server route that sends that operation. No client calls it today.
- `internal/workspace/git.go`: `CleanAllLocalBranches` and `DeleteGitBranch`
  also remove worktrees without `--force` and say "preserve local changes" on
  failure; this is the project's convention.
- `internal/agent/agent_macro_worktree.go`: batch (`pickup-issues`) and macro
  worktrees are shared by several tickets.
- `handoff-issue` skill: removes only an unused, clean worktree and its
  confirmed merged branch, and keeps a shared batch worktree until every ticket
  is handed off.

### Ambiguities (worst first)

1. **A worktree with uncommitted or untracked changes.** Either the archive
   goes ahead and leaves the worktree in place with a message, or the dialog
   offers to delete it anyway (`--force`, the changes are lost), or archiving is
   refused until the worktree is clean. Each leads to different UI and agent
   code. Question Q1.
2. **The local branch.** Removing the worktree keeps the `feat/<n>` branch and
   its commits, including unpushed ones. Deleting the branch as well frees
   everything but can lose unpushed commits, and an unmerged branch needs
   `git branch -D`. Question Q2.
3. **When the clean-up happens.** Always, on every archive, or only when the
   user ticks an option in the archive dialog. Question Q3.
4. **A worktree shared by other tickets** (batch or macro worktree). Removing
   it would break the other tickets' work. Settled below: it is kept.
5. **The specifications worktree.** A project with a distinct specifications
   repository gives the ticket a second worktree there. Settled below: it is
   cleaned like the code worktree.

### Critical dependencies

- The local agent must be connected: the worktree lives on its workstation, and
  the removal is an agent operation. With the agent stopped the archive still
  happens in the UI and the worktree is reported as left in place.
- An older agent answers a multi-repository removal with an empty result;
  `RemoveTaskWorktree` already turns that into "update the agent".
- No migration and no new stored data: the archive state stays in
  `localStorage`, and the worktree path is derived by the agent as today.
- Windows: any new Git call goes through `gitLocal`, which already applies
  `agentexec.Hidden`.

### Technical choices settled from the code (reversible)

- **Reuse `remove_workspace`.** The Desktop asks its local agent to run the
  existing operation for the archived task (a new `/desktop/...` agent route or
  the server's `DELETE /api/tasks/{id}/worktree`, chosen at specification), so
  single- and multi-repository tickets behave the same.
- **Order:** stop executions, then remove the worktree, then hide the runs. A
  removal that fails does not block the archive itself; the failure is shown in
  the dialog (or as an error notice when no dialog was open), naming the
  repository and Git's reason.
- **Only the ticket's own worktree.** Free consoles and macro runs have no task
  worktree and archive as today. A worktree checked out for another ticket of a
  batch, or a macro worktree, is never removed by archiving one ticket.
- **Worktrees off** (`useWorktrees` false): nothing is removed; the main
  checkout is never touched.
- **Context folders** (attached repositories such as argocd-sp) are never
  touched: only worktrees Sectile created for the ticket are removed.
- **Un-archiving** is out of scope: the next launch on the ticket recreates the
  worktree from its branch through `prepare_workspace`, as it already does.
- **Changelog:** the change is user-visible, so the pull request adds a line
  under `## [Unreleased]` / `Changed`.
- **UI text** of new strings is in English, as the rest of the Desktop.

### Product questions

- **Q1 - Dirty worktree.** When the worktree holds uncommitted or untracked
  changes, what does archiving do?
  - (a) **Recommended:** archive the task, keep the worktree, and say why
    ("Worktree kept: it has uncommitted changes"), with a second, explicit
    "Delete worktree anyway" button that forces the removal after a warning
    that the changes are lost.
  - (b) archive and keep the worktree, with no force option.
  - (c) refuse to archive until the worktree is clean.
- **Q2 - Local branch.** Is the local branch deleted together with the
  worktree?
  - (a) **Recommended:** no, keep the branch. Removing the worktree loses
    nothing committed, and a later launch reuses the branch.
  - (b) delete it only when it is merged into the default branch
    (`git branch -d`), keep it otherwise.
  - (c) always delete it.
- **Q3 - Trigger.** Is the clean-up automatic on every archive?
  - (a) **Recommended:** yes, every archive removes the clean worktree, and the
    archive tooltip and dialog say so.
  - (b) opt-in: a "Also remove the worktree" checkbox in an archive dialog,
    remembered per workstation.
