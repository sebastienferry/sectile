## Round 1 — analysis (2026-09-22)

### Restated request and scope

A Jira project key is today the whole of what a Sectile project imports: every work item
of `PE` of the configured issue types lands on the board. This ticket adds a per-project
option that narrows that import to the work items carrying a given Jira **label**, so
several Sectile projects can live on one Jira project key, each owning its own slice.
Out of scope: any equivalent for GitHub or GitLab, changing what a Jira label means for
the workflow stage (ADR 0013 keeps its meaning), the board/column mapping, and removing
from the local board the tasks that were imported before the filter existed (see
ambiguity 4 — it is a real consequence, not a silent one).

### Verified findings

1. **There is a clean insertion point.** `jiraJQL(projectKey, issueTypes, extra)`
   (`jira_mapping.go:250`) already appends an arbitrary `AND <extra>` clause; `SyncIssues`
   passes `""` today and `GetEpics` passes `issuetype = Epic`. A label filter is one more
   `extra` term, `labels = "<value>"`, and needs no new query plumbing.

2. **Nothing Sectile writes would strip the label.** Jira label writes go through
   `labelOps` (`jira.go:391`), which emits `add` / `remove` operations rather than
   replacing the array, and `StaleWorkflowLabels` only ever targets the stage spellings
   listed in `workflowLabelVariants`. A project label set by a human survives every stage
   advance.

3. **Jira labels cannot contain spaces and are case-sensitive.** `cleanLabels`
   (`jira.go:314`) already rewrites spaces to `-` on the write side; JQL `labels = "x"`
   does not match `X`. Whatever the option stores has to be matched verbatim, and a value
   with a space has to be rejected or rewritten at input time rather than silently
   producing a filter that matches nothing.

4. **The import never prunes.** `ImportOrUpdateTasks` (`db.go:939`) is an upsert over the
   returned work items, and `afterTrackerSync` only refreshes teams, columns and PR links.
   A work item that stops matching the filter is not removed from the local board; it
   simply stops being refreshed. This is a behaviour of the feature, not a bug to fix here
   — but it decides what "turning the option on" means for an existing project (question 4).

5. **The setting belongs on the project, not on Settings.** `JiraProject` has a
   user-level fallback (`db.go:2241`, `4701`), but a label whose purpose is to separate two
   Sectile projects sharing one key is meaningless at user level: a global value would
   apply the same slice to both. `IssueTypes` is the right precedent — project-only.

6. **Creation is the hole to watch.** Both remote-creation paths (`db.go:2308` and
   `db.go:5377`) pass only the task's own labels. With a filter on and nothing else done,
   a work item Sectile creates would be written to Jira without the project label and
   would disappear from the board at the next sync (question 3).

### Resolved technical choices (no answer needed)

- **Storage.** One new column `projects.jira_label` (TEXT NOT NULL DEFAULT ''), added with
  the same idempotent `ALTER TABLE ... ADD COLUMN` pattern as `jira_project`
  (`db.go:730`), plus the field on `Project`, `CreateProjectRequest`,
  `UpdateProjectRequest` and the three SQL statements that name the project columns.
- **Query.** `SyncIssues` builds the `extra` clause; the value is quoted and its `"`
  escaped exactly as `jiraJQL` already does for the project key.
- **Empty means today's behaviour.** No label configured ⇒ no `labels` term in the JQL, so
  every existing project keeps importing exactly what it imports now.
- **UI.** A text input in the `issueTracker === 'jira'` block of `ProjectModal.tsx`, under
  "Projet Jira (clé)", French copy like the rest of that panel.
- **Not exposed to agents.** `internal/agentconfig` publishes the tracker identity an
  agent needs (`jiraProject`, repo, remote); a sync-side filter is not part of that
  contract and stays out of `AGENTS.md`.
- **Tests.** `internal/trackerapi/jira_test.go` covers the adapter with a stub site and is
  where the JQL assertion goes; `internal/db/jiratracker_test.go` covers the project-level
  plumbing.

### Dependencies

- SQLite migration on the `projects` table — additive, and the existing pattern makes it
  safe on an already-populated database.
- No third party, no other service, no data to backfill. The labels themselves have to
  exist in the customer's Jira, which is a setup step for whoever turns the option on, not
  work for this ticket.

## Open product questions (Round 1)

1. **Who spells the label?** Free text typed per project (e.g. `team-alpha`, an existing
   label of the customer's Jira), or a value Sectile derives from the project
   (`sectile-<slug>`) and owns? — *Recommendation: free text.* The labels usually already
   exist on the board; imposing a spelling would force a mass re-labelling in Jira and
   would break the moment a project is renamed.

2. **One label, or several?** A single value, or a list matching `labels IN (a, b)`? —
   *Recommendation: a single value for now.* No use case in the ticket needs more, and a
   list can be added later without changing what is stored first.

3. **Should Sectile stamp the label on the work items it creates?** With the filter on,
   an issue created from Sectile that does not carry the label vanishes from the board at
   the next sync. — *Recommendation: yes, add it automatically on creation* (both
   `CreateTask` and `PushTaskToTracker`), which is the only behaviour that makes the
   feature self-consistent.

4. **What happens to what is already on the board when the filter is turned on, or
   narrowed?** Today nothing: the non-matching cards stay, frozen, because the import never
   prunes (finding 4). — *Recommendation: accept it for this ticket and say so in the UI
   hint;* pruning touches every tracker and deserves its own ticket.

5. **How far does the filter reach?** `SyncIssues` only, or also `GetEpics`
   (`jira.go:977`), which lists the epics offered as a parent when creating a work item? —
   *Recommendation: both;* an epic belonging to another Sectile project has no business in
   that list. `GetIssue` by explicit key stays unfiltered either way — asking for `PE-42`
   by name is an explicit request, not a browse.
