# Clarification #732 - Split the ticket transition prompt from the Sectile skills

## Round 1 (2026-10-05)

### Request

Today every Sectile stage skill is a single document. It mixes two things: the
work of the stage (how to clarify, specify or implement), and Sectile's own
contract (task access, run lifecycle, waiting, `transition_stage`, the
pull-request policy). The ticket asks for the work part to be replaceable by a
custom one while the transition part stays Sectile's. A project or team could
then change *how* a stage is done without forking, and slowly losing, the way the
stage is recorded on the board.

Out of scope unless the owner says otherwise:

- republishing or reworking the Equativ marketplace copy of the plugin;
- the inverted `skillCommands` precedence, where the workstation defaults win over
  the project map;
- `get_project_context` reporting the server command instead of the workstation
  override;
- adding new stages or changing the stage enum, which stays fixed.

### Current behaviour (why the ticket matters)

| Customization surface | Where | What happens to the Sectile contract |
|---|---|---|
| Project custom skill (web Skills view) | server `project_skills` | The whole SKILL.md is replaced. The contract is lost unless the author copied it, and it is frozen at the copied version (except adjust). |
| Workstation custom skill | `settings.json` `skills` | Same: whole replacement, frozen. |
| Custom command per stage (`skillCommands`, for example specify → `/plan-jira`) | workstation | Sectile launches `/plan-jira <key>` + the runId line. Nothing tells the command to call `transition_stage`, so the card does not advance. |
| Fork of the plugin (team marketplace) | another repository | The contract is frozen at the fork's version and drifts. |

### Ambiguities (worst first)

1. **Where the work part and the contract are composed.** The two readings lead
   to different code.
   - **(A) Runtime meta skill**, as sketched in the ticket. `clarify-issue` becomes a
     wrapper that tells the agent to run `/clarify-issue-internal` (replaceable), then
     a `/transition` skill. That means new internal skills per stage, a new
     transition skill, and pickup chaining skills instead of inlining fragments.
     - It depends on the agent invoking one skill from another. Claude Code can, through
       its Skill tool. Codex and Antigravity have no equivalent Sectile can rely on.
     - The run, waiting and exit-condition rules must also survive across two separate
       skill invocations.
   - **(B) Render/dispatch-time composition**, generalizing `adjustmentCustomContent`
     and `AdjustmentContract`.
     - A custom skill supplies only the work sections. Sectile still renders one
       SKILL.md, with its contracts around the custom body (custom content), or appends
       the contract to the launch prompt (custom command).
     - It works for all three providers and keeps a single invocation.
   - Recommended: **(B)**. It follows the existing precedents (ADR 0038, adjust and
     clarification 267) and every supported provider can run it.
2. **Which customization surface(s) the split must serve.** Each needs different
   wiring:
   - server project skills;
   - workstation `skills`;
   - `skillCommands` pointing at a foreign command (the `/plan-jira` case, where the
     card does not advance today);
   - a third-party plugin or marketplace shipping only work parts.
3. **Pickup.** `pickup-issue` and `pickup-issues` inline the clarify, specify, implement
   and adjust fragments and ignore any custom skill today. Should a custom work part
   also apply inside pickup?
4. **Existing whole-content custom skills.** Should they keep working as they do,
   be converted to work-only, or be deprecated?
5. **A user-invocable `/transition`.** Should a `/transition` command (or skill) exist
   that people can call by hand, for example after a custom command finished? Or does
   the transition stay internal to the composed skill?

### Dependencies

- **Providers.** Only Claude Code has a dependable skill-invokes-skill mechanism.
  Under reading (A), Codex and Antigravity would need another path.
- **Plugin channel (ADR 0039).**
  - The plugin is generic: it cannot embed a project's custom body.
  - Custom content already reaches a run as a run-local SKILL.md (`writeRunSkill`).
    Composition therefore happens at dispatch for launched runs.
  - A skill invoked by hand from the plugin only carries the built-in work part.
- **Server and storage.** A "work-only" custom skill needs a way to tell it apart from a
  full replacement: a `project_skills.mode` value or a new column, plus the same flag
  in workstation `settings.json`. The web Skills view and the desktop editor have to
  show which mode a skill is in.
- **Contract wording.** The "result-file contract" / "Managed Sectile run" sentences
  in `contracts/transition.md` and `task-access.md` describe a retired mechanism
  (`docs/CAPABILITIES.md:145-155`). They must be cleaned if the contract becomes a
  standalone block that is appended to foreign commands.
- **Goldens.** Moving the contract boundary rewrites
  `internal/skills/testdata/golden/*` and `testdata/plugin/`.
- **ADR.** A new ADR records which parts are Sectile-owned and how they are composed,
  amending ADR 0039's "the plugin is the whole skill".

### Technical choices settled from the code (reversible)

1. **Sectile-owned parts**, never replaceable:
   - frontmatter `name`, ID, directory and command;
   - task access, session title / links / experience / status update;
   - execution and ticket state (start/finish run, waiting, `transition_stage`, PR
     recording);
   - the pull-request policy;
   - the stage's exit condition (for example "never transition new → clarified while a
     product question is open"). It is moved out of `guard.md` into the contract, since
     it governs the transition.
2. **Replaceable work parts**: Goal, Read first, Steps, the remaining guard ("Do
   not") and Report. This is the existing fragment layout. A custom work part may
   replace any subset, and a missing section falls back to the built-in fragment.
3. **One composition function for every stage**, the generalization of
   `adjustmentCustomContent`. Adjust's `## Mandatory adjustment requirements` /
   `AdjustmentContract` becomes one instance of it, not a special case.
4. **Custom work parts are stored as work only**, so a Sectile update to a contract
   reaches every customized skill on its next render or launch, with no re-copy.
5. Changelog: one `Added` line under `[Unreleased]`, plus a `Changed` line if the
   adjust composition visibly changes.

### Product questions

1. **Composition model.** Should Sectile adopt (B), render/dispatch-time composition,
   rather than the ticket's (A), runtime meta skills calling `/<stage>-internal` and
   `/transition`?
   *Recommended: (B).*
2. **Surfaces in scope** (several allowed):
   - (a) server project custom skills;
   - (b) workstation custom skills;
   - (c) `skillCommands` to a foreign command, with the contract appended at dispatch
     so `/plan-jira` advances the card;
   - (d) a third-party plugin shipping only work parts.

   *Recommended: (a) + (b) + (c). (d) depends on (A) or on a plugin-side mechanism,
   and could be a follow-up.*
3. **Pickup.** Should a custom work part also apply inside `pickup-issue` and
   `pickup-issues`?
   *Recommended: yes for content customizations (a and b). A foreign command (c) cannot
   be inlined into pickup, so pickup keeps the built-in work for that stage.*
4. **Existing whole-content custom skills.**
   *Recommended: keep them working unchanged as a "full replacement" mode, add
   "work only" as the new default for new customizations, and never migrate silently.*
5. **User-invocable `/transition`.**
   *Recommended: no in this ticket. Transitions stay inside the composed skill or the
   appended contract, and stage evidence (prUrl, note) keeps being produced by the run
   that did the work.*

## Round 2 - answers from the owner (2026-10-05)

### Answers

1. **Composition model.** "The composite skill could be generated locally when
   you override an internal step." This is composition at generation time, not the
   runtime meta skill: the work steps are overridable, and the agent generates
   the composite locally on the workstation.
2. **Surfaces in scope**: server project skills, workstation skills, and custom
   commands (`skillCommands`). A third-party plugin shipping only work parts is out
   of scope (possible follow-up).
3. **Pickup**: yes for content customizations. Pickup inlines the custom work part.
   A foreign command cannot be inlined, so that stage keeps the built-in work inside
   pickup.
4. **Compatibility**: existing whole-content custom skills keep working as a
   "full replacement" mode, with no silent migration. A user-invocable
   **`/transition`** is added.

### Settled decisions

1. **Composition happens on the workstation.**
   - An override carries only the work steps. The local agent (`sectile-agent`)
     generates the composite SKILL.md: the custom step(s) plus the current Sectile
     contracts from the agent's embedded fragments.
   - The server stores and serves only the overridden work part. It no longer serves
     a pre-rendered full skill for this mode.
   - A contract fix therefore reaches every customized skill as soon as the
     workstation's agent is updated and regenerates.
2. **Override granularity**: the "internal steps" are the existing work sections,
   Goal, Read first, Steps, the guard ("Do not") and Report. They can be overridden
   one by one, and a section that is not overridden keeps the built-in fragment.
   - The Sectile-owned parts listed in Round 1 (technical choice 1), including the
     stage exit condition, are never overridable.
3. **Launched runs.** The agent generates the composite into the run folder
   (`writeRunSkill`, `internal/agent/skillsource.go:262`) at dispatch. It does so for
   server and workstation overrides, and for pickup, where the composite inlines the
   custom work part for each overridden stage.
4. **Custom command (`skillCommands`).** The agent appends the Sectile contract for
   that stage to the launch prompt (the `AdjustmentContract` pattern,
   `internal/agent/agent_config.go:802`), so `/plan-jira <key>` is told to start and
   finish the run and to record its stage.
5. **Full replacement mode is kept** for existing custom skills, which stay as they
   are. Work-only becomes the default for new overrides, and the editors show which
   mode a skill is in.
6. **`/transition` is a generated skill**, from the same `contracts/transition.md`
   fragment, so it cannot drift from the composed skills.
   - It ships in the plugin and in the direct setup, like the stage skills.
   - Usage: `/transition <taskKey> <stage>`. It reads the task, gathers the stage's
     evidence (note, branch, `prUrl`/`prUrls` or `noRepositoryChange`), shows it, and
     calls `transition_stage`. The server's own validation of the stage order and of
     pull requests stays authoritative.
   - Composed skills keep the contract inline. `/transition` is for recording a stage
     by hand, for example after a foreign command that ignored the appended contract.
     It is not a second step of every skill.

### Reversed assumptions

- Round 1 recommended no `/transition`. The owner chose to add one (decision 6).
- Round 1 left open where composition runs (server render or dispatch). It now runs
  on the workstation agent (decision 1).

### New ambiguity

- **Where the composite lives for a skill invoked by hand** (typed `/clarify-issue`
  rather than launched from the board).
  - A launched run needs no installed file: the composite sits in the run folder.
  - A hand invocation runs whatever the provider finds in its skill folder or plugin.
    The plugin (`/sectile:<skill>`) cannot be regenerated by the agent (ADR 0039: the
    agent never writes plugin state).

### Product questions

6. **Hand invocation of an overridden skill.**
   - Should the agent also write the composite to the provider's direct skill folder
     (for example `~/.claude/skills/clarify-issue`)?
   - It would do so whenever an override changes or on init / Initialize /
     `sync_config`, as a managed file, so `/clarify-issue` typed by hand runs the
     custom work too. `/sectile:clarify-issue` from the plugin would stay built-in.
   - The alternative is that overrides apply only to runs launched by Sectile.
   - *Recommended: write it to the direct folder (managed, regenerated, backed up if
     edited by hand, as `refresh` does today).*
