## Round 1 (2026-09-23)

### Restated request and scope

A stage transition that carries PR evidence must work for a project whose
checkout has no `origin` remote, and for a project whose code changes land in
another repository: a missing remote is reported by name, and a `prUrl` that
points to another repository on a supported forge is verified against that
repository instead of the project checkout. Out of scope: creating PRs in
foreign repositories, declaring several code repositories per project in the
settings UI, changing the PR state refresh (it already works from the link
alone), and replaying SFE-360 as part of the pull request.

### Verified findings

- `validateStagePR` (`internal/db/adjustment.go:85`) never uses `prUrl` to find
  the PR. It looks the PR up **by branch** in the project repository, then
  compares the found URL with `prUrl`. A PR in another repository can therefore
  never match, even with an `origin`.
- Routing is decided from the project, not from the link: `stagePRForge` reads
  `gitRemoteUrl`/`githubRepo`. SFE has neither, so the forge is `""` and the
  lookup goes to the local agent (`agentBranchPullRequest`).
- On the agent, `pr_evidence` (`internal/agent/agent_operations.go:296`) calls
  `Runner.BranchPullRequest(target, branch)`, whose first step is
  `git remote get-url origin` (`internal/runner/adjustment.go:128`). Without a
  remote git exits with status 2 and the error surfaces as
  `read repository remote: exit status 2`, wrapped as a generic lookup failure.
- After a successful lookup, `validateStagePR` also calls `git_evidence` and
  requires the **project worktree** HEAD to equal the PR head SHA (and, for
  `adjust`/`pickup`, a clean tree). For a cross-repository PR this check
  compares two unrelated repositories and always fails.
- The agent deliberately ignores server-supplied paths ("A server path is never
  trusted", `localTaskPath`). `Task.RepoPath` and `Project.RepoPaths` exist
  (per-ticket pinned repository, list of known working directories) but are not
  used by `pr_evidence`/`git_evidence`.
- `Project.MonoRepo` already models "tickets span several repositories"; it is
  not used by stage validation today.
- PR state refresh (`internal/trackerapi/prstates.go`) parses the forge and
  repository from each link, so a cross-repository link recorded on a task is
  already refreshed correctly. `PullRequestForge`/`pullRequestReference` are the
  existing URL parsers to reuse.
- The test hook is `prEvidenceLookup func(repo, branch string)`
  (`internal/db/db.go:139`); it does not receive `prUrl`.
- SFE project: Jira tracker, `gitRemoteUrl` and `githubRepo` empty,
  `prCreationStage=implemented`, worktrees enabled. The SFE-360 work lives in
  `~/Sources/iac/argocd/argocd-arch/.tasks/worktrees/SFE-360`, a checkout of
  `gitlab.com/smartadserver/private/arch/argocd-arch` on
  `feature/SFE-360-remove-arch-api`. SFE-360 pins no `repoPath`.
- SFE-360 currently reads `status=implemented`, label `#specified`,
  `branchName=feat/sfe-360`, no PR link: its state was changed outside the
  failed transition, so the literal replay of acceptance criterion 4 may no
  longer be possible as written.

### Ambiguities (worst first)

1. **Which repositories may carry a task's PR.** Today the project repository
   is the implicit trust boundary. Deriving the repository from `prUrl` moves
   that boundary to whatever link the caller supplies. Readings: any
   repository, only for multi-repository projects, or an explicit allowlist;
   each leads to different validation code and possibly a new setting. → Q1.
2. **What replaces the SHA check for a foreign PR.** The project worktree cannot
   vouch for the MR head. Readings: forge evidence only; SHA on a local
   checkout of the target repository when the agent can identify one; or a
   mandatory checkout. → Q2.
3. **How acceptance criterion 4 is verified**, given SFE-360 has already moved.
   → Q3.

### Reversible technical choices (settled from the code)

- **Missing remote:** when no `prUrl` is given and the checkout has no `origin`,
  `BranchPullRequest` returns a typed error whose message names the remote and
  the fix, e.g. `project checkout has no origin remote; configure the project
  repository or pass the prUrl of the repository that carries the pull
  request`. It stays a lookup failure (never absence, never permission to
  create) but is no longer an opaque `exit status 2`.
- **Routing by link:** when `prUrl` is given and names a repository different
  from the project's (or the project has none), validation looks the PR up by
  URL in that repository instead of by branch in the project checkout. The
  forge comes from the link: GitHub through the server's GitHub client for
  that owner/repo; GitLab (host containing `gitlab` or path containing
  `/-/merge_requests/`) through the local agent with `glab mr view <iid> -R
  <host>/<path>`. Any other host is refused as an unsupported forge.
- **Existing rules kept:** the PR's source branch must equal the task branch,
  `models.AcceptPullRequest` still refuses a PR on an unrelated branch, merged
  is accepted, draft is refused where readiness is required, and a forge or
  credential failure on the foreign repository is a lookup failure, not a
  refusal.
- **Protocol:** `pr_evidence` gains an optional `prUrl` field in
  `agentprotocol.Operation`; an older agent that ignores it keeps today's
  behaviour, so no version gate is needed beyond the one #391 added.
- **Tests:** `prEvidenceLookup` is widened to receive the `prUrl`, so the
  cross-repository case and the no-remote case are covered through the same
  hook the existing tests use, plus a runner-level test on a checkout without
  a remote.
- **Same-repository behaviour unchanged:** a project with an `origin` and a
  `prUrl` on that same repository keeps the current path, SHA check included.

### Critical dependencies

- The local agent must be updated alongside the server for the GitLab
  cross-repository path (new `pr_evidence` parameter). An older agent keeps
  failing as today: the explicit missing-remote message is raised by the agent
  too, so it also needs the new version.
- `glab` must be authenticated on the workstation for the target GitLab host;
  the server's GitHub credential must be able to read a foreign GitHub
  repository. Missing access is reported as a lookup failure.
- No database migration unless Q1 selects an explicit allowlist.

### Open product questions (owner: @sebastienferry)

1. **Q1: Trust boundary for a foreign `prUrl`.**
   - (A, recommended) Accept a foreign repository only when the project has no
     code remote configured or is not mono-repo (`monoRepo=false`). A mono-repo
     project with a remote keeps the strict same-repository rule. No new
     setting.
   - (B) Accept any repository on a supported forge, for every project.
   - (C) Per-project allowlist of repositories (new setting, migration, UI).
2. **Q2: Head SHA verification for a foreign PR.**
   - (A, recommended) The agent looks for a local checkout of the target
     repository among the paths it can verify itself: the task's pinned
     `repoPath`, then the project's `repoPaths`, accepting one only if its own
     `origin` matches the `prUrl` repository; it then checks the branch head SHA
     (and cleanliness for `adjust`/`pickup`) there. Without such a checkout, the
     forge evidence alone is accepted and the transition note says the SHA was
     not verified locally. SFE-360 would pass on forge evidence.
   - (B) Forge evidence only, never a local SHA check for foreign PRs.
   - (C) A verified local checkout is mandatory; without one the transition is
     refused with a message asking to pin the task's `repoPath`.
3. **Q3: Acceptance criterion 4 (SFE-360 replay).**
   - (A, recommended) Keep it as a manual post-merge check by the owner once
     server and agent are updated, not a gate of the pull request; the
     automated tests reproduce the SFE-360 shape (no remote, GitLab MR in
     another repository, branch `feature/SFE-360-remove-arch-api`).
   - (B) Drop it, since SFE-360 has already moved to `implemented` by hand.
