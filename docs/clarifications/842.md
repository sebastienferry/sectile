### Ambiguities, in priority order

1. Authorization could mean tool approvals/sandbox, provider account login, or Sectile MCP credentials. These require different settings and workflows.
2. Assistant could mean a user-invoked wizard in engine settings or mandatory first-launch onboarding.
3. Setup could cover only existing Claude/Codex/Antigravity integrations or also install/log in AI CLIs and support custom engines.
4. Completion could mean configuration written, or a live engine check proving skills and MCP are usable.

### Reversible technical choices

- Reuse the engine catalogue and dispatch setup by provider; clearly disclose provider-wide effects for engines sharing it.
- Reuse skills installation and MCP APIs rather than introduce a second configuration writer.
- Keep SDD project setup separate. Preserve unrelated provider settings and existing permission decisions.
- Show each step's outcome and allow retry after partial failure. Read available current state; do not claim complete readiness solely from a prior write.
- Ask the user to choose the project supplying skills rather than silently infer the source when several projects exist.
- Offer the existing remote HTTP default and local proxy choice; keep STDIO accessible as an advanced existing option.
- Do not auto-escalate permissions. Display supported provider-specific controls and explain unavailable ones.
- Preserve the existing runtime surface language; repository artifacts stay English.
- Include a user-facing changelog acceptance criterion in the later specification.

These are proposed implementation conventions, subject to the product answers below, not a technical specification.

### Dependencies and limits

- A paired, running, compatible local agent and a configured project supplying server skills.
- Writable user provider configuration and valid Sectile pairing credentials for remote MCP.
- Local proxy mode depends on the local agent remaining active; remote configuration writes credentials to the provider file.
- Provider-specific permission capabilities and Claude's Windows sandbox limitation.
- Live readiness verification would need an explicit supported probe and engine lifecycle rules; existing configuration endpoints do not prove readiness.
- No database migration or new third-party service is identified for the proposed baseline.
