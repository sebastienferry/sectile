## Round 1 (2026-09-29)

### Restated request and scope

In Sectile Desktop, when a new execution (run) appears for a ticket whose sidebar row is currently selected — the
console shows one of that ticket's earlier executions — the desktop should switch the console to the new execution
instead of staying on the old one. Out of scope: tickets that are not the selected one (their row only updates), the
server and agent (no API change), the web board, and the execution ordering in the sidebar.

"Task" in the title is read as a Desktop *execution*: the sidebar groups executions per ticket (one "local task" row),
while `selected` holds one execution ID.

### Verified findings

Files read: `desktop/src/main.js` (`select`, `render`, `refresh`, `launchTaskWork`, `submitTicketLaunch`, the `#rerun`
dialog, `openAgentConsole`), `desktop/src/task-order.mjs`, `desktop/src/run-console.mjs`,
`desktop/tests/execution-history.ui.cjs`.

- `refresh()` (`main.js` ~l.680) re-selects only the **already selected** execution, when its status or session
  changes, or picks the first visible execution when nothing is selected. A new execution of the same ticket is never
  selected by the poll.
- The ticket row stays highlighted (`isSelected = executions.some(id === selected)`) and its glyph/label follow the
  group's representative execution (active first, then newest, `task-order.mjs`), so the row can show the new run as
  running while the console still shows the old, finished one. That mismatch is the bug.
- Only one path already switches: the toolbar **Next step / Full chain** buttons (`launchTaskWork`, ~l.3036) select the
  execution that was not in the list before the launch, if the same ticket is still displayed.
- Paths that do **not** switch today:
  - the **Relaunch** dialog (`#rerun`, ~l.2782): `launchServerTask` then `refresh()`;
  - a launch from the **Tickets** pane (`submitTicketLaunch`, ~l.2730) for the ticket whose row is selected;
  - a launch from the **web board** or any other client, which reaches the desktop through the agent's run list on the
    next poll;
  - a new execution that starts in `queued` state and only later becomes `running`.
- `select(run, true, {deferrable:true})` is the existing "background" selection: it keeps the Tickets pane open and
  defers the sidebar rebuild while a rename field or menu is busy (`sidebarBusy`). A queued or preparing execution
  shows the console notice "Execution queued. Waiting for a console." and the existing status-change branch of
  `refresh()` attaches the console once it starts.
- The execution history drop-down (`#execution-history`) lets the user deliberately pick an older execution of the
  ticket.

### Ambiguities (worst first)

1. **Which launches trigger the switch.** Only launches made from this desktop (relaunch dialog, Tickets pane), or any
   new execution of the displayed ticket that shows up in the run list, including web-board launches. Different code:
   hook each launch path vs. detect "new execution for the selected ticket" in `refresh()`.
2. **Deliberate history choice / live console.** If the user picked an older execution from the history drop-down, or
   is typing in the displayed execution's still-running interactive console, does a new execution still take over?
3. **Queued executions.** Switch as soon as the new execution appears (showing the "queued" notice, then attaching
   automatically when it starts), or only when it starts running.

### Critical dependencies

None outside the desktop renderer: the agent already lists every execution with `taskId`, `createdAt` and `status`.
No migration, no server change.

### Resolved technical choices (reversible, from existing conventions)

- Detect the new execution by comparing the previous and next poll (`runs` vs `next`), as `announce(transitions(...))`
  already does, and reuse `select(run, true, {deferrable:true})` so the switch does not close the Tickets pane nor
  break a rename in progress.
- Match the ticket with the existing `taskKey(run)` grouping; free consoles and macro runs keep their own keys and are
  not affected.
- When several new executions of the ticket appear in one poll, select the one the row shows (the group's
  representative: active first, then newest).
- Keep the existing `launchTaskWork` selection; the new detection makes it redundant but harmless. The specification
  decides whether to fold it in.
- Hidden projects (disconnected) are skipped as `select` already does.
- Covered by a Playwright UI test in `desktop/tests/` in the style of `execution-history.ui.cjs` (a fake agent whose run
  list gains a new execution between two polls).

### Product questions (with recommendation)

1. **Scope of sources** — Recommended: any new execution of the displayed ticket, whatever launched it (desktop
   relaunch, Tickets pane, web board, another client). Alternative: only launches made from this desktop window.
2. **Older execution chosen from the history, or a live interactive console** — Recommended: always switch to the new
   execution; the history drop-down still lets the user go back. Alternative: do not switch while the displayed
   execution was picked from the history, or while it is still running.
3. **Queued executions** — Recommended: switch as soon as the new execution appears, showing its "queued" notice, and
   attach its console automatically when it starts. Alternative: switch only once it starts running.
