## Round 1 (2026-10-07)

### Restated request and scope

The ticket asks for "MCP/API support for Macro" but has no description or discussion, so the intended operations and callers are unknown. The clarification must identify which macro capabilities should be exposed through MCP, HTTP, or both; changes to the macro UI and the specification skills are outside the proposed scope unless the owner asks for them.

### Files read and existing behavior

- `internal/taskmcp/server.go`: `get_macro` reads one macro by project ID and key; `update_macro_todos` replaces its ordered todo list. Macro worktree preparation and run reporting are already available. Task tools provide a pattern for typed reads and writes with caller identity.
- `internal/taskmcp/macros_test.go`: verifies reads, todo replacement, rejection of unknown macros, linked-story preservation, and anonymous write refusal.
- `internal/handlers/handlers.go`: HTTP already lists macros, creates, edits, and deletes them under `/api/projects/{id}/macros`; subroutes cover skill runs, slicing, labels, and tracker copy actions. No single-macro GET route is visible in the generic macro branch.
- `internal/models/models.go`: `MacroMeta` includes identity, title, description, framing, horizon, status, closed state, axes, labels, todos, computed write flags, and tracker copy status.
- `internal/db/macros.go` and `internal/db/macrotodosmirror.go`: contain macro CRUD and the existing single-macro read used by MCP. Some writes affect a remote milestone or queue tracker synchronization.
- `.agents/MEMORY.md`: server tracker operations must use its HTTP tracker abstraction, and writes carry the acting user's identity.
- `docs/adrs/0026-macro-runs-and-macro-worktrees.md` and `docs/adrs/0051-macro-and-issue-specifications-folders.md`: macro runs and worktrees already have separate contracts from task runs.

### Ambiguities, worst first

1. **Meaning of "support".** It could mean an MCP equivalent of the existing HTTP macro CRUD, an HTTP read of one macro, a complete MCP/HTTP parity effort, or only a subset needed by an agent workflow. Each yields a different tool and route set.
2. **Permitted mutations.** Full lifecycle support includes create and delete, which can create or remove a remote milestone and detach child tasks. Metadata editing alone has a smaller impact. The ticket does not say which the agent may invoke.
3. **Included macro operations.** Slicing, story creation, labels, run launching, and tracker copy repair exist as HTTP subactions but not as dedicated MCP macro tools. Including them substantially expands the API contract.
4. **Read coverage.** HTTP currently lists project macros while MCP gets one. The request could require list on MCP, get-one on HTTP, both, or neither.

### Critical dependencies

- Remote tracker support differs for local macros, GitHub milestones, and Jira epics; create, edit, and delete can have remote side effects or partial local success.
- The MCP caller must be identified for writes, following the existing `requireCaller` and acting-user context pattern. The HTTP routes already apply web-session identity.
- New MCP tools change the server catalog used by the workstation's bridge; compatibility and tool tests would be required during implementation.
- No schema migration appears necessary if the request exposes existing macro operations.

### Reversible technical choices from conventions

- Address macros with `projectId` plus `macroKey`, as `get_macro` does; a key alone is not globally unique.
- Reuse existing database operations and authorization rules, rather than maintain a second macro implementation.
- Keep writes explicit and typed. Preserve partial-success behavior where a remote tracker refuses a write after local persistence; do not silently report complete success.
- Retain existing HTTP `/api/projects/{id}/macros` routes and their response shape unless the owner identifies an incompatibility.

### Product questions for the owner

1. **Which outcome is #781 meant to deliver?** Recommended: complete the basic macro resource contract: MCP list, get, create, and update metadata, plus HTTP get-one; reuse existing HTTP list/create/update. Should delete be included, or reserved for the UI?
2. **Should this ticket expose the advanced macro actions through MCP?** Recommended: no; leave slicing, story creation, labels, run launching, tracker copy repair, and worktree preparation on their current interfaces, and handle any specifically needed action in a separate ticket. If an agent workflow needs one now, name it.
3. **May agents create or delete macros?** Recommended: allow create with an identified caller and the same project/tracker rules as HTTP, but reserve delete for a separately confirmed destructive action. If neither is needed, narrow question 1 to read and metadata update.

## Round 2 - answers from the owner (2026-10-07)

The owner answered "confirmed" and "Confirm the proposed operation set and agent permissions" in the interactive specification session, approving the recommended scope presented there.

### Settled scope and decisions

- Complete basic macro resource support: MCP list/get/create/update metadata and HTTP get-one, reusing existing HTTP list/create/update behavior.
- Allow creation and metadata editing by identified agents with existing project/tracker rules and acting-user propagation.
- Add no agent deletion capability. Existing HTTP deletion remains unchanged.
- Exclude new MCP slicing, story creation, arbitrary label management, run launching, tracker copy repair, and worktree operations. Existing interfaces remain unchanged.
- Preserve dedicated todo replacement and its linked-story protections.
- Use project ID plus macro key for addressing and preserve truthful partial-success reporting for saved local changes with reported tracker failures.
- Apply OpenSpec from the live project configuration, reusing `feat/781` and the assigned worktree.

The technical metadata contract covers title, description, framing comment, horizon, closed state, priority, quarter, and readiness from the existing editor. Todo lists, arbitrary labels, and computed fields are not accepted by metadata editing.

### Reversed assumptions and remaining dependencies

No prior settled decision was reversed. Round 1 recommendations are now accepted scope. Tracker capability differences, acting-user credentials, and asynchronous copy behavior remain implementation constraints; they require no further product decision.
