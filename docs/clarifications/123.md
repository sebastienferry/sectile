# Clarification - #123 - Autonomous or interactive skill runs

Stage: new → clarified (re-clarification of an already specified change).

## Restated request and scope

A skill run is either **autonomous** (the provider CLI runs headless, nobody
answers it, the worker posts the stage transition) or **interactive** (a terminal
window the user answers, and the stage moves only when the user confirms). The
choice is configurable per skill in the web configuration, overridable for a
single launch from the web, and overridable for a single launch from the desktop
app; the resolved value decides how the agent invokes the CLI.

Out of scope: the web PTY terminal (`HandleTerminalWs`), the content of the
skills themselves, adding an AI provider, and what
`/api/tasks/{id}/advance/confirm` does for an interactive run.

## What changed since the first clarification

The first pass produced the OpenSpec change
`openspec/changes/123-interactive-or-headless-skill-runs` (commit `65c5d72`). It
covered the per-skill setting, the project default, the one-off override on the
card, and the headless invocation on the agent. This re-clarification adds one
missing surface and settles the vocabulary:

- **New**: the desktop app is a first-class launch surface and must offer the
  same one-off choice. It was absent from the change's impact list, although it
  is the surface a user actually sits in front of.
- **Settled**: "autonomous" is now the product word for a headless run, so the
  `>>` chain loses that word and becomes the **full chain** run.

## Ambiguities, worst first

1. **"Autonomy" already means the `>>` chain.** `EnqueueAutonomousRun` chains
   steps until `AutonomousStopStage`, and the web `>>` launches the `pickup`
   skill that does the whole ticket. Using the same word for a single headless
   run would leave two features named identically in the UI and the spec.
   → Resolved by decision 4.
2. **Which launch surfaces carry the one-off choice.** "Quand on lance la tâche"
   is ambiguous between the card's advance action and the detail modal's skill
   launcher; the desktop has three entry points, one of which is a one-click
   button with no dialog to put a control in. → Resolved by decisions 1 and 2.
3. **Whether the project default survives.** The request enumerates three levels
   (skill config, web launch, desktop launch) and omits the project default the
   first pass introduced. → Resolved by decision 3.
4. **What an autonomous run shows in the desktop app.** The desktop UI is built
   around one console per run and already renders "No console is available for
   this execution" as an error state (`desktop/src/main.js:116`). → Settled
   below as an assumption: the pane stays, read-only.

## Critical dependencies

- None external. The change is additive on the server, the agent and both
  clients; both new project fields default to today's behaviour.
- Blocked at clarification time: the local Sectile server is unreachable (MCP
  server `sectile` reports `CONNECTION_CLOSED`, `http://localhost:8090` refuses
  the connection), so this clarification could not be posted as a ticket comment
  and the `new → clarified` transition could not be applied. Both remain pending.

## Decisions

1. **Web surfaces** - the one-off choice appears on the card `...` menu advance
   action *and* on the skill launcher of the task detail modal. Every surface
   where the user explicitly triggers a skill offers it.
2. **Desktop surfaces** - the choice appears in the "Launch" dialog and in the
   "Relaunch" dialog, and is valid for that launch only. The footer
   "Next: <label>" button stays a single click and uses the resolved mode.
3. **Project default kept** - precedence stays at four levels: one-off override
   > skill setting > project default (`defaultSkillMode`) > interactive.
4. **Vocabulary** - a run is **autonomous** or **interactive**, in the UI, the
   spec and the persisted values (`autonomous` | `interactive`). The `>>` action
   is renamed **full chain**, and its project setting becomes
   `fullChainStopStage`.

## Settled scope and assumptions

- The mode is resolved on the server where the job is enqueued and travels to
  the agent on `agentconfig.Dispatch`; the agent never re-decides it. Unchanged
  from the first pass.
- `RunSkillRequest` gains an optional mode field. An absent field means "no
  override", not "interactive", so the precedence chain still applies.
- The desktop IPC (`launchServerTask`), the `/desktop/tasks` POST input and
  `desktopTasks`'s forwarded body each carry the same optional field. The agent
  does not interpret it beyond passing it on.
- A desktop autonomous run keeps its row and its output pane in the app: the
  pane streams the captured CLI output read-only instead of hosting a PTY, so
  the run list, selection, log export and stop button keep working.
- An interactive run keeps today's behaviour exactly, on both clients.
- The full chain run forces the autonomous mode on every step it enqueues, and
  refuses to start when the provider has no attested headless invocation.
- Providers with an attested headless invocation: `claude -p`, `codex exec`,
  `vibe -p`. `agy`, `gemini`, `cursor` and a custom `AICommandTemplate` without
  a mode placeholder refuse an autonomous launch with an explicit error rather
  than falling back to interactive.
- Renaming `AutonomousStopStage` to a full-chain name is an internal rename with
  no stored value to migrate; the constant keeps serving as the fallback for a
  project with nothing stored.
- No production code is written at this stage and the specification of the
  change is updated, not started from scratch.
