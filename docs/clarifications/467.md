## Round 1 (2026-09-25)

### Restated request and scope

Build a Grafana dashboard that charts the Prometheus metrics the Sectile server
already exposes at `/metrics` (ADR 0027): HTTP traffic, errors and latency per
controller, active users, active runs, the running build, and the Go runtime
and process series. Adding new metrics, alerting rules, and changing how the
server is scraped are out of scope unless the owner says otherwise.

### Verified findings

- The ticket body is only the dev deployment's `/metrics` URL; there are no
  comments and no parent epic.
- `internal/metrics/metrics.go` exposes `sectile_http_requests_total`
  (`handler`, `method`, `code`), `sectile_http_errors_total` (`handler`,
  `method`, `class`), `sectile_http_request_duration_seconds` (histogram,
  `handler`, `method`, default buckets, streams excluded),
  `sectile_active_users`, `sectile_active_runs` (`status`),
  `sectile_build_info` (`version`, `commit`), plus `go_*` and `process_*`.
- ADR 0027 and the README fix the aggregation rules a dashboard must follow:
  HTTP series are per replica and are **summed**; board series are read from
  the shared database and identical on every replica, so they take **`max()`**,
  never `sum()`. A failed database read leaves a gap, not a zero.
- The README already documents the reference PromQL for error rate, p95
  latency, active users and active runs.
- The dev deployment is already scraped: `sectile_build_info` is present in the
  dev Thanos datasource of the company Grafana, with `namespace`, `pod`,
  `service`, `env` and `k8s_cluster_name` labels. The per-cluster dev
  Prometheus datasource does not return it; Thanos does.
- No Sectile dashboard or folder exists in that Grafana yet.
- The repository is public: datasource UIDs, cluster names, pod IPs and
  internal Grafana URLs must not be committed.

### Ambiguities (worst first)

1. **Where the dashboard lives.** A JSON model committed to this repository and
   imported by hand, a dashboard created only in the company Grafana, or a
   dashboard provisioned as code from the deployment repository lead to
   entirely different deliverables.
2. **Which environments it covers.** Dev only, or a selector over dev, the
   `testenv-*` boards and a future prod namespace.
3. **Panel scope.** Only the existing metrics, or also panels that require new
   series (for instance run durations or tracker sync failures).

### Critical dependencies

- A Prometheus-compatible datasource that retains the Sectile series (the dev
  Thanos datasource today). No prod deployment is scraped yet.
- Write access to a Grafana folder if the dashboard is created there.
- No server change, migration or new metric is needed for the recommended scope.

### Resolved reversible choices

- Datasource and namespace are dashboard variables (`$datasource`,
  `$namespace`, optionally `$pod`), so nothing environment-specific is baked in
  and the JSON is safe for a public repository.
- Aggregation follows ADR 0027: `sum` for HTTP series, `max` for board series.
- Proposed layout, in rows: **Overview** (running version from
  `sectile_build_info`, replica count, active users, active runs by status);
  **HTTP** (request rate by handler, 5xx ratio by handler, 4xx rate, p50/p95/p99
  latency by handler, top handlers by traffic); **Runtime** (goroutines, heap
  and RSS, CPU, GC pauses, open file descriptors), per pod.
- The `/metrics` handler itself is filtered out of the HTTP panels by default,
  since it only reflects scrapes.

### Product questions for the owner

1. **Location.** Recommended: commit the dashboard JSON model to this
   repository (e.g. `deploy/grafana/sectile.json`, with variables and no
   internal identifiers), document the import in the README, and import it
   once into the company Grafana. Alternatives: Grafana only, no file; or
   provisioned from the deployment repository.
2. **Environments.** Recommended: a `$namespace` variable defaulting to the dev
   namespace and listing every Sectile namespace present (dev, `testenv-*`,
   prod later).
3. **Scope.** Recommended: existing metrics only; new series become their own
   ticket. Alerting stays out of scope.
