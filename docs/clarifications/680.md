## Round 1 (2026-10-06)

### Request

On Jira, a project may map the epic priority and the epic quarter each to one
closed-list custom field (single select or two-level cascading select) picked
from an epic's edit screen, with option maps deduced only to fill holes and
editable by hand; an axis write sets the label and the field, and the import
reads the field first and the label second. A project that maps no field keeps
exactly today's label-only behaviour, with no extra tracker request.

Out of scope, unchanged from #635: a field for the readiness axis or the
horizon, writing one axis to two fields, the ticket priority (part B), GitHub
and GitLab, and migrating values already written.

### What changed since #635 was specified

These are corrections to the #635 plan, not new decisions:

1. **Migration number.** The plan names migration 41; the next free one is
   48. The column stays `projects.epic_axis_fields`, `TEXT NOT NULL DEFAULT
   '{}'`, added in `migrations.go` only and dropped by the rewind helpers.
2. **Where the settings live.** The spec says "the Roadmap section of the
   Tracker tab"; a Roadmap tab has since been added and already holds the
   axis prefixes. The field pickers and option maps go in that tab, under the
   prefixes.
3. **Storing what is learned.** Part B introduced the pattern for a mapping
   discovered from the tracker and stored on the project (merge that fills
   holes, never overwrites a hand-set line). The quarter map learned at write
   time reuses that pattern rather than a new one.

### Ambiguities, worst first

1. **Whether part C is built at all (gate G1).** The ticket, the #635
   clarification and AC1 make part C conditional on an explicit confirmation
   by the owner, given on this ticket after A and B are merged. No such

   Question 1.
2. **Epics of a declared roadmap project (#632).** The roadmap also shows

### Critical dependencies

- **Parts A and B: merged.** Nothing else blocks the start.
- **Migration 48**, new project column only (see above).
- **Jira only.** Discovery needs one epic of the project and edit rights on it
  (`editmeta`); a project with no epic yet cannot discover its fields, and the
  setting says so.
- **#632 axis writes.** On a declared roadmap project, a field write happens
  only where `RoadmapAxisWrites` already allows the label write.
- **Public repository.** No `customfield_<n>` id and no real field or option
  name in code, tests, fixtures or docs (AC7, C8).

### Technical choices settled from existing code

- **Declared roadmap projects.** Jira custom field ids are site-wide, so the
  mapping of the project whose roadmap shows an epic applies to every epic it
  shows, exactly as part A applies that project's prefixes (US3.5 of #635).
  Reading costs nothing more: the mapped field ids join the one epic search.
  Writing to an epic of a declared project follows `RoadmapAxisWrites`; when
  that epic's edit screen does not carry the field, the label is written and
  the activity says the field is absent from that epic, as for a value with no
  option.
- **Everything else** is as settled in #635: candidates are single and
  cascading selects from `editmeta`, detected from the schema `custom` suffix;
  priority map prefilled only on an exact level label; quarter map deduced
  from `2026 - Q4`, `2026-Q4`, `2026 Q4`, or a year parent with a quarter
  child stored as `parent/child`; a value with no option leaves the field
  untouched and is named in the activity; a cleared value clears the field;
  an unmapped field value read at import is ignored and the label decides; an
  epic whose field and label disagree joins the pending pushes.

## Round 2 - answers from the owner (2026-10-06)

Answered interactively by the owner in the clarification session.

### Settled decisions

1. **Gate G1: part C is confirmed, on one condition.** The owner's first answer
   was "I do not want a mapping in Sectile's code: it is open source". Asked
   whether part C as specified meets that, the owner confirmed it in that form:
   - Sectile compiles in no field and no option. The candidate fields are
     listed from an epic's `editmeta` at runtime, and the person picks the
     field and maps its options in the project settings.
   - The field id, its kind and the option maps are project data stored in the
     database, never in the repository.
   - Tests, fixtures and docs name only synthetic fields and options.
   - The deductions (an option labelled exactly `P0` for `p0`, the recognised
     quarter formats) stay: they are generic rules over whatever options the
     site returns, they only fill holes, and every line remains editable by
     hand.
2. **G1 is closed.** Tasks C1 to C10 of `specs/635-epic-axes-tracker-fields/`
   apply, with the corrections of round 1 (migration 48, settings in the
   Roadmap tab, part B's store-and-merge pattern for learned quarter options)
   and the round 1 choice for the epics of declared roadmap projects.

### Reversed assumptions

None. The owner's concern restates guardrails already in the #635
specification (US14, FR-C7, AC7); it becomes an explicit acceptance criterion
of this ticket: no tracker-specific mapping lives in Sectile's code, only in a
project's stored settings.

### Open product questions

None.
