## Round 1 — initial analysis (2026-10-02)

### Restated request and scope

Sign people in to Sectile through Auth0 on every surface they use: the web app, Sectile Desktop, the local agent and MCP clients. Once signed in, a workstation should stay signed in for about 90 days, through reboots, with no new sign-in. Out of scope unless confirmed otherwise: changing the role model (ADR 0013), the sealed tracker credentials (ADR 0014/0044), supporting an identity provider other than through the existing generic OIDC configuration, and repairing the stale MCP header of a particular workstation.

### Verified findings

- **The 90-day goal is already met on the machine side.** The agent, Desktop and MCP all use one workstation API key (ADR 0011). Its default lifetime is 90 days (`DefaultAPIKeyTTL`, `internal/db/identity.go:21`), it can be renewed with the same secret, and it is stored on disk, so a reboot never asks for a new sign-in. Desktop keeps the key encrypted with Electron `safeStorage` and starts the agent with `TOKEN=<key>`.
- **What re-authenticates often is the web session.** It is an opaque cookie with a fixed 12-hour lifetime (`WebSessionTTL`, `internal/db/sessions.go:16`). There is no sliding renewal and no refresh token. When it expires the user goes back through the identity provider.
- **Auth0 already fits the web sign-in without new code.** Web sign-in is generic OIDC: discovery, authorization code flow with PKCE and a nonce, identity read from UserInfo, subject stored as `issuer|sub`, configured by `SECTILE_OIDC_*` (`internal/auth/oidc.go`). ADR 0013 names Okta or Auth0 as the target, "neither of which is wired up yet". Clarification #237 notes that Auth0 needs a post-login Action to emit a namespaced role claim, to be verified against a real tenant.
- **No machine surface talks to an identity provider.** The agent, Desktop and MCP get their key by redeeming a 10-minute pairing code that a signed-in web user creates. The server checks keys as opaque hashes (`AgentAPIAuth`, `internal/handlers/agent_api.go:93-131`). The repository has no JWT or JWKS validation, no `audience` handling, and no OAuth discovery endpoint (`/.well-known/oauth-protected-resource`, `oauth-authorization-server`, `WWW-Authenticate` with `resource_metadata`). ADR 0008 chose UserInfo over JWT verification on purpose.
- **MCP clients carry a static bearer.** `internal/agentconfig/mcp.go` writes `~/.claude.json` with `headers.Authorization: Bearer <key>`. Because the header is set, Claude Code disables its own OAuth fallback. This session's MCP connection was refused with 401 "Valid agent bearer token required", which means the key is unknown or revoked, not expired (an expired key gets "API key expired"). Re-pairing creates a new key but does not rewrite an older MCP entry, so the old one goes stale. That is a separate issue from Auth0.
- **A standalone agent cannot read a key Desktop encrypted.** Desktop saves the encrypted key as `secret` (`desktop/electron/credential-store.cjs:7`). The Go agent's `ReadConnection` reads only `apiKey` (`internal/agentconfig/connection.go:17-50`). An agent started by Desktop is not affected, because Desktop passes `TOKEN`. An agent started by hand on the same workstation is.
- **Long web sessions would weaken an existing safeguard.** Unlocks of sealed personal credentials assume the owner is present, with a 30-minute idle window (`internal/db/credentialunlocks.go`, ADR 0032). Logout forgets them. A 90-day web session would not break this check, but it would keep that presence assumption valid for much longer.
- **Reusable building blocks exist.**
  - Jira OAuth (`internal/atlassian/oauth.go`, ADR 0044) already stores rotating refresh tokens and handles `invalid_grant`.
  - `internal/secrets` seals stored secrets (it needs `SECTILE_SECRET_KEY` under PostgreSQL).
  - Key renewal and per-workstation revocation already exist.

### Ambiguities (worst first)

1. **What "the agent, Desktop and MCP connect through Auth0" means in code.**
   - (a) They present Auth0-issued tokens. The server then validates Auth0 JWTs through JWKS and an audience, which reverses ADR 0008 and needs a new ADR. Desktop and the Go agent would need their own OAuth flow (loopback redirect with PKCE, or device authorization grant). They would store and rotate refresh tokens. `/mcp` would implement RFC 9728 discovery, with Auth0 as the authorization server: either Dynamic Client Registration enabled on the tenant, or a pre-registered client per MCP client.
   - (b) They keep the Sectile key described in ADR 0011, but you get it by signing in to Auth0. Desktop or `sectile-agent pair` would open the browser on Auth0, and the server would mint the 90-day key for that identity. The pairing code stays as a fallback.
   - **Recommendation: (b).** It meets "Auth0" and "90 days through reboots" with the existing renewal and revocation. MCP keeps working with a static header. It also avoids a JWT stack and an ADR reversal.
2. **Whether "90 days" also covers the web app.**
   - (a) A fixed 90-day cookie.
   - (b) A sliding session: for example 90 days of absolute lifetime, renewed on activity, with an idle timeout.
   - (c) Keep Auth0 refresh tokens (`offline_access`) and refresh the session silently. The real lifetime would then be capped by the tenant's refresh-token settings.
   - **Recommendation: (b), 90 days absolute with an idle timeout to be agreed.** The ADR 0032 unlock window stays at 30 minutes regardless.
3. **MCP OAuth.**
   - (a) Make `/mcp` an OAuth protected resource, so Claude Code signs in through Auth0 by itself.
   - (b) Keep the bearer key and make sure it is kept up to date. For example, rewriting the `sectile` entry when the key changes would have prevented this session's 401.
   - **Recommendation: (b) in this ticket, (a) as a follow-up** if it is wanted. Option (a) depends on Auth0 tenant features (DCR or pre-registered clients) and on JWT validation.

### Critical dependencies

- **An Auth0 tenant**, plus whoever administers it, with:
  - a Regular Web application for the server (client ID, secret, callback URL);
  - a Native application if Desktop or the agent start the sign-in themselves;
  - the post-login Action that emits the role claim (#237);
  - refresh-token rotation and lifetime settings, if refresh tokens are used.
  All of this needs a real tenant to verify. It cannot be assumed from Auth0's defaults.
- **A new ADR, under option 1(a) only**: it replaces part of ADR 0008 (JWT validation) and touches ADR 0011.
- **`SECTILE_SECRET_KEY` under PostgreSQL**, if the server stores Auth0 refresh tokens.
- **The deployment environment.** `deploy/` holds only a Grafana dashboard, so the production `SECTILE_OIDC_*` values live outside this repository.
- **Data.** No migration for 1(b) beyond linking a key to its OIDC subject; the existing `device_credentials` table already belongs to a user. Option 2(b) may add a column to `web_sessions`.

### Reversible technical choices (resolved from code and conventions)

- Keep the generic OIDC client: Auth0 is configuration (`SECTILE_OIDC_ISSUER=https://<tenant>.auth0.com/`), as ADR 0008/0013 intend. No Auth0 SDK.
- Any stored refresh token follows the Jira OAuth pattern (rotation, `invalid_grant` means sign in again) and is sealed with `internal/secrets`.
- Desktop keeps `safeStorage`. Make the Go agent able to use the key Desktop stores, or make Desktop always hand it over, so that an agent started by hand survives a reboot as well.
- The pairing code stays as the headless and offline fallback (ADR 0019: no open mode on machine surfaces).
- Report text in English (AGENTS.md); user-facing strings stay in French.

### Open product questions (owner)

1. **Machine surfaces:** option 1(b), Auth0 sign-in that mints the existing 90-day key, or 1(a), Auth0 tokens end to end? *Recommended: 1(b).*
2. **Web app:** should the 90 days apply to the web session too, and as which model? *Recommended: 2(b), a sliding session with 90 days absolute and an idle timeout.* Which idle timeout (for example 7 or 30 days)?
3. **MCP:** keep the bearer key (and keep it fresh) here, with OAuth discovery as a follow-up ticket? *Recommended: yes.*
4. **Tenant:** does an Auth0 tenant for Sectile already exist, and who can create the applications and the role Action? Is Auth0 the only provider to support, or must Okta keep working through the same generic configuration? *Recommended: generic OIDC kept, Auth0 verified first.*
5. **What does "re-authenticate on every reboot" refer to today?** The web sign-in after 12 hours, Desktop asking for pairing again, or the MCP 401? The code shows only the first as expected behaviour. The other two would be bugs worth fixing within this ticket.
