## Round 1 (2026-09-28)

### Restated request and scope

The web sidebar's project picker gets a short menu with the 3 most recent non-favorite
projects and the favorites. Search covers every project, matching the name, slug,
description, repository and tracker, with at most 6 results and keyboard navigation.
A new "Browse projects…" entry opens an overview of every project, which can be filtered
by text and tracker.

Out of scope: any API or server change (recents are client-side), a global shortcut to open
the picker, the desktop app's project picker, and the collapsed-sidebar project button.

### Files read

- `web/src/components/Sidebar.tsx`: the picker, `searchBookmarked` / `searchOthers`,
  the list's `max-h-48 overflow-y-auto`, "All projects" and "New project…".
- `web/src/context/AppContext.tsx`: `setSelectedProjectId` (persists
  `sectile_selected_project_id`), `openBoardView`, the `/` shortcut and task deep links that
  select the task's project.
- `web/src/components/CommandPalette.tsx`: it also calls `setSelectedProjectId`.
- `web/src/types/index.ts`: `Project` and `ViewMode`.
- `web/src/locales/shell.ts`: `projectPicker` strings in both locales.
- `CHANGELOG.md` `[Unreleased]`, and the mockup's source.

### Verified findings

- `Project` has no activity date. `updatedAt` is the date of the last change to the project's
  configuration, not of its last task activity. The mockup sorts "Other projects" matches by
  last activity and shows "active N days ago" on the cards. Neither can be computed without
  an API change, which the ticket excludes.
- The favorites list is not capped when the search is empty. The only thing that keeps the
  menu short today is its own `max-h-48` scroll area. With 10 favorites, the "no scrollbar"
  criterion needs either a cap or a menu taller than the viewport.
- In the mockup, favorites that match are never capped: only "Other projects" are trimmed to
  `6 - favorites`. With 8 favorites matching, it shows 8 rows, which breaks the "at most
  6 results" criterion.
- The mockup draws the overview as a section below the menu. It doesn't say whether the
  product renders it as a modal or as a view in the main area.
- The web app already has several modals (`ProjectModal`, `BoardViewModal`,
  `CommandPalette`). `ViewMode` is a routed list of main-area views that the sidebar
  navigation reads.
- Every project selection goes through `AppContext.setSelectedProjectId`: the picker, the
  command palette and the task deep link. The initial restore from `localStorage` does not.

### Critical dependencies

None. There is no server, migration or third-party change: the data comes from the `projects`
list the web app already loads, plus `localStorage`.

### Technical choices settled from the code (reversible)

1. **Where recents are recorded.** `setSelectedProjectId` records every explicit project id,
   whether it comes from the picker, the overview, the command palette or a task deep link.
   `'all'` and the restore at startup are not recorded. One hook point means no path can be
   missed.
2. **Storage.** The key is `sectile_recent_project_ids`: a JSON array of ids, most recent
   first, capped at 10 so that recents can still be filled after favorites are skipped. Ids
   of unknown or deleted projects are ignored when the array is read. Every read and write
   sits in a `try/catch`. If storage is unavailable, the history lives in memory for the
   session.
3. **Search cap.** At most 6 project rows in total, favorites first, as the acceptance
   criterion requires (unlike the mockup). The "N more matches in the overview →" link counts
   every match left out, favorites included.
4. **Matching.** Text is normalized to NFD with diacritics stripped and case folded. Matching
   covers the name, slug and description. It also covers the repository: every
   `repositories[].remote` or `gitRemoteUrl`, and `githubRepo` or `gitlabProject`. For the
   tracker, it covers the label (GitHub / GitLab / Jira / Local) and `jiraProject`. The
   second line of a row shows the description excerpt only when the match is in the
   description. Otherwise it shows the tracker and the repository, with the matched term
   highlighted.
5. **Displayed repository.** The first repository (the code remote), shortened to
   `owner/name`. When there is none, the slug is shown, as in the mockup.
6. **Keyboard.** Opening the menu focuses the search field. ↑ / ↓ cycle through the project
   rows and the "more matches" link. Enter opens the highlighted row; with no highlighted row
   and a non-empty query, it opens the first result. Esc clears the query, then closes the
   menu and gives focus back to the trigger. Action entries stay reachable with Tab. The `/`
   shortcut is not changed.
7. **Menu rows.** They keep the favorite star, the task count and the configure button they
   have today. Overview cards have the star but no configure button.
8. **"Browse projects…" count.** `projects.length`, the same number as the menu header.
9. **Empty search result.** It explains what the search covers: name, slug, description,
   repository and tracker. "No favorite project" disappears: with no recents and no
   favorites, the menu shows only its actions and "Browse projects…".

### Open product questions

1. **"Last activity" on the cards, and the order of "Other projects".** The server exposes no
   activity date, and the API is out of scope.
   - **A (recommended):** replace it with "opened N days ago", taken from this browser's
     history, and show nothing for a project never opened here. Order "Other projects"
     matches by that history, then A–Z.
   - **B:** drop the information entirely. Order the matches A–Z.
   - **C:** add an activity date on the server, which brings an API change into scope.
2. **Favorites overflowing the short menu.** Nothing caps the favorites, and the menu must not
   scroll.
   - **A (recommended):** show at most 6 favorites, A–Z, followed by "N more favorites in the
     overview →". Recents (3) plus favorites (6) make at most 9 rows.
   - **B:** no cap. The menu grows with the favorites and may exceed the window's height.
   - **C:** a different cap (give the number).
3. **What the overview looks like.**
   - **A (recommended):** a large modal over the board, with no URL and no sidebar entry. It
     closes on Esc or when a project is opened. This matches the existing modals and doesn't
     change `ViewMode` or routing.
   - **B:** a main-area view (a new `ViewMode`) that replaces the board, with its own URL
     that can be bookmarked.

## Round 2 - answers from the owner (2026-09-28)

The owner took the recommended option for each question, in the interactive session.

### Settled choices

1. **Activity.** 1A: no server activity date. An overview card shows "opened N days ago" /
   « ouvert il y a N jours », read from this browser's history, and nothing for a project
   never opened here. "Other projects" matches, in the menu and in the overview after the
   favorites, are ordered by that history (most recent first), then A–Z.
2. **Favorites in the short menu.** 2A: with an empty search, at most 6 favorites, A–Z, then a
   "N more favorites in the overview →" link, which opens the overview unfiltered. The overview
   lists favorites first. The menu shows at most 3 recents plus 6 favorites, so at most 9
   project rows, and never scrolls.
3. **Overview.** 3A: a large modal over the current view, with no URL, no `ViewMode` and no
   sidebar entry. It closes on Esc, on its close button, on a click outside it, and when a
   project is opened. Opening from the "more matches" link fills its text filter with the
   menu's query.

### Reversed prior assumptions

- Round 1, choice 2 (storage) is revised to support 1A. `sectile_recent_project_ids` stores
  `{ id, openedAt }` entries (ISO date), most recent first. The cap goes from 10 to 50, so the
  history can order more than just the first matches and date them. Unknown ids are still
  ignored when the history is read, and there is still an in-memory fallback.
- The ticket's criterion on the overview cards ("last activity") now reads "last opened in
  this browser".

### Acceptance criteria adjusted by this round

- With an empty search, the menu shows at most 3 recents and 6 favorites. When there are more
  favorites, a link opens the overview.
- The overview is a modal. Each card shows when the project was last opened in this browser,
  or nothing if it never was.
- "Other projects" matches are ordered by local history, then A–Z.

### Newly surfaced ambiguities

None. The new strings ("N more favorites in the overview", "opened N days ago", the overview's
title, filter and close button) go in both locales of `web/src/locales/shell.ts`, following
the existing plural pattern.
