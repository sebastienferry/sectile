# Clarification: GitHub #428

Task: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-428`
URL: https://github.com/sebastienferry/sectile/issues/428
Branch: `feat/428`

## Round 1: analysis (2026-09-26)

### Restated request and scope

Produce installable Sectile Desktop packages, each bundling the local agent built
for the same platform, as release artefacts that a user can download and run
without cloning the repository or installing Node and Go. Auto-update, an app
store listing and a change to what the desktop app does once running are assumed
out of scope.

### Verified findings

- The ticket has a title only: no description, no comments. Sectile reports
  `parentType: macro` but returns no parent key, so there is no epic to read.
- `desktop/electron/package.cjs` already packages the app with
  `@electron/packager` for the **host platform only**, into `desktop/release/`,
  copying `desktop/bin/sectile-agent[.exe]` as an extra resource.
  `make desktop-package` (`build-app-package`) drives it after `build-app`. The
  output is an unpacked directory (`Sectile-darwin-arm64/Sectile.app`), not an
  archive or an installer.
- `desktop/electron/runtime.cjs` resolves the bundled agent from
  `process.resourcesPath` once packaged, so the agent inside the package must
  match the package's OS and architecture.
- `.gitlab-ci.yml` (GitLab mirror of the public GitHub repository) builds the Go
  `server` and `agent` binaries for darwin/arm64, darwin/amd64, linux/amd64,
  linux/arm64 and windows/amd64 **on tags only**, stamps them with the tag,
  writes `SHA256SUMS` and uploads them to the Generic Package Registry under
  package `sectile`, version `<tag>`. No job builds or publishes the desktop app;
  `test:desktop` sets `ELECTRON_SKIP_BINARY_DOWNLOAD=1` and runs plain Node tests.
- ADR 0018 makes a release a `vX.Y.Z` tag and nothing else, publishes binaries on
  tags only, and states the desktop version comes from `desktop/package.json`,
  which the release procedure in `AGENTS.md` bumps. The desktop settings already
  show `app.getVersion()` next to the agent's version (`main.cjs:171`).
- ADR 0003: "Development packages are unsigned and not notarized"; Windows
  supervision "remains unsupported". Yet #301 fixed console windows flashing on
  Windows and #351 fixed Windows test issues, so Windows is used in practice.
- ADR 0012 notes a packaged macOS build is ad-hoc signed with bundle identifier
  `com.electron.sectile`; macOS notification attribution depends on packaging.
- `desktop/README.md` warns that overwriting a macOS executable in place triggers
  `Taskgated Invalid Signature`; atomic replacement is the local convention.
- Memory: the repository is public, so no internal host, project or secret name
  may be committed with the pipeline changes.

### Ambiguities (worst first)

1. **Where the packages are produced and published.** A tag pipeline job
   uploading next to the agent binaries, a local `make` target producing
   distributable archives, or GitHub Releases on the public repository lead to
   entirely different code (CI jobs and runners versus Makefile only).
2. **Signing and notarization.** Unsigned/ad-hoc packages are what ADR 0003
   accepts, but a browser-downloaded unsigned macOS app is quarantined by
   Gatekeeper ("damaged" / "unidentified developer"). Developer ID signing plus
   notarization (and Authenticode on Windows) needs certificates, CI secrets and a
   macOS runner.
3. **Target platforms.** The Go matrix has five targets; the desktop may ship
   all of them or a subset (for instance macOS only, or without Windows given
   ADR 0003's support statement).
4. **Package format.** Zipped packager output versus native installers (`.dmg`,
   NSIS/MSI, AppImage/`.deb`). Installers need another tool
   (`electron-builder`/Forge makers) and change the job and the file names.

### Critical dependencies

- **Runners.** Packaging a macOS app from a Linux runner works with
  `@electron/packager` but cannot codesign; a valid signature and notarization
  require a macOS runner (GitLab-hosted macOS runners depend on the GitLab plan).
  Packaging for Windows from Linux needs Wine for `rcedit` (icon and version
  metadata) or a Windows runner.
- **Electron download in CI.** `ELECTRON_SKIP_BINARY_DOWNLOAD=1` is global; the
  packaging job must override it and download one Electron build per target.
- **Apple Developer and Windows code-signing certificates**, stored as protected
  CI variables, if signing is chosen.
- **Artefact size.** About 100 MB per Electron target, uploaded to the package
  registry per tag.

### Technical choices resolved from existing conventions

- **Version:** each package reports `desktop/package.json`'s version, already
  bumped to the tag by the release procedure; the bundled agent is the tag-stamped
  agent from `build:binaries`, so both numbers in the settings match on a release.
- **Tag only:** packages are releases (ADR 0018), so they are produced on tags
  and never on branches; a branch build stays `make desktop-package` locally.
- **Naming:** `sectile-desktop-<os>-<arch>.<ext>`, alongside
  `sectile-agent-<os>-<arch>` in the same `sectile/<tag>` package, and listed in
  the same `SHA256SUMS`.
- **Agent pairing:** each package embeds the agent cross-compiled for its own
  OS/arch, reusing `build:binaries` artefacts rather than recompiling.
- **Gate:** the publication waits on the same test jobs as `publish:binaries`.
- **Documentation:** `desktop/README.md` and the root `README.md` gain a
  download-and-install section; `CHANGELOG.md` gets one `Added` line; ADR 0003's
  "unsigned" sentence is revisited or confirmed.

### Product questions (with recommendation)

1. **Publication channel**: recommended: the GitLab tag pipeline, uploading to
   the existing `sectile/<tag>` Generic Package Registry package next to the agent
   binaries (consistent with ADR 0018). Alternatives: GitHub Releases on the public
   repository; local `make` target only.
2. **Signing**: recommended: unsigned (ad-hoc on macOS), with the Gatekeeper
   workaround documented (`xattr -dr com.apple.quarantine Sectile.app`); Developer
   ID signing and notarization as a follow-up ticket. Alternative: sign and
   notarize now.
3. **Platforms**: recommended: darwin-arm64, darwin-x64, linux-x64 and
   windows-x64 (linux-arm64 dropped as no desktop user is known). Alternatives:
   all five, or macOS only.
4. **Format**: recommended: `.zip` of the packager output (`.tar.gz` on Linux),
   no installers. Alternative: native installers (`.dmg`, NSIS, AppImage).

## Round 2: answers from the owner (2026-09-26)

### Settled

1. **Publication channel:** both streams. The packages go to the GitLab Generic
   Package Registry (`sectile/<tag>`, next to the agent binaries) **and** to a
   GitHub Release on the public repository. This reverses the Round 1
   recommendation of GitLab only.
2. **Signing:** unsigned (ad-hoc on macOS), the Gatekeeper workaround documented;
   Developer ID signing and notarization left to a follow-up ticket.
3. **Platforms:** darwin-arm64, darwin-x64, linux-x64, windows-x64.
4. **Format:** `.zip` of the packager output (`.tar.gz` on Linux), no installers.

### Newly surfaced

- **Who creates the GitHub Release.** The pipeline lives on the GitLab mirror,
  which knows nothing of GitHub. Either a GitLab job calls the GitHub API with a
  GitHub token stored as a protected, masked GitLab CI variable, or a GitHub
  Actions workflow on the tag builds and publishes on GitHub's own runners
  (duplicating the build matrix, but giving macOS runners for free).
- **What the GitHub Release carries.** Only the desktop packages, or the full
  release set (agent and server binaries, `SHA256SUMS`) mirroring GitLab.
- **Release notes.** Assumed: the tag's `CHANGELOG.md` section, the same text the
  release procedure puts in the annotated tag message.

## Round 3: answers from the owner (2026-09-26)

### Settled

5. **GitHub Release producer:** a GitHub Actions workflow triggered by the
   `vX.Y.Z` tag on the public repository builds on GitHub's runners and creates
   the release. This rejects the Round 2 recommendation of a GitLab job pushing to
   GitHub with a stored GitHub token: no GitHub credential lives in GitLab.
6. **GitHub Release contents:** the full release set, mirroring the GitLab
   package: the four desktop archives, the agent and server binaries of the Go
   matrix, and `SHA256SUMS`. Release notes are the tag's `CHANGELOG.md` section.

### Consequences recorded

- Two independent builds of the same tag: GitLab and GitHub each compile and
  package from the same commit, so their archives are equivalent but not
  byte-identical, and each stream's `SHA256SUMS` only vouches for its own files.
  Accepted as a consequence of choosing GitHub Actions.
- The GitHub workflow can package each macOS target on a native macOS runner
  (ad-hoc signature applied by the packager), Windows on a Windows runner and
  Linux on Ubuntu. The GitLab jobs run on the existing Linux runners and
  cross-package; whether a cross-packaged macOS archive needs an explicit ad-hoc
  signature step to launch on Apple Silicon is a technical point for the
  specification, not a product question.
- The GitHub workflow uses the built-in `GITHUB_TOKEN` (`contents: write`) only;
  it must not reference any internal host or secret name (public repository).
- `AGENTS.md` step 6 and ADR 0018 must describe the second stream; a new ADR is
  suggested for "releases are published on both forges".

### Settled scope

- In: tag-only packaging of Sectile Desktop for darwin-arm64, darwin-x64,
  linux-x64 and windows-x64 as `.zip` (`.tar.gz` on Linux) archives named
  `sectile-desktop-<os>-<arch>.<ext>`, each bundling the tag-stamped agent of its
  own platform; upload to GitLab `sectile/<tag>` and a GitHub Release carrying the
  full set; checksums; install documentation including the Gatekeeper
  workaround; changelog line.
- Out: code signing and notarization (follow-up ticket), native installers,
  auto-update, linux-arm64 desktop package, branch builds.
