## Ambiguities, worst first

1. **Autonomous/Batch Execution Behavior (`pickup-issue` / `pickup-issues`)**.
   `pickup` embeds the clarification steps to run autonomously to PR. If clarification requires explicit interactive owner confirmation in every case, an autonomous pickup run would stall or lose autonomy.
   *Resolution*: In unattended/autonomous runs (`pickup`, `pickup-issues`), if all ambiguities can be resolved via existing code and conventions (zero open product questions), Round 1 concludes the clarification stage and proceeds autonomously. However, if any product decision remains open, the unattended run must record the questions in `docs/clarifications/<n>.md`, post them to the ticket via `add_comment`, and stop without transitioning `new → clarified`.

2. **Canonical Template Source vs Repository Mirrors**.
   Skills are installed in multiple directories (`.claude/skills/clarify-issue/SKILL.md`, `.agents/skills/...`, `.gemini/skills/...`, `.agy/skills/...`, `.skills/...`, `.claude/commands/clarify-issue.md`).
   *Resolution*: `internal/db/skilltemplates.go` (`StageSkills["clarify"]`) is the canonical source of truth for Sectile skill generation. Both the Go template in `skilltemplates.go` and all repository-level mirror files must be updated together, ensuring unit tests and new project scaffolding remain aligned.

3. **Round State Tracking and Persistence**.
   How the agent identifies previous rounds when starting a continuation.
   *Resolution*: Reusing the assigned branch/worktree (`feat/<n>`) and the established report file (`docs/clarifications/<n>.md`). When `docs/clarifications/<n>.md` already exists, the agent reads existing rounds, inspects the latest ticket comments via `get_task`, appends `## Round N - answers from the owner (<date>)`, updates decisions, commits with `docs(spec): clarify #<n> (round <r>)`, and posts the summary via `add_comment`.

4. **Remote Execution Run ID per Round**.
   Each round is an independent invocation.
   *Resolution*: Each round executes its own remote run (`start_run` / `finish_run`). An unattended round stopping for user answers finishes its run with status `completed` (or note indicating awaiting user input) and does not call `transition_stage`. The subsequent round uses the new run ID passed by the launcher.

## Decisions

1. **Explicit Round Loop in Skill Contract**:
   The `clarify-issue` skill text explicitly defines:
   - **Round 1**: Analyze ticket and code, produce `docs/clarifications/<n>.md`, ask essential product questions (interactively in session, or via ticket comment when unattended). Commit with `docs(spec): clarify #<n> (round 1)`.
   - **Round N**: Triggered by owner answers. Read previous report and ticket discussion via `get_task`. Append `## Round N - answers from the owner (<date>)`. Address reopened ambiguities and revised decisions.
   - **Exit Condition**: Rounds continue until the owner confirms the clarification is satisfactory (e.g. "the clarification is satisfactory").
   - **Unambiguous Transition Rule**: Never invoke `transition_stage` to `clarified` while any product question is open.
2. **Synchronize All Skill Mirrors and Master Generator**:
   Update `StageSkills["clarify"]` in `internal/db/skilltemplates.go`, and update `.claude/skills/clarify-issue/SKILL.md`, `.agents/skills/...`, `.gemini/skills/...`, `.agy/skills/...`, `.skills/...`, and `.claude/commands/clarify-issue.md`.
3. **Documentation Updates**:
   Update `docs/CAPABILITIES.md` to document the round-based clarification loop and exit criteria; reference it in `docs/README.md`.

## Questions, with the recommended option

1. **Exit condition for autonomous runs (`pickup-issue`)**: When no product questions are open in Round 1 (all ambiguities resolved via code conventions), should `pickup` automatically proceed to specification without waiting for interactive owner confirmation?
   - *Recommended*: **Yes**. Autonomous pickup should proceed when zero product decisions remain open. If any product decision is open, it must halt, post the questions, and wait for Round 2.
   - *Alternative*: Require explicit owner confirmation for all clarifications even in pickup mode (disabling fully autonomous pickup from `new`).

2. **Commit message convention**: Should the commit message include the round number when rounds > 1?
   - *Recommended*: **Yes**, e.g., `docs(spec): clarify #239 (round 1)` and `docs(spec): clarify #239 (round 2)`.
   - *Alternative*: Standard `docs(spec): clarify #239` on all rounds.
