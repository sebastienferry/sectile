### Settled from the ticket

- Preserve the full supplied report text in the Markdown attachment, rather than converting it through ADF.
- Publish a short summary and identify the attachment.
- Attachment failure must be visible to the caller but must not block an otherwise successful stage transition.
- When upload fails, still attempt the summary comment and say the report could not be attached.
- Keep the full report in Sectile history and make it accessible from the task view, including intermediate clarification rounds.
- Cover standalone and managed publication, and update the generated issue skills accordingly.
- No production code or technical specification is written at this stage.

### Reversible technical choices

- Pass explicit report metadata through the shared publication path rather than treating every long or Markdown-formatted comment as a report.
- Construct minimal plain-text ADF directly for report summaries. Running summaries through the general Markdown parser would preserve the original failure class.
- Upload using the same tracker and acting-person credential resolution as the comment; do not silently switch accounts.
- Treat upload failure as a structured warning alongside a successful transition, rather than a fatal tool error that encourages the caller to repeat an already completed transition.
- Keep ordinary summary-comment failure visible as a publication failure; the ticket only makes attachment failure non-blocking.
- Do not automatically retrieve workstation files from the server: the full report text is supplied in the publication contract.
- A user-visible changelog entry is required during implementation.

### Ambiguities, in priority order

1. Summary compatibility: a new caller-supplied summary produces meaningful question/decision summaries, but existing clients and managed result contracts supply only a note. Rejecting them, deriving summaries, or using a generic fallback are different behaviours.
2. Report classification: explicit stage/round metadata prevents discussion comments from accidentally becoming attachments; automatic recognition also captures legacy reports but risks false positives.
3. Attachment history: separate round files preserve the published chronology; replacing a cumulative report requires deletion/replacement semantics and changes what previous links mean.
4. Tracker scope: extending to GitHub or GitLab adds provider APIs and changes otherwise working publication.
5. Board retention: tracker comments alone cannot preserve full intermediate rounds after switching them to summaries, particularly when upload fails. Durable Sectile report storage and task-view access are necessary.

### Dependencies and acceptance implications

- Jira attachments can be disabled or exceed the instance limit; upload can fail independently of commenting. Those cases use the documented fallback without splitting the full report into Jira comments.
- Check both token and OAuth authentication, endpoint scope routing, permission errors, and upload response attachment identifiers/URLs.
- Preserve stage-operation retry semantics: if upload succeeds but commenting fails, retry should reuse that publication's attachment rather than create another unnecessarily. A genuinely new report is a new publication.
- Full report retention must happen before remote upload and survive upload failure for every publication path. Its storage shape and UI entry point belong to specification.
- GitHub/GitLab splitting stays as currently configured if the proposed Jira-only scope is confirmed.
- No live Jira credential or issue is needed for clarification; implementation can prove the contract with HTTP fixtures and workflow integration tests.
