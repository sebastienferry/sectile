# Clarification #584 - A task that changes no repository cannot reach implemented

- Ticket: https://github.com/sebastienferry/sectile/issues/584
- Branch: `feat/batch-393-497-498-584-647-648` (batch of #393, #497, #498, #584, #647, #648)
- Report: `docs/clarifications/584.md` (committed on the batch branch)

## Round 1 - initial analysis (2026-10-01)

### Request

A task whose work changed no repository (a configuration change made through
an API, a review, a follow-up) cannot reach `implemented`: the transition
always asks for pull request evidence, and the only ways out of the error do
not apply. `transition_stage` gets an explicit statement that the task changed
no repository, which the server records instead of a pull request.

Out of scope: tasks that changed code (they keep needing their pull request),
forging or inferring a pull request, and the board's manual move.

### Code read

- `internal/taskmcp/server.go`: `transition_stage` schema and handler, which
  call `TransitionTaskStageWithPRs`.
- `internal/db/stage.go`: `TransitionTaskStageWithPRs` runs
  `validateStagePRs` for `clarified`, `specified`, `implemented` and
  `reviewed`, and appends its notice to the note.
- `internal/db/stageprs.go`: `validateStagePRs`, the multi-repository path,
  and `prDeferredNotice` / `prDeferredBySpecArtifacts`, the existing
  precedent of a stage that goes without its pull request and says why in the
  report.
- `internal/db/adjustment.go`: `stagePRRequired` (`implement` and `adjust`
  always require evidence, whatever `prCreationStage` says; `specify` and
  `clarify` when they own the creation), `validateStagePRAt`, the
  `git_evidence` agent operation, and the `prEvidenceLookup` test hook.
- `internal/runner/adjustment.go`: `ErrNoOriginRemote`, the error of the
  ticket.

### Finding

The guard is not tied to `prCreationStage=implemented` only: `implement` and
`adjust` require evidence on every project. A task without code is therefore
stuck at `specified` and, once moved by hand, again at `reviewed`. The
statement has to be accepted on every stage that requires evidence.

### Ambiguities (worst first)

1. **How strictly the server checks the statement.** The ticket lists a
   check that the branch has no commit ahead of the default branch as
   optional. The agent's `git_evidence` operation reports the branch, its
   head and whether the checkout is clean, not the number of commits ahead,
   so the check needs a new agent operation, and an older agent cannot answer
   it (#391 skew).
2. **How the task shows that no pull request was expected.** Either a line
   in the stage report (the way `prDeferredNotice` works today, visible in
   the activity and in the tracker comment), or a stored flag with its own
   display on the card and the detail view (a migration and UI work).

### Dependencies

- None external. SFE-367 can be moved once the server is deployed.

### Technical choices settled here (reversible)

- **Input.** `transition_stage` gains `noRepositoryChange: boolean`. It is
  refused together with `prUrl` or `prUrls`, and the note, already required,
  carries the justification.
- **Checks the server can make without the agent.** The statement is
  refused when the task records a pull request on its branch, or when
  `prepare_repository_worktree` recorded a changed repository for it. Both
  say the task did change a repository.
- **What a call without the statement does.** Exactly what it does today,
  the explicit #392 error included.
- **Skills.** `code-issue`, `implement-issue`, `adjust-issue`,
  `pickup-issue`, `pickup-issues` and `handoff-issue` document the path for
  tasks with no code, in the project's skill sources (`make plugin` copies),
  never in the hand-maintained marketplace plugin.
- **Tests.** Through `prEvidenceLookup`: the statement succeeds on
  `implemented` and `reviewed` with a lookup that would fail, the same call
  without it fails with the current error, and the statement is refused with
  a `prUrl`, with a recorded PR on the branch, and with a changed repository.
- **Changelog.** One `Fixed` line.

### Open product questions

1. **Commit-ahead check and display.**
   - A. No agent-side commit check; the server-side checks above only. The
     task shows it through a line in the stage report ("No pull request:
     this task changed no repository."), with no migration.
   - B. A. plus a new agent operation that refuses the statement when the
     branch has commits ahead of the default branch.
   - C. B. plus a stored flag shown on the card and the detail view.
   - Recommended: **A**. The statement is explicit and justified in the
     note, the server refuses the cases it can see, and B and C add agent
     protocol and UI work for the rare case of a session lying about its
     own branch.

## Round 2 - answers from the owner (2026-10-01)

Answered interactively in the batch session.

### Settled decisions

1. **Option A.** `noRepositoryChange: true` with the justification in the note.
   The server refuses it with `prUrl` / `prUrls`, with a pull request recorded
   on the task branch, and with a repository recorded as changed. No
   agent-side commit-ahead check, no migration: the stage report carries the
   line "No pull request: this task changed no repository." and that is how
   the task shows it. The third acceptance criterion (commit check) is
   dropped, as the ticket made it conditional.
2. The last acceptance criterion (SFE-367 moved with the statement) is a
   step for the owner once the server is deployed.

### Open questions

None. Exit condition met.
