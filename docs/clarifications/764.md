Add a sixth list, `excludedCommands`, to the Claude settings at workstation and

### What Claude Code actually does with `excludedCommands`

These facts change the ticket as written:

1. **An entry uses `Bash(...)` rule syntax, and a pattern without a wildcard is
   an exact match.** `git` matches only `git` with no argument; `git *`
   matches `git` with or without arguments. The ticket's example
   `excludedCommands: ["git", "glab"]` would exclude nothing useful.
2. **Every command of a call must match**: `npm ci && git push` stays
   sandboxed unless `npm ci` is excluded too. A redirect to a file, a `cd` or a
   `$(...)` keeps the whole call sandboxed. The match is on the text, so a
   script that calls `git` internally is not excluded.
3. **An excluded command goes through the regular permission flow**: an allow
   rule or a read-only command runs without a prompt, anything else prompts
   (in Sectile, through the desktop permission request). The ticket's "no
   per-command prompt" holds only for commands an allow rule already covers.
4. **`--settings` entries are honoured under a strict sandbox.** With
   `allowUnsandboxedCommands: false` set through `--settings`, Claude Code
   treats the sandbox as admin-required and ignores the *repository's*
   `excludedCommands`, but still applies those of `~/.claude/settings.json`
   and `--settings`. The file Sectile generates is therefore the right place,
   and the workaround in `~/.claude/settings.json` works for the same reason
   (arrays of every source are merged).
5. **Why `git` over SSH fails**: Claude Code's default sandbox read policy
   allows `~/.ssh`; the "Dangerous actions" preset's `Read(~/.ssh/**)` deny
   rule is what Claude Code turns into a sandbox read denial. An excluded
   command runs with no filesystem restriction, so the deny rule no longer
   reaches it (deny rules on the `Bash(...)` command itself still apply).

### Ambiguities (worst first)

1. **The preset's content and its default.** "Consider a preset (`git`,
   `glab`, `gh`)": either broad patterns (`git *`, `gh *`, `glab *`) or only
   the commands that need the network (`git fetch *`, `git pull *`,
   `git push *`, `git clone *`, `git ls-remote *`, `gh *`, `glab *`), and
   either part of "Apply recommended" or opt-in. Product question Q1.
2. **The `--force-with-lease` deny rules ("Related").** Fixing them is either
   part of this ticket or a ticket of its own; and an owner who already applied
   "Dangerous actions" keeps the old rules either way, because a catalogue
   change never rewrites the lists an owner has (#745). Product question Q2.
3. **The acceptance criterion `["git", "glab"]`.** Read literally it is
   satisfied by the file but not by the third criterion (the commands would
   stay sandboxed). Settled below as a correction.

### Critical dependencies

- No migration: `excludedCommands` is a new optional key of `claudeSandbox` in
  `~/.config/sectile/settings.json`; an absent key means an empty list, and
  `foldProjectSandboxes` only runs on layouts below 4, which cannot hold it.
- Claude Code: `--settings` entries honoured under a strict sandbox from
  v2.1.285 (point 4); earlier versions from v2.1.282 to v2.1.284 ignored only
  the repository's entries, so `--settings` is not affected.
- No server, database or web change.

### Settled technical choices (reversible, from the code and conventions)

- `ClaudeSandbox.ExcludedCommands []string` with JSON key `excludedCommands`,
  handled everywhere the other lists are: `IsZero`, `NormalizeClaudeSandbox`
  (trim, refuse empty and multi-line entries, drop duplicates),
  `MergeClaudeSandbox` (keep an entry the store gained meanwhile),
  `ResolvedClaudeSandbox` (workstation entries then the project's, each once),
  `claudeSandboxPayload`.
- `claudeSettingsDocument` writes `sandbox.excludedCommands` when the list is
  non-empty, and leaves it out on Windows with the rest of the `sandbox`
  object. The list alone is enough to write a file.
- Desktop: `fromStored`, `sandboxPayload`, `resolvedValues`,
  `launchesGetSettings` (counts only where the sandbox runs) and a
  `listEditor` row "Commands outside the sandbox" right after "Allowed network
  domains", hidden or disabled as that row is where the platform has no
  sandbox, with inherited workstation entries shown as "Global" like the other
  lists. Placeholder `glab *`; hint: a pattern ending in ` *` matches the
  command with arguments, a bare name matches it alone; the command runs with
  full access and still follows the allow and deny rules.
- Entries are stored as typed: Sectile does not append ` *` to a bare name,
  because an exact match is a legitimate pattern. The hint explains it.
- Presets: `excludedCommands` becomes a fifth list of every preset (empty in
  the existing ones), applied only where the sandbox runs, so `presetApplied`,
  `applyPreset`, `removePreset` and `listsEmpty` cover it unchanged in shape.
- Documentation: `docs/CAPABILITIES.md` (Claude settings entry and a
  paragraph on when to prefer an excluded command over
  `allowUnsandboxedCommands: true`: no escape for every command, the rest
  stays sandboxed, allow rules still decide prompts), and a `CHANGELOG.md`
  line under `Added`. ADR 0048 already covers the generated file; whether a
  new key needs an ADR is left to the specification.
- Acceptance criterion corrected: the example becomes
  `excludedCommands: ["git *", "glab *"]`, producing
  `"sandbox": {"excludedCommands": ["git *", "glab *"], ...}`.

### Open product questions

**Q1. What does the preset hold, and is it recommended by default?**
Options:
- (a) **Recommended**: a new opt-in preset "Outside the sandbox (git, gh,
  glab)" with `git fetch *`, `git pull *`, `git push *`, `git clone *`,
  `git ls-remote *`, `gh *`, `glab *`, not part of "Apply recommended".
  Local git stays sandboxed; only what needs SSH or TLS leaves it. Being
  opt-in, nobody's sandbox widens without a click.
- (b) The same preset with broad `git *` (simpler, but every git command,
  including hooks that run repository scripts, leaves the sandbox).
- (c) Add the entries to the existing presets instead (`git` network
  commands and `gh *` to Common, `glab *` to GitLab CLI); Common is in
  "Apply recommended", so new workstations would get them by default.
- (d) No preset: the list only.

**Q2. Do the `--force-with-lease` deny rules belong to this ticket?**
Options:
- (a) **Recommended**: a separate ticket. It changes "Dangerous actions"
  (replace `git push --force*` and `git push * --force*` with exact
  `--force` forms so `--force-with-lease` is not denied) and has to decide
  what happens to owners who already applied the old rules, which this ticket
  does not touch.
- (b) In this ticket, catalogue change only: owners with the old rules remove
  them by hand.
- (c) In this ticket, with a one-shot rewrite of the old rules in existing
  settings.

## Round 2 - answers from the owner (2026-10-06)

Answers given interactively in the clarification session.

### Settled decisions

- **Q1 → (a)**: a new opt-in preset, "Outside the sandbox (git, gh, glab)",
  with `excludedCommands` `git fetch *`, `git pull *`, `git push *`,
  `git clone *`, `git ls-remote *`, `gh *`, `glab *`, and no entry in the
  other four lists. It is not part of "Apply recommended" (`RECOMMENDED` stays
  `['common','dangerous']`). It has nothing to apply on Windows, so it shows
  there as the network-only presets do. Its description says the commands run
  with full access and still follow the allow and deny rules, so `git push`
  keeps prompting unless an allow rule covers it.
- **Q2 → (b)**: the `--force-with-lease` fix is in this ticket, as a catalogue
  change only. In "Dangerous actions", `Bash(git push --force*)` and
  `Bash(git push * --force*)` become `Bash(git push --force)`,
  `Bash(git push --force *)`, `Bash(git push * --force)` and
  `Bash(git push * --force *)`; the `-f` rules are unchanged. Neither
  `--force-with-lease` nor `--force-if-includes` is denied any more; a bare
  `--force` or `-f` still is.
- No rewrite of existing settings: an owner who applied "Dangerous actions"
  before keeps the two old rules, which still deny `--force-with-lease`. The
  preset then reads as not applied (its new entries are missing); applying it
  again adds the four new rules beside the old ones. The owner removes the two
  old rules by hand, and the `CHANGELOG.md` line says so.

### Reversed assumptions

- Round 1 left the force-push rules out of scope (recommended option (a)); they
  are now in scope, catalogue only.
