## Round 1 (2026-09-29)

### Restated request and scope

The roadmap sync keeps the labels a tracker epic carries instead of discarding
them, the roadmap row shows them as badges, the toolbar filters the roadmap on
them, and the epic's panel lets the user add and remove its free labels, while
the labels the roadmap owns for its own axes (`roadmap:<horizon>` today) can be
neither shown as free labels nor edited there. Out of scope: the priority and
quarter axes themselves (#627), per-project axis prefixes (#635), the maturity
counter on the row (#629), renaming a label across epics, and the child
tickets' `phase:` / `goal:` groupings, which stay as they are.

### Verified findings

1. The labels already reach Sectile and are dropped at the last step.
   `ImportMacroHorizons` (`internal/db/macrohorizons.go:209`) receives
   `epic.Labels` from `ListEpics`, uses them only to derive the horizon, and
   `MacroMeta` has no field and the `macros` table no column to keep them.
2. Only the Jira adapter implements `ListEpics` and declares `CapEpic`
   (`internal/trackerapi/jira.go:35`, `:995`). GitHub and GitLab fall back to
   `Unsupported`, and the sync skips the roadmap step for them
   (`internal/db/db.go:4463`). On GitHub a macro is a milestone (`M-<n>`),
   which carries no labels at all; `macroTracker` already refuses to label
   milestones, local keys and epics of another project.
3. The horizon push writes labels through `UpdateIssue` with `Labels` and
   `RemovedLabels` only, from a queued activity, never inline with a click
   (`internal/db/macrohorizons.go:113-145`). An edit of free labels can use the
   same call and the same queue.
4. The horizon is a local-first decision with a pending-push list
   (`PendingHorizonPushes`); the tracker wins at import when the epic carries a
   label.
5. The roadmap's existing label chip is the application-wide `labelFilter`,
   sent to the server to filter tickets (`web/src/context/AppContext.tsx:1233`),
   so the roadmap rows follow it only through their child tickets.
6. `roadmap:` is the only prefix the server owns on epics. `phase:` and `goal:`
   (`web/src/lib/labelAxes.ts:23`) are axes of the child tickets, not of the
   epic.
7. Taskativ change 38 covers keeping, showing and filtering, and explicitly
   excludes writing labels. Editing free labels is Sectile's own addition.

### Ambiguities, worst first

1. **Which trackers.** The feature can only exist where epics are read
   (finding 2). Either it is Jira-only, or the ticket also asks for GitLab
   epics to be read, which is new tracker work. → Question 1.
2. **What a failed label edit leaves behind.** Either the edit is local-first
   with a pending list like the horizon, or the tracker stays the only source
   and the local copy changes only once the write succeeded. → Question 2.
3. **Which filter.** Reusing the global ticket `labelFilter`, or a filter local
   to the roadmap that applies to the epic rows. Resolved below (decision 3).
4. **What "protected" covers.** Hidden from badges and filter, refused by the
   editor, or both. Resolved below (decision 4).

### Resolved technical choices

1. **Storage.** The labels are stored as the tracker returns them, horizon
   labels included, as a JSON list in the new column, written by the sync
   through a new `labels *[]string` pointer on `saveMacroMetaFull` (nil leaves
   them untouched, so horizon and framing saves keep them). A label removed on
   the tracker disappears at the next sync. Following Taskativ: hiding is a
   display concern, and `PendingHorizonPushes` needs the real list.
2. **Display.** The expanded row shows every free label as a badge; the
   condensed row shows at most two and a `+n` counter. A row without free
   labels keeps its height.
3. **Filter.** A multi-select in the roadmap toolbar, local to the view,
   offering the free labels the epics of the view carry with their epic count,
   OR semantics (labels of one axis are exclusive, AND would empty the view),
   tab counters follow, not persisted between visits, hidden when no epic
   carries a free label, and a selected label that no longer appears is
   dropped rather than emptying the view silently. The global ticket
   `labelFilter` is left as it is. Following Taskativ's rejected alternatives.
4. **Protection.** A single server-side list of axis prefixes owned by the
   roadmap, holding `roadmap:` today and extended by #627 and #635. A label
   under one of them is neither shown as a badge, nor offered by the filter,
   nor accepted by the editor (added or removed), and the server refuses it
   too, so another client cannot bypass the view. Matching ignores case and a
   leading `#`, as `HorizonFromLabels` does.
5. **Editing.** In the epic's panel: the free labels as removable chips and an
   input that suggests the labels already carried by the project's epics.
   Each edit sends only the added and removed labels through `UpdateIssue`,
   from a queued tracker activity, as the horizon push does. Milestones, local
   keys and epics of another project show their labels read-only with the
   sentence `macroTracker` already produces.

### Open product questions

1. **Tracker scope.** Only Jira returns epics and their labels today; on
   GitHub a macro is a milestone, which has no labels. Is the feature
   Jira-only, badges, filter and editor simply absent elsewhere?
   *Recommended: yes, Jira-only; reading GitLab epics would be a separate
   ticket.*
2. **Failed edit.** When a label edit cannot be written to the tracker:
   *Recommended: the tracker stays the source of free labels; the local copy
   changes only once the write succeeded, the failure stays readable in the
   activity and a toast, and nothing is queued for a later retry.*
   Alternative: local-first with a pending list and a "push again" action, as
   for the horizon.
