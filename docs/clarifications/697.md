# Clarification #697: a task carries one pull request per repository it changed

## Round 1 (2026-10-02)

### Request

A task that changed several repositories (`changedRepositories`) records the
pull request of each one, and every surface (desktop toolbar, web task detail,
board card) shows all of them with their state, the primary repository's first.
Out of scope: opening the secondary repositories' pull requests automatically,
and merging or tracking reviews across repositories.

### What already exists (read before restating the problem)

Part of the ticket's "Problem" section predates #456 and #678, which already
landed on `main`:

- `transition_stage` takes `prUrls` (`internal/taskmcp/server.go:321`), and
  `validateStagePRs` (`internal/db/stageprs.go`) checks one pull request per
  changed repository, refuses a link for a repository the task did not change,
  and appends every accepted link to `prLinks`, the primary repository's last
  (`internal/db/stage.go:106-110`, `pullRequestLinkLast`).
- The managed result contract carries `prUrls` too (`models.go:1298`,
  `internal/db/postback.go:63-70,181`).
- The implement skill and the launch prompt already tell the agent to give
  `prUrls` (`internal/agent/repositories.go:248`); handoff asks to confirm each
  repository's pull request is merged.
- `refreshPullRequestStates` (`internal/db/prstates.go`) already refreshes every
  non-merged link of `prLinks`, not only the last.

What is really missing:

1. **Paths that record a single pull request.** `adjust-issue` and `create-pr`
   never mention `prUrls`; `create-pr` records nothing at all on the task (it
   only reports). The adjust dispatch in the agent (`internal/agent/agent.go:1139-1156`)
   reads `CurrentPullRequest` and patches a single `prUrl`. The web/REST
   `PATCH prUrl` (`internal/handlers/handlers.go:1902,2952`) and PR discovery
   (`internal/db/prdiscovery.go:157`) apply `AcceptPullRequest`, which reasons
   on branches only, not on repositories.
2. **No repository on a link.** `TaskPullRequest` holds `url`, `branch`,
   `state`. The repository is only recoverable by parsing the URL
   (`models.ParsePullRequestLink(...).Identity()`), which `validateStagePRs`
   already does.
3. **Display.** Desktop shows one indicator, the last link
   (`desktop/src/pullRequests.mjs`, `desktop/src/main.js:2691`). The web task
   detail (`web/src/components/TaskDetailModal.tsx:1393-1451`) lists all links as
   one flat history with no repository; the board card (`TaskCard.tsx:715,1002`)
   shows `task.prUrl` only.
4. **`finished`.** The server checks no merge at `finished` (`stage.go` has no
   skill for that stage), for the primary repository either; only the handoff
   skill asks the agent to confirm each merge.

### Ambiguities, worst first

1. **What "recorded" means outside a stage transition.** `create-pr` has no
   tool to write a pull request to a task today. Either it gains one, or it
   stays report-only and the next `transition_stage` records it.
2. **What the board card shows** when a task has several pull requests: the
   primary one only, every one, or the primary one with a count.
3. **Whether `finished` checks secondary merges on the server**, given that it
   does not check the primary one either.
4. **Backfill.** Whether a task that already changed a secondary repository
   without recording its pull request (the observed case) gets it discovered by
   branch, or must be fixed by hand.
5. **Forge credentials.** Refreshing a GitLab merge request of a GitHub-tracked
   project (or the reverse) needs a token for that forge; without one the state
   stays unknown.

### Critical dependencies

- **New MCP tool** (if ambiguity 1 goes that way): the agent MCP bridge
  whitelists the catalog and its count, so `agentmcp`, `mcptest` and two count
  tests move with it.
- **Skill goldens**: `adjust-issue`, `create-pr` and the pickups change, so the
  plugin testdata and catalog goldens are regenerated (`UPDATE_GOLDEN=1`).
- **No migration** if the repository is derived from the URL (decision 1 below);
  `prLinks` keeps its shape.
- **Per-forge credentials** for state refresh: `ForActingUser(forge, projectID)`
  resolves a client per forge and per project; a secondary repository on another
  forge needs the acting user's token for it.

### Settled technical choices (reversible, from the code)

1. **Repository of a link is derived from its URL**, through
   `ParsePullRequestLink(...).Identity()`, the identity `changedRepositories`
   and `validateStagePRs` already use. It is exposed read-only in the API
   (`repository` on each link) so clients do not parse URLs; nothing new is
   stored, no migration.
2. **Storage order stays** "primary repository's current pull request last", so
   `prUrl` and `CurrentPullRequest` keep meaning the primary one and every
   single-PR consumer (workflow checks, adjust dispatch, tracker sync) is
   unchanged. Display order (primary first, then the others) is computed by the
   clients.
3. **`AcceptPullRequest` becomes per repository**: a link for a repository
   already in the set is checked against that repository's links only (same
   branch or same URL accepted, other branch refused); a link for another
   repository the task changed is an addition; a link for a repository the task
   did not change is refused. Links whose URL cannot be parsed keep today's
   branch-only rule.
4. **The "current" pull request of a repository** is its last link; a new link
   in a secondary repository never displaces the primary one as `prUrl`
   (`pullRequestLinkLast` is applied on every append path, not only at
   transition).
5. **Workflow checks** (PR creation owner, `reviewed`) keep reading the primary
   repository's pull request; `validateStagePRs` already checks the secondary
   ones where it applies.
6. **Skills**: `adjust-issue` and the pickups say to pass `prUrls` for every
   secondary repository they pushed, as `implement-issue` already does.

### Product questions (with recommendation)

1. **`create-pr` recording.** Recommended: add one MCP tool,
   `record_pull_request(taskKey, url)`, that appends a pull request to the task
   under the per-repository rule, without changing the stage; `create-pr` calls
   it once per repository it pushed. Alternative: `create-pr` stays report-only.
2. **Board card.** Recommended: the primary pull request's icon, plus a small
   `+N` badge when other repositories have one; the full list stays in the task
   detail and the desktop toolbar. Alternatives: every icon, or primary only.
3. **`finished` and secondary merges.** Recommended: no server check, as for the
   primary repository today; the handoff skill keeps confirming each merge, and
   the views show an unmerged secondary pull request with its state.
   Alternative: the server refuses `finished` while any recorded pull request is
   open.
4. **Backfill of missing secondary pull requests.** Recommended: PR discovery
   looks up, by task branch, the pull request of every changed repository that
   has none recorded, so the observed task heals on its next sync. Alternative:
   no discovery, the owner adds it by hand from the task detail.
5. **Missing forge credential for a secondary repository.** Recommended: show
   the link with "state unknown" and a tooltip naming the missing token; no
   failure, no warning on every sync. Alternative: surface a sync warning.
