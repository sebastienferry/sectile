# Clarification for GitHub #434 (Add the color point in priority in task edition)

Task: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-434`

## Round 1: analysis (2026-09-24)

### Request restated

Show the priority colour dot, the one the board card, the backlog row, the filter bar and
the pinned bar already use, inside the priority field of the task edit form, so that the
field reads the same way as the task it edits. Out of scope: new priority levels, new
colours, changing how priority is stored or synchronised with the tracker, and the roadmap
view's `PRIORITY_META` badge, which deliberately uses its own palette.

The ticket has no description and no comments; the title is the whole request.

### Files read

- `web/src/components/TaskDetailModal.tsx`: the priority field (`{/* Priority */}`) is a
  plain `<select>` with four text options and no colour; `handlePriorityChange` saves on
  change.
- `web/src/components/QuickAddModal.tsx` and `web/src/components/CloneTaskModal.tsx`: the
  same text-only `<select>` in the creation and clone forms.
- `web/src/components/TaskCard.tsx` (`PRIORITY_DOTS`), `TaskFilters.tsx`
  (`PRIORITY_DOTS`), `ListView.tsx` (`PRIORITY_OPTIONS`), `PinnedBar.tsx`
  (`PRIORITY_DOT`): four copies of the same mapping, urgent → `--status-danger`,
  high → `--status-warn`, medium → `--status-info`, low → `--text-muted`.
- `web/src/lib/roadmap.ts` (`PRIORITY_META`): a different palette (high uses the accent
  colour) for roadmap badges.
- `desktop/src/style.css` (`.priority-dot`): the desktop app's own dot, hard-coded hex
  values.

### Ambiguities (worst first)

1. **Which forms count as "task edition".** Reading A: only the task detail modal, where
   an existing task is edited. Reading B: every form that sets a priority, so also quick
   add and clone. Settled as B (D2): the three forms share the same field markup, and a
   dot in one but not the others would itself be an inconsistency.
2. **Where the dot sits.** A native `<option>` cannot render a coloured shape on every
   platform (macOS ignores option styling). Settled (D3): the dot is drawn inside the
   closed field, left of the selected label; the open list keeps the native options.

### Dependencies

None: web only, no API, migration or tracker change. The desktop app has no task edit
form, so it is untouched.

### Resolved technical decisions (reversible, settled here)

- **D1: One source for the colours.** A `web/src/lib/priority.ts` module exports the
  ordered levels and their colour; the edit field and the four existing dot renderings
  read it, so the form cannot drift from the card again. Colours and order are unchanged.
- **D2: Scope.** Task detail modal, quick add and clone, through one shared
  `PrioritySelect` component.
- **D3: Rendering.** A native `<select>` (keyboard, accessibility and mobile behaviour
  kept) with the dot overlaid on its left edge, marked `aria-hidden`; the label stays the
  accessible name.
- **D4: Changelog.** The change is visible to users, so it gets one `Changed`
  line under `[Unreleased]`.

### Product questions

None open. The owner was not present in this run; D2 is the only choice with a product
flavour, and it is reversible by dropping the component from the two creation forms.

### Exit condition

Met: zero open product questions. Ready for specification.
