### Ambiguities, ordered by impact
1. Multiple eligible devices: the ticket proposes affinity or primary/most recent, while current behavior explicitly asks for a device. The exact ranking and the meaning of "previously ran work" are unspecified.
2. Unavailable task affinity: silently selecting a different device may create a fresh worktree without uncommitted local work; refusing requires an explicit user choice instead.
3. API naming: targetDeviceId overlaps existing deviceId. Removing, aliasing or retaining the existing name changes client compatibility.
4. Inventory compatibility: unknown inventories currently work through wildcard registration; strict inventory filtering would refuse older clients.
5. UI scope: the acceptance criterion requires a durable activity display, but does not explicitly require a workstation picker or a primary preference setting.

### Technical choices resolved from existing conventions
- Restrict eligible targets to the authenticated user's devices and the resolved run project; never dispatch to another user's machine.
- Validate a target before creating launch/activity side effects. Explicit targets never silently fall back to another device.
- Preserve the exact selected route through dispatch, across server replicas and reconnect grace; a failed or unconfirmed launch does not trigger a second dispatch elsewhere.
- Desktop supplies its own paired device identity, using its existing authenticated forwarding path.
- Persist structured workstation identity on both the execution run and its launch activity; keep historical unknown values empty, without guessing or parsing summaries.
- Display the recorded identity in activity history even after completion or disconnection. Device ID is a reliable initial display; a friendly label may supplement it if available.
- Keep batches on their selected lead workstation; do not distribute members to different machines.
- Preserve existing busy/force, authorization and engine resolution behavior. Add a user-facing changelog entry during implementation.
These technical choices are recommendations pending the owner's confirmation of this baseline.

### Dependencies and risks
- Reuse existing multi-device connection/presence and reported project inventory; no external service or worktree synchronization is needed.
- A database migration and all activity read/write paths must preserve device identity. Durable affinity depends on that recorded history.
- Cross-instance availability and inventory must give the same eligible set as local routes.
- Existing clients use deviceId and may not report inventories. Compatibility decisions below must be explicit.
- There is no established primary-workstation preference in the inspected code; adding such a preference would enlarge this ticket.

### Essential questions for the owner
1. For Web automatic routing, approve this order: the latest successfully launched run for this task, project and user, then the eligible workstation most recently connected, with device ID as a stable tie-breaker? Recommendation: use this order and omit a new primary-workstation setting. Alternative: require an explicit choice whenever multiple eligible devices remain.
2. If the task's previous workstation is offline or no longer serves the project, should automatic routing stop and request an explicit target, or fall back to another eligible workstation? Recommendation: stop when recorded affinity is unavailable, avoiding accidental continuation without local work. Also recommend refusing unknown/empty project inventories rather than treating wildcard registration as proof that a project is available; approve or request legacy compatibility.
3. Approve compatibility and UI scope: introduce targetDeviceId as an alias for existing deviceId, accept matching values and reject conflicting values; Desktop always pins its local device; show the recorded device in activity history, without adding a Web picker or primary-device settings in this ticket? Recommendation: approve. An API caller can still explicitly choose another workstation.
