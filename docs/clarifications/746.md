# Clarification #746 - Desktop rewrites settings.json without a lock shared with the agent

Ticket: https://github.com/sebastienferry/sectile/issues/746
Branch: `feat/746`

## Round 1 (2026-10-06)

### Request

Sectile Desktop (Electron) and the local agent both run read-modify-write
cycles on `~/.config/sectile/settings.json`, and nothing serializes them
across the two processes, so a save by one can put back a value the other has
just changed. The fix makes every writer of that file, on both sides, take the
same cross-process guard, so that neither ever reverts the other's change.
Out of scope: binaries already released (an agent built before the fix keeps
writing without the guard), the semantics of which process owns which key
(#305 stays as it is), and #744's layout guard, which already landed (#748).

### Code and files read

- `desktop/electron/main.cjs`: `readSettings`, `settingsPath`,
  `saveCredential`, the `save-settings`, `set-appearance` and
  `set-console-view` handlers, `startAgent`, `connectAgent`.
- `desktop/electron/credential-store.cjs`: `storeKey` (`secret` or `apiKey`).
- `internal/agentconfig/settings.go`: `ReadSettings`, `WriteSettings`,
  `storeSettings`, `settingsMu`, `UpdateSettings`, `LockSettings`.
- `internal/agentconfig/connection.go`: `WriteConnection`.
- `internal/agentconfig/engines_migration.go`: the start-up migration's
  `storeSettings` call.
- Callers of `LockSettings` + `WriteSettings`: `internal/agent/agent_desktop.go`,
  `repositories.go`, `agent_desktop_repositories.go`, `any_repository.go`;
  `internal/agent/pair.go` for `WriteConnection`.
- `docs/clarifications/744.md` (Q3, which split this ticket out).

### What the code does today

Writers of the file, and what serializes them:

| Writer | Process | Serialized by |
| --- | --- | --- |
| `saveCredential`, `save-settings`, `set-appearance`, `set-console-view`, `startAgent` | Electron main | nothing; each is a synchronous read, merge, write to `.tmp`, rename |
| `UpdateSettings` and the five `LockSettings` + `WriteSettings` cycles | agent | `settingsMu`, in-process only |
| start-up migration (`storeSettings(settings, false)`) | agent | `settingsMu` only if the caller holds it |
| `WriteConnection` (`sectile-agent pair`) | agent CLI, its own process | nothing, not even `settingsMu` |

Both sides already write through a temporary file and a rename, so the file is
never torn; the loss is a lost update, not a corruption.

How a change gets lost:

1. **Agent change reverted by Electron.** Electron reads the whole file
   (including the agent-owned sections), the agent renames its new file in,
   Electron renames its own copy over it: the agent's change is gone. Every
   Electron writer does this, since each spreads `previous` into the file.
2. **Electron change reverted by the agent.** `storeSettings` re-reads the
   file right before writing and keeps every key it does not own, so an
   Electron write is only lost when it lands between that re-read and the
   rename. The window is narrow but real.
3. **Two agents.** `startAgent` spawns a new agent when `connectAgent` fails,
   which can happen while an older agent is still alive (unreachable, or
   shutting down); their `settingsMu` are distinct. The same holds for
   `sectile-agent pair` run beside a running daemon.

The Electron windows are short (synchronous I/O in one tick), which is why the
loss is rare and never logged; nothing in the code bounds it, though, and the
agent's own cycles (`LockSettings` callers) can hold their read for longer.

### Ambiguities, worst first

1. **Which mechanism.** The ticket lists three directions; they lead to
   different code and different guarantees (Q1).
2. **What a writer does when the guard is held for too long** (a crashed
   process, a hung save): wait and fail, or write anyway (Q2).

### Critical dependencies

- No database migration, no server change, no third-party limit.
- Desktop and agent ship together in the Desktop archives, so both sides of
  the guard land in one release. Binaries already out there do not take it:
  an agent older than the fix that is still running during the upgrade can
  still revert a change once. The layout guard of #744 already limits what
  such an agent can destroy.
- Node has no portable advisory lock (`flock`/`LockFileEx`) without a native
  module; the repository adds no native Electron dependency today.

### Technical choices settled from the code

- **One lock, every writer.** Whatever mechanism Q1 picks, it covers every
  writer in the table above, including `WriteConnection` and the start-up
  migration, which today escape even `settingsMu`. In the agent, the
  cross-process guard is taken inside the existing `settingsMu` section
  (`UpdateSettings`, `LockSettings`), so the in-process mutex stays the first
  line and the file guard the second.
- **Electron funnels its writes through one helper** (`updateSettings(change)`
  in a new `desktop/electron/settings-file.cjs`) that takes the guard, reads,
  applies `change`, writes the `.tmp` and renames, instead of five copies of
  the same five lines.
- **A lock file, if Q1 picks it**, is `settings.json.lock` beside the file,
  created with exclusive create (`O_CREATE|O_EXCL` in Go, `fs.openSync(..., 'wx')`
  in Node), holding the owner's PID, process name and start time, removed on
  release. Exclusive create behaves the same on macOS, Linux and Windows and
  needs no native module. Windows: a rename onto a file another process holds
  open can fail with `EPERM`/`EBUSY`; the writer retries the rename a few times
  before reporting it.
- **Stale lock.** A lock whose PID no longer runs, or older than 30 s, is
  stale: it is broken, and the break is logged (agent log on the agent side,
  `agent.log`-style console line on the Electron side).
- **Tests.** Go: two goroutines simulating two processes through the lock file
  (not `settingsMu`), plus a stale-lock break and a held-lock timeout. Node
  (`node --test`): the helper against a lock held by another process and a
  stale one. One cross-process test spawns the agent binary's write and the
  Electron helper's write concurrently and asserts both keys survive.
- **Documentation.** An ADR records the cross-process settings lock (who takes
  it, the file name, the stale rule), since a third writer added later must
  follow it. `CHANGELOG.md` gets a `Fixed` line under `[Unreleased]`: a save in
  Sectile Desktop no longer silently reverts a workstation setting the agent
  saved at the same moment, and the other way round.
- Error messages and log lines stay in the language their surface already uses.

### Open product questions

**Q1. Mechanism.** Recommended: **A**.
- A. **A cross-process lock file** taken by every writer on both sides
  (settled details above). It works whether or not the agent runs, covers the
  standalone agent, `sectile-agent pair` and two agents alive at once, and
  needs no new API.
- B. **Route Electron's writes through the agent when it runs.** Desktop
  writes before any agent is up (pairing, `startAgent`) and while an
  unreachable one may still be alive, so B still needs A, or keeps those
  windows open; it also adds endpoints for appearance and connection keys.
- C. **Compare-and-swap with retry** (re-read the content or mtime right
  before the rename, retry on change). A rename cannot be made conditional, so
  a window remains between the compare and the rename; it narrows the race
  without closing it.

**Q2. A guard held longer than the wait.** Recommended: **A**.
- A. A writer waits up to 5 s for a live lock, then fails the save with an
  error saying the settings file is busy (the dialog shows it, the agent
  endpoint returns it, `startAgent` reports it like any start failure); a
  stale lock (dead PID or older than 30 s) is broken and logged, then the save
  proceeds.
- B. After the wait, write anyway and log it: no save ever fails, at the cost
  of the race the ticket is about in that one case.

## Round 2 - answers from the owner (2026-10-06)

### Answers

- **Q1: neither A, B nor C.** The owner asked why there are two writers at
  all, and chose a new option **D: one writer per file**. Sectile Desktop stops
  writing `~/.config/sectile/settings.json`; the agent becomes its only writer
  among the processes Desktop starts. This reverses the round 1
  recommendation (A, a cross-process lock file): no lock file is added.
- **Q2 is withdrawn**: with no shared lock there is no held-lock behaviour to
  choose.

### Why Desktop writes the file today, and what D does with each key

Launched by Desktop, the agent receives what it needs as arguments and
environment (`--url`, `--repo`, `TOKEN`), so most of what Desktop writes is
for Desktop alone:

| Key | Today | With D |
| --- | --- | --- |
| `appearance`, `consoleView` | Desktop only; the agent keeps its own `consoleView` copy through `PUT /desktop/console-view` (#711) | Desktop's own file |
| `repo` | Desktop, read back by Desktop and passed as `--repo` | Desktop's own file |
| `secret` (key encrypted with `safeStorage`) | Desktop only; the agent cannot decrypt it | Desktop's own file |
| `apiKey` in clear (no OS key store), `server`, `deviceId` | shared: Desktop and `sectile-agent pair` both write them, the standalone agent and the daemon's `newerStoredKey` read them (ADR 0049) | Desktop keeps its copy in its own file; `settings.json` holds only what the agent side writes |

### Settled technical choices

- **Desktop's own file** is `desktop.json` in Electron's `userData` (not
  `settings.json`: under `SECTILE_DESKTOP_DATA_DIR` the tests already put
  `settings.json` in `userData`). Desktop writes it through one helper in a new
  `desktop/electron/settings-file.cjs`; Desktop is its only writer, and its
  writes all run in the Electron main process, so no lock is needed.
- **Desktop only reads `settings.json`**, never writes it. It reads it for
  three things: the first migration below, a key stored by
  `sectile-agent pair` (below), and the `deviceId` of a workstation the CLI
  paired, so a Desktop pairing replaces that device's key instead of creating
  a second device (#717).
- **Migration.** At its first start, when `desktop.json` does not exist,
  Desktop copies `appearance`, `consoleView`, `repo`, `server`, `deviceId` and
  `secret` or `apiKey` from `settings.json` (or the legacy `agent-settings.json`
  fallback) into `desktop.json`. It leaves `settings.json` as it is.
- **Leftovers in `settings.json`.** The agent's start-up migration removes the
  keys only Desktop used (`appearance`, `consoleView`, `repo`, `secret`). It
  leaves `apiKey`, `server` and `deviceId`, which the standalone agent and
  `pair` still read.
- **Which key is the newest.** Today `pair` deletes `secret` so that Desktop
  never shadows a newer CLI key. With two files that trick is gone, so each
  pairing stamps the time it was made: `WriteConnection` writes `pairedAt` beside
  `apiKey`, and Desktop writes `pairedAt` beside its key in `desktop.json`.
  Desktop uses the `settings.json` key instead of its own only when it is for
  the same server and stamped later. An unstamped key, which predates this change, is older
  than any stamped one. The daemon's `newerStoredKey` applies the same rule:
  a stored key replaces the one it started with only when it is stamped later.
  Desktop passes the stamp of the key it hands over, so a revoked key that
  Desktop left in `settings.json` before the migration is never taken for a
  newer one.
- **The daemon records the connection's public part.** When Desktop starts it, the daemon
  writes `server` and `deviceId` into `settings.json` through its own
  `settingsMu` cycle, never the key. Desktop passes it the `deviceId` as
  well, so `sectile-agent pair` run later on the same workstation still finds
  the device to replace.
- **Remaining writers of `settings.json`**: the daemon (serialized by
  `settingsMu`) and `sectile-agent pair` (`WriteConnection`, its own process).
  A `pair` run while a daemon saves is the one cross-process race left; it is
  out of scope here, and `WriteConnection` is moved under `settingsMu` so at
  least the in-process case is closed. Two daemons alive at once (a restart
  while the old one has not exited) remain possible but are not new.
- **Downgrade.** A Desktop older than the change reads only `settings.json`:
  after the agent's migration removed `secret` it finds no encrypted key and
  asks to pair again. Accepted: it is an explicit downgrade, and it costs a
  pairing, not data.
- **Tests.** Node and UI tests that read or seed `settings.json` for
  Desktop-owned keys move to `desktop.json`: `appearance.ui.cjs`,
  `console-view-sync.ui.cjs`, `pairing.ui.cjs`, `autostart.ui.cjs`,
  `run-folders.ui.cjs`, `conversation.ui.cjs`, `datadir.test.cjs` (which also
  carries the file across the app rename; `desktop.json` joins
  `CARRIED_FILES`). New tests: the migration copies the keys once and never
  writes `settings.json`; a key `pair` stamped later wins over Desktop's, an
  unstamped one does not; a UI test asserts that `settings.json` is
  byte-identical after every Desktop save path (pairing, connection, appearance,
  console view, agent start). Go: the start-up migration removes the
  Desktop-only keys; `newerStoredKey` ignores an unstamped or older key;
  `WriteConnection` stamps `pairedAt`.
- **Documentation.** A new ADR records that `settings.json` has a single
  writer on the Desktop side and that Desktop keeps its own file, and amends
  the key-storage paragraph of ADR 0049 (`pairedAt` replaces "pair deletes
  `secret`"). `CHANGELOG.md`, under `Fixed`: a save in Sectile Desktop no longer
  silently reverts a workstation setting the agent saved at the same moment.

### Open product question

**Q3. The standalone agent reusing a Desktop pairing.** Recommended: **A**.
Today the standalone agent (`sectile-agent` run by hand) can reuse the key
Desktop stored only when Desktop stored it in clear (`apiKey`), that is on a
host with no OS key store, in practice Linux without a keyring. On macOS and
Windows Desktop stores `secret`, which the agent cannot read, so the
standalone agent already needs `sectile-agent pair` or `TOKEN`.
- A. Dropped everywhere: the standalone agent is paired with
  `sectile-agent pair` (or `TOKEN`), as on macOS and Windows today. The daemon
  never writes a key to `settings.json`.
- B. Kept where it works today: when Desktop holds its key in clear, the
  daemon it starts also writes that key as `apiKey` in `settings.json`.

## Round 3 - answers from the owner (2026-10-06)

### Answers

- **Q3: A.** The standalone agent no longer reuses a key Desktop stored. It is
  paired with `sectile-agent pair` or given `TOKEN`, on every platform. The
  daemon Desktop starts never writes a key to `settings.json`; it writes only
  `server` and `deviceId`.

### Consequences recorded

- On a host with no OS key store (Linux without a keyring), a standalone agent
  that relied on the key Desktop wrote in clear needs `sectile-agent pair`
  once after the upgrade. `CHANGELOG.md` gets a `Changed` line for it beside
  the `Fixed` line of round 2: the standalone agent no longer picks up the key
  Sectile Desktop paired with; pair it with `sectile-agent pair`.
- The `apiKey` Desktop left in `settings.json` before the migration is not
  removed by the agent's start-up migration (it cannot tell it from a key
  `pair` wrote); the `pairedAt` rule of round 2 keeps it from being taken for
  a newer key, and the next `sectile-agent pair` replaces it.

### Settled scope

1. Desktop keeps its own keys (`appearance`, `consoleView`, `repo`, `server`,
   `deviceId`, `secret` or `apiKey`, `pairedAt`) in `desktop.json` in
   `userData`, written by one helper, and never writes `settings.json`.
2. A one-time migration copies those keys from `settings.json` (or the legacy
   `agent-settings.json`) into `desktop.json`, leaving `settings.json`
   untouched; the agent's start-up migration removes `appearance`,
   `consoleView`, `repo` and `secret` from `settings.json`.
3. Every pairing is stamped with `pairedAt`; Desktop and the daemon's
   `newerStoredKey` prefer a stored key only when it is stamped later.
4. Desktop passes the `deviceId` (and the key's stamp) to the daemon it starts;
   the daemon records `server` and `deviceId` in `settings.json` under
   `settingsMu`, never the key.
5. `WriteConnection` runs under `settingsMu`. The `pair`-beside-a-daemon race is
   out of scope.
6. Tests, the new ADR, the ADR 0049 amendment and the two `CHANGELOG.md` lines
   as listed in round 2 and above.

No product question is open.
