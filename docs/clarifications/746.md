# Clarification #746 - Desktop rewrites settings.json without a lock shared with the agent

Ticket: https://github.com/sebastienferry/sectile/issues/746
Branch: `feat/746`

## Round 1 (2026-10-06)

### Request

Sectile Desktop (Electron) and the local agent both run read-modify-write
cycles on `~/.config/sectile/settings.json`, and nothing serializes them
across the two processes, so a save by one can put back a value the other has
just changed. The fix makes every writer of that file, on both sides, take the
same cross-process guard, so that neither ever reverts the other's change.
Out of scope: binaries already released (an agent built before the fix keeps
writing without the guard), the semantics of which process owns which key
(#305 stays as it is), and #744's layout guard, which already landed (#748).

### Code and files read

- `desktop/electron/main.cjs`: `readSettings`, `settingsPath`,
  `saveCredential`, the `save-settings`, `set-appearance` and
  `set-console-view` handlers, `startAgent`, `connectAgent`.
- `desktop/electron/credential-store.cjs`: `storeKey` (`secret` or `apiKey`).
- `internal/agentconfig/settings.go`: `ReadSettings`, `WriteSettings`,
  `storeSettings`, `settingsMu`, `UpdateSettings`, `LockSettings`.
- `internal/agentconfig/connection.go`: `WriteConnection`.
- `internal/agentconfig/engines_migration.go`: the start-up migration's
  `storeSettings` call.
- Callers of `LockSettings` + `WriteSettings`: `internal/agent/agent_desktop.go`,
  `repositories.go`, `agent_desktop_repositories.go`, `any_repository.go`;
  `internal/agent/pair.go` for `WriteConnection`.
- `docs/clarifications/744.md` (Q3, which split this ticket out).

### What the code does today

Writers of the file, and what serializes them:

| Writer | Process | Serialized by |
| --- | --- | --- |
| `saveCredential`, `save-settings`, `set-appearance`, `set-console-view`, `startAgent` | Electron main | nothing; each is a synchronous read, merge, write to `.tmp`, rename |
| `UpdateSettings` and the five `LockSettings` + `WriteSettings` cycles | agent | `settingsMu`, in-process only |
| start-up migration (`storeSettings(settings, false)`) | agent | `settingsMu` only if the caller holds it |
| `WriteConnection` (`sectile-agent pair`) | agent CLI, its own process | nothing, not even `settingsMu` |

Both sides already write through a temporary file and a rename, so the file is
never torn; the loss is a lost update, not a corruption.

How a change gets lost:

1. **Agent change reverted by Electron.** Electron reads the whole file
   (including the agent-owned sections), the agent renames its new file in,
   Electron renames its own copy over it: the agent's change is gone. Every
   Electron writer does this, since each spreads `previous` into the file.
2. **Electron change reverted by the agent.** `storeSettings` re-reads the
   file right before writing and keeps every key it does not own, so an
   Electron write is only lost when it lands between that re-read and the
   rename. The window is narrow but real.
3. **Two agents.** `startAgent` spawns a new agent when `connectAgent` fails,
   which can happen while an older agent is still alive (unreachable, or
   shutting down); their `settingsMu` are distinct. The same holds for
   `sectile-agent pair` run beside a running daemon.

The Electron windows are short (synchronous I/O in one tick), which is why the
loss is rare and never logged; nothing in the code bounds it, though, and the
agent's own cycles (`LockSettings` callers) can hold their read for longer.

### Ambiguities, worst first

1. **Which mechanism.** The ticket lists three directions; they lead to
   different code and different guarantees (Q1).
2. **What a writer does when the guard is held for too long** (a crashed
   process, a hung save): wait and fail, or write anyway (Q2).

### Critical dependencies

- No database migration, no server change, no third-party limit.
- Desktop and agent ship together in the Desktop archives, so both sides of
  the guard land in one release. Binaries already out there do not take it:
  an agent older than the fix that is still running during the upgrade can
  still revert a change once. The layout guard of #744 already limits what
  such an agent can destroy.
- Node has no portable advisory lock (`flock`/`LockFileEx`) without a native
  module; the repository adds no native Electron dependency today.

### Technical choices settled from the code

- **One lock, every writer.** Whatever mechanism Q1 picks, it covers every
  writer in the table above, including `WriteConnection` and the start-up
  migration, which today escape even `settingsMu`. In the agent, the
  cross-process guard is taken inside the existing `settingsMu` section
  (`UpdateSettings`, `LockSettings`), so the in-process mutex stays the first
  line and the file guard the second.
- **Electron funnels its writes through one helper** (`updateSettings(change)`
  in a new `desktop/electron/settings-file.cjs`) that takes the guard, reads,
  applies `change`, writes the `.tmp` and renames, instead of five copies of
  the same five lines.
- **A lock file, if Q1 picks it**, is `settings.json.lock` beside the file,
  created with exclusive create (`O_CREATE|O_EXCL` in Go, `fs.openSync(..., 'wx')`
  in Node), holding the owner's PID, process name and start time, removed on
  release. Exclusive create behaves the same on macOS, Linux and Windows and
  needs no native module. Windows: a rename onto a file another process holds
  open can fail with `EPERM`/`EBUSY`; the writer retries the rename a few times
  before reporting it.
- **Stale lock.** A lock whose PID no longer runs, or older than 30 s, is
  stale: it is broken, and the break is logged (agent log on the agent side,
  `agent.log`-style console line on the Electron side).
- **Tests.** Go: two goroutines simulating two processes through the lock file
  (not `settingsMu`), plus a stale-lock break and a held-lock timeout. Node
  (`node --test`): the helper against a lock held by another process and a
  stale one. One cross-process test spawns the agent binary's write and the
  Electron helper's write concurrently and asserts both keys survive.
- **Documentation.** An ADR records the cross-process settings lock (who takes
  it, the file name, the stale rule), since a third writer added later must
  follow it. `CHANGELOG.md` gets a `Fixed` line under `[Unreleased]`: a save in
  Sectile Desktop no longer silently reverts a workstation setting the agent
  saved at the same moment, and the other way round.
- Error messages and log lines stay in the language their surface already uses.

### Open product questions

**Q1. Mechanism.** Recommended: **A**.
- A. **A cross-process lock file** taken by every writer on both sides
  (settled details above). It works whether or not the agent runs, covers the
  standalone agent, `sectile-agent pair` and two agents alive at once, and
  needs no new API.
- B. **Route Electron's writes through the agent when it runs.** Desktop
  writes before any agent is up (pairing, `startAgent`) and while an
  unreachable one may still be alive, so B still needs A, or keeps those
  windows open; it also adds endpoints for appearance and connection keys.
- C. **Compare-and-swap with retry** (re-read the content or mtime right
  before the rename, retry on change). A rename cannot be made conditional, so
  a window remains between the compare and the rename; it narrows the race
  without closing it.

**Q2. A guard held longer than the wait.** Recommended: **A**.
- A. A writer waits up to 5 s for a live lock, then fails the save with an
  error saying the settings file is busy (the dialog shows it, the agent
  endpoint returns it, `startAgent` reports it like any start failure); a
  stale lock (dead PID or older than 30 s) is broken and logged, then the save
  proceeds.
- B. After the wait, write anyway and log it: no save ever fails, at the cost
  of the race the ticket is about in that one case.
