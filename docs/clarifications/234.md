## Round 1 (2026-09-23)

### Restated request and scope

Make the existing `make fmt-check` gate run server-side, so that a pull request introducing an unformatted Go file shows a failing check on that pull request, and document that `make fmt-check` reproduces the failure locally. Out of scope: changing the formatter (`gofmt -s`, `gofumpt`), fixing the pre-existing Go test failures, and any change to the image, binary or promotion jobs.

### Verified findings

Files read: `Makefile` (`fmt-check`, `test`), `.gitlab-ci.yml`, `openspec/changes/163-gofmt-baseline/design.md`, `go.mod`, `Dockerfile`, `README.md` (§ "Container image and GitLab CI", § gofmt), `AGENTS.md` (release section).

- **The ticket's premise is outdated.** The #163 design (last touched 2026-09-17) rejected CI because "there is no `.github/` directory and no CI convention". One day later, `81e3bc1` (2026-09-18) added `.gitlab-ci.yml`: the GitHub repository is **pull-mirrored into GitLab**, and a pipeline runs on every mirrored branch and tag (`workflow: rules` on `$CI_COMMIT_BRANCH` / `$CI_COMMIT_TAG`) with `test:go`, `test:postgres`, `test:web` and `test:desktop` jobs. So a CI convention exists now. It is GitLab, not GitHub Actions.
- **That pipeline does not know about GitHub pull requests.** Its header says "the pipeline knows nothing of pull requests", and README says "The GitHub pull request alone spawns nothing". A branch pipeline does run on the head commit of a same-repo PR branch after the mirror syncs. Whether its result shows up on the GitHub PR depends on the GitLab project's GitHub integration, which posts commit statuses back. That is project configuration and can't be checked from the repository.
- **The pipeline does not run `make test` as a whole.** It splits the suite into separate jobs, and `test:go` is `allow_failure: true` because of four pre-existing failures on `main`. So a "run the wider `make test`" gate would currently be red on every PR, or it would be advisory, which misses the point.
- **Nothing runs `gofmt` in CI today.** `fmt-check` is only reached through the local `make test`.
- **Toolchain:** `go.mod` declares `go 1.26.6`. CI sets `GOTOOLCHAIN=auto`, so the runner fetches exactly 1.26.6 even when its image ships 1.26.4. A contributor using Go's default `GOTOOLCHAIN` behaves the same way. `gofmt` therefore already matches across both sides without a separate pin.
- `README.md` already documents `make fmt-check` / `gofmt -w .` as the local reproduction (lines ~919-922).

### Ambiguities (worst first)

1. **Which CI hosts the gate:** a job in the existing GitLab mirror pipeline, or a new GitHub Actions workflow. This is the ticket's main "Decide" question. The finding above changes the trade-off, see Q1.
2. **Whether GitLab results reach the GitHub PR.** If they don't, a GitLab job can't meet the ticket's "Done when" (a failing check *on that pull request*).
3. **Scope of the gate:** `fmt-check` alone or the wider `make test`.
4. **Required status check:** it is configured in GitHub branch protection, outside the repository. With GitLab, the status GitHub receives is pipeline-level, not per job.

### Critical dependencies

- **GitLab ↔ GitHub status reporting** (GitLab project settings → Integrations → GitHub). Needed if the gate goes into GitLab.
- **Mirror sync latency.** A pull mirror updates on a schedule unless it is triggered, so a GitLab-hosted check can lag behind a push.
- **Fork pull requests.** The pull mirror only copies the repository's own branches, so PRs from forks never get a GitLab pipeline. Only GitHub Actions covers them.
- **GitHub branch protection on `main`.** Only a repository admin can make a check required. It is a manual settings change, not code.
- **GitHub Actions** (if chosen): no secrets needed for `gofmt`, and public-repo runners are free.

### Resolved technical choices (reversible, by convention)

- **Command:** the job runs `make fmt-check` (or its exact recipe), so CI and the local reproduction stay one command, as the ticket asks.
- **Toolchain:** follow `go.mod` (`go-version-file: go.mod` for Actions, or `GOTOOLCHAIN=auto` as already set for GitLab). No second version pin that could drift.
- **If GitLab:** a new `lint:gofmt` job (or `test:fmt`) in the `test` stage, extending `.go-test` / `.go-cache`, `needs: []`, **not** `allow_failure`. This follows the `test:postgres` precedent: it starts green, and its purpose is to gate. It is not added to the `needs` of the publish jobs, so the scope stays out of the publishing path.
- **If GitHub Actions:** trigger on `pull_request` and on `push` to `main`. The job needs no secrets and runs on `ubuntu-latest` with `actions/setup-go`.
- **Docs:** extend the README gofmt paragraph with one sentence naming the CI job and saying `make fmt-check` reproduces it.

### Open product questions

**Q1. Where does the gate live?**
- **(a) Recommended, if the GitLab project already reports commit statuses to GitHub:** add a job to the existing `.gitlab-ci.yml`. No new CI system, it follows the convention adopted after #163, and it costs almost nothing. Limitations: fork PRs are not checked, results can lag behind a push by the mirror sync interval, and GitHub sees one pipeline-level status.
- **(b)** Add a minimal `.github/workflows/fmt.yml`. This is the only option that reliably gives a per-check result on every GitHub PR, fork PRs included. Cost: a second CI system to maintain next to GitLab.
- Please also confirm whether the GitLab project's GitHub integration is enabled (status of a recent PR's head commit on GitHub). If it isn't, (a) can't meet "Done when" unless someone enables it.

**Q2. Scope: `fmt-check` only, or the wider `make test`?**
Recommended: **`fmt-check` only.** The GitLab pipeline already runs the web and desktop suites. The Go suite can't gate today because `test:go` is `allow_failure` over four known failures. Widening the gate belongs to the ticket that fixes those failures.

**Q3. Should the check become a required status check on `main`?**
Recommended: **yes.** The ticket's goal is to block merges, and an advisory check doesn't. This has to be done by a repository admin in GitHub branch protection after the first green run. The deliverable will document the check name to require. With option (a), the required status is the whole GitLab pipeline, which also covers publishing jobs. Please confirm that's acceptable, or it's a point for (b).

Triggers (PRs and pushes to `main`) and toolchain pinning are settled above by convention and need no answer.

## Round 2 - answers from the owner (2026-09-23)

Answers given in session: "1 a 2 gofmt only 3 yes".

### Settled decisions

1. **CI host: the existing GitLab mirror pipeline (option a).** Add a gating `lint:gofmt` job to `.gitlab-ci.yml` in the `test` stage. It extends `.go-test` / `.go-cache`, has `needs: []`, is not `allow_failure`, and runs `make fmt-check`. No `.github/` workflow is added. The owner accepts the stated limits: fork pull requests are not checked, and the result waits for the mirror to sync.
2. **Scope: `fmt-check` only.** The wider `make test` stays out of the gate until the four `test:go` failures are fixed under their own ticket.
3. **Required status check on `main`: yes.** The status GitHub receives covers the whole GitLab pipeline, publish jobs included, and the owner accepts that. A repository admin configures it in GitHub branch protection after the job's first green run. The deliverable documents which status context to require.

### Reversed prior assumptions

- The #163 design rejected CI because "no CI convention" existed. That is superseded: the gate follows the GitLab convention introduced in `81e3bc1`.
- The GitHub Actions option is dropped.

### Remaining dependency (not a product question)

- **Operational prerequisite:** "Done when" (a failing check on the GitHub PR) holds only if the GitLab project's GitHub integration posts commit statuses back to GitHub. The implementation must check this on a PR's head commit. If it is off, enabling it (GitLab → Settings → Integrations → GitHub) is a one-time admin action. Record it in the PR, since it is not a code change.

### Settled scope

- `.gitlab-ci.yml`: new `lint:gofmt` job as above. It does not change the `needs` of the publish or promote jobs.
- `README.md` gofmt paragraph: name the CI job and state that `make fmt-check` reproduces it locally. Note that making the check required is a branch-protection setting.
- No change to `Makefile`, the formatter or the toolchain pin: `go.mod` together with `GOTOOLCHAIN=auto` already aligns `gofmt`.

### Exit condition

All three product questions are answered, and none remain open. Clarification is complete.
