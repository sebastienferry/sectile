# Clarification #913 - Tauri: auto-expanding composer and Up/Down prompt history navigation

Ticket: https://github.com/sebastienferry/sectile/issues/913
Branch: `feat/913`

## Round 1 - initial analysis (2026-11-17)

### Restated request

Both composers of Sectile Desktop (Tauri), the "New prompt" view and the
active conversation, get a textarea that grows with its content from a ~2-line
resting height up to `max(150px, 40% of the conversation view height)`, kept in
sync by a `ResizeObserver`, then scrolls internally; and the conversation
composer lets the user step through the prompts already sent in that
conversation with `ArrowUp` / `ArrowDown`, `Escape` clearing a recalled prompt.

Out of scope: history persisted across conversations or app restarts, search
in history (Ctrl+R style), the Electron desktop and the web client, the
read-only history footer (it has no composer), and queued messages that were
not sent yet.

### Code read

- `desktop-tauri/src/components/ProjectPrompt.tsx`: both textareas are
  `rows={2}` with no sizing logic (new prompt, line 125; conversation, lines
  514-530). `sendOnEnter` (line 30) already ignores IME composition. In the
  conversation, `Escape` interrupts the running turn while `busy` (line 521).
- `desktop-tauri/src/App.css:1770`: `.project-prompt .composer textarea` has
  `min-height:48px; max-height:200px; line-height:1.45; resize:none`.
  The textarea never grows today because nothing sets its height; the fixed
  `200px` cap must become the dynamic one.
- `desktop-tauri/src/lib/conversation.ts`: the snapshot carries `events`
  (JSON lines) decoded by `decodeEvents`; user prompts are events of
  `kind: "user"`.
- `desktop-tauri/src/components/ConversationTranscript.tsx:31`:
  `cleanUserEventText` strips the trailers Sectile injects (run contracts,
  task UUID prefixes), which is the text the transcript shows.
- `desktop-tauri/src/lib/conversation-queue.ts`: queued messages live outside
  the snapshot events until they are sent.
- Reference: `claudian/src/features/chat/composer/textareaSizing.ts`,
  `PromptHistoryNavigation.ts`, `src/style/components/composer-editor.css`.
- Tests: `desktop-tauri/tests/*.test.ts` (node test runner, `npm test`) and
  `tests/*.ui.test.tsx` (vitest, `npm run test:ui`), e.g. `prompt.ui.test.tsx`.

### Ambiguities (worst first)

1. **History in the "New prompt" view.** The acceptance criterion "works in
   both views" is clear for the auto-grow, but the new-prompt view has no
   session, so "prompts sent in the active session" is empty there. Either the
   history is simply absent there, or it draws from somewhere else (the
   project's recent conversations), which needs a new data source. -> Q1.
2. **`Escape` while a turn runs.** In the conversation composer `Escape`
   already interrupts the running turn. With a recalled prompt in the
   composer during a turn, one key has two meanings. -> Q2.
3. **Non-empty draft with the caret on the first row.** The ticket reads
   "empty or caret on the first/last row", which could let `ArrowUp` replace a
   draft the user typed. The reference only *starts* a recall from an empty
   composer, and uses the edge-row rule only while a recalled prompt is shown.
   Settled as decision D3 (no draft is ever overwritten).
4. **Which text is recalled.** Raw `user` event text contains injected
   trailers. Settled as decision D4.

### Critical dependencies

- None outside `desktop-tauri`: no agent, server, migration or tracker change.
  History is derived from the snapshot events already loaded on the client.
- `ResizeObserver` must be stubbed in the vitest/jsdom environment.
- jsdom has no layout, so "first/last rendered row" is approximated by logical
  lines in unit tests; the real row detection is verified manually.

### Settled technical choices (reversible, from code and conventions)

- D1. Sizing: a small hook (e.g. `useAutoGrowTextarea`) resets `height` to
  `auto` and sets it to `scrollHeight` on every value change, clamped by a CSS
  custom property `--composer-max-height` computed as
  `Math.max(150, viewHeight * 0.4)`. The observed container is
  `.project-prompt` for the new-prompt view and `.conversation-main-column`
  for the conversation (the column that holds the transcript, so the side pane
  does not count). `min-height:48px` and `line-height:1.4` as in the ticket;
  `overflow-y:auto` only once the cap is reached. The fixed `max-height:200px`
  is removed.
- D2. History logic lives in a pure, framework-free module (e.g.
  `src/domain/prompt-history.ts`) taking the prompt list, the current value,
  the caret and the key, and returning the new value or "not handled", so it is
  unit-tested with `npm test`; the component wires it in `onKeyDown`.
- D3. A recall starts only from an empty composer with `ArrowUp`. While the
  composer shows exactly the recalled text, `ArrowUp`/`ArrowDown` move through
  history only when the caret is collapsed on the first/last rendered row;
  otherwise they move the caret. As soon as the user edits the recalled text it
  becomes an ordinary draft and the arrows stop recalling. Modifier keys
  (Shift, Ctrl, Alt, Meta) never recall.
- D4. Recalled prompts are the conversation's `kind: "user"` events, in order,
  with the text the transcript shows (`cleanUserEventText`), empty ones
  dropped. Queued, not yet sent messages are not part of history.
- D5. IME: no recall while `isComposing` or between `compositionstart` and
  `compositionend`, as `sendOnEnter` already does for Enter.
- D6. Recall state resets when the conversation changes (`id`) and after a
  send.
- D7. Test coverage: unit tests for the history module, UI tests in
  `prompt.ui.test.tsx` (recall, step, clear, multi-line caret, IME, the
  `--composer-max-height` update from a stubbed `ResizeObserver`).
- D8. `CHANGELOG.md` gets one `Added` line under `[Unreleased]`.

### Open product questions

- **Q1. Up/Down history in the "New prompt" view.** Recommended: **(A)** the
  view gets the auto-grow only; `ArrowUp` keeps its native behaviour there,
  since there is no session yet. Alternative (B): recall the project's recent
  prompts across its conversations, which needs a new source of data and goes
  beyond "the active session".
- **Q2. `Escape` while a turn runs and a prompt is recalled.** Recommended:
  **(A)** `Escape` first clears the recalled prompt; a second `Escape`, on an
  empty or ordinary draft, interrupts the turn as today. Alternative (B):
  `Escape` always interrupts while a turn runs, and clears a recall only when
  idle.

## Round 2 - answers from the owner (2026-11-17)

Answers given interactively in the clarification session.

### Settled decisions

- **Q1 -> (A).** The "New prompt" view gets the auto-grow only. `ArrowUp` and
  `ArrowDown` keep their native caret behaviour there; prompt history exists
  only in an active conversation composer. The acceptance criterion "works in
  both views" applies to the auto-grow; history coverage targets the
  conversation composer.
- **Q2 -> (A).** In the conversation composer, while a prompt is recalled,
  `Escape` clears it back to an empty draft, whether or not a turn runs. When
  no prompt is recalled (empty or ordinary draft), `Escape` interrupts the
  running turn exactly as today. Clearing a recall therefore never interrupts,
  and a second `Escape` does.

### Reversed assumptions

None. Decisions D1 to D8 of Round 1 stand. D1 still observes `.project-prompt`
for the new-prompt view, since the auto-grow applies there.

### New ambiguities or dependencies

None.
