# #318 - A run blocked on a user question cannot be told apart from a working run

## Provenance of this report

The clarification ran in two rounds on 2026-09-22 and the owner confirmed it the
same day. The report and the specification it led to were committed on a
`feat/318` branch that was never pushed and no longer exists: neither the
commits quoted on the ticket (`06f5a27`) nor the files survive in any worktree,
reflog or unreachable object. What survives is the clarification comment the
workflow posted on the issue, which records every settled decision.

This file is rebuilt from that comment on 2026-09-24, in the pickup of the batch
#318 + #319. It restates the settled decisions and the technical choices; it does
not reopen them. Where the comment is terse, the reading chosen is the one the
code supports, and it is marked as such.

## Request restated

Since #307 a silent MCP session keeps its run `running` and gets one sentence
appended to it; the board still cannot say whether that run is working or is
blocked on a question its owner has to answer, and in the second case nobody is
told. The request is to feed the ADR 0012 waiting model again from a path that
survives the removal of the Claude Code hook, so that a run blocked on the user
shows as waiting on the board and on the desktop.

Out of scope: the silence marking itself (#307), a new visual "silent" state
(that belongs to #319), a tracker notification, the text of the question, and
detecting tool permission prompts.

## Ambiguities (settled in round 2)

- **A1 - Who declares the wait.** A hook is excluded (ADR 0012 revision). The
  only party that knows it is about to block is the model itself, so the wait is
  declared through an MCP tool it calls before asking.
- **A2 - Who clears it.** Relying on the model to clear its own wait leaves a run
  waiting forever the day it forgets. The wait is therefore cleared implicitly
  as well: by the declaring session's next MCP call, since a session that speaks
  again is no longer blocked, and by every terminal status, as today.
- **A3 - What the desktop banner is fed from.** The desktop reads the local
  agent's run list, which lost `waitingSince` with #260. It has to be carried
  there again.

## Critical dependencies

- No migration: `waiting_since` already exists on both stores.
- The desktop banner depends on the agent's run list carrying `waitingSince`,
  which needs a server-to-agent message (the report is made on the server, over
  MCP, not on the workstation).
- The skills shipped by Sectile must tell the model to call the tool, or the
  signal stays as idle as it is today.

## Settled decisions (owner, round 2)

- **S1 - One MCP tool declares and clears an in-run wait**, `report_waiting`
  `{taskKey, runId, waiting}`. The wait is also cleared implicitly on the
  declaring session's next MCP call, and on every terminal status.
- **S2 - Tool permission prompts stay undetected**, and the documentation says
  so. Only a question the model asks deliberately is declared.
- **S3 - No "silent" visual state in this ticket.** The #307 note is unchanged;
  the silent state is #319's.
- **S4 - The desktop banner is repaired** by carrying `waitingSince` to the local
  agent's run list, for the workstation user's own runs only.
- **S5 - No tracker notification.** The board and the desktop banner are the
  notification.
- **S6 - No question text.** The mark stays a timestamp, so there is no
  migration.

## Technical decisions (reversible, settled here)

- **T1 - Ownership mirrors `finish_run`**: the run's owner, an admin, or anyone on
  an ownerless legacy run may declare or clear its wait.
- **T2 - A headless run is a no-op**: an autonomous run has nobody to answer, so a
  wait reported on one is accepted and ignored, and the tool says so.
- **T3 - First mark wins**: a second `waiting: true` keeps the original
  `waitingSince`, so the elapsed time the board shows is the real one.
- **T4 - The skill fragments and their golden files are updated** so every
  shipped skill tells the model to report the wait before a blocking question.
- **T5 - ADR 0012 gets a revision** naming the new reporter.
