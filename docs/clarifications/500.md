# Clarification #500 - Next button in desktop

- Ticket: https://github.com/sebastienferry/sectile/issues/500
- Branch: `feat/500`
- Stage: new -> clarified

## Round 1 - analysis (2026-09-25)

### Request restated

In the desktop app, the workflow button of the console toolbar reads
`Current: <skill>` while an execution of the selected task is running, and
`Next: <skill>` once no execution of that task is active, instead of always
reading `Next: <skill>` and merely greying out during a run. Out of scope: the
web client, the workflow itself (which skill follows which stage), and the
launch mechanics behind the button (freshness recheck, duplicate guard,
"Launch anyway").

### What exists today (files read)

- `desktop/src/main.js:39`: the toolbar holds `#next-step` (the workflow
  button), `#mark-reviewed`, `#retry-next-step`, `#force-next-step`, and the
  footer status `#next-step-status`.
- `desktop/src/main.js:2323` `renderNextStep()`: the button shows
  `'Next: '+step.label` whenever the computed step has a skill, and is only
  disabled while `busy` (any active run on the task, `activeRun` at line 83:
  `running`, `queued`, `preparing`, `waiting`) or `pending` (submitting, or
  submitted and waiting for its console). The footer says
  `<key> · <stage> · Execution in progress` in that case.
- `desktop/src/workflow.mjs`: `nextTaskStep(task, project)` derives the step
  from the task's workflow stage only (`new -> Clarify`, `clarified ->
  Specify`, `specified -> Implement`, `implemented -> Adjust` or `Create PR`,
  `reviewed -> Handoff`). It knows nothing about runs.
- `desktop/src/main.js:79` `runLabel()`: a task run is identified by
  `run.skill`, the skill id actually launched (`clarify`, `pickup`, `adjust`,
  `discuss`, ...), which is not necessarily the step the stage would propose.
- `desktop/src/main.js:2021` `updateTicketRow()`: the Tickets pane of the
  desktop has its own per-row `Run: <label>` button, disabled with the tooltip
  "An execution is active on this task" during a run.
- `desktop/tests/next-step.ui.cjs`, `desktop/tests/concurrent-launch.ui.cjs`:
  UI tests assert the `Next: <label>` accessible names.

### Ambiguities (worst first)

1. **What `XXXX` names while a run is active.** Reading A: the label of the
   stage's step (`nextTaskStep`), which during a normal run is the skill being
   run, since the stage has not moved yet. Reading B: the skill of the active
   execution (`run.skill`). They differ as soon as the running execution is
   not the stage's step: a `pickup` chain, an `adjust` launched from the
   Tickets menu, a discussion console, a custom-instructions run. Reading A
   would say `Current: Clarify` while `pickup` is actually running.
2. **"Session running" is the selected console or the task.** The button
   already reasons per task (`busy` = any active run on the task). If the
   selected console is a finished execution of a task that has another active
   execution, reading "selected console" would show `Next:`, reading "task"
   would show `Current:`.
3. **Whether `Current:` is actionable.** Today the button is disabled during a
   run. It could stay a disabled indicator, or become a shortcut that selects
   the running console when the user is looking at another execution of the
   same task.
4. **Transitional states.** Between the click and the console appearing
   (`Submitting execution…`, `Execution submitted; waiting for its console`),
   and for `queued`, `preparing` and `waiting` runs: `Current:` or `Next:`?
5. **Tickets pane.** Whether the per-row `Run: <label>` of the desktop Tickets
   pane follows the same rule (`Current: <label>` during a run) or is left
   alone.

### Critical dependencies

None. The change is confined to the desktop renderer: no server, migration,
MCP or tracker change. The run list the desktop already polls carries
`status`, `skill` and `taskId`, which is everything the label needs.

### Technical choices resolved from the code

- **Wording and casing** follow the existing English toolbar labels:
  `Current: Clarify`, `Next: Specify` (no space before the colon, which the
  ticket's `Current : XXXX` shows in French typography).
- **Skill display name.** When the label comes from `run.skill`, the id is
  mapped to the same labels `workflow.mjs` uses (`clarify -> Clarify`, ...)
  so that `Current: Clarify` then `Next: Specify` read as one family; an id
  without a known label is shown capitalized as is (`Pickup`).
- **Footer status** keeps its current messages (`Execution in progress`, ...).
- **Tests.** `desktop/tests/next-step.ui.cjs` gains the `Current:` case;
  existing `Next:` assertions stay valid for idle tasks.
- **Changelog.** User-visible, so one `Changed` line under `[Unreleased]`.

### Product questions (recommendation first)

1. What does `Current:` name? **Recommended: the skill of the active
   execution (`run.skill`)**, because it tells the truth when a pickup or a
   manually chosen skill is running. Alternative: the stage's step.
2. Scope of "running": **Recommended: any active execution of the task**
   (`running`, `queued`, `preparing`, `waiting`, plus the submitting and
   submitted states), consistent with the existing busy guard. Alternative:
   only the selected console's own status.
3. Is `Current:` clickable? **Recommended: a disabled indicator**, as today.
   Alternative: it selects the running console when another one is shown.
4. Tickets pane `Run: <label>`: **Recommended: out of scope**, keep this
   ticket to the console toolbar button. Alternative: apply the same rule.
