# Clarification #855: Personal GitHub/GitLab OAuth for end-user ticket and comment operations; sync on a service account or token

## Round 1 (2026-10-21)

Report: `docs/clarifications/855.md` on `feat/855` (worktree `.tasks/worktrees/issue-855`, created from `origin/main` at `a6a5c60a`). Not pushed (`pushStageCommits` off). No pull request at this stage (`prCreationStage` is `implemented`).

### Restated request and scope

A person can connect GitHub and GitLab through OAuth, but that connection only signs the ticket and comment operations that person performs themself: creating and editing tickets, and posting comments. Everything else (board sync, tracker polling, unattended work, the admin screens) authenticates with the provider's server credential, the token an administrator set, and never with somebody's grant.

Out of scope: merge-request work done on the workstation through `glab`/`gh`, signing in to Sectile (OIDC, ADR 0008), Sectile Desktop. #804 is closed as not planned and PR #807 was closed unmerged; this ticket replaces both.

### Ambiguities, worst first

1. **Where the line between "operations the person performs" and "synchronisation" falls.** ADR 0029 ties to the person every write they *cause*, including the writes Sectile makes later on their behalf (stage labels and reports, managed run transitions, epic and macro mirrors, milestone writes) and every read made in their name. The ticket keeps the personal credential for "creating and editing tickets, and posting comments" only. Reading A: only direct ticket actions stay personal and everything else moves to the service account, which amends ADR 0029. Reading B: ADR 0029 stays as is and the ticket only fixes the GitLab check inversion and the admin screens. The two readings change the routing of about fifteen operation kinds. See Q1.
2. **Whether the rule is about the OAuth grant only, or every personal credential.** Main already routes pasted tokens and the Jira grant through the same `ForActingUser`. Restricting only the GitHub/GitLab grant would make the same action go out under a different account depending on how the person authenticated. See Q2.
3. **Reads.** The ticket does not mention them. On main, a person-tied read uses that person's credential first. Under the owner's rule, a board status list, a PR state refresh or a comment list are synchronisation-like reads. See Q1, line "Reads".
4. **The admin check.** Main already shows the admin's own account when GitHub or Jira is re-checked with an empty token on the Administration screen. See the technical decisions.

### Reversible technical choices resolved from existing code and conventions

- **The Administration credential check never reads a personal credential.** With an empty token it checks the stored server credential, for GitHub, GitLab and Jira alike. Checking one's own credential stays on *Profile → Tracker credentials* (`ConfirmUserTrackerCredential`), which already exists. This fixes the inversion and its GitHub/Jira siblings on main.
- **One routing function per category, not per call site.** Sectile already funnels writes through `ForWrite`; the change becomes a classification of each operation (personal or server), held in one place and pinned by a test that lists every `TrackerOp` kind and every direct write.
- **Reuse from PR #807**, rebased on main:
  - kept: `forgeoauth` and its fake, the grant store with GitLab refresh, the OAuth flow table's `tracker` column (new migration number), one OAuth app per tracker, connect and callback handlers, the web connect and OAuth app panels, the scope pin tests, fr/en strings;
  - dropped: the GitLab empty-token check of the caller's grant; plugging the grant into the read path and into the unattended paths;
  - renumbered: the ADR becomes 0058, and it amends ADR 0029.
- **#804 decisions carried over unchanged:** a GitHub OAuth App (not a GitHub App), gitlab.com only, the pasted token kept behind "Use a token instead", no migration of existing tokens, a GitHub `401` marking the grant disconnected, GitLab refresh with compare-and-set, the grant sealed under the server key, best-effort revocation on disconnect, the account filled from `GET /user`.
- **Scopes are re-pinned to the personal operations only.** GitHub's `read:project` was needed by ProjectsV2 reads that now go to the service account; the specification pins the least scopes the personal writes need, in a test.
- **Provider app registration and the end-to-end check stay planned tasks** (E1 GitHub OAuth App and organisation approval, E2 gitlab.com application, E3 end-to-end check), as the owner asked on #804.
- Documentation: ADR 0058, `docs/API_AND_DATA_SPEC.md`, `docs/USER_GUIDE.md`, `.env.sample`, CHANGELOG under Unreleased.

### Critical dependencies

- **A service account on each forge with enough rights.** Under reading A, the server credential now signs stage labels, transitions, epic mirrors and milestone writes for every project. The GitHub and GitLab service accounts need write access to every repository Sectile serves, and the GitHub one needs `read:project`/`project` for ProjectsV2. Today a missing server token only broke the sync; it would then break those writes too.
- **Provider OAuth apps** registered by their administrators (E1, E2), with callbacks `https://sectile.internal.eqtv.dev/auth/github/callback` and `https://sectile.internal.eqtv.dev/auth/gitlab/callback`; GitHub organisations that restrict OAuth apps must approve it.
- No other repository involved. One migration (the `tracker` column on the OAuth flow table).

### Product questions

1. **Q1 - Which operations use the person's credential?** Recommended, per category:

   | Operation | Credential |
   | --- | --- |
   | Create a ticket (web, MCP create_task from an interactive session) | personal |
   | Edit a ticket: title, description, labels, fields, assignee, parent, team, sprint, a board column drop | personal |
   | Post a comment (web, MCP add_comment from an interactive session) | personal |
   | Stage transitions, workflow labels and stage reports posted by a skill run (`transition_stage`, managed runs, pickup) | **service** |
   | Epic and macro mirrors (horizon, priority, quarter, readiness, labels, todos, framing, push horizons, GitHub milestones) | **service** |
   | Reads: board statuses, PR states, comments, issue lists, checks | **service** |
   | Synchronisation, polling, Administration | service (already so) |

   This amends ADR 0029: the server credential then signs every write Sectile makes by itself, not only unattended ones. Alternative: keep ADR 0029 (everything a person causes, stage reports included, stays personal) and only fix the GitLab check and the admin screens.
2. **Q2 - Does the rule apply to every personal credential, or only to the GitHub/GitLab OAuth grant?** Recommended: to every personal credential (pasted token, Jira grant, GitHub/GitLab grant), so an operation goes out under the same account whatever way the person authenticated. That brings Jira into the change. Alternative: only GitHub/GitLab grants; pasted tokens and Jira keep ADR 0029.
3. **Q3 - Fallback without a personal connection.** Recommended: the pasted token stays an accepted personal credential; with neither, a personal operation is refused with the existing *Profile → Tracker credentials* message, never sent under the service account (ADR 0029). Alternative: fall back to the service account, so the operation is attributed to it.
4. **Q4 - GitLab scope.** Recommended: gitlab.com only, as settled on #804; a self-hosted GitLab keeps the pasted token. Alternative: one OAuth app per GitLab instance.
5. **Q5 - Baseline.** Is this clarification satisfactory: the reuse plan for PR #807, the Administration check limited to server credentials, ADR 0058 amending ADR 0029, and E1 to E3 kept as planned tasks?
