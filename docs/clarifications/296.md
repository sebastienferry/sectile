# #296 - Dual DB support

Round 1 - 2026-09-21

## Request restated

Sectile stores everything in a single embedded SQLite file opened by `db.NewDB(dbPath)`.
The ticket asks for PostgreSQL as an alternative backing store, selected at startup through
environment variables, behind a thin code-level abstraction so the rest of the application
does not know which engine is underneath.

Out of scope for this ticket: changing the data model, changing what is stored, adding an ORM,
sharding or replication, and any change to the desktop packaging — SQLite stays the default and
the only engine the desktop app ships with.

boundary, it is just not an interface.

## Ambiguities, worst first

### A1 — Where exactly is the "thin interface"? (resolved, see D1)

Two readings lead to very different code:

- **Repository interface above `*DB`**: `type Store interface { ...210 methods... }` with a
  SQLite implementation and a PostgreSQL implementation. That means writing a second copy of
  ~20 000 lines and maintaining both forever. It is what "a thin interface abstracting the
  underlying technology" says literally, and it is not thin.
- **Dialect layer below `*DB`**: one `*DB`, one set of 342 queries, and a small `dialect`
  abstraction handling the six things that actually differ between the two engines
  (placeholders, DDL column types, upsert syntax, catalogue introspection, the boolean
  representation, and connection setup).

### A2 — Do the legacy migrations have to run on PostgreSQL? (resolved, see D3)

The current migration model is "run `ALTER TABLE ... ADD COLUMN` and ignore the error", plus one
full table rebuild (`migrateTasksKeyUnique`) that reads `sqlite_master`, runs a 20-statement
script under `PRAGMA foreign_keys=OFF`, and renames a table. That rebuild only exists to repair
databases created before `UNIQUE(project_id, key)`. A PostgreSQL database has no such history.

### A3 — Timestamps (resolved, see D4)

`NewDB` passes `_time_format=sqlite` and #294 exists precisely because timestamp round-tripping
was broken. Columns are declared `DATETIME` (not a PostgreSQL type) and defaulted with
`CURRENT_TIMESTAMP`, which in SQLite returns UTC as a string and in PostgreSQL returns a
`timestamptz` in the session zone. `repairNumericZoneTimestamps` and `timestamprepair.go` are
SQLite-specific repairs. This is the single most likely source of silent wrong behaviour.

### A4 — Booleans (resolved, see D5)

24 columns are `INTEGER NOT NULL DEFAULT 0/1` and scanned into Go `bool` via the SQLite driver's
implicit conversion. PostgreSQL will not scan an `integer` into a `*bool`.

### A5 — Placeholders (resolved, see D6)

Every one of the 342 queries uses `?`. `pgx`/`lib/pq` require `$1..$n`.

### A6 — The encryption key location (dependency, see C1)

`NewDB` calls `secrets.ServerKey(filepath.Dir(dbPath))`, i.e. it derives the key file's location
**from the database file path**. In PostgreSQL mode there is no database file and no directory.

### A7 — Background loops and multiple instances (open, see Q3)

`NewDB` starts `go db.startQueueWorker()` and `main.go` calls `database.StartAutoSync()`.
Both assume exactly one process owns the database. `ProjectLimiter` is an in-process mutex.
Moving to PostgreSQL is normally motivated by running more than one server against one database
— at which point every queued skill job runs twice and the sync loop fights itself.

## Critical dependencies

- **C1 — `secrets.ServerKey`**: must stop deriving its directory from `dbPath`. In PostgreSQL
  mode the resolution has to be `SECTILE_SECRET_KEY` (already supported) then `appDataDir()`.
  Without this, PostgreSQL mode cannot read or write any sealed tracker credential.
- **C2 — `CGO_ENABLED=0`**: the Dockerfile and the release jobs build without cgo. The chosen
  PostgreSQL driver must be pure Go. `pgx` and `lib/pq` both are; this constraint is satisfiable
  but it removes any driver that wraps libpq.
- **C3 — CI**: the test jobs have no database service. Running the suite against PostgreSQL
  requires a `services: [postgres:16]` block in `.gitlab-ci.yml` and a way for ~80 `NewDB` call
  sites to reach it. See Q2 — this is the bulk of the effort, not the driver work.
- **C4 — `resolveDBPath`**: `cmd/server/main.go` probes the filesystem for `tasks.db` before
  calling `NewDB`. It must not run at all in PostgreSQL mode, and the startup log line that
  reports `dbOrigin` has to say something meaningful instead.
- **No third-party or migration dependency beyond these.** No external service, no data
  migration required by the ticket as written (but see Q1).

## Resolved technical decisions (reversible, settled here)

- **D1 — A dialect layer below `*DB`, not a repository interface above it.** `*DB` stays one
  type with its 210 methods and its 342 queries. A new unexported `dialect` interface inside
  `internal/db` carries what differs: `Rebind(string) string`, the DDL type names
  (`textType`, `boolType`, `timestampType`), `UpsertClause`, `HasTable`/`HasColumn`, and
  `Open(dsn) (*sql.DB, error)`. Rationale: the ticket asks for a *thin* interface; duplicating
  20 000 lines is the opposite, and there is no second consumer that would justify it. The
  package boundary already isolates SQL from the rest of the application.
- **D2 — Driver: `github.com/jackc/pgx/v5/stdlib`.** Pure Go (satisfies C2), maintained, and it
  plugs into `database/sql` so `d.conn *sql.DB` is unchanged. Note for the spec: pgx's default
  extended protocol rejects multi-statement `Exec`, which `migrateTasksKeyUnique` relies on —
  a further reason D3 keeps that migration SQLite-only.
- **D3 — A PostgreSQL database is created at the current schema, with no historical replay.**
  `initSchema` and the other `CREATE TABLE ... IF NOT EXISTS` blocks run; the ~40 additive
  `ALTER TABLE` statements and `migrateTasksKeyUnique` are gated behind the dialect and are
  no-ops on PostgreSQL, because the tables they patch are created complete. `timestamprepair.go`
  (`pragma_table_info`) and the `epics` check in `macros.go` (`sqlite_master`) are likewise
  SQLite-only repairs and stay gated.
- **D4 — Timestamps: `TIMESTAMPTZ` on PostgreSQL, `CURRENT_TIMESTAMP` kept, everything stored
  and read in UTC.** The dialect maps `DATETIME` → `TIMESTAMPTZ` and the DSN sets `TimeZone=UTC`,
  so `CURRENT_TIMESTAMP` matches SQLite's UTC semantics and Go receives a real `time.Time`
  instead of a formatted string. The `_time_format=sqlite` workaround stays on the SQLite path
  only.
- **D5 — Booleans stay `INTEGER` on both engines.** The dialect maps the boolean column type to
  `INTEGER` on PostgreSQL too. This keeps the 24 columns and every `Scan`/`Exec` site byte-identical
  rather than auditing 24 columns' worth of Go code for a cosmetic gain. Reversible later.
- **D6 — A `Rebind` at the dialect boundary, not 342 hand-edited queries.** Queries keep `?`;
  a small rewriter converts to `$n` for PostgreSQL. It is applied in wrappers
  (`d.exec`, `d.query`, `d.queryRow`) that the existing call sites are mechanically switched to,
  which is a rename, not a rewrite. The rewriter must be literal-aware (it cannot naively count
  `?` inside quoted strings) and gets its own unit tests.
- **D7 — Environment variables.** `DB_DRIVER` (`sqlite` default, `postgres`) selects the engine;
  `DATABASE_URL` carries the PostgreSQL DSN; `DB_PATH` keeps its exact current meaning and is
  ignored when `DB_DRIVER=postgres`. Rationale: `DB_PATH` is documented in `.env.sample` and
  baked into the Dockerfile, so it must not change meaning; `DATABASE_URL` is the conventional
  name and avoids inventing six `PG_*` variables. Mis-set combinations fail fast at startup
  with an explicit message rather than silently falling back to SQLite.
- **D8 — `NewDB(dbPath string)` becomes `NewDB(cfg Config)`** with a `NewDB(path)`-shaped helper
  kept for the ~80 test call sites, so this ticket does not touch 38 test files.

## Open product questions

These change the acceptance criteria and I will not decide them alone.

1. **Is migrating an existing SQLite database to PostgreSQL in scope?**
   The ticket says "support PG SQL alternative", which I read as: a fresh deployment can choose
   PostgreSQL. It does not say an existing user can move their data across.
   *My recommendation: out of scope for #296.* A one-shot `sectile-server --migrate` export/import
   is a separate ticket, because it needs a row-level copier for 21 tables plus an identity/
   credential re-encryption pass. Confirm, and if you disagree, the acceptance criteria grow
   substantially.

2. **How far must the PostgreSQL path be tested in CI?**
   Three levels, very different costs:
   (a) unit tests for the dialect (`Rebind`, DDL mapping) only, PostgreSQL never actually started;
   (b) (a) plus a `postgres:16` CI service running a **smoke subset** — schema creation, a
   task CRUD round-trip, one upsert, one timestamp round-trip;
   (c) the **entire** `internal/db` + `internal/handlers` suite run twice, once per engine.
   *My recommendation: (b) for this ticket*, with (c) noted as a follow-up. (c) requires per-test
   database isolation for ~80 `NewDB` call sites — that is a bigger piece of work than the feature.

3. **Is PostgreSQL meant to allow several `sectile-server` instances against one database?**
   This is the question that decides whether #296 is a two-day change or a two-week one. If yes,
   `startQueueWorker`, `StartAutoSync` and `ProjectLimiter` all need a distributed story
   (advisory locks or a leader election) or every queued skill job runs once per instance.
   *My recommendation: no for this ticket* — PostgreSQL as an **external, operator-managed store
   for a single server instance** (the real motivation being backup, HA storage and ops tooling,
   not horizontal scaling). If you want multi-instance, say so now and it becomes its own ticket
   with a hard constraint on the queue design.

4. **In PostgreSQL mode, where does the server encryption key live?** (see C1)
   *My recommendation:* `SECTILE_SECRET_KEY` env var first — already supported — then a key file
   in `appDataDir()`. Confirm that requiring operators to supply the key by environment in a
   containerised PostgreSQL deployment is acceptable; it is the only option that survives a
   stateless container with no volume.

## Exit condition

**Not met.** Four product questions above remain open. The stage stays `new`; no transition to
`clarified` is recorded by this round.

## Round 2 - answers from the owner (2026-09-21)

Three of the four questions are settled. The fourth was not understood as asked and is
re-formulated below.

### Settled — Q1: data migration IS in scope (reverses my Round 1 recommendation)

**Assumption reversed.** Round 1 recommended keeping the SQLite → PostgreSQL data migration out
of #296. The owner decided it is in scope. #296 therefore delivers both the dual-engine support
*and* a way to move an existing SQLite database into PostgreSQL.

Consequences to carry into the specification:

- The 21 tables must be copied in foreign-key order, not alphabetically.
- **Sealed credentials do not need re-encryption.** `secrets.Seal(key, Binding{UserID, Tracker},
  token)` binds the ciphertext to the user and the tracker, never to the database or its path.
  A plain row copy therefore survives the move — *provided the same server key is present on the
  PostgreSQL side*. This is what makes Q4 load-bearing rather than cosmetic.
- The migration is one-way (SQLite → PostgreSQL). The reverse direction is not requested and is
  not implied.
- Open sub-question for the specification, not a product question: whether the migration is a
  `sectile-server` subcommand, a separate binary, or an automatic first-start import when the
  target PostgreSQL schema is empty. All three are reversible; the specification stage decides.

### Settled — Q2: PostgreSQL service in CI plus a smoke subset

`.gitlab-ci.yml` gains a `postgres:16` service. The smoke subset covers: schema creation from
empty, one task CRUD round-trip, one `ON CONFLICT` upsert, one timestamp round-trip (the #294
regression, re-run against PostgreSQL), and — added by Q1 — one migration round-trip from a
seeded SQLite file. Running the full `internal/db` + `internal/handlers` suite against both
engines stays a noted follow-up, because per-test database isolation for ~80 `NewDB` call sites
across 38 files is larger than this feature.

### Settled — Q3: single server instance

PostgreSQL is an **external, operator-managed store for one `sectile-server` instance**. Backup,
HA storage and ops tooling are the motivation; horizontal scaling is not. `startQueueWorker`,
`StartAutoSync` and `ProjectLimiter` keep their in-process design unchanged, and no advisory
lock or leader election enters this ticket. A future multi-instance deployment is a separate
ticket with its own constraint on the queue.

### Still open — Q4: where the server encryption key lives

The owner asked what this key is. Answer, for the record:

Sectile lets a user store a personal tracker token (a GitHub PAT, a Jira token). Those tokens are
never written to the database in clear. `NewDB` loads a 32-byte AES key — `secrets.ServerKey` —
and `internal/db/usercredentials.go` uses it to seal each token before insert and to open it on
read. Today that key is resolved in two steps: the `SECTILE_SECRET_KEY` environment variable if
set, otherwise a `secret.key` file **placed next to the database file**, generated on first start
if absent. That second step is what breaks: `NewDB` computes the directory with
`filepath.Dir(dbPath)`, and in PostgreSQL mode there is no database file and no directory to
derive.

If the key is lost or differs, every stored personal tracker token becomes unreadable and each
user must re-enter theirs. With Q1 now in scope, the same key must also be present on the
PostgreSQL side for the migrated rows to open at all.

The question is therefore what the fallback becomes in PostgreSQL mode. It is re-asked with that
context.

### Round 2 exit condition

**Not met.** One product question (Q4) remains open. The stage stays `new`.
