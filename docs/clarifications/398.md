# Clarification - #398 - Recreate Gitlab tracker support

Stage: new → clarified.

Ticket: https://github.com/sebastienferry/sectile/issues/398. Title only, no
description, no comments. Parent macro: M-8 "Core features".

## Restated request and scope

Register a `gitlab` adapter in `internal/tracker.Registry` that implements
`tracker.TicketingSystem` against the GitLab REST API v4, so a project whose
`issueTracker` is `gitlab` can be synchronised, read, created, updated,
commented and closed from Sectile the way a GitHub or Jira project is today,
and expose GitLab again as a choice in the project and personal tracker
screens. "Recreate" refers to the GitLab tracker Taskativ, the predecessor
project, had; Sectile itself never carried one (no GitLab adapter appears in
its history).

Out of scope: merge-request stage evidence (already delivered by #364 through
the local agent), the CI mirror on GitLab (`.gitlab-ci.yml`), a GitLab-specific
Markdown converter (GitLab speaks GFM natively), and any change to the GitHub
or Jira adapters.

## What the code does today (files read)

- `internal/tracker/ticketing.go`, `tracker.go`, `sprints.go`, `registry.go` -
  the `TicketingSystem` interface (CRUD, sync, comments, boards, sprints,
  statuses, issue types, epics, teams, required create fields), the optional
  `PullRequestDiscoverer`, `SprintManager` and `Writer` interfaces, and the
  capability list (`create` … `incremental_sync`, `sprint_manage`).
- `internal/trackerapi/adapters.go` - `NewDefaultRegistry` registers `github`,
  `jira` and `local` only. The GitHub adapter is the smallest complete one:
  CRUD, sync, incremental sync, comments, labels, assign, PR discovery, with
  `forProject` resolving the acting user's token or the server credential
  (#464).
- `internal/trackerapi/mapping.go`, `github.go` - GitHub carries the stage as a
  `#<stage>` label (`#new`, `#clarified`, …), closes the issue at `finished`,
  reads the macro from `macro:` / `parent:` labels, the sprint from a milestone
  whose title starts with `sprint` or `s-`, and the incremental window through
  `since`.
- `internal/trackerapi/jira*.go` - the full-parity adapter (#180): boards,
  columns, sprints read and write, teams, epics, required create fields.
- `internal/trackerapi/client.go` - GitLab plumbing already exists and is
  unused by any adapter: `SECTILE_GITLAB_TOKEN`, `SECTILE_GITLAB_API_URL`
  (default `https://gitlab.com/api/v4`), `SECTILE_GITLAB_PROJECT`,
  `GitlabURL/GitlabProject/GitlabToken` resolution, the personal-token
  override, and `CheckGitlab` (Bearer on `/user`).
- `internal/db/servercredentials.go`, `trackercredentials.go` - `gitlab` is a
  server-credential provider and a personal-credential provider; project
  overrides for `gitlabUrl` / `gitlabProject` resolve on top of the settings.
- `internal/models/models.go` - `GitlabUrl` / `GitlabProject` on settings,
  project and project patch.
- `web/src/lib/trackers.ts` - GitLab is described but filtered out:
  `PROJECT_TRACKERS` lists `local`, `github`, `jira`; `PERSONAL_TRACKERS`
  drops GitLab because it "has no registered adapter".
- `web/src/components/ServerTrackerCredentialsPanel.tsx`,
  `web/src/lib/serverCredentials.ts` - the admin can already store a GitLab
  server token.
- `internal/runner/mergerequest.go`, `internal/agent/agent_operations.go` -
  GitLab merge requests are recognised as stage evidence (#364).
- `docs/clarifications/180.md`, `docs/adrs/0013-labels-carry-the-stage-on-jira.md`,
  `0017-pull-requests-are-rediscovered-on-sync.md`,
  `0028-tracker-sync-uses-a-server-credential-per-provider.md` - the precedent
  for reinstating a tracker and the conventions it settled.
- Reference implementation, Taskativ (`~/Sources/apps/taskativ`):
  `internal/runner/gitlab_rest.go` (issues, incremental read, notes, milestones,
  boards and lists, create/update/delete, error text), `gitlab_graphql.go`
  (iterations and cadences), `gitlab_epics.go` (group epics, parent, members,
  milestone writes), `internal/tracker/gitlab.go` and `gitlab_writer.go`
  (scoped `workflow::<stage>` labels as the stage, `team::` labels as the team,
  milestone vs iteration disambiguation on sprint writes),
  `internal/tracker/issuetypes.go` (creatable types `issue`, `incident`,
  `task`, `test_case`).

## Ambiguities, worst first

1. **Feature parity.** GitHub parity (issues, comments, labels, assignee,
   incremental sync, MR discovery, milestone read as sprint) and Jira parity
   (plus boards and columns, sprint writes, epics, teams, issue types) are two
   adapters of very different size and test surface. → product question 1.
2. **How the stage is written.** Plain `#<stage>` labels, as on GitHub and
   Jira, or GitLab scoped labels `workflow::<stage>`, as in Taskativ. Both read
   back; they differ in exclusivity, in what an existing GitLab board shows and
   in the mapping code shared with GitHub. → product question 2.
3. **What a macro is on GitLab.** `macro:` / `parent:` labels like GitHub, or
   GitLab group epics (Premium tier, group-level, a different API surface). →
   product question 3.
4. **Sprint source.** Project milestones (REST, every tier) or group
   iterations (GraphQL, Premium). Taskativ read both and only wrote
   milestones. Settled with question 1: milestones only unless full parity is
   chosen.

## Critical dependencies

- **GitLab tier.** Epics, iterations, scoped-label exclusivity and issue
  weights require Premium. A feature relying on them fails on a Free instance
  and must degrade (declared unsupported) rather than error the sync.
- **Self-managed instances.** The API URL is already configurable per settings
  and per project; the adapter must not assume `gitlab.com`.
- **Server credential (#464, ADR 0028).** The synchronisation runs with the
  admin-set GitLab server token; the adapter reuses `ForActingUser` exactly as
  GitHub does.
- **Project identity.** The GitLab project is a path (`group/sub/project`) or a
  numeric id, URL-encoded in every call. It comes from the `gitlabProject`
  override, else from the settings default.
- **Key collisions.** GitLab issue keys (`#12`) look like GitHub's. Task ids
  must be namespaced (`gl-<project>-<iid>`), as `FormatTaskID` does for GitHub.
- **No schema migration** is expected: every GitLab column already exists.

## Decisions (reversible, taken from the code and conventions)

1. Adapter lives in `internal/trackerapi` (`gitlab.go`, `gitlab_mapping.go`,
   tests), on the shared `Client` (redirect and size guards, per-project and
   per-user credentials), and is a **port** of Taskativ's REST client, not a
   rewrite. Bearer personal access token, scope `api`.
2. Finishing a task closes the issue (`state_event=close`); leaving `finished`
   reopens it. Import treats a closed issue as finished, label or not.
3. Incremental sync through `updated_after`, pagination through
   `X-Next-Page` / `Link`, same window semantics as GitHub.
4. Comments are notes; system notes are filtered out on read.
5. PR discovery (`CapPullRequests`) through
   `GET /projects/:id/issues/:iid/related_merge_requests`, so ADR 0017's
   rediscovery on sync works for GitLab projects.
6. Priority follows the GitHub adapter's handling (labels, default medium);
   no GitLab weight mapping.
7. `ListIssueTypes` returns the creatable work item types (`issue`,
   `incident`, `task`, `test_case`), lowercase with underscores as GitLab
   expects.
8. UI: GitLab added to `PROJECT_TRACKERS`, the `hasAdapter` filter lifted for
   personal credentials; the user-visible strings stay in French.
9. Documentation: README tracker section, `docs/CAPABILITIES.md`,
   `docs/API_AND_DATA_SPEC.md`, `docs/ARCHITECTURE.md`; a `CHANGELOG.md` line
   under `Added`; an ADR if the stage-label convention differs from GitHub's.

## Questions, with the recommended option

1. **Parity level of this ticket?** Recommended: GitHub parity plus
   milestone-as-sprint read (decisions above), boards / sprint writes / epics /
   teams / iterations left to a follow-up ticket. Alternative: full Jira parity
   by porting all of Taskativ, including GraphQL iterations and group epics.
2. **Stage label format?** Recommended: `#<stage>`, identical to GitHub and
   Jira, so the mapping code and every tracker read the same labels.
   Alternative: scoped `workflow::<stage>` (Taskativ), GitLab-native
   exclusivity on Premium, but a second convention to maintain.
3. **Macro on GitLab?** Recommended: `macro:` / `parent:` labels, as on
   GitHub, working on every tier. Alternative: group epics (Premium only).

## Settled scope and assumptions (pending the answers above)

- One `gitlab` adapter registered in `NewDefaultRegistry`, embedding
  `BaseTicketingSystem`; everything not chosen is `ErrUnsupported`.
- `httptest`-backed tests: sync pagination and incremental window, create,
  update with label merge, close and reopen, notes round trip, MR discovery,
  credential resolution (server vs personal token), registry resolving a task
  whose `Source` is `gitlab`, and a self-managed base URL.
- No production code is written at this stage.

## Round 2 - answers from the owner (2026-09-25)

1. **Parity level**: **full Jira parity**. The recommended GitHub-parity scope
   is reversed: boards and columns, sprint reads and writes over milestones
   and iterations, teams, issue types and statuses come into this ticket, as a
   port of Taskativ's GitLab client.
2. **Stage label**: `#<stage>`, as recommended. Scoped `workflow::` labels are
   not used; the GitHub mapping of stage labels is shared.
3. **Macro**: `macro:` / `parent:` labels, as recommended, on every tier.

### What this reopens, and how it is settled

1. **Sprints come in two kinds.** Project milestones (REST, every tier) and
   group iterations (GraphQL, Premium). → Both are listed as sprints; a sprint
   id carries its kind (`milestone:<id>` / `iteration:<gid>`) so `SetSprint`
   never guesses, instead of Taskativ's "look it up among milestones first".
   `CreateSprint` / `UpdateSprint` / `DeleteSprint` (`CapSprintManage`) work on
   milestones and on iterations of a manual cadence; an automatic cadence is
   refused with a clear error.
2. **Premium-only features on a Free instance.** → Probed once per client
   (GraphQL `iterationCadences` answering, epics endpoint answering 403/404);
   what is absent is omitted from the lists rather than failing the sync, and
   a write that needs it returns `ErrUnsupported`.
3. **Boards are label lists.** A GitLab board column is a label (or the
   implicit Open / Closed lists). → `ListBoards` / `ListBoardColumns` import
   project boards and their lists; a column drag (`TargetStatus`) swaps the
   source list label for the target one, and the Closed list closes the issue.
   The `#<stage>` label is untouched by a drag, as on Jira (ADR 0013).
4. **Statuses.** GitLab has only `opened` / `closed`. → `ListStatuses` returns
   those two plus the board list labels, so the project's column mapping has
   something to map.
5. **Epics versus macros.** Answer 3 keeps the Sectile parent on labels, which
   leaves open whether GitLab group epics are read or written at all. →
   product question 4.
6. **Teams.** GitLab has no team field. → product question 5.

### Open questions (round 2)

4. **GitLab group epics?** Recommended: not used; `macro:` / `parent:` labels
   are the only parent, `CapEpic` not declared, `ListEpics` unsupported.
   Alternative: `ListEpics` reads group epics for the roadmap and `SetParent`
   attaches the issue to one, alongside the labels.
5. **Team on GitLab?** Recommended: a `team::<name>` scoped label (Taskativ's
   convention), `SearchTeams` listing those labels, `TeamMembers` from
   project members. Alternative: no team on GitLab (`CapTeam` not declared).

## Round 3 - answers from the owner (2026-09-25)

4. **Group epics**: not used, as recommended. `macro:` / `parent:` labels are
   the only parent; `CapEpic` is not declared and `ListEpics` stays
   `ErrUnsupported`. Taskativ's `gitlab_epics.go` epic calls are not ported
   (its member and milestone calls are).
5. **Team**: a `team::<name>` scoped label, as recommended. `SetTeam` swaps
   the `team::` label, `SearchTeams` lists the project's `team::` labels,
   `TeamMembers` reads the project members. This is the only scoped label the
   adapter writes; the stage stays `#<stage>`.

## Settled scope (final)

- **Adapter**: `gitlab` registered in `NewDefaultRegistry`, in
  `internal/trackerapi` on the shared `Client`, ported from Taskativ's
  `gitlab_rest.go`, `gitlab_graphql.go`, the milestone and member parts of
  `gitlab_epics.go`, and `internal/tracker/gitlab_writer.go`. REST v4 plus
  GraphQL for iterations, Bearer PAT, gitlab.com and self-managed.
- **Capabilities**: `create`, `get`, `update`, `delete`, `sync`,
  `incremental_sync`, `comment`, `labels`, `assign`, `transition` (close /
  reopen and board-list moves), `sprint`, `sprint_manage`, `team`, `board`,
  `pull_requests`. Not declared: `epic`.
- **Stage and parent**: `#<stage>` labels and `macro:` / `parent:` labels,
  sharing the GitHub mapping; closed issue ⇒ finished; finishing closes,
  leaving finished reopens.
- **Sprints**: milestones and iterations, kind carried in the sprint id,
  Premium features probed and degraded on Free.
- **Boards**: project boards and their label lists as columns; a drag swaps
  the list label, the Closed list closes.
- **Other reads**: `ListStatuses` (`opened`, `closed`, list labels),
  `ListIssueTypes` (`issue`, `incident`, `task`, `test_case`),
  `RequiredCreateFields` returns none. MR discovery through
  `related_merge_requests`.
- **Credentials**: server token for the sync, acting user's personal token
  otherwise, as GitHub (#464, ADR 0028); project from `gitlabProject`
  override, else settings.
- **UI**: GitLab back in `PROJECT_TRACKERS` and personal trackers; French UI
  strings.
- **Docs**: README, `docs/CAPABILITIES.md`, `docs/API_AND_DATA_SPEC.md`,
  `docs/ARCHITECTURE.md`, `CHANGELOG.md` (`Added`), and an ADR recording the
  GitLab mapping (labels for stage/parent, scoped label for team, board lists
  as columns, two sprint kinds).
- **Tests**: `httptest`-backed adapter tests for each capability above,
  including the Free-tier degradation and a self-managed base URL.
- **Out of scope**: group epics, GitLab weights, the CI mirror, merge-request
  stage evidence (#364), changes to the GitHub and Jira adapters.
- No production code is written at this stage.
