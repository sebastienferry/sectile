# Clarification - #251 - Register a GitLab tracker adapter, or drop GitLab from the settings

Stage: new → clarified.

Ticket: https://github.com/sebastienferry/sectile/issues/251. No comments at
round 1. Parent type: macro.

## Round 1 (2026-09-23)

### Restated request and scope

GitLab is half-configured: its connection parameters (site, project, token)
can be stored at server, project and personal level, checked against the
instance and read from `SECTILE_GITLAB_*`, but `trackerapi.NewDefaultRegistry`
registers no `gitlab` adapter, so no project can use GitLab Issues and a GitLab
token has no execution path. The ticket asks to pick one honest outcome: write
a GitLab Issues adapter and expose GitLab in `PERSONAL_TRACKERS` and
`PROJECT_TRACKERS`, or remove every GitLab *tracker* setting so nothing
promises a tracker that does not exist.

Out of scope, whichever outcome is chosen: GitLab as a **forge** — merge-request
discovery and evidence through `glab` (`internal/runner/mergerequest.go`,
`internal/runner/adjustment.go`), the "GitLab MR" badges on task cards
(`ListView.tsx`, `TaskCard.tsx`), `prUrl` handling, and the GitLab CI
pipeline / mirror (`.gitlab-ci.yml`, README "Container image and GitLab CI").
These do not use the tracker settings and keep working.

### What the code does today (files read)

- `internal/trackerapi/adapters.go` - `NewDefaultRegistry` registers `github`,
  `jira`, `local`. No GitLab adapter anywhere in the package.
- `internal/trackerapi/client.go` - `Credentials` and `Client` carry
  `GitlabURL/GitlabProject/GitlabToken`; `NewClient` reads
  `SECTILE_GITLAB_API_URL`, `SECTILE_GITLAB_PROJECT`,
  `SECTILE_GITLAB_TOKEN`/`GITLAB_TOKEN`; `For` and `ForActingUser` substitute
  them; `CheckGitlab` authenticates on `/user`.
- `internal/db/db.go` - `gitlab_url`, `gitlab_project`, `gitlab_token` columns on
  both `settings` and `projects` (create statements + additive `ALTER TABLE`
  migration at ~L855), read/write in settings and project CRUD,
  `trackerDisplayName("gitlab")`, `firstNonEmpty(..., proj.GitlabProject)`.
- `internal/db/trackercredentials.go` - resolution project → settings →
  environment includes GitLab; `CheckTrackerCredentials` / `SaveTrackerCredentials`
  have a `gitlab` case; redaction sets `GitlabTokenSet` / `GitlabTokenFromEnv`.
- `internal/db/usercredentials.go` - `user_tracker_credentials` keyed by
  `(user_id, tracker)`; nothing prevents a `gitlab` row.
- `internal/handlers/handlers.go` (`HandleTrackerSetup`) - checks and saves
  `gitlab` like `github` and `jira`. `internal/handlers/authz.go` - GitLab
  fields are in the admin-only settings allow-list.
- `internal/models/models.go` - GitLab fields on `Settings`, `Project`,
  `ProjectUpdate`, `TrackerSettings`.
- `web/src/lib/trackers.ts` - `TRACKER_CONFIGS` lists GitLab with
  `hasAdapter: false`; `personalTrackers()` filters it out (Profile > Trackers,
  done in #180); `PROJECT_TRACKERS` has no GitLab; `storedFor` has a GitLab case.
- `web/src/components/TrackerSetup.tsx` - the first-start setup dialog uses
  `getTrackers(t)`, **not** the filtered list: GitLab is still offered there,
  checked and saved to the server settings. This is the remaining visible
  half-configuration the ticket does not mention.
- `web/src/types/index.ts`, `web/src/locales/translations.ts` - GitLab fields and
  labels (fr/en).
- `README.md` (L112, L233-L240, L288-L304), `docs/API_AND_DATA_SPEC.md` -
  document the GitLab settings and variables, and say no adapter exists.
- Neighbouring precedent: `docs/clarifications/180.md` (#180 removed the `acli`
  Jira remnants and wrote the HTTP Jira adapter; the GitLab adapter was
  explicitly out of scope there). `internal/trackerapi/github.go` (459 lines)
  plus `jira*.go` (~2.5k lines) give the size of an adapter.

### Ambiguities (worst first)

1. **Which outcome.** Adapter vs removal lead to entirely different changes
   (a new ~500+ line adapter with tests, or a cross-cutting deletion). This is
   the product decision; see Q1.
2. **If removal: what happens to stored data.** Existing rows may hold a GitLab
   token in `settings`, `projects` or `user_tracker_credentials`. Dropping the
   columns vs leaving them inert vs blanking them changes the migration code.
   See Q2.
3. **If adapter: capability level.** GitHub declares create/update/delete/sync/
   get/comment/labels/assign/pull-requests/incremental-sync. A GitLab adapter
   could match all of it, or ship a smaller set (sync + get + comment + labels)
   first. See Q3.
4. **If adapter: GitLab Issues semantics.** Close/reopen via `state_event`,
   labels as workflow stages (same as GitHub), `iid` vs global `id` for task
   keys (`gl-<projectId>-<iid>` following the `gh-...` pattern), self-managed
   instances through `GitlabURL`. Technical, resolved below by mirroring the
   GitHub adapter.

### Critical dependencies

- **Removal**: a schema change on `settings` and `projects`. The project
  supports two databases (#296, dual DB); SQLite `DROP COLUMN` needs 3.35+, and
  `migrate.go` copies `user_tracker_credentials` between stores. Leaving the
  columns in place avoids both risks.
- **Removal**: the setup endpoint accepting `tracker: "gitlab"` is a public API
  change (`POST /api/setup/tracker[/check]`); older clients would get a
  refusal instead of a save.
- **Adapter**: a GitLab instance and token for manual verification; GitLab API
  rate limits and pagination (`X-Next-Page`) for sync; incremental sync via
  `updated_after`.
- Either way: `web/src/types/index.ts` `TrackerCredentials['tracker']` type and
  translations fr/en must stay in sync.

### Reversible technical choices (resolved from conventions)

- If removal, the forge side (glab MR discovery, MR badges, CI) is kept intact;
  only tracker configuration goes.
- If removal, `TrackerSetup.tsx` is fixed by removing GitLab from
  `TRACKER_CONFIGS` itself, so `hasAdapter` and `personalTrackers()` lose their
  reason to exist and the three screens share one list again (same rationale as
  the `PROJECT_TRACKERS` comment).
- If removal, `HandleTrackerSetup` answers 400 "unsupported tracker" for
  `gitlab` rather than silently falling through to "return settings".
- If adapter, it mirrors `GithubAdapter`: HTTP only through `Client` (no `glab`
  on the tracker path, as #180 did for Jira), workflow stage as labels, task ID
  `gl-<projectId>-<iid>`, personal-token substitution via the existing
  `ForActingUser` case, tests with an `httptest` server like `adapters_test.go`.
- If adapter, `hasAdapter: false` is removed and GitLab is added to
  `PROJECT_TRACKERS` as "GitLab Issues"; `IssueTracker` gains `'gitlab'`.

### Product questions

**Q1. Which outcome?**
- (a) **Remove the GitLab tracker settings** — *recommended*. The board is on
  GitHub, GitLab here is only the CI mirror, no user asked for GitLab Issues,
  and it closes the misleading half-state now with a bounded change. An adapter
  can be a separate ticket later when there is a real GitLab-Issues project.
- (b) Write the GitLab Issues adapter and expose GitLab in both lists.

**Q2. (if removal) What happens to already-stored GitLab values?**
- (a) **Stop reading and writing them, leave the columns inert** —
  *recommended*: no destructive schema change on two databases; a later
  cleanup can drop them. Existing `gitlab` rows in `user_tracker_credentials`
  are deleted by a one-off migration so no token lingers.
- (b) Drop the columns (`ALTER TABLE ... DROP COLUMN`) and the rows.
- (c) Leave everything stored, only stop exposing it.

**Q3. (if adapter) Capability scope for the first version?**
- (a) Parity with GitHub (create, update, delete, sync, get, comment, labels,
  assign, incremental sync) — *recommended if Q1 = b*.
- (b) Read-mostly first: sync, get, comment, labels; writes in a follow-up.

**Q4. (if adapter) Self-managed GitLab instances?**
- (a) Supported through the existing `GitlabURL` setting — *recommended*, it
  costs nothing beyond what the client already does.
- (b) gitlab.com only.

### Acceptance criteria draft (depends on Q1)

- (Q1 = a) No settings screen, setup dialog, API field, environment variable or
  `Client` field refers to a GitLab *tracker*; `POST /api/setup/tracker` refuses
  `gitlab`; README and `API_AND_DATA_SPEC.md` no longer document it; GitLab MR
  discovery, MR badges and the CI pipeline behave as before; Go and web tests
  pass.
- (Q1 = b) A project can select "GitLab Issues", sync imports its issues,
  stage changes and comments are written back under the personal GitLab token
  when one is set, GitLab appears in Profile > Trackers and in the project
  tracker list.

## Round 2 - answers from the owner (2026-09-23)

### Settled decisions

- **Q1 = (a) remove the GitLab tracker settings.** No GitLab Issues adapter in
  this ticket.
- **Q2 = (a) leave the columns inert.** `gitlab_url`, `gitlab_project`,
  `gitlab_token` stay in the `settings` and `projects` schemas (create
  statements and the additive migration keep them, so fresh and migrated
  databases stay identical on both backends) but no code reads or writes them.
  A one-off, idempotent migration deletes `user_tracker_credentials` rows whose
  `tracker = 'gitlab'`, so no personal GitLab token lingers.
- **Q3 / Q4 dropped**: they only applied to the adapter outcome.

### Settled scope (what the implementation removes)

- `trackerapi.Client` / `Credentials`: `GitlabURL`, `GitlabProject`,
  `GitlabToken`; `DefaultGitlabURL`; the `SECTILE_GITLAB_API_URL`,
  `SECTILE_GITLAB_PROJECT`, `SECTILE_GITLAB_TOKEN` / `GITLAB_TOKEN` reads;
  the `gitlab` cases in `For`, `ForActingUser`; `CheckGitlab`.
- `internal/db`: GitLab fields in settings/project reads, writes, updates and
  credential resolution/redaction; the `gitlab` cases in
  `CheckTrackerCredentials` / `SaveTrackerCredentials`.
- `internal/models`: GitLab fields on `Settings`, `Project`, `ProjectUpdate`,
  `TrackerSettings` (the JSON fields disappear from API responses and are
  ignored on input).
- `internal/handlers`: `HandleTrackerSetup` answers 400 for `gitlab`
  (unsupported tracker); GitLab keys leave the `authz.go` allow-list.
- Web: GitLab leaves `TRACKER_CONFIGS` (fixing the first-start `TrackerSetup`
  dialog, which still offered it); `hasAdapter` / `personalTrackers()` filtering
  become unnecessary and are simplified; `storedFor` loses its GitLab case;
  GitLab fields leave `types/index.ts` and the tracker translations (fr/en).
- Docs: README (env var table, setup text, "no GitLab adapter" note) and
  `docs/API_AND_DATA_SPEC.md` (columns marked as unused/legacy).

### Kept unchanged (reconfirmed)

GitLab as a forge: `glab` merge-request discovery and evidence in
`internal/runner`, the MR badges in `ListView.tsx` / `TaskCard.tsx`, `prUrl`
handling, `.gitlab-ci.yml` and the mirror documentation. Whether
`trackerDisplayName` keeps its `gitlab` case is a technical check at
specification time.

### Reversed assumptions

None; round 1 recommendations were accepted.
