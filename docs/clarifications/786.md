## Round 1 (2026-10-07)

### Restated request and scope

In Sectile Desktop, the control that launches a skill or a discussion on a ticket should always be usable, rather than disabled whenever no next workflow step can be computed. It should also show the AI engine the launch will use, which is the default engine, and let the user pick another one from that control.
Proposed out of scope: the web app (`web/src/components/TaskCard.tsx` has its own launch menu and a per-launch model picker), the engine catalogue and its settings, a per-launch model choice, and the free "Project prompt" console, which already has an engine select.

### Files read and existing behavior

- `desktop/src/main.js` `ticketRow()` (about lines 2949-3065): each ticket row has a primary `Run: <step>` button (`.ticket-run`) and a `…` menu. The menu lists Pickup, every project skill, "Skip to Handoff…" (implemented stage only), "Discussion (no skill)", "Discussion in native terminal" and "Custom instructions…". Menu entries are only disabled when the project has no configured local repository.
- `desktop/src/main.js` `updateTicketRow()` (about lines 3104-3126): `run.disabled=!step.skillId||active||pending`. The title then explains why: no next step, "An execution is active on this task" or "Submitting execution…".
- `desktop/src/workflow.mjs` `nextTaskStep()`: returns no skill for a finished task, for an unmapped stage, for an unconfigured project, or when the project lacks the next skill. Finished tasks are already filtered out of the ticket table.
- `desktop/src/main.js` execution toolbar (`renderNextStep()`, `launchTaskWork()`, about lines 3531-3624): `Next: <step>` button, Pickup, "Launch anyway" after a duplicate refusal, and "Relaunch". The Relaunch dialog lets the user choose the skill, instructions and execution mode, but not the engine.
- `desktop/src/main.js` `renderEngineToggle()` / `switchTaskEngine()` (about lines 3066-3102) and `desktop/src/engines.mjs`: when the agent reports the `task-engines` capability, the ticket table has an Engine column. Clicking it cycles the task through the catalogue, and it is highlighted when the task leaves its project default. The choice is persisted per task by the agent (`/desktop/task-engines`) and applies from the next launch.
- `desktop/src/main.js` `openAgentConsole()` (about lines 3638-3679): the free "Project prompt" console is the only launch with an `AI engine` select today. It defaults to the project default engine.
- `internal/agentconfig/engines.go`: resolution is task engine, then project engine, then workstation default engine, then first catalogue entry. The catalogue and the per-project and per-task choices live in the workstation settings, never on the server.
- `internal/agent/agent_desktop.go` (`/desktop/tasks` POST, about lines 1017-1063): the launch body carries `TaskID`, `SkillID`, `Prompt`, `Mode`, `Force` and `View`, and no engine. The agent resolves the engine from the task.
- `internal/agent/agent_config.go` `LaunchModel()`: a one-off model is ignored when the task left its project default engine.

### Ambiguities, worst first

1. **Which control and what "always available" means.** Today the row's `Run` button is disabled in three cases: (a) no next skill (unmapped stage, or the project lacks the next skill), (b) an execution is active on the task, (c) a launch is being submitted. The `…` menu is already available in all three cases. Readings that lead to different code:
   - the primary button never disables, and falls back to a discussion when there is no next step;
   - it also stays enabled while a run is active, relying on the server's duplicate refusal and "Launch anyway";
   - the request means merging Run and `…` into one split button whose menu half is always enabled.
2. **Is the engine choice one-off or persisted on the task?** The existing Engine column persists a per-task choice that every later launch uses. A picker on the launch control could either set that same per-task engine, or override the engine for this launch only. A one-off override needs a new `engineId` field on the `/desktop/tasks` launch body, and changes in the agent's dispatch and in `LaunchModel()`. A persisted choice reuses `/desktop/task-engines` as it is.
3. **What happens to the Engine column.** With an engine shown on the launch control, the column either stays as a second way to switch, or is removed so that a single control shows and changes the engine.
4. **Which launch points get the engine.** Possible targets: the row control, the toolbar `Next:` button, the Relaunch dialog and the "Custom instructions…" compose row. Each one added is extra UI and extra tests.

### Critical dependencies

- The engine catalogue exists only on agents that report the `task-engines` capability. An older agent must keep today's launch, with no engine picker.
- A one-off engine (reading 2b) changes the desktop to agent launch contract. The desktop and the agent ship together, but the desktop must tolerate an agent that does not know the field yet.
- Conversations exist only for Claude and Codex. Any other engine falls back to the terminal. That fallback is unchanged, but the picker could say so.
- No server, database or migration change is expected: engines are workstation-local.

### Reversible technical choices from conventions

- The default shown is the task's effective engine (`taskEngine()` / `projectDefault`). It uses the same monogram and tooltip helpers (`engineMark`, `engineTooltip`) as the Engine column and the console select.
- The picker is a menu or select listing the catalogue in its configured order, with the project default marked. The choice is reached by keyboard, as the row menu is today: roles, arrow keys and Escape.
- A launch that the agent refuses still surfaces its message in the view status, as `submitTicketLaunch` does today.
- Desktop UI tests (`desktop/tests/*.ui.cjs`) and unit tests (`desktop/tests/*.test.mjs`) cover the new states. The README and CHANGELOG get a user-visible line under `[Unreleased]`.

### Product questions for the owner

1. **What does "always available" cover?** Recommended: the row's primary launch button is enabled as long as the project is configured. When no next workflow skill exists, it launches "Discussion" instead of disabling itself. While an execution is active, it stays enabled and goes through the existing duplicate refusal, with "Launch anyway". Alternatively, should it stay disabled while a run is active, and only stop disabling when there is no next step?
2. **Does a changed engine apply to this launch only, or stick to the task?** Recommended: it sticks to the task, which is the same stored choice as today's Engine column, so the next launches and the toolbar use it too and the change is visible on the row. This reuses `/desktop/task-engines` and needs no launch contract change. Choose one-off if you want the task's stored engine to stay untouched.
3. **Should the Engine column be removed once the launch control shows the engine?** Recommended: yes. The engine moves into the launch control, as a mark on the button and a picker next to it, so a row has one place that shows and changes it. The highlight when the task leaves its project default is kept there.
4. **Which launch points carry the engine?** Recommended: the ticket row control, and the Relaunch dialog as an `AI engine` select defaulting to the task engine, like the Project prompt console. The toolbar `Next:` button only shows the engine in its tooltip, and the web app stays out of scope. Say if the web launch menu must follow in this ticket.
