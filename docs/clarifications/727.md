# Clarification #727 - Desktop Conversation mode error

## Round 1 (2026-10-05)

### Request

In Sectile Desktop's Conversation mode, Claude Code emitted the stream frame
`{"type":"system","subtype":"ui_invalidate","event":"ui.render",...}` and the
chat showed it as a red error block holding the raw JSON line. The fix makes
such frames stay out of the chat, as any other frame Sectile does not read.
Out of scope: rendering `ui_invalidate` (or any other new system frame) as a
message, and changing how genuinely non-JSON stdout lines are shown.

### Root cause

`conversationTurn` (`internal/agent/agent_conversation.go`, the stdout `line`
callback) decodes every line into one struct that declares
`Event conversationStream`, an object, for the `event` field of `stream_event`
frames. In this new `system` frame `event` is a string (`"ui.render"`).
`json.Unmarshal` then returns an `UnmarshalTypeError`, the
`json.Unmarshal(...) == nil && frame.Type != ""` guard fails, and the line
falls through to the last branch, which writes any non-empty unparsed line as
`conversationWrite(run.trace, "error", line, "")`.

The comment on `conversationOutput` already states the intended contract:
"Unknown JSON stays out of the rendered chat". A well-formed frame whose shape
differs from what Sectile expects for one field breaks that contract.

### Files read

- `internal/agent/agent_conversation.go`: `conversationStream`,
  `conversationOutput`, `conversationTurn` frame dispatch.
- `internal/runner/reasoning.go`: `reasoningLine` / `ParseReasoningLine`
  declares no `event` field and ignores unreadable lines, so it is not affected.
- `internal/agent/agent_headless.go:282` and
  `internal/agent/agent_conversation_approvals.go:334`: they decode narrower
  structs and treat a decode failure as "not my frame", so they are not
  affected.

### Ambiguities

None that changes the code: the frame is valid JSON with a known `type`, and
the existing contract says unknown frames are not rendered.

### Dependencies

None. No migration, no API change, no web or desktop change: the bug and its
fix are in the agent's Go stream parser.

### Technical choices settled from the code (reversible)

1. A field whose type differs from the declared one must not discard the whole
   frame. Decode `event` lazily (for example as `json.RawMessage`, decoded into
   `conversationStream` only for `stream_event` frames), so the other fields
   (`type`, `session_id`, `model`, `mcp_servers`...) are still read.
2. Only a line that is not JSON at all keeps the current "error" rendering.
   A JSON line whose decoding fails for another reason is dropped silently,
   like the reasoning parser does, rather than shown raw.
3. `ui_invalidate` gets no dedicated handling: it is a Claude Code UI hint with
   nothing for the conversation view to show.
4. Regression test in `internal/agent/agent_conversation_test.go`: feed the
   frame from the ticket through the conversation output and assert no
   "error" event reaches the trace.
5. Changelog: one `Fixed` line under `[Unreleased]` (user-visible: a spurious
   error block in the conversation view).
