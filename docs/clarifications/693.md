# Clarification #693 - PostgreSQL | Run output is truncated by bytes on a SQL_ASCII database

## Round 1 (2026-10-01)

### Request

A PostgreSQL database whose encoding is not UTF8 makes `LENGTH` and `SUBSTR`
count bytes, so `AppendRemoteRunOutput` keeps half the run output for
non-ASCII text and can cut a multibyte character in two. The fix makes Sectile
detect a non-UTF8 database, both when the server opens its store and when the
PostgreSQL tests open theirs, says so explicitly, and documents that the
database must be UTF8.

Out of scope: making the output cap correct on a SQL_ASCII database (counting
characters in Go, or re-encoding stored data), converting an existing
database, SQLite (always UTF-8), and any change to the dev deployment, whose
database is created by the infrastructure module with the UTF8 default.

### Code read

- `internal/db/remoterun.go:880-900`: the SQL cap, `LENGTH(output) + LENGTH(?) > ? THEN SUBSTR(...)`, whose comment assumes characters "on both engines".
- `internal/db/db.go:201-230`: `Open` / `openWith`, which already turns an unreachable database into a startup failure (`cannot reach the %s database`) right after `Ping`, before the schema migration.
- `internal/db/dialect_postgres.go`: the PostgreSQL dialect; `LowerASCII` already documents a cluster-dependent behaviour (collation) and neutralises it.
- Test helpers reading `SECTILE_TEST_POSTGRES_DSN`: `internal/db/postgres_smoke_test.go` (`postgresDSN`, `openPostgres`), `internal/handlers/postgres_mcp_cluster_test.go` (`openPostgresInstance`), `cmd/server/multireplica_test.go` (`TestPostgresMultiReplicaHarness`, which starts real server binaries).
- `internal/db/postgres_concurrency_test.go`: `TestPostgresConcurrentOutputAppendsTruncateOnce`.
- `.gitlab-ci.yml` `test:postgres`: `postgres:16` service, whose default `initdb` gives a UTF8 database, which is why CI is green.
- `README.md` "PostgreSQL" section and `docs/TESTING.md`: neither states the encoding requirement.

### Ambiguities, worst first

1. **Refuse to start or warn** (product question Q1 below). The two lead to
   different code: a refusal is an error returned by `openWith`, which also
   makes the test helpers fail fast for free; a warning is a log line, leaves
   the truncation wrong in production, and needs a separate check in each test
   helper.
2. **Which encodings are accepted.** Only `UTF8`. `LATIN1` and the other
   single-byte encodings count characters correctly but cannot store most of
   what an agent prints (emoji, CJK), so they are treated like `SQL_ASCII`.
   Settled as a reversible technical choice.
3. **What is checked.** The database encoding, read with `SHOW server_encoding`
   (it reports the current database's encoding), not `client_encoding`, which
   pgx always sets to UTF8 and which says nothing about storage. Settled.

### Critical dependencies

- No migration and no schema change.
- Upgrade risk: an existing deployment on a non-UTF8 database would stop
  starting after the upgrade if the refusal is chosen. The known deployment is
  created by the infrastructure module with the UTF8 default, so it is not
  affected; a self-hosted one could be.
- The behaviour test needs a non-UTF8 database. `CREATE DATABASE ... ENCODING
  'SQL_ASCII' TEMPLATE template0` works inside any UTF8 cluster for a role
  with `CREATEDB` (the CI role is the service superuser), so no second cluster
  is needed.

### Reversible technical choices (settled from the code)

- The check lives in the PostgreSQL dialect and runs in `openWith` right after
  `Ping`, before `migrateSchema`, so nothing is written to a database the
  server is about to refuse. SQLite has nothing to check.
- The decision ("is this encoding acceptable") is a small pure function with a
  unit test that runs everywhere; one PostgreSQL integration test creates a
  throwaway `SQL_ASCII` database with `TEMPLATE template0`, opens it, asserts
  the outcome, and drops it. It skips without `SECTILE_TEST_POSTGRES_DSN`, like
  the other PostgreSQL tests.
- The message names the encoding found, says the database must be UTF8, and
  gives the fix (`CREATE DATABASE <name> ENCODING 'UTF8' TEMPLATE template0`,
  or `initdb --encoding=UTF8`). It is in English, like the neighbouring
  `cannot reach the %s database` error it sits beside.
- The test helpers (`postgresDSN` / `openPostgres`, `openPostgresInstance`)
  get the same check before any test body runs, with a message naming
  `SECTILE_TEST_POSTGRES_DSN`. If the server refuses to start, this is the
  `Open` error surfacing through the existing `t.Fatalf`; the multi-replica
  harness gets a pre-flight check so it fails on the encoding, not on a replica
  that never became ready.
- Docs: the README "PostgreSQL" section and `docs/TESTING.md` state the UTF8
  requirement and how to create such a database; the comment in
  `remoterun.go` that claims characters "on both engines" names the condition.
- `CHANGELOG.md`: one line under `[Unreleased]`, because an operator can see
  the change (a refusal or a warning at startup).

### Product questions

- **Q1. Non-UTF8 database at server start: refuse or warn?**
  Recommended: **refuse to start**, with an explicit error. A warning leaves a
  server running that silently keeps half the output and may store invalid
  UTF-8; `openWith` already treats a misconfigured database as a startup
  failure rather than a degraded service. Alternative: log a warning and start.
- **Q2. Escape hatch.** If Q1 is "refuse", should an environment variable let
  an operator start anyway on a non-UTF8 database? Recommended: **no**; the
  supported fix is to recreate the database as UTF8, and an override would keep
  the corruption reachable.

### Status

Report committed on `feat/693`. Two open product questions for the owner;
no transition until they are answered.
