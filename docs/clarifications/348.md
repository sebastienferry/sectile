## Round 1 — analysis (2026-09-22)

### Restated request and scope

The sidebar account button (and the status bar) keeps displaying `Developer` after the
person has changed their display name in Settings → Account, because those two widgets
read a different field from the one the Account tab writes. This ticket is about making
the name shown in the chrome be the name the person actually set. Out of scope: the
sign-in flow, roles and the admin users view, the avatar image, the `userEmail`
projection (already correct), and the assignee-matching semantics of the "My Tasks"
filter beyond what question 4 decides.

### Verified findings

1. **Two identities exist, and the UI reads the wrong one.** The name in the sidebar
   (`Sidebar.tsx:960`), its initials (`:955`) and the status bar (`StatusBar.tsx:43`) all
   render `settings.userName`. The Account tab does **not** write that field: it renames
   the *account* through `PATCH /api/me` → `SetDisplayName` → `users.chosen_name`
   (`SignInStatus.tsx` `saveName` → `useCurrentUser.rename`). The two never meet, so the
   rename is saved correctly and simply is not what the sidebar displays.

2. **`settings.userName` has no editor left anywhere in the interface.** The only
   reference that writes it is `ProfileModal.tsx:153`, `userName: settings.userName` — a
   pass-through of the value it just read. Grepping `web/src` finds no input bound to it.
   It is therefore frozen at whatever the database seeded, which is the literal
   `'Developer'`: `db.go:319` (column default), `:883`/`:900`/`:932` (seed inserts),
   `:3348` (no-row fallback) and `:3591-3593` (empty-value normalisation), mirrored
   client-side by `AppContext.tsx:368`. The ticket's "Developper" is that string.

3. **`userEmail` already solves exactly this problem, and `userName` was left behind.**
   `composedSettings` (`handlers.go:2643-2646`) overwrites `composed.UserEmail` with the
   account's address, and the write path deletes `userEmail` from the payload
   (`handlers.go:2691`) with the comment *"on a read and ignored on a write"*. ADR 0015
   records this as *"`userEmail` is a projection … the retirement of the free-text
   identity"*. `composedSettings` does **not** do the same for `UserName`, and
   `personalSettingsKeys` (`authz.go:147`) still lists `userName` as writable. The defect
   is that half of the ADR 0015 retirement shipped.

4. **The rest of the application already shows the real identity.** Execution owners go
   through `ownerDisplayName` over `COALESCE(NULLIF(u.chosen_name,''), u.display_name)`
   (`db.go:3200`, `:5027`, `:5138`), so `RemoteRunBadge` shows the correct name on the
   same screen as the wrong one. Local comments prefer `actor.Name` and only fall back to
   `settings.UserName` (`comments.go:155-160`). The sidebar is the outlier.

5. **`user.DisplayName` is already the resolved name.** `userColumns`
   (`identity.go:436`) selects `COALESCE(NULLIF(chosen_name,''), display_name)`, so
   `GetUser(...).DisplayName` — which `composedSettings` can reach, it already calls
   `GetUser` for the e-mail — is the chosen name when there is one and the provider claim
   otherwise. No new query is needed.

6. **A front-end-only fix costs more than the server one.** `AppContext` does not carry
   the current user; `App.tsx:124` is the single `useCurrentUser()` mount. Making
   `Sidebar` and `StatusBar` read `user.displayName` means either two more `/api/me`
   fetches or plumbing the user through the context, against one line in
   `composedSettings`.

7. **Hardcoded placeholders sit next to the bug.** `Sidebar.tsx:955` falls back to the
   initials `'SF'` and `:960` to the literal name `'Sylvain Ferry'` when `userName` is
   empty; `:963` falls back to `'Paramètres & Profil'` for the e-mail. These are a
   maintainer's own name shipped as a default.

### Dependencies and constraints

- No migration is involved. `users.chosen_name` and `user_settings` already exist; the
  `settings.user_name` / `user_settings.user_name` columns stay readable whatever is
  decided, so no upgrade step is at risk.
- ADR 0015 explicitly lists `userName` in the personal, writable half. Making it a
  projection contradicts the record as written and needs the record amended (question 5).
- `personalSettingsKeys` is also the member-authorization list. Removing `userName` from
  it would make a payload that changes it an **admin-only violation** for a member
  (`memberSettingsViolations`), i.e. a 403 rather than a silent ignore — so the
  `userEmail` treatment (`delete(sent, "userName")` *before* the violation check, key
  left in the map) is the only shape that stays compatible with the interface posting the
  whole row.
- `/api/settings` is consumed by the MCP surface too (`mcp_test.go:149` asserts what is
  and is not exposed); a write that starts being ignored is a contract change for any
  agent that sets `userName`.
- The `default` account and the local-agent `ImplicitUser` have no provider claim; their
  `display_name` may be empty, which is what makes question 2's fallback chain real.

### Reversible technical decisions (taken here)

- **Fix on the server, in `composedSettings`**, not in the two components — finding 6.
- **Reuse the existing `GetUser(userID)` call** already made for the e-mail rather than
  adding a query.
- **Keep the database columns.** Nothing is dropped; the value simply stops being read
  for display, which is exactly what was done for `userEmail`.
- **Mirror the `userEmail` code shape verbatim** (projection on read at `handlers.go:2643`,
  `delete(sent, ...)` on write at `:2691`) so the two identity fields stay one pattern,
  and extend `authz_test.go:276-282` with the symmetric assertion.
- **Leave `comments.go`'s fallback alone**; it already prefers the identity.

### Open product questions

1. **Projection or editor?** Either `settings.userName` becomes a read-only projection of
   the account's display name (symmetric with `userEmail`, and the Account tab stays the
   one place to rename), or it stays a free-text field and the Account tab gains a second
   input that writes it.
   *Recommendation: projection. ADR 0015 already retired the free-text identity for the
   e-mail, the Account tab is already the rename UI, and two editable names for one person
   is the bug class this would re-create.*

2. **What shows when the account has no display name?** The resolution chain today stops
   at `COALESCE(chosen_name, display_name)`, which can be empty for `default` or a local
   account.
   *Recommendation: `chosen_name → display_name → email → userId`, and `'Developer'`
   disappears as a displayed value entirely (the column default may stay, it would no
   longer be read).*

3. **Should a write of `userName` be ignored, or still accepted and stored?** Ignoring it
   makes the field unambiguous and matches `userEmail`; accepting it keeps the API
   backward-compatible for any agent that posts it, at the price of a stored value nothing
   displays.
   *Recommendation: ignore it, with the same `delete(sent, "userName")` placement as the
   e-mail so a member's whole-row post is not turned into a 403.*

4. **The "My Tasks" filter.** `Sidebar.tsx:260`/`:631` filters tasks whose `assignee`
   string equals `settings.userName`. Changing what `userName` resolves to changes which
   tasks that button matches — and on a GitHub-tracked project the assignee is a GitHub
   login, which a display name will rarely equal either way.
   *Recommendation: out of scope. Fix the displayed name here; raise the assignee-identity
   matching as its own issue rather than widening this one.*

5. **ADR 0015.** It names `userName` as personal and writable. If question 1 resolves to a
   projection, is the deliverable an amendment to ADR 0015, or a new short ADR superseding
   that one sentence?
   *Recommendation: a short amendment inside ADR 0015 extending the `userEmail` projection
   paragraph to `userName` — it is a completion of that decision, not a reversal.*

6. **The hardcoded placeholders** `'Sylvain Ferry'`, `'SF'` and `'Paramètres & Profil'`
   (`Sidebar.tsx:955`, `:960`, `:963`).
   *Recommendation: remove them in this ticket — they become unreachable once question 2's
   chain is in place, and shipping a maintainer's name as a default is the same defect in
   a second place.*

### Status

Round 1 written. Exit condition **not** met — questions 1-6 are open, owner to answer.
Stage transition new → clarified is blocked.

## Round 2 — answers from the owner (2026-09-22)

The owner accepted every Round 1 recommendation, in those words: *"I agree with all
recommandations."* All six questions are settled and **no prior assumption is reversed** —
Round 1 took no position that the answers contradict.

1. **Projection, not a second editor.** `settings.userName` becomes a read-only
   projection of the signed-in account's display name, symmetric with `userEmail`. The
   Account tab (`SignInStatus`) stays the one and only place a name is changed.
2. **Fallback chain: `chosen_name → display_name → email → userId`.** `'Developer'` stops
   being a displayed value anywhere. The column defaults in `db.go` may stay as they are —
   they are simply no longer read for display.
3. **A write of `userName` is ignored,** exactly as `userEmail` is: `delete(sent, "userName")`
   in `HandleSettings` **before** `memberSettingsViolations` runs. `userName` stays in
   `personalSettingsKeys`; removing it from that map would turn a member's whole-row POST
   into a 403, which is the failure mode this placement exists to avoid.
4. **The "My Tasks" filter is out of scope.** `Sidebar.tsx:260`/`:631` keep comparing
   `task.assignee` to `settings.userName`; whatever that comparison gets right or wrong is
   raised as its own issue, not folded into #348.
5. **ADR 0015 is amended, not superseded.** A short addition extending its
   *"`userEmail` is a projection"* paragraph to `userName`, recorded as a completion of
   that decision rather than a reversal of it.
6. **The hardcoded placeholders go.** `'Sylvain Ferry'` (`Sidebar.tsx:960`), `'SF'`
   (`:955`) and `'Paramètres & Profil'` (`:963`) are removed; the chain of answer 2 makes
   them unreachable.

### Settled contract (what an implementation must satisfy)

**Server — `internal/handlers/handlers.go`**

- In `composedSettings`, inside the existing `if user, err := h.db.GetUser(userID); ...`
  block that already sets `composed.UserEmail`, also set `composed.UserName` from the
  resolved chain. No new query: `User.DisplayName` is already
  `COALESCE(NULLIF(chosen_name,''), display_name)` (`identity.go:436`), so the chain is
  `user.DisplayName → user.Email → userID`, each step taken only when the previous is
  blank after trimming.
- In `HandleSettings`, next to `delete(sent, "userEmail")`, add `delete(sent, "userName")`,
  with the same placement relative to `memberSettingsViolations` and the same explanatory
  comment shape.
- `personalSettingsKeys` (`authz.go:147`) is **unchanged**.

**Client — `web/src/components/`**

- `Sidebar.tsx:955` initials and `:960` name keep reading `settings.userName`; they need no
  change beyond dropping the `'SF'` and `'Sylvain Ferry'` fallbacks, because the server now
  guarantees a non-empty value for a signed-in caller. `:963` drops
  `'Paramètres & Profil'` likewise. `StatusBar.tsx:43` drops its `'Profile'` fallback on
  the same grounds.
- `ProfileModal.tsx:153` (`userName: settings.userName`) may stay — the write is now
  ignored server-side — but removing it is preferred, so the payload stops carrying a
  field nothing reads.
- `AppContext.tsx:368` (`userName: 'Developer'`) becomes an empty string: it is a
  pre-fetch placeholder, and the literal is the string the ticket reports.

**Tests**

- Extend `internal/handlers/authz_test.go` around lines 276-282 with the assertion
  symmetric to the `userEmail` one: a POST setting `userName` to something else answers
  200, and the following GET still answers the account's display name.
- Cover the fallback chain of answer 2 for an account whose `chosen_name` and
  `display_name` are both empty (the `default` account's shape).

**Documentation**

- Amend `docs/adrs/0015-sign-in-is-mandatory-and-settings-are-personal.md`: the
  *"`userEmail` is a projection"* paragraph extends to `userName`, and the personal-half
  list stops presenting `userName` as a field anyone types.

### Settled scope

- **In scope:** the `composedSettings` projection, the `delete(sent, "userName")` write

- **Out of scope:** the "My Tasks" assignee matching, the avatar, the sign-in flow, roles

- **Reported, not fixed:** `Sidebar.tsx:260`/`:631` compare a task assignee, which on a
