# #275 - Autonomous and JSON stream not visible with AGY/CLAUDE

- Type: Bug
- Tracker: https://github.com/sebastienferry/sectile/issues/275
- Branch: feat/275
- Round: 1 (open - awaiting owner answers)

## Restatement

An autonomous (headless) launch driven by the AGY or CLAUDE provider does not show
what the CLI prints: neither the progressive output nor the `stream-json` events
reach the surface where a user watches a run. The ticket is about the visibility
of a headless run's output, not about the run failing to execute.

Out of scope for this ticket: interactive (PTY) runs, provider authentication,
model selection, and any change to the workflow stages themselves.

## Ambiguities (worst first)

1. **Which of the two symptoms is the bug** - the title joins "Autonomous" and
   "JSON stream" with "and". Two readings lead to different code:
   a. the *configuration* is not visible (autonomous command field / preset not
      offered or not applied for AGY and CLAUDE), or
   b. the *run output* is not visible (a headless AGY/CLAUDE run shows nothing,
      or shows raw JSON, in the activity panel).
   Reading (b) is the one the code supports as a real defect; see the hypothesis below.
2. **Which surface** - the web UI activity panel, the desktop application's run
   view, or both. The desktop lists a headless run but has no console for it
   (`agent_headless.go`), so "not visible" may simply be the desktop's expected
   behaviour rather than a bug.
3. **AGY *and* CLAUDE, or AGY *via* CLAUDE** - whether both providers are affected
   independently, or the report describes a single AGY run using a Claude model.
4. **Expected rendering of `stream-json`** - raw NDJSON lines as printed, or parsed
   events rendered as readable progress. This changes whether the fix is plumbing
   or a new renderer.
5. **Live vs. final** - whether the run output is missing during the run only, or
   still missing after the process exits.

## Leading technical hypothesis (to be confirmed by the owner's answers)

Both default autonomous presets buffer everything until exit:

- AGY: `agy ... --output-format stream-json -p "{prompt}" | jq -rs 'map(select(.event == "result"))[0].result.response'`
  `jq -rs` slurps the whole stream before emitting anything, so the 3-second flush
  in `superviseHeadlessRun` has nothing to post until the CLI has finished, and the
  individual `stream-json` events are discarded by the `jq` filter by design.
- Claude: `claude -p --permission-mode bypassPermissions ...` carries no
  `--output-format stream-json`, so it prints a single final answer.

If this is the reported behaviour, the defect is in the presets and in how the
headless channel is expected to consume a JSON event stream, not in the transport
(`postRunOutput` -> `HandleAgentRunOutput` -> `AppendRemoteRunOutput`), which is
already incremental.

## Dependencies

- Provider CLIs are external: the exact `stream-json` event shape for `agy` and for
  `claude` is owned by those tools and must be treated as unstable input.
- `RemoteRunOutputLimit` (256 KiB) caps what one run can record; a raw event stream
  is far more verbose than a final answer and will hit that cap on long runs.
- The tracker's comment API returned HTTP 401 during this run, so the ticket's own
  discussion could not be read. If the owner already answered there, that answer was
  not visible to this round.

## Reversible technical choices, resolved here

- Keep the existing output transport (agent -> `/api/v1/agent/run-output` -> activity
  output) rather than adding a second channel; it already flushes every 3 seconds.
- Keep `web/src/lib/commandTemplate.ts` mirroring `internal/agent/agent_config.go`
  as the file's own doc comment requires; any preset change lands in both.
- Presets stay overridable by environment (`SECTILE_PRESET_*` / `VITE_PRESET_*`),
  so no default is hard-coded past the point of being changed by a user.

## Round 2 - answers from the owner (2026-09-21)

### Settled

1. **The symptom is the run output, not the configuration.** An autonomous AGY/CLAUDE
   run executes, but what it prints never appears. The settings UI is out of scope:
   the autonomous command field and the presets are visible and applied correctly.
2. **Surface: the desktop application.** This matters beyond the presets. A headless
   run is registered with no PTY session (`registerHeadlessRun`, `Headless: true`),
   so the desktop lists it but has no console for it. Fixing the command so it emits
   progress is not sufficient on its own: the desktop must render the run activity's
   accumulated output for a headless run. Both halves are in scope.
3. **Expected display: readable progress while the run is alive**, with the final
   answer still standing out. Not raw NDJSON, and not silence until exit.
4. **Both default presets change.** AGY stops slurping the stream through `jq -rs`,
   and the Claude autonomous preset gains `--output-format stream-json`. Only the
   presets change; a user's custom command is never rewritten.
5. **Both providers are affected**, as independent providers, not one AGY run on a
   Claude model.

### Reversed or narrowed assumptions

- Round 1 treated "only the final answer at the end" as a live option. It is rejected.
- Round 1 left open whether the defect was in the presets or in the transport. The
  transport is sound; the defect is in the command shape *and* in the desktop's
  rendering of a console-less run.
- The owner's no-TTY suspect is narrowed, not dismissed: with `--output-format
  stream-json` the CLIs emit machine-readable events regardless of a terminal, so
  the absence of a TTY stops being the cause of silence. It remains worth a check
  during implementation that neither CLI gates its event stream on a terminal.

### Owner's constraint on the presets

The owner confirmed the extraction must stay: the point of the `jq` in the AGY preset
is to turn the event stream into something a human can read, and that requirement
holds. What is rejected is `-rs`, which slurps the whole stream before emitting
anything. The owner asked for a recommendation on how to satisfy both.

## Open question (Round 2)

1. Where should the JSON event stream be turned into readable text - in the shell
   pipeline (`jq`) or in the Sectile agent (Go)? (owner)

   **Recommendation: in the agent, in Go.** The preset then carries only
   `--output-format stream-json` and no pipeline, and `superviseHeadlessRun` parses
   the NDJSON as it drains the pipe, emitting one readable line per event and the
   final answer verbatim. Reasons:
   - No dependency on `jq` being installed on every workstation that runs an agent.
   - No `--unbuffered` / pipe-buffering trap: the 3-second flush already in place
     posts exactly what has been read so far.
   - An unrecognised event shape can fall back to printing the raw line, so a
     provider changing its schema degrades instead of producing an empty panel.
   - The two providers emit different event schemas; one Go renderer per provider is
     testable, whereas two `jq` programs embedded in preset strings are not.
   - A non-zero exit or a crash mid-stream still shows everything received, where a
     `jq` filter selecting the terminal `result` event shows nothing.

   The alternative - a streaming `jq --unbuffered -r` filter in the preset - keeps
   the rendering user-editable without rebuilding Sectile, which is its one real
   advantage. It is the right answer if the owner wants the rendering to stay
   configurable per workstation.

## Round 3 - answers from the owner (2026-09-21)

### Settled: the rendering stays in the preset, with `jq`

The owner chose `jq` in the command template over a Go renderer in the agent, for
agnosticism. The argument is accepted and reverses the Round 2 recommendation:

- What stays agnostic is the **agent**, not the filter. `superviseHeadlessRun` keeps
  draining bytes and knows nothing about any provider's event schema. Adding a
  fourth CLI is a new preset, with no Go change and no rebuild.
- A Go renderer would have required one provider-specific branch in the agent for
  each CLI, which is exactly the coupling the owner wants to avoid.

Consequence to state plainly: the *filters* cannot be shared. `claude`, `agy` and
`codex` emit different event schemas, so each preset carries its own `jq` program.
The agnosticism is in the mechanism, not in the expression.

### Constraints this choice imposes (settled, not optional)

1. **No `-s` / slurp.** `jq --unbuffered -r` emits per event, as it arrives. `-rs`
   is the defect being fixed and must not reappear in any preset.
2. **Render every event, not only the terminal one.** A filter that selects
   `.event == "result"` prints nothing until the run ends, and prints nothing at all
   if the CLI crashes mid-stream. Each preset renders progress events as readable
   lines and still surfaces the final answer.
3. **Tolerate non-JSON lines.** A CLI writes warnings and diagnostics to the same
   stream (`cmd.Stderr = cmd.Stdout` in `startHeadlessRun`). A filter reading with
   `-R` and falling back to the raw line (`fromjson? // .`) keeps those visible
   instead of aborting the pipeline and blanking the panel.
4. **`jq` becomes a runtime prerequisite of an autonomous run.** Its absence must
   surface as a stated error on the run, not as an empty output panel. Where that
   check lives - preflight in the agent, or documented prerequisite - is a
   specification-stage decision, not a product one.
5. **The desktop must render a headless run's accumulated output.** Independent of
   the pipeline: a headless run has no PTY session by design, so the desktop needs
   to show the activity output rather than an empty console. Without this half, a
   correct pipeline is still invisible on the surface where the bug was reported.

### Reversed assumption

Round 2 recommended parsing the NDJSON in Go. That recommendation is withdrawn; the
owner's agnosticism argument prevails and the rendering stays in the presets.

## Exit condition

All product questions are answered. The scope is settled: fix the three autonomous
presets so they stream readable per-event output, and make the desktop display a
headless run's output. No open question remains.
