# Clarification - GitHub #472

Task: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-472`
URL: https://github.com/sebastienferry/sectile/issues/472
Branch: `feat/472`

## Round 1 (2026-09-25)

### Restated request and scope

Make the MCP tool `create_task` create the work item on Jira for a
Jira-tracked project, with its title, Markdown description (as ADF), issue
type, parent epic, priority and labels, and return the new key and browse URL
exactly as it already does for GitHub. Out of scope: creating a Jira project or
issue type, editing the created issue afterwards (`update_task`), the other MCP
tools' credential handling beyond what the owner settles below, and any change
to the web creation form.

### Verified findings

- The refusal is a single guard in `DB.CreateTaskAs`
  (`internal/db/db.go:2502`): `RequireRemoteCreation` is only accepted for the
  `local` and `github` sources. It dates from `adadaea6` (2026-09-13), before
  the Jira adapter was ported back.
- `JiraAdapter` already declares `CapCreate`, and
  `JiraAdapter.CreateIssue` (`internal/trackerapi/jira.go:197`) already does
  most of what the ticket asks: `MarkdownToADF` for the description, `parent`
  from `ParentKey`, the issue type (defaulting to the project's first type, then
  `Task`), labels, priority through the creation screen (or set afterwards when
  the screen lacks it), mandatory custom fields through `Fields`, and assignment.
- The web form already reaches that adapter: `POST /api/tasks` calls
  `CreateTaskAs` without `RequireRemoteCreation`, so the guard does not apply.
  The desktop quick-create (`internal/agent/agent_desktop.go:991`) sets
  `RequireRemoteCreation` and is therefore blocked on Jira projects too.
- `CreateTaskAs` drops fields on the way to the tracker: it forwards only
  `Title`, `Description`, `Priority` and `Labels` in `tracker.CreateIssueRequest`,
  although the request type carries `IssueType`, `ParentKey`, `Assignee`,
  `Sprint` and `Fields`. So even without the guard, `issueType` and `parentKey`
  from MCP would reach the local row but never Jira.
- `RequireRemoteCreation` is not enforced when the tracker cannot be resolved:
  if `TrackerForProject` errors or the adapter does not support creation, the
  task is silently created on the local board only, which contradicts the
  `create_task` contract ("fails rather than leaving a ticket that exists only
  on the local board").
- MCP `create_task` calls `database.CreateTask`, i.e. `CreateTaskAs` with
  `context.Background()`: no acting user. `JiraAdapter.forProject` then uses the
  project/server credential. The web and desktop paths carry the acting user,
  and `forProject` refuses a user-initiated Jira write without that user's
  personal token (ADR 0014: a Jira write is attributed to the token's account).
  The MCP server can resolve its caller (`callerOf`, already used by
  `prepare_macro_worktree`, runs and comments).
- The "Related" `get_task` failure has the same root: `GetTaskComments` is also
  called without the caller, falls back to the server credential, and the
  server settings on this instance hold no Jira e-mail, hence
  `configure the Jira account e-mail` (`internal/trackerapi/jira_client.go:62`).
- A sealed, not unlocked personal credential already surfaces as
  `ErrCredentialLocked` from `ResolveUser`; it only reaches the caller once the
  call carries the acting user.

### Ambiguities (worst first)

1. Whose Jira account creates the issue from MCP: the caller's personal token
   or the server credential. Different code paths, different attribution, and
   on this instance only one of them works (see dependencies).
2. Whether `get_task` comment reads are fixed in this ticket or separately.
3. Mandatory custom fields: `create_task` has no way to supply them, so a Jira
   project with a required field can never be created into from MCP.
4. Assignee: listed in "Expected", absent from the acceptance criteria and from
   the MCP schema.

### Reversible technical choices (settled from the code)

- Replace the source allow-list with the adapter's own capability: under
  `RequireRemoteCreation`, creation proceeds when the project's tracker adapter
  supports `CapCreate`, and fails explicitly otherwise, including when the
  tracker cannot be resolved (closing the silent local fallback).
- Forward `IssueType`, `ParentKey` (and `Sprint`/`Assignee`/`Fields` when the
  request carries them) from `CreateTaskAs` into `tracker.CreateIssueRequest`,
  for every tracker; adapters that ignore a field keep doing so.
- Reuse `JiraAdapter.CreateIssue` as is for ADF conversion, parent, priority
  and issue-type defaults; no new Jira client code.
- The local row keeps using the adapter's returned key and URL
  (`jira-<projectId>-<KEY>`, `<site>/browse/<KEY>`), status `to_clarify` and the
  `#new` label, as today.
- Tracker errors are wrapped as `Jira issue creation failed: <cause>`, like the
  GitHub message, so a locked credential or a missing e-mail reads as such and
  never as "not supported".
- Tests use the existing fake-HTTP Jira adapter tests and the MCP server tests;
  nothing touches the real site.
- A `Fixed` line under `[Unreleased]` in `CHANGELOG.md` (user-visible).

### Critical dependencies

- A usable Jira credential for whoever the creation runs as. On the owner's
  instance the only personal Jira credential is keyed to the legacy `default`
  user (see ADR 0020) and the server settings hold no Jira e-mail or token, so
  manual verification needs the token re-entered from Profil > Trackers first.
- The MCP transport must carry the caller: the HTTP transport resolves it from
  the bearer; a transport without headers names nobody and would fall back to
  the server credential.
- No migration, no new service, no third-party limit beyond Jira's own
  validation (unknown issue type, parent not an epic, required fields).

### Questions for the owner

1. **Attribution of MCP creation.** Recommended: run `create_task` as the MCP
   caller, like the web form: their personal Jira token, with an explicit
   error when they have none or it is sealed; the server credential only when
   the call names nobody. Alternative: always use the project/server credential,
   as the ticket's "same credential that tracker sync uses" wording suggests,
   which creates issues under the service account's name.
2. **`get_task` comments.** Recommended: include it, and carry the same caller
   into `get_task`'s comment read, since it is the same one-line root cause and
   the ticket names it. Alternative: leave it to a separate ticket (and, if so,
   should `add_comment` and the other MCP tracker writes be part of that one?).
3. **Mandatory custom fields.** Recommended: out of scope for now, but when Jira
   refuses for a missing required field, the error names the fields
   (`RequiredCreateFields` already lists them). Alternative: add an optional
   `fields` map (field id → value or option id) to `create_task`.
4. **Assignee.** Recommended: out of scope (no `assignee` parameter), and Jira's
   project default applies. Alternative: assign the new issue to the caller, or
   add an `assignee` parameter.

## Round 2 - answers from the owner (2026-09-25)

The owner answered the four Round 1 questions interactively, choosing the
recommended option each time.

### Settled decisions

1. **Attribution:** `create_task` runs as the MCP caller. The caller resolved
   by `callerOf` is put on the context (`tracker.WithActingUser`) and the store
   is called through `CreateTaskAs`, so `JiraAdapter.forProject` uses the
   caller's personal Jira token. No personal token, or a sealed one not
   unlocked, is an explicit error. The project/server credential is used only
   when the call names nobody (a transport without headers).
2. **`get_task` comments:** in scope. `get_task` reads comments with the same
   caller (`GetTaskCommentsAs`), so the Jira comment read no longer falls back
   to a server credential without an e-mail. `add_comment`, `update_task`,
   `transition_stage` and the other MCP tracker calls stay out of scope.
3. **Mandatory custom fields:** out of scope as an input. When Jira refuses a
   creation, the error names the fields the site makes mandatory for that issue
   type, from `RequiredCreateFields`. `create_task` gets no `fields` parameter.
4. **Assignee:** out of scope. No `assignee` parameter; Jira's project default
   applies.

### Reversed assumptions

- The ticket's wording "through the same Jira credential that tracker sync
  already uses" is not followed: an MCP creation that names a caller uses the
  caller's own credential, not the sync's.
- The "Expected" section's assignee is dropped from the scope.

### Newly settled technical points

- The required-field lookup happens only after Jira refuses a creation, so a
  successful creation costs no extra request. A failure of that lookup keeps
  Jira's original error rather than hiding it.
- The fix to `get_task` also covers GitHub-backed projects (the caller's token
  when stored), which matches what the web detail view already does.

### Acceptance criteria after Round 2

- `create_task` on a Jira-backed project creates the Jira issue under the
  caller's account and returns its key and browse URL.
- `issueType` and `parentKey` reach Jira; `parentKey` links the issue to its
  parent epic.
- The Markdown `description` is sent as ADF.
- A missing or sealed personal credential returns an explicit error naming the
  cause, never "not supported".
- A creation Jira refuses for a missing mandatory field names those fields.
- `RequireRemoteCreation` fails when the project's tracker cannot be resolved
  or cannot create, instead of creating a local-only task.
- The new task lands on the local board at the first workflow stage.
- `get_task` returns Jira comments for a caller with a personal credential.
- `CHANGELOG.md` gets a `Fixed` line under `[Unreleased]`.
