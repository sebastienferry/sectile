## Round 1 (2026-09-25)

### Restated request and scope

Keep the MCP endpoint stateful (ADR 0007) when several server instances share one
PostgreSQL database: a request carrying an `Mcp-Session-Id` that another instance
created is served by that instance, a dead instance's sessions end with a `404` and
their runs are canceled but stay recoverable, and `GET /api/mcp/sessions` lists the
sessions of every live instance.

Out of scope: moving sessions between instances (a session dies with its instance,
as settled for #397 Q2), stateless MCP, balancer configuration and the external
deployment change (#397 Q4), the SQLite single-instance mode (unchanged), and the
multi-replica integration harness (macro ticket 8).

### Verified findings

1. **Half of the second criterion already exists.** Since #403, every activity carries
   the id of the instance that created it, and a live instance reclaims the work of
   instances unseen for 45 s: client-created remote runs are set to `canceled`. A run
   started through a session is created by the instance that holds the session, so,
   once requests are forwarded to their owner, the owner's death already cancels the
   right runs, from whichever survivor sweeps first. No session table is needed for
   this.
2. **But those runs are not recoverable today.** The reclaim writes the summary
   `Interrupted by server restart: the client session that owned this run is gone`
   (`interruptedClientRun`). `FinishRemoteRunAs` only lets an owner rewrite a canceled
   run whose summary contains `models.RunDisconnectNote`. A run lost with its instance
   is therefore final, which contradicts the ticket ("recoverable through
   `finish_run`") and ADR 0007's #307 amendment. The same holds for the single-process
   restart sweep, which writes the same summary. See Q2.
3. **The unknown-session path is already the right one.** The go-sdk answers
   `404 session not found` to an id it does not hold, which is what MCP clients react to
   by re-initializing. So a dead owner only needs the receiving instance to not forward
   and let the local handler answer.
4. **The forwarding of #406 cannot be reused as is.** It is a JSON verb protocol
   (`/internal/agent/<verb>`) that answers once. MCP needs the HTTP exchange itself to
   cross: `POST` (JSON answer here, `JSONResponse: true`), `GET` (a long-lived SSE
   stream for server-to-client messages) and `DELETE` (session end). What is reusable:
   the internal listener, its port, the derived bearer, the advertised address and the
   liveness table. What is new: a streaming reverse proxy and an instance lookup by id
   (no `DB` method returns one instance's address today; presence joins it only for
   agents).
5. **Session ids are generated by the SDK** (random). `ServerOptions.GetSessionID` lets
   Sectile choose them, which is how the owning instance id gets into the id. Instance
   ids are UUIDs, safe in a header.
6. **The registry stays local and correct.** Adoption, silence, abandon and
   `DELETE`-driven closing all happen on the owner, because every request of a session
   reaches it. Only the status view (`Snapshot`) must look beyond the local instance.
7. **The sessions view is consumed by the web app** (`useMcpSessions`, summary of
   clients and runs). Adding a field is backward compatible.

### Ambiguities, worst first

1. **Routing mechanism** (#397 Q5): forwarding in the application, balancer affinity on
   the header, or stateless MCP. Three different implementations; product question Q1.
2. **Recoverability of a run lost with its instance** (finding 2): the ticket says
   recoverable, the code says final. Q2.
3. **An owner that is alive but unreachable.** `404` makes the client drop a session
   the owner still holds (its runs stay adopted there until the abandon bound); a
   retryable error keeps the session but blocks the client until the owner answers or
   is declared dead (45 s). Resolved technically below (R3).
4. **What the aggregated view does when a replica does not answer.** Q3.

### Critical dependencies

- #403 and #406 are on `main` (instance table, liveness, internal listener, derived
  bearer). No other open child ticket of #397 touches `/mcp`.
- No migration is needed if sessions stay in memory (R1 below): the instance id is in
  the session id, and liveness is `server_instances`.
- The internal listener only starts when `database.Shared()` (PostgreSQL); SQLite keeps
  one instance and no forwarding.
- The internal bearer derives from `SECTILE_SECRET_KEY`; without it #406 already
  disables forwarding and says why. MCP forwarding inherits that behaviour.
- The balancer must not buffer SSE on `GET /mcp` (already required by #397 for
  `/api/events`); nothing new for the ingress under Q1 (a).

### Reversible technical choices, resolved from the code

- **R1. Session id format.** `GetSessionID` returns `<instanceID>.<random>` (the random
  part as the SDK does it today). Used on every engine, so a single instance behaves
  identically and tests need no switch; the receiving instance parses the prefix.
- **R2. Forwarding path.** A public `/mcp` request whose session prefix names another
  instance is reverse-proxied (streaming, flush on every write, method, headers and
  body intact, the client's `Authorization` included) to
  `<owner address>/internal/mcp` on the internal listener. The owner authenticates the
  internal bearer **and** the client's bearer as the public route does, so forwarding
  never widens access. A forwarded request is never forwarded again (loop guard, as in
  #406). `initialize` (no session id) is always served locally.
- **R3. Owner unreachable.** Owner absent from the live instances → no forwarding, the
  local handler answers `404` and the client re-initializes; its runs are reclaimed by
  the sweep within the 45 s bound. Owner listed as live but the connection fails →
  `503` with a readable reason, never a retry (the request may have reached it, as #406
  decided). Once the owner is declared dead the next request gets `404`.
- **R4. Reclaim stays where #403 put it.** No new sweep: the dead-instance reclaim
  already cancels the right runs. The only change there is the summary (Q2).
- **R5. ADR 0007 gets a third amendment**: sessions are owned by one instance, found
  through their id, and die with it; nothing else of the decision changes.
- **R6. Tests** use two `Handler`s on one PostgreSQL test database behind two
  `httptest` servers, a client alternating between them, then one server stopped. The
  full harness stays in macro ticket 8.

### Product questions

**Q1. MCP session routing (#397 Q5).**
(a) In-app forwarding: the session id names its owner, any instance proxies to it;
works behind any balancer, reuses #406's internal channel. (b) Balancer affinity on
`Mcp-Session-Id`: no Sectile code for routing, but depends on the balancer hashing a
header, and `/api/mcp/sessions` aggregation is still needed. (c) Stateless MCP: reverses
ADR 0007, runs would end on a heartbeat timeout instead of a disconnect.
Recommendation: **(a)**.

**Q2. Can a run lost with its instance be recovered through `finish_run`?**
(a) Yes, for a dead instance **and** for a single-process restart: the reclaim summary
carries `RunDisconnectNote`, so the owner may correct the outcome, exactly as after a
disconnection. (b) Yes, for a dead instance only; a restart stays final. (c) No, both
stay final (the ticket's criterion is then reworded).
Recommendation: **(a)**: to the client, both are its session vanishing, and ADR 0007
already calls that recoverable.

**Q3. `/api/mcp/sessions` when a replica does not answer.**
(a) Answer with the sessions of the instances that did, each session carrying its
`instance`, plus the list of instances that did not answer; the view stays usable.
(b) Fail the whole request. Recommendation: **(a)**, with a 2 s bound per instance.
Whether the web view shows the instance (or the unreachable ones) is a presentation
choice; default: not shown in this ticket.
