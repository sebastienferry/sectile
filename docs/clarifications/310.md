# Clarification #310 — Une activité de projet est une chaîne magique dans task_id

Ticket : https://github.com/sebastienferry/sectile/issues/310
Type : Technical debt — suite de la PR #304.
Branche : `feat/310`.

## Round 1 — cadrage (2026-09-21)

### Reformulation

`task_activities.task_id` sert aujourd'hui deux rôles : la clé étrangère vers une
tâche, et un identifiant synthétique `sync-<projectID>` / `sync-<syncType>` pour les
activités qui appartiennent à un projet ou à personne. Ce ticket sépare les deux :
`task_id` devient nullable et porte de nouveau une clé étrangère vers `tasks`, une
colonne `project_id` accueille les activités de projet, et les lignes existantes sont
migrées.

Hors périmètre : toute refonte de l'historique d'activités au-delà de ce découpage,
et tout changement du contrat de l'API `/api/activities` autre que ceux imposés par
la nouvelle colonne.

### Mesures demandées par le ticket

**1. Qui produit un `task_id` non-tâche.** Un seul site : `EnqueueSyncAs`. Tous les
autres `TaskID:` de `internal/db/db.go` (lignes 2686, 2707, 4138, 4157, 4378, 4401,
4637, 4666, 5177) valent `task.ID`. Le commentaire du schéma, qui dit « the queue does
the same for work that belongs to a project », décrit en réalité le `SkillJob` qui
relaie ce même `targetTaskID` (ligne 4526) — pas un second producteur. Le périmètre
de production est donc d'une fonction.

**2. Les lectures qui filtrent sur `task_id`.**

| Site | Filtre | Impact |
| --- | --- | --- |
| `getTaskActivitiesUnsafe` (`db.go:3116`) | `a.task_id = ?` | Appelé avec `sync-<proj>` par les tests et par les chemins de sync. Une activité de projet ne sera plus atteignable par là. |
| `GetActivities` (`db.go:4747`) | `a.task_id = ?` (param `taskId`) + filtre projet | Le filtre projet repose sur `a.task_id LIKE '%id%' OR a.prompt LIKE '%id%'` : deuxième convention implicite, qui disparaît avec `project_id`. |
| `GetActivityStats` (`db.go:4967`) | même heuristique `LIKE` | Idem. |
| `GetActivityByID` (`db.go:4881`) | `LEFT JOIN tasks` | Déjà tolérant à l'absence de tâche (`COALESCE`). |
| `remoterun.go:168,384,394` | `id=? AND task_id=?` | Toujours des tâches réelles, non impacté. |
| `db.go:2915,2921` (`DeleteTask`) | `WHERE task_id = ?` | Inchangé. |

**3. L'interface.** `web/src/components/ActivitiesView.tsx` et `SyncView.tsx`
consomment `/api/activities?projectId=…`. Le contrat JSON ne change pas si `task_id`
nul est rendu comme chaîne vide.

**4. La migration.** Deux parties à ne pas confondre :
- Le **DDL** (passage de `task_id` en nullable, ajout de `project_id`, rétablissement
  de la clé étrangère). SQLite ne sait ni relâcher un `NOT NULL` ni ajouter une clé
  étrangère par `ALTER TABLE` : il faut une reconstruction de table
  (`CREATE … / INSERT SELECT / DROP / RENAME`). PostgreSQL le fait par `ALTER`.
  Conformément à l'ADR 0016, une base PostgreSQL neuve naît au schéma courant.
- Le **backfill** des lignes `sync-*` existantes. Il doit tourner sur **les deux**
  moteurs : des bases PostgreSQL créées depuis #304 contiennent déjà de telles lignes.
  Ce n'est donc pas une migration historique SQLite.

### Choix techniques réversibles, tranchés ici

1. `task_id` nullable en base ; le champ Go `TaskActivity.TaskID` reste un `string`,
   les lectures faisant `COALESCE(a.task_id, '')`. Le contrat de l'API ne bouge pas.
2. Les requêtes gardent leurs placeholders `?` et passent par `Rebind` (ADR 0016).
3. Le DDL différent entre moteurs passe par le `dialect`, pas par du SQL conditionnel
   dispersé.
4. Nouvelle méthode de lecture dédiée aux activités de projet plutôt que de faire
   accepter un identifiant de projet à `GetTaskActivities`.
5. Index : `idx_activities_task` conservé, ajout d'un index sur `project_id`.
6. Les tests qui écrivent `TaskID: "sync-" + project.ID` sont réécrits sur
   `ProjectID`, pas conservés en l'état.

### Questions produit ouvertes

1. **L'autosync sans `ActingUser` fait-il partie de ce ticket ?** Le ticket le
   présente comme « probablement à traiter dans le même mouvement ». C'est un
   changement de comportement (quel jeton est utilisé pour synchroniser), pas un
   changement de modèle. *Recommandation : non — ticket voisin distinct, ouvert
   depuis celui-ci.*
2. **Supprime-t-on l'heuristique `a.prompt LIKE '%projectID%'`** du filtre projet de
   `GetActivities` et `GetActivityStats` ? C'est la même famille de magie, et
   `project_id` la rend inutile pour les activités de sync — mais elle peut rattraper
   aujourd'hui d'autres lignes. *Recommandation : oui, la retirer dans ce ticket ; sa
   présence est précisément ce que le ticket veut faire disparaître.*
3. **Que devient une ligne `sync-<x>` dont le suffixe ne résout aucun projet**
   (`sync-all`, `sync-github`, ou un projet supprimé) ? *Recommandation :
   `task_id = NULL` et `project_id = NULL` — une activité globale, qui reste visible
   dans l'historique « tous projets ».*
4. **Clé étrangère vers `projects` : oui ou non, et avec quel `ON DELETE` ?**
   *Recommandation : oui, `ON DELETE CASCADE` — l'historique d'un projet supprimé n'a
   plus de lecteur.*
5. **Impose-t-on une contrainte `CHECK` d'exclusivité** (au plus un de `task_id` /
   `project_id` renseigné) ? *Recommandation : oui — c'est ce qui empêche la
   convention implicite de revenir par une autre porte.*
6. **Les activités d'une tâche doivent-elles aussi porter le `project_id` de leur
   tâche** (dénormalisation qui simplifierait le filtre projet en un seul prédicat) ?
   *Recommandation : non — deux sources de vérité pour le même rattachement, et la
   jointure sur `tasks` est déjà en place.*

À arbitrer par le propriétaire du ticket.

### Critère d'acceptation, inchangé

Une synchronisation apparaît dans l'historique du projet sur les deux moteurs, aucune
ligne de `task_activities` ne porte un `task_id` qui n'est pas une tâche, et la clé
étrangère est rétablie pour les activités de tâche.
