# Clarification #730 - Desktop / Agent authorization

- Ticket: [#730](https://github.com/sebastienferry/sectile/issues/730)
- Task ID: `gh-11a4f59c-b6bd-4747-8ea5-0a10d5b78da4-730`

## Round 1 - initial report (2026-10-05)

### Request

The ticket asks to move the Sandbox settings, today a category of each
project's settings in Desktop (#700, ADR 0048), to the workstation level so
that one set of values applies to every project, and to let the owner keep a
whitelist of what Claude Code may do there. Out of scope: other engines than
Claude Code, custom command templates (they never receive the generated
settings), the server (the values never leave the workstation), and the
owner's own `~/.claude/settings.json`, which Sectile does not edit.

### What the code does today

Files read:

- `internal/agentconfig/claude_sandbox.go`: `ClaudeSandbox` (enabled, allowed
  domains, extra writable paths, allow and deny rules), normalisation,
  `MergeClaudeSandbox` (keeps rules an "Always allow" added while the dialog was
  open), and the generated file `~/.config/sectile/claude/<projectId>.json`.
- `internal/agentconfig/workstation.go`: the values live under
  `projectSettings.<projectId>.claudeSandbox`; `Defaults` (the workstation
  level, "Execution defaults") has no sandbox field.
- `internal/agentconfig/local.go`: `overlay` carries the project value with
  `firstSandbox`.
- `internal/agent/agent_desktop_settings.go`, `agent_desktop.go`: the project
  settings save and payload (`claudeSandbox`, `claudeSandboxBase`,
  `platformSandbox`).
- `internal/agent/agent_conversation_approvals.go`: "Always allow" adds the
  approved rule to the project's allow rules (`addProjectAllowRules`).
- `internal/agent/agent_config.go`: `settingsArg` hands `--settings=<file>` to
  built-in Claude lines; headless lines run with
  `--permission-mode bypassPermissions`.
- `internal/agent/agent_headless.go`: Claude's refusals become activity lines
  pointing at "the project's Sandbox settings".
- `desktop/src/sandbox-settings.mjs`, `desktop/src/main.js`: the "Sandbox"
  category of `PROJECT_SETTINGS_CATEGORIES`; the workstation
  `SETTINGS_CATEGORIES` has none.
- `docs/adrs/0048-claude-sandbox-values-reach-claude-through-a-generated-settings-file.md`.

Neighbouring precedent: the execution settings already have two levels
(#305): the workstation defaults and a project section that speaks over them,
resolved in `Resolve`/`overlay`.

### Ambiguities, worst first

1. **What "whitelist" means.** The Sandbox category already holds an allow
   list (`permissions.allow`) and an allowed-domains list. Readings that lead
   to different code:
   - (a) the existing allow list and domains, simply moved to the global level;
   - (b) a new whitelist for headless runs: they run with
     `bypassPermissions` today, so the allow rules "change nothing for them"
     (the panel says so); the whitelist would replace the bypass with
     `--permission-mode dontAsk`/`default` plus the allowed rules, so a headless
     run only does what is listed;
   - (c) a whitelist of projects or folders the global values apply to.
2. **"Move to global": replace or layer.** Either the project category
   disappears and only the global one remains, or a global level is added and
   the project category stays as an override, as the execution settings do.
3. **Where "Always allow" writes.** To the global allow list (every project
   then trusts the rule) or to the project's.
4. **What happens to the values projects already hold.** Folded into the
   global level on first start, kept as project overrides, or dropped.

### Critical dependencies

- No database migration: everything is in the workstation settings file. A
  schema change of that file must still read the existing
  `projectSettings.*.claudeSandbox` sections.
- Claude Code merges array settings across sources, so a global list and a
  project list can be unioned, but the `--settings` flag takes one file: the
  launch must write one document holding the resolved values.
- If reading (b) is chosen: Claude Code's `dontAsk` mode and its behaviour on a
  refused tool in `-p` mode must be checked against the installed version, as
  ADR 0048 did for the sandbox keys. A headless run that hits an unlisted tool
  fails or stalls instead of proceeding, which changes every unattended stage.
- ADR 0048 is amended or superseded by a new ADR.
- Desktop UI tests `desktop/tests/sandbox-settings.ui.cjs` and the command
  preview tests move with the panel.

### Technical choices resolved from the code

- The global values live in the workstation settings under `defaults`, beside
  the other workstation defaults; they never reach the server (ADR 0048 rule
  kept).
- The launch keeps writing one generated file per project,
  `~/.config/sectile/claude/<projectId>.json`, from the resolved values, so the
  command lines and their preview do not change shape.
- If both levels exist: lists are the union global then project, deduplicated
  in order; the sandbox state of the project speaks over the global one when it
  is not "Inherited". This mirrors Claude Code's own merge, where a list can
  only add.
- The concurrent-save protection (`claudeSandboxBase`, `MergeClaudeSandbox`)
  applies to the global save as it does to the project one.
- The global category goes into the workstation settings dialog
  (`SETTINGS_CATEGORIES`), under the label "Sandbox".
- On Windows the sandbox state and lists stay disabled and only the rules
  apply, as today.
- The headless refusal line names the place the rule is to be added, global or
  project depending on the answer to question 3.

### Product questions

1. **What is the whitelist?** Recommended: (b), a whitelist that headless runs
   honour, replacing `bypassPermissions`, with the allow list as the
   whitelist. It is the only reading that adds a capability; (a) is already
   there. Offer it as a switch ("Headless runs: allow everything / only the
   allow rules"), default "allow everything", so no existing pipeline breaks.
2. **Replace or layer?** Recommended: layer. A global Sandbox category
   applies to every project, and the project category stays as an addition
   (union of lists, project state overriding), as the execution settings do.
3. **Where does "Always allow" write?** Recommended: the project, as today,
   because a rule approved on one repository should not silently apply to
   all; the panel offers to move a rule to the global list.
4. **Existing project values?** Recommended: kept as they are, as project
   values; nothing is moved automatically.

## Round 2 - answers from the owner (2026-10-05)

Answers given interactively in the session, in two passes: the four Round 1
questions, then four follow-ups their answers raised.

### Settled decisions

1. **The whitelist is a list of Sectile projects** the global Sandbox values
   apply to (Round 1 reading (c), project granularity rather than filesystem
   folders). The global Sandbox category shows one checkbox per project.
2. **An empty whitelist means every project.** Checking projects restricts the
   global values to the checked ones; a project left out receives only its own
   project values.
3. **Two levels, layered.** A global Sandbox category is added to the
   workstation settings, and each project keeps its own Sandbox category. For a
   project the global values reach: lists are the union global then project,
   deduplicated in order; the project's sandbox state speaks over the global
   one when it is not "Inherited".
4. **"Always allow" keeps writing to the project's allow rules**, as today.
   The project panel offers to move a rule up to the global allow list.
5. **Existing project values are folded into the global level** once, when
   the agent first reads settings written before this change:
   - the four lists (allowed domains, extra writable paths, allow rules, deny
     rules) of every project are unioned into the global lists, in project
     order then entry order, and removed from the projects;
   - the sandbox state goes to the global level only when every project that
     states one agrees; when they diverge, each project keeps its own state
     and the global state stays "Inherited";
   - the whitelist starts empty, so every project receives the merged values.

### Reversed assumptions

- Round 1 recommended reading (b), a whitelist that headless runs honour
  instead of `bypassPermissions`. It is not chosen: headless runs keep
  `bypassPermissions`, and the panel's hint that allow rules change nothing for
  them stays true.
- Round 1 recommended keeping existing project values in place. Reversed: they
  are folded into the global level (decision 5).

### Consequences and new points, resolved from the code

- The migration widens what a project allows: a rule approved on project A
  applies to project B after the fold. This is the owner's choice; the
  changelog line and the ADR say it, and the global panel lists every entry so
  it can be removed.
- The fold runs once and is recorded, like the seeds in `Seeded`
  (`internal/agentconfig/workstation.go`), so a project value added later is
  never folded again. Both the current settings file and the legacy layouts
  `overlay` reads are covered.
- The global values live under `defaults` in the workstation settings (a
  `claudeSandbox` field beside the execution defaults), with the whitelist as a
  list of project IDs. A project removed from Desktop is dropped from the
  whitelist; an ID no longer known is ignored at launch.
- Resolution happens where the project file is written today
  (`ClaudeSettingsFile`): the generated
  `~/.config/sectile/claude/<projectId>.json` holds the resolved values, so a
  launch keeps one `--settings` argument and the command preview its shape.
  The project panel's preview shows the resolved result and says which entries
  come from the global level.
- The global save uses the same base-and-merge protection
  (`MergeClaudeSandbox`) as the project save, so an "Always allow" or a rule
  moved up while the dialog is open is not lost.
- The headless refusal line in `internal/agent/agent_headless.go` keeps
  pointing at the project's Sandbox settings, since "Always allow" writes
  there; it is a user-visible French string and is left as is.
- ADR 0048 is superseded in part by a new ADR describing the two levels, the
  whitelist and the one-time fold.
