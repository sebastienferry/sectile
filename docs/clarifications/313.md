## Round 1 — analysis (2026-09-21)

### Restated request and scope

Make the board-column synchronisation work for a Jira-tracked project: the project's
columns and the tracker statuses they group must be obtainable from the Jira board,
both on demand from the project settings and during a tracker sync. Out of scope:
changing the column model itself, the GitHub path (beyond keeping it working),
sprints, and any write-back of columns to Jira.

### Files read

- `internal/trackerapi/jira.go` (`ListBoards`, `ListBoardColumns`, `ListStatuses`, `statusNamesByID`)
- `internal/db/board.go` (`ImportProjectBoardColumns`, `SyncProjectBoardColumns`, `GetProjectTrackerStatuses`)
- `internal/db/db.go` (`afterTrackerSync`)
- `internal/handlers/handlers.go` (`/api/projects/detected-statuses`, `/{id}/boards`, `/{id}/board-columns`, `/{id}/tracker-statuses`)
- `web/src/context/AppContext.tsx` (`listProjectBoards`, `importProjectBoardColumns`)
- `web/src/components/BoardColumnsEditor.tsx`, `web/src/components/ProjectModal.tsx`

### Verified findings (why it does not work)

1. **No board is ever selected for a Jira project.** `listProjectBoards` and
   `importProjectBoardColumns` exist in `AppContext.tsx` but no component calls them:
   `ProjectModal.tsx` has no board picker. `Project.BoardID` therefore stays empty.
2. **The sync step is consequently skipped.** `afterTrackerSync` (`internal/db/db.go:3855`)
   only calls `SyncProjectBoardColumns` when `proj.BoardID` is non-empty. On Jira it
   never runs, even though `SyncProjectBoardColumns` itself can fall back to the first
   scrum board.
3. **The status palette is GitHub-only.** `GetProjectTrackerStatuses`
   (`internal/db/board.go:117`) has a single `if proj.IssueTracker == "github"` branch
   and returns an empty slice for Jira — so the editor shows no status to drag.
4. **"Détecter" is GitHub-only too.** `/api/projects/detected-statuses`
   (`internal/handlers/handlers.go:520`) only queries GitHub ProjectsV2; for Jira it
   returns nothing, which the UI reports as "Aucune colonne trouvée".
5. **The "Détecter" UI does not model columns.** Even when statuses come back, the
   editor creates one column per status name (`BoardColumnsEditor.tsx:95-108`) instead
   of using the board's real column → statuses grouping, which is exactly what
   `JiraAdapter.ListBoardColumns` already returns.
6. The Jira adapter side is sound: it declares `CapBoard`, reads
   `/rest/agile/1.0/board/{id}/configuration` and resolves status ids via
   `/rest/api/3/status`. The defect is wiring, not the adapter.

### Dependencies and constraints

- A reachable Jira credential resolved per acting user (`forProject`); read-only scopes
  on `/rest/agile/1.0` and `/rest/api/3/status` are sufficient.
- `/rest/api/3/status` returns the whole instance's statuses; on large sites it is a
  heavy call and status names are not unique across workflows (resolution is by id, so
  this is safe today, but the palette must not list the whole instance).
- No database migration is expected: `BoardID`, `TrackerColumns` and `StageColumns`
  already exist on the project model.
- Minor, non-blocking: several user-facing strings in `board.go` are French
  (`"aucun board sur le projet"`), against the repository's English-only policy.

### Reversible technical decisions (taken here)

- Route the Jira path through the existing `tracker.TicketingSystem` capability
  (`CapBoard`), not through a Jira-specific branch in `board.go`: the GitHub-only `if`
  becomes an adapter dispatch, so GitLab gets the same behaviour for free.
- Reuse `SyncProjectBoardColumns`' existing merge rules (tracker owns names/order,
  hand-assigned statuses and hidden flags survive). No new merge semantics.
- Keep the two endpoints as they are (`/boards`, `/board-columns`); the fix is to call
  them from the UI rather than to add an API surface.

### Open product questions

1. **Board selection.** Should the project settings expose an explicit board picker
   (list from `/api/projects/{id}/boards`), or should Sectile silently pick the first
   scrum board and never ask? *Recommendation: explicit picker, pre-selected with the
   first scrum board, and persist it in `BoardID`.*
2. **What "Détecter" produces on Jira.** One Sectile column per Jira board column, with
   the statuses that column groups, or one column per status? *Recommendation: mirror
   the board columns with their grouped statuses — that is what a Jira user expects.*
3. **Status palette content.** Should the draggable status list be the board's statuses
   only, or all statuses reachable by the project's workflows (`ListStatuses`)?
   *Recommendation: the project's statuses, so a status absent from the board can still
   be mapped by hand.*
4. **Automatic sync.** Once a board is selected, should every tracker sync re-apply the
   board's columns (current `afterTrackerSync` intent), or should refresh stay manual?
   *Recommendation: keep it automatic — it is the documented intent of the function.*
5. **Blast radius.** Fix Jira only, or generalise the same wiring to every `CapBoard`
   tracker in this ticket? *Recommendation: generalise the plumbing, validate on Jira,
   leave GitHub behaviour unchanged.*

## Round 2 — answers from the owner (2026-09-21)

All five open questions are settled. No prior assumption was reversed; the owner
confirmed every recommendation made in Round 1.

1. **Board selection — explicit picker.** The project settings expose the board list
   from `GET /api/projects/{id}/boards`, pre-selected with the first scrum board, and
   persist the choice in `Project.BoardID` (via the existing
   `POST /api/projects/{id}/board-columns`).
2. **"Détecter" on Jira — mirror the board columns.** One Sectile column per Jira board
   column, carrying the statuses that column groups, from
   `JiraAdapter.ListBoardColumns`. The one-column-per-status behaviour is not used on a
   `CapBoard` tracker.
3. **Palette — the project's statuses.** The draggable status list comes from
   `ListStatuses`, a superset of the board's statuses, so a status absent from the board
   remains assignable by hand.
4. **Automatic sync — yes.** Once a board is selected, `afterTrackerSync` re-applies
   `SyncProjectBoardColumns` on every tracker sync, keeping its merge rules: the tracker
   owns column names and order; hand-assigned statuses the tracker claims nowhere, and
   the hidden flag, survive.
5. **Blast radius — generalise the plumbing.** `GetProjectTrackerStatuses` and
   `/api/projects/detected-statuses` dispatch on the `CapBoard` capability instead of
   `if proj.IssueTracker == "github"`. GitHub behaviour is unchanged; GitLab inherits the
   same path. Validation is performed on Jira.

### Settled scope

- In scope: board picker in the project settings, Jira-aware status palette and
  detection, column mirroring through the existing merge, automatic refresh on sync,
  and the capability-based dispatch that replaces the GitHub-only branches.
- Out of scope: any write-back of columns to Jira, sprints, the column data model, and
  changes to GitHub's observable behaviour.
- Side note carried to specification, not a requirement of this ticket: the French
  user-facing strings in `internal/db/board.go` violate the English-only policy and can
  be corrected opportunistically in the touched lines.

satisfactory and zero product questions remain. Stage transition new → clarified applied.
