## Round 1 (2026-09-30)

### Request

A project names its own label prefixes for the epic priority, quarter and
readiness axes; on Jira it can also map the epic priority and quarter to custom
fields (a flat select or a two-level cascading select), learning the options it
does not know yet when it writes and never sending a value it cannot map. The
project also stores, shows and lets a person correct how the tracker's ticket
priorities map to Sectile's four levels, and a write refuses a mapping that was
only guessed.

Out of scope: the values of the axes (still `p0` to `p3`, `YYYY-qN`, `idea`,
`shaping`, `ready`), the `roadmap:` horizon prefix, a custom field for the
readiness axis, writing the same axis to two fields at once, the priority of
GitHub and GitLab tickets, and migrating labels already written under an old
prefix.

### Ambiguities, worst first

1. **Whether the whole ticket is worth building.** Rows 36 and 38 are generic;
   row 37 is tied to one Jira configuration (the PE project's `Epic Priority`
   and cascading `Target Quarter` fields drove Taskativ's changes 87 to 93).
   Keeping all three, or dropping row 37, gives two very different amounts of
   code. Question 1.
2. **What "refuse a guessed mapping on write" does to a write.** Today a
   scheme Sectile cannot name (P1 to P4, a translation) is written by rank.
   Refusing could reject the whole edit, or write everything but the
   priority. The two leave the card in different states, and every existing
   project on such a scheme is affected the day it lands. Question 2.
3. **Whether the sync reads the axis custom fields back.** Taskativ writes the
   field and the label but reads only the label, so a person changing the field
   in Jira is not seen. Reading the field changes the import and the pending
   pushes. Question 3.
4. **Which axes get a configurable prefix.** Row 36 names priority, quarter and
   readiness; the horizon's `roadmap:` could be one too. Settled below from the
   row: not the horizon.

### Technical choices settled from existing code

- **Axes with a prefix.** Priority, quarter and readiness, as row 36 says. The
  horizon keeps `roadmap:`: its labels drive the tabs and the pending pushes of
  every project, and no ticket asks for it.
- **Prefix format.** The whole prefix is typed, separator included
  (`priority:`, `prio-`, `target/`). It is trimmed, lower-cased, stripped of a
  leading `#`, and refused when it carries a space, when it is empty after
  cleaning but was not empty, or when it starts another axis's prefix (so
  `p` and `priority:` cannot coexist). Empty keeps the current default.
- **Values under a prefix.** Unchanged: `p0` to `p3`, `YYYY-qN`, `idea`,
  `shaping`, `ready`. The bare `2026-Q3` stays read as a quarter whatever the
  quarter prefix is.
- **Changing a prefix.** Nothing is migrated. The stored values stay; the next
  import no longer finds them under the new prefix, so those epics join the
  pending pushes, which the user confirms as today. A push removes the axis
  labels under the current prefix only; a label left under the old prefix
  becomes a free label.
- **Where the settings live.** A "Roadmap" section of the Tracker tab, beside
  the roadmap projects, shown when the tracker can carry epic labels. They are
  project settings stored on the server, not workstation overrides: a label
  convention is a team decision about a tracker.
- **Custom field candidates.** Only closed-list fields from `editmeta`: single
  select and cascading select. One field per axis.
- **Epic priority map.** Four selects, one per level, storing option ids.
  Prefilled only when an option's label equals the level (`P0` for `p0`, case
  ignored); anything else is set by hand. Never deduced by rank.
- **Epic quarter map.** Deduced from option labels, the axis being open:
  `2026 - Q4`, `2026-Q4`, `2026 Q4` on a flat field; a year parent with a `Q4`
  or `2026 - Q4` child on a cascading one, stored as `parent/child`. A value
  missing from the map is looked up in the field's options at write time, and
  what is learned is stored on the project. A value set by hand wins over a
  deduction.
- **Writing an axis with a field mapped.** The label is written as today, and
  the field too. A value with no option in the field is not sent: the label is
  still written, and the activity says which value is missing from which field.
- **Ticket priority mapping.** Stored per project, since a Jira priority scheme
  belongs to a project. Each option of the scheme carries a level and a
  confidence: sure when its name is in the aliases, guessed when it came from
  the rank, sure when set by hand. When several options share a level, the
  most urgent one is written unless the person picks another. A later
  discovery fills only the options that have no level yet and never overwrites
  a hand-set one. The Tracker tab shows the table, marks the guessed lines, and
  lets each be confirmed or changed. Sectile's existing aliases are kept
  (`Critical` high, `Major` medium), not Taskativ's.
- **Reading keeps guessing.** A ticket priority read from the tracker still
  falls back on the rank: a ticket must land on some level.

### Product questions

1. **Scope.** Recommended: keep all three rows, delivered in three pull
   requests in this order: A, the prefixes (row 36); B, the ticket priority
   mapping (row 38); C, the custom fields (row 37). Alternative: drop row 37,
   as #426 dropped the template fields.
2. **A priority write that is only guessed.** Recommended: an update is
   refused before anything changes, with a message pointing to the Tracker
   tab; a creation creates the ticket without a priority and says so. On the
   day it lands, every project on a scheme Sectile cannot name sees its
   priority writes refused until someone confirms the guessed lines, which the
   table prefills.
3. **Reading the axis fields back at sync.** Recommended: yes. When a field is
   mapped, the import reads it first and the label second; a person changing
   the field in Jira is seen at the next sync, and an epic whose field and
   label disagree joins the pending pushes.
