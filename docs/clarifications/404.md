# Clarification for GitHub #404 (Auto-sync runs once per project across replicas)

## Round 1: analysis (2026-09-23)

### Request restated

Make the background synchronisation loop decide "this project is due" once across all
server replicas, and keep its pacing, full-pass dating, 429 backoff and reported status
in the database instead of process memory. Out of scope: deduplicating a sync job that
outlives its interval (true today with one process as well), per-tracker backoff, and
any change to what a sync job does.

### Files read

- `internal/db/autosync.go`: the loop, `runAutoSyncPass`, `recordAutoSyncPass`,
  `autoSyncWindow`, `enterAutoSyncBackoff`, `AutoSyncStatus`, the in-memory `autoSync`.
- `internal/db/db.go`: `EnqueueSyncWith` (no deduplication), the background branch of
  the sync job that calls `recordAutoSyncPass`.
- `internal/db/prdiscovery.go`, `prstates.go`: other callers of `enterAutoSyncBackoff`.
- `internal/db/autosyncwindow_test.go`, `autosyncowner_test.go`, `prdiscovery_test.go`:
  tests that write the in-memory maps directly.
- `internal/db/migrations.go`, `bookmarks.go` (`ON CONFLICT DO NOTHING` accepted by both
  engines), the web client (`AppContext.tsx`, `types/index.ts`): the status is fetched
  from `/api/sync/auto` but no screen displays it.

### Findings that settle the design

- **A pass does not sync, it queues.** `runAutoSyncPass` files one job per due project
  and returns within milliseconds; the job runs later on the same instance. What must be
  atomic across replicas is the decision that a project is due, not a long-running
  section. A lock held for the duration of a pass is not needed.
- **#404 does not need #403's code.** The claim needs no instance id. It is stacked on
  `feat/403` only because its migration must be number 4, after #403's number 3.

### Resolved technical decisions (reversible, settled here)

- **D1: Claim by conditional update, not advisory lock.** A per-project row holds
  `last_pass_at`; a replica claims the project with
  `UPDATE ... SET last_pass_at = now WHERE project_id = ? AND (last_pass_at IS NULL OR last_pass_at < now - interval)`.
  Exactly one replica sees one affected row. It works on both engines and needs no
  dedicated connection.
- **D2: The window keeps its meaning.** It is computed from the `last_pass_at` and
  `last_full_sync_at` read before the claim, as today.
- **D3: Schema, migration 4.** `auto_sync_projects (project_id PK → projects ON DELETE
  CASCADE, last_pass_at, last_full_sync_at)` and a one-row `auto_sync_state (backoff_until,
  last_run_at, last_error, last_imported, passes, imported)`, seeded by the migration.
- **D4: Backoff stays global**, as today, but persisted: a 429 seen by any replica
  pauses the loop on all of them for ten minutes.
- **D5: Status.** `/api/sync/auto` reads the persisted fields, so every replica answers
  the same. `passes` and `imported` become totals kept by the database rather than
  since this process started; no screen shows them. `running` stays per process: a pass
  lasts milliseconds, and it only guards against overlapping passes in one process.
- **D6: No `d.mu` in the new statements.** Each one is a single atomic statement, and
  `recordAutoSyncPass` / `enterAutoSyncBackoff` are called from paths whose lock state
  varies; taking the non-reentrant mutex there would risk a deadlock.
- **D7: Tests** that wrote the in-memory maps write the rows instead, through small
  helpers.
