# Clarification #498 - A wait survives when the MCP client re-initializes its session

- Ticket: https://github.com/sebastienferry/sectile/issues/498
- Branch: `feat/batch-393-497-498-584-647-648` (batch of #393, #497, #498, #584, #647, #648)
- Report: `docs/clarifications/498.md` (committed on the batch branch)

## Round 1 - initial analysis (2026-10-01)

### Request

A wait declared with `report_waiting(true)` is recorded with the declaring MCP
session (`waiting_session`). After a server restart the client initializes a
new session, so its next Sectile call no longer matches and the "?" glyph
stays until Enter in the console or `finish_run`. The run's next call must end
its wait even after the re-initialization, and a call from another session or
run must never end it.

Out of scope: waits set by hand or by a launch (`waiting_session = ''`), the
Enter path of #475, and the index of #497.

### Code read

- `internal/taskmcp/server.go`: session ids are `<instance id>.<random>`
  (`sessionIDFor`); the receiving middleware calls `sessions.Resume` on every
  `tools/call` but `report_waiting`; `report_waiting` stores
  `sessionID(req.Session)`.
- `internal/taskmcp/sessions.go`: `SessionRegistry.Resume` relays to
  `db.ResumeWaits(sessionID)`.
- `internal/db/remoterun.go`: `setRemoteRunWaiting`, `ResumeWaits`,
  `AnswerRemoteRunWait`.
- `internal/handlers/mcp_cluster.go`: a session lives in the memory of the
  instance that created it; "a session whose owner is gone is not found
  anywhere, and its client initializes a new one".
- `internal/agentmcp/mcp.go`: the stdio bridge every agent-launched console
  uses. It connects once; after a restart its upstream session answers 404
  and the client (the bridge, or Claude Code reconnecting it) starts over
  with a new session.
- `internal/agent/agent.go`, `agent_desktop.go`, `agent_console.go`,
  `agent_macro_dispatch.go`: every launched console gets `SECTILE_RUN_ID` in
  its environment, which the stdio bridge it spawns inherits.
- `specs/475-restart-after-question/spec.md`: the accepted residual this
  ticket removes.

### Ambiguities (worst first)

1. **What identifies "the run's next call" once the session changed.** Two
   readings lead to different code:
   - A. *The run carries its identity on every call.* The stdio bridge sends
     the run it was launched for (`SECTILE_RUN_ID`) in a request header, and a
     call carrying it ends that run's wait, whatever the session. Exact: only
     the named run is touched. It covers every launched run (the desktop and
     the board case), and not a session started by hand with `start_run`
     without a launcher runId, which keeps the #475 residual.
   - B. *The server infers it from the call.* When the declaring session is
     dead (its instance is gone, or it is not in this instance's registry), a
     call by the same user that names the run (`runId`) or its task ends the
     wait. It also covers sessions started by hand, but a different live
     session of the same user that reads the same task (a second console, a
     `get_task` from another conversation) would end a wait whose owner has
     not answered, which the second acceptance criterion forbids.

### Dependencies

- Reading A changes the agent: an agent older than the server sends no
  header and keeps today's behaviour, with no error. Nothing else breaks.
- The restart acceptance test needs a test server that drops its sessions,
  which the handler tests already simulate with a fresh `SessionRegistry`.

### Technical choices settled here (reversible)

- The header is `X-Sectile-Run-Id`, set by the bridge's HTTP client from
  `SECTILE_RUN_ID` when it is not empty, and read from
  `CallToolRequest.Extra.Header` in the same middleware that resumes the
  session's waits.
- The run named by the header is cleared only when it is `running`, waiting
  with a non-empty `waiting_session` that differs from the calling session,
  and owned by the caller (or has no owner), the rule `report_waiting` itself
  applies. A wait set by hand or by a launch stays.
- `report_waiting` keeps storing the session: the header only adds a second
  way to end the same wait, so a session that stays alive behaves as today.
- Tests: a DB test for the run-scoped clear (match, other run, other owner,
  hand-set wait), a handler test that declares a wait, replaces the session,
  calls `get_task` with the header and sees the wait end, and the same call
  without the header or with another run's id leaving it in place.
- Changelog: one `Fixed` line, since the glyph is what the user sees.

### Open product questions

1. **Which reading of "the run's next call"?**
   - A. Run identity carried by the launched console (`X-Sectile-Run-Id`).
   - B. Inference from a dead session plus the run or task the call names.
   - Recommended: **A**. It is the only one that keeps the second acceptance
     criterion for every case; the case it leaves out (a hand-started session
     re-initializing during a wait) keeps the Enter and `finish_run` paths.
