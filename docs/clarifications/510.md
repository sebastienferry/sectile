## Round 1 (2026-09-26)

### Restated request and scope

A project can declare several AI engines on a workstation, from the desktop
project settings: the engine it has today becomes its default engine, and
further engines (each a full profile: provider, model, per-skill models,
interactive and headless command templates) can be added. The desktop project
ticket table shows, for each task, the icon of the engine its next run uses;
clicking the icon cycles to the next engine, the choice sticks to the task
until the next click, and runs of that task use the chosen engine.

Out of scope: the web task card and any web editor, a server-side store of
engines or of the per-task choice, sharing engines across a team (#493),
workstation-level extra engines (unless Q4 says otherwise), and choosing an
engine from the Launch or Relaunch dialog.

### Verified findings

- Since #305 the engine is resolved only by the local agent, from
  `~/.config/sectile/settings.json`: `ProjectSettings.Execution` over
  `Defaults.Execution` over the provider defaults. The server stores no engine.
- A desktop launch goes desktop → local agent (`POST /desktop/tasks`) → server
  (`POST /api/tasks/{id}/run-skill`) → server queue → dispatch back to an
  agent, which calls `agentconfig.Resolve` with the task known
  (`internal/agent/agent_config.go:359`). The dispatch already carries a
  one-off `Model`; it carries no provider.
- The agent already corrects the run record with the engine it actually
  launched (`POST /api/activities/{id}/engine`), so the run history shows the
  right provider and model whatever the server guessed.
- The desktop ticket table shows no engine today. The only per-launch engine
  choice in the product is the free console's provider (Codex or Claude).
- No provider logo exists in the repository.

### Ambiguities (worst first; each changes the code)

1. **Which launches honour the task's engine.** Only launches started from the
   desktop ticket table, or every launch of that task that ends up running on
   this workstation (desktop, web, relaunch, every stage of a full chain). The
   first needs a new field on the server dispatch; the second needs none. (Q1)
2. **How a one-off model meets a switched engine.** The web offers one-off
   models from the default provider's list; applied to another engine's CLI it
   produces a model that CLI does not know. (Q3)
3. **Two engines with the same provider** (Claude with Opus, Claude with
   Sonnet): allowed or not, and how the icon tells them apart. (Q2)
4. **Level of the extra engines**: project only, as asked, or also a
   workstation list every project inherits. (Q4)

### Critical dependencies

- The agent and the desktop must be upgraded together: the desktop hides the
  toggle when the running agent does not announce the capability, following
  the existing `status.capabilities` pattern (`create-task`).
- No server change and no database migration if Q1 takes the recommended
  option.
- Skills and the Sectile MCP registration must be installed for every engine's
  provider, or a switch lands on an unprepared CLI.

### Reversible technical choices (resolved from the code and conventions)

- **Storage of the engines.** The default engine stays the existing
  `ProjectSettings.Execution` fields, so an existing local file needs no
  migration. Extra engines are a new `ProjectSettings.Engines` list, each with
  a stable generated ID, a name, a provider, a model, per-skill models and both
  templates. Validation reuses `ValidateExecution`.
- **Storage of the per-task choice.** In the local file, as a map from task ID
  to engine ID in a new top-level `Settings` field. It survives a restart, it
  is per workstation like every execution setting, and the agent reads it at
  dispatch time. An entry naming a removed engine reads as the default engine
  and is pruned on the next write; an entry for a finished task is pruned too.
- **Resolution.** A new function applies an extra engine over the resolved
  default the same way `Resolve` applies a project provider today: a provider
  different from the default drops the inherited templates, and the default
  engine's model and per-skill models are not inherited by an engine with a
  different provider (a model written for one CLI never serves another). The
  project's worktrees, parallelism, terminal and skill command names stay
  shared by all engines.
- **Setup providers.** The providers of the extra engines are added to the
  project's effective setup providers, so skills and MCP are installed for
  them.
- **Capability report.** Unchanged: it describes the default engine. The run
  record is corrected by the existing engine report, so history stays true.
- **Cycle order.** The default engine first, then the extra engines in the
  order the project settings list them; the last wraps to the default. With a
  single engine the icon shows and does nothing on click.
- **Icon.** A provider mark drawn in the app (letters or a generic glyph, no
  third-party logo), highlighted when the task is not on the default engine,
  with a tooltip naming the engine, provider and model. It is a keyboard
  reachable button with an accessible name. A click while a run is active only
  changes the next run.
- **Where the click is written.** The desktop asks the local agent to store the
  choice (new local endpoint), exactly as the project settings are saved; the
  desktop does not keep it in browser storage.

### Product questions (owner: @sebastienferry)

- **Q1 - Which launches use the task's engine?**
  Recommended: every launch of that task that runs on this workstation,
  including a launch from the web, a relaunch and each stage of a full chain.
  Alternative: only launches started from the desktop ticket table; the others
  keep the default engine.
- **Q2 - Can two engines share a provider?**
  Recommended: yes; each engine has a name you choose, the icon is the
  provider's mark, and the tooltip gives the name and model.
  Alternative: one engine per provider, which makes the icon unambiguous.
- **Q3 - A one-off model chosen on the web, on a task switched to another
  engine?**
  Recommended: the one-off model applies only when the task runs on its
  default engine; on another engine it is ignored and the run uses that
  engine's model.
  Alternative: the one-off model always wins, as it does today.
- **Q4 - Extra engines per project only?**
  Recommended: yes, per project, as the ticket asks; the default engine keeps
  inheriting from the workstation defaults as today.
  Alternative: also a workstation-level list that every project inherits and
  can extend.

## Round 2 - answers from the owner (2026-09-26)

Answers given interactively in the session.

### Settled decisions

- **Q1 - every launch on this workstation.** Every launch of a task that runs
  on this workstation uses the task's engine: desktop, web, relaunch and each
  stage of a full chain. The agent applies the choice at dispatch time; no
  server change, no new dispatch field.
- **Q2 - several engines may share a provider.** Each engine has a name the
  owner chooses. The icon is the provider's mark; the tooltip gives the name,
  provider and model.
- **Q3 - a one-off model applies on the default engine only.** When the task
  runs on another engine, a one-off model from the web is ignored and the run
  uses that engine's model. "Default engine" means the project's default
  engine (see Q4).
- **Q4 - every engine is declared globally, with a migration.** The owner
  reopened the question and chose a workstation catalogue instead of per
  project engines:
  - the desktop workstation settings hold a catalogue of named engines, each
    a full profile (provider, model, per-skill models, interactive and
    headless templates), and mark one as the workstation's default engine;
  - a project no longer defines an engine. It may pick its default engine from
    the catalogue; without a pick it uses the workstation's default engine;
  - clicking the icon in the ticket table cycles through the whole catalogue,
    starting from the project's default engine, in catalogue order, wrapping
    around;
  - the existing engine fields (workstation defaults and project sections,
    shipped by #305) are migrated once, automatically, into catalogue entries.
    Identical profiles collapse into one entry. A project that had its own
    engine keeps it as its default engine. Nobody has to configure anything
    again after the upgrade;
  - the desktop project form loses its provider, model, per-skill model and
    template fields and gains a single "default engine" selector with an
    "inherit the workstation default" choice.

### Reversed or amended assumptions

- Round 1 kept the default engine in `ProjectSettings.Execution` and put extra
  engines in `ProjectSettings.Engines`. Reversed: engines live in a
  workstation-level catalogue (`Defaults.Engines`, each with a stable ID) plus
  a default engine ID; a project section holds only an optional default engine
  ID. The engine fields of `Execution` (`aiProvider`, both templates,
  `aiModel`, `aiSkillModels`) stop being written; they are read only by the
  migration.
- Round 1 said the default engine's models are not inherited by another
  engine. With full profiles in one catalogue there is nothing to inherit:
  each engine resolves from its own profile, then the provider defaults.
- Out of scope in round 1, "workstation-level extra engines", is now the core
  of the change.

### Settings that stay where they are

Worktrees, parallelism, terminal and extra setup providers keep their
workstation default and project override. Skill command names stay per
project. The model list per provider (`aiProviderModels`) and the editor stay
global. None of them describe an engine.

### New dependencies surfaced

- **Local file migration.** A new settings layout version, written by the
  agent under the existing settings lock, idempotent, with a backup of the
  previous file. An agent that predates it must not rewrite the new layout;
  the migration needs a test for each source shape (defaults only, project
  override with and without its own provider, a provider change that dropped
  the inherited templates, identical profiles across projects).
- **Server seed (#305 US6).** A workstation seeded after this change writes
  the server values into the catalogue, not into the engine fields of
  `Defaults`.
- **Setup providers.** Skills and the Sectile MCP registration are installed
  for the provider of every catalogue engine, on top of the configured extra
  setup providers, so a switch never lands on an unprepared CLI.
- **Capability report.** It describes the project's default engine, as the
  single project engine today. The run record keeps being corrected by the
  existing `/api/activities/{id}/engine` report.
- **ADR.** Moving engines from per-level fields to a named catalogue amends
  the model of #305; the specification stage should propose an ADR.

### Exit condition

All four product questions are answered. The owner confirmed the
clarification is satisfactory on 2026-09-26: no open product question, ready
for the specification.
