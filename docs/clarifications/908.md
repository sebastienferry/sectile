# Clarification #908 - Tauri: show skill completion status in ticket conversations

Ticket: https://github.com/sebastienferry/sectile/issues/908
Branch: `feat/908`

## Round 1 - initial analysis (2026-11-15)

### Request

Sectile Desktop (Tauri) must show, in a ticket conversation, the one reconciled
skill status that the Electron client computes with `primaryStatus`
(`desktop/src/skill-result.mjs`, spec #878): `Working · <skill>`, `Needs your
answer`, `Done · <outcome>` with `Next: <step>`, `Needs verification`, `Could
not finish`, `Stopped`, with the recorded reason, including the successor skill
of a console that went on to run another one (#586). Out of scope: the server,
the local agent's `/desktop/run-result` payload (it already carries `summary`,
`error`, `disconnected`, `successor`), the web UI, desktop notifications, free
conversations and discussions, and the Electron client.

### Code read

- `desktop/src/skill-result.mjs` (`primaryStatus`, `verdict`, `processStatus`,
  `recordedReason`, `withDiagnostics`), `desktop/src/skill-result-refresh.mjs`
  (`skillResultDue`, `skillResultStamp`, `skillEnded`), `desktop/src/main.js`
  (call site, `launchStages` persistence for pickups).
- `specs/878-clear-skill-status/spec.md` (precedence table, scope).
- `desktop-tauri/src/domain/workflow.ts` (`skillResultLabel`, `RunResult`,
  `taskStage`, `nextSkill`), `desktop-tauri/src/domain/execution.ts` (`Run`,
  `waitingSince`, `statusLabel`).
- `desktop-tauri/src/components/ProjectPrompt.tsx` (`ConversationStatus`, the
  `conversation-status-strip` with the `Execution: <run state>` menu, the
  ticket workflow pane and its next-step launch button).
- `desktop-tauri/src/components/WorkflowTask.tsx` (polls `runResult` every 4 s
  and shows `skillResultLabel` under the run heading).
- `desktop-tauri/src-tauri/src/workspace.rs` (`run_result` proxies
  `GET /desktop/run-result`), `internal/agent/agent_desktop.go`
  (`desktopRunResult`: activity/successor carry `summary`, `error`,
  `disconnected`, `waitingSince`).
- `desktop-tauri/tests/workflow.test.ts`, `desktop-tauri/README.md`.

### Current state

- The Tauri `RunResult` type drops `summary`, `error`, `disconnected` and
  `waitingSince`, although the agent already sends them.
- `skillResultLabel` gives a coarse, technical label ("Skill completed · stage
  validation pending", "Skill failure recorded", "Process completed · skill
  result unconfirmed") and is shown only in the ticket workflow panel
  (`WorkflowTask`), not in the conversation strip.
- The conversation strip shows the conversation turn ("Responding", "Ready to
  respond", "Your answer needed") and `Execution: <run state>`; nothing tells
  the outcome of the skill.

### Ambiguities (worst first)

1. **Where the status lives in the conversation strip**: a new indicator beside
   `Execution: <run state>`, or in place of it. #878 settled for Electron that
   two side-by-side indicators disagree and must be merged. (Question 1)
2. **The ticket workflow panel's existing `skillResultLabel` line**: kept, or
   replaced by the reconciled status so both surfaces say the same thing.
   (Question 2)
3. **Sidebar rows**: Electron shows the verdict on the task row too; the ticket
   only names the conversation strip / header. (Question 3)

### Critical dependencies

- None on the server or the agent: `/desktop/run-result` already returns every
  field `primaryStatus` reads. Only the Tauri type must be widened.
- Pickup outcomes (`Done · Now <stage>`) need the stage the task was at when
  the run started; Electron records it client-side (`launchStages` in
  `localStorage`). Tauri must record it the same way, or a pickup always reads
  `Needs verification`.

### Technical choices settled (reversible)

- **Port, do not import**: `desktop-tauri` imports nothing from `desktop/` or
  `shared/` today. The reconciliation is ported to TypeScript as a pure
  function in `desktop-tauri/src/domain/` (e.g. `skill-status.ts`) following
  the #878 precedence table row by row, with the few `runStates` helpers it
  needs (`isSilentSummary`, silence prefix). Labels, details and reasons are
  copied verbatim from Electron (already English).
- **`skillResultLabel` is superseded** by the ported function; its tests are
  rewritten against the new function.
- **Refresh**: port `skillResultDue` / `skillResultStamp` / `skillEnded`
  semantics: read the result on run status or `waitingSince` change, at every
  poll during a 30 s settling window and while an ended skill's console stays
  live (successor detection), otherwise every 30 s (live) / 120 s (ended). The
  conversation turn going from busy to idle also triggers a read. One reader
  per run, shared by the strip and the workflow panel, rather than two pollers.
- **Pickup launch stage**: recorded the first time a live pickup run's result
  is read, persisted in `localStorage` like Electron, pruned with the runs.
- **Next step**: shown as text (`Next: <label>` from `nextSkill`), as Electron
  does; the conversation's existing next-step launch button stays the action.
- **Reason and diagnostics**: the short detail is shown inline; the full reason
  and the diagnostics line (`Execution: … · Skill record: … · Task stage: …`)
  go into the strip's existing execution menu panel and the element's `title`.
- **Free conversations**: `primaryStatus` returns `null` for no task / `discuss`
  / console; the strip then renders exactly as today (plus `Stopping` while a
  requested stop is pending, as in Electron).
- **Docs**: `desktop-tauri/README.md` gets a "Skill status" paragraph;
  `CHANGELOG.md` `[Unreleased]` gets one `Added` line.

### Open product questions (owner: @sebastienferry)

1. **Placement in the conversation strip.** Recommended: the reconciled status
   **replaces** the `Execution: <run state>` summary (e.g. `Done · Clarified ·
   Next: Specify`), the raw run state and diagnostics move into that menu's
   panel. Alternative: add it as a third element and keep `Execution: …`.
2. **Ticket workflow panel.** Recommended: replace the `skillResultLabel` line
   under the run heading in `WorkflowTask` with the same reconciled status, so
   the panel and the strip never disagree. Alternative: leave the panel as is.
3. **Sidebar rows.** Recommended: out of scope here, follow-up ticket for the
   sidebar conversation / ticket rows (they only show a dot and a tooltip
   today). Alternative: include the verdict in the sidebar row tooltip now.

## Round 2 - answers from the owner (2026-11-15)

Answers given interactively in the clarification session.

### Settled choices

1. **Placement (Q1): replace.** The reconciled status replaces the
   `Execution: <run state>` summary of the conversation status strip
   (`ConversationStatus` in `ProjectPrompt.tsx`). The raw run state, the full
   reason and the diagnostics line move into that menu's panel. The left-hand
   turn indicator ("Responding", "Ready to respond", "Your answer needed") is
   unchanged: it describes the conversation turn, not the skill. For a free
   conversation the summary keeps reading `Execution: <run state>`.
2. **Ticket workflow panel (Q2): same status.** The `skillResultLabel` line
   under the run heading in `WorkflowTask.tsx` shows the same reconciled
   status, computed by the same function, so the panel and the strip never
   disagree. `skillResultLabel` is removed.
3. **Sidebar rows (Q3): colour or icon.** The owner chose a third option: the
   sidebar conversation row reflects the verdict visually, without text.

### Assumption recorded for Q3 (reversible)

- Only the sidebar **conversation row** (`ConversationNavigation` in
  `App.tsx`) is concerned: its `conversation-indicator` dot takes a modifier
  per status kind (`working`, `waiting`, `done`, `verify`, `failed`,
  `stopped`, `stopping`), with a colour per kind and a distinct shape or glyph
  for the attention kinds (`verify`, `failed`) so the meaning never rests on
  colour alone. The live pulse stays for `working`. The row's existing `title`
  tooltip and accessible name end with the status label (e.g.
  `Done · Clarified`) instead of the plain run state.
- Free conversations and rows without a ticket skill keep today's indicator.
- The tickets pane rows, the execution queue and the legacy run rows are not
  changed.
- Reading a result per visible sidebar row reuses the throttled refresh
  ported from `desktop/src/skill-result-refresh.mjs`, so the sidebar does not
  multiply server reads; the strip, the panel and the row share one reader
  per run.

### Reversed assumptions

- Round 1 left the sidebar out of scope; it is now in scope as an indicator
  colour/icon only.

### Open product questions

None, subject to the owner confirming the Q3 assumption above.
