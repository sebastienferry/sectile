# #307 - An active MCP run is canceled after 15 minutes of silence

Round 1 - 2026-09-21

## Request restated

A stateful MCP session is bounded by fifteen minutes of *client-to-server silence*
(`defaultMCPSessionTimeout`, `internal/handlers/agent_api.go:23`). When that bound fires, the SDK
closes the session, `SessionRegistry.Close` cancels every run the session adopted, and the agent's
later `finish_run` is rejected. The ticket asks that a live agent which simply spent a long time
compiling, testing or waiting for its owner stop losing its run — and stop silently killing the
rest of an autonomous chain.

Out of scope for this ticket: reviving the ADR 0012 "waiting for input" signal (its only producer
was removed by `openspec/changes/260-remove-claude-hooks`), reinstating the stdio bridge, changing
the run status vocabulary exposed by the tool contract, and the ADR 0007 restart safety net, which
stays as it is.

## Diagnosis confirmed

Everything the ticket asserts checks out in the code:

| Claim | Verified |
| --- | --- |
| Only a POST rearms the idle timer | Yes — `sessionInfo.startPOST`/`endPOST` are the sole callers |
| `SessionTimeout: 0` disables the bound | Yes — `if i.timeout <= 0 { return }` guards both |
| The keepalive that made 15 min harmless is gone | Yes — it lived in the bridge's `ClientOptions{KeepAlive: 60s}`; the recommended declaration is now a direct `{"type":"http"}` |
| `finish_run` is rejected on a canceled run | Yes — `UPDATE ... AND status='running'`, then the mismatch check at `remoterun.go:187` |
| A chain dies silently | Yes — `handBackRun` returns early on any status other than `completed` |
| `finish_run` with `status:"canceled"` would "succeed" | Yes — the `count == 0` branch tolerates a status that already matches |
| Enabling `ServerOptions.KeepAlive` is not a fix | Yes — with `JSONResponse: true` the ping needs a standalone GET the client may never open |

So this is a regression introduced by a documentation-level assumption that stopped holding, not a
badly chosen number. `README.md` and the interface contract both still justify the bound by a
keepalive that no longer exists — they need correcting whatever remedy is chosen.

## Ambiguities, worst first

### A1 — What does an expired-by-silence run look like on the board?

The tool contract accepts `completed`, `failed` and `canceled` only, and `sessions.go:12-15` already
records that the distinction between a reported end and a vanished client lives in the note. If a
silent session must no longer cancel its runs, the run stays `running`. Two readings:

- **Leave it strictly `running`**: nothing on the board changes, the run remains the agent's to
  finish, and a truly dead client leaves an active indicator until the next server restart.
- **Mark it orphaned/expired without changing its status**: needs a carrier — an appended summary
  sentence (`noteRun` already does exactly this), a new column, or the existing `waiting_since`.
  A summary sentence is free; a column is a migration on both engines.

These produce different code, hence the product question Q2.

### A2 — Does the fix remove the bound or move it?

`SessionTimeout: 0` hands the SDK no bound at all. Sectile can then either keep no inactivity
notion whatsoever (only DELETE, a broken connection and restart end a session), or carry its own
timer in `SessionRegistry` so a silence still *marks* the session without cancelling its runs. The
ticket's "correctif de fond" describes the second; the "palliatif" describes neither. Q1/Q3.

### A3 — How wide is the `finish_run` rewrite?

Allowing the owner to overwrite a run canceled by disconnection is safe as the ticket argues, but
the predicate matters: any `canceled` run, or only one carrying `disconnectNote`? The first lets an
agent silently undo a deliberate cancel from the UI; the second is narrow but couples the DB layer
to a string owned by `taskmcp`. Q4.

## Critical dependencies

- **No migration, no external service.** The palliative is a single environment variable; the deep
  fix is contained in `internal/handlers/agent_api.go`, `internal/taskmcp/sessions.go` and, for the
  rewrite complement, `internal/db/remoterun.go`.
- **Dual-store constraint (#296/#302/#304).** If Q2 is answered with a new column, it must be
  written for SQLite *and* PostgreSQL. A summary sentence avoids that entirely.
- **`.env.sample`, `README.md`, `docs/contracts/server-agent-v1.md`** all document the fifteen
  minutes and the vanished bridge keepalive; they are part of the deliverable, not an afterthought.
- **ADR 0007** is the decision being amended. Its "keepalive tuned against clients that idle
  legitimately" consequence is precisely what broke. Q5.
- **Log verification** the ticket asks for (no POST on `/mcp` between `start_run` and expiry) could
  not be performed from the worktree: it needs the deployment's access logs. The code path is
  nonetheless conclusive on its own, so this stays a corroboration, not a blocker.

## Resolved technical decisions (reversible, settled here)

- **D1 — `ServerOptions.KeepAlive` stays off.** Confirmed by reading `streamable.go`: with
  `JSONResponse: true` the ping travels on the standalone SSE stream a JSON-only client never
  opens, so it fails faster than the current bug.
- **D2 — Server-side, not client-side.** Asking every agent to ping is not enforceable: third-party
  clients (Claude Desktop, Codex, Antigravity) are exactly the population ADR 0007 set out to make
  visible without requiring managed skills.
- **D3 — Adoption semantics are unchanged.** A run reused through `SECTILE_RUN_ID` is still not
  adopted (`server.go:220-226`); nothing in this ticket touches that.
- **D4 — Clean closures keep cancelling.** A DELETE or a broken connection remains immediate
  cancellation with the existing note. Only *silence* changes meaning.
- **D5 — Test location.** `internal/taskmcp/sessions_test.go` for the registry behaviour, plus a
  `remoterun` test if Q4 is answered yes. `internal/agent/agent_keepalive_test.go` is a different
  transport and is left alone.

## Open product questions

1. **Which remedy ships in #307?**
   - (a) Palliative only: raise `SECTILE_MCP_SESSION_TIMEOUT` to ~4h in the deployment and fix the
     documentation. Zero code, ships today, leaves a dead client's run active up to 4h.
   - (b) Deep fix: `SessionTimeout: 0`, inactivity carried by Sectile, silence no longer cancels.
   - (c) **(b) plus the `finish_run` rewrite complement** — *recommended*. (b) alone still loses the
     three runs already canceled and any run canceled before the deploy; the complement makes those
     recoverable and, as the ticket notes, replaying the hand-back on a corrected status unblocks
     the chain rather than duplicating a step.
   *Recommendation: (c), with the documentation correction in the same PR.*

2. **What should a run whose session went silent show?**
   *Recommendation: stay `running`, with one appended summary sentence via the existing `noteRun`
   naming the silence and its duration.* Visible to an operator, no migration, no new status, and it
   keeps the run the agent's to finish.

3. **What inactivity bound, once Sectile owns it?**
   *Recommendation: a `SECTILE_MCP_SESSION_TIMEOUT` still honoured but reinterpreted as "mark, do not
   cancel", defaulting to 4h.* The alternative — no bound at all — makes the ADR 0007 restart sweep
   the only reaper, which is acceptable but leaves the session list growing on a long-lived server.

4. **How narrow is the `finish_run` rewrite?**
   *Recommendation: owner-only, and only on a run whose summary carries the disconnect note.* A
   cancel a human made from the UI must not be silently overwritten by a late agent.

5. **Does this warrant an ADR?**
   *Recommendation: yes — a short amendment to ADR 0007 rather than a new ADR*, since it changes one
   of its stated consequences (silence as a proxy for death) without changing its decision.

Questions 1 to 5 are for the ticket owner (@sebastienferry).
