## Round 1 — analysis (2026-10-02)

### Restated request and scope

Make Sectile faster by serving frequently repeated reads from an in-memory cache instead of recomputing or re-reading them on every request. The ticket names a solution but neither the slowness it should fix nor a target. Any shared cache service (Redis or similar), sticky sessions and changes to the tracker sync pacing are out of scope: accepted ADR 0030 makes PostgreSQL the only shared infrastructure. A client-side cache library in the web app is also out of scope unless the owner redirects the ticket there.

### Verified findings

- The ticket has a title only: no description, no comments, no parent returned by Sectile.
- **Several replicas are a decided feature.** ADR 0030 (`docs/adrs/0030-several-server-replicas-share-one-postgresql.md`, Accepted) runs PostgreSQL replicas active/active: every replica serves every request, with "no Redis, no session store, no sticky sessions". SQLite remains a single-instance store. A process-local cache is therefore only consistent across replicas if something invalidates it on every replica.
- **Invalidation signal.** On PostgreSQL, `internal/db/bus.go` relays events between replicas through `LISTEN/NOTIFY` on `sectile_events`. The messages carry names and identifiers only (the receiver reads the task back from the database). Only `Handler.BroadcastEvent` publishes on it (`internal/handlers/handlers.go:216-229`), from six call sites, with these event types: `task_updated`, `agent_connected`, `agent_disconnected`, `agent_step_status` and the local-only `agent_pty_output`. **Project, settings, credential and activity writes do not publish anything**, so a cache of those could not be invalidated across replicas today without new events.
- **Existing caches.** The only data caches are three process-local `sync.Map` caches with a ten-minute TTL for Jira metadata: `jiraFieldCache` (`internal/trackerapi/jira_fields.go:27`), `jiraPriorityCache` and `jiraCreatePriorityCache` (`internal/trackerapi/jira_priority.go:41,351`). OAuth app configuration is deliberately "never cached" (`internal/db/oauthapps.go:75`). `go.mod` has no cache library (no LRU, ristretto or singleflight). No API handler issues an ETag or answers `304`. Hashed static assets are already `immutable` (`cmd/server/main.go:384-391`).
- **Hot read paths found in the code.**
  - Web board (`web/src/context/AppContext.tsx`): it polls `/api/tasks`, `/api/activities` and `/api/activities/stats` every 3 s while jobs run and every 25 s otherwise (around lines 2059-2172). In addition, every `task_updated` SSE event makes **every open browser refetch all three lists in full** (lines 2013-2030). The fan-out is (browsers × updates × 3 full list reads).
  - Task list query: `GetTasksInScope` (`internal/db/db.go:1700`) is one unbounded SELECT. For each row without a stored `external_url`, `computeExternalURLUnsafe` (db.go:1113-1126, called around line 1944) loads the task's project with a separate query: an N+1 on the most-polled endpoint.
  - Desktop: a 2 s timer (`desktop/src/main.js:832`) calls `refresh()` (line 746), which reads `api.runs()` and `api.status()` from the **local agent**, not the server, then the visible skill results.
  - Other polls: auto-sync status every 30 s, agent status every 30 s plus SSE, admin stats every 15 s, macro realign every 5 s / 30 s.
  - Trackers: auto-sync reads incrementally every minute (at least 30 s), with a full read every 30 min and a ten-minute pause on rate limits, shared by all replicas (`internal/db/autosync.go`). No GitHub conditional request (ETag) is used.
- **Measurement.** `/metrics` exposes `sectile_http_request_duration_seconds` per handler and method (`internal/metrics/metrics.go:54-66`), charted per controller and replica in `deploy/grafana/sectile.json`. There is no DB query timing, no pprof and no tracing. A before/after comparison can only rely on the per-handler latency histogram today.
- No ADR, spec, openspec change or earlier clarification designs an application data cache.

### Ambiguities (worst first)

1. **What is slow.** The candidates lead to unrelated code: (a) the board's task and activity lists (server-side cache of query results, or removal of the N+1); (b) the SSE fan-out of three full refetches per event per browser (a client change, not a server cache); (c) tracker API calls (a response cache with conditional requests); (d) the Desktop poll, which mostly hits the local agent, not the server.
2. **What is cached.** Rendered list responses per scope and filter, or individual entities (projects, settings, tracker metadata) looked up while building them. The two need different keys and invalidation.
3. **Staleness across replicas.** With several replicas, a write served by replica A leaves replica B's cache stale until it expires or is invalidated. Either a short TTL with accepted staleness, or invalidation through the event bus, which needs new events for projects and settings.
4. **Success criterion.** No latency target or affected surface is given, so "done" is undefined.

### Critical dependencies

- ADR 0030: any cache must stay correct with several PostgreSQL replicas, and adding shared infrastructure would need a new ADR.
- Event bus coverage: invalidating project, settings or activity data on other replicas requires publishing new bus events from those writes.
- Baseline: only `sectile_http_request_duration_seconds`. Without production numbers, the hot path is inferred from the code, not measured.
- No migration, external service or third-party limit is identified for a process-local cache.

### Technical choices resolved by convention (reversible)

- Process-local, standard library only (`sync.Map` or a mutex-guarded map with a TTL), in the style of `jiraFieldCache`. No new dependency and no shared cache service.
- Correctness first: a cached value must never outlive a write on the same replica, so writes on the same instance invalidate synchronously. Cross-replica freshness follows the answer to Q2.
- Credentials and OAuth configuration stay uncached, as `oauthapps.go` already decides.
- Success is measured on the existing per-handler histogram (p50/p95 before and after) for the endpoints in scope.

### Open product questions

1. **Which slowness should this fix?** *Recommendation:* the web board's task list (`GET /api/tasks`) and activity endpoints, the most polled server reads. First remove the per-row project lookup with a process-local project cache keyed by ID, then decide whether to cache the list results themselves. If you have observed a specific slow screen or the p95 per handler in Grafana, name it and it replaces this recommendation.
2. **How stale may a cached read be on another replica?** *Recommendation:* no visible staleness for tasks and activities, so those are invalidated through the existing `task_updated` event. For projects and settings, a short TTL (30 s) is acceptable, or new bus events if they must be immediate. Choose between "30 s TTL is fine" and "must be immediate".
3. **Is the SSE fan-out in scope?** Every `task_updated` event triggers three full list reloads in every browser. Reducing it (update the changed task in place, or debounce the refetch) is a client change, not a cache. *Recommendation:* out of scope here, and filed as a separate ticket. Say if you want it included.
4. **What target counts as done?** *Recommendation:* a measurable reduction of p95 on the endpoints chosen in Q1 (for example at least 30 %) on the existing histogram, with no stale data visible after a write. Alternatively, "no regression and fewer queries per request" if no production baseline can be collected.

## Round 2 - answers from the owner (2026-10-02)

The owner answered the four Round 1 questions interactively.

### Settled decisions

1. **Scope (Q1): the board's task and activity lists.** The work targets the server reads behind `GET /api/tasks`, `/api/activities` and `/api/activities/stats`. The first step is to remove the per-row project lookup (`computeExternalURLUnsafe`, `internal/db/db.go:1113-1126`) with a process-local project cache keyed by project ID. Caching the list results themselves is allowed if it can meet decision 2. Tracker API calls and the Desktop poll are out of scope.
2. **Staleness (Q2): tasks immediate, the rest 30 s.** Cached task data (and any cached list containing tasks) must never be stale after a write, on any replica: it is invalidated on the writing replica synchronously and on the others through the existing `task_updated` bus event. Projects and settings may be served from a cache with a TTL of at most 30 s on other replicas; the writing replica invalidates its own entry at once. Activities follow the task rule (immediate). Activity writes do not all publish a bus event today, so activity results are cached only where an invalidating event exists or is added; otherwise they stay uncached. The specification decides which.
3. **SSE fan-out (Q3): separate ticket.** The three full list reloads per `task_updated` event per browser stay unchanged in #486. A follow-up ticket is to be filed for it (update the changed task in place or debounce the refetch).
4. **Done criterion (Q4): fewer queries, no regression.** No production baseline or latency target is required. Done means fewer database queries per request on the endpoints in scope, shown by tests (for example a query count on `GetTasksInScope` that no longer grows with the number of rows), with no stale task or activity visible after a write and no latency regression on `sectile_http_request_duration_seconds`.

### Reversed or narrowed assumptions

- Round 1 recommended a p95 reduction of at least 30 %. Replaced by "fewer queries, no regression" (decision 4).
- Round 1 offered tasks and activities "invalidated through the existing `task_updated` event". Narrowed: that event covers tasks only, so activity caching depends on an invalidating event (decision 2).

### Technical choices kept from Round 1

Process-local, standard library only, in the style of `jiraFieldCache`. No new dependency, no shared cache service (ADR 0030). Credentials and OAuth configuration stay uncached. On SQLite (single instance) only same-process invalidation applies.

### Open questions

None. All four product questions are answered, and the owner confirmed the clarification is satisfactory (2026-10-02). The owner files the SSE fan-out ticket.
