# Clarification #691: republish every pending framing copy

Ticket: https://github.com/sebastienferry/sectile/issues/691 (child of macro M-11).
Branch: `feat/691`, fast-forwarded to `origin/main` (`09fa967c`) before this round.

## Round 1 - initial report (2026-10-06)

### Restated request

The roadmap gains one action, next to the existing "labels à pousser" button, that
republishes in a single gesture the Jira comment copy of the framing of every epic whose
copy is pending, signed by the person who starts it, through the tracker activity queue.
Out of scope: changing how a single framing save or the single "Republier" button works,
publishing anything on GitHub, GitLab, local projects, `M-<n>` keys or roadmap projects'
epics, replaying copies automatically at startup (rejected by ADR 0046 for signing reasons),
and the MCP tools.

### Neighbouring features

- **Single republish** (`POST …/macros/{key}/framing-mirror`): refuses with a reason when the
  macro is not eligible, otherwise queues one `epic_framing` activity with `Force: true`,
  signed by the acting user. A failure marks that activity `failed` and stores
  `framing_mirror_error` on the macro, which the panel shows as "échec" with "Republier".
- **Pending labels push** (`push_horizons`): GET lists the pending epics (the count drives the
  button, shown only when > 0), POST queues **one** activity for the whole batch. The batch
  runs the epics sequentially, lists each failure as a `❌` step, and ends `completed` even
  when some epics failed.

### Ambiguities, worst first

1. **One activity per epic, or one activity for the batch.** The criteria say "queues one
   `epic_framing` write per epic". Read literally, that is N activities. The queue worker starts
   every tracker op in its own goroutine with no concurrency limit (`db.go:4214`), so a roadmap
   with 60 pending epics would fire 60 concurrent Jira writes, protected only by three retries
   on 429, and would flood the Activities list with 60 rows. The other reading follows
   `push_horizons`: one activity that writes the epics one after another, one step per epic.
   The two readings produce different code and a different Activities list → **Q2**.
2. **Include the todos copy (`epic_todos`).** Left open by the ticket → **Q1**. The two copies
   share everything (`macroCopyPart`), so adding todos costs little code, but it changes the
   scope: the todos copy is also allowed on a GitHub milestone (as a description block), so
   including it makes the action appear on GitHub projects too, where the ticket says
   "GitHub milestones are never written" for the framing.
3. **What "skipped" counts.** An epic with an empty framing and no comment yet is already
   reported as up to date by `macroCopyStatus`; it is not "pending". Settled below (D3).

### Critical dependencies

- No migration: the pending state is computed from the existing `framing_mirror_*` columns
  (migration 45). Epics framed before #636 have `hash == "" && ref == ""` and read as pending
  when their framing is non-empty, which is exactly the population this ticket targets.
- No tracker read is needed to list pending epics: the state is a comparison of local hashes,
  unlike `push_horizons`, which reads the epics from Jira.
- Jira only, through `MarkedCommentWriter`; the writes use the starter's personal Jira
  credential (#482). A starter without a token gets every write refused, reported through the
  existing missing-token chain (#645).
- Jira rate limits: relevant only with per-epic concurrent activities (ambiguity 1).

### Settled technical choices (reversible, from existing code)

- **D1: Route.** `GET` and `POST /api/projects/{id}/macros/framing-mirror` (and the `epics/`
  alias, as `push-horizons`), project-level, beside the per-macro route. GET lists the pending
  eligible macros; POST queues the work and answers 202.
- **D2: Eligibility.** Reuse `eligibilityOf` with the framing `macroCopyPart`: GitHub,
  GitLab, local projects, `M-<n>` keys and roadmap projects' epics are never listed nor
  written. On a non-Jira project the button never appears (GET returns an empty list).
- **D3: Counts.** "Queued" counts the pending eligible epics handed to the queue. "Skipped"
  counts the eligible epics whose framing is empty and that have no comment yet (ticket
  criterion 3); they are excluded from the list and no comment is created for them. Both counts
  are computed from local state at POST time and returned in the 202 answer, so the toast can
  say them without waiting for the writes.
- **D4: No force.** The bulk writes with `force=false`: an epic saved, and so copied, between
  the listing and the write is skipped as "déjà à jour" instead of being rewritten.
- **D5: Per-epic failure.** Whatever the answer to Q2, each failure is stored on its macro
  (`framing_mirror_error`), so the panel of that epic shows "échec" and its own "Republier", as
  the single republish does; the activity output lists `KEY : error` per failed epic.
- **D6: Button.** Shown next to "labels à pousser", only when the pending count is > 0,
  re-read on the same triggers (project change, `activeJobCount`); after POST the web refreshes
  the activities, as `pushPendingHorizons` does.
- **D7: Strings.** New labels go into `web/src/locales/planning.ts` in both catalogs (FR and
  EN), matching the neighbouring `pendingPushes` entries.
- **D8: Changelog.** User-visible: one line under `## [Unreleased]` / `Added`.

### Product questions

- **Q1: Todos copy in the same action?**
  - (a) **Recommended:** framing only, as the title says. The todos copy keeps its per-epic
    "Republier"; a follow-up ticket can add it to the action (or a second button) if needed.
    This keeps the action Jira-only and the criteria unchanged.
  - (b) Both copies in one action, with separate counts per copy. The action then also shows
    on GitHub projects, for the milestones' todos block.
- **Q2: One activity per epic, or one for the batch?**
  - (a) **Recommended:** one `epic_framing` batch activity, signed by the starter, writing
    the epics sequentially, one step per epic (`✅ KEY` / `❌ KEY : error`), ending `failed`
    only when no epic was written (same rule as `refusalOrFailures`). No concurrent burst on
    Jira, one row in Activities, per-epic failures still visible on each epic's panel (D5).
    The criterion becomes "queues one write for every epic, in one activity".
  - (b) One `epic_framing` activity per epic, as the criterion literally says, each with its
    own status. Needs a concurrency cap on tracker ops (new) to avoid a burst of Jira writes,
    and fills Activities with one row per epic.

## Round 2 - answers from the owner (2026-10-06)

Answered interactively in the clarification session.

### Settled choices

- **Q1: framing only.** The action republishes the framing copy (`epic_framing`) and nothing
  else. The todos copy (`epic_todos`) keeps its per-epic "Republier"; adding it to a bulk
  action is left to a follow-up ticket. The action therefore stays Jira-only: on GitHub,
  GitLab and local projects the GET list is empty and the button never shows (D2).
- **Q2: one activity for the batch.** POST queues a single `epic_framing` batch activity,
  signed by the starter, that writes the pending epics one after another, as `push_horizons`
  does. Each epic adds one step (`✅ KEY` or `❌ KEY : error`); the activity ends `failed`
  only when no epic was written, with the `refusalOrFailures` rule so a missing personal
  token is named (#645). Each failure is also stored on its macro (D5), so the epic's panel
  shows "échec" and its own "Republier".

### Reversed or reworded assumptions

- Ticket criterion 1, "queues one `epic_framing` write per epic", is read as "writes every
  pending epic, in one queued activity". No concurrency cap on tracker ops is needed.
- The new batch op is a kind of its own (for example `epic_framing_bulk`), so the existing
  single `epic_framing` op and its `Force: true` stay untouched; the batch writes with
  `force=false` (D4).

### Final scope

- `GET`/`POST /api/projects/{id}/macros|epics/framing-mirror`: GET lists the pending eligible
  macros; POST answers 202 with `{queued, skipped, activity}`, `skipped` counting the eligible
  epics with an empty framing and no comment yet (D3). POST with nothing pending queues no
  activity and says so.
- Roadmap button beside "labels à pousser", shown when the pending count is > 0, FR and EN
  strings (D6, D7); the toast states the queued and skipped counts and the web refreshes the
  activities.
- Tests: eligibility (Jira only, `M-<n>`, roadmap projects' epics excluded), skip of empty
  never-copied epics, partial failure recorded per macro, all-failed batch ends `failed`,
  signing by the starter.
- Changelog: one `Added` line under `## [Unreleased]` (D8).
