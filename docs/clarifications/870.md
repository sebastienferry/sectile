# Clarification #870: Jira refuses a comment whose Markdown has inline code inside bold text (HTTP 400 INVALID_INPUT)

## Round 1 (2026-10-26)

Report: `docs/clarifications/870.md` on `feat/870` (worktree `.tasks/worktrees/issue-870`, from `main` at `43229200`). Committed, not pushed (`pushStageCommits` off). No pull request at this stage (`prCreationStage` is `implemented`).

### Restated request and scope

The Markdown-to-ADF converter must never emit a text node that carries the `code` mark together with any mark other than `link`, so that Jira accepts comments, stage reports and issue descriptions holding inline code inside bold, italic or struck-through text. Separately, when the report note of `transition_stage` cannot be posted to the tracker, the agent that called `transition_stage` must learn it instead of seeing a plain success.

Out of scope: the other converter defect tracked in #252 (a list item continued on the next line), the other ADF mark combinations that Jira tolerates today, retrying a failed report automatically, and the GitHub and GitLab trackers (they receive Markdown, not ADF).

### Defect confirmed in the code

- `internal/trackerapi/adf.go:400` (`parseInline`): inline code is emitted with `append(marks, code)`, so it inherits every mark of the enclosing span. `**a `b` c**` yields a text node `b` with `[strong, code]`; `*…*`, `_…_` and `~~…~~` produce `[em, code]` and `[strike, code]` the same way. The ADF schema allows `code` only alongside `link`, and Jira rejects the whole document with `INVALID_INPUT`.
- The converter feeds four Jira writes (`internal/trackerapi/jira.go:231`, `391`, `610`, `631`): issue creation, issue description update, comment creation and comment update. The fix therefore also repairs descriptions pushed with such a span, not only comments.
- `parseInline` is the only place that creates marked text nodes, so the fix has a single site.

### Why the stage report fails silently

- `transition_stage` (`internal/taskmcp/server.go:448`) commits the stage, enqueues a `TrackerOpStage` job (`internal/db/stage.go:160`) and returns at once with `"trackerSync": "queued"`.
- The job (`runStageOp`, `internal/db/trackerops.go:885`) applies the tracker status and label, then posts the note through `AddTaskCommentAs`. A refused note is not swallowed there: the activity gets the step `❌ Rapport d'étape non consigné sur …` and ends in error (`trackerops.go:974`).
- So the failure is recorded on the task's activity, but only after the MCP call has returned. The agent has no way to learn it, and the skills tell it to trust the tool result. `add_comment`, by contrast, posts synchronously (`PostTaskCommentBy`) and returns the tracker error.

### Dependencies

- No migration, no new service. Jira's ADF validation is the only third-party constraint.
- The skills (`clarify-issue` and siblings) read the `transition_stage` result; any new field in it should be documented in the tool description so agents act on it.

### Technical choices settled (reversible)

1. **Drop, do not split.** A node carrying `code` keeps only `code` and `link`; `strong`, `em` and `strike` are dropped for that node. Splitting cannot help: the span is a single run of code text, and there is no valid ADF way to make it bold. The surrounding bold text keeps its mark. This matches what the ticket proposes first.
2. **Fix at the emit site.** The filter goes into the `code` branch of `parseInline`, not into a post-pass over the whole document, since no other code path creates marked text.
3. **Round trip.** `ADFToMarkdown` needs no change: it renders `code` + `link` correctly already. A Jira comment read back shows `` `pe` `` without the surrounding `**` for that span only, which is acceptable.
4. **Tests.** `internal/trackerapi/adf_test.go` gets cases for `` **a `b` c** ``, `` *a `b` c* ``, `` ~~a `b` c~~ `` and `` [a `b` c](url) `` (link kept), plus a check that no emitted node anywhere in a document carries `code` with a non-`link` mark.

### Open product question

**Q1. How should `transition_stage` tell its caller that the report note was refused by the tracker?**

The stage itself is applied either way: it is committed before the tracker is called, and the ticket does not ask to undo it.

- **A (recommended).** `transition_stage` waits a bounded time (around 15 s) for its tracker job and returns its outcome: `trackerSync` becomes `done`, `failed` (with the tracker error, and the stage still applied) or `queued` when the job is still running at the deadline. The call is not an MCP error, so an agent does not retry the transition; the skills are told to post the note with `add_comment` when `trackerSync` is `failed`. This is the closest to "like `add_comment` does".
- **B.** `transition_stage` stays fully asynchronous; `get_task` exposes the last failed tracker sync of the task (`trackerSyncError`), and the skills read it after a transition. No waiting, but one more call, and a race with a job still running.
- **C.** Post the note synchronously before committing the stage, and refuse the transition when the note is refused. The stage and its report then never diverge, but a tracker outage blocks the workflow, and the status and label sync stays asynchronous anyway.

## Round 2 - answers from the owner (2026-10-26)

Report: `docs/clarifications/870.md` on `feat/870`, committed after round 1 (`a75d95b8`). Not pushed (`pushStageCommits` off).

### Settled decisions

- **Q1 → A, bounded wait.** `transition_stage` keeps committing the stage first, then waits a bounded time (around 15 s) for the tracker job it queued and returns that job's outcome in `trackerSync`:
  - `done`: status, label and report note all reached the tracker;
  - `failed`: the job ended in error; the result carries the tracker error, and the stage stays applied locally;
  - `queued`: the job was still running at the deadline, as today.
- The call is not an MCP error when `trackerSync` is `failed`, so an agent never retries the transition itself.
- The tool description of `transition_stage` documents the three values.
- The shared skill contract `internal/skills/fragments/contracts/transition.md` tells the skills to read `trackerSync`: on `failed`, report the error and post the note with `add_comment`, so the report still reaches the ticket once the converter accepts it.
- The converter fix of round 1 is unchanged: a node carrying `code` keeps only `code` and `link`.

### Reversed assumptions

None. Round 1 assumed the stage stays applied whatever happens to the note; option A keeps that.

### Remaining reversible choices for the specification

- The exact wait (15 s is the proposal) and whether the wait observes the job through the activity row or a completion signal of the job queue: settled by the specification after reading the job worker.
- Option A applies to `transition_stage` only. `noRepositoryChange` transitions take the same path, since they enqueue the same job.
