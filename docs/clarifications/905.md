# Clarification #905: Tauri: queue follow-up messages while an agent is responding

## Round 1 (2026-11-15)

Report: `docs/clarifications/905.md` on `feat/905` (ticket [#905](https://github.com/sebastienferry/sectile/issues/905)), committed on the task branch.

### Restated request and scope

In the Sectile Desktop (Tauri) conversation view, a user can type and submit follow-up messages while the agent is still responding; they are held in a visible, per-conversation queue and sent one at a time, in order, each after the preceding turn completes, without interrupting the active turn. An idle conversation keeps its immediate-send behaviour, and a queued message can be removed before it is sent.

Out of scope: scheduled or offline delivery, the "new prompt" composer (`ProjectPrompt`, which has no active turn), the Electron desktop and the web client, steering the active turn (injecting a message into the turn in progress), and any change to the Go conversation engine.

### Files read

- `desktop-tauri/src/lib/conversation-controller.ts`: per-conversation `ConversationController` (module-level map, 20-entry eviction of non-retained controllers), `send()` refuses while `busy`/`pending`/`error`/`readOnly` and never replays a lost acknowledgement, polling every 750 ms while busy.
- `desktop-tauri/src/lib/conversation.ts`: `ConversationSnapshot` (`busy`, `readOnly`, `approvals`, `events`), `TurnOptions`, `controlConversation` actions.
- `desktop-tauri/src/components/ProjectPrompt.tsx`: `Conversation` composer (submit refused while `busy`, Send button hidden behind the Interrupt button while busy, Esc interrupts, `TurnSettings` disabled while busy), `ConversationStatus`, Stop discussion (`stopRun`).
- `desktop-tauri/src-tauri/src/agent.rs`: `read_conversation` / `control_conversation` forward to the agent.
- `internal/agent/agent_conversation.go`: message admission, `busy` handling, `next` buffer, end-of-turn dispatch, shutdown handling.
- `desktop-tauri/README.md`, `desktop-tauri/CHANGELOG.md`, `desktop-tauri/AGENTS.md`.

### Neighbouring behaviour already in the code

The Go agent already accepts a message while a turn is in progress, but with semantics that do not match this ticket:

- **Claude Code**: the message is written to the running turn's stdin and *joins the current turn* (steering, as in the Claude Code terminal). It changes the active response instead of waiting for it.
- **Codex / agy**, or Claude without a live stdin: the message is appended to `run.conversation.next`; at the end of the turn *all* buffered messages are joined with a blank line and sent as a single next turn.
- In both cases the message is written to the transcript as a `user` event immediately, so it cannot be distinguished from sent messages nor removed.

The Tauri UI currently never uses this path: it refuses to submit while `busy`.

### Ambiguities, worst first

1. **Where the queue lives.** Server-side (reuse `next`) vs. client-side in the Tauri controller. Server-side would merge messages into one turn, join the active Claude turn, and make removal impossible, which contradicts three acceptance criteria. → Resolved technically below (client-side).
2. **What happens to the queue when the turn does not complete normally**: user interrupt (Esc / Interrupt), Stop discussion (conversation becomes read-only), turn ending in an error. Auto-dispatch after an interrupt would immediately start a turn the user just tried to stop. → Product question Q2.
3. **Application restart / companion restart.** An in-memory queue is lost when the app quits; persisting it requires a storage decision. → Product question Q1.
4. **Runtime language.** The ticket asks to "preserve the existing French runtime UI", but the Tauri UI was translated to English (commit `b7daa94e`); the strings around the composer are English today. → Product question Q4.
5. **Steering vs. queueing.** Claude users may expect the terminal behaviour (message joins the current turn). → Product question Q3.

### Critical dependencies

- No Go, Rust or API change is required for the recommended design: the client only calls the existing `control_conversation` `message` action when the snapshot reports `busy: false`.
- Race with the server: if the client dispatches just as another client (web, CLI) starts a turn, the agent will join/merge the message server-side. Accepted as an edge case; the client only dispatches after a fresh snapshot shows the conversation idle.
- `ConversationController` eviction: a controller holding a non-empty queue must count as `retained`, otherwise switching across more than 20 conversations could drop it.

### Reversible technical choices (settled from the code)

- **Client-side queue in `ConversationController`**, one per conversation ID. Queues are therefore isolated per conversation by construction, survive switching views inside the running app, and a controller with queued items is `retained`.
- **Enqueue rule**: a submit goes to the queue when the conversation is busy (`snapshot.busy` or a local send/read is pending) *or* the queue is not empty (preserves order when a turn closes as the user hits Enter). Otherwise it is sent immediately as today.
- **Dispatch rule**: the head of the queue is sent only when a fresh snapshot shows `busy: false`, no pending approval/question, not read-only, no controller error, agent available, and the queue is not paused. One message per turn, never merged. The turn options (model, mode) are captured at enqueue time.
- **Send failure**: the failed message stays at the head of the queue, marked failed with the error text, and the queue pauses. It is never retried automatically (consistent with the existing "a lost acknowledgement is ambiguous, never replay" rule). The user retries or removes it explicitly.
- **Disconnection** (agent unavailable): the queue pauses dispatch and resumes on reconnection, once a refreshed snapshot shows the conversation idle.
- **Pending approval or question**: the queue waits; queued messages never answer an approval.
- **UI**: while busy, Enter and a dedicated "queue" button add the draft to the queue next to the existing Interrupt button; queued messages are rendered between the transcript and the composer with a distinct "queued" style, their position, and a remove button. A queued message is not editable in place (remove and retype).
- **Limits**: same 32,000-character limit per message; a cap of 20 queued messages per conversation.
- **Coverage**: Vitest unit tests on the controller (order, one per turn, removal, isolation between two controllers, failure keeps the message and pauses, no double send) and a UI test on the composer.
- **Docs**: `desktop-tauri/README.md` conversation section and `desktop-tauri/CHANGELOG.md` `[Unreleased]`, plus the root `CHANGELOG.md` if the release includes the Tauri app.

### Product questions (owner)

- **Q1: Restart.** What happens to queued messages when Sectile Desktop quits or restarts?
  *Recommended*: memory only; queued messages are lost on quit. They are never sent behind the user's back after a restart. (Alternative: persist and restore them paused.)
- **Q2: Interrupt, stop and error.** After a user interrupt, a Stop discussion, or a turn ending in an error, what does the queue do?
  *Recommended*: the queue **pauses** and is kept visible; the user resumes it with one action (or removes items). On a read-only (stopped) conversation the items stay visible and can be copied back into the clipboard or removed. (Alternative: continue automatically after an error, or clear the queue on interrupt.)
- **Q3: Steering.** Should Claude conversations also offer "send into the current turn" (the terminal behaviour the agent already supports)?
  *Recommended*: no, queueing only in this ticket; steering can be a follow-up.
- **Q4: Language.** The acceptance criterion says to preserve the French runtime UI, but the Tauri UI is now in English. Which language do the new strings use?
  *Recommended*: English, the language that surface speaks today, per `AGENTS.md`; the criterion is read as "do not translate existing strings as a side effect".

## Round 2 - answers from the owner (2026-11-15)

Report: `docs/clarifications/905.md` on `feat/905`, committed on the task branch. Answers given interactively by the owner, who then confirmed the clarification is satisfactory.

### Settled decisions

- **Q1: Restart.** The queue lives in memory only. Queued messages are lost when Sectile Desktop quits or restarts, and are never sent after a restart.
- **Q2: Interrupt, stop and error.** After a user interrupt (Esc / Interrupt), a Stop discussion, or a turn ending in an error, the queue **pauses** and stays visible. The user resumes it with one action or removes items. On a stopped (read-only) conversation, queued messages stay visible and can be copied or removed; they are never sent.
- **Q3: Steering.** Queueing only. No "send into the current turn" action in this ticket; steering may become a follow-up ticket.
- **Q4: Language.** New UI strings are in English, the language the Tauri surface speaks today. The acceptance criterion "preserve the existing French runtime UI" is read as "do not translate existing strings as a side effect".

### Reversed assumptions

- The ticket's "preserve the existing French runtime UI" no longer describes the Tauri app (translated to English in `b7daa94e`); replaced by Q4 above.

### Settled scope (unchanged from Round 1)

Client-side, per-conversation queue in `ConversationController`; one queued message per turn, in order, dispatched only when a fresh snapshot shows the conversation idle with no pending approval; send failures stay at the head of the queue, marked failed, and pause it without automatic retry; disconnection pauses dispatch; 20 messages per conversation at most; no Go, Rust or API change. Documentation: `desktop-tauri/README.md` and `desktop-tauri/CHANGELOG.md`.

### Open questions

None. Exit condition met: the owner confirmed the clarification.
