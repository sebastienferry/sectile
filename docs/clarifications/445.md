## Round 1 (2026-09-25)

### Original request

> Add selection of macro. Make a bigger screen. Left part: description. Right
> side: Project. Remove destination. Offer option to rewrite the story or
> clarify the story right after the save.

### Restated request and scope

Rework the web "Quick add" modal (`QuickAddModal`) into a wider two-column
dialog (title and description on the left, the project and ticket metadata on
the right) that lets the user attach the new ticket to a macro, no longer
shows the "Destination" chooser, and, once the ticket is saved, offers to
rewrite it as a user story or to launch its clarification.

Out of scope: the desktop app's own quick add (`desktop/src/main.js`,
`quickAdd()`), the full task detail modal, the macro view's "TODO line becomes
a story" flow, and any change to what the `rewrite_story` and `clarify` skills
do.

### Code read

- `web/src/components/QuickAddModal.tsx`: the whole modal: `max-w-lg` single
  column; title, 3-row textarea, project select (saved-view aware, #387),
  "Destination" (GitHub / Sectile buttons driving `source`), issue type,
  status, priority, sprint, labels.
- `web/src/context/AppContext.tsx`: `createTask` (POST `/api/tasks`, success
  toast linking the new ticket, #432), `fetchProjectMacros`,
  `createStoryFromMacroTodo`, the `/tasks/{id}/macro` attachment call, `runSkill`.
- `web/src/components/TaskDetailModal.tsx`: how `clarify` and `rewrite_story`
  are triggered today and how a rewrite proposal is reviewed then applied
  (`rewriteActivity`, "apply" writes the description).
- `internal/models/models.go`: `CreateTaskRequest` already carries `parentKey`.
- `internal/db/db.go`: `CreateTaskAs`: `parentKey` is only stored locally; the
  source defaults to the project's tracker when empty.
- `internal/db/macros.go`: `SetTaskMacro` writes the parent locally **and**
  enqueues a `set_parent` tracker op (this is what attached #445 to M-7).
- `internal/taskmcp/server.go`: MCP `create_task` accepts `parentKey`.
- `desktop/src/main.js`: separate quick add, confirmed out of scope.

### Findings

1. **A `parentKey` sent to POST `/api/tasks` never reaches the tracker.**
   `CreateTaskAs` stores it in the local row only; the tracker parent (GitHub
   milestone, Jira epic) is written by `SetTaskMacro` through a queued
   `set_parent` op. Passing `parentKey` alone would show the ticket under the
   macro on Sectile's board and nowhere else, and the next tracker pull would
   detach it again.
2. **The "Destination" chooser is already inconsistent.** It only offers GitHub
   and Sectile, even for a Jira project, and the server falls back to the
   project's tracker when `source` is empty. Removing it means `source` is
   always the project's tracker.
3. **A rewrite is a proposal, not an edit.** `rewrite_story` produces an output
   that the detail modal shows with "apply" / "dismiss"; nothing writes the
   description until the user applies it. Any post-save "rewrite" option needs
   a place where that proposal can be reviewed.
4. **Macros are per project.** `fetchProjectMacros(projectId)` returns the
   project's macros (with a closed flag); the list must reload when the
   project changes and the selection reset.
5. The modal's labels are hard-coded French strings ("Projet *",
   "Type de ticket", "Destination"…); new strings go through
   `translations.ts` like `t.quickAdd.*`.

### Ambiguities (worst first)

1. **What "offer option right after the save" looks like**: a step shown by
   the modal once the ticket exists, choices ticked before saving and run
   automatically, or actions in the success toast. Each is a different flow
   and different acceptance criteria. → Question 1.
2. **Where a rewrite proposal is reviewed**: in the ticket's detail modal
   (existing apply/dismiss) or applied automatically. → Question 2.
3. **Whether a local-only ticket remains possible** once "Destination" is
   gone, for a project backed by GitHub or Jira. → Question 3.
4. **What goes in the right column**: only the project (and macro), or all the
   metadata fields. → Question 4.

### Critical dependencies

- The tracker attachment to a macro goes through the `set_parent` tracker op
  (`SetTaskMacro`); no migration, no new tracker capability.
- `rewrite_story` and `clarify` are launched through the existing
  `POST /api/tasks/{id}/run-skill`; `clarify` depends on the project's
  execution mode (local agent or server runner), which is unchanged.

### Reversible technical choices (resolved)

- **Macro attachment:** the ticket is created, then attached with the same
  path as `SetTaskMacro` so the tracker receives the parent. Whether this is
  done by the web client (second call) or by the server when POST
  `/api/tasks` carries `parentKey` is decided in the specification; a failed
  attachment leaves the ticket created and is reported as a warning, like
  `createStoryFromMacroTodo` does.
- **Macro field:** optional, defaults to "none", lists the chosen project's
  open macros, reloads and resets on project change, and is pre-selected with
  the macro the board is currently filtered on when it belongs to the chosen
  project.
- **Size:** a wider dialog (in the order of `max-w-4xl`) with a taller
  description editor; the two columns stack on a narrow window.
- **Description editor:** reuse the existing `MarkdownEditor` if it fits the
  modal, otherwise a taller textarea; a presentation detail for the spec.
- Every other existing field and behaviour (saved-view project choice #387,
  labels seeded from the view, the toast link #432, Escape and backdrop
  dismissal) is kept.

### Product questions (asked to the owner)

1. **Post-save option.** Recommended: once saved, the modal turns into a short
   confirmation step ("#N created") with three actions: *Rewrite as a user
   story*, *Clarify*, *Done*. Alternatives: checkboxes before saving that run
   automatically; actions in the success toast.
2. **Rewrite review.** Recommended: *Rewrite* opens the new ticket's detail
   modal and launches `rewrite_story` there, so the proposal is reviewed and
   applied with the existing controls. Alternative: apply the rewrite to the
   description automatically.
3. **Destination.** Recommended: the ticket always goes to the project's own
   tracker; creating a local-only ticket in a tracker-backed project is no
   longer possible from quick add. Alternative: keep a discreet "local only"
   switch.
4. **Right column.** Recommended: left = title + description; right = project,
   macro, type, status, priority, sprint, labels. Alternative: right = project
   and macro only, the other fields under the description.
