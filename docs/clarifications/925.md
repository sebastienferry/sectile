### Existing behavior

The Tauri header shows the next-step button for a task with an available skill and launch callback when no related run is active. Agent unavailability disables it. `nextSkill` already handles finished/unknown stages, missing project configuration, missing skills and PR recovery.

ConversationStatus renders the Workflow chip in both writable and read-only layouts. A read-only history has no editable input, but retains the status strip and history options. Ending a skill or a turn does not by itself define a closed conversation. Archive is a separate action; archived histories can offer Start over. Stop discussion uses stopRun and exists while the run is active, including an idle active provider session.

The legacy Electron post-success offer has different eligibility: it requires a successful completed skill and explicitly rejects read-only histories. It is not the Tauri header's eligibility contract and must not be copied into this change.

### Settled technical choices

- Target Tauri; retain the existing nextSkill resolution and onLaunchSkill launch path rather than introduce a second workflow resolver or backend endpoint.
- Reuse compact icon-button presentation, chevron, accessible name and tooltip, consistent with #922; do not depend on its exceptional oversized primary styling.
- Preserve existing availability: hide when no eligible next step or another task run is active; disable for unavailable agent. Existing workflow status explains the stage; no new disabled-action design is proposed.
- Rendering the action must not submit, clear or modify the controlled draft, folders or context. Reuse established launch behavior; do not introduce draft transfer to a successor as an incidental feature.
- Retain archive and start-over semantics and existing launch error handling.
- Implementation should cover lifecycle visibility, keyboard/accessibility, next-skill callback and unavailable states using existing UI test conventions; update root and Tauri changelogs and relevant README documentation.

### Essential product questions (owner)

1. What does closed mean? Recommended: the selected conversation is read-only history and no task run is active; show the action beside its Workflow chip even though the editable composer is absent, preserving existing archived-history behavior. Alternative: include an idle writable conversation once its skill execution finishes, which changes the current active-run eligibility rule. A turn merely becoming idle must not be assumed to mean closed.
2. Should the header next-step button remain? Recommended: retain it and add the contextual action beside Workflow in the agreed closed state. Alternative: move the header action there for that state, so only one next-step control is shown.
3. Include a close action beside Workflow? Recommended: move the existing Stop discussion action there while the conversation run is active, preserving its current behavior/guards, and keep Archive in the header when inactive. Alternative: defer the optional close action entirely. An idle-only close action or a new graceful-close operation would require different acceptance criteria; no close action is proposed for read-only history.

### Dependencies and risks

No migration, new service or third-party API is required by the proposed placement change. Live task/project eligibility, current run activity and agent availability remain prerequisites. #922 is a visual consistency reference rather than a required workflow dependency. The product definition of closed and whether Stop is the intended close action are blocking decisions.
