## Restated request and scope

Let a project take the bodies of its workflow skills from an external,
versioned catalogue — a "marketplace" — instead of only from the templates
compiled into Sectile. Sectile would fetch a skill pack, resolve it as a new
baseline underneath the project's own edits, and install the result into the
agent skill directories exactly as it does today.

Out of scope as read here: changing the wording of the built-in skills;
changing where the rendered files are installed (that is #106, and
`ResolveLocations` already answers it); publishing Sectile's own skills *to* a
marketplace; and any change to the stage graph itself (`new → clarified →
specified → implemented → reviewed → finished`).

## Verified findings

What a skill actually is today, read in this checkout:

- **The catalogue is Go.** `StageSkills` in `internal/db/skilltemplates.go:52`
  is a hardcoded slice of ten entries. Each carries both metadata (`ID`,
  `DirName`, `Command`, `FromStage`, `ToStage`, `Scope`, `Mode`) and the prose
  (`goal`, `readFirst`, `stepsBody`, `guard`, `report`) as Go string literals.
- **A SKILL.md is assembled, not copied.** `RenderSkillContent`
  (`skilltemplates.go:601`) prepends the frontmatter and the stage line, then
  appends three generated contracts — `renderTaskAccessContract`,
  `renderSessionTitleContract`, `renderTicketTransitionContract` — the last of
  which is built from `FromStage`/`ToStage`/`Scope` and the skill id. Two
  skills compose others: `renderPickupSteps` (`skilltemplates.go:577`) inlines
  the bodies of `clarify`, `specify`, `implement` and `adjust`. Two more render
  a different body per SDD framework (`specifyFrameworkBody`).
- **There is already one override layer.** `project_skills` (SQLite, per
  project, `internal/db/projectskills.go:21`) stores edited content and an
  execution mode. `EffectiveProjectSkills` (`projectskills.go:139`) resolves
  built-in template → project override, then appends the project's pull request
  policy. `ListProjectSkillEditor` diffs the resolved content against
  `ProjectSkillTemplates(framework)` to compute `isCustom`, and against the
  file on disk to compute `diverged`.
- **The ids and directory names are load-bearing.** `models.SkillDirNames`
  (`internal/models/models.go:511`) maps a skill id to its directory, which is
  also its slash command. The runner invokes a step as `/<dirName> {issueKey}`
  (`skillSlashPrompt`, `internal/runner/runner.go:217`) and locates the file
  through `installedSkillPath` (`runner.go:187`), which tries
  `.claude/commands/<dirName>.md` first and then the five agent conventions in
  `models.SkillAgentDirs`. A pack that renamed a step would break dispatch.
- **Installation is agent-side and already has a precedent for fetching.**
  `WriteProjectSkillToRepo` calls the local agent with `sync_config`
  (`projectskills.go:345`); `InstallSpecFramework` (`internal/db/specframework.go:72`)
  calls it with `spec_install`, runs an external toolchain in the user's
  environment and records the outcome as an activity
  (`skillId: install_spec_framework`). A marketplace fetch has the same shape.
- **`.claude/skills` is not a marketplace.** Nothing in the repository mentions
  a marketplace, a plugin manifest or a remote skill index today; `grep -ri
  marketplace` over the tree is empty. This ticket introduces the concept.

## Ambiguities, worst first

1. **What "a marketplace" is.** Three readings lead to three different
   implementations: the Claude Code plugin convention (a git repo carrying
   `.claude-plugin/marketplace.json`, i.e. reuse of an existing ecosystem but
   Claude-shaped, while Sectile supports codex, agy, gemini, cursor and vibe);
   a Sectile-native index (a manifest that maps Sectile skill ids to bodies,
   so the packs are guaranteed to fit the stage contract); or simply a git URL
   or local path pointing at a directory of `SKILL.md` files. The manifest
   format, the fetch mechanism and the validation rules all differ.
2. **What a pack is allowed to contain.** Bodies for the ten known stage ids
   only, or new skills with their own ids and stages? The first is a third
   layer in an existing precedence chain. The second turns the workflow graph
   into data — `StageSkills`, `SkillDirNames`, the stage enum in
   `transition_stage`, the runner's dispatch and the interface's stage columns
   all assume a fixed set — and is a different, much larger ticket.
3. **How much of a pack's text Sectile still owns.** The transition contract,
   the task-access contract and the pull request policy are what keep an
   autonomous agent attached to the protocol. If a pack could replace them, a
   third-party skill could silently stop calling `transition_stage`.
4. **Where the source is configured, and at which granularity.** The catalogue
   is global today, the overrides are per project. A marketplace source could
   be a global setting, a per-project pin, or both (a list of sources
   globally, a selected pack + version per project).
5. **Whether a fetched pack applies by itself.** A skill body is a prompt
   executed by a CLI that Sectile launches with permissions skipped
   (`--dangerously-skip-permissions`, `internal/runner/runner.go:531`).
   Auto-applying a remote update and requiring an explicit per-skill review are
   both defensible, and they produce different acceptance criteria.
6. **Offline and reproducibility.** Whether a pack is vendored into the
   project (cached on disk, pinned by version or commit) or refetched on each
   install decides whether a run is reproducible and whether Sectile works
   without network.

## Critical dependencies

- **#202 — "Extract the skill bodies out of Go into embedded markdown
  fragments"** (still `to_clarify`). It is the natural prerequisite: once the
  prose is a set of markdown fragments with a documented layout, a marketplace
  pack is the same layout fetched from elsewhere, and the golden-file safety
  net it proposes is also what would protect a pack swap. Doing #267 first
  means designing the pack format twice.
- **#106 — "Create a feature to distribute skills"** (still `to_clarify`).
  It is the other half of the same subject, in the opposite direction:
  distributing Sectile's skills to the agent's global folder. The two should
  agree on one vocabulary (source, pack, install) rather than inventing two.
- **#239 — round-based clarification** touches the body of the same skill this
  ticket would let a pack replace. Whichever lands second inherits a conflict.
- **No external service exists.** There is no Sectile marketplace to source
  from; the first pack would have to be Sectile's own catalogue published
  somewhere. Which repository hosts it, and who may publish to it, is not
  decided by this ticket.
- **Agent availability.** Fetching happens in the user's environment through
  the local agent, like `spec_install`. A project whose agent is offline
  cannot install a pack; the existing `callAgent` failure path applies.

## Questions

1. **Which marketplace format?** *Recommended: a Sectile-native manifest
   (`sectile-skills.json` at the root of a git repository or a local
   directory), listing packs by name and version, each mapping Sectile skill
   ids to body fragments.* The Claude plugin convention would tie an
   agent-agnostic product to one CLI, and a bare directory of `SKILL.md` files
   cannot express versions, framework variants or which stage a file belongs
   to. A Sectile manifest can still be published in a repository that also
   carries a Claude marketplace file, so this does not close that door.
2. **May a pack add new skills, or only replace the bodies of the ten known
   ones?** *Recommended: bodies only, for this ticket.* A pack declares ids
   from `models.SkillDirNames`; unknown ids are reported and ignored rather
   than installed. Adding steps means making the stage graph data, which
   deserves its own ticket. If the answer is "new skills too", the acceptance
   criteria change substantially and #202 becomes a hard prerequisite.
3. **Global source, per-project selection, or both?** *Recommended: both —
   sources are declared once in the global settings, and each project pins one
   pack and one version.* That mirrors how `AIProvider` and `SpecFramework`
   already fall back from project to settings
   (`resolveSpecFrameworkTarget`, `specframework.go:17`), and keeps one machine
   from needing the same source registered per project.
4. **Does a fetched pack apply automatically, or after an explicit review?**
   *Recommended: fetch is explicit and per project, and the diff is shown in
   the existing skills editor before it becomes effective.* `SkillsView`
   already renders custom-vs-default and diverged-on-disk states; a
   "marketplace" origin is a third badge, not a new screen. Silent remote
   updates to a prompt that runs with permissions skipped is the one
   irreversible mistake here.

## Settled scope and assumptions

Resolved from the existing code and conventions; these do not need an answer
to start:

- **Precedence becomes built-in default → marketplace pack → project edit.**
  The project's own edited content stays the highest layer, so installing a
  pack never destroys a hand-written skill. `DefaultContent` in
  `SkillEditorEntry` becomes the *resolved baseline* (pack when one is pinned),
  which keeps `isCustom` meaningful: "custom" goes on meaning "differs from
  what this project would otherwise get".
- **Sectile keeps generating the contracts.** A pack supplies goal, read-first,
  steps, guard and report. The frontmatter, the stage line,
  `renderTaskAccessContract`, `renderSessionTitleContract`,
  `renderTicketTransitionContract` and the pull request policy stay Sectile's
  and are appended to whatever the pack provides, exactly as
  `adjustmentCustomContent` already reconciles an edited `adjust` skill with
  its contract.
- **Ids, `DirName` and the slash command stay Sectile's.** A pack cannot rename
  a step: `installedSkillPath` and `skillSlashPrompt` resolve by `DirName`, and
  `transition_stage` validates against a fixed stage enum.
- **Fetching is an agent operation**, with a new action alongside `sync_config`
  and `spec_install`, recorded as an activity the way
  `recordSpecFrameworkActivity` does. The server does not reach the network
  itself; the workstation does.
- **Storage reuses `project_skills`**, with a `source` column (`builtin`,
  `marketplace`, `user`) and the pack coordinates, rather than a parallel
  table. The resolution code already reads one row per (project, skill).
- **Framework variants survive.** A pack may ship `steps.openspec.md` and
  `steps.speckit.md` for `specify` and `refine_macro`; when it ships only one,
  the built-in variant is kept for the other framework rather than the pack
  being rejected.
- **Composition is re-derived, not shipped.** `pickup` and `pickup_issues` keep
  being assembled from the resolved bodies of `clarify`, `specify`, `implement`
  and `adjust`, so a pack that updates one stage cannot leave the batch run
  behind.

## Round 2 — 2026-09-19, decision on question 1

**Decided by the owner: the Claude official plugin-marketplace format.** Question 1
is closed; the Sectile-native manifest recommended in round 1 is dropped.

### The format, as verified

Read from the marketplaces installed on this workstation
(`~/.claude/plugins/marketplaces/`), not from memory:

- A marketplace is a git repository with `.claude-plugin/marketplace.json` at its
  root: `{name, owner, metadata, plugins[]}`. Each entry is
  `{name, source, description, version}`, `source` being a path relative to the
  repository (`./plugins/be/cli-tools`).
- A marketplace is registered by source kind, not by revision:
  `{"source":"github","repo":"owner/repo"}`, `{"source":"git","url":"..."}`, or a
  local path. `known_marketplaces.json` records `installLocation`, `lastUpdated`
  and an optional `autoUpdate` boolean — **no commit is pinned**.
- A plugin is a directory carrying `plugin.json` (accepted both at its root and
  under `.claude-plugin/`) with `{name, version, description}` and optional keys
  such as `"skills": "./skills/"`.
- A skill is `skills/<name>/SKILL.md`, frontmatter `name` + `description`, free
  body. Sibling files (`references/`) are allowed. Plugins may also ship
  `commands/`, `agents/`, `hooks/` and `.mcp.json`.
- Installed plugin skills and commands are **namespaced** `<plugin>:<name>`.

### What this changes

1. **Sectile reads the format; it does not shell out to `claude`.** The layout is
   plain JSON and directories. Driving `claude plugin marketplace add` would make
   every project depend on the Claude CLI — including codex, agy, gemini, cursor
   and vibe projects — and would put the content under `~/.claude/plugins/`,
   where Sectile controls neither the refresh nor the revision. Sectile fetches
   the marketplace repository into its own cache and parses
   `.claude-plugin/marketplace.json` itself. The pack body is then rendered into
   every agent convention exactly as today, so the feature stays agent-agnostic
   even though the format is Claude's.
2. **Stage mapping by directory name, with no extension to the schema.** The
   official format has no notion of a Sectile stage. A plugin's skill directory
   name is matched against `models.SkillDirNames` — `clarify-issue`,
   `specify-issue`, `code-issue`, `adjust-issue`, `handoff-issue`, `create-pr`,
   `pickup-issue`, `pickup-issues`, `rewrite-story`, `refine-macro`. Anything
   else is reported and ignored. This is the only mapping that requires adding
   nothing to the official manifest.
3. **Namespacing must not reach dispatch.** Because plugin content is invoked as
   `/<plugin>:<name>`, the marketplace is treated as a *source of body text*, not
   as an install channel. Sectile keeps writing the repository's own
   `.claude/commands/<dirName>.md` and agent skill directories, so
   `skillSlashPrompt` (`internal/runner/runner.go:217`) and `installedSkillPath`
   (`runner.go:187`) are unchanged and `/clarify-issue` keeps resolving.
4. **A pack ships a whole `SKILL.md`, not fragments.** This revises round 1: a
   pack no longer supplies goal / read-first / steps / guard / report separately.
   Sectile appends its generated contracts — task access, session title,
   transition, pull request policy — to the pack body, the way
   `adjustmentCustomContent` already reconciles an edited `adjust` skill with its
   contract. This also **weakens the #202 dependency**: a whole-file pack does
   not need the embedded-fragment layout, so #267 no longer has to wait on it.
5. **The format carries no framework variant.** `specify` and `refine_macro`
   render differently for `openspec` and `speckit`, and a plugin can only ship one
   `specify-issue/SKILL.md`. Resolution: a marketplace publishes one plugin per
   framework when it needs both, and a pack that supplies a single `specify-issue`
   applies to both frameworks, the built-in variant being kept for whichever the
   pack omits.
6. **The format carries no revision pin, and its own default is auto-update.**
   Reproducibility therefore becomes Sectile's responsibility: record the resolved
   commit SHA on the project when a pack is applied, alongside the plugin
   `version`, and re-resolve only on an explicit action. Sectile does not adopt
   `autoUpdate`.

### Questions still open

2. **May a pack add new skills, or only replace the ten known bodies?**
   *Recommended, unchanged: bodies only.* The directory-name mapping above makes
   this the natural reading — an unmatched skill directory has no stage to attach
   to. Allowing new steps means turning the stage graph into data and is its own
   ticket.
3. **Global source, per-project selection, or both?** *Recommended, unchanged:
   both* — marketplaces registered once in the global settings (mirroring
   `known_marketplaces.json`), each project pinning one plugin, one version and
   one resolved commit.
4. **Automatic apply or explicit review?** *Recommended, and now sharper: explicit.*
   The official format defaults to `autoUpdate: true`; Sectile should not, because
   a skill body is a prompt executed by a CLI it launches with
   `--dangerously-skip-permissions` (`internal/runner/runner.go:531`). Fetch is an
   explicit per-project action and the diff is shown in the existing skills editor
   before it becomes effective.
