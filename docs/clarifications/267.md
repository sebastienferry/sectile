## Restated request and scope

Let a project take the bodies of its workflow skills from an external,
versioned catalogue — a "marketplace" — instead of only from the templates
compiled into Sectile. Sectile would fetch a skill pack, resolve it as a new
baseline underneath the project's own edits, and install the result into the
agent skill directories exactly as it does today.

Out of scope as read here: changing the wording of the built-in skills;
changing where the rendered files are installed (that is #106, and
`ResolveLocations` already answers it); publishing Sectile's own skills *to* a
marketplace; and any change to the stage graph itself (`new → clarified →
specified → implemented → reviewed → finished`).

## Verified findings

What a skill actually is today, read in this checkout:

- **The catalogue is Go.** `StageSkills` in `internal/db/skilltemplates.go:52`
  is a hardcoded slice of ten entries. Each carries both metadata (`ID`,
  `DirName`, `Command`, `FromStage`, `ToStage`, `Scope`, `Mode`) and the prose
  (`goal`, `readFirst`, `stepsBody`, `guard`, `report`) as Go string literals.
- **A SKILL.md is assembled, not copied.** `RenderSkillContent`
  (`skilltemplates.go:601`) prepends the frontmatter and the stage line, then
  appends three generated contracts — `renderTaskAccessContract`,
  `renderSessionTitleContract`, `renderTicketTransitionContract` — the last of
  which is built from `FromStage`/`ToStage`/`Scope` and the skill id. Two
  skills compose others: `renderPickupSteps` (`skilltemplates.go:577`) inlines
  the bodies of `clarify`, `specify`, `implement` and `adjust`. Two more render
  a different body per SDD framework (`specifyFrameworkBody`).
- **There is already one override layer.** `project_skills` (SQLite, per
  project, `internal/db/projectskills.go:21`) stores edited content and an
  execution mode. `EffectiveProjectSkills` (`projectskills.go:139`) resolves
  built-in template → project override, then appends the project's pull request
  policy. `ListProjectSkillEditor` diffs the resolved content against
  `ProjectSkillTemplates(framework)` to compute `isCustom`, and against the
  file on disk to compute `diverged`.
- **The ids and directory names are load-bearing.** `models.SkillDirNames`
  (`internal/models/models.go:511`) maps a skill id to its directory, which is
  also its slash command. The runner invokes a step as `/<dirName> {issueKey}`
  (`skillSlashPrompt`, `internal/runner/runner.go:217`) and locates the file
  through `installedSkillPath` (`runner.go:187`), which tries
  `.claude/commands/<dirName>.md` first and then the five agent conventions in
  `models.SkillAgentDirs`. A pack that renamed a step would break dispatch.
- **Installation is agent-side and already has a precedent for fetching.**
  `WriteProjectSkillToRepo` calls the local agent with `sync_config`
  (`projectskills.go:345`); `InstallSpecFramework` (`internal/db/specframework.go:72`)
  calls it with `spec_install`, runs an external toolchain in the user's
  environment and records the outcome as an activity
  (`skillId: install_spec_framework`). A marketplace fetch has the same shape.
- **`.claude/skills` is not a marketplace.** Nothing in the repository mentions
  a marketplace, a plugin manifest or a remote skill index today; `grep -ri
  marketplace` over the tree is empty. This ticket introduces the concept.

## Ambiguities, worst first

1. **What "a marketplace" is.** Three readings lead to three different
   implementations: the Claude Code plugin convention (a git repo carrying
   `.claude-plugin/marketplace.json`, i.e. reuse of an existing ecosystem but
   Claude-shaped, while Sectile supports codex, agy, gemini, cursor and vibe);
   a Sectile-native index (a manifest that maps Sectile skill ids to bodies,
   so the packs are guaranteed to fit the stage contract); or simply a git URL
   or local path pointing at a directory of `SKILL.md` files. The manifest
   format, the fetch mechanism and the validation rules all differ.
2. **What a pack is allowed to contain.** Bodies for the ten known stage ids
   only, or new skills with their own ids and stages? The first is a third
   layer in an existing precedence chain. The second turns the workflow graph
   into data — `StageSkills`, `SkillDirNames`, the stage enum in
   `transition_stage`, the runner's dispatch and the interface's stage columns
   all assume a fixed set — and is a different, much larger ticket.
3. **How much of a pack's text Sectile still owns.** The transition contract,
   the task-access contract and the pull request policy are what keep an
   autonomous agent attached to the protocol. If a pack could replace them, a
   third-party skill could silently stop calling `transition_stage`.
4. **Where the source is configured, and at which granularity.** The catalogue
   is global today, the overrides are per project. A marketplace source could
   be a global setting, a per-project pin, or both (a list of sources
   globally, a selected pack + version per project).
5. **Whether a fetched pack applies by itself.** A skill body is a prompt
   executed by a CLI that Sectile launches with permissions skipped
   (`--dangerously-skip-permissions`, `internal/runner/runner.go:531`).
   Auto-applying a remote update and requiring an explicit per-skill review are
   both defensible, and they produce different acceptance criteria.
6. **Offline and reproducibility.** Whether a pack is vendored into the
   project (cached on disk, pinned by version or commit) or refetched on each
   install decides whether a run is reproducible and whether Sectile works
   without network.

## Critical dependencies

- **#202 — "Extract the skill bodies out of Go into embedded markdown
  fragments"** (still `to_clarify`). It is the natural prerequisite: once the
  prose is a set of markdown fragments with a documented layout, a marketplace
  pack is the same layout fetched from elsewhere, and the golden-file safety
  net it proposes is also what would protect a pack swap. Doing #267 first
  means designing the pack format twice.
- **#106 — "Create a feature to distribute skills"** (still `to_clarify`).
  It is the other half of the same subject, in the opposite direction:
  distributing Sectile's skills to the agent's global folder. The two should
  agree on one vocabulary (source, pack, install) rather than inventing two.
- **#239 — round-based clarification** touches the body of the same skill this
  ticket would let a pack replace. Whichever lands second inherits a conflict.
- **No external service exists.** There is no Sectile marketplace to source
  from; the first pack would have to be Sectile's own catalogue published
  somewhere. Which repository hosts it, and who may publish to it, is not
  decided by this ticket.
- **Agent availability.** Fetching happens in the user's environment through
  the local agent, like `spec_install`. A project whose agent is offline
  cannot install a pack; the existing `callAgent` failure path applies.

## Questions

1. **Which marketplace format?** *Recommended: a Sectile-native manifest
   (`sectile-skills.json` at the root of a git repository or a local
   directory), listing packs by name and version, each mapping Sectile skill
   ids to body fragments.* The Claude plugin convention would tie an
   agent-agnostic product to one CLI, and a bare directory of `SKILL.md` files
   cannot express versions, framework variants or which stage a file belongs
   to. A Sectile manifest can still be published in a repository that also
   carries a Claude marketplace file, so this does not close that door.
2. **May a pack add new skills, or only replace the bodies of the ten known
   ones?** *Recommended: bodies only, for this ticket.* A pack declares ids
   from `models.SkillDirNames`; unknown ids are reported and ignored rather
   than installed. Adding steps means making the stage graph data, which
   deserves its own ticket. If the answer is "new skills too", the acceptance
   criteria change substantially and #202 becomes a hard prerequisite.
3. **Global source, per-project selection, or both?** *Recommended: both —
   sources are declared once in the global settings, and each project pins one
   pack and one version.* That mirrors how `AIProvider` and `SpecFramework`
   already fall back from project to settings
   (`resolveSpecFrameworkTarget`, `specframework.go:17`), and keeps one machine
   from needing the same source registered per project.
4. **Does a fetched pack apply automatically, or after an explicit review?**
   *Recommended: fetch is explicit and per project, and the diff is shown in
   the existing skills editor before it becomes effective.* `SkillsView`
   already renders custom-vs-default and diverged-on-disk states; a
   "marketplace" origin is a third badge, not a new screen. Silent remote
   updates to a prompt that runs with permissions skipped is the one
   irreversible mistake here.

## Settled scope and assumptions

Resolved from the existing code and conventions; these do not need an answer
to start:

- **Precedence becomes built-in default → marketplace pack → project edit.**
  The project's own edited content stays the highest layer, so installing a
  pack never destroys a hand-written skill. `DefaultContent` in
  `SkillEditorEntry` becomes the *resolved baseline* (pack when one is pinned),
  which keeps `isCustom` meaningful: "custom" goes on meaning "differs from
  what this project would otherwise get".
- **Sectile keeps generating the contracts.** A pack supplies goal, read-first,
  steps, guard and report. The frontmatter, the stage line,
  `renderTaskAccessContract`, `renderSessionTitleContract`,
  `renderTicketTransitionContract` and the pull request policy stay Sectile's
  and are appended to whatever the pack provides, exactly as
  `adjustmentCustomContent` already reconciles an edited `adjust` skill with
  its contract.
- **Ids, `DirName` and the slash command stay Sectile's.** A pack cannot rename
  a step: `installedSkillPath` and `skillSlashPrompt` resolve by `DirName`, and
  `transition_stage` validates against a fixed stage enum.
- **Fetching is an agent operation**, with a new action alongside `sync_config`
  and `spec_install`, recorded as an activity the way
  `recordSpecFrameworkActivity` does. The server does not reach the network
  itself; the workstation does.
- **Storage reuses `project_skills`**, with a `source` column (`builtin`,
  `marketplace`, `user`) and the pack coordinates, rather than a parallel
  table. The resolution code already reads one row per (project, skill).
- **Framework variants survive.** A pack may ship `steps.openspec.md` and
  `steps.speckit.md` for `specify` and `refine_macro`; when it ships only one,
  the built-in variant is kept for the other framework rather than the pack
  being rejected.
- **Composition is re-derived, not shipped.** `pickup` and `pickup_issues` keep
  being assembled from the resolved bodies of `clarify`, `specify`, `implement`
  and `adjust`, so a pack that updates one stage cannot leave the batch run
  behind.

## Round 2 — 2026-09-19, decision on question 1

**Decided by the owner: the Claude official plugin-marketplace format.** Question 1
is closed; the Sectile-native manifest recommended in round 1 is dropped.

### The format, as verified

Read from the marketplaces installed on this workstation
(`~/.claude/plugins/marketplaces/`), not from memory:

- A marketplace is a git repository with `.claude-plugin/marketplace.json` at its
  root: `{name, owner, metadata, plugins[]}`. Each entry is
  `{name, source, description, version}`, `source` being a path relative to the
  repository (`./plugins/be/cli-tools`).
- A marketplace is registered by source kind, not by revision:
  `{"source":"github","repo":"owner/repo"}`, `{"source":"git","url":"..."}`, or a
  local path. `known_marketplaces.json` records `installLocation`, `lastUpdated`
  and an optional `autoUpdate` boolean — **no commit is pinned**.
- A plugin is a directory carrying `plugin.json` (accepted both at its root and
  under `.claude-plugin/`) with `{name, version, description}` and optional keys
  such as `"skills": "./skills/"`.
- A skill is `skills/<name>/SKILL.md`, frontmatter `name` + `description`, free
  body. Sibling files (`references/`) are allowed. Plugins may also ship
  `commands/`, `agents/`, `hooks/` and `.mcp.json`.
- Installed plugin skills and commands are **namespaced** `<plugin>:<name>`.

### What this changes

1. **Sectile reads the format; it does not shell out to `claude`.** The layout is
   plain JSON and directories. Driving `claude plugin marketplace add` would make
   every project depend on the Claude CLI — including codex, agy, gemini, cursor
   and vibe projects — and would put the content under `~/.claude/plugins/`,
   where Sectile controls neither the refresh nor the revision. Sectile fetches
   the marketplace repository into its own cache and parses
   `.claude-plugin/marketplace.json` itself. The pack body is then rendered into
   every agent convention exactly as today, so the feature stays agent-agnostic
   even though the format is Claude's.
2. **Stage mapping by directory name, with no extension to the schema.** The
   official format has no notion of a Sectile stage. A plugin's skill directory
   name is matched against `models.SkillDirNames` — `clarify-issue`,
   `specify-issue`, `code-issue`, `adjust-issue`, `handoff-issue`, `create-pr`,
   `pickup-issue`, `pickup-issues`, `rewrite-story`, `refine-macro`. Anything
   else is reported and ignored. This is the only mapping that requires adding
   nothing to the official manifest.
3. **Namespacing must not reach dispatch.** Because plugin content is invoked as
   `/<plugin>:<name>`, the marketplace is treated as a *source of body text*, not
   as an install channel. Sectile keeps writing the repository's own
   `.claude/commands/<dirName>.md` and agent skill directories, so
   `skillSlashPrompt` (`internal/runner/runner.go:217`) and `installedSkillPath`
   (`runner.go:187`) are unchanged and `/clarify-issue` keeps resolving.
4. **A pack ships a whole `SKILL.md`, not fragments.** This revises round 1: a
   pack no longer supplies goal / read-first / steps / guard / report separately.
   Sectile appends its generated contracts — task access, session title,
   transition, pull request policy — to the pack body, the way
   `adjustmentCustomContent` already reconciles an edited `adjust` skill with its
   contract. This also **weakens the #202 dependency**: a whole-file pack does
   not need the embedded-fragment layout, so #267 no longer has to wait on it.
5. **The format carries no framework variant.** `specify` and `refine_macro`
   render differently for `openspec` and `speckit`, and a plugin can only ship one
   `specify-issue/SKILL.md`. Resolution: a marketplace publishes one plugin per
   framework when it needs both, and a pack that supplies a single `specify-issue`
   applies to both frameworks, the built-in variant being kept for whichever the
   pack omits.
6. **The format carries no revision pin, and its own default is auto-update.**
   Reproducibility therefore becomes Sectile's responsibility: record the resolved
   commit SHA on the project when a pack is applied, alongside the plugin
   `version`, and re-resolve only on an explicit action. Sectile does not adopt
   `autoUpdate`.

### Questions still open

2. **May a pack add new skills, or only replace the ten known bodies?**
   *Recommended, unchanged: bodies only.* The directory-name mapping above makes
   this the natural reading — an unmatched skill directory has no stage to attach
   to. Allowing new steps means turning the stage graph into data and is its own
   ticket.
3. **Global source, per-project selection, or both?** *Recommended, unchanged:
   both* — marketplaces registered once in the global settings (mirroring
   `known_marketplaces.json`), each project pinning one plugin, one version and
   one resolved commit.
4. **Automatic apply or explicit review?** *Recommended, and now sharper: explicit.*
   The official format defaults to `autoUpdate: true`; Sectile should not, because
   a skill body is a prompt executed by a CLI it launches with
   `--dangerously-skip-permissions` (`internal/runner/runner.go:531`). Fetch is an
   explicit per-project action and the diff is shown in the existing skills editor
   before it becomes effective.

## Settled design

This section is the contract the specification works from. It supersedes the
round-1 recommendations wherever the two differ.

### Source and format

- A source is a **Claude plugin marketplace**: a git repository (or local
  directory) with `.claude-plugin/marketplace.json` at its root. The three
  registration kinds of the official format are supported — `github` + `repo`,
  `git` + `url`, and a local path.
- Sectile **parses the format itself** and never invokes the `claude` CLI, so a
  project running codex, agy, gemini, cursor or vibe can use a marketplace just
  as a Claude project can.
- Within a marketplace, the unit a project selects is **one plugin**. Its skills
  are read from `skills/<name>/SKILL.md`, per `plugin.json` (`"skills"` when
  present, `./skills/` otherwise).
- Sectile **does not adopt `autoUpdate`**. When a pack is applied, the project
  records the marketplace name, the plugin name, the plugin `version` and the
  **resolved commit SHA**. Nothing re-resolves without an explicit action, which
  is what makes a run reproducible and lets Sectile work offline from its cache.

### What a pack may contain

- Bodies for the ten workflow skills, identified by **skill directory name**
  matched against `models.SkillDirNames`: `clarify-issue`, `specify-issue`,
  `code-issue`, `adjust-issue`, `handoff-issue`, `create-pr`, `pickup-issue`,
  `pickup-issues`, `rewrite-story`, `refine-macro`.
- Any other skill directory is **reported and ignored** — never installed,
  never silently dropped. A pack supplying none of the ten is an error worth
  surfacing, not an empty success.
- A pack supplies **whole `SKILL.md` bodies**, not fragments. It carries no
  stage metadata: ids, `DirName`, `FromStage`/`ToStage`, `Scope` and the slash
  command remain Sectile's, so `/clarify-issue` keeps resolving through
  `skillSlashPrompt` and `installedSkillPath` unchanged.
- A pack **cannot replace the generated contracts**. The frontmatter, the stage
  line, `renderTaskAccessContract`, `renderSessionTitleContract`,
  `renderTicketTransitionContract` and the project pull request policy are
  appended by Sectile to whatever the pack provides, the way
  `adjustmentCustomContent` already reconciles an edited `adjust` skill. A
  third-party body can therefore never detach an agent from the transition
  protocol.

### Configuration and precedence

- Marketplaces are registered **once in the global settings**, mirroring the
  shape of `known_marketplaces.json`. A project pins **one plugin, one version,
  one commit**, following the project → settings fallback that
  `resolveSpecFrameworkTarget` already uses for `AIProvider` and
  `SpecFramework`.
- Resolution becomes **built-in default → marketplace pack → project edit**, the
  project's own edited content always winning. Applying a pack never destroys a
  hand-written skill.
- `DefaultContent` in `SkillEditorEntry` becomes the **resolved baseline** — the
  pack body when one is pinned — so `isCustom` keeps meaning "differs from what
  this project would otherwise get". The entry gains the origin (`builtin` or
  `marketplace`) and the pack coordinates so the editor can name where a body
  came from.
- Storage reuses `project_skills` with a `source` column and the pack
  coordinates, rather than a parallel table: the resolver already reads one row
  per (project, skill).

### Applying a pack

- Fetching is an **agent-side operation**, a new action beside `sync_config` and
  `spec_install`, recorded as an activity the way `recordSpecFrameworkActivity`
  does. The server never reaches the network itself; the workstation does, and a
  project whose agent is offline simply cannot fetch — the existing `callAgent`
  failure path applies.
- Applying is **explicit and per project**, and the diff against the current
  resolved content is shown in the existing skills editor before it becomes
  effective. `SkillsView` already renders custom-versus-default and
  diverged-on-disk; marketplace origin is a third state on the same screen, not
  a new one. This is deliberate: a skill body is a prompt executed by a CLI
  Sectile launches with `--dangerously-skip-permissions`
  (`internal/runner/runner.go:531`).
- Once applied, installation is unchanged: the resolved content is rendered into
  every agent convention in the checkout and into the provider's user-level
  directory, exactly as today.

### Framework variants and composition

- The official format has no framework variant. A marketplace that needs both
  publishes **one plugin per framework**; a pack supplying a single
  `specify-issue` or `refine-macro` applies to both, and the built-in variant is
  kept for whichever the pack omits.
- `pickup` and `pickup_issues` keep being **composed from the resolved bodies**
  of `clarify`, `specify`, `implement` and `adjust`, so a pack that updates one
  stage cannot leave the batch run behind.

## Left to the specification

Reversible, technical, and deliberately not decided here:

- Where the marketplace cache lives and how it is refreshed and garbage
  collected.
- The validation a pack must pass before it can be applied (frontmatter present,
  non-empty body, unknown directories reported), and how failures surface.
- The exact column and API shapes for the pack coordinates and the origin.
- Whether the skills editor shows the pack diff inline or in a dedicated review
  step.

## Dependencies, as they now stand

- **#202** is no longer a prerequisite. A pack ships whole `SKILL.md` bodies, so

- **#106** is still the same subject in the opposite direction — distributing

### What this reverses

Rounds 2 and 3 treated the marketplace as **a source of body text, not an
install channel**: Sectile read a third-party plugin, spliced its `SKILL.md`
bodies into its own rendering and kept writing the skills and the MCP
registration itself. Round 4 turns this around:

- **Sectile itself becomes the plugin.** Its workflow skills and its MCP server
  declaration are published in the Claude plugin-marketplace format, and a user
  installs them with the agent's own plugin mechanism
  (`claude plugin marketplace add` / `claude plugin install`).
- **The agent's direct setup becomes optional.** Today it is systematic, not
  on-demand (read on `origin/main`):
  - `internal/agent/agent_config.go` — every task dispatch runs
    `agentconfig.Scaffold` then `bootstrapLocalMCP`, and a registration that
    cannot be written aborts the dispatch;
  - `internal/agent/agent_macro_dispatch.go` — same for every macro dispatch;
  - `syncLocalProject` — same on every project sync after a reconnection;
  - `sync_config` (`internal/agent/agent_operations.go`,
    `InstallProjectSkills`, `WriteProjectSkillToRepo`) — the explicit path,
    also used by every save in the skills editor;
  - `internal/agentconfig/locations.go` — the files are user-level:
    `~/.claude/skills` + `~/.claude.json`, `~/.agents/skills` +
    `~/.codex/config.toml`, `~/.gemini/...`.
  An explicit entry point already exists in the desktop (#390, "initialize
  provider skills and MCP"), which is the natural home of an on-demand setup.

### Consequences already clear from the code

1. **Namespacing now reaches dispatch.** Round 2 relied on Sectile writing
   `/clarify-issue` itself. A plugin-installed skill is invoked as
   `/<plugin>:clarify-issue`, so `skillSlashPrompt`
   (`internal/runner/runner.go`) and `installedSkillPath` must learn which of
   the two forms is present on the workstation for the provider being launched.
2. **A plugin is static; today's skills are rendered per project.** The
   installed `SKILL.md` carries the project's skill edits, the spec-framework
   variant (`openspec` / `speckit`), the PR creation stage and the generated
   contracts. A published plugin cannot. The plugin skills have to be generic
   and read the project specifics at run time (`get_project_context` already
   returns the framework, the PR creation stage and the skill references).
   Note that user-level installation already makes the content collide across
   projects today: the last project dispatched wins.
3. **The MCP declaration needs per-workstation values.** A plugin's MCP server
   entry is the same for everyone, while the server URL and the workstation API
   key are not. They must come from the environment or from a value the user
   supplies at install time — to be verified against the plugin format during
   specification.
4. **Only Claude has plugin marketplaces.** codex, agy, gemini, cursor and vibe
   keep the direct setup; "optional" cannot mean "removed".
5. **The work already done on this branch no longer matches the ticket.** The
   stage reads `clarified`, and `feat/267` carries a specification and an
   implementation (PR #350, conflicting with `main`) built on the round-3
   design. Both need to be reconsidered once the questions below are answered.

   the project expects — the generic plugin skill for an unedited skill, the
   project's rendering for an edited one — and say so when it is not.
7. **Edited direct copies still collide across projects.** Installation is
   user-level (`internal/agentconfig/locations.go`): two projects that edit the
   same skill differently share one `~/.claude/skills/<dir>/SKILL.md`, the last
   install winning. The check in 6 is what surfaces it.
8. **The separate repository has to be fed.** Generating the plugin from the
   built-in templates stays in the sectile repository; publishing it to another
   repository needs a pipeline step and a credential with write access to it.

### Open product questions (round 4, follow-up)

9. **Identity check: version, checksum, or both?** Recommended: both, for
   different jobs. The plugin `version` is the Sectile release tag and answers
   "is this plugin compatible with this server's MCP contract". A SHA-256 of
   each rendered `SKILL.md`, computed by the agent from the file on disk (the
   way `skills_status` already detects a copy diverged on disk), answers "is
   this exact skill the one this project expects" — a version number cannot
   see a project edit.
10. **What does a dispatch do on a mismatch** (no plugin and no direct copy, an
    edited skill not installed or stale, a plugin older than the server)?
11. **How is the separate repository versioned and fed?**

### Answers from the owner on Q9–Q11 (2026-09-26, same session)

- **Q9 — no reconciliation mechanism.** The owner considered reconciling on
  timestamps (plugin release date vs skill customisation date) and rejected it
  as too implementation-specific. Settled:
  - the dispatch **uses the skills it finds**; no version, checksum or date
    comparison between what is installed and what the server holds;
  - a **user setting** decides whether a project's custom skill (edited in the
    skills editor, stored on the server) takes precedence over the installed
    one. When it is allowed and the project has a custom version of the skill
    being run, the custom one wins; otherwise the installed skill runs.
  - This supersedes the version + checksum proposal made in Q9.
- **Q10 — no nagging.** A customisation that works is not disturbed by a plugin
  update. The only signal is passive: a warning icon next to the settings entry
  and a "custom skills used" indication inside the settings.
- **Q11 — out of scope.** How the separate marketplace repository is versioned
  and fed is not decided by this ticket.

### Consequence settled from the code

9. **The custom skill reaches the CLI through the dispatch, not through an
   installed file.** Since nothing is written at dispatch (Q6) and nothing is
   reconciled (Q9), a server-side custom skill can only take effect if the
   dispatch hands its resolved content to the CLI — inline in the prompt, or in
   a file private to the run — instead of the `/<dir>` slash command built by
   `skillSlashPrompt`. It also removes the cross-project collision of
   consequence 7, since no user-level file is involved. Inline vs run-private
   file is left to the specification (command-line length, notably on
   Windows, is the deciding constraint).

### Open product questions (round 4, last follow-up)

12. **Which installed skill runs when several are found** — the plugin's
    namespaced `/<plugin>:<dir>`, or a direct copy `/<dir>` installed by `init`
    or the desktop?
13. **Where does the "custom skills win" setting live, and what is its
    default?**

### Answers from the owner on Q12–Q13 (2026-09-26, same session)

- **Q12 — a setting.** A workstation setting, "source of installed skills",
  chooses between the direct copy (`/<dir>`) and the plugin
  (`/<plugin>:<dir>`), falling back to the other when the preferred one is not
  found. **Default: direct copy first**, which keeps today's behaviour after an
  upgrade. The trade-off was stated and accepted: a user who installs the
  plugin while old direct copies remain must switch the setting, or the old
  copies keep running.
- **Q13 — a workstation setting (desktop), on by default**, consistent with the
  execution settings living on the workstation since #305.

## Settled design (round 4)

Supersedes "Settled design" (round 3) entirely; that section and rounds 2–3
remain above as history only.

**Scope.** Sectile's workflow skills and its MCP server declaration are
distributed as a Claude plugin that users install themselves. The agent's
direct setup (writing skills and the MCP registration into the agent's
user-level folders) stays available but becomes optional and manual.

**Out of scope.** Third-party packs replacing built-in bodies (the round-3
feature, PR #350 — to be closed by the owner, the code kept as material for a
possible separate ticket). How the separate marketplace repository is
versioned, fed and published (Q11). Any reconciliation between installed and
server-side skills (Q9). Adding workflow steps.

**Decisions.**

1. *Distribution.* A Claude plugin in a **separate marketplace repository**,
   carrying the workflow skills and the Sectile MCP server declaration. Its
   skills are generic and read the project specifics at run time
   (`get_project_context`).
2. *Direct setup is manual.* No task dispatch, macro dispatch or agent start
   writes skills or an MCP registration any more — today they do
   (`prepareDispatchLocked`, `agent_macro_dispatch.go`, `syncLocalProject`).
   The direct setup is offered, never imposed, from the agent's `init` and from
   the desktop (#390 entry point). It remains the only route for codex, agy,
   gemini, cursor and vibe.
3. *No reconciliation.* The dispatch uses the skills it finds; no version,
   checksum or timestamp comparison.
4. *Which skill runs*, per skill, in this order:
   1. the project's custom skill from the server, when the workstation setting
      "custom skills win" is on (default **on**) and the project has one;
   2. otherwise the installed skill of the preferred source per the workstation
      setting "source of installed skills" (default **direct copy**), falling
      back to the other source;
   3. otherwise nothing is found and the dispatch fails with a message pointing
      at the plugin install, `init` or the desktop — still without writing.
5. *Custom skills reach the CLI through the dispatch*, inline or in a file
   private to the run, never through a user-level file (consequence 9).
6. *Signals are passive.* A plugin update never interrupts a working
   customisation. When a custom skill is used, a warning icon appears next to
   the settings entry and the settings show "custom skills used".

**Left to the specification** (reversible): inline prompt vs run-private file
for custom skills; how the agent detects the plugin per provider (Claude's
installed-plugins state) and builds the namespaced slash command in
`skillSlashPrompt` / `installedSkillPath`; how the plugin's MCP declaration
receives the per-workstation server URL and API key (environment expansion or
install-time value — to be verified against the plugin format); the plugin
generator inside the sectile repository and its test; wording and placement of
the two settings and of the warning icon; the fate of the `sync_config` calls
the skills editor makes on save (they write to disk today, which Q6 forbids
outside an explicit action).

**Stage.** The task reads `clarified`, but the specification and the
implementation on `feat/267` follow the round-3 design. The next
`/specify-issue` rewrites the specification from this section.
