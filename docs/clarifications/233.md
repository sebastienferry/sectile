# #233 — Pull request state icons

## Round 1 — recovered tracker discussion (2026-09-22)

The existing tracker comment described a clarification report on `feat/233`, but that file was absent from the assigned checkout when this run resumed. This section preserves the discussion rather than claiming the original artifact was recovered.

Tasks currently keep ordered PR URLs and branches, while forge reads can observe merge state. The discussion asked which states and surfaces to display, which PR controls the icon, and when to refresh. It proposed persisting forge state, with an optional workflow-derived fallback.

## Round 2 - answers from the owner (2026-09-23)

Display the actual GitHub pull request or GitLab merge request state throughout the web and desktop interfaces. This change does not merge requests, alter task stages, or add a dedicated polling loop.

Settled decisions:

1. Persist the real forge state per PR/MR link. Never infer a merge from the task workflow stage.
2. Distinguish open, conflicting, merged, and closed without merge. A draft remains open unless its forge reports conflicts. Unknown mergeability must not be interpreted as a conflict.
3. Cover every existing web and desktop PR-link surface. Individual history links describe their own PR; task indicators describe the current PR.
4. The current PR is the last recorded link; refreshing state never reorders the links.
5. Refresh during synchronization and workflow steps. A project refresh must not expand into unitary story synchronization for all tasks. When a story is modified or explicitly resynchronized, any additional targeted work updates only its PR metadata.
6. Missing credentials, rate limits, and temporary forge failures preserve previously known state. Legacy links without observed state retain a neutral icon.

The owner explicitly added GitLab and conflict handling to the previous proposal and rejected broad per-story refresh fan-out. No product questions remain.

Dependencies: authenticated forge APIs, the existing ordered PR-link persistence and synchronization lifecycle. The server must use HTTP clients and preserve acting-user/project credential resolution.
