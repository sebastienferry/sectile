## Round 1 (2026-09-23)

### Restated request and scope

When the local agent prepares a task worktree, it should make the main checkout's installed JavaScript dependencies (and possibly its local `.env*` files) available inside that worktree, so `npm run build --prefix web` and `npm run lint --prefix web` work without a manual `npm ci`. The step must be a silent no-op for repositories with nothing to provision. Out of scope: changing how dependencies are installed in the main checkout, the `.gitignore` rule itself (#248), the web test suite (#162), and any other part of worktree creation such as branch selection, stale-path handling or skill scaffolding.

### Verified findings

- **The ticket names the wrong function.** `DB.EnsureTaskWorktree` (`internal/db/db.go:1962`, no longer line 1641) creates nothing now. It only forwards a `prepare_workspace` operation to the local agent and stores the returned branch and path. Worktrees are created by `ensureLocalWorktree` (`internal/agent/agent_config.go:292`), which `agentDaemon.prepareDispatch` (`internal/agent/agent_config.go:377`) calls before `agentconfig.Scaffold`. That is where provisioning belongs. The "Done when" criterion should read "a worktree prepared by the local agent", not "created by `EnsureTaskWorktree`".
- `ensureLocalWorktree` returns early in two cases: the assigned branch is already checked out somewhere, including the main checkout, or `useWorktrees` is false. In both cases no new tree is created.
- No `os.Symlink` call exists outside tests, which confirms the ticket's finding.
- On this workstation, the main checkout has `web/node_modules` and `desktop/node_modules` but **no root `node_modules`**. The root holds a `package-lock.json` and no `package.json`. The guide's root `node_modules` entry is therefore a no-op for this repository today.
- The `Makefile` already has an idempotent real-install path: `make web-deps` and `make desktop-deps`, which run `npm ci` behind a lockfile stamp. `desktop-deps` also runs `node node_modules/electron/install.js`.
- **#248 is not merged into this branch.** Commit `4777883` ("ignore node_modules symlinks, not only directories") exists only on `feat/248`. On the current base, the root `.gitignore` rule `node_modules/` matches directories only. A symlinked `desktop/node_modules` or root `node_modules` would therefore show up as an untracked file and could be committed, as happened before. `web/.gitignore` already ignores `node_modules` without the trailing slash.
- `.env` and `.env.local` are gitignored at the root.
- `golang.org/x/sys` is already a dependency, which helps with Windows-specific linking if needed.
- Sectile provisions worktrees for **every** project it manages, not only itself. A hardcoded `web/`/`desktop/` list encodes this repository's layout into the product.

### Ambiguities (worst first)

1. **Which paths get provisioned, and who decides.** The options are a fixed list (the guide's list plus `desktop/node_modules`, from the comment on #248), automatic discovery (every `node_modules` directory in the main checkout that sits next to a `package.json`, down to a bounded depth), or a per-project setting. Each option leads to different code and a different behaviour on other projects.
2. **Link or real install.** A link is instant, but it shares state. An `npm install` run in the worktree writes through the link into the main checkout. `npm ci` deletes `node_modules` and can empty the main checkout's copy. A branch that changes `package.json` builds against stale dependencies. A per-worktree `npm ci` is correct but slow, needs the network, and runs for every task.
3. **`.env` / `.env.local`.** Should they be linked, given that they may hold secrets and agents run inside the worktree?
4. **Backfill.** Should provisioning run only when a worktree is created, or on every `prepare_workspace`, which would also repair existing worktrees at their next launch?

### Critical dependencies

- **#248 must be merged first**, or this ticket must carry the same ignore fix. Otherwise a provisioned root or `desktop` symlink can be committed.
- On Windows, `os.Symlink` needs Developer Mode or elevation. The agent runs on Windows workstations.
- No migration, external service or API change is needed if provisioning stays inside the agent.

### Reversible technical choices (resolved from code and conventions)

- **Location:** implement in the agent (`internal/agent`) as a step of `prepareDispatch` or `ensureLocalWorktree`, not in `internal/db`. Correct `docs/REIMPLEMENTATION_GUIDE.md:36` to match the implementation.
- **Skip cases:** do nothing when the worktree is the main checkout (`useWorktrees` false, or the branch is checked out in root), when a source path is missing, and when the destination already exists as a file, directory or link. Never overwrite anything.
- **Failure policy:** a provisioning failure is logged and does not fail the launch. A missing dependency folder is a degraded worktree, not a reason to refuse the run.
- **Windows:** try `os.Symlink` first. For directories, fall back to a directory junction, which needs no elevation. If both fail, log and skip.
- **Tests:** Go tests in `internal/agent` covering a linked path, a missing source (no-op), an existing destination (left alone), and a checkout that is not a JavaScript project (no-op).

### Product questions (recommendation first)

1. **Path selection.** *Recommended:* automatic discovery. Link every `node_modules` directory found in the main checkout at the root or one level down, when a `package.json` sits next to it. This covers `web/` and `desktop/` here, yields a no-op on non-JavaScript projects, and avoids hardcoding this repository's layout into a product that manages other repositories. Alternatives: a fixed list (`node_modules`, `web/node_modules`, `desktop/node_modules`), or a project setting.
2. **Link or install.** *Recommended:* link, as the guide says, and accept shared state. Document that running `npm ci` or `npm install` inside a worktree affects the main checkout, and that a branch changing dependencies should run `make web-deps` after replacing the link. Alternative: a per-worktree `npm ci`, which is correct but slow and needs the network.
3. **`.env*` files.** *Recommended:* do **not** link them. Nothing in the build or lint path needs them. Linking them exposes secrets to every agent session and lets a worktree edit the main checkout's configuration. Correct the guide instead. Alternative: link them as the guide says.
4. **Backfill.** *Recommended:* provision on every `prepare_workspace`. The step is idempotent because it only creates missing links, so existing worktrees are repaired at their next launch at no extra cost. Alternative: provision newly created worktrees only.
