# Clarification #547 - Support config short-cut

Ticket: https://github.com/sebastienferry/sectile/issues/547
Branch: `feat/547`

## Round 1 - initial analysis (2026-09-27)

### Requested outcome

Pressing Cmd+, on macOS opens the existing configuration surface. The ticket
also asks to determine the equivalent shortcut on Windows; redesigning settings,
changing saved values, adding a configurable keymap, and system-wide shortcuts
are out of scope.

### Evidence reviewed

- `.agents/MEMORY.md`: project constraints and prior implementation findings.
- `desktop/src/main.js`: `openSettings('Profile')` is the Settings button's
  action; `openProject()` opens project configuration. Both share the full-page
  configuration shell, with general and project categories in its navigation.
  Reopening settings rebuilds the content, so an unconditional shortcut could
  discard an unsaved project form. Existing Cmd/Ctrl+K and sidebar shortcut
  handlers run in capture phase; xterm terminals are embedded in the workspace.
- `desktop/electron/main.cjs`: macOS has application, Edit and Window menus;
  Windows/Linux have no application menu. No Settings accelerator is defined.
- `desktop/package.json`: Electron desktop with unit and UI verification scripts.
- `desktop/README.md`: workstation Settings and project settings documentation.
- `desktop/tests/sidebar-shortcut.ui.cjs`: existing desktop shortcut UI coverage.
- `web/src/context/AppContext.tsx`: separate browser keyboard handling, meaning
  including the web client requires a separate implementation and destination.
- `docs/clarifications/545.md`: full-page configuration scope and back navigation.
- `docs/clarifications/474.md`: platform-specific modifiers, terminal handling,
  exact chords, discoverability, and modal conventions for the sidebar shortcut.

### Ambiguities, worst first

1. Desktop only or desktop and web: these are separate settings surfaces and
   keyboard handlers. Recommended: desktop only, matching the native settings
   shortcut and the recent desktop configuration work.
2. Windows/Linux shortcut and terminal focus: capturing Ctrl+, while a terminal
   has focus takes the chord away from the terminal application. Recommended:
   Ctrl+, on Windows/Linux, active even in a terminal, to make configuration
   consistently reachable from the desktop's primary workspace.
3. Destination and repeated invocation: global Profile, selected project settings,
   or a remembered category lead to different navigation. Recommended: the
   existing Settings button destination (general Profile) when outside
   configuration; do nothing when any configuration category is already open,
   preserving unsaved fields and the selected category.

### Technical recommendations

- Reuse the existing settings opening action and full-page shell from #545.
- Bind Cmd+, on macOS and Ctrl+, on Windows/Linux, using existing platform
  detection. Require the exact chord, without Alt, Shift, or the other primary
  modifier; ignore auto-repeat.
- Use the desktop renderer shortcut conventions. This is an application-local
  shortcut, available only while the app has focus, including ordinary inputs
  and the terminal; no global OS registration or new native menu is needed.
- Ignore the shortcut while an unrelated modal is open, preserving that workflow.
- Keep current Back/Escape navigation and restore the workspace as today.
- Advertise the platform-specific shortcut on the existing Settings control,
  with accessible shortcut metadata, and document it in `desktop/README.md`.
- The change is user-visible: add one English entry under `CHANGELOG.md`
  Unreleased / Added during implementation.

### Dependencies and risks

- The full-page configuration implementation from #545 is already in this checkout.
- No server API, migration, tracker integration, infrastructure repository change,
  or third-party service is required.
- Existing configuration can be opened before agent connection; preserve that
  availability rather than making this shortcut depend on a running agent.
- Keyboard handling must avoid duplicate opens, destroying unsaved forms, or
  sending an intercepted chord to xterm. Validate supported platforms and
  focus contexts with the existing desktop UI test infrastructure.

### Open product questions for the owner

1. Confirm desktop only, or include the web application too?
2. Confirm Ctrl+, on Windows/Linux, including when a terminal has focus?
3. Confirm opening general Profile like the Settings button, and leaving any
   already-open configuration category untouched?

### Round status

Recommendations await the owner's answers and confirmation of satisfaction.
No production code or technical specification has been written. The task must
remain at its current clarification stage while these questions are open.

## Round 2 - answers from the owner (2026-09-27)

The owner confirmed desktop-only scope in session, then explicitly accepted
questions 2 and 3 with "2 oui 3 oui". All product questions are settled and the
proposed clarification is accepted. No prior assumption was reversed.

### Settled scope and acceptance baseline

1. Desktop only; the browser client is out of scope.
2. Cmd+, on macOS and Ctrl+, on Windows/Linux open the existing configuration
   page, including when an embedded terminal or ordinary text input has focus.
   An intercepted shortcut must not also reach the terminal.
3. Outside configuration, open General / Profile through the existing Settings
   button action. If any configuration category is already open, leave its
   category and unsaved fields untouched.
4. Use the exact platform-specific chord, without Alt, Shift, or the other
   primary modifier. Ignore auto-repeat and unrelated open modal dialogs.
5. Keep existing Back/Escape navigation and pre-connection settings availability.
6. Show the shortcut on the Settings control with accessible shortcut metadata,
   document it in the desktop README, and add one user-visible English
   changelog entry during implementation.
7. No new native menu, global OS shortcut, configurable keymap, settings redesign,
   server API, migration, or infrastructure change is required.

### Round status

No open product questions remain. The owner has confirmed satisfaction with
all three recommendations; the clarification exit condition is met.
Production implementation and the technical specification remain for their
respective workflow stages.
