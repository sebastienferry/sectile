## Round 1 (2026-09-26)

### Restated request and scope

Give Sectile Desktop a light appearance next to its current dark one, with a
way for the user to choose between them, so that the whole window (sidebar,
toolbar, dialogs, settings, diff view, title bar) renders consistently in the
chosen mode. The web interface's own theme, the web profile modal and any
redesign of the desktop's layout or palette beyond what a second mode needs
are out of scope.

### Verified findings

- The ticket has a title only: no description, no comments, no parent epic.
- The desktop has no notion of theme. `desktop/src/style.css` hard-codes a
  dark palette: about 93 literal colors (`#11151c`, `#d8e0ec`, `#1a212d`,
  `#62d3be`, ...) and only three `var(--...)` references, one of them
  `var(--muted,#8892a4)` with no definition.
- Three places outside the stylesheet paint dark colors:
  - `desktop/src/main.js:48`: the xterm terminal is created with
    `theme:{background:'#11151c',foreground:'#d8e0ec'}`;
  - `desktop/electron/main.cjs:320`: the `BrowserWindow` uses
    `backgroundColor:'#11151c'` and
    `titleBarOverlay:{color:'#11151c',symbolColor:'#d8e0ec'}` (the overlay is
    what Windows and Linux draw for the window controls);
  - Electron's `nativeTheme` is never used, so native widgets (scrollbars,
    `<select>` popups, the `<dialog>` backdrop) follow the OS appearance, not
    the app.
- The web interface already has a per-user theme stored on the server:
  `internal/models/models.go:840` (`Theme` "dark", "light", "system"),
  `internal/db/usersettings.go`, `web/src/types/index.ts:578`
  (`'dark' | 'light' | 'system'`). The web profile modal only offers Dark and
  Light, and `web/src/context/AppContext.tsx:1023` treats anything but `light`
  as dark, so `system` is declared but not implemented.
- The web light palette lives in `web/src/index.css` (theme layer, `.light`
  and `.dark` classes on the root).
- The desktop never reads the user's server settings. Its renderer talks to
  the local agent through `/desktop/*` IPC handlers
  (`desktop/electron/main.cjs:47-302`); the Profile panel
  (`desktop/src/main.js:935-944`) says the web interface owns the profile.
  Workstation preferences live either in the Electron `settings.json`
  (`settings` / `save-settings` IPC) or in renderer `localStorage`
  (`sidebarCollapsed`, `sidebarWidth`, `collapsedProjects`).
- The settings dialog is organised in categories
  (`desktop/src/main.js:904-910`: Profile, Connection, AI Engine CLI, Logs,
  Changelog) and already uses a `.segmented` control for exclusive choices.

### Ambiguities (worst first)

1. **Where the choice comes from.** Either the desktop keeps its own
   workstation preference, or it follows the user's `theme` from the server
   profile the web edits, or it only follows the OS. The first is local
   storage and a settings row; the second needs a new agent/desktop route to
   read (and maybe write) user settings and a refresh path; the third needs no
   setting at all.
2. **Default for an existing install.** "Follow the system" changes the look
   of every current user whose OS is light; "Dark" keeps today's appearance
   until they opt in.
3. **The terminal.** The xterm console shows CLI output (Claude Code, Codex,
   agy) that picks its own colors, often assuming a dark background. A light
   terminal is a different xterm theme with a full ANSI palette; keeping it
   dark is no work.

### Critical dependencies

- No migration, no server change and no tracker impact for a workstation-local
  preference. Following the server profile would need a new route through the
  local agent, since the desktop has no path to `/api/settings` today.
- Electron `nativeTheme.themeSource` drives `prefers-color-scheme` in the
  renderer and the native widgets; the title bar overlay colors must be
  updated with `BrowserWindow.setTitleBarOverlay` when the mode changes.
- The desktop UI tests load `dist/index.html`, so they need a build first.

### Reversible technical choices, resolved from the code

- Move the desktop palette to CSS custom properties on `:root`, with a dark
  set and a light set, instead of duplicating every rule.
- Drive the mode through `nativeTheme.themeSource` (`system`, `dark`,
  `light`) so the renderer only answers `prefers-color-scheme`, native widgets
  follow, and the window background and title bar overlay are set from the
  main process at start and on change.
- Reuse the web light palette's values where a desktop surface has a web
  counterpart, so both clients read as one product.
- Put the control in the settings dialog as a segmented control, the pattern
  it already uses for exclusive choices, in a new "Appearance" category.
- A `CHANGELOG.md` line under `[Unreleased]` / `Added`, since the change is
  visible to users.

### Product questions

1. **Source of the choice.** Recommended: a workstation-local desktop setting
   (System / Dark / Light), independent of the web profile. It needs no server
   change and matches how the desktop already keeps its own preferences.
   Alternative: follow the web profile's theme.
2. **Default value.** Recommended: System, so the app matches the OS from the
   first launch after the update. Alternative: Dark, which keeps today's look.
3. **Terminal.** Recommended: the terminal follows the chosen mode, with a
   light xterm palette. Alternative: the terminal stays dark in both modes.

## Round 2 - answers from the owner (2026-09-26)

The owner answered the three questions of round 1 in session, each with the
recommended option.

### Settled decisions

1. **Source of the choice:** a workstation-local desktop setting with three
   values, System, Dark and Light. It is independent of the web profile's
   `theme`; the desktop neither reads nor writes the server's user settings.
2. **Default value:** System. An existing install without the setting follows
   the OS appearance from the first launch after the update, so a user whose
   OS is light sees the desktop turn light.
3. **Terminal:** the xterm console follows the chosen mode, with a complete
   light palette (background, foreground, cursor, selection and the 16 ANSI
   colors) in light mode, and switches live when the mode or the OS appearance
   changes.

### Reversed assumptions

None. Round 1 made no assumption the answers contradict.

### Consequences and technical choices

- **Storage:** the preference is kept in the Electron `settings.json`
  (the `settings` / `save-settings` IPC), not in renderer `localStorage`. The
  main process must know it before creating the window, to set
  `nativeTheme.themeSource`, the window `backgroundColor` and the title bar
  overlay colors without a dark flash on a light start.
- **Live switch:** changing the setting, or the OS appearance while on System,
  takes effect without a restart: `nativeTheme` `updated` event in the main
  process for the overlay and background, `prefers-color-scheme` in the
  renderer for the stylesheet and the terminal.
- **Scope of the light mode:** every desktop surface, including the setup and
  pairing screens, dialogs, settings, run queue, diff view, notifications and
  status colors. The status colors (running, failed, PR states) keep their
  meaning and are re-toned for contrast on a light background.
- **Out of scope, confirmed:** the web interface's theme, including its
  unimplemented `system` value; syncing the choice between desktop and web.
- **Changelog:** one `Added` line under `[Unreleased]`.

None.
