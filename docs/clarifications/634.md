## Round 1 (2026-09-30)

### Restated request and scope

In a macro's roadmap panel, let the owner select several slicing lines and
create all their stories in one gesture: each story lands in the target project
its own line names, lines already attached to a story are skipped, one failure
does not stop the others, and the outcome is reported line by line. Each
slicing line also shows where it came from (tasks.md, spec.md, an existing
story, or typed by hand).

Out of scope: creating stories from the lines of several macros at once; one
target project imposed on the whole batch; any change to the single-line
"create story" action and its contract; a batch tool on the MCP interface;
editing the origin of a line.

### Verified findings

- The single-line action exists: `POST /api/projects/{id}/macros/{key}/story`
  with a `todoId` (`internal/handlers/handlers.go:1200`), backed by
  `DB.CreateStoryFromMacroTodo` (`internal/db/macros.go:490`). It is already
  idempotent (a line with a `storyKey` is refused: "cette ligne a déjà produit
  %s"), refuses a line attached to a roadmap project, and validates the line's
  target project (missing project, other tracker instance) before writing.
- Each line carries its own `TargetProjectID`, chosen in the panel and frozen
  once the story exists (`web/src/components/RoadmapView.tsx:2355-2387`).
- The checkbox a slicing line already shows is **not** a selection: it toggles
  `done`, is persisted, strikes the line through and feeds the "done / total"
  count of the heading (`RoadmapView.tsx:2325-2345`).
- The origin is stored but never displayed: `MacroTodo.SourceKind` and
  `SourceEntry` (`internal/models/models.go:327-360`,
  `web/src/types/index.ts:141-165`). The stored values are `tasks` (a tasks.md
  group), `spec` (a spec.md requirement or a Spec Kit user story), `stories` (a
  story already under the macro, which arrives attached) and empty (typed by
  hand, also every line saved before the field). There is no "scenarios" value,
  unlike the wording of the ticket.
- Saving the slicing is a local write only (`SaveMacroMeta`,
  `internal/db/macros.go:285`): unlike Taskativ, Sectile does not republish the
  shaping as a comment on the epic ticket, so saving per line costs no tracker
  write.
- The single-line creation records no activity; its result (key, notice) is
  only returned to the panel.
- Taskativ reference read:
  `openspec/changes/archive/2026-09-09-taskativ-74-batch-story-creation`
  (proposal and spec). Its requirements map onto Sectile almost one to one,
  except the "write once" rule, which in Taskativ existed to avoid N comment
  republications.

### Ambiguities (worst first)

1. **What "ticked" means.** Reusing the existing `done` checkbox as the batch
   selection, or adding a separate, non-persisted selection box. The two lead
   to different code and to different meanings of "done". See Q1.
2. **Where the per-line report lives.** Only in the panel until it is closed,
   or also recorded as one activity that survives a reload. See Q2.
3. **How the origin is shown and named.** The ticket says "specification,
   scenarios, typed by hand"; the stored kinds are tasks, spec, stories and
   empty. See Q3.

### Resolved technical choices (reversible)

- **New route beside the existing one**:
  `POST /api/projects/{id}/macros/{key}/stories` with `{ "todoIds": [...] }`,
  answering one outcome per requested line (`created` with key and notice,
  `skipped` with the existing key, `failed` with the reason). The single-line
  route and its contract stay unchanged.
- **Shared per-line core**: the checks and the creation of
  `CreateStoryFromMacroTodo` are extracted into one function both paths call,
  so a batch line and a single line are refused for the same reasons.
- **Sequential, in slicing order**: lines are created one after the other in
  the order they appear, not in parallel, which keeps tracker rate limits and
  story numbering predictable.
- **The key is saved after each successful line**, not once at the end. Since a
  save is local only, this costs nothing on the tracker and guarantees that a
  crash or a failed final save never leaves a created story unrecorded, which
  would make a relaunch create a duplicate. The saved slicing is re-read under
  the lock before each write, so a concurrent edit of another line is kept.
- **Skipped, not failed**: a selected line that already carries a story
  (including an origin `stories` line) is reported as skipped and is not
  counted as a failure. A failed line keeps no key, so relaunching retries it.
- **The selection is interface state**: never stored on the line, cleared when
  the panel shows another macro and on reload. Attached lines cannot be
  selected.
- **Acting user**: the batch writes as whoever the request names
  (`actingContext`), as the single-line action does.
- **User-facing text** stays in French, like the rest of the panel.
- **Changelog**: the change is user-visible, so the implementation PR adds a
  line under `## [Unreleased]`.

### Product questions

1. **Selection box.** Recommended: a separate selection box per unattached
   line, plus "select all unattached lines", leaving the existing `done`
   checkbox as it is. Alternative: the ticked (`done`) lines are the batch.
2. **Report.** Recommended: the per-line report is shown in the panel (on each
   line and as a summary "N créées, M passées, K en échec"), with no activity
   recorded, consistent with the single-line action. Alternative: also record
   one activity carrying the per-line outcome, as Taskativ does.
3. **Origin display.** Recommended: a small badge on every line, named after
   the stored kind ("tâches", "spécification", "story existante", "saisie à la
   main"), with the raw `SourceEntry` as tooltip. Alternative: show a badge
   only on hand-typed lines, the case the model comments call the most
   interesting.
4. **Branch base.** `feat/634` was created from `feat/desktop-conversation-test`
   and carries two commits that are not on `main` (`1f8a2032`, `0d9dd516`,
   desktop Claude conversation prototype). The branch is not pushed yet.
   Recommended: rebuild `feat/634` from `origin/main` and replay only this
   clarification commit, so the future PR contains only #634. Alternative:
   keep it as is and let the PR carry those commits.

### Critical dependencies

- The tracker of the macro and of each target project, and a tracker token for
  the acting user (story creation is a tracker write since #482).
- No migration: the selection is not stored and the origin is already stored.
- No external service. The study document
  `docs/taskativ-roadmap-comparison.md` is not on `main` (it lives on
  `claude/clarify-issue-gh-11a4f59c-217c0f`); nothing here depends on it.
