# Clarification - #180 - Implement a JIRA based tracker

Stage: new → clarified.

Ticket: https://github.com/sebastienferry/sectile/issues/180. Description as
filed: "Implement JIRa base tracker interface using Jira API." No comments, no
parent epic.

## Restated request and scope

Register a `jira` adapter in `internal/tracker.Registry` that implements
`tracker.TicketingSystem` against the Jira Cloud REST API over plain HTTP, so a
project whose `issueTracker` is `jira` can be synchronised, read, created,
updated, commented and closed from Sectile exactly as a GitHub project is
today. The adapter replaces the retired `acli`-based integration whose
configuration, models and UI remnants are still in the code base.

Out of scope: pull-request and merge-request handling (GitHub and GitLab stay
the forges; `runner/adjustment.go` is untouched), Jira Agile board import
(boards, columns, sprints), Sprint / Team / Epic writes, Jira Server and Data
Center authentication, a GitLab adapter, and the out-of-database secret file the
setup screen still mentions.

## Ambiguities, worst first

1. **Which Jira and which authentication.** Jira Cloud authenticates with
   `email:api-token` Basic auth and speaks REST v3 with ADF bodies; Jira Data
   Center uses a Bearer personal access token, REST v2 and wiki-markup bodies.
   The stored settings (`jiraEmail` + `jiraApiToken`, site URL such as
   `https://acme.atlassian.net`) are Cloud-shaped. → Decision 1.
2. **Who carries the workflow stage: labels or Jira statuses.** GitHub carries
   the Sectile stage as a label (`new`, `clarified`, ...) and uses the issue
   state only for finished. Jira has real workflow statuses with transitions,
   and the board mapping (`StageColumns`) was designed for them. Two readings
   lead to two adapters: label-driven with transitions only on close, or
   status-driven with a transition on every stage change. → Decision 2.
3. **Body format.** Sectile writes Markdown (reports, comments, rewritten
   stories). Jira Cloud v3 accepts and returns Atlassian Document Format (ADF)
   for descriptions and comments; sending Markdown as a plain string is
   rejected. A conversion layer is needed in both directions and its depth
   decides what a report looks like in Jira. → Decision 3.
4. **Which capabilities the adapter declares.** The `Writer` interface names
   assign, transition, sprint, team, epic and labels. Sprint needs the Agile
   API, Team is an instance-specific custom field, Epic is the `parent` field.
   Declaring them means implementing them now. → Decision 4.
5. **Local identity of a Jira task.** GitHub tasks are `gh-<projectID>-<n>` with
   key `#n`. A Jira key `PE-123` is unique per site, not across sites, and the
   existing URL builder and assignment code expect `task.Key` to be the Jira
   key. → Decision 5.
6. **Credential resolution and the setup screen.** `trackerapi.Credentials`
   has no Jira fields, the environment fallbacks exist for GitHub and GitLab
   only, `CheckTrackerCredentials` cannot verify a Jira token, and the setup
   screen promises a token file that nothing writes. → Decision 6.
7. **Search endpoint.** Atlassian removed `GET /rest/api/3/search` from Jira
   Cloud in 2025 in favour of `GET /rest/api/3/search/jql`, which paginates with
   `nextPageToken` and returns only requested fields. Code written from older
   documentation fails at runtime. → Decision 7.

## Critical dependencies

- **A Jira Cloud site and an API token for manual verification.** None is
  available in the repository or the CI. Automated tests must run against
  `httptest` servers, as `internal/trackerapi/client_test.go` does for GitHub;
  a live check is a manual step on the author's own site.
- **Atlassian API surface.** REST v3 with `search/jql`, `issue`, `issue/{key}/
  comment`, `issue/{key}/transitions`, `issue/{key}/assignee`,
  `user/assignable/search`, `project/{key}/statuses`, `myself`. No SDK: the
  server already forbids anything but `net/http` for trackers.
- **Runtime boundary tests** (`cmd/server/runtime_boundary_test.go`): the
  adapter lives in `internal/trackerapi`, which the server may import; nothing
  in `internal/runner` or `internal/workspace` may be pulled in.
- **No schema migration is required** for the settings-level credentials: the
  four `jira_*` columns exist on `settings` and `jira_project`, `tracker_url` on
  `projects`.

## Decisions

1. **Jira Cloud only, Basic auth, REST v3.** `Authorization: Basic
   base64(email:token)`, base URL from `Project.TrackerUrl` then
   `Settings.JiraUrl`, API prefix `/rest/api/3`. Data Center (Bearer PAT, v2) is
   a follow-up; the base URL stays configurable so nothing is closed off.
   Rationale: the stored settings and the UI are already Cloud-shaped, and
   Basic auth is the only documented token scheme on Cloud.
2. **Labels carry the workflow stage; transitions are used on close and on an
   explicit target.** Import derives the Sectile status from the workflow labels
   exactly as `githubTask` does, then from the Jira status category (`done` →
   finished) the way `closed` does for GitHub. Updates push labels through the
   `labels` field. `DeleteIssue` and an `UpdateIssue` whose status is finished
   run the first available transition whose target status category is `done`,
   and report an error naming the issue when the workflow offers none.
   `UpdateIssueRequest.TargetStatus` and `Writer.Transition` resolve a
   transition by target status name. Rationale: it is what #179 settled for
   every tracker (one label spelling), it keeps the project's `StageColumns`
   mapping as the optional, later, status-driven refinement, and it never
   forces a transition the Jira workflow does not have.
3. **Markdown ↔ ADF for a bounded subset.** Outbound: paragraphs, headings
   1-3, bullet and ordered lists, fenced code blocks, inline code, bold,
   italics, links. Inbound: ADF → Markdown for the same nodes, unknown nodes
   flattened to their text. Everything lives in one file next to `mapping.go`
   with table-driven tests. Rationale: skill reports are lists, headings and
   code blocks; a raw-string fallback would make every report unreadable in
   Jira, and REST v2 (wiki markup) would need the same converter for a format
   Cloud is moving away from.
4. **Capabilities declared in v1**: `create`, `get`, `update`, `delete`,
   `sync`, `comment`, `labels`, `transition`, `assign`. `SearchAssignable`
   uses `user/assignable/search`; `Assign` takes an account id, which is what
   `db.go:2430` already expects. `sprint`, `team` and `epic` stay
   `ErrUnsupported` so the UI shows a limit, not a failure. Rationale: they are
   the GitHub set plus the two Jira has natively; Agile and custom fields are
   separate work.
5. **Identity.** `task.Key` is the Jira key (`PE-123`), `task.Source` is
   `jira`, `task.ID` is `jira-<projectID>-<KEY>` from `FormatTaskID`,
   `ExternalURL` is `<site>/browse/<KEY>`. `Registry.ForTask` needs no new
   heuristic since `Source` is set on import and on creation. Existing
   `db.go:798` URL code keeps working unchanged.
6. **Credentials follow change 149.** `trackerapi.Credentials` and `Client`
   gain `JiraURL`, `JiraEmail`, `JiraToken`; `trackerCredentials` resolves them
   from `Settings` (project override limited to the existing `TrackerUrl` and
   `JiraProject`; a per-project e-mail/token pair is deferred); environment
   fallbacks `SECTILE_JIRA_URL`, `SECTILE_JIRA_EMAIL`, `SECTILE_JIRA_TOKEN` →
   `SECTILE_TRACKER_TOKEN` → `JIRA_API_TOKEN`, with `JiraAPITokenFromEnv`
   reported like the other two. `CheckTrackerCredentials("jira")` calls
   `GET /rest/api/3/myself` and answers with `displayName`;
   `SaveTrackerCredentials("jira")` persists site, e-mail, project key and
   token with the write-only and `__clear__` rules. The "store the token in a
   file" checkbox is removed from the setup screen: no server code has ever
   written such a file, and 149 left the question open without a taker.
7. **Search and sync.** Full sync runs JQL `project = <KEY>` plus
   `AND issuetype IN (...)` when `Project.IssueTypes` is set, `ORDER BY updated
   DESC`, through `GET /rest/api/3/search/jql` with explicit `fields` and
   `nextPageToken` pagination, 100 per page, same-origin and repeated-page
   guards as `githubPages`. The auto-sync loop keeps its per-task `GetIssue`
   path; the incremental JQL described in `autosync.go`'s header is not
   implemented here and the comment is corrected.
8. **Creation.** `POST /rest/api/3/issue` with project key, summary, ADF
   description, labels, issue type from `CreateIssueRequest.IssueType`, else
   the first of `Project.IssueTypes`, else `Task`. Priority is sent by name
   when set; import maps `Highest`/`High` → high, `Medium` → medium,
   `Low`/`Lowest` → low. Assignee travels as an account id only.
9. **Dead code goes.** The `sync_jira` special case in `processSyncJob`, the
   "support retiré" answer of `HandleSyncJira` (which enqueues like GitHub
   again), the `jira` refusal in project status listing (replaced by
   `GET /rest/api/3/project/{key}/statuses`), the `acli` wording in
   `SyncView.tsx`, the `jiraSearchFields` constant in the runner, and the
   README/ARCHITECTURE/CAPABILITIES/ADR 0006 sentences saying Jira is
   unsupported. No `if tracker == "jira"` is added to `internal/db`; the
   Jira-shaped activity text in `enqueueTrackerUpdateUnsafe` is driven by the
   resolved adapter's `Name()`.

## Questions, with the recommended option

Asked for the record. The run is unattended, so the work proceeds under the
recommended option, stated as an assumption below; a different answer changes
acceptance criteria but not the shape of the adapter.

1. **Cloud only in this ticket?** Recommended: yes (decision 1). Alternative:
   also accept a Bearer PAT for Data Center, which adds an auth mode switch and
   REST v2 fallbacks.
2. **Does finishing a task in Sectile transition the Jira issue to Done?**
   Recommended: yes, mirroring GitHub's close, through the first `done`-category
   transition (decision 2). Alternative: labels only, Jira status untouched.
3. **Sprint, Team and Epic writes in scope?** Recommended: no, declared
   unsupported (decision 4). Alternative: Epic through the `parent` field is
   the cheapest to add if wanted now.

### What this reopens, and how it is settled

1. **Where the Sprint and Team values live.** They are custom fields whose ids
   differ per site. → Discover them once per client through
   `GET /rest/api/3/field`: the sprint field has schema custom suffix
   `:gh-sprint`, the team field has schema type `team` or suffix
   `:atlassian-team`. Cache on the client; request them explicitly in
   `search/jql` `fields`.
2. **Where team members come from.** Atlassian teams are not in the Jira API;
   the organisation-scoped public Teams API needs an org-admin token. → Use the
   site gateway `GET /gateway/api/v4/teams/{teamId}/members?siteId=<cloudId>`
   with the same Basic auth, the cloud id read from `GET /_edge/tenant_info`,
   then `GET /rest/api/3/user/bulk` for display names and avatars. This is the
   path the retired implementation used and had working; it is undocumented,
   so it is isolated in one file and its failure degrades to "members unknown"
   without failing the sync. Team search uses the JQL autocomplete suggestions
   endpoint, as before.
3. **Sprints need a board.** `SetSprint` goes through the Agile API
   (`POST /rest/agile/1.0/sprint/{id}/issue`, `POST /rest/agile/1.0/backlog/issue`
   to clear), sprints are listed per board (`GET /rest/agile/1.0/board/{id}/sprint`),
   boards per project (`GET /rest/agile/1.0/board?projectKeyOrId=`). →
   `Project.BoardID` and `Project.Sprints` are populated again: board discovery,
   sprint listing and **board column import** (`GET /rest/agile/1.0/board/{id}/configuration`
   with status names) come back in scope, since a sprint without a board is
   unreachable and the columns are read from the same configuration call.
4. **Epics.** Parent is the `parent` field on `PUT /rest/api/3/issue/{key}`
   (`null` detaches). Import reads `fields.parent.key` and
   `fields.parent.fields.summary` into `ParentKey`, `ParentTitle`,
   `ParentType: "Epic"`. Epic listing for the roadmap is a JQL read
   `project = KEY AND issuetype = Epic`.
5. **Interface extension.** `TicketingSystem` grows a read side, with
   `BaseTicketingSystem` defaults returning `ErrUnsupported` so `github` and
   `local` change nothing:
   `ListBoards(ctx, project)`, `ListBoardColumns(ctx, project, boardID)`,
   `ListSprints(ctx, project, boardID)`, `ListIssueTypes(ctx, project)`,
   `ListStatuses(ctx, project)`, `ListEpics(ctx, project)`,
   `SearchTeams(ctx, project, query)`, `TeamMembers(ctx, project, teamID)`.
   Capabilities `CapBoard` and `CapEpic`/`CapSprint`/`CapTeam` gate them. The
   database stubs `ListProjectTrackerBoards`, `ListProjectIssueTypes`,
   `SyncProjectBoardColumns`, `SearchTrackerTeams`, `RefreshTeamMembersNow`,
   `RefreshProjectTeamMembers` and the `jira` refusal in project status listing
   route through the resolved adapter and stop being stubs.
6. **Creation with mandatory fields.** Some instances require extra fields on
   creation (the retired code cites "Epic Type" on epics). → Port
   `RequiredCreateFields` (`GET /rest/api/3/issue/createmeta/{key}/issuetypes/{id}`)
   so the epic creation dialog can ask for them; `CreateEpic` already passes a
   `fields` map.

### Key input for the specification: a reference implementation exists

Commit `e6e16ec` ("clean jira", 2026-08-27) deleted a complete Jira Cloud REST
client from `internal/runner`: `jira_rest.go` (boards, sprints, board
configuration, field discovery, `search/jql` with `nextPageToken`, transitions
by target status, create with required fields), `jira_teams.go` (cloud id,
team members through the gateway, user bulk lookup, assignable search, team
search, set team, move to sprint, issue types, identity), `comments.go` (REST
comments) and `internal/tracker/jira.go` (the `Writer` adapter declaring assign,
transition, sprint, team, epic, labels, comment). Read it at `e6e16ec^`. It
used Basic auth and the current search endpoint. It was removed because it
lived on the workstation side of the #54 server/agent split and mixed in acli
fallbacks, not because it was wrong. The specification should plan a **port
into `internal/trackerapi`** on top of the shared `Client` (redirect and
size guards, per-project credentials) rather than a rewrite, dropping every
acli fallback and adding what it lacked: `TicketingSystem` CRUD and sync,
Markdown ↔ ADF, and the read-side interface above.
