## Round 1 (2026-09-25)

### Restated request and scope

A project whose tickets span several repositories must let each task run in
the repository it belongs to, and let the agent read the other repositories of
the project as context, whether the run is interactive or autonomous. When the
task's repository cannot be determined, an interactive run asks the user to
pick or add one; an autonomous run never guesses.

Out of scope: a single task that changes several repositories at once (one
worktree, branch and pull request per repository). It is a candidate phase 2.

### Verified findings

- The local agent resolves exactly one root per project and per workstation:
  `Overrides.Projects[projectID]`, or the current checkout when its `origin`
  matches `GitRemoteURL` (`internal/agent/agent_config.go:145`). Server paths
  are never used as a working directory, by design (ADR 0003, ADR 0026).
- The task worktree is always created under that single root
  (`<root>/.tasks/worktrees/<KEY>`, `ensureLocalWorktree`,
  `localTaskPath` at `internal/agent/agent_operations.go:368`).
- **A per-task working directory already exists but has no effect on runs.**
  `Task.RepoPath` is edited in the task detail
  (`web/src/components/TaskDetailModal.tsx:178`, shown at line 1377), and
  `registerProjectRepoPathUnsafe` feeds the project's `RepoPaths` dropdown from
  it (`internal/db/db.go:5993`, capped at 25). The local agent ignores both;
  only PR evidence lookup reads them (`internal/agent/evidence.go:108`). A task
  pinned to another repository therefore runs in the project root today.
- These stored values are absolute paths from whoever typed them, so they are
  meaningless on another workstation.
- `Project.MonoRepo` already says "tickets span several repositories"
  (`internal/models/models.go:148`); it only drives branch display today.
- The specifications checkout is already a second, workstation-owned folder
  (`Overrides.SpecRepos`, ADR 0026), with its own macro worktrees.
- `get_project_context` returns no filesystem path
  (`internal/taskmcp/server.go:135`). The prompt template exposes `{repoPath}`
  and `{repo}` only (`internal/agent/agent_template.go:35`).
- Neither the interactive command (`agentCommandLine`, `agent_config.go:497`)
  nor the headless one (`headlessCommandLine`, `agent_config.go:514`) passes
  an additional directory to the CLI.
- #392 already handles a pull request whose repository differs from the
  project checkout (`checkoutCandidates`, `internal/agent/evidence.go:95`).

### Ambiguities (worst first)

1. **What identifies a repository across workstations.** Keep absolute paths
   (today's `RepoPaths`), or key repositories by git remote and let each
   workstation map remote → path. Different data model, migration and UI. → Q1.
2. **What happens to the existing `Task.RepoPath` / `Project.RepoPaths`.**
   Make the agent honour them, convert them to remotes, or retire them. → Q2.
3. **Where context folders are declared.** Per project (every task sees the
   same set), per task, or both. → Q3.
4. **How "read-only" is enforced for context folders.** A prompt instruction,
   or a hard guarantee. With `--permission-mode bypassPermissions` on
   autonomous runs, `--add-dir` grants write access too; a hard guarantee needs
   per-provider permission rules. → Q4.
5. **Whether the spec repository becomes one context folder among others**, or
   stays a separate concept with its own macro worktrees. → Q5.

### Reversible technical choices (settled from the code)

- Workstation mappings stay in `~/.config/taskflow/settings.json`, never
  uploaded (ADR 0003). The server stores only repository identity.
- Repository identity is compared with `models.RepositoryIdentity`, as
  `localProjectRoot` already does for `origin`.
- The worktree is created only in the task's primary repository, with the
  existing `ensureLocalWorktree` logic applied to that repository's root.
- Context folders reach the CLI through a new command template placeholder
  (`{addDirs}`), expanded per provider in `modeCommandLine` /
  `headlessCommandLine`; a provider without a known flag gets none rather than
  a guessed one, as `headlessCommandLine` already does.
- The folder map given to the agent is built by the local agent (prompt block
  and a `SECTILE_*` environment variable, like the existing ones at
  `internal/agent/agent.go:1040`), never returned by `get_project_context`.
- The picker choice is pinned on the task, so later stages run in the same
  repository.
- An autonomous run whose repository is ambiguous stops in
  waiting-for-input (ADR 0012) instead of guessing.
- The remote-keyed repository model gets an ADR.

### Critical dependencies

- A schema change goes into `internal/db/migrations.go` only, never the
  baseline `CREATE TABLE`, for both SQLite and PostgreSQL (ADR 0016, 0021).
- CLI support for extra directories: Claude Code has `--add-dir`; Codex's
  flag must be checked against the installed version; vibe is unknown.
- The desktop settings (repository mapping UI) and the web task detail
  (current `repoPath` field) both change.
- Stage validation (`validateStagePR`, #392) must compare HEAD against the
  task's primary repository, not the project root.

### Open product questions (owner: @sebastienferry)

1. **Repository identity.** Recommended: key repositories by git remote. The
   project lists its remotes on the server; each workstation maps
   remote → local path in its settings.
2. **Existing per-task path.** Recommended: convert `Task.RepoPath` and
   `Project.RepoPaths` to remotes (read each path's `origin` where it exists on
   the migrating workstation, drop what cannot be resolved), then make the
   agent honour the task's repository. Alternative: honour paths as-is.
3. **Context folders scope.** Recommended: per project in the first
   iteration: every repository of the project other than the primary one is a
   context folder when mapped on the workstation. Per-task selection later.
4. **Read-only guarantee.** Recommended: a prompt instruction only in the
   first iteration, documented as not enforced. Alternative: per-provider
   permission rules denying writes outside the worktree.
5. **Spec repository.** Recommended: keep it a separate concept (it owns macro
   worktrees), but also list it in the folder map given to the agent.
6. **Phase 2 (multi-repository changes).** Recommended: out of scope, tracked
   as its own ticket.
7. **Interactive picker trigger.** Recommended: ask only when the project is
   multi-repo, the task has no repository pinned, and more than one repository
   is mapped on this workstation; otherwise use the only candidate silently.
