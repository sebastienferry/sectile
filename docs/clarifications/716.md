## Round 1 (2026-10-02)

### Restated request and scope

Find out why Claude Code's `sectile` MCP server fails to connect after the workstation restarts, and, if the owner confirms, change Sectile so the connection survives restarts without manual repair. Out of scope: other MCP clients' own reconnection behaviour, the machine API's authentication rules (a refused key stays refused), and new authentication schemes such as OAuth unless the owner asks for them.

### Observed symptom (this workstation, this run)

- Claude Code reports the `sectile` server as failed: HTTP 401 `{"error":"Valid agent bearer token required"}`. The entry is the top-level `mcpServers.sectile` in `~/.claude.json`: remote HTTP to `https://sectile.internal.eqtv.dev/mcp` with a static `Authorization: Bearer sectile_…` header. That is exactly the shape `agentconfig.ConfigureMCP` writes.
- In the same session, the desktop agent's loopback gateway (`http://127.0.0.1:8091/mcp`) works. It forwards with the daemon's own workstation key. So the server is up, the daemon's key is valid, and the key in `~/.claude.json` is a different key.
- The ticket has no description and no comments. The owner's wording, "each time the computer is restarted", is the only description of when it happens.

### Verified findings

- **What the 401 means.** `agentAuthMessage` (`internal/handlers/agent_api.go:121-131`) returns this exact text for an **unknown or revoked** key. An expired key and a blocked account each get their own message. So the configured key is not expired; the server does not recognise it, or it was revoked.
- **No key rotates at startup.** Workstation keys are stored hashed and last 90 days (`internal/db/identity.go`). A new key is issued only when the workstation pairs again or someone creates a key by hand. Pairing again does not revoke the previous key (`RedeemPairingCode`). Nothing at computer, desktop or daemon start creates or revokes a key. The desktop only checks the stored key (`desktop/electron/server-check.cjs`). A network failure there returns "unavailable" and does not ask for a new pairing code.
- **The startup refresh never reaches this entry.** `refreshMCPConnections` (`internal/agent/agent_mcp_settings.go:103-140`) rewrites only the providers saved as `MCPConnections` from the desktop MCP tab (ADR 0023, ADR 0039 §Decision). It does so only when the address, key or executable fingerprint changed. On this workstation `~/.config/sectile/settings.json` has **no** `mcpConnections` at all. So the `sectile` entry in `~/.claude.json` came from `init`/Initialize, `sync_config` or a hand-made `claude mcp add`, and no code path ever updates its key.
- **This workstation re-paired at least once recently.** The device id in `settings.json` differs from the one in `settings.json.bak-layout0` (saved 2026-09-28 23:22). The oldest backup (2026-09-18) still pointed to a local server on `127.0.0.1`. The agent log shows the switch from `localhost:8090` to the remote server. Every new pairing gives the daemon a new key. A `sectile` entry written before that pairing keeps the old key, and that key is refused once revoked from the profile.
- **Alternatives that already exist:**
  - Local HTTP mode: a loopback URL and no key in the file (`internal/agentconfig/mcp.go:140-160`, ADR 0023). Its port is refreshed at start, because 8091 may be taken (`internal/agent/agent.go:447-457`).
  - The stdio bridge `sectile-agent mcp`. It reads only `SECTILE_AGENT_TOKEN`/`--token`, not the stored key, which the desktop keeps OS-encrypted.
  - The Claude plugin (ADR 0039), which also uses a static key.
  - None of them supports `headersHelper`, OAuth or `mcp-remote`.

**Root cause (supported, not yet proven):** the key in `~/.claude.json` is stale or revoked, and Sectile never refreshes it, because that entry is not a saved desktop MCP choice. The 401 text confirms that the key is unknown or revoked. The evidence does **not** yet show why it went stale, or that a restart causes it. A key comparison was not done in this run; the workstation's permission policy blocks reading the credential.

### Ambiguities (worst first)

1. **Is restart really the trigger?**
   - (A) The entry has been dead since a re-pairing or a key revocation. The 401 shows up after a restart only because that is when Claude Code reconnects. Then the fix is to keep the Claude entry in sync with the daemon's key.
   - (B) Something at restart makes the desktop pair again. For example, the OS-encrypted `secret` can't be read early in the session, so the desktop asks for a new pairing code and a new key is issued. Then the desktop's credential handling must be fixed as well.
   - Each reading leads to different code.
2. **Which entries Sectile may rewrite.** ADR 0023 makes MCP writes explicit, saved choices. Silently rewriting an entry the user added by hand would go against that ADR. Recording the choice when `init` writes the entry would not.
3. **Local mode as the default.** It removes the key from the file, but Claude Code then depends on the daemon running when it starts. A Claude session opened before the desktop would also fail to connect.

### Resolved technical choices (reversible)

- Keep the server's refusal as is: an unknown key stays a 401, and the message stays generic for security (`agent_api.go:118-120`).
- Any fix reuses the existing `ConfigureMCP` writer, the atomic owner-only file replacement and the fingerprint mechanism. No new file format.
- No secret or key fragment ever appears in logs, reports or desktop previews (ADR 0023).

### Open product questions (owner)

1. **Trigger.** After a restart, does the desktop ask you for a new pairing code? What do you do today to make `sectile` work again (re-pair, run Initialize, `claude mcp add`, nothing)? Your web profile lists this workstation's keys: how many are there, and are some revoked? The answers tell readings A and B apart.
2. **Deliverable.** Is a diagnosis with a manual fix enough (re-save the Claude connection from the desktop MCP tab, no code change)? Or should Sectile be changed so the problem cannot come back?
   - *Recommended:* a code change. The parent macro is about UX fixes, and the diagnosis alone does not stop it happening again.
3. **Fix direction**, if you choose a code change. *Recommended:* (a), with (c) as an optional extra.
   - (a) Make `init`/Initialize and `sync_config` save their Claude registration as an `MCPConnections` choice, so the existing startup refresh updates the key after a re-pairing. For an existing `sectile` entry the agent did not save, the desktop flags that its key is refused and offers a one-click repair. It never rewrites that entry silently.
   - (b) Make local mode (loopback, no key) the default for Claude.
   - (c) Let the stdio bridge fall back to the daemon's key.
   - (d) New authentication plumbing (`headersHelper`/OAuth).
4. **Scope if reading B is confirmed.** Should this ticket also fix the desktop asking for a new pairing code at restart, or should that be a separate ticket? *Recommended:* the same ticket, since it is the same symptom.
