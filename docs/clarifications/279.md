# Clarification - #279 - Be able to break the adjust cycle by declaring the code as reviewed

Stage: new → clarified.

Ticket: https://github.com/sebastienferry/sectile/issues/279

## Restated request and scope

Allow developers in the desktop app to break out of the perpetual "Adjust" skill loop on implemented tasks by explicitly declaring the code as reviewed, transitioning the task workflow stage from `implemented` to `reviewed` (`#reviewed` label and `to_close` status). Once a task reaches the `reviewed` stage, the desktop app must propose `handoff` as the next action (`Next: Handoff` in the execution toolbar and `Run: Handoff` on the ticket row).

Out of scope:
- Automating the Git merge itself on GitHub/GitLab (the merge remains human responsibility before or during handoff).
- Modifying the web application workflow or board columns (the web board already models `reviewed` → `handoff`).
- Creating a separate database schema migration (existing `/api/tasks/{id}/stage` and labels already handle `reviewed`).

## What the code does today (files read)

- `desktop/src/workflow.mjs:1-41`:
  - `skills` maps `new` → `clarify`, `clarified` → `specify`, `specified` → `implement`, and `implemented` → `implementedStep`.
  - `implementedStep(task, project)` unconditionally returns `['adjust', 'Adjust']` whenever `prUrl` is populated.
  - `nextTaskStep(task, project)` explicitly intercepts `if (stage === 'reviewed') return { stage, message: 'Awaiting human merge' }`, omitting `skillId`. Consequently, the execution toolbar hides `#next-step`.
  - `closingStep(task, project)` was added as a fallback specifically for `offerClosure` (when stopping an execution) and `updateTicketRow`, returning `{ skillId: 'handoff', label: 'Close the task' }`. It is never surfaced in `#next-step`.
- `desktop/src/main.js:1078-1128, 1144-1166, 1420-1479`:
  - `ticketRow(view, task)` renders action controls: primary `ticket-run` and `ticket-more` menu (`…`). The menu only lists server skills, `pickup`, `discuss`, and custom instructions. There is no control to transition stage or declare code reviewed.
  - `updateTicketRow(view, entry)` binds `run` to `chosen.skillId` (`adjust` when implemented, `handoff` via `closingStep` when reviewed).
  - `renderNextStep()` in the execution view displays `Next: [label]` only when `step.skillId` is defined. Because `nextTaskStep` omits `skillId` for `reviewed`, the button is hidden and only footer text `Awaiting human merge` is shown.
- `desktop/electron/preload.cjs:1-37` & `desktop/electron/main.cjs:170-220`:
  - The Electron IPC bridge exposes `launchServerTask`, `serverTasks`, `project`, etc., but lacks any `transition-stage` handler.
- `internal/agent/agent_desktop.go:150-200, 711-790`:
  - The local agent daemon handles `/desktop/tasks` (listing tasks and launching skills via `/api/tasks/{id}/run-skill`), but has no route to trigger stage transitions via `/api/tasks/{id}/stage`.
- `internal/handlers/handlers.go:1266-1320, 2098-2185`:
  - The server exposes `POST /api/tasks/{id}/stage` (and `/transition`), accepting `{"stage": "reviewed", "note": "...", "prUrl": "...", "branch": "..."}` and invoking `TransitionTaskStageBy`.
- `web/src/lib/workflow.ts:105-121` & `web/src/components/TaskCard.tsx:322-336`:
  - The web application already defines `skillForStage('reviewed') === 'handoff'` and shows `Handoff` as the primary action once a task is `reviewed`.

## Ambiguities, worst first

1. **Where the "Declare code as reviewed" gesture belongs in the Desktop UI.**
   - *Ambiguity*: Should the user declare the code reviewed from the ticket list table row, from the execution toolbar/console header, or from both?
   - *Impact*: Confining the action to the ticket list forces a developer viewing a diff or test run in the console to navigate away to transition the task. Confining it to the console prevents triaging tickets directly from the list.
   - *Decision*: Expose the action in both places:
     - In the ticket row `…` (more) menu: add an item **Declare code as reviewed** (visible when `taskStage(task) === 'implemented'`).
     - In the execution toolbar / status area: when viewing a task at `implemented` stage, provide a secondary action (e.g. **Mark reviewed** button or dialog action) alongside `Next: Adjust`.

2. **How `nextTaskStep` resolves the `reviewed` stage.**
   - *Ambiguity*: Should `nextTaskStep` return `['handoff', 'Handoff']` immediately upon reaching `reviewed`, or should it continue returning `{ stage: 'reviewed', message: 'Awaiting human merge' }` and require an out-of-band action?
   - *Impact*: Currently, `nextTaskStep` conceals `handoff`, causing the next-step button to disappear.
   - *Decision*: Map `skills.reviewed = ['handoff', 'Handoff']` in `workflow.mjs`. `nextTaskStep` will return `{ stage: 'reviewed', skillId: 'handoff', label: 'Handoff', message: 'Ready for the next step' }`.
   - *Rationale*: This aligns desktop directly with the web application (`skillForStage('reviewed') === 'handoff'`). The ticket explicitly requires: *"once the code is ok, we should migrate to the #reviewed state and proposed the handoff."* When launched, the `handoff-issue` skill safely validates whether the PR is merged into `main` before cleaning the workspace, aborting with a clean status message if the merge is still pending.

3. **Interaction model for declaring code reviewed.**
   - *Ambiguity*: Should clicking "Declare code as reviewed" execute immediately, or prompt for confirmation?
   - *Impact*: An accidental click could advance a task and trigger tracker updates prematurely.
   - *Decision*: Use a lightweight confirmation dialog (matching `offerClosure` and `rerun` dialog patterns) stating: *"Declare <key> as reviewed? This transitions the task to #reviewed and proposes Handoff after human merge."* with a **Confirm** button.

4. **Desktop IPC and local agent routing.**
   - *Ambiguity*: Should the desktop renderer call the Sectile server directly or route through the local agent daemon?
   - *Impact*: Direct calls bypass local agent credential handling and daemon connection state.
   - *Decision*: Route through `localAgent.transitionStage(taskId, stage, note)` -> Electron IPC `transition-stage` -> Local Agent endpoint `POST /desktop/tasks/transition` -> Server `POST /api/tasks/{id}/stage`.

## Critical dependencies

- None external.
- Sectile server `/api/tasks/{id}/stage` endpoint is already implemented and handles `#reviewed` transitions, database updates, and tracker synchronization.
- No database migrations or new tracker adapters needed.

## Settled scope and assumptions

1. **IPC & Local Agent Daemon**:
   - Add `transitionStage(taskId, stage, note)` to `desktop/electron/preload.cjs` and handle it in `desktop/electron/main.cjs`.
   - Add endpoint in `internal/agent/agent_desktop.go` to proxy transition requests to `POST /api/tasks/{id}/stage`.
2. **Workflow logic**:
   - In `desktop/src/workflow.mjs`, define `reviewed: ['handoff', 'Handoff']` in `skills` so `nextTaskStep` proposes `handoff` for reviewed tasks.
   - Retire the special-casing in `nextTaskStep` that hid the next skill for `reviewed`.
3. **UI integration**:
   - In `desktop/src/main.js`:
     - Add **Declare code as reviewed** to the ticket row menu when the task is `implemented`.
     - Add a **Mark reviewed** secondary action in the execution toolbar when viewing an `implemented` task.
     - Confirmation dialog confirms and executes the transition, followed by `refresh()`.
     - With `nextTaskStep` returning `handoff`, the toolbar automatically displays `Next: Handoff` and the row displays `Run: Handoff`.
4. **Test coverage**:
   - Update `desktop/tests/workflow.ui.cjs` and `desktop/tests/next-step.ui.cjs` to assert that `stage === 'reviewed'` resolves to `handoff`.
   - Add test cases for the "Declare code as reviewed" action and transition flow.
