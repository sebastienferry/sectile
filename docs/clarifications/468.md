### Restatement

Clicking **My Tasks** in the sidebar must narrow the board to the tickets assigned to the
signed-in user, on every tracker the board shows (GitHub, Jira, local), alone or combined
in "All projects" and saved views. Out of scope: the assignee picker in the header, the
assignment of a ticket itself (who gets assigned, write-back to the tracker), and the
account display name, which #348 settled.

### Diagnosis: why it matches nothing

The button sends `assignee=<settings.userName>` and the database compares it with
`assignee = ?`, an exact, case-sensitive string match. Since #348, `settings.userName` is
the **account display name** (`chosen_name → display_name → email → id`). But:

| Source | What `tasks.assignee` holds | Matches the display name? |
| --- | --- | --- |
| GitHub | the assignee's **login** (`sebastienferry`) | practically never |
| Jira | the assignee's Atlassian **displayName** (else accountId) | only if the Sectile name is typed exactly as in Atlassian |
| Local | whatever label was picked in the assignee field | only by coincidence |

Two secondary defects follow from the same design:

- A single string cannot match both a GitHub login and a Jira display name, so on "All
  projects" or a saved view mixing trackers the filter is wrong even for a correct name.
- The value is frozen into the per-view filter memory (`sectile_filters_view_<id>`,
  `assignee: 'Alice'`), and `isMyTasksActive` compares it to the current name: renaming the
  account leaves a stale filter that the button no longer shows as active.

### Ambiguities (worst first)

1. **What identity is "me" on each tracker.** Reading A: the tracker identity of the user's
   personal credential (GitHub login from `/user`, Jira display name/accountId from
   `/myself`). Reading B: a handle the user types per tracker in their profile. Reading C:
   the account name and e-mail only, compared loosely. They lead to different code and
   different storage. → product question 1.
2. **What happens when no tracker identity is known** (no personal credential, only the
   server-wide token, whose identity is not the user's). Hide/disable, fall back to the
   name, or explain. → product question 2.

### Dependencies

- Personal tracker credentials (`user_tracker_credentials`) are the only place a user's
  tracker identity can be derived from; a deployment using only the server-wide token has
  none. A sealed, still-locked credential cannot be probed either.
- The tracker identity is not stored today; deriving it on each board load would call
  GitHub/Jira on the read path. Caching it (on credential save/verify) likely needs a new
  column or table, a numbered migration in `migrations.go`, never the baseline.
- Jira `assignee` is a display name, not an accountId: matching on accountId would require
  syncing and storing `assignee_account_id` (another migration plus a re-sync).

### Technical choices resolved from the code (reversible)

- **Resolve "mine" on the server, not in the client.** The client sends `mine=1` (a new
  flag) instead of a literal name; `GET /api/tasks` resolves the caller's identities from
  the session and applies `assignee IN (…)` per source. This fixes mixed-tracker scopes,
  makes the per-view memory store a flag instead of a name, and keeps
  `assignee=<name>` for the header's person picker unchanged.
- **Button state is the flag**, not a string comparison with `userName`; the header chip
  shows "My Tasks" rather than a name.
- **Jira matches on the display name** already stored in `tasks.assignee` (no
  `assignee_account_id` migration in this ticket), compared case-insensitively and trimmed.
- **Identities are cached, not probed per request:** recorded when a personal credential is
  saved or verified (the existing `checkAccount` / `/myself` probes already return them).
- **Local tasks** match the account's `Name()` and e-mail, case-insensitively.
- **Tests:** a Go test of the `mine` resolution per source, and the browser test in
  `board-views.browser.mjs` extended to assert the flag rather than `assignee=Alice`.

### Product questions

1. **Where does the tracker identity come from?**
   - (a) *Recommended:* derived automatically from the user's personal tracker credential
     (GitHub login, Jira display name), plus the account name and e-mail for local tasks.
     Nothing to type; exact on GitHub.
   - (b) (a) plus an optional, editable "tracker handle" per tracker in the profile, for
     users who have no personal credential.
   - (c) Manual handles only.
2. **When a tracker in scope has no known identity for the user** (no personal credential):
   - (a) *Recommended:* the filter still applies with the account name and e-mail as a
     fallback, and the button's tooltip says which trackers lack an identity and how to fix
     it (add a personal credential).
   - (b) the button is disabled for those scopes with the same explanation.
3. **Changelog:** the fix is user-visible, so it adds a `Fixed` line under `[Unreleased]`
   ("My Tasks now finds the tickets assigned to you on GitHub and Jira"). Confirm.

## Round 2 - answers from the owner (2026-09-25)

The owner accepted every Round 1 recommendation. All three questions are settled and **no
prior assumption is reversed**.

1. **The tracker identity is derived from the personal tracker credential.** GitHub: the
   `login` returned by `/user` for the user's own token. Jira: the `displayName` returned by
   `/rest/api/3/myself` for the user's own credential. Local tasks: the account's `Name()`
   and e-mail. No manual "tracker handle" field is added.
2. **No known identity falls back to the account name and e-mail.** The filter still
   applies on a tracker for which the user has no personal credential (or a sealed one not
   yet unlocked), matching the account `Name()` and e-mail. The button's tooltip names the
   trackers in scope that lack an identity and says that adding a personal credential fixes
   it. The button is never disabled.
3. **Changelog:** a `Fixed` line under `## [Unreleased]`, along the lines of "My Tasks now
   finds the tickets assigned to you on GitHub and Jira".

### Settled contract (what an implementation must satisfy)

- `GET /api/tasks` accepts `mine=1`. The server resolves the caller from the session and,
  per task source, keeps the tasks whose `assignee` equals (trimmed, case-insensitive) one
  of the caller's identities for that source: the cached tracker identity when known, the
  account `Name()` and e-mail otherwise, and always for local tasks. It combines with
  every other filter, with `projectId`, "All projects" and `viewId`.
- `assignee=<name>` keeps its current meaning for the header's person picker.
- The tracker identity is cached when a personal credential is saved or verified (the
  existing `checkAccount` and `/myself` probes), never probed on the board read path.
  Storage goes through a new numbered migration in `migrations.go`, never the frozen
  baseline.
- The web client sends `mine=1`; the button's active state, the per-view filter memory
  and the header chip carry the flag, not a name. A value stored by the old code
  (`assignee: <name>`) keeps working as a plain person filter.
- The tooltip lists the trackers in scope without an identity (the server exposes which
  sources resolved to a fallback).
- Tests: a Go test of the `mine` resolution per source (GitHub login, Jira display name,
  local name/e-mail, fallback without credential); `board-views.browser.mjs` asserts
  `mine=1` instead of `assignee=Alice`.
- `CHANGELOG.md`: the `Fixed` line of answer 3.

### Out of scope (unchanged)

The header's person picker, how tickets get assigned or written back, the account display
name (#348), and matching Jira on `accountId` (would need an `assignee_account_id` column
and a re-sync; raise separately if homonyms become a problem).

## Specification note (2026-09-25)

Recorded while writing `specs/468-my-tasks-filter/`. It refines answer 2 of Round 2
without reopening a question.

- **A sealed, locked personal credential keeps its confirmed account.** Round 2 listed "a
  sealed one not yet unlocked" among the cases that fall back to the account name and
  e-mail, because it assumed the identity was probed when the board is read. The
  specification caches the account instead, when the tracker confirms the credential
  (save or verify). The account is a login or a display name, not a secret, so it is
  stored in clear next to the sealed record and stays readable while the credential is
  locked. The owner accepted this on 2026-09-25: a sealed and locked credential whose
  account was confirmed keeps that account for My Tasks (spec FR 5). Only a credential
  never confirmed, or none at all, falls back.
