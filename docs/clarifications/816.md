### Settled technical choices and proposed baseline

1. Reuse inventory-backed online eligibility and existing authorization. Do not expose other users' workstation credentials or route to a machine that lacks the project.
2. Use the existing deviceId wire field for the selected target; treat targetDeviceId in the ticket as the conceptual target unless the owner requires a new public alias.
3. Add structured workstation attribution rather than parsing a device ID from summary text. Resolve a readable label from paired-device metadata, with a device ID fallback. Preserve attribution for historical runs and reconnects.
4. Present cancellation explicitly in the task panel and activity view; reuse the existing stop-versus-force-close distinction. Align activity cancellation with remote-run ownership and process cancellation semantics.
5. Preserve queued/pending/running protection, completion validation, and existing workflow handback behavior.
6. Cover selection, disappearing targets, queued/pending cancellation, running agent cancellation, unreachable-agent force close, permissions and subsequent relaunch through relevant server and UI tests during implementation.
7. Add English user-facing changelog entries at implementation; preserve each runtime surface's existing locale.

### Essential product questions — owner answers required

1. **Automatic recovery after disconnect.** A workstation can lose its server connection while its local process continues. Should automatic recovery close the record after a timeout even without proof of termination? Recommended: retain an unconfirmed running run, visibly mark the workstation unavailable, and let the owner/admin explicitly force-close it; automatically close only proven orphaned runs. Alternative: expire unconfirmed runs after a specified grace period, explicitly record that the local process may continue, and define how late completion/reconnection is handled. If the alternative is wanted, provide the grace period and whether an expired run is failed or canceled.
2. **Launch entry points and defaults.** Recommended: all Web task skill launches, including card shortcuts, go through the same selection logic; auto-select the sole eligible workstation, require an explicit choice when several are available, and block agent execution with a clear explanation when none are available. No remembered device preference in this ticket. Alternative: add the picker only to a specific launch surface, leaving other entry points unchanged; identify that surface if preferred. Macro and batch launches need an explicit scope decision: recommended exclude macros, include task batches only when every selected task is available on the chosen workstation.
3. **Scope confirmation.** Are the recommendations and exclusions above satisfactory as the baseline for specification? In particular, automatic rerouting and changing Desktop launch UX are excluded, and forced recovery clears the run record without claiming the disconnected process stopped.
