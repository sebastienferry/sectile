## Round 1 - initial report (2026-09-28)

### Restated request and scope

A Git folder attached to a project in the desktop settings while a session is
running on one of its tasks must be usable by that session right away:
`prepare_repository_worktree` must accept the repository, and `transition_stage`
must then accept its pull request in `prUrls`, without restarting the desktop app
or launching a new run. If that cannot be done for a reason that turns out to be
by design, the refusal must at least say that the attachment only applies to new
runs.

Out of scope: refreshing the environment of a running agent process
(`SECTILE_REPOSITORIES` and the folder list in the launch prompt are a launch
snapshot and cannot be changed from outside the process), accepting a pull request
in `prUrls` for a repository the task never prepared, and linking argocd-pl-tooling
!844 to SFE-376 (the owner does it once the fix is in, or from the task detail view).

### Verified findings

Files read: `internal/agent/repositories.go`, `internal/agent/attached.go`,
`internal/agent/agent_operations.go`, `internal/agent/agent_config.go`,
`internal/agent/agent_desktop_repositories.go`, `internal/agent/agent.go`
(launch environment), `internal/agentconfig/settings.go`,
`internal/agentconfig/local.go`, `internal/db/repositories.go`,
`internal/db/stageprs.go`, `internal/db/agentoperations.go`,
`internal/handlers/agent_operations.go`, `internal/agentmcp/mcp.go`, and the
attached-folders panel in `desktop/src/main.js`.

- **The ticket's likely cause is contradicted by the code.** Nothing on the path of
  `prepare_repository_worktree` reads the launch context or caches attachments:
  - the MCP bridge (`agentmcp`) forwards the call to the server as is;
  - the server (`DB.PrepareRepositoryWorktree`) does not check the repository
    against attachments, it relays a `repository_worktree` operation to the
    caller's agent (`AgentDispatcher.CallOperation`, routed by user and project);
  - the agent (`executeOperation`) calls `localProjectRoot`, which reads
    `~/.config/sectile/settings.json` from disk on every operation, then
    `repositoryWorktree` -> `repositoryFolder` -> `attachedFolders`, which lists
    `projectSettings[<project>].folders` and runs `git rev-parse` and
    `git remote get-url origin` on each folder at each call.
  - The desktop "Attach folder" button calls `POST /desktop/folders` on the local
    agent, which writes the folder to the same file immediately (`editFolders`,
    under the settings lock). There is no deferred save.
- `SECTILE_REPOSITORIES` is only written into the launch environment
  (`agent.go`, run launch) and in the launch prompt. No server or agent code reads
  it back to decide anything: it is informative only.
- The workstation settings today hold the attachment: project SFE
  (`0f862b4e-...`) lists `/Users/sferry/Sources/iac/argocd/argocd-pl-tooling` among
  its folders, and the folder has an origin. Read statically, the same call should
  succeed now, from an old or a new session.
- The `transition_stage` refusal is a consequence, as the ticket says:
  `validateStagePRs` only accepts links in the task's changed repositories, and a
  secondary repository becomes changed only when `PrepareRepositoryWorktree`
  succeeds (`AddChangedRepository`). Its message does not say how to make a
  repository changed.

So the bug is real as observed, but its cause is not the one written in the
ticket, and it cannot be located by reading. Candidates, none verified:

1. the operation was answered by another agent connection than the one the
   desktop wrote through (two agents connected for the same user and project,
   for example the desktop's agent and a separately started one, or a stale
   route after a reconnection), whose view differs (older build, other `HOME`);
2. the attachment was first saved on another project (a project picked by
   mistake), then moved;
3. something on this path that only a live repro shows (a `git` call failing in
   the agent's environment for that folder at that moment, reported as "not
   attached" because `describeFolder` swallows the error).

Candidate 3 matters whatever the cause: `describeFolder` turns any `git` failure
into "not a Git folder / no remote", and `repositoryWorktree` then answers "not
attached", which sends the owner to attach a folder that is already attached.

### Critical dependencies

- A reproduction. The specification stage cannot choose a fix before one of the
  candidates is confirmed. The plan is a Go test driving `POST /desktop/folders`
  then the `repository_worktree` operation on the same daemon (expected green,
  which rules out caching), plus a manual repro on the owner's workstation with
  the agent log open.
- No migration, no server contract change expected for the fix itself.

### Reversible technical choices resolved

- Refusals of `repository_worktree` name the actual reason: folder not attached
  to this project, attached but not a Git checkout, attached but without an
  origin, attached with another origin, or `git` failing (with its message).
  They stay in French, as the surface already speaks it.
- The `transition_stage` refusal for a link outside the changed repositories adds
  that a repository becomes changed by calling `prepare_repository_worktree` for it.
- `SECTILE_REPOSITORIES` and the prompt folder list stay a launch snapshot; the
  tool description says that `prepare_repository_worktree` reads the current
  settings and is the source of truth.

### Product questions for the owner

1. **Can you still reproduce it?** From an already running session, after
   attaching a new folder, does `prepare_repository_worktree` still refuse it? If
   you have the agent log of the SFE-376 run (2026-09-28), or can tell whether two
   agents were connected at the time (desktop app and a separate `sectile agent`,
   or another workstation), that decides the fix.
   Recommendation: if it no longer reproduces, the ticket becomes "report the real
   reason of a refusal" (the choices above), and caching is ruled out by a test.
2. **Should `prUrls` accept a pull request in an attached or project repository
   that the task never prepared through `prepare_repository_worktree`** (for
   example a branch pushed from the main checkout), recording it as changed on the
   way? Recommendation: no, keep the rule and only improve the message; accepting
   it would need the server to ask the agent about attachments during
   `transition_stage`.

## Round 2 - answers from the owner (2026-09-28)

Answers given interactively in the clarification session.

### Settled choices

1. **Reproduction (question 1):** the owner does not know whether it still
   reproduces. The specification stage starts with the reproduction: a Go test
   that attaches a folder through `POST /desktop/folders` and then runs the
   `repository_worktree` operation on the same daemon, plus a manual repro on the
   owner's workstation with the agent log open, checking how many agents are
   connected for the user and project. The fix follows the confirmed cause. Whatever
   the cause, the refusals name the actual reason (resolved choices of round 1).
2. **`prUrls` (question 2):** no. `transition_stage` keeps accepting pull requests
   only in the task's changed repositories. Its refusal says to call
   `prepare_repository_worktree` for the repository first.

### Reversed assumptions

None. The round 1 finding stands: the ticket's "likely cause" (launch-context
snapshot or cached attachments) is contradicted by the code, and
`SECTILE_REPOSITORIES` stays a launch snapshot that nothing decides on.

### Settled scope

- Reproduce, then fix the confirmed cause so that an attachment applies to the
  calls that follow it, including from a running session. If the cause proves to
  be by design (for example an operation answered by another workstation), the
  refusal says so instead.
- `repository_worktree` refusals name the actual reason: folder not attached to
  this project, attached but not a Git checkout, attached without an origin,
  attached with another origin, or `git` failing (with its message). The wording
  stays in French.
- The `transition_stage` refusal of a link outside the changed repositories points
  at `prepare_repository_worktree`.
- The `prepare_repository_worktree` tool description says it reads the current
  workstation settings, and that `SECTILE_REPOSITORIES` is the launch snapshot.
- Out of scope: refreshing a running process's environment, accepting unprepared
  repositories in `prUrls`, linking argocd-pl-tooling !844 to SFE-376.
- A changelog line under `Fixed` is expected, since the refusal messages and the
  behaviour are visible to users.
