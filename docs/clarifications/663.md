## Round 1 (2026-10-01)

### Restated request and scope

A macro (epic) on the roadmap carries an ordered list of one-line todos, each a
pre-ticket for a story to come. People can reword, add, remove and reorder those
todos (the order is the intended order of execution), the list is mirrored as a
single comment on the epic in the tracker that Sectile updates whenever the list
changes, and the list can be read and written through the Sectile MCP server,
which the `refine-macro` skill uses to save the todos it proposes.
Out of scope: changing how a todo becomes a story (single and batch creation,
#634), the readiness and axes of an epic (#633, #635), the heuristic "Refine"
button of the panel, and any write to an epic of a declared roadmap project
(ADR 0043).

### Verified findings

Files read: `internal/models/models.go` (`MacroMeta`, `MacroTodo`),
`internal/db/macros.go` (`SaveMacroMeta`, `saveMacroMetaKeys`, `UpdateMacro`,
`CreateStoriesFromMacroTodos`, `RefineMacro`), `internal/db/macroaxes.go`,
`internal/taskmcp/server.go` (tool list), `web/src/components/RoadmapView.tsx`
(framing panel), the `refine-macro` skill
(`internal/skills/testdata/golden/refine_macro.speckit.skill.md`) and
`docs/adrs/0043-declared-roadmap-projects-are-read-except-new-stories-and-opted-in-axes.md`.

- **Todos already exist** as the macro's "slicing" checklist: `MacroMeta.Todos`
  is an ordered `[]MacroTodo` (`id`, `text`, `done`, `storyKey`, target project,
  source kind/entry) stored as JSON in the `macros.todos` column. The ticket's
  "Todos" are these lines; no new entity is needed.
- **The panel** (framing mode of `RoadmapView.tsx`) can add a line, tick it,
  pick its target project, create its story (one or a batch) and delete it.
  It **cannot reword** a line (the text is a plain `<span>`) and **cannot
  reorder** lines (no drag handle, no move action). The array order is already
  the persisted order, so reordering needs no schema change.
- **Nothing reaches the tracker**: `UpdateMacro` says "the horizon, the framing
  and the slicing are Sectile's own"; only title, description and closed state
  travel to a GitHub milestone. The framing comment is local too, despite its
  name.
- **On GitHub a macro is a milestone** (`githubMilestoneMacros`). A GitHub
  milestone has a description but **no comments**, so "a comment inside the
  epic" cannot exist there as such. Jira epics and GitLab epics are issues or
  work items that do take comments.
- **The MCP server exposes no macro read or write**: `prepare_macro_worktree`
  returns the todos read-only, and there is no tool to save them.
- **The `refine-macro` skill** only *outputs* a proposed list ("Do not overwrite
  existing todos or tasks without user confirmation in the UI"); a person then
  has to retype or import it.
- ADR 0043 already refuses the framing comment on a declared roadmap project's
  epic; the todo comment falls under the same rule.

### Ambiguities (worst first)

1. **Source of truth and direction of the comment.** Either the Sectile list
   is authoritative and the comment is a mirror Sectile rewrites, or the comment
   can be edited on the tracker and is read back into the list. The second needs
   parsing, conflict handling and a sync path; the first does not.
2. **Where the comment lives on GitHub**, where a macro is a milestone with no
   comments.
3. **When the comment is written**: on every save of the list, or on an
   explicit "publish" gesture.
4. **Rewording a line that already has its story**: rename the story as well,
   or only the line.

### Critical dependencies

- Tracker APIs to create **and update** one comment per epic: Jira comment
  update, GitLab epic or work-item notes, GitHub milestone description (see Q2).
  The comment id must be stored per macro: a new column, added in
  `internal/db/migrations.go` only, never in the frozen baseline.
- Tracker writes need an acting person with a personal token or the unattended
  marker (#482); a save without one must not lose the local list.
- Tracker comment size limits (GitHub 65,536, Jira about 32,767 characters) for
  long lists.
- ADR 0043: no comment write on a declared roadmap project's epic.

### Reversible technical choices (settled from the code)

- Reuse `MacroTodo` and the `macros.todos` column; the order of the array is the
  order of execution. No new table.
- Reordering in the panel by drag and drop, with keyboard move up/down for
  accessibility, saved through the existing `persist(..., { todos })` path.
- Rewording by inline edit of the line text, saved the same way.
  `saveMacroMetaKeys` already keeps a line's story key across saves.
- MCP: add `get_macro` (meta and todos of one macro) and `update_macro_todos`
  (the full ordered list, matched by line `id`, new lines without an id get
  one; story keys are preserved as today). Both take `projectId` and `macroKey`,
  like the other macro tools.
- `refine-macro`: after the owner confirms the proposed list in the session, it
  saves it with `update_macro_todos` instead of only printing it.
- The comment write goes through the same queued tracker crossing point as the
  axes (`macroTracker`), so a refused or failed write is retried and reported,
  never lost locally.
- The comment carries a stable marker (an HTML comment) so Sectile finds and
  updates its own comment and never edits a person's comment.

### Product questions (recommended option first)

1. **Source of truth.** Recommended: the Sectile list is authoritative; the
   tracker comment is a read-only mirror Sectile rewrites, and an edit made by
   hand on the comment is overwritten at the next save. Alternative: two-way,
   with the comment parsed back into the list.
2. **GitHub milestones.** Recommended: on GitHub, mirror the list in a
   marker-delimited block at the end of the milestone description (the only
   place a milestone has); on Jira and GitLab, a comment on the epic.
   Alternatives: no mirror on GitHub, or a comment on a pinned issue.
3. **When the comment is written.** Recommended: automatically after each save
   of the list (debounced, queued). Alternative: an explicit "Publish the todos"
   button.
4. **Rewording an attached line.** Recommended: the line only, the story keeps
   its title. Alternative: rename the story too.
