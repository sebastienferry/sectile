## Round 1: analysis (2026-09-23)

### Request restated

Give every running `sectile-server` process an identity and a heartbeat in the
database, stamp the work it owns with that identity, and replace the global restart
sweep with one that only reclaims the work of processes that are dead, so that a
second replica or a rolling deploy with surge no longer cancels the live replica's
jobs and client-owned runs. Out of scope: routing agents, MCP sessions or events
between replicas (#405, #406, #408), auto-sync coordination (#404), `DB.mu` races
(#407), readiness probe and operator docs (#410).

  orphan report, queue worker, seed), `recoverInterruptedRuns` (two global

### Correction to the ticket text

The acceptance criterion "new columns follow the ADR 0016 rule: CREATE TABLE, legacy
ALTER and `lateColumns`" is outdated: since ADR 0021 a new column goes in a numbered
migration and nowhere else. This ticket adds migration version 3. Another branch
merging its own version 3 first means renumbering on rebase.

### Ambiguities, worst first

**A1: What "multi-replica mode is refused on SQLite" means (open, Q1).** There is no
mode switch today. Two SQLite server processes on one file are dangerous now and stay
dangerous; the readings differ in code:

- (a) *Lock file*: the server takes an exclusive OS lock on a file beside the SQLite
  database (released by the kernel on crash) and refuses to start when another
  process holds it. Released even after a crash; needs a Windows implementation
  beside the Unix one.
- (b) *Heartbeat check*: at boot on SQLite, a fresh heartbeat from another instance
  refuses the start; a crashed process leaves a fresh row for up to the liveness
  bound, so a quick restart after a crash is refused (or has to wait) unless the row
  is recognised as ours through host and PID.
- (c) *No detection*: SQLite keeps its single-process assumption, documented; the
  criterion is dropped from this ticket.

**A2: Upgrade from a version without instance ownership (resolved, D5).** Rows written
by the previous version carry no owner.

**A3: Where the address of an instance comes from (resolved, D7).** The ticket lists an
internal address, but nothing in this ticket reads it.

**A4: Graceful shutdown (resolved, D8).** The server does not handle SIGTERM today.

### Critical dependencies

- PostgreSQL for any multi-replica test; the suite skips without
  `SECTILE_TEST_POSTGRES_DSN`, which must never point at a real database (it is
  emptied).
- Migration numbering shared with every concurrent branch (version 3).

### Resolved technical decisions (reversible, settled here)

- **D1: Instance identity.** A random id generated per process start. A
  `server_instances` table (`id`, `hostname`, `pid`, `started_at`, `last_seen`) holds
  one row per live process.
- **D2: Lifecycle is started by the server, not by `db.Open`.** A `StartInstance`
  call in `cmd/server/main.go`, like `StartAutoSync`, registers the row and starts the
  heartbeat and the reaper. `sectile-migrate` and tests open the store without
  becoming an instance.
- **D3: Ownership stamp.** `task_activities.instance_id` (migration 3). Every
  activity inserted through `insertTaskActivity` or the remote-run insert carries the
  inserting instance, which is also the one executing it (the job queue is
  in-process). `SessionRegistry.Adopt` re-stamps a client-owned run with the instance
  holding the MCP session. Agent-dispatched runs (`RunActionAgent`) stay out of every
  sweep, as ADR 0006 requires.
- **D4: Scoped sweep.** The reaper, running in every instance, reclaims `running`,
  `queued` and `pending` activities whose `instance_id` names an instance not seen for
  the liveness bound, with the existing statuses and messages (`failed` "Interrupted
  by server restart" for server work, `canceled` for client-owned runs), then deletes
  the dead instance's row. The reclaim is one conditional `UPDATE` per kind, so two
  survivors reclaiming at once do the same work once.
- **D5: Legacy rows.** At the first start of this version, rows with an empty owner
  are reclaimed as today. During a rolling upgrade from the previous version, that
  one start still cancels the old pod's work, once; from then on the sweep is scoped.
- **D6: SQLite keeps an immediate recovery.** SQLite serves one process by
  construction, so at boot every other instance row is declared dead and its work
  reclaimed immediately, which is today's behaviour after a restart. PostgreSQL waits
  for the liveness bound.
- **D7: No address column yet.** #406 is the first reader of an instance address and
  adds it with its own migration and configuration.
- **D8: No signal handling in this ticket.** A stopped replica's work is reclaimed by
  a survivor once its heartbeat expires. Graceful shutdown belongs to #410 with the
  readiness probe.
- **D9: Bounds.** Heartbeat every 10 s, dead after 45 s without one, reaper pass every
  15 s. Constants with test overrides, no new environment variable.

### Open product questions

**Q1: How is multi-replica refused on SQLite?** Recommendation: **(a) the lock file**.
It is the only reading that is right both after a crash and with two processes
started together, and it also protects the desktop and development setups where two
servers can open one file today.
