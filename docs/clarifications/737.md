# Clarification #737 - Agent: option to work in any repository, not only the project's

Ticket: https://github.com/sebastienferry/sectile/issues/737
Branch: `feat/737`

## Round 1 (2026-10-05)

### Request

On a project with many repositories, an option lets the agent change a
repository the project neither declares nor maps nor attaches: the agent names
a local checkout it found, or Sectile clones the repository, and the worktree,
branch and pull request then work as for a declared repository. Out of scope:
searching the workstation from Sectile itself, changing what a pinned ticket's
primary repository is, and the "change only in a secondary repository" case
raised in the second comment (see Q6).

### Code read

- `internal/agent/attached.go`: `repositoryFolder`, `attachedFolders`,
  `describeFolder`.
- `internal/agent/repositories.go`: `repositoryRoot`, `primaryRoot`,
  `repositoryWorktree`, `repositoryNotFound`, `removeRepositoryWorktrees`,
  `rememberConvertedFolders`.
- `internal/agent/agent_config.go`: `ensureLocalWorktree`.
- `internal/agent/agent_run_folders.go`: `desktopRunFolder` (attach a folder
  to a running session, `/add-dir` typed in, #676/#689).
- `internal/db/repositories.go`: `PrepareRepositoryWorktree`,
  `AddChangedRepository`.
- `internal/db/stageprs.go`: `taskPullRequestScope`, `validateStagePRs`.
- `internal/agentconfig/claude_sandbox.go`, `internal/agentconfig/workstation.go`:
  the Sandbox values of #700/#730 and the workstation `Defaults`.

### Findings that shape the design

1. **The server is already open.** `PrepareRepositoryWorktree` accepts any
   remote URL or `host/path`, declared or not, and records it with
   `AddChangedRepository`. The whole restriction is on the agent side, in
   `repositoryFolder`.
2. **The workstation mapping is not project-scoped.** `repositoryRoot` reads
   `Settings.Repositories[identity]`, a workstation-wide map from repository
   identity to folder, without checking that the project declares the
   repository. The desktop only offers it for declared repositories, but the
   agent already honours any entry, and `rememberConvertedFolders` already
   writes entries itself. "Remembering" a found or cloned checkout is therefore
   one write to this map, and needs no new storage.
3. **Handoff cleanup depends on it.** `removeRepositoryWorktrees` finds each
   changed repository through `repositoryFolder`. A repository used through a
   one-off `path` and not remembered would be reported "not found on this
   workstation" at handoff and its worktree left behind. Remembering is
   therefore required, not optional.
4. **No fetch before branching.** `ensureLocalWorktree` creates a missing
   branch from `origin/<branch>` when the remote has it, else from the
   checkout's current `HEAD`, without `git fetch`. A stale clone, or a clone
   left on a feature branch, gives a stale or wrong base. This already holds
   for declared repositories.
5. **The agent receives only the identity.** The operation sent to the agent
   carries `Repository: target.Identity` (`host/path`), not the URL. Cloning
   needs a URL, so the operation must carry the one the caller gave.
6. **A running session does not see a new folder.** A launch passes the
   project's mapped and attached folders as `--add-dir`. A worktree created
   mid-run in a folder that was not among them is outside the session's
   directories, and outside what the Claude Code sandbox lets it write. The
   attach-from-run path (`desktopRunFolder`) already solves this by typing
   `/add-dir` into the session; the new path must do the same.
7. **A ticket whose only change is in a secondary repository is refused.**
   `validateStagePRs` always requires a pull request for the primary
   repository; only secondary repositories may be skipped as unchanged. This
   confirms the second comment's concern but is independent of this option.

### Ambiguities, worst first

1. **Who finds and who clones.** "The agent finds the checkout, may clone it"
   reads either as the AI session searching and cloning with its own shell, or
   as Sectile's agent daemon doing it. The two differ in code (a new MCP
   parameter versus a new daemon operation) and in security (the Claude Code
   sandbox applies to the first only). See Q2 and Q3.
2. **Level of the option.** Workstation, project, or both. See Q1.
3. **Whether the fetch fix covers declared repositories too.** See Q5.

### Critical dependencies

- **MCP catalogue and bridge.** A new `path` parameter on
  `prepare_repository_worktree` changes its schema: `internal/agentmcp`
  whitelist, `internal/mcptest/contract.go` and the count tests follow.
- **Agent protocol.** The operation gains the repository URL and the optional
  path; an older agent must be told apart, as `worktree.Repository` already
  does today.
- **Claude Code sandbox (#730).** A clone run by the daemon is outside the
  sandbox. The worktree it creates must still be added to the running session
  (`/add-dir`), and the sandbox must allow writing there. Claude Code treats
  `--add-dir` folders as writable in its sandbox; to be verified during
  implementation rather than assumed.
- **Credentials.** A clone by the daemon uses the workstation's own git
  configuration (SSH agent, credential helper), as every other git call of the
  agent does. Sectile stores no git credentials.
- **Windows.** Every new `git` call goes through `agentexec.Hidden` (AGENTS.md).

### Technical choices settled from the code

- **Keep `prepare_repository_worktree` in the path** (first comment): it is
  what records the repository as changed, so its pull request is accepted,
  shown and cleaned up. A hand-made `git worktree add` stays unsupported.
- **`path` is checked, not trusted.** The agent accepts it only when it is an
  absolute folder, the top level of a Git checkout, and its `origin` has the
  requested identity. Otherwise the call is refused with the reason.
- **A folder accepted through `path` or a clone is remembered** in the
  workstation mapping `Settings.Repositories`, unless that identity is already
  mapped (finding 2 and 3). An existing mapping wins over `path`.
- **Clone URL.** The URL the caller gave is used as is. When it gave only
  `host/path`, the URL is built in the scheme of the project's code remote
  (SSH when the code remote is SSH, HTTPS otherwise).
- **New worktree visible to the running session** through the existing
  `/add-dir` path of `desktopRunFolder`.
- **French runtime messages stay French**, new ones follow the project's rule
  for user-facing strings.

### Product questions

**Q1. Where does the option live?**
- (a) **Recommended:** per project, on the workstation (desktop project
  settings, `ProjectSettings`), off by default. The risk (disk, credentials,
  which repositories may be touched) is the workstation's, and the need is the
  multi-repository project's.
- (b) Workstation-wide, with a project whitelist as the Sandbox values of #730.
- (c) A project setting on the server, shared by every workstation.

**Q2. How is a checkout found?**
- (a) **Recommended:** the AI session finds it (memory, its own search) and
  passes it as `path`; Sectile itself never scans the disk.
- (b) Sectile also searches configured roots (for example `~/Sources`) when no
  `path` is given.

**Q3. Cloning**
- (a) **Recommended:** allowed when the option is on, done by the agent daemon
  when no mapping, attachment or `path` answers, into a "clones folder" set
  next to the option (default `<parent of the project checkout>/<repo name>`),
  with the workstation's git credentials. The clone is then remembered.
- (b) Not done by Sectile: the AI session clones with its own shell (needing
  the sandbox's network host and writable folder of #730), then passes `path`.
- (c) No cloning in this ticket.

**Q4. Remembering the folder.** Settled as a technical consequence (finding
3): a folder accepted through `path` or cloned is written to the workstation
mapping. Confirm that the mapping being **workstation-wide** (every project of
the workstation then finds this repository there) is acceptable, rather than
attaching it to the one project.

**Q5. Fetch before branching.** When a branch does not exist yet in a
secondary repository, fetch `origin` and create it from the remote default
branch rather than from the local `HEAD`.
- (a) **Recommended:** for every secondary repository, declared ones included,
  since they suffer the same stale base today.
- (b) Only for repositories reached through the new option.

**Q6. The second comment (change only in a secondary repository).** Finding 7
confirms that a ticket without a primary pull request is refused.
- (a) **Recommended:** out of scope here; a separate ticket covers pinning to
  an undeclared repository and a primary repository decided by the agent once
  the change is known, reusing this ticket's lookup.
- (b) In scope of #737.
