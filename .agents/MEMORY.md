# Project Knowledge Base (MEMORY.md)

## Architecture Decisions & Constraints

### 1. Web Server HTTP API Only (No Workstation CLIs)
- **Constraint**: The web server (`cmd/server`, `internal/handlers`, `internal/db`, `internal/trackerapi`) must access remote issue trackers (GitHub) solely via HTTP REST and GraphQL APIs through `tasks/internal/trackerapi.Client`.
- **Enforcement**:
  - Web server packages must never execute `os/exec` or workstation CLI binaries (`gh`, `git`).
  - Runtime boundary tests (`cmd/server/runtime_boundary_test.go`) forbid importing `tasks/internal/runner`, `tasks/internal/workspace`, or `tasks/internal/terminal` from `../server`.

### 2. Pluggable Ticketing System Abstraction
- **Pattern**: All issue operations (`CreateIssue`, `GetIssue`, `UpdateIssue`, `DeleteIssue`, `SyncIssues`, `AddComment`, `GetComments`, `Transition`) are defined in `tasks/internal/tracker.TicketingSystem` (extending `tracker.Writer`).
- **Resolution**:
  - `tasks/internal/tracker.Registry` manages registered adapters (`github`, `local`).
  - `DB` provides `d.TrackerForProject(proj)` and `d.TrackerForTask(task)`.
  - Avoid hardcoded `if tracker == "github" ... else if tracker == "jira"` checks in database operations; always route operations through the resolved `TicketingSystem`.
- **Plugging New Trackers**:
  - Implement `tracker.TicketingSystem` (can embed `tracker.BaseTicketingSystem` to inherit default refusal behavior for unsupported capabilities).
  - Implement `FormatTaskID(projectID, key, rawID string) string` on each tracker to encapsulate canonical task ID formatting (e.g. `gh-<projID>-<num>` for GitHub vs a generated UUID locally). Never hardcode tracker-specific ID prefixing in `internal/db`.
  - Register the adapter in `trackerapi.NewDefaultRegistry` or via `registry.Register(name, adapter)`.
  - Sync routines (`processSyncJob`) dynamically resolve tracker adapters from `d.TrackerRegistry().Get(trackerName)`, allowing any registered tracker with `CapSync` to synchronize without modifying core switch statements.
- **The interface has a read side too** (since #180): `ListBoards`, `ListBoardColumns`, `ListSprints`, `ListStatuses`, `ListIssueTypes`, `ListEpics`, `SearchTeams`, `TeamMembers`, `RequiredCreateFields`, gated by `CapBoard` and the existing `CapSprint` / `CapTeam` / `CapEpic`. `BaseTicketingSystem` answers `ErrUnsupported` for all of them, so adding one costs nothing to the adapters that lack the notion. `internal/db` (`board.go`, `teams.go`) routes every "what is this project made of" question through it and must never test a tracker name for those.

### 2.0 Tracker Credentials Can Be Personal (2026-09-18, #180)
- **Two stores, not one**: the server-wide credential still lives in the single `settings` row (`id = 1`); a personal one lives in `user_tracker_credentials`, keyed by `(user_id, tracker)`. Resolution order for a call: the acting user's own token, else the project override, else the settings, else the environment.
- **The acting user travels in the `context.Context`** (`tracker.WithActingUser` / `tracker.ActingUser`), because every `TicketingSystem` method already takes one. A context naming nobody resolves to the server credential, which is exactly what the background queue does, and deliberately so: the queue carries no owner until #237 lands `task_activities.user_id`. Do not add a user parameter to the adapter signatures.
- **A personal token cannot be hashed**: Sectile *presents* it to Jira, unlike a device token which it *verifies*. `internal/secrets` encrypts it with AES-256-GCM, with the user id and the tracker name as additional authenticated data, so a row moved between users stops decrypting. That AAD binding is the answer to "someone with the database reuses my colleague's token"; removing it silently breaks the guarantee while every test about round trips keeps passing.
- **The key lives outside the database**: `SECTILE_SECRET_KEY`, else a 0600 `secret.key` beside the database file, generated on first open. `NewDB` fails outright when it cannot be read, rather than starting with credentials it cannot open.
- **A sealing passphrase is optional and never stored**, not even hashed. Its key is derived with Argon2id and held in memory for the server's lifetime only. A locked credential answers `ErrCredentialLocked` and the operation **fails**: never fall back to the server token, or a write lands under a name nobody chose (ADR 0014).
- **The identity probe is an exact path match**: `publicPath` used to let anything under `/api/me` bypass the session guard, which would have made personal credentials public. It now matches `/api/me` exactly, and `internal/handlers/auth_test.go` pins the new routes as guarded.

### 2.1 The Jira Cloud Adapter (2026-09-18, #180)
- **Where it lives**: `internal/trackerapi/jira*.go` and `adf.go`, on the shared `trackerapi.Client` (redirect/size guards, per-project credential resolution). It is a port of the client deleted in `e6e16ec` (`internal/runner/jira_rest.go`, `jira_teams.go`), minus every `acli` fallback: the server may not execute a workstation CLI (section 1).
- **Authentication is Basic, not Bearer**: Jira Cloud takes `base64(email:api-token)`. The e-mail is therefore part of the credential — `CheckTrackerCredentials` and `SaveTrackerCredentials` carry an `email` parameter that only the Jira case reads. A project overrides the **site only** (`trackerUrl`); one Atlassian API token is valid on every site of the account.
- **`GET /rest/api/3/search` is gone**: Atlassian removed it in 2025. The only search is `GET /rest/api/3/search/jql`, paginated by `nextPageToken`, not `startAt`. The Agile API (`/rest/agile/1.0/...`) still paginates with `startAt` / `isLast`, hence two separate page walkers on the client.
- **Sprint and Team are custom fields whose ids differ per site**: discovered once through `GET /rest/api/3/field` (schema custom suffix `:gh-sprint`, schema type `team` or `:atlassian-team`, then by display name) and cached per base URL. A site exposing neither still syncs, with both values empty — do not turn that into an error.
- **Team members are not in the Jira API**: they come from the site gateway `GET /gateway/api/v4/teams/{id}/members?siteId=<cloudId>` (cloud id from `/_edge/tenant_info`), then `GET /rest/api/3/user/bulk` for names and avatars. That path is undocumented, so it lives alone in `jira_teams.go` and its failure must degrade to "members unknown" in the activity rather than fail the sync (`afterTrackerSync`).
- **The Team field write is site-dependent**: some instances want the bare team id, others `{"id": …}`. The adapter sends the bare form and retries with the object on refusal. Do not "simplify" that to one form.
- **Stage vs status**: labels carry the workflow stage, a transition runs only on close or on an explicit target status, and the closing transition is picked by status **category** (`done`), never by the transition's own (localised) name. See ADR 0013.
- **Bodies are ADF, not Markdown**: `adf.go` converts both ways for a bounded subset. Sending a Markdown string where Jira expects a document is refused, and sending it as one paragraph makes every skill report unreadable.
- **`cleanJiraKey` matches a key pattern, it does not strip a prefix**: `JIRA-101` is a legitimate Jira key whose project key happens to be `JIRA`. Recognise `^[A-Z][A-Z0-9_]*-[0-9]+$` first, and only then read the last two segments of a local `jira-<projectID>-<KEY>` identity. Stripping a `jira-` prefix corrupts that key, which `internal/db/pins_test.go` catches.

### 3. Project Settings Are Runtime State, Not Repository Artifacts
- **Constraint**: Per-project settings exposed on `models.Project` (`specFramework`, `prCreationStage`, `aiProvider`, `issueTracker`, ...) live **only** in the Sectile SQLite database. No repository file carries them: not `.taskflow/agent.json` (which stores the agent-side project/path mapping and provider defaults), not `AGENTS.md`, not a committed seed.
- **Consequence**: A ticket asking to correct such a setting is a **data fix with no diff and therefore no pull request**. Do not scaffold a specification or invent a code change to satisfy a PR-shaped workflow; report the absence of a deliverable instead. Ticket #117 (`specFramework: speckit -> openspec`) is the reference case.
- **How to read and mutate**:
  - `GET /api/projects` and `GET /api/projects/{id}` return the stored values.
  - `PUT`/`PATCH /api/projects/{id}` decodes `models.UpdateProjectRequest`, whose fields are pointers, so a partial payload such as `{"specFramework":"openspec"}` updates that single field and leaves the rest untouched.
- **Resolution order for the SDD framework** (`db.resolveSpecFrameworkTarget`): explicit request field, then the project setting, then global settings, then `models.NormalizeSpecFramework` — which falls back to `speckit` for empty or unknown values. Repository layout is **never** consulted, so the configured framework can silently disagree with the repository's actual `openspec/` or `.specify/` tree.

### 4. MCP Session Ownership (ADR 0007)
- **Constraint**: `/mcp` is served **statefully** (`mcp.StreamableHTTPOptions{JSONResponse: true, SessionTimeout: ...}` in `internal/handlers/agent_api.go`). Do not restore `Stateless: true`: a stateless endpoint builds a throwaway session per request, so the server can neither tell two clients apart nor observe a disconnection, which is what closes abandoned runs.
- **Ownership rule**: a run created by `start_run` is adopted by the calling session (`taskmcp.SessionRegistry`) and closed as `canceled` when that session ends. A run **reused** through `runId`/`SECTILE_RUN_ID` is deliberately **not** adopted — it belongs to the dispatching agent, whose supervisor reports the real process exit (see ADR 0006). Adopting it would cancel an execution that is still running.
- **Non-obvious SDK behaviour** (`modelcontextprotocol/go-sdk` v1.7.0):
  - `StreamableHTTPOptions.SessionTimeout` counts idle time, and **only POST requests reset it** (`sessionInfo.startPOST`). A long-lived GET/SSE stream does not. Clients that must stay connected have to ping; the stdio bridge sets `ClientOptions.KeepAlive` for exactly that reason.
  - Session lifecycle hooks: `ServerOptions.InitializedHandler` gives the start, `ServerSession.Wait()` blocks until the end (client `DELETE`, dropped connection, or idle timeout), and `ServerSession.ID()` is the `Mcp-Session-Id`.
- **Closure status**: the `finish_run` contract accepts only `completed`, `failed` and `canceled`, so a disconnection closes with `canceled` plus an explanatory note rather than a new status value.
- **Restart**: a restart destroys every session, so `NewDB` closes `remote_run` activities whose `action != db.RunActionAgent` (`internal/db/db.go`, next to the rule that fails interrupted server jobs). The action field is the persisted owner marker — `db.RunActionClient` vs `db.RunActionAgent` — and is the only thing a restart can rely on, since sessions live in memory. Do not widen that cleanup to agent-owned runs: their supervisor reconnects and reports the real exit (ADR 0006).

### 5. Linear, `projectType` and the Daily Digest Removal (2026-09-16)
- **Decision**: Linear was removed end to end: web UI, `internal/trackerapi/linear.go`, the registry entry, the runner's `linear` CLI calls and the `/api/sync/linear` route. The supported trackers are now `github`, `jira` and `local` — `jira` being metadata-only until #180 gave it a real adapter (section 2.1).
- **Decision**: `models.Project.ProjectType` ("standard" / "personal") was removed with its `NormalizeProjectType` helper.
- **Decision**: the daily digest was removed entirely: `internal/db/digest.go`, the `/api/projects/{id}/daily-digest` routes, the `DailyDigest*` models, `settings.prompt_digest_agenda` and the web `DigestView`. The generic `run_prompt` agent operation stays: it is part of the server-agent v1 contract and is no longer digest-specific.
- **Retired storage is actually dropped**: `db.dropRetiredColumns` runs on every open and removes `projects.linear_team`, `projects.project_type`, `settings.linear_team`, `settings.prompt_digest_agenda` and the `daily_digests` table. The statements are idempotent by failure, like the `ADD COLUMN` migrations above: on a database created after the removal SQLite refuses the `ALTER` and the error is deliberately ignored. `internal/db/retiredstorage_test.go` rebuilds the legacy shape and asserts nothing survives a reopen.
- **Trap to avoid**: the `INSERT`/`SELECT`/`UPDATE` on `projects` and `settings` list their columns explicitly, and their `VALUES (...)` placeholder count must be updated in the same edit. Removing a column name without removing its `?` yields `SQL logic error: N values for M columns` at runtime, which only the DB tests catch.
- **Where the parallelism slider ended up**: this branch first put a 1-10 slider in the project settings. `main` then made parallelism workstation-only, removing the project field entirely, so the slider moved to the desktop project dialog (`desktop/src/main.js`) and `agentconfig.MaxParallelism` went from 5 to 10. A segmented control was dropped there for a reason: ten buttons do not fit the dialog, and the value is a magnitude rather than a set of named choices. The project-level workflow settings `main` added at the same time (`defaultSkillMode`, `fullChainStopStage`) live in the new **Agentic workflow** tab, beside Create PR/MR.

### 6. Sectile Writes `~/.claude/settings.json` (2026-09-17, #174)
- **Change of nature**: until #174 Sectile only ever **read** that file, in `checkExternalMCPPolicies` (`internal/agentconfig/mcp_migration.go`). It now **writes** it, to register the hook script it installs under `~/.claude/hooks` (`sectile-hook.sh`, on `Notification`, `Stop`, `UserPromptSubmit`, `PreToolUse` and `PostToolUse`). Any future change there must keep the merge rules: read, decode, touch only the Sectile-owned entries, preserve every other key and third-party hook, rewrite atomically, and leave an unparseable file exactly as it is with the failure reported instead of aborting the setup (`internal/agentconfig/hooks.go`).
- **Ownership marker**: a registration is recognised as Sectile's by the script file name (`sectileHookFile`: the current `sectile-hook.sh` or a retired `sectile-notification.sh` / `sectile-stop.sh`), not by the full command path, so a workstation whose home directory moved is updated in place rather than gaining a second, dead entry. Renaming the script means adding the old name to `retiredClaudeHookFiles`, otherwise an existing manifest is rejected as foreign (`anyManagedPath`) and the old registration stays behind as a hook error on every turn.
- **The wait must be closed by the hooks, not assumed**: Claude Code has no "resumed" event. `Stop` means the agent awaits the next prompt (a wait, not a resume), `idle_prompt` only arrives 60 s after the turn ends, and `Notification` fires for sign-ins and quota notices too. The working state comes from `UserPromptSubmit`, `PreToolUse` and `PostToolUse`; `PreToolUse` fires *before* the permission prompt of the same tool, `PostToolUse` after it ran. An autonomous (headless) run must never be marked waiting: its `Stop` fires as the process exits and would flash a false banner. See ADR 0012, revision.
- **Executable bit**: `Scaffold` writes every managed file 0600 through `atomicWrite`. That is right for a skill and useless for a script Claude Code has to run, so `executableHooks` chmods the hook paths 0700 after `refresh`. A hook Claude cannot execute fails silently, with no error anywhere.
- **`SECTILE_AGENT_URL` is the server, not the loopback**: the launched-session environment sets `SECTILE_AGENT_URL` and `SECTILE_SERVER_URL` to `d.link.serverURL`, while some tests and the MCP bridge use the loopback for the same name. #174 added `SECTILE_LOOPBACK_URL` rather than overloading the existing one. A hook that must reach the local agent uses `SECTILE_LOOPBACK_URL`.
- **`waiting_since` joins the explicit column lists**: `task_activities` is read by four separate queries (`insertTaskActivity`, `getTaskActivitiesUnsafe`, `getActivityByIDUnsafe`, and the two in `GetActivities`/`GetActivityByID`). All of them name their columns, so a new column means five edits plus the `ALTER TABLE` — the same trap recorded in section 5 for `projects` and `settings`.

### 7. Remote Run Activities: `skill_id` Is the Record Kind, Not the Skill (2026-09-17)
- **Quirk**: every remote execution is a `task_activities` row with `skill_id = 'remote_run'`; the launched skill (`implement`, `specify`, ...) is stored in `skill_name` (`internal/db/remoterun.go`). The `FinishRemoteRun` and reuse checks key on `skill_id='remote_run'`.
- **Trap**: any consumer that wants "which skill ran" must read `SkillName`. The desktop `run-result` handler (`internal/agent/agent_desktop.go`) once forwarded `SkillID`, so the renderer's `activity.skillId === run.skill` match never succeeded and every finished console showed **Execution ended · skill completion unconfirmed** even after a successful `finish_run`. Fixtures in tests must mirror the real shape (`SkillID: "remote_run", SkillName: "<skill>"`), otherwise the mismatch is invisible.
