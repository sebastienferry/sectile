## Execution and ticket state
- **Stage label**: the stage of a ticket is one Jira label, `sectile:clarified`, `sectile:specified`, `sectile:implemented`, `sectile:reviewed` or `sectile:finished`; no such label means `new`. The Sectile board reads these labels. A ticket carries at most one: setting a stage removes the previous `sectile:` label in the same edit and leaves every other label as it is. Never change the Jira status, which belongs to the team's workflow.
{{if .FromStage}}- **Recording a stage**: after verifying each completed step, edit the issue's labels to the new stage, then post the stage report as one Jira comment headed `Sectile · <stage>`, carrying the structured report, the actual branch and, when there is one, the pull request URL. Read the issue back to check the label. If the label edit is refused, post the comment anyway, say the label is pending and give it for the owner to apply; never claim a stage the ticket does not show.
{{if or (eq .ID "pickup") (eq .ID "pickup_issues")}}Record clarified, specified and implemented after each corresponding step. After PR verification, record reviewed with the PR URL. For a batch, give every completed ticket the same actual branch and combined PR URL; never mark unfinished work reviewed.
{{else if eq .ID "clarify"}}Move new → clarified only when the exit condition is met: the owner confirms the clarification is satisfactory (or zero product questions remain open in unattended pickup). Never move new → clarified while any product question or decision remains open.
{{else}}Move {{.FromStage}} → {{.ToStage}} only when this step is complete.
{{if eq .ID "adjust"}}The stage comment carries the verified pull request URL, and the pull request of every other repository the task changed.
{{end}}{{end}}- **Pull requests**: link each pull request from the Jira issue (a remote link), once per repository, and repeat its URL in every later stage comment. A task whose work changed no repository has no pull request to give: the stage comment says what was done instead.
- Intermediate discussion, such as a clarification round with open questions, is a plain Jira comment, never a stage comment.
{{end}}- Reuse the assigned worktree and actual branch. Never merge or delete remote objects. Keep work available for review and retry until confirmed handoff.
