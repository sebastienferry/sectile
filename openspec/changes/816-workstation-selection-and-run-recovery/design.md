# Design

## Evidence and architecture
The repository uses Go handlers and database-backed task activities, a distributed AgentDispatcher, and React AppContext launch helpers. `agent_inventory.go` already derives availableWorkstations from the caller's live sessions and explicitly reported project inventory. `task_selection.go`, merged through #815/#819, already validates task routes against reported inventory, pins explicit targets/reconnects, and retains successful-launch affinity for callers without a target. Generic SelectRoute remains for unrelated commands. Activity deviceId persistence and the targetDeviceId compatibility alias already exist. `identity.go` provides DeviceCredential.Label. `remote_run.go` handles running remote-run cancellation, while the activities cancel handler otherwise calls DB.CancelActivity; these paths must share remote stop semantics. `idx_activities_one_active_run` protects queued/pending/running records across instances.

## Selection and request contract
1. Resolve the execution project before choosing a workstation, reusing boardRunProject and RunProjectPicker. When the project changes, discard the previous selection. Consult the existing agent status endpoint with projectId; extend each availableWorkstations item with `label` (paired credential label trimmed, falling back to deviceId). Never expose credential hashes or tokens.
2. Add optional `deviceId` to AppContext runSkill options and request bodies. Introduce one promise-based Web picker following RunProjectPicker so every task entry point passes through the same preparation logic. Zero candidates refuses locally; one sends its ID automatically; multiple require an accessible explicit choice. Canceling the dialog sends no launch request. Do not persist a preference.
3. Extend activity retry requests with optional deviceId and run the same preparation for agent executions. Retry creates a new run on the chosen device; reconnect of an existing run stays on its original device. Resolve a legacy activity's execution project before eligibility lookup.
4. At admission and immediately before dispatch, validate the authenticated owner's exact selected device against live reported inventory for the resolved project. Web always sends an explicit deviceId after its zero/one/many preparation; keep #815's affinity and newest-eligible defaults for non-Web clients that omit a target. Retain its alias normalization (conflicting deviceId/targetDeviceId returns 400), invalid explicit-target errors (400), unavailable automatic-target errors (428), and busy conflicts (409). No work record is created for admission refusal. If a device becomes unavailable after admission, fail the undispatched launch through the existing terminal/handback path, release the busy guard and never dispatch it elsewhere. Reuse selectTaskLaunchRoute/taskRoutes and their receiving-replica inventory checks; keep generic terminal/PTY routes compatible. Do not introduce a second eligibility definition. A refreshed picker must not silently preselect an old affinity when several candidates exist, and choosing a different device does not copy the previous workstation's worktree.
5. For pickup_issues batches, derive every task's execution project using existing project/batch rules, then intersect eligible device IDs. Verify all members and the chosen device on the server before recording/dispatching the batch. If any member cannot resolve its project, preserve the existing project refusal before opening the workstation picker. Excluded macros continue through their existing path.

## Persistent attribution
Reuse existing activity `deviceId`/device_id and add an empty-default `deviceLabel`/device_label snapshot in Go models, a new database migration and all activity read/write paths, mirrored in Web TaskActivity. Do not recreate the device_id migration from #815. Store the selected device and resolved label at admission and carry them to the adopted remote run, batch membership display, retries and reconnect synchronization. Do not infer attribution from summary text. Identity is scoped to run.UserID; an admin canceling a run still targets that owner's device.

Snapshot the label at assignment so credential renaming/removal does not erase history. Reconnect cannot overwrite a recorded different device; agent-reported legacy runs can fill absent attribution from an authenticated connection, never from an arbitrary client-supplied label. Older rows without trustworthy attribution show the existing run information without fabricating a workstation. Known device with absent label uses the ID. Current availability is derived from owner/device live presence independently of the snapshot, and is shown as unavailable only for active runs; a finished historical run is not relabeled offline.

Target persistence: internal/models/models.go, internal/db/db.go and migration/read/write helpers, run adoption/synchronization in handlers.go and dispatcher ownership restoration. Migration must support both SQLite and PostgreSQL and preserve existing rows and the active index. Broadcast existing activity-change events after assignment and recovery; reload must retain the label.

## Cancellation and races
Unify `POST /api/activities/{id}/cancel` and `/api/tasks/{id}/cancel-run` around a shared execution cancellation service. Activity cancellation accepts an optional `{force: true}` body; an empty body remains compatible. The task endpoint retains `{runId, force}`. Validate the full activity/task relationship and owner/admin permission before any queue, process or database mutation. Terminal/stale IDs return conflict without changing another run.

Queued/pending work proven not dispatched is removed from the queue and atomically terminalized as canceled before a worker can claim it. Cancellation racing admission/dispatch must share the claim/terminal-state guard: if dispatch may have occurred, use remote stopping semantics rather than claiming no process exists. Batch cancellation acts on the batch execution and releases all members using existing batch lifecycle rules.

For an agent-owned execution, route stop to the persisted owner/device (restore dispatcher ownership after restart), retaining the current bounded cancel protocol. A positive stop acknowledgement permits canceled status. Complete authoritative non-ownership evidence permits orphan closure; a reply from another device, absence, timeout or transport failure alone does not. Reconnect reconciliation may automatically close a proven orphan through the same terminalization service, but must retain unknown runs. Never introduce an expiry timer.

An unconfirmed stop leaves the active record intact and returns the existing actionable error. Both task and activity surfaces then offer a separate force-close confirmation that explicitly says the local process may continue. Authorization applies again server-side even to force. Force terminalizes bookkeeping as canceled with a distinct truthful note, without a fabricated process-stop acknowledgement. An ordinary client-owned MCP run continues through closeClientRun/FinishRemoteRunAs and session release; server-owned activities retain their registered job cancellation.

Use the existing FinishRemoteRun/FinishRemoteRunAs and completion result validation/handback mechanisms, extended for queued/pending where needed. A terminal run is never resurrected by late agent status or reconnect, and a late completion is processed only by the existing authenticated completion contract; it cannot overwrite a newer run, bypass checks, or advance the workflow solely because the old record was force-closed. Preserve legitimate existing late-report behavior for client-owned runs. Cancellation and completion racing each other leave one coherent terminal outcome and no lock held. This ticket does not change recovery-time workflow stages.

## UI and target files
AppContext.tsx centralizes discovery, selection and retries; RunProjectPicker.tsx provides the interaction pattern; BatchPickupModal.tsx shares batch selection. Add a small WorkstationPicker and pure eligibility/display helpers. TaskCard.tsx and TaskDetailModal.tsx display workstation attribution near run state; ActivitiesView.tsx shows it alongside the activity summary and provides pending as well as queued/running cancel controls. RemoteRunBadge.tsx and remoteRunIndicator.ts share recovery permissions/state with the explicit detail/activity actions. Duplicate labels are disambiguated with device IDs; controls work with keyboard and accessible labels. Use existing locale catalogs and preserve each surface's locale. Do not translate neighboring text incidentally.

## Rejected alternatives
- A new request selector contract: Web uses accepted deviceId and preserves the targetDeviceId alias already merged through #815, without adding or removing aliases.
- Browser-only validation or generic project affinity: permits stale or unknown inventory targets and inconsistent batches.
- Summary parsing or in-memory-only device ownership: loses attribution and cancellation targeting after restart.
- Closing on transport timeout, clearing the unique index, or redirecting to another workstation: violates accepted recovery/selection guarantees.
- Generic DB.CancelActivity for remote executions: marks stopped without reaching the process or checking its owner.

## Validation
Extend agent inventory/device selection tests, remote_run_test.go, activity cancellation/ownership tests, migration/persistence tests and batch tests. Use real restart/migration databases as required by docs/TESTING.md. Browser tests should follow run-project-picker.browser.mjs and batch pickup fixtures, asserting actual requests, rendered attribution and recovery behavior. Run OpenSpec strict validation now; implementation runs the repository Go/web checks and relevant browser suites. No new child process launcher is needed; any introduced command must obey agentexec.Hidden and its Windows test convention.
